### 2026-08-24 (continued) — a second AI on #30/#31 caught two real gaps; both chased down

Filed and landed `fix/1-bug-key-set-seek-declines-when-probe-is-join.md` (now

reachable from plain SQL, fixed in the same pass with regression tests. All green,
10248 passing. Replied on #30 with the real mechanism and a heads-up about the bonus fix.

**#31 — root cause found, real design gap, correctly left in backlog.** Reproducing
`MIN(date) FROM entry WHERE entity_id = ?` against a real store-backed table (not the
in-memory reference provider) found the actual mechanism: `IndexedDBProvider` declares an
honest, measured `pointRead = 3.0` cost, and the store module's index-vs-scan cost
comparison is blind to the fact a `MIN`/`MAX` boundary read only needs one row — it prices
the walk as if every matching row were wanted. At `pointRead = 1.0` (the in-memory
reference) the index wins up to ~77% selectivity, which is why this was never caught
in-tree; at `pointRead = 3.0` it only wins up to ~30%, and any `entity_id` more common than
that declines the index and full-scans. Not a new bug — an existing unlanded ticket,
`backlog/feat-sort-absorb-blind-to-limit`, already described this exact gap and predates
the release; updated it with this evidence, tying it directly to the live regression
rather than leaving it as a theoretical someday-ticket. **Left in backlog, not promoted** —
its own `tradeoffs:` names two real fix routes (teach the cost comparison to look upward
through the Sort for a LIMIT, or add a fused sort+limit plan node) and picking between them
is a design call, not a bounded fix. Replied on #31 with the honest mechanism, correcting
the previous comment's implication that ascending `MIN` already works on this backend.
