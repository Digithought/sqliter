----
description: Several places in the SQL parser check for a plain word using a narrow test that a handful of ordinary words (like "on") silently fail, so those words get rejected with a confusing error even though the grammar was designed to allow them there.
files: packages/quereus/src/parser/parser.ts (all `this.check(TokenType.IDENTIFIER)` call sites — currently ~18 — plus the single-argument `this.consumeIdentifier(<message>)` call sites), packages/quereus/src/parser/lexer.ts (KEYWORDS, CONTEXTUAL_KEYWORDS)
tradeoffs: auditing every one of the ~18 sites is a mechanical but non-trivial time sink, and most of them are probably fine (positions where a keyword genuinely shouldn't be a value); a maintainer might reasonably defer this until another instance actually surfaces, rather than pre-emptively auditing a class that's mostly benign.
----

`pragma-on-off-value-parsing` fixed one instance: `nameValueItem` in `parser.ts` used a bare `this.check(TokenType.IDENTIFIER)` to decide whether the next token could serve as a value, instead of the existing `consumeIdentifier(CONTEXTUAL_KEYWORDS, …)` mechanism that exists precisely so common words that happen to be reserved (`on`, `key`, `default`, `check`, `unique`, `references`, `cascade`, `restrict`, `like`, `set`, `action`) can still be used as identifiers/values in positions where the grammar doesn't need them as keywords.

`grep -n "check(TokenType\.IDENTIFIER)" packages/quereus/src/parser/parser.ts` currently finds ~18 call sites. Not all are bugs — many are positions where only a true identifier makes sense and a contextual keyword genuinely shouldn't be accepted. But `nameValueItem` shows the bug is real when it does occur, and the failure mode is specifically nasty: it doesn't just reject the input, it prints a misleading, unrelated hint ("'ON' must follow a JOIN") from the generic error-hinting logic in `error()`, which makes the actual problem harder to diagnose from the message alone.

## Scope

1. Walk the `this.check(TokenType.IDENTIFIER)` call sites in `parser.ts` (and any equivalent pattern elsewhere in the parser) and classify each as: (a) correctly identifier-only, (b) should also accept `CONTEXTUAL_KEYWORDS` tokens like `nameValueItem` did, or (c) should accept the full keyword set as a bareword (name-position lenience).
2. For each (b)/(c) site, apply the same fix pattern as `pragma-on-off-value-parsing`.
3. Second arm, same root cause, different spelling: the **single-argument** `this.consumeIdentifier(<message>)` overload passes an empty keyword list, so every site using it is as narrow as a bare `check(TokenType.IDENTIFIER)`. `nameValueItem`'s own *name* position (`parser.ts` ~line 4164) is one of them — after the pragma fix, `name = on` parses but `on = 1` (a virtual-table module argument named with a contextual keyword) still does not. Audit these sites the same way; the asymmetry inside a single function is the clearest evidence the narrow spelling is easy to reach for by accident.
4. Consider a rung-1 fix per the ticket workflow's "Architecture first" ladder. Note the check-side helper the original ticket proposed (`checkIdentifierOrContextualKeyword`) already exists as `checkIdentifierLike(keywords)` — the gap is not a missing helper but that the narrow spellings (`check(TokenType.IDENTIFIER)`, single-arg `consumeIdentifier`) remain easier to write than the correct ones. Options: require the keyword-list argument explicitly (drop the single-arg overload so each site states its intent), or add a lint rule against the bare `check(TokenType.IDENTIFIER)` spelling inside `parser.ts`.
5. Add or extend a grammar/property test (see `test/property.spec.ts` "Parser Robustness" fuzzing) that feeds `CONTEXTUAL_KEYWORDS` words into name/value positions across statement kinds, so a regression fails a general test rather than requiring a bug report per keyword per position.

## Edge cases & interactions

- The generic `error()` hint logic (`parser.ts` ~line 2282) that appends "'ON' must follow a JOIN" for any un-consumed `ON` lexeme — worth checking whether other contextual keywords have similarly misleading generic hints that would mask a real fix-site elsewhere.
- Case sensitivity — `KEYWORDS` lookups lowercase first; `consumeIdentifierOrContextualKeyword` returns a keyword token's raw `lexeme` (case preserved, matching identifier behavior). Confirm any generalized helper keeps that.
- `runtime/emit/pragma.ts` wraps a rejected pragma *value* into an `Unknown pragma: <name>` error, which mis-labels a value problem as an unknown-name problem (`pragma foreign_keys = key` reports the wrong thing). Pre-existing and separate from the parser audit, but it is the message a user hits once the parser starts accepting these barewords — worth fixing in the same pass.
