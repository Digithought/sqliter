# What landed

**Tests** — `packages/quereus/test/bench-comparison.spec.ts` gained 18 tests, all pure
over hand-built plain objects (no benchmark actually runs), matching the file's existing
style:

- `describe('flattenCounters', ...)` — 5 tests: a full `WorkCounterSnapshot` flattens
  across `plan`/`instructions`/`tables`/`totals`; an instruction inserted at the front of
  the `instructions` array is addressed by its `key` and reports exactly one added path
  (`instructions.r#new.executions`) rather than shifting every later instruction's path;
  a bare `PlanShape` and a named bag of two snapshots (`firstBatch`/`lastBatch`, the
  `mutation.bench.mjs` shape) both flatten with no special-casing; an explicit
  `nodeType: undefined` is skipped rather than recorded, and the flattened result is
  identical before and after a `JSON.parse(JSON.stringify(...))` round-trip.
- `describe('diffCounters', ...)` — 4 tests: a difference of one is reported with no
  tolerance; changes come back sorted by path; a path present on only one side is
  reported with `null` on the other, in both directions; two identical blocks produce an
  empty change list.
- `describe('counter verdict', ...)` inside the existing `describe('compareRun', ...)` —
  9 tests covering every `CounterStatus` the JSDoc in `compare.mjs` documents: `same`,
  `changed` (with the exact diff), `new` (baseline has no counters — distinct from
  `changed`), `dropped` (this run has none, baseline did), `none` (neither side has one),
  `skipped` (`{ counters: false }`, i.e. `--no-counters`), and that a `--filter`-excluded
  or failed benchmark carries `none` rather than a diff. A final test confirms a
  `changed` counter status never sets `gated` and is never counted in `regressions` —
  reporting only, no gate, per the file's own comment on that behavior.

All 18 pass (`node test-runner.mjs --grep "flattenCounters|diffCounters|counter verdict"`),
as does the full `yarn test` (736 passing in `@quereus/quereus`, 0 failing anywhere in the
monorepo) and `yarn lint` (which type-checks the spec file too).

**Docs** — `docs/benchmarking.md` gained a "Work counters: exact-count comparison"
section, placed after "Outcomes that are not deltas" and before "Ratio guards" (both are
portable, machine-independent measures — counters and ratios sit together in the
document's flow). It covers, in order:

1. What a work counter is and the one-sentence reason it shares no column with a timing
   delta (a timing delta claims "might be slower" and needs a noise floor; a counter
   delta claims "does different work" and is an exact integer, needing none).
2. How to add a `counters()` pass, with a `snapshotStatement` example, and that it runs
   once, after the timed loop, before `teardown` — never inside `fn`.
3. The drain requirement, by reference to the existing bullet under "Adding a benchmark"
   rather than restated.
4. Which suites qualify, as a table: `execution` 15/15 and `mutation` 4/4 (both run a
   statement to completion), `planner` 4/4 (`snapshotPlanShape` only — these never
   execute), `parser` 0/4 (nothing to count). Pulled from the stability check landed in
   `bench-counter-suite-passes` (`tickets/complete/2.21-bench-counter-suite-passes.md`),
   not re-derived.
5. `--no-counters` and the `counters_collected` field, and how it distinguishes a
   `--no-counters` run from a suite that simply declares no `counters()` pass on some
   benchmarks.
6. The `Counters` table column, the `COUNTER_CHANGES_SHOWN` (12) per-benchmark cap on
   printed diff lines, and that the full list is always in the results JSON's
   `comparison` block.

`bench/lib/counters.mjs` was added to the "Where the code lives" table.
