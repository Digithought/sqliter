# What landed

Three independent bits of shared plumbing that the two micro-benchmark tickets
(`bench-store-micro-keys`, `bench-store-micro-paths`) depend on. Nothing here is benchmark
content — it is API surface, a test double, and one doc section.

## 1. `ROW_RESOLUTION_BATCH` is now a public export of `@quereus/store`

One additive line in `packages/quereus-store/src/common/index.ts` re-exporting the constant
from `store-table-scan.ts`, with a comment saying why it is public: a caller that must
derive an expected round-trip count reads the constant instead of restating `256`.

No import cycle — `store-table-scan.ts` imports only sibling modules (`kv-store`,
`encoding`, `bytes`, `key-builder`, `serialization`, `pk-key-resolution`,
`store-table-base`), never `common/index.js`.

## 2. The benchmark harness's single door into `@quereus/store` is wider

`packages/quereus/bench/lib/store-counters.mjs` still holds exactly ONE dynamic import of
the store package (the reason for that is in its file header and unchanged). What it
resolves through that import grew from three names to ten:

- unchanged: `createIsolatedStoreModule`, `createInMemoryProvider`, `createCountingProvider`
- new: `encodeValue`, `encodeCompositeKey`, `decodeCompositeKey`, `buildDataKey`,
  `buildIndexKey`, `BUILTIN_KEY_NORMALIZER_RESOLVER`, `ROW_RESOLUTION_BATCH`

The "a name this file needs that the package no longer has" check is kept and generalized:
every resolved name must be a function, except names listed in a new `NUMERIC_EXPORTS` set
(today just `ROW_RESOLUTION_BATCH`), which must be numbers. A missing constant would
otherwise arrive as `undefined` and silently size a benchmark to `NaN`; now it reaches
`storeLoadFailure` and becomes a stated skip reason.

New export `loadStoreKeyApi()` hands the seven key/encoding names to a suite, so a suite
never needs its own `import('@quereus/store')`.

`openStoreDatabase()` now returns `{ db, close, provider }` — additive. The counting handle
is unchanged (it already has `resetCounters` / `readCounters`).

## 3. `CountingKVStore` counts writes

Four new counters alongside the four read ones:

| Field | Means |
| --- | --- |
| `directPutCount` | puts issued one at a time, outside any batch |
| `directDeleteCount` | deletes issued one at a time, outside any batch |
| `batchWriteCalls` | `WriteBatch.write()` calls — the write-side round-trip count |
| `batchOpCount` | put/delete operations those `write()` calls carried |

`reset()` zeroes all eight.

The structural part: `DelegatingKVStore.batch()` hands back the INNER store's batch, whose
`put`/`delete`/`write` never pass through the wrapper. So `CountingKVStore` overrides
`batch()` to return a new module-private `CountingWriteBatch`. Its counting rule —
**operations are attributed to the `write()` that carried them, not to the moment they were
queued** — means a batch that is queued and then `clear()`ed, or abandoned without writing,
contributes nothing. The hand-off happens before awaiting the inner write, so a commit that
throws still counts as a round trip issued.

`readStoreCounters` in the bench harness surfaces the four as `directPuts`,
`directDeletes`, `batchWrites`, `batchOps`. No derivation on the write side (direct and
batched are disjoint paths) — unlike `singleGets`, which stays derived.

## The new spec

`packages/quereus-store/test/counting-store-writes.spec.ts`, 11 tests in two blocks:

- **unit** — a point put counts as a direct put and as zero batch traffic; a point delete
  likewise; a batch of three ops committed once is `batchWriteCalls === 1` /
  `batchOpCount === 3` and zero direct writes; an empty commit is a round trip carrying
  nothing; `clear()` drops queued ops rather than attributing them to the next commit; two
  batches are two round trips; writing advances no read counter; `reset()` zeroes all eight.
  Each write assertion is paired with a `get` proving the write actually reached the inner
  store — a counter that counts but does not forward would otherwise pass.
- **through `StoreModule`** — `begin` / multi-row `insert` / `commit` gives
  `batchWriteCalls === 1` and `batchOpCount === <row count>` on the data store, at 4 rows
  and again at 50. This is the flat-commit claim the micro suite's commit benchmark rests
  on.

## Real numbers from the bench run (evidence the counters mean something)

`mutation/bulk-insert-10k@store-mem`, data store: `singleGets: 30000`, `batchWrites: 20`,
`batchOps: 10000` — three reads per row provoked, and the writes committed in 20 round
trips carrying 10 000 operations. `single-row-insert-1k`: `batchWrites: 1000`,
`batchOps: 1000` — one round trip per row, which is exactly the shape the write counters
exist to distinguish from the batched case. `__stats__` shows `directPuts` (stats are point
writes), `delete-where-100` shows `batchOps: 100` with `directDeletes: 0` (deletes commit
batched).

# Known gaps and things a reviewer should push on

- **One-time report noise, not a regression.** Every `@store-mem` row's counter block gained
  four fields. Comparing a run made now against a `bench/results/` file written before this
  change reports the new paths as appeared-path counter changes on all nineteen store rows.
  Counter deltas never contribute to the exit code (docs/benchmarking.md § Exit-code
  contract) and `bench/results/` is gitignored.
- **`batchWrites` is a fact about the in-memory counting provider, not about LevelDB.**
  `createCountingProvider` exposes no `beginAtomicBatch`, so the transaction coordinator
  takes its per-store fallback (one `WriteBatch` per touched store). A provider with a
  shared commit domain commits the same transaction as ONE cross-store atomic write, and
  `batchWrites` would not describe it. Stated in both the harness file header and
  docs/benchmarking.md; worth checking those wordings are strong enough.
- **`AtomicBatch` is not counted at all.** `CountingKVStore` wraps `WriteBatch` only. Today
  nothing counted uses the atomic path (the counting provider has no `beginAtomicBatch`), so
  this is dormant rather than wrong. If someone later gives the counting provider a shared
  commit domain, the commit would silently report zero writes. Left as-is deliberately
  rather than building an `AtomicBatch` wrapper nothing exercises. **NOTE parked?** No — the
  gap lives in the harness header and this handoff, not in a code comment; a reviewer may
  reasonably ask for a `NOTE:` at `CountingKVStore.batch()` instead. Flagging rather than
  deciding.
- **Counter-zeroing call sites: I converted more than the ticket asked.** The ticket named
  `test/key-set-seek-store.spec.ts` only; I also converted the nine direct-assignment sites
  in `packages/quereus-store/test/pushdown.spec.ts` to `store.reset()`. Two of those
  (pushdown ~1499, ~1522) asserted on `getManyCalls`/`getManyKeyCount` while zeroing only
  `iterateEntryCount`/`getCount` — they happened to pass because seeding issues no
  `getMany`, which is a latent trap, not a design. Worth a reviewer confirming none of those
  conversions weakened or strengthened an assertion in a way that matters; all still pass.
  `test/unique-constraints.spec.ts:55` is a class FIELD DECLARATION on an unrelated double,
  not a zeroing site — deliberately untouched.
- **`loadStoreKeyApi` has no caller yet.** It exists for the two downstream micro tickets.
  Its names are shape-checked at import (so a rename in the store package surfaces as a
  stated skip reason rather than a mid-benchmark throw), but nothing exercises the returned
  functions. That coverage arrives with the suites that use them.
- **The three read-counter specs were not touched in substance.**
  `test/index-scan-batching.spec.ts` untouched entirely; `test/bounded-iterate.spec.ts`
  untouched; `test/key-set-seek-store.spec.ts` changed only at the zeroing site. All pass.
- **`packages/quereus/test/bench-store-counters.spec.ts` grew two tests** and its existing
  deep-equals gained the four write fields. A reviewer should check the shared `NO_WRITES`
  spread does not hide a field that should have been asserted non-zero.
