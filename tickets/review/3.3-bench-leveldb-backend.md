# What this is

`yarn bench` used to measure only in-memory storage. It can now also run every
`execution` and `mutation` workload against **LevelDB on a real temporary directory** —
the storage a Node deployment actually uses. Those rows are opt-in, and their numbers are
**advisory**: printed, recorded, compared against a baseline, and never allowed to fail a
build, because a timing dominated by the machine's disk is not a property of this
repository's code.

```bash
yarn workspace @quereus/quereus bench:leveldb                       # every suite, disk rows included
QUEREUS_BENCH_LEVELDB=1 yarn workspace @quereus/quereus bench --filter @store-leveldb
yarn workspace @quereus/quereus bench                               # disk rows print a skip reason
```

The plumbing (temp directories, the lazy plugin import, the `informational` flag end to
end) landed in a prior run and was already committed. **This run did the measurement,
the verification, the `BACKENDS` decision and the documentation** — plus one lint fix and
new unit coverage, both described below.

# The decision the prior run deferred

`STORE_LEVELDB_BACKEND` **is now in `BACKENDS`**, so all 19 workloads fan out over it.
That was a measurement, not a preference. Machine: AMD Ryzen AI 9 HX 370, NVMe, Windows
11, node 24.2 — treat every absolute number below as that machine's.

| | measured |
| --- | --- |
| the 19-row `@store-leveldb` arm, opted in | **84.3 s** |
| the same 19 rows *skipping*, on a default run | **9.2 s** of a **163.2 s** / 90-benchmark run (~6%) |
| slowest single row, `mutation/delete-where-100@store-leveldb` | 1.95 s median → ~14 s wall, vs the 120 s `BENCH_TIMEOUT_MS` |
| `mutation/bulk-insert-10k@store-leveldb` | 917 ms/call (a whole LevelDB opened and closed inside every timed call) |
| `mutation/single-row-insert-1k@store-leveldb` | 907 ms/call (1 000 statements, one fsync-ed commit each) |

The two rows the prior run flagged as most likely to blow the budget are the two that
came in around 900 ms. Nothing is close to the timeout, so no row needed pinning with
`iterations`/`warmup`.

The 9.2 s a *default* run pays buys the rows printing `skipped — … set
QUEREUS_BENCH_LEVELDB=1 …` rather than vanishing — the harness's existing rule that an
omitted row reads as "unchanged" to anyone diffing two runs. It is roughly `0.5 s × rows`
(a fork plus a `dist/` import each, because the skip reason is a runtime fact the worker
evaluates). Recorded as a `NOTE:` tripwire on `BACKENDS`: fine at one opt-in backend,
worth moving a backend-level skip question into the parent if a second or third lands.

# What was verified, and how

Each of these was run by hand; none is covered by an automated test (see *Known gaps*).

- **Opt-in and skip visibility.** Variable unset → all 19 rows print a skip reason naming
  the variable; full `yarn bench` completes in 163 s and exits 0.
- **Plugin load failure is a skip, not a crash.** Simulated by making
  `@quereus/plugin-leveldb` unresolvable (a `node:module` resolve hook). The row printed
  `skipped — @quereus/plugin-leveldb is not usable here (…): simulated: classic-level
  native binding failed to load` and the run exited **0**.
- **Normal-run cleanup.** After the full 19-row opt-in arm, `%TEMP%` held no
  `quereus-bench-*`.
- **Killed-worker cleanup (the layer that motivated the sweep).** Lowered
  `BENCH_TIMEOUT_MS` to 3 s so the parent `SIGKILL`ed a live LevelDB worker. The parent
  printed `Removed 1 temporary database directory left by killed worker(s).` and `%TEMP%`
  was clean. Timeout restored.
- **Sweep safety, as a unit check.** With three synthetic directories present: the one
  owned by a **dead PID** was removed, the one owned by a **live PID** was left alone (so
  two concurrent bench runs cannot delete each other's databases), a non-`quereus-bench-`
  directory was untouched, and the force-PID override removed a live-PID directory when
  the caller asserted it was dead.
- **Advisory rows do not gate.** Doctored a baseline so
  `mutation/update-where-1k@store-leveldb` looked 2× faster there, then re-ran against it:
  status `1 REGRESSED`, the yellow `1 informational benchmark(s) regressed — reported,
  never gated` line, **exit 0**. Control, same doctoring on the non-advisory
  `@store-mem` twin: `1 benchmark(s) regressed beyond the noise floor`, **exit 1**.
- **A ratio guard naming an advisory row is refused.** Temporarily added
  `{ name: 'correlated-subquery@store-leveldb', … }`: `ratio guard misconfigured: guard
  names '…@store-leveldb', whose row is informational`, exit 1 — and it fired under a
  `--filter` that excluded both of the guard's benchmarks, which is the "checked before
  every other case" claim actually holding. Guard reverted.

## One thing the ticket's model of cleanup got wrong

The ticket assumed the parent's own SIGINT handler covers Ctrl+C. It does — but a parent
that dies *without* running a handler covers nothing, and that is reachable: Task Manager,
a CI tree-kill, and on Windows **any `kill` from another process**, which terminates
rather than signalling. Measured twice: killing `run.mjs` mid-benchmark that way left
`quereus-bench-<pid>-store-leveldb-*` behind both times.

What collects it is the **next** `run.mjs` invocation's sweep, whose liveness check by
then sees a dead PID — verified: the following run printed `Removed 1 temporary database
directory left by killed worker(s).` So the sweep is a **cross-run** backstop, not only a
within-run one, and a stale directory costs some disk until the next bench run while never
reaching a measurement. That is now stated in `bench/lib/tempdir.mjs`'s header and in
`docs/benchmarking.md`.

# Changes this run made beyond measurement and docs

- **A real lint failure fixed.** `yarn lint` (which type-checks the bench `.mjs` files)
  failed on `tempdir.mjs`: `error TS2339: Property 'code' does not exist on type '{}'` —
  `catch` binds `unknown`, and `pidAlive` reads `err.code`. Annotated as
  `NodeJS.ErrnoException`. **The prior run never ran lint**, so this shipped broken at
  `9dd90e02d`; a reviewer diffing against that commit should expect it.
- **New unit coverage for the `informational` flag** — the flag had none. In
  `bench-backends.spec.ts`: the stamp lands on every row a declaring backend produces, an
  ordinary backend's rows carry **no** `informational` key at all, the stamp composes with
  a backend skip rather than replacing it, a non-boolean is rejected, and
  `informationalNames` reports across the whole suite set, ignores a truthy-non-`true`
  value, and `selectBenchmarks` normalizes to a strict boolean. In
  `bench-comparison.spec.ts`: an advisory regression keeps `status: 'regression'` and
  `note`, gets `gated: false`, and contributes 0 to `regressions` — plus a control proving
  it ungates *that* row without ungating its neighbour in the same run.
- **`bench:leveldb` script** in `packages/quereus/package.json`. Yarn's portable shell
  handles the `QUEREUS_BENCH_LEVELDB=1` prefix on Windows; confirmed by running it.

# Known gaps — please probe these

- **No automated test ever runs a LevelDB benchmark.** `bench-backends.spec.ts` and
  `bench-comparison.spec.ts` are pure functions over synthetic objects, and `yarn bench` is
  not part of `yarn test`. Everything in *What was verified* above was done by hand, once,
  on one machine. `tempdir.mjs`'s sweep is the piece most worth a real automated test — it
  is pure enough for one (it only needs a directory and a PID) and it is the layer standing
  between a killed worker and a corrupted next measurement.
- **`run.mjs`'s presentation is unverified by machine.** The cyan `informational` marker,
  the yellow advisory-regression summary and the `misconfigured` guard verdict were all
  read off a terminal. Nothing would catch a future edit that dropped the marker.
- **The Ctrl+C path specifically was not exercised.** Windows cannot deliver SIGINT to
  another process programmatically (`child.kill('SIGINT')` terminates instead — confirmed:
  the handler did not run, exit was `code=null signal=SIGINT`). The handler's two halves
  were each verified through the timeout path, which uses the same
  `killedWorkerPids` → `SIGKILL` → `sweepTempDirs` sequence, but the handler itself never
  ran in any test here. A reviewer on Linux/macOS can close this in one run.
- **Whether an orphaned worker's own exit hook fires is not observable.** `run.mjs` forks
  workers with piped stdio and forwards it, so once the parent is gone the worker's stderr
  has no reader. Noted in `tempdir.mjs` so nobody infers "the hook worked" from a silent
  run. If layer 2 is in fact dead weight on this path, the honest fix is to say so, not to
  add a fourth layer.
- **`syncCommits` is left at its default `true`** and is the biggest term in these costs.
  Deliberate — it is what a deployment runs — but it means the write rows are largely an
  fsync benchmark, and a reviewer should be comfortable that this is the intended claim
  before any of these numbers gets quoted as "the store's write cost".
- **The numbers are one machine's.** An NVMe laptop; a spinning disk or a CI container
  with a throttled filesystem could be an order of magnitude slower, and
  `delete-where-100@store-leveldb`'s ~14 s of wall clock has about 8× of headroom before
  the 120 s timeout. The rows are advisory and opt-in, so the blast radius of being wrong
  is a slow opt-in run rather than a red build — but the `BACKENDS` decision does rest on
  this one sample.
- **No storage round-trip counters on this backend**, by construction: the counting
  provider wraps an in-memory map. The rows carry timings only. `store-mem` reports the
  round-trip counts exactly and for free on every run, which is why this was judged not
  worth solving here.

# Review findings

- Tripwire parked at `BACKENDS` in `bench/lib/backends.mjs`: the ~0.5 s-per-row fork cost
  of printing a skip reason scales linearly with always-skipped backends (9.2 s for 19
  rows today). Fine at one opt-in backend; if a default `yarn bench` ever pays 20-30 s to
  print skip reasons, move a backend-level skip question into the parent rather than
  dropping the rows.
