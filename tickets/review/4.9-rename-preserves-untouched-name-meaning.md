# What landed

`ALTER TABLE … RENAME TO` already guaranteed that a reference it **rewrites**
still resolves to the renamed table. It now guarantees the other half too: a
reference it does **not** rewrite must still resolve to whatever it resolved to
before.

The gap: a rename also *creates* a name, and that new name can capture a
reference in a body whose text never mentions the renamed table.

```sql
create table main.k (id integer primary key, x integer);   -- 1, 10
create table temp.other (id integer primary key, x integer);  -- 99, 999
create view temp.v as select id, x from k;   -- bare `k` falls through to main.k

select * from temp.v;                -- [{"id":1,"x":10}]
alter table temp.other rename to k;  -- temp now holds a `k`
select * from temp.v;                -- was [{"id":99,"x":999}] — now [{"id":1,"x":10}]
```

The stored body is byte-identical (`select id, x from k`); what changed was what
`k` *means* under the view's home schema path `[temp, main]`. The same rename
re-bound an assertion (it silently stopped watching `main.k`) and a materialized
view (masked by its already-materialized rows until the next `refresh`).

## How

One new arm at `renameTableInAst`'s sink
(`packages/quereus/src/schema/rename/table-rename.ts`). For a reference the walk
did **not** match, compare `resolve(ref.schema, ref.name)` (the catalog as the
body planned it) with `resolveAfter(...)` (the catalog as it will be); when they
differ, schema-qualify the reference to the schema its **before**-answer named,
recovered with `objectRefKeySchema`. Both resolvers were already threaded to the
sink — no signature or caller changes.

Qualification stays conditional in both arms, so an unrelated rename still leaves
every body byte-identical and no materialized view's `bodyHash` churns.

## The one thing that was NOT in the ticket — read this first

The ticket assumed the arm could just be added at the sink. It could not, without
a scope restriction, because **the walk is deliberately applied more than once to
the same AST**:

- `runRenameTable` (`runtime/emit/alter-table.ts:295`) rewrites the renamed
  table's own CHECK / partial-index / column expressions *before* the catalog
  swap;
- `propagateTableRename` (`:2174`) then walks every table in every schema,
  including that one — the comment there says outright it relies on the walk
  being idempotent;
- a persisting module (`quereus-store/src/common/store-module-rename.ts`)
  rewrites the *same shared AST nodes* inside its own `renameTable` hook, for the
  same reason.

The rewrite arm is idempotent (after it runs, nothing names `oldName`). The
untouched arm **cannot be**: once the rewrite has turned `s` into `s2`, a second
walk sees an unqualified `s2` that is indistinguishable — to the resolvers — from
one the new name captured, and "preserves" it onto the wrong table. This was not
theoretical: it broke the existing test *own-table self-reference: stays
unqualified even though temp holds the new name* on the first run, producing
`(select count(*) from temp.s2)`.

Resolution: `TableRenameOpts.schemaAuthoredBody`, set by the three collection
helpers (`renameTableIn{IndexPredicates,CheckConstraints,ColumnExpressions}`),
turns the untouched arm off for exactly those expressions. Two facts agree here:

- **Nothing is lost.** A CHECK, a column DEFAULT / generated body and a
  partial-index predicate plan under `schemaAuthoredContext` — their owning
  schema and nothing else. The arm fires only when an unqualified name resolves
  *through* to another schema, which that context already rejects, so it could
  only ever fire on a body the planner refuses to evaluate anyway. (This is the
  rule already documented at `schema/object-ref-resolver.ts:41-53`.)
- **It confines the arm to bodies walked exactly once** — view bodies,
  materialized-view bodies, assertion checks — which is what the arm needs.

`assertRenameDependentsPersistable`'s pre-flight probe walks `spineCloneAst`
copies, so it is unaffected either way.

**This is the highest-value thing to attack in review.** Specifically:

- Is the "schema-authored expressions plan under their owning schema only" claim
  actually airtight for all three arms, on every path (including `ALTER TABLE …
  ALTER COLUMN … SET DEFAULT`, and generated columns)? If a bare cross-schema
  name is reachable in any of them, the opt-out silently loses coverage there.
- Is there a *fourth* re-walk of a home-path body (view / MV / assertion) that I
  did not find? I traced: propagation walks each schema's views and assertions
  once each, MVs once in the second global pass, and the differ's inverse pass
  passes one resolver as both `resolve` and `resolveAfter` (inert by
  construction). A missed one would produce a **wrong** qualifier, not a missing
  one.
- The alternative I rejected — eagerly qualifying every rewritten reference so
  the walk is idempotent by construction — would make the whole thing immune to
  call-site discipline, at the cost of qualifying every cross-schema dependent on
  every rename (breaking several tests that pin no-churn, and reversing a
  decision documented in `store-module-rename.ts`). Worth a second opinion.

## Test coverage (this is a floor, not a ceiling)

Walker level — `test/schema/rename-cross-schema.spec.ts`, inside the existing
`rename rewrite post-condition` describe. New hand-built resolver pair models
`alter table temp.other rename to k` over home path `[temp, main]`:

- untouched FROM source, DML target, and seedless bare column qualifier all get
  qualified to `main`;
- a bound column qualifier stays bare while its source qualifies;
- an already-qualified reference and a name the rename cannot re-bind come back
  byte-identical, walker returns `false`.

Plus a nested describe pinning the hazard above: re-applying the same rename to
an already-rewritten CHECK is a no-op, and a captured bare name in a CHECK is
left alone.

Engine level — new describe `rename preserves what an untouched reference
resolves to (new-name capture)`: view, materialized view (asserted **after**
`refresh materialized view`, so the stale backing cannot mask it), assertion (a
violating write to `main.k` still refused; the same write to the table that took
the name is accepted), a main-owned body that cannot be captured, and an
unrelated body left byte-identical.

End to end — `test/logic/41.3-alter-rename-propagation.sqllogic` § 66, written as
the mirror of the existing § 60.

**Verified the tests bite:** with the new arm stubbed out, § 66 fails. Not just
present — actually load-bearing.

### Known gaps

- **No test for the walk-order hazard at the engine level.** The idempotence
  regression is pinned only at the walker level (via
  `renameTableInCheckConstraints` called twice). Nothing asserts that the engine's
  three call sites stay consistent with the `schemaAuthoredBody` split — a future
  refactor that drops the flag from one helper would be caught only by the
  existing `own-table self-reference` test, and only in the collision shape.
- **No coverage of an untouched reference in an MV read through a *view*
  chain** (`main` MV → `temp` view → captured bare name). The existing chain
  tests cover the rewrite arm only.
- `CREATE TABLE` / `DROP TABLE` shift bare names identically and have no
  propagation pass to hang a fix on — out of scope per the ticket, now recorded
  as a Known limitation in `docs/sql-alter.md`.
- Column-verb (`RENAME COLUMN`) has no analogue of this arm; not investigated.
