# What landed

## 1. `yarn bench:gate` is in `yarn check`

`package.json` (root):

- New passthrough `"bench:gate": "cd packages/quereus && yarn bench:gate"`, matching the
  existing `test:store` / `test:fork-strict` pattern.
- `check` chain is now
  `docs:check → lint → build → typecheck → bench:gate → test:full → fork-strict →
  context-strict → repr-strict`.
- The gate sits **after `typecheck`, before `test:full`** — a deliberate departure from the
  plan ticket, which assumed the end of the chain. Reason (recorded in the `//check` NOTE
  in package.json, in docs/architecture.md section 6, and in docs/benchmarking.md): the
  chain is `&&`-chained, `test:full` is by far its longest step, and the gate needs only
  the `dist/` that `build` two steps earlier produced, so a changed counter surfaces in
  about a minute instead of after the whole test run.

## 2. Three new ratio guards (four total)

All bounds set from a full `yarn bench` on an unchanged tree; the measured ratio is
recorded in a comment beside each guard.

| Guard | Measured | Bound | Headroom | Catches |
| --- | --- | --- | --- | --- |
| `execution/correlated-subquery` / `hand-batched-peer-count` (pre-existing; gained a `note`) | 1.00× | 10× | 10× | `scalar-agg-decorrelation` failing to fire |
| `execution/filtered-scan-index-10k` / `full-scan-10k` | 0.010× | 0.1× | 10× | index access selection collapsing to a full scan |
| `store/multi-seek-pk-10` / `store/point-read-pk` | 2.00× | 8× | 4× | per-key cost creeping into batched multi-key resolution |
| `store/index-resolve-four-batches` / `store/index-resolve-one-batch` | 2.37× | 8× | 3.4× | index-then-fetch resolution going superlinear in row count |

`store.bench.mjs` had no `ratioGuards` export before; it has one now, with a header comment
explaining why a ratio guard is worth having on rows that already assert exact storage
round trips (the counter asserts see *changed* round trips; a ratio sees the round-trip
count staying right while the work behind each one gets more expensive).

The `execution.bench.mjs` policy comment was rewritten for the new surface: bounds below 1,
cross-suite `suite/name` names, the optional `note`, the gate's re-measure rule, and the
requirement to record the measured ratio next to every guard.

# Measured numbers (AMD Ryzen AI 9 HX 370 / NVMe / Windows 11, node 24.2)

- Full `yarn bench`: **159.0 s**, 92 rows (docs previously said ~150 s).
- Gate counters pass: **24.3 s**. **The doc previously said "about 42 s"** — I measured
  24 s on two consecutive runs and wrote that number in. I did not investigate why the
  old figure is higher; it may predate a change, or have been taken on a busier machine.
  Worth a reviewer's eye.
- Gate guard pass: **9.1 s** across 8 forked processes, identical on two runs.
- Total gate cost added to `yarn check`: **~35 s**.

# Validation — what I ran, and what I did not

Ran and passed:

- `node bench/run.mjs` (full suite, 92 rows) — the measurement run the bounds come from.
- `node bench/gate.mjs` from `packages/quereus` — 56 counters match, all four guards ok.
- `yarn bench:gate` **from the repo root**, exercising the new passthrough — same result,
  guard pass 9.1 s.
- `node scripts/check-docs.mjs` — passes.

**Not run: `yarn check` end to end.** A clean `build` plus `test:full` plus the three
strict passes runs well past the 10-minute ceiling on a single agent command, so it is not
agent-runnable inside this ticket (per the tess efficiency rules). Everything the chain
change touches was exercised individually: `docs:check` passes, the gate passes through the
root passthrough, and no TypeScript or test file was modified. The residual risk is
therefore chain-mechanical (yarn script resolution under `&&`), and the root passthrough
was invoked directly to reduce even that. **A human or the reviewer should run
`yarn check` once on a clean tree before this is considered proven.**

# What a reviewer should poke at

- **The `store/multi-seek-pk-10` / `point-read-pk` guard is the loose one.** Full
  calibration: 2.00×. The gate's reduced calibration read 2.64× and 2.92× on two
  consecutive runs, with member spreads of 32-53% — these are the two fastest query-shaped
  rows in the suite (tens of microseconds). Bound 8× leaves ~2.7× over the worst
  observation, and the full-calibration re-measure is the backstop against a false red.
  Judge whether that is the right trade or whether the guard should be dropped in favour
  of the steadier `index-resolve` one. A `NOTE:` at the site says the fix for chronic
  re-measuring is more samples, not a higher bound.
- **`execution/filtered-scan-index-10k` measured 113.9% spread at the gate's reduced
  calibration** (85 µs row, batched × 4). Its ratio is still two orders of magnitude below
  the bound, so it does not threaten a false red — but if you want a guard member that is
  merely *stable*, this is not it.
- **The skip path is reasoned, not exercised.** Every `store` guard member carries
  `skipUnlessStoreLoads`, so on a checkout with no built `@quereus/store` the guards should
  report `not-evaluated` (never a failure) via the `skippedNames` branch in
  `bench/lib/guards.mjs`. I read that path rather than reproducing it — reproducing it
  means deliberately breaking the store build. `test/bench-guards.spec.ts` covers the rule
  as a unit; the end-to-end version is untested.
- **The counters-pass 42 s → 24 s discrepancy** noted above.
- **`docs/benchmarking.md` is now 11 511 words against a 12 000-word cap** and
  `check-docs.mjs` prints its within-500-words notice on every run. Not a failure, and
  splitting the doc is out of scope here — but the next section that lands in this file
  will need a split first. Trimming brought it down from 11 652; the remaining content is
  load-bearing.
- Bound arithmetic in the table above, against the comments at each guard site.
