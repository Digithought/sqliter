# What landed

`yarn bench` now runs every `execution` and `mutation` workload twice: once on the memory
vtab module (bare name, unchanged) and once on `@store-mem` — `StoreModule` wrapped by the
isolation layer, over an in-memory key-value provider. 19 new rows, 46 benchmarks total.

Each `@store-mem` row also reports **storage round trips**: its `counters()` block nests
`{ engine, store }`, where `store` is keyed by built store name and carries four counts per
store — `iterateEntries`, `getManyCalls` (round trips), `getManyKeys`, `singleGets`.

## The four pieces

**`bench/lib/store-counters.mjs` (new).** The harness's ONE dynamic-import site for
`@quereus/store`, plus both databases built on the far side of it (`openStoreDatabase` for
the timed loop, `openCountingStoreDatabase` for the untimed counters pass) and
`readStoreCounters`. The import is lazy because `run.mjs` imports every suite file in the
PARENT just to enumerate names — a static import would let an unbuilt
`packages/quereus-store/dist` kill the parser and planner suites too. Both builders live
here rather than in `backends.mjs` so there is only one such site.

`singleGets` is derived once, here, as `getCount - getManyKeyCount`, because
`CountingKVStore.getMany` deliberately routes every key of a batch through its own counted
`get`. A negative value throws rather than being reported.

**`backends.mjs`.** `STORE_MEM_BACKEND`, added to the shared `BACKENDS` array so both
suites get it without either suite file changing. Two new optional members on
`BenchBackend`:

- `skipWorkload(workload)` — the backend's half of `Benchmark.skip`, wired in by
  `expandBackends`. Composes with a binder-supplied `skip`: backend asked first, its reason
  wins, then the binder's is consulted. A benchmark on a backend without one carries no
  `skip` key at all, exactly as before.
- `openCounting()` — builds the instrumented second database. A backend without one (the
  memory backend) reports engine counters only, unchanged.

**The two binders.** `queryCounters` / `mutationCounters` branch on `backend.openCounting`.

**`MutationWorkload.counters(db, ctx)`.** New second argument with one member,
`ctx.beginMeasured()`, called by each workload at the boundary between its own fixture and
the work it means to count. Without it `delete-where-100`'s store block would describe
10 000 fixture inserts with one delete buried inside. No-op on non-counting backends.

# What to test / re-verify

## The acceptance criterion

```
yarn build
node packages/quereus/bench/run.mjs --filter @store-mem
node packages/quereus/bench/run.mjs --filter @store-mem --baseline latest
```

Second run must report **`Counters: 19 identical, 0 changed`**. It did here. Identical
*timings* are not asserted and must not be — one row's spread moved from 34% to 6% between
runs purely on machine load.

## Memory rows must not have moved

```
node packages/quereus/bench/run.mjs --baseline <a pre-change results file>
```

Reported `Counters: 23 identical, 0 changed` against
`bench/results/2026-08-19T15-02-20-112Z.json`. Every bare-named row's counter block is
byte-for-byte what it was.

## The counts, and what they'd catch

Worth eyeballing — these are the numbers the metric exists to protect:

| row | store block |
| --- | --- |
| `filtered-scan-index-10k@store-mem` | index store: 10 `iterateEntries`; data store: **1** `getManyCalls` carrying 10 `getManyKeys` |
| `text-pk-point-seek-10k@store-mem` | 1 `singleGets`, nothing else |
| `full-scan-10k@store-mem` | 10 000 `iterateEntries`, zero reads |
| `correlated-subquery@store-mem` / `hand-batched-peer-count@store-mem` | both 10 100 `iterateEntries` — decorrelation confirmed at the storage layer, not only in the ratio guard |
| `bulk-insert-10k@store-mem` | 30 000 `singleGets` for 10 000 rows — three reads per inserted row |
| `update-where-1k@store-mem` | 20 000 `iterateEntries` (two full scans, one per statement) + 4 000 `singleGets` |

If index row resolution ever stopped batching, the first row's `getManyCalls` goes 1 → 10
and `singleGets` takes the keys. That is the regression class none of this had coverage for.

## Divergences confirmed, not assumed

- `text-pk-range-scan-10k@store-mem` returns its 1 000 rows despite the store applying
  NOCASE to an undecorated text primary key where memory applies BINARY. Ran it; correct.
- `join-1kx1k@store-mem` returns its 1 000 rows despite the store's cost model being free
  to pick a different join shape. Ran it; correct. Its counters may describe a different
  plan than the memory row's, which is fine and is commented as such.

Nothing skips today. The `skipWorkload` seam's live job is the store-package-load probe.

# Known gaps — please push on these

**The `skipWorkload` store-load probe has never been watched to fail.** Unit tests cover
the composition and ordering with synthetic backends, but nobody has renamed
`packages/quereus-store/dist` and confirmed that 19 rows print `skipped — @quereus/store
did not load …` while parser and planner still run. That is the whole justification for the
lazy import and it is currently a claim, not an observation. Worth 30 seconds of a
reviewer's time.

**Store counters are READS only.** `CountingKVStore` counts `get`/`getMany`/`iterate` and
has no write counters, so every mutation row's store block describes the reads its writes
provoked and never the writes. `bulk-insert-10k@store-mem`'s 30 000 `singleGets` is real and
diffable; it is not the whole cost of an insert. Parked as a `NOTE:` at the top of
`bench/lib/store-counters.mjs` naming the fix (add `setCount`/`deleteCount`/`batchCalls` to
`CountingKVStore` — additive, its specs assert on read counters only). Judgement call: I did
not widen scope into `@quereus/store`'s testing surface. Push back if that is wrong.

**`__catalog__` and `__stats__` appear in every block, usually all zeros.** Deliberate — a
store that was opened but never read is a different claim from one never opened, and the
comparison reports an appeared path as loudly as a changed count. But it is four zeroed
lines per store in every results file, and a reviewer may reasonably prefer pruning
all-zero entries. I did not measure the file-size cost.

**`ctx.beginMeasured()` is an unenforced contract.** A future mutation workload that forgets
to call it gets a store block silently describing its fixture as well as its subject.
Nothing errors. A cheap guard (throw if a counting pass finishes without it having been
called) was not built.

**The store block for `bulk-insert-10k@store-mem` covers all 20 batches** while its engine
block covers only the first and last, so the two halves describe the same body at different
granularities. Commented at the site. Defensible, but it is the one place the block's scope
does not line up with the engine snapshot beside it.

**`mutation/single-row-insert-1k@store-mem` was flagged unstable in one run** (105% spread,
5 samples) and clean in two others (5.9%, 6%). Attributed to background load from parallel
runs on this machine, not to the benchmark — but three observations is thin. The harness
already excludes it from gating when it happens. If it proves genuinely unstable the fix is
a per-backend row count with the count in the name, not pinning (a pinned row forfeits its
spread figure).

**Wall-clock roughly doubled**: 48 s / 27 rows before, 102 s / 46 rows after (AMD Ryzen AI 9
HX 370, node 24.2). No row is near the 120 s per-benchmark timeout — slowest single call is
~370 ms — so nothing is pinned. The store counters passes cost ~1 s total, so the
per-backend counters-scale parameterization the plan allowed for was measured and **not**
built; the module constants in `bench/workloads/mutation.mjs` are untouched.

**One row read as REGRESSED in the full comparison**: `execution/distinct-text-10k`, +12–19%
against `bench/results/2026-08-19T15-02-20-112Z.json`, counters identical. That baseline's
23.93 ms is the lowest value in 33 recorded runs of that benchmark; post-change runs land at
26.6–26.8 ms, inside the 23.9–29.5 ms band that benchmark occupies at HEAD on a quiet
machine. Nothing in this diff touches the memory execution path. Read as baseline-selection
drift, not a regression — but it was not disproved by measuring HEAD directly, because doing
so would have meant reverting the working tree.

**No cross-machine check.** Counter portability remains an assumption; store round trips are
reported as facts about the run that produced them, and there is deliberately no gate on
them.
