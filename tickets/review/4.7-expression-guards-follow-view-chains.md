# What changed

`DROP TABLE`, `DROP VIEW`, `DROP MATERIALIZED VIEW` and `ALTER TABLE … DROP
COLUMN` already refused when another table's CHECK constraint, column `DEFAULT`
or `GENERATED ALWAYS AS` body **named** the dropped object. They now also refuse
when that body **reaches** it through any chain of view / materialized-view
bodies, and the refusal names the chain.

The reachability closure was not written here — it already existed
(`schema/object-dependency-closure.ts`, built for the assertion guards). This
ticket moved the CHECK / DEFAULT / generated family onto it, so the catalog holds
one definition of "reaches" instead of two.

## Site by site

**`object-dependency-closure.ts`** — `reachableObjects` gained a fifth parameter,
`rootOpts?: TableRenameOpts`, applied to the ROOT body's collection only
(`current.ownerKey === undefined` identifies the root uniquely; every reached body
gets an `ownerKey` from `childBody`). Required because a table's CHECK / DEFAULT
owns the `new.` / `old.` namespace: rooted there without `rowImageContext`, a
table literally called `new` lands in the reach and false-refuses its own drop.
The assertion callers pass nothing and are unaffected. The header note that told
this consumer to thread the option was replaced with a description of the
parameter.

**`expression-dependents.ts`** — `ExpressionProbe` now returns
`ReadonlyArray<string> | undefined` (the reach path; empty = direct match) rather
than a boolean, and `ExpressionDependent` carries a `path`. The table verb's probe
is `reachableObjects(...).namerOf(targetKey)?.path`; the column verb loops
`reach.bodies` the way `assertNoAssertionNamesColumn` does, seeding the probe only
on the probed table's own ROOT body. Both entry points keep their signatures and
walk order.

**Both guard call sites** — direct refusals keep byte-identical wording (which is
why no existing test section needed editing); indirect ones lead with the
expression and append `describeReachPath`, matching `assertion-drop-guard.ts`:

```
direct    cannot drop table 'main.t': it is referenced by CHECK constraint 'ck' on table 'x' — drop or redefine it first
indirect  cannot drop table 'main.t': CHECK constraint 'ck' on table 'x' reaches it through view 'vv' — drop or redefine it first
direct    Cannot drop column 'v' from 't': it is referenced by CHECK constraint 'ck' on table 'x'
indirect  Cannot drop column 'v' from 't': CHECK constraint 'ck' on table 'x' reaches it through view 'v2' -> view 'v1'
```

`drop-column-guards.ts`'s header sentence claiming the two expression guards do
not follow view bodies was false after this change and was rewritten.

## Must stay allowed — the false-refusal shapes

These are the reason this consumes the shared closure (scope-aware by
construction) rather than growing a second name-collecting walk. Breaking any of
them is the most likely regression:

- Plain view over `t` with nothing reading the view — `drop table t` is legal and
  leaves the view broken. The engine's stated asymmetry; 41.10.4 §5, unchanged.
- A CTE inside the VIEW's body that merely shadows the name (`create view vv as
  with t as (select … from u) select … from t`) — 41.10.4 §15, 41.10.2 §30.
- `check (new.n > 0)` on `x` plus a real table called `"new"` — 41.10.4 §15. This
  is what `rootOpts` exists for; drop the parameter and this test goes red.
- A view over a THIRD table with a like-named column — 41.10.2 §30 (§21's shape
  one view deeper).
- Cross-schema shadow: a bare name inside a `temp` view body that `temp` itself
  holds — 41.10.4 §14, 41.10.2 §30.
- A view in the chain naming the TABLE but not the COLUMN — the column verb must
  allow it; the table verb must still refuse (it matches the object, not a
  column). 41.10.2 §26.

# Known gaps — flagged, not papered over

**An own-table CHECK whose subquery reads a VIEW and names a column
*unqualified* still false-refuses.** Pre-existing, not introduced here, and
documented in the ticket as *Known interaction*:

```sql
create table t (id integer primary key, v integer);
create view uv as select id, v from u;          -- u is a DIFFERENT table
alter table t add constraint ck check (id < (select max(v) from uv));
alter table t drop column v;
-- Cannot drop column 'v' from 't': it is referenced by CHECK constraint 'ck'   ← wrong
```

Cause: `buildColumnSourceResolver` answers "does source `s.t` expose column
`col`?" via `getTable(t)?.columnIndexMap`, and a VIEW is not a table there, so it
returns false and the seeded probe concludes the bare `v` binds the seeded own
table. Same missing capability (`ViewSchema` carries no resolved output column
list) that `drop-column-guard-blind-to-star-reexposure` (sequenced 4.8, right
after this) owns; an arm was already appended there. **Consequence honoured in the
tests:** every own-table-through-a-view case uses a QUALIFIED column reference,
and no control depends on the unqualified own-table spelling being allowed.
41.10.2 §29's comment states this at the site.

**Column lineage through a STAR projection is still blind.** `create view v as
select * from t` spells no column name, so the column verb does not see `t.x`
through it. Unchanged by this ticket, and now the CHECK / DEFAULT family has the
same hole the assertion family already had — which is exactly why 4.8 is
sequenced next and covers both. Noted in `drop-column-guards.ts`'s
`assertNoAssertionNamesColumn` header. The TABLE verb has no such hole.

**Tie-breaking on equal-length chains is undefined.** Two chains of the same
length to the same object tie on queue order (already a `NOTE:` on
`ObjectReach.namerOf`). Harmless while the path is advisory, but a future test
fixture that pins a specific chain in that situation would be flaky. No test here
constructs one.

# Where a reviewer should push

- **The seeded/unseeded split in `columnProbe`.** `const seeded = ownTable &&
  reached.ownerKey === undefined` is the load-bearing line. Getting it wrong in
  either direction is silent: too seeded false-refuses every table with a
  like-named column, too unseeded misses the own-table CHECK entirely. 41.10.2
  §21/§29/§30 are the tests that would catch each direction — worth confirming
  they actually would.
- **`rootOpts` really is root-only.** The `ownerKey === undefined` test is the
  whole mechanism. A view body walked WITH `rowImageContext` would silently stop
  seeing a source named `new`, which no current test would catch (nothing
  constructs a view over a table called `new` reached from a CHECK — 41.10.4 §15
  reaches `"new"` through a view but names it as a normal FROM source, so it
  passes either way).
- **Cost.** Each stored expression now builds its own closure instead of doing one
  AST walk. Bounded — the closure only expands objects a body actually names, so
  an expression naming no view costs the same single walk as before — but the
  claim is reasoned, not measured. The module header `NOTE:` records it.
- **Message wording on multi-arm hits.** Only the FIRST dependent is reported
  (unchanged policy), and past the probed table the order follows catalog
  insertion (existing `NOTE:` on `tablesProbedTargetFirst`). With two referencing
  tables, which one the refusal names is not user-predictable.
