# What changed

`SchemaManager.createTable` (`packages/quereus/src/schema/manager.ts`) now calls

```ts
assertCatalogObjectPersistable(this.db, 'table', baseTableSchema);
```

immediately after the existing duplicate-UNIQUE-constraint guard and before `module.create` /
`createBacking` is invoked. This is the same synchronous pre-flight veto `CREATE VIEW`,
`CREATE MATERIALIZED VIEW`, and the `ALTER TABLE … RENAME` dependent scan already ran — it
loops every registered module and lets the first refusal propagate out of the statement.

No changes were needed in `catalog-persistability.ts` or `store-module-catalog.ts`: the
`'table'` kind, `ownsTableCatalogEntry` (the store's self-filter so it doesn't veto a
`using memory` table), and `prospectiveCatalogEntry`'s `'table'` arm were all already built
out for the RENAME pre-flight (`assertRenameDependentTablesPersistable`) — this ticket's only
gap was that plain `CREATE TABLE` never called the shared entry point. The whole diff in
`manager.ts` is the one call plus a placement-rationale comment.

`baseTableSchema` (the pre-`module.create` object) is what's passed, not the post-create
`completeTableSchema` — the latter doesn't exist yet at that point in the function, and the
veto only reads the generated DDL text, which `finalizeCreatedTableSchema`'s one remaining
change (PK collation reconciliation, always to another engine-known collation name) cannot
make unencodable.

# Test changes

`packages/quereus-store/test/lone-surrogate-keys.spec.ts`, describe block "an identifier or
persisted DDL text carrying a lone surrogate":

- Rewrote the block's header comment: it used to describe "three different rejection
  timings" including "DDL-text problems surface on the first INSERT/SELECT rather than at
  CREATE TABLE" — that's now false for a live `createTable` call, so the comment now
  describes two mechanisms (identifier guard, DDL-text pre-flight) both firing at CREATE, and
  notes the lazy-persist path still applies only to a legacy catalog entry that predates the
  guard (import/rehydrate never calls `createTable`).
- Flipped `'rejects a column name carrying a lone surrogate...'` and `'rejects a DEFAULT
  string literal carrying a lone surrogate'`: both now assert the `create table` statement
  itself throws and `db.schemaManager.getTable('main', <name>)` is `undefined`, instead of
  letting the CREATE succeed and asserting a later INSERT throws.
- Added `'rejects a CHECK constraint string literal carrying a lone surrogate'` — proves the
  veto reads the whole generated DDL text, not just identifiers.
- Added `'still creates a memory-backed table with the same unencodable column name'` — the
  negative case: a `using memory` table in the same database, with the identical
  lone-surrogate column name, still creates and accepts writes. Confirms the store's
  ownership self-filter (`ownsTableCatalogEntry`) isn't over-triggering.
- Added `'refuses a table the store could never write, rather than silently losing it if
  untouched'` — makes the original silent-data-loss bug directly observable: creates a
  store table with an unencodable `DEFAULT`, never touches it, and asserts both that the
  `create table` itself was refused AND that a fresh `StoreModule.loadAllDDL()` over the same
  provider finds nothing — i.e. there's nothing left to lose on reopen.

# Use cases for review / validation

- `create table t (id integer primary key, "<lone surrogate>" text) using store` → throws
  naming the unpaired surrogate, table not registered.
- `create table t (id integer primary key, v text default '<lone surrogate>') using store`
  → same, and the loss case: create it, close the database, reopen — nothing there, but now
  because it was never created rather than because it silently failed to persist.
- `create table t (id integer primary key, v text check (v <> '<lone surrogate>')) using
  store` → same.
- The identical column name on `using memory` in the same database → succeeds normally.
- `apply schema` executing a `create table` mid-batch that trips this guard → the batch
  aborts through the existing `endSchemaBatch(error)` arm (not independently re-verified in
  this pass; it's a straight-line consequence of `createTable` throwing, which every other
  guard in that function already relies on).
- `create table … maintained as …` (`createMaintainedTable` → `buildDeclaredTableSchema` +
  `createTable(stmt, /*preferBacking*/ true)`) → the guard fires before `createBacking` is
  called, so a maintained table with an unencodable definition never gets a backing store
  built. Verified by code reading (`createMaintainedTable` calls `sm.createTable` before
  anything backing-related), not by a dedicated new test — see gaps below.
- `create table … if not exists` on an already-existing table → returns early before the
  guard is reached, unchanged.
- A pre-existing catalog entry with an unencodable literal (hand-written or from an older
  version) → still opens; the guard is not on `buildTableSchemaFromAST`, `importTable`, or
  `importDDL`.
- A memory-only database (no store module registered) → `assertCatalogObjectPersistable`'s
  loop is a no-op, zero behavior change, zero cost.

# Known gaps / not independently re-verified this pass

- No new test exercises the `create table … maintained as …` path directly against an
  unencodable definition — the ticket's edge-case list calls this out explicitly
  ("the refusal must arrive before any backing store is built"). I confirmed by reading
  `createMaintainedTable` in `materialized-view-helpers.ts` that `sm.createTable` (which now
  carries the guard) runs before `createBacking`/`attachMaintainedDerivation`, so the ordering
  requirement holds, but there's no regression test pinning it the way the plain-CREATE cases
  are pinned.
- No new test exercises `apply schema` hitting this guard mid-batch. The ticket says the
  existing `endSchemaBatch(error)` arm should handle it with "no new rollback machinery" — I
  didn't add anything there and didn't write a dedicated test, since `createTable` throwing
  synchronously is exactly the failure shape every other in-`createTable` guard (duplicate
  UNIQUE, duplicate constraint names, FK collation) already produces and that path presumably
  already handles.
- Didn't add a test for the isolation-wrapped store on the CREATE TABLE path specifically
  (the RENAME pre-flight's isolation coverage already exists and is unchanged/still passing;
  I didn't duplicate it for plain CREATE).
