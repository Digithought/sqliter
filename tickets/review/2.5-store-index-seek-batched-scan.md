# Review: batched row fetches behind secondary-index scans

## What was built

One mechanism, three arms, all in `store-table-scan.ts`:

- **`ROW_RESOLUTION_BATCH = 256`** (exported): entries per row-resolution batch,
  matching the iterate pager's default page. This is the bound `KVStore.getMany`'s
  "bounded by the caller" note already pointed at.
- **Producer** `produceIndexEntries`: walks one byte window via `iterateEffective`
  (read-your-own-writes merge, index-key order) and yields each surviving entry's data
  key plus its window's FilterInfo list. Entry-only defenses stay here: the zero-length
  legacy-value skip, and the multi-seek `seen` PRE-check (saves the read for a
  cross-window duplicate an earlier window already yielded).
- **Consumer** `resolveIndexEntries` / `resolveRowBatch`: collects up to 256 entries,
  resolves them with ONE `readEffectiveRowsByKeys` (pending overlay resolved before the
  store batch, positional nulls), then in entry order: skip null rows, RE-check `seen`
  (catches a duplicate INSIDE one batch, which the pre-check cannot see), accept when the
  row matches ANY of the entry's FilterInfos, add to `seen` on yield only.
- **`scanIndex`** (arm B) = the consumer over one window's producer.
- **`scanMultiSeek`** (arm C) = the SAME consumer over the concatenation of every
  disjoint window's producer — batches bound by entry count, not window count, so a
  hundred single-row windows collapse into one round trip. It no longer calls
  `scanIndex`; the old `multi?: MultiSeekWindowContext` parameter and interface are gone
  (replaced by `PendingIndexEntry`).
- **`scanMultiSeekPrimary`** (arm C) = plain bounded slices over its sorted,
  deduplicated point-key list, one `readEffectiveRowsByKeys` per slice.

Unchanged on purpose: `readEffectiveRowByKey` and its other callers
(constraint probes, backing-host), all window derivation, all residual/collation logic,
the only-add-`seen`-on-yield rule, and emission order everywhere.

## Deliberate behavior change a reviewer should weigh

`limit 1` now reads one BATCH, not one row — the same trade `pagedIterate` makes and the
ticket explicitly blessed. Concretely: `key-set-seek-store.spec.ts`'s test "stops after
the first window under limit 1" asserted the old per-window laziness (`getCount ≤ 3`);
it could not survive and was rewritten (with the ticket's blessing baked into its new
name) to assert the new bound: at most one `getMany` round trip, at most
`ROW_RESOLUTION_BATCH` keys, over a 300-window seek. If per-row laziness under `limit 1`
was load-bearing for some consumer, this is the place to push back.

## How to validate

- `yarn workspace @quereus/store run test` — 1643 passing (includes the new
  `index-scan-batching.spec.ts`).
- `yarn test` (full workspace) — all green, including the IndexedDB plugin suite
  (147 passing, fake-indexeddb) and isolation/sync packages.
- `yarn test:store` — 9307 passing (quereus logic tests vs LevelDB store).
- `yarn build` + `yarn workspace @quereus/store run typecheck` — clean.

Key new tests (all in `index-scan-batching.spec.ts` unless noted):

- Single-window range scan under an open transaction with pending puts, deletes, and a
  re-key both inside and outside the window — asserts rows AND emission order (queries
  deliberately omit ORDER BY so the scan's own order is what's asserted).
- Multi-seek with a pending row merged into a middle window and a pending delete
  emptying the first — rows and cross-window order.
- A forged stale duplicate index entry (two entries → one row) inside one batch yields
  the row exactly once — pins the post-read `seen` re-check.
- `limit 1` over 300 matching entries: at most one batch of index entries visited, at
  most one `getMany`, no data-store iteration.
- A 300-row drain: exactly `ceil(300/256) = 2` batches, rows and order intact across
  the batch boundary.
- 100 single-row multi-seek windows: exactly ONE `getMany` of 100 keys (was 100
  serialized point reads).
- `scanMultiSeekPrimary` probe (protected-method call with a hand-built FilterInfo,
  same idiom as pushdown's `buildPKRangeBounds` probe): unsorted keys + one missing key
  → rows in PK order, missing key skipped positionally, one batch round trip.
- pushdown.spec.ts narrowing tests now also assert `getManyCalls === 1`.

## Known gaps / honest notes

- **No browser measurement.** The 10×-slower-than-full-scan IndexedDB numbers in the
  ticket are the downstream project's; the fix is verified here by round-trip counting
  against store doubles, not by profiling headless Chromium. The IndexedDB backend's
  `getMany` (one transaction for N gets) was landed and conformance-tested by the
  prerequisite tickets; this ticket only routes the scan through it.
- **Single-window scans still have no duplicate dedup** — only multi-seek carries
  `seen`. Two index entries pointing at one row in a plain `scanIndex` window yield the
  row twice, exactly as before this change (corrupt-index territory; not a regression,
  just unchanged).
- **Primary multi-seek arm is unreachable from the module's own plans** (the planner
  claims IN-lists only for secondary indexes), so its batching is covered by the direct
  probe test, not by SQL.
- **Overlay sampling granularity.** `readEffectiveRowsByKeys` snapshots the pending-ops
  bucket once per batch where the old path sampled it per row. A same-transaction write
  interleaved into a suspended scan can therefore be observed at batch granularity
  rather than row granularity. Neither timing was ever guaranteed, and all
  read-your-own-writes tests pass, but it is a semantic difference a reviewer may want
  to eyeball.
- **Buffer-ownership assumption.** A batch holds up to 256 `entry.value` references
  across the `getMany` await; this leans on `KVStore.iterate`'s per-entry
  buffer-ownership contract (each yielded entry independently owned, already enforced
  by the conformance tiers). If a future backend ever reuses buffers across yields, the
  batch would corrupt — but that backend would already be violating the contract.
