# What changed

Both join-ordering rules read a row count from `physicalSourceRows(child.physical, child)`
now — the child's physical row estimate, falling back to its logical `estimatedRows`
getter. Before, both read the logical getter directly, which is `undefined` for every
table-backed input (the physical access nodes stamp their catalog count into
`computePhysical` only), so each rule fell through to a sentinel that made its own
comparison meaningless.

**`rule-join-greedy-commute`** — the `?? Number.POSITIVE_INFINITY` is gone. An unknown
estimate on either side is now an explicit "do not swap" (`rightIsSmaller` requires both
sides to be defined); only the singleton-functional-dependency arm applies then. Strict
`<` is preserved, so equal estimates never swap. The stale `NOTE:` pointing at the parent
plan ticket is deleted.

**`rule-quickpick-enumeration`** — the `1e9` magic number is gone. The base-order
computation is extracted into an exported `quickPickBaseOrder(relations)`: ascending
physical row count, unknown last (`UNKNOWN_RELATION_ROWS = MAX_ROW_ESTIMATE`, finite so
two unknowns subtract to 0 rather than `NaN`), ties broken by relation index.

Guards were verified to still precede the row-count read in both rules: join type
(commute line ~31; QuickPick bails inside `extractJoinGraph`), correlation (~39),
side effects (~45 / the `subtreeHasSideEffects` loop before `baselineCost`).

# How to exercise it

New spec: `packages/quereus/test/optimizer/join-order-row-estimates.spec.ts`
(`yarn workspace @quereus/quereus run test --grep "join ordering reads physical row estimates"`).
13 tests in three groups:

- **`quickPickBaseOrder` (unit)** — smallest first; unknown last; two unknowns keep index
  order (the `NaN` case); equal estimates keep index order; a relation with only a logical
  count still sorts by it.
- **`rule-join-greedy-commute` row-count arm** — the rule is called directly on a
  hand-built `JoinNode` over two real access nodes. Pins: a table-backed scan reports a
  count physically (10 / 500) and *nothing* logically; a smaller known right side commutes;
  a larger right side does not; equal counts do not; an outer join never commutes; and an
  unknown side on *either* position does not commute even when the other side is provably
  smaller (`unmeasured` is deliberately left out of `ANALYZE`).
- **three-table join** — the same three-way chain (10 / 200 / 2000 rows, `ANALYZE`d)
  written largest-first and smallest-first plans the same table order and returns the same
  rows.

Manual check, if you want to see the difference: build a three-table join over clearly
different table sizes, `ANALYZE`, and compare `db.getPlan()` between the two spellings.

# Known gaps — please push on these

- **The three-table order-independence test passes on the pre-change code too.** I
  verified this by neutralizing both reads and re-running: only the commute tests fail.
  For that chain the plan already came out `large,mid,small` either way, so the test pins
  a property worth keeping but is *not* a regression pin for the QuickPick half. The
  QuickPick change is pinned only by the `quickPickBaseOrder` unit tests. If you can find
  a query where the pre-change arbitrary base order actually produced a worse plan, that
  test is worth adding — I did not find one, and the ticket below explains why I think
  such queries are rare right now.

- **The QuickPick payoff is throttled by a separate defect I found and filed.** A
  `JoinNode`'s self-cost is fixed in its constructor from the same logical getter, with a
  `?? 100` default, so it is `100 * 100 = 10000` for every join over tables. QuickPick
  scores candidate orderings with `getTotalCost()`, and every ordering of N relations
  contains N-1 joins, so each candidate carries the same flat `10000 * (N-1)` and the
  orderings separate only on their leaves. Measured: in the three-way `txn`/`entry`/`cat`
  plan below, 20000 of the plan's 20406 total was those two constants. Not fixable at the
  site (physical properties do not exist at construction; `estimatedCost` is a constructor
  value), and it is a class of ~12 constructors, so it is filed as
  `backlog/debt-node-self-cost-reads-the-blank-estimate` with a `NOTE:` at the JoinNode
  site. **Worth a reviewer's opinion on whether that should have blocked this ticket
  instead of following it.**

- **The commute rule now fires in the Structural pass, ahead of cost-based physical
  selection, and can pre-empt it.** This is the intended behaviour, but it has a visible
  consequence: when one side of a join is tiny, the commute puts it on the left and the
  physical pass then prefers a nested loop over a hash join. That is a reasonable outcome
  (a one-row outer needs no hash build) but it *is* a heuristic overriding a later
  cost comparison, and it caused one of the two test churns below.

- **No `.sqllogic` coverage added.** The row-level correctness of a commuted join is
  already covered by existing logic tests; I added plan-shape coverage only.

# Plan churn, and why each new shape is right

Two existing specs changed. No golden `.plan.json` changed.

1. `test/optimizer/index-nested-loop.spec.ts` → *"feeds a physical join ABOVE the
   exchanged sides the right columns"*. That test needs a hash join above a mirrored
   pair, to pin that the lower join's side-exchange happens before the hash join takes
   its positional attribute snapshot. Its `cat` fixture had two rows, so after this
   change the commute put `cat` on the left and the upper join became a nested loop —
   the assertion `to.have.lengthOf(1)` on hash joins failed, and the test would have
   gone vacuous. **Fix: `cat` now has 40 rows, of which still exactly one matches
   `entity_id = 7`.** The three expected result rows are byte-identical; the extra rows
   exist only to keep the upper join hash-worthy. Bisected to confirm the commute change
   (not the QuickPick change) was the cause. Reviewer: check you agree that enlarging the
   fixture preserves the test's subject rather than papering over a regression — my
   argument is that the data sizes were incidental to what the test says it pins.

2. `test/optimizer/join-row-estimates.spec.ts` → two tests located a node by *pre-order
   position* ("the `o` branch's pushed Filter is the first one in the plan"). The commute
   now puts the 3-row `regions` branch on the left, so the first Filter in the walk is
   the other one. **Fix: a new `findNodeOverTable(root, type, table)` helper locates the
   node by the table its subtree reads.** No expected value changed — the orders branch
   still estimates 33 rows, the alias still relays it. The now-unused `findFilter` helper
   was removed.

# Review checklist

- Is "unknown means do not swap" the right posture, or should the commute rule fall back
  to a default row count? (The ticket said no default; I agree, but it is a judgment call
  and the code now states it explicitly rather than achieving it by `Infinity` accident.)
- `UNKNOWN_RELATION_ROWS = MAX_ROW_ESTIMATE` makes an unknown relation sort after a
  genuinely huge measured one only by the tie-break. Is that the intent, or should
  unknown sort strictly after every known count?
- `quickPickBaseOrder` is exported purely for the unit test. Acceptable, or should the
  test reach it another way?
- `bug-join-order-depends-on-wall-clock` (backlog) covers QuickPick's `Date.now()` time
  limit and was deliberately not touched. The new tie-break is deterministic, so this
  change does not make that nondeterminism worse — worth a second pair of eyes.
