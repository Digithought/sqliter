# What was built

Every rename/probe walker (`renameTableInAst`, `tableReferencedInAst`,
`renameColumnInAst`, `renameColumnInCheckExpression`, both column probes, all
six collection helpers) now takes a `ResolveObjectRef` callback plus a
`targetKey` (`objectRefKey(schema, name)` — canonical lowercase
`<schema>.<name>`) instead of a `defaultSchemaName`. A reference matches when
its planner-parity resolution equals the target key. `schemaMatches` is gone.

Two resolver builders:

- `snapshotObjectRefResolvers(db)` / `buildObjectRefResolver(db, homeSchema)`
  (new `schema/object-ref-resolver.ts`): qualified names pass through;
  unqualified names resolve through `db._homeSchemaPath(home)` (home schema
  first, then the session default path) against a **name-set snapshot of the
  catalog taken at build time**; a miss everywhere falls back to the home
  schema's key so probe/rewrite stay total.
- `singleSchemaObjectRefResolver(schemaName)` (in `rename/shared.ts`): for the
  schema differ's declared world, which is single-schema by construction —
  reproduces exactly what the old `schemaMatches` equality decided there, so
  forward/inverse reconcile parity is preserved.

**Deliberate deviation from the ticket's design prose**: the ticket described a
resolver that "reads the live catalog" with build-before-mutation as
discipline. That cannot pass the ticket's own required test — with `main.t` and
`temp.t` both present, renaming `main.t` runs propagation after the catalog
swap, and a live lookup of a bare `t` under `[main, temp]` would then find
`temp.t` and miss the rewrite. The implemented resolver snapshots each schema's
table+view name sets at build time, which makes "build before the statement's
first catalog mutation" literally sufficient. The snapshot discipline is
documented on the builder and is pinned by the `dep_bare` test below.

Second arm (from the prereq's review): `rewriteTableForTableRename` no longer
hand-rolls the CHECK / index-predicate / column-expression loops — it calls the
same `renameTableIn{CheckConstraints,IndexPredicates,ColumnExpressions}`
helpers the store module's catalog rewrite calls, so the per-arm
row-image-context decision exists in exactly one place. The per-item
`{...cc}` / `{...idx}` shallow copies are gone (they achieved nothing; the
record-identity change is what re-registers the table). The FK arm stays
hand-rolled but became a key comparison (`fk.referencedSchema ?? childSchema`,
matching FK resolution rules — never the session path).

Call sites all build their resolver **before the statement's first catalog
mutation** and thread it through: `runRenameTable` / `runRenameColumn` build
one `snapshotObjectRefResolvers` each (shared by the persistability pre-flight
and the propagation; per-walked-schema resolvers come from
`forHomeSchema(schema.name)`); the DROP guards and assertion-drop guard build
at entry (no prior mutation); the memory module's `renameColumn` and the
store module's `renameTable` / `renameColumn` hooks build inside the hook
(which runs before the engine's catalog swap) — the store's **reverse** pass
(persist-failure rollback) reuses the same snapshot with the new name's key,
relying on the miss→home fallback.

# Behavior changes (beyond signatures)

- **False negative fixed**: a CHECK / column DEFAULT / generated expression in
  any schema naming `temp.t` explicitly now follows `alter table temp.t rename
  …` (both verbs). The table loop always walked every schema; the matcher was
  what failed.
- **False positive fixed**: a bare `t` that resolves to `main.t` no longer
  follows a rename of `temp.t`, and vice versa — including through unaliased
  cross-schema FROM sources and aliases (`from temp.t z` + `z.x` no longer
  matches a rename of `main.t`; the alias map now stores resolved keys).
- Column walker's qualified-ref resolution is now a unified innermost-first
  binding walk (`resolveQualifierBinding`): the innermost frame that binds the
  qualifier decides, so an inner `from temp.t` + `t.x` binds the temp table
  rather than "direct-hitting" a same-named renamed table. Row image (`new.` /
  `old.`) is consulted only for unbound qualifiers, preserving the "a real
  table named new resolves through its binding" rule.
- DML targets in the column walker (INSERT/UPDATE) now respect the statement's
  own WITH clause (a CTE-named target is not the renamed table) — parity with
  the table walker's `visitDmlTarget`.
- Subquery/function-source aliases are still NOT recorded in the column
  walker's scope frames (pre-existing limitation, kept deliberately and
  documented on `resolveQualifierBinding`).

# Validation

- `yarn build`, `yarn test` (all workspaces; 8795 quereus tests), `yarn lint`
  — all green.
- New `test/schema/rename-cross-schema.spec.ts`:
  - resolver unit spec: qualified passthrough + case folding, home-first on
    collision, session-path fallthrough, home dedupe, miss→home fallback,
    snapshot-not-live semantics, views resolve like tables;
  - `alter table temp.t rename to t2` rewrites a `main` CHECK subquery and a
    `main` column DEFAULT naming `temp.t` (false negative);
  - both-exist scenarios for both verbs (false positive + the post-swap
    snapshot trap);
  - a temp view's bare `from t` follows `temp.t`'s rename, not `main.t`'s;
  - idempotence across sequential renames;
  - row-image parity: renaming a table named `new` leaves a CHECK's bare
    `new.a` alone — pinned at the shared-helper level (the single site both
    engine and store now call) AND through the engine ALTER path.
- Store-mode logic tests (LevelDB): `--grep "41"` (all ALTER suites, 43
  passing) and `--grep "schema|declarative|rename"` (867 passing).

# Known gaps / notes for review

- **Full `yarn test:store` was not run to completion** — it exceeds the agent's
  10-minute command budget. The targeted store-mode subsets above cover every
  suite that exercises the changed store/memory module paths (ALTER, schema,
  declarative, rename). A full store run in CI or by a human would close this.
- The view / MV / assertion propagation loops remain gated to the renamed
  object's own schema, per the ticket's scope. The resolver and target key are
  already threaded through them, so `bug-rename-not-propagated-across-schemas`
  should only need to widen the loops (each schema's bodies resolving under
  `forHomeSchema(thatSchema)`).
- The differ deliberately uses `singleSchemaObjectRefResolver` — its declared
  world has no catalog and is single-schema. For the renamed table's own
  definitions (the only cross-surface the store path shares), the single-schema
  and catalog-backed resolvers provably agree (the target's bare name always
  resolves home-first to the target, which exists pre-mutation).
- The self-qualifier strip walker kept its `defaultSchemaName` parameter (the
  CHECK's owning schema, passed by `constraint-builder.ts`); its check was
  inlined as an exact owning-schema comparison — a qualified self-reference
  must name the owning schema, no path resolution applies.
- Tripwire, recorded at the site: `snapshotObjectRefResolvers` snapshots every
  schema's name set on each DDL statement (`NOTE:` in
  `object-ref-resolver.ts`) — snapshot lazily per consulted schema if it ever
  shows up hot.
- Behavior deltas listed above are deliberate but reviewer-worthy: the unified
  qualifier-binding walk and the DML CTE-target guard change outcomes on edge
  shapes that previously "direct-hit" by bare name (all previously-wrong or
  illegal-SQL shapes; no existing test moved).
