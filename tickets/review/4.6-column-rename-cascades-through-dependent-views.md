# Implemented: column rename cascades through dependent views

`ALTER TABLE … RENAME COLUMN` used to rewrite only the objects reading the
renamed table directly. When that rewrite shifted the name a view *publishes*
(`select id, x from t` starts publishing `y`), anything reading the view kept
naming a column that no longer existed — a second view broke on next read, and
an assertion in that position broke **every write** to the database. Both
repros from the ticket now pass (pinned in 41.3 §50 and 95's
`arc_a1` section).

## What was built

- **Worklist driver** (`runtime/emit/column-rename-cascade.ts`,
  `runColumnRenameCascade`): breadth-first fixpoint seeded with the renamed
  table. Each round re-enters the *existing* all-schema propagation
  (`propagateColumnRenameInSchema` + `propagateColumnRenameToMaterializedViews`,
  threaded in as a callback from `propagateColumnRename` to avoid an import
  cycle), so tables' CHECK/DEFAULT/GENERATED expressions, views, MVs, and
  assertions are covered at every depth. Visited set keyed
  `targetKey:oldColLower` (insurance — views can't be recursive).
  `restoreUnaffectedMaterializedViews` runs once, after the whole cascade.
- **Exposure predicate** (`bodyExposesRenamedColumn` in
  `schema/rename/column-rename.ts`): shares the CTE exposure internals
  (`cteExposesRenamedColumn` was split into a query-level core; nothing was
  copied). Post-rewrite contract: compares against the NEW name. Alias
  suppresses; bare projection and `*`/`t.*` over the target expose. Explicit
  view/MV column lists are the *call site's* guard (driver skips them).
  Note: the driver scans **all** views per round rather than only "views the
  round rewrote" — a `select *` body shifts its published names with zero text
  change, so a rewritten-only scan would miss it (ticket's own edge case).
- **Collision refusal** (`assertColumnRenameCascadePublishable` + the
  `bodyPublishesColumnNamed` predicate): a read-only pre-flight in
  `runRenameColumn`, BEFORE the first side effect, that walks the same
  fixpoint on spine clones and throws when any round would make a view/MV
  publish two columns of the new name. Runs pre-mutation deliberately — the
  live cascade rewrites ASTs in place with no rollback, so a mid-cascade throw
  would strand a partial rename. Collision test runs on the pristine body
  (pre-rename, the target cannot publish `newCol`, so any `newCol` found is a
  different column — no exclusion logic needed).
- **Pre-stale MVs are excluded from the cascade**: their backing columns are
  not renamed (only REFRESH may reshape), so their published names don't shift
  and their readers are deliberately left alone.
- **Persistability veto stays round-1-only** — `NOTE:` added in
  `catalog-persistability.ts` with the revisit condition (the veto growing a
  whole-body check). The `newCol` string itself is always vetted by the
  module's own `alterTable` rename guard even when round 1 rewrites nothing.

## Behavior changes a reviewer should know about

- **53.2 §6 asserted the OLD behavior** (chained MV goes stale after a source
  column rename shifts its producer's output name) and was updated: both MVs
  now stay live and follow the rename. The matching "rejected alternative"
  bullet in `docs/mv-schema-change.md` was flipped to record why the old
  rejection no longer holds.
- A body read by TWO rounds (a view reading both the base table and a shifted
  view) fires `view_modified` once per genuine change — two events in one
  statement. Deliberate; pinned in the spec (`vb2` case). No spurious event
  fires when a re-visit leaves a body unchanged (diamond case, also pinned).

## Known gaps (honest)

- **Pre-flight ↔ live-driver equivalence is argued, not proven.** The
  collision pre-flight simulates the cascade on clones against the
  pre-mutation catalog; the live driver analyzes post-rewrite live ASTs. They
  agree because a round only rewrites references binding its own target and
  exposure is per-result-column — but a pathologically ambiguous body (one
  unqualified ref resolvable against two FROM sources that both expose it)
  could in principle diverge. Worst case: the veto misses a collision and the
  cascade produces a duplicate-name view body without an error (soft failure,
  no data corruption).
- **`resolveColumnInSource` answers only for tables** (`getTable`), so
  `bodyPublishesColumnNamed` cannot see a collision arriving only through
  `select *` over a *view* source, and the walker's inner-FROM disambiguation
  has the same blind spot for view sources. Pre-existing limitation class
  (same as aliased-subquery / CTE sources), documented on the predicate.
- **Compound (union) bodies**: the exposure predicate examines the first
  arm's result list (which is what names the output); VALUES / DML bodies
  never cascade. Untested for unions.
- **Cross-schema `select *` MV chains** still ride the single-pass
  `restoreUnaffectedMaterializedViews` ordering NOTE (helpers ~line 2960):
  a star-body chain whose consumer's schema iterates before its producer's
  can be left stale until REFRESH. Unchanged by this ticket (cascade rounds
  are no-ops for pure star chains — their bodies never name the column); the
  existing NOTE already records the fix direction (topological order or a
  second round).
- `alter-table.ts` grew by ~25 lines (pre-flight call + delegate comment)
  despite the driver living in its own module; the file remains on
  `backlog/debt-oversized-source-files`.
