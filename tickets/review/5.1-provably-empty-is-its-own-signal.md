# Review: "provably empty" is now its own signal, separate from a zero row estimate

## What changed

`BestAccessPlanResult.rows` is documented as an estimate, but `selectPhysicalNode` read
`rows === 0` (plus "every claimed filter handled") as a PROOF that the query can match
nothing and replaced the whole table read with a static empty relation. An honest estimate
could therefore delete a read that must happen — planning precedes execution, so a table
empty at plan time can still be written and read back by the same statement.

The proof now has its own channel:

- `BestAccessPlanResult.provablyEmpty?: boolean` — set only when the module has proven no
  row can satisfy the filters it claimed. `rows` is an estimate with no exception.
- `AccessPlanBuilder.empty(handledFilters)` builds the entire answer (cost 0, rows 0, the
  filter claims, the flag) and throws if the claims are all false, so the shape cannot be
  half-expressed. `setProvablyEmpty()` exists for a module that built its plan another way.
- `validateAccessPlan(request, result, moduleName?)` rejects (`StatusCode.INTERNAL`) a
  `provablyEmpty` plan that claims no filter, and one whose `rows` is anything but 0
  (`undefined` included). Rejected, never normalized. The new optional third argument names
  the offending module in the message; the memory module and both planner probe sites pass
  `tableInfo.vtabModuleName`.
- The fold in `selectPhysicalNode` tests `accessPlan.provablyEmpty` and no longer looks at
  `rows`. The `handledFilters.length > 0 && every(...)` conjunct stays purely as a runtime
  backstop for modules that never call `validateAccessPlan` (the store module does not).
- The memory module's `IS NULL` on a NOT NULL column arm now builds its answer with
  `AccessPlanBuilder.empty(...)`.
- Three `Math.max(1, ...)` floors were re-commented, not removed: they are now conservative
  cost-model guards rather than load-bearing correctness guards.
- `docs/module-authoring.md` rewrites the row-count contract and carries an explicit
  "contract change" callout; `docs/optimizer-costing.md` and `docs/store.md` were stale on
  the same protocol and were corrected.

## Behavior change worth checking

A third-party module that returned `rows: 0` with every filter claimed and no flag used to
have its access folded away. It is now READ and its filters enforced normally. That is the
correct new behavior (the old one could return nothing for rows the same statement wrote),
but it IS a visible change for such a module, and it is called out in the docs.

## Use cases / how to exercise

- `select ... where <not-null col> is null` on a memory table — still plans to `EMPTYRESULT`
  and returns nothing. The memory module's proof is the one shipped producer of the flag.
- A module answering a filtered request with `AccessPlanBuilder.empty(...)` — access folds
  away (`packages/quereus/test/optimizer/empty-relation.spec.ts`, `ProvenEmptyModule`).
- A module stamping `rows: 0` on a plan that claims every filter — the table IS read and the
  row comes back (`ZeroEstimateModule`, same file). This is the regression the ticket exists
  for; before the change this query returned nothing.
- A module reporting a live count of zero on a no-filter scan — unchanged, still read
  (`LiveCountModule`, same file, pre-existing).
- `validateAccessPlan` rejections and `AccessPlanBuilder.empty` guard —
  `packages/quereus/test/vtab/best-access-plan.spec.ts`.
- Store backend: `yarn test:store` was NOT run (see gaps). The store module never sets the
  flag and its floors are unchanged, so its plan shapes should be identical.

## Known gaps / where to look hardest

- **The `every(...)` backstop is stricter than soundness requires.** A proof over a claimed
  filter holds no matter what the engine does with the unclaimed ones (they can only remove
  more rows), so a module claiming 1 of 2 filters with `provablyEmpty` passes validation but
  does NOT fold. That is a lost optimization, never a wrong answer, and it is what the
  ticket asked for. Worth a second opinion on whether `some(h => h)` is the better guard —
  it would match what validation enforces.
- **No module in the tree exercises `setProvablyEmpty()`** (only `empty()`), so that setter
  is covered by the builder unit test alone.
- **`quereus-isolation` audit result:** the layer delegates `getBestAccessPlan` verbatim
  (flag carried through). The one place it BUILDS a plan is the fallback for an underlying
  module that has no `getBestAccessPlan`; it claims no filter and sets no flag, which is the
  safe answer. Commented in place. No spread/rebuild sites elsewhere — worth re-grepping if
  the reviewer wants independent confirmation.
- **`schema/lens-prover.ts` ~2472** was checked and is unrelated (a coarse cardinality band
  for a fingerprint, not an access-plan signal). Untouched.
- **The seek-side empty-result paths** in `rule-select-access-path` (NULL seek keys, all-NULL
  `IN` lists) build `EmptyResultNode` from planner-side proofs, not module answers. Confirmed
  unaffected; untouched.
- **Tripwires recorded as `NOTE:` comments, not tickets** — the three `Math.max(1, ...)`
  floors (`vtab/memory/module.ts` `estimateEqualityRows`,
  `quereus-store/src/common/store-module-access-plan.ts`,
  `quereus-store/src/common/store-module.ts` `sizeRequestFromLiveCount`) each say they are
  now conservative and can be revisited if a genuine zero estimate ever needs to reach the
  cost model. Removing them is a cost-model change with its own plan churn.
- Stale comment reference to `backlog/debt-empty-access-plan-fold-trusts-estimate` deleted
  as instructed; that ticket does not exist on the board or in the pruned ledger.
