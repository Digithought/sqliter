# What changed

Both assertion DROP guards asked *"does this one assertion body mention this one
object, in this one schema?"*. They now ask *"can this assertion — in any schema —
reach this object?"*, where reach is the closure over stored view and
materialized-view bodies.

## The new primitive

`collectTableRefsInAst` (`schema/rename/table-rename.ts`) is a **third sink** over
the same `walkTableRefs` traversal the rename rewrite and the read-only probe
already share — no second traversal was written. It returns
`Map<canonicalKey, objectNameLower>`; the name is returned rather than re-derived
because a schema name may contain a dot, so splitting a key by separator scan is
wrong (`objectRefKeySchema` does the split, and needs the name).

Because it is the same traversal, the closure inherits scope-awareness for free: a
`with t as (…)` that merely shadows a name contributes no key, so the widening
cannot false-refuse where the direct probe already did not.

## The closure

`schema/object-dependency-closure.ts` — `reachableObjects(db, root, homeSchema,
resolvers)`, breadth-first from a root body over stored bodies, each walked under
**its own** home-schema resolver, terminating on a visited set of object keys.

`resolvers` is a required parameter, not built inside: a caller looping over many
assertions must share ONE pre-mutation snapshot, and a default argument would have
silently given each root its own.

Returns `bodies` (root first, then breadth-first) and `namerOf(key)`. Each
`ReachedBody` carries a `path` — the described chain from the root to it inclusive
(`["view 'v2'", "view 'v1'"]`) — which is what the error messages quote.

## The guards

- **Table verb** (`assertNoAssertionDependsOn`): scans assertions in every schema,
  home schema first, and refuses when the dropped key is in the reach.
- **Column verb** (`assertNoAssertionNamesColumn`): same scan, then probes **every
  body in the reach** — the assertion's own included — with `columnReferencedInAst`.
  No column lineage through a view's projection is built and none is needed: if no
  body in the chain names the column, the assertion could not have been reading it.

Messages keep the old wording for a direct reference and add the chain for an
indirect one, and qualify the assertion when it lives in another schema than the
dropped object.

# How to exercise it

All of the below reproduce as failures at the parent commit and pass now.

```sql
-- Reached through a view
create table t (x integer primary key);
create view v as select * from t;
create assertion av check (not exists (select 1 from v where x < 0));
drop table t;
-- cannot drop table 'main.t': assertion 'av' reaches it through view 'v' — drop or redefine the assertion first

-- Three deep; intermediate views guarded too
create view v1 as select * from t; create view v2 as select * from v1;
create assertion ad check (not exists (select 1 from v2 where x < 0));
drop table t;   -- … 'ad' reaches it through view 'v2' -> view 'v1'
drop view v1;   -- … 'ad' reaches it through view 'v2'
drop view v2;   -- … 'ad' still refers to it

-- Another schema's assertion
create table main.q (x integer primary key);
create assertion temp.qa check (not exists (select 1 from main.q where x < 0));
drop table main.q;   -- … assertion 'temp.qa' still refers to it

-- Column verb, through a view
create table u (id integer primary key, x integer);
create view uv as select id, x from u;
create assertion ua check (not exists (select 1 from uv where x < 0));
alter table u drop column x;
-- Cannot drop column 'x' from 'u': it is referenced by assertion 'ua' through view 'uv' — …
```

## What must still be ACCEPTED (the false-refusal shapes)

These are the ones worth attacking — over-refusal is the risk this change carries,
since it turns previously-legal drops into errors:

- A `with t as (…)` in an assertion body that merely shadows the dropped name.
  Pinned in both sqllogic files; the collect-everything mistake would lose exactly
  this.
- A FROM alias shadowing the name.
- An assertion in `temp` whose bare `t` binds `temp.t` — does not block dropping
  `main.t`.
- A plain view over the dropped table with **no** assertion reading it: the
  engine's stated asymmetry. The view breaks, the drop stands.
- A view in the chain that names the table but not the dropped column
  (`select id from t` while dropping `t.x`).
- An unrelated drop with a live assertion in the database.

# Known gaps — read these before trusting the diff

- **`yarn test:store` was not run.** Both guards run in the emitter, before any
  `requireVtabModule` / `module.alterTable` call, so the store path sees the same
  refusals — but that is an argument, not a measurement.

- **The CHECK / DEFAULT / generated family is still one hop.** Deliberately out of
  scope; it is `fix/4.7-expression-guards-follow-view-chains`, which is written to
  consume this closure rather than grow a second one. Both `docs/sql-alter.md` and
  `schema/expression-dependents.ts` still document that limit, now re-pointed at
  the module instead of at this ticket's slug.

- **The closure walks every body without `rowImageContext`, and the next consumer
  must not inherit that silently.** Correct for everything it walks today (view
  bodies and assertion CHECKs own no `new.` / `old.` namespace), wrong for a root
  that is a table CHECK or column DEFAULT — a table literally named `new` would
  land in the reach and false-refuse its own drop. Recorded as a `NOTE:` on
  `reachableObjects`; the fix belongs to 4.7, where it can be tested.

- **Cycle termination is only pinned by injection.** The parser has no
  `create or replace view`, so no statement sequence builds a view cycle; the spec
  swaps a `ViewSchema.selectAst` behind the planner's back to close one. The
  visited set still guards a real path — `importDDL` and store-backed catalog
  reload both add views without checking the graph is acyclic — but the test is
  white-box and would not catch a cycle arriving by some other route.

- **Cost is a per-drop BFS per live assertion, uncached.** Recorded as a `NOTE:`
  at both guard sites with what would make caching worth it (many assertions over
  deep view chains). Not measured — DDL is rare and the walks are over
  already-parsed ASTs, so no number was taken.

- **Which assertion a refusal names, when two block, follows catalog insertion
  order** past the home schema. `NOTE:` on `assertionsHomeSchemaFirst`. Harmless
  while the message is advisory, and it mirrors the existing
  `tablesProbedTargetFirst` behaviour.

- **`95-assertions.sqllogic` had a comment pointing at
  `backlog/bug-drop-table-under-view-an-assertion-names`** describing the
  bare-name-falls-through arm as an open miss. That arm is closed and the comment
  is gone; the backlog ticket itself was already folded into the 4.x sequence and
  is not on the board.

# Suggested review attack surface

- The `path` / `namerOf` contract when the SAME object is reachable by two
  different chains — breadth-first means the shorter one wins, but nothing pins
  which one wins at equal depth.
- `objectRefKeySchema(key, nameLower)` in `expandStoredBody` — it assumes the key's
  name half is exactly the reference's lowercased name. True by construction of
  `collectTableRefsInAst`, but it is the one place the two files are coupled by an
  invariant rather than by a type.
- Whether the column verb should ALSO refuse when a body in the reach names the
  table but the column only survives via `select *` re-exposure — the current
  answer is no (§7-style bodies drop freely), and that answer is asserted, not
  derived.
