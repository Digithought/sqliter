# Two UNIQUE constraints may not derive one backing structure name

## What was wrong

Every `UNIQUE` rule is enforced through a hidden backing structure whose name is the
constraint's own name when it has one, and `_uc_<covered column names joined by _>` when
it does not. Nothing stopped two rules on one table deriving the *same* name:

```sql
-- 1. a constraint name written with the engine's reserved `_uc_` prefix
create table t (id integer primary key, c integer, b integer,
                constraint _uc_c unique (b), unique (c));        -- both derive `_uc_c`

-- 2. no reserved prefix — the `_`-joined auto-name colliding on ordinary names
create table t (id integer primary key, a_b integer, a integer, b integer,
                unique (a_b), unique (a, b));                    -- both derive `_uc_a_b`
```

On the memory backend the second constraint adopted the first's structure and was then
enforced by one keyed on the *other* constraint's columns — silently accepting duplicates
it should reject. `ALTER TABLE` already refused the same declaration, but only on memory
and only by accident (the guard compared against `tableSchema.indexes`, where the memory
module happens to materialize a constraint's structure and the store module does not).

## What changed

**`schema/catalog.ts`** — a constraint-side twin of the existing index-side search:

- `findUniqueConstraintSharingBackingName(tableSchema, constraintName, columnNames)`
  searches `tableSchema.uniqueConstraints` (which *both* backends carry) for a constraint
  whose own derived structure name case-folds equal to the prospective one. Skips
  `derivedFromIndex` constraints — their structure *is* the `CREATE UNIQUE INDEX` that
  synthesized them, already compared by the index arm.
- `assertUniqueConstraintIndexNameFree` runs that arm **before** the `.indexes` arm, so a
  collision both arms can see reports identically on memory and store. Existing message
  (`would collide with existing index '<name>'`) is byte-unchanged for index collisions.
- `assertUniqueConstraintBackingNamesDistinct(declared, operation)` is the pairwise form
  for callers holding a whole declaration with no table to compare against;
  `assertNoDuplicateUniqueConstraintBackingNames(constraints, columns, operation)` is the
  built-constraint wrapper over it.

**`schema/manager.ts` `createTable`** — calls the wrapper immediately after
`assertNoDuplicateUniqueConstraints` (so a genuine duplicate keeps its constraint-worded
message) and before `module.create` (so a refusal leaves no storage behind). Not on
`importTable` / `importDDL`.

**`runtime/emit/alter-table.ts` `runAddColumn`** — **beyond the ticket's TODO list**: two
inline `unique` constraints on one *new* column can derive one name without duplicating
each other (`add column c text constraint _uc_c unique unique`), and neither is on the
table yet, so no per-constraint check could see the pair. The pairwise form runs once
after the existing per-constraint loop (after, so a plain duplicate still reports as a
duplicate). Flagging it explicitly since it was not in the ticket.

### Messages

```
Cannot <op>: its backing structure '<name>' would collide with the backing structure
of the UNIQUE constraint <other> on the same table. Rename the constraint.

Cannot <op>: the UNIQUE constraint <a> and the UNIQUE constraint <b> both derive
backing structure name '<name>'. Rename one of them.
```

`<other>` / `<a>` / `<b>` name each side the way the user wrote it — `'<name>'` when
named, `on (<cols>)` when not. **Minor deviation from the ticket**, which spelled the
first message's other side as `on (<columns>)` unconditionally; naming a named constraint
by its name reads better and matches the ticket's own instruction for the second message.

## Use cases to test / validate

Refused (all of these, on **both** backends, with the same message):

- `create table t (id integer primary key, c integer, b integer, constraint _uc_c unique (b), unique (c))`
- `create table t (id integer primary key, q_r integer, q integer, r integer, unique (q_r), unique (q, r))`
- the same with mixed case (`constraint _UC_C …`) — folds
- the same with a column-level `unique` on one side and a table-level one on the other
- `alter table t add constraint _uc_c unique (b)` where `unique (c)` is already declared
- `alter table t add unique (c)` where `constraint _uc_c unique (b)` is already declared
- `alter table t add column c text unique` where `_uc_c` is another constraint's name
- `alter table t add column c text constraint _uc_c unique unique`
- `alter table t rename column x to m` where the post-rename auto-name is another
  constraint's derived name — and nothing moves
- `alter table t rename constraint u to _uc_<other constraint's columns>`
- `apply schema` carrying any declaration above (it emits ordinary CREATE/ALTER statements)

Still legal — the negative controls that matter most for regression:

- two differently-named UNIQUEs over the same columns
- a named UNIQUE beside an unnamed one over the same columns
- a UNIQUE whose columns are already covered by a user index of a *different* name
  (structure reuse matches on columns, never names)
- a constraint synthesized by `create unique index`, plain or partial — the constraint arm
  skips it, so a declaration onto that name is still refused as an *index* collision with
  the old message
- case-only `rename column` / `rename constraint`
- every pre-existing `would collide with existing index '<name>'` assertion — re-confirmed
  green, none moved

Legacy catalogs: the guard is on `createTable` only, so a catalog written before it still
opens. Pinned in `packages/quereus-store/test/index-persistence.spec.ts` by hand-editing a
persisted bundle into the colliding shape and reopening.

## Known gaps / things worth a reviewer's eye

- **The legacy-catalog test could not be written memory-side.** `importTable` rehydrates
  through `module.connect`, and the memory module has no definition to connect to for a
  table it never created, so `importCatalog(['CREATE TABLE …'])` fails with
  `Memory table definition for 't' not found` regardless of this ticket. The test lives in
  the store package instead, where rehydrate is real; a `NOTE:` at the old site in
  `index-ddl-roundtrip.spec.ts` points there. The store test simulates the legacy catalog
  by regex-rewriting the persisted bundle — brittle against DDL-generator format drift,
  though it asserts the rewrite actually changed the text, so drift fails loudly rather
  than silently passing.
- **`RENAME COLUMN` compares against the table's CURRENT derived names**, including those
  of constraints the same rename is about to move. Argued sufficient in the doc comment on
  `findUniqueConstraintSharingBackingName` (two constraints can only newly collide under a
  rename if both cover the renamed column, and two such names differ only in their
  unrenamed parts). Worth a second read — it is the one place the guard reasons about a
  future state rather than a present one.
- **`RENAME COLUMN` self-comparison is not explicitly excluded.** The constraint being
  renamed is in the searched set under its pre-rename name; safe because a non-case-only
  column rename always changes the joined name, and case-only renames are gated out before
  the loop. Symmetric with the pre-existing `.indexes` arm, which has the same exposure on
  memory (the constraint's own structure is materialized there under the old name).
- **Partial UNIQUE constraints are covered only through the index arm.** A declared
  `UNIQUE` is never partial (`AST.TableConstraint` has no predicate field), so every
  partial UNIQUE constraint today is `derivedFromIndex` and its structure is its own index.
  Tested that way; if a declared partial UNIQUE ever becomes expressible, the constraint
  arm already handles it (it compares names, not rules) but nothing pins that yet.
- **Message wording deviates slightly from the ticket** — see *Messages* above.
- The naming rule itself is untouched: `_uc_<cols>` stays ambiguous by construction
  (`(a_b)` vs `(a, b)`), because it is persisted in existing catalogs and mirrored by
  `quereus-store`'s `implicitUniqueIndexName` and `MemoryTableManager.implicitIndexNameFor`.
  The collision is refused rather than the name disambiguated.
