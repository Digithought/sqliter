# Run a high-latency index-nested-loop join's seeks concurrently — implemented

## What shipped

An **index-nested-loop join** (one index seek into the inner table per outer
row) whose seek provably returns at most one row per outer row is now also
offered, inside `ruleJoinPhysicalSelection`'s cost comparison, as a
**one-branch `FanOutLookupJoinNode` in `batched` outer mode**. The fan-out's
existing batched driver (`runFanOutLookupJoinBatched`) keeps many seeks in
flight under a shared budget and re-orders finished rows back into outer order,
so the output is identical to the one-at-a-time plan while a remote module's
round trip is paid once per batch rather than once per row. No runtime code
changed; the driver is reused verbatim.

The pieces, in the order the ticket listed them:

1. **The at-most-one proof** — `provesAtMostOne(tableSchema, combined)` in
   `index-nested-loop.ts`, exported, with `atMostOne` (plus `rowsPerSeek` and
   `perSeekLatencyMs`, so the caller can re-price without re-probing) added to
   `IndexNestedLoopCandidate`. Reads the full constraint list offered to the
   module; holds when some enforced key — primary key, non-partial UNIQUE
   constraint, or non-partial UNIQUE index — has every column pinned by an
   equality whose collation is BINARY or equal to the key's enforcement
   collation. Key collations come from `uniqueEnforcementCollations` (index
   per-column COLLATE for an index-derived constraint, else the column's), and
   from the PK member's own collation for the primary key, rather than always
   the column's declared collation — a `create unique index … (b collate
   nocase)` is enforced NOCASE even over a BINARY column, and the proof reads it
   that way. **One gate beyond the ticket's spec:** an equality whose value
   side is non-deterministic (`b.id = random()`) does not count — nothing
   upstream keeps such a predicate out of pushdown, and a Filter re-applying
   it is re-evaluated per inner row, so several rows could pass.
2. **`toBatchedOuter(node, tuning.parallel)`** extracted from
   `rule-fanout-batched-outer.ts` — every gate, the `EagerPrefetchNode` wrap
   and the rebuild, verbatim; `ruleFanOutBatchedOuter` is a two-line wrapper.
   Its idempotence gate is what lets the rule later re-visit a node the
   selection rule already flipped (pinned: one fan-out, one prefetch).
3. **`batchedIndexNestedLoopJoinCost(outerRows, rowsPerSeek, perSeekLatencyMs,
   inFlight)`** in `cost/index.ts`; in-flight count
   `min(outerBatchConcurrency, maxOuterReadAhead)`, with the coupling to
   `deriveReadAhead` stated at both ends. `tryBatchedIndexNestedLoop` in the
   selection rule builds the serial one-branch node (branch = `Filter(ON)` over
   the rebuilt inner, `atMostOne-inner` / `atMostOne-left`, `concurrencyCap` 1,
   un-mirrored pins the join's attributes, mirrored derives), hands it to
   `toBatchedOuter`, and prices the result only if it came back — a serial
   one-branch fan-out is never entered into the comparison. Two new candidates:
   `index-nl-batched` directly after `index-nl`, `index-nl-mirrored-batched`
   directly after `index-nl-mirrored`, all strict `<`.
4. Both `NOTE:`s (dropped `usingColumns` EXPLAIN label; row estimate becomes the
   outer's cardinality) sit on `tryBatchedIndexNestedLoop`'s doc comment.

**Inert in-tree, by construction and by a short-circuit:** at
`perSeekLatencyMs === 0` the selection rule does not even build the node —
the batched price equals the serial one there and a strict `<` after the
serial entry could never pick it — so the golden-plan hot path constructs
nothing new. The full golden sweep is unchanged.

## How to exercise it

Register a module that declares `expectedLatencyMs` (tests use
`class HighLatencyMemoryModule extends MemoryTableModule { readonly expectedLatencyMs = 25; }`),
put the **inner** table on it, and either give the outer ≥ 256 rows
(`batchedOuterMinRows`) or lower that knob to 0 via
`db.optimizer.updateTuning({ ...t, parallel: { ...t.parallel, batchedOuterMinRows: 0 } })`.
Then:

```sql
select s.id, big.w from s join big on big.id = s.k          -- big.id is the PK
```

plans as `FanOutLookupJoin(N=1, cap=1, batched) [b0:atMostOne-inner]` over
`EagerPrefetch(s)` with branch `Filter(big.id = s.k) / IndexSeek(big primary)`.
`left join` gives `atMostOne-left`; the same query against plain `memory` stays
the serial index-nested-loop.

## Known gaps / things for the reviewer to push on

- **A user Filter above a walk leaf is invisible to the proof.** The proof reads
  `offered.combined` — join keys plus the displaced *seek* leaf's
  `pushedConstraints`. A predicate the module could not push (`where b.id = 5`
  on the second column of PK `(tenant, id)` with no index on `id`) stays a
  `Filter` above an `IndexScan`, the walk arm offers only the join key, and the
  candidate is unproved even though that Filter would make it true. Pinned by a
  negative test; the ticket's composite example needed `create index … (id)` to
  be real. `feat-index-nested-loop-offer-filter-predicates` (backlog) would fold
  those predicates into `combined`, and the proof would see them for free.
- **The proof's soundness argument leans on the rule's correctness invariant**
  ("every constraint in `combined` is enforced somewhere in the rebuilt inner").
  That invariant is argued in `index-nested-loop.ts`, not asserted; a future
  change that drops a declined pushed constraint instead of re-applying it would
  silently turn a proof into a runtime `CONSTRAINT` error. Worth a reviewer's
  eye on whether a cheap assertion belongs at the construction site.
- **Cross-type equalities over a TEXT unique key are not specially handled**
  (`b.name = 5` against `name text unique`). SQL `=` with coercion is assumed to
  be at least as fine as the key's equality; I did not find a case where it is
  coarser, but did not prove it either.
- **Hash join's latency pricing still favours hash on shapes it should lose**
  (a remote full scan is priced as one round trip). Out of scope — filed
  earlier as `feat-per-row-latency-cost-for-remote-scans`.
- No wall-clock measurement. The ~10× crossover claim in the docs is evaluated
  from the formulas, as the plan ticket said.
- `HighLatencyMemoryModule` is duplicated into one more spec
  (`debt-shared-high-latency-test-module` already tracks consolidation).
