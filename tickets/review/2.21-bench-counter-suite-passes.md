benchmarks, which declare none on purpose and now say so in a comment.

| suite | declares `counters()` | what it snapshots |
|---|---|---|
| execution | 15 / 15 | `snapshotStatement` — the same query `fn` times |
| mutation | 4 / 4 | `snapshotStatement` / `snapshotStatements` — see below |

## Acceptance: stability was measured, and it holds

```
node bench/run.mjs                    # run A → results/2026-08-19T12-52-31-706Z.json
node bench/run.mjs --baseline latest  # run B → results/2026-08-19T12-53-24-419Z.json
```

Run B's summary line:

```
Counters: 23 identical, 0 changed, 0 new, 0 dropped (never gated)
```

Every `Counters` cell read `same` for the 23 collecting benchmarks and `—` for the 4
parser ones. **The work-counter-changes block did not print at all.** Nothing had to have
its `counters()` removed.

Confirmed a second way, independent of the harness's own comparison — a direct
`JSON.stringify` diff of the two results files' `counters` blocks:

```
byte-identical counters blocks: 23 | differing: 0 | no counters either side: 4
```

Worth noting for the reviewer: `execution/join-1kx1k` and `mutation/delete-where-100` were
both flagged **timing**-unstable in these same runs (spread 21.2% / 21.6%, excluded from
timing gating) and their counters still came back byte-identical. That is the property the
whole feature is for, demonstrated rather than asserted.

## Cost of the counters pass: +834 ms on a ~48 s run (+1.8%)

Two runs each way, `wall_clock_ms` straight from the results files:

| | run 1 | run 2 | mean |
|---|---|---|---|
| with counters | 48 567 ms | 47 681 ms | 48 124 ms |
| `--no-counters` | 47 293 ms | 47 286 ms | 47 290 ms |

Delta **+834 ms, +1.8%**.

That delta is close to run-to-run wall-clock noise (the two counters runs differ from each
other by 886 ms), so it is corroborated rather than left standing alone: summing one median
per collecting benchmark from run A predicts **858 ms** of extra untimed work. Predicted 858,
observed 834 — the counters pass costs almost exactly the one extra execution per benchmark
it is defined to be, and nothing else.

# Two design calls that deviate from the ticket, and are the first thing to review

**1. Execution SQL was hoisted into a shared `SQL` object rather than duplicated.**
The ticket showed `counters() { return snapshotStatement(db, 'select * from bench_t'); }`,
which repeats the query literal already inside `fn`. Doing that 15 times creates a drift
hazard with a nasty failure mode: edit the query in `fn` alone and the counters pass keeps
reporting perfectly *stable* counts for a statement the benchmark no longer runs. So each
query is now named once in a module-level `SQL` map and referenced twice. This also matches
what `planner.bench.mjs` already did with `simpleScan` / `joinPlan` / etc.

**What to check:** that every hoisted string is byte-identical to the literal it replaced,
including the two multi-line template literals (`correlatedSubquery`, `handBatchedPeerCount`)
whose indentation changed when they moved. A mechanical check that each key is used exactly
twice passes (15 keys × 2), but that does not prove the *contents* survived — the diff does.

**2. `mutation.bench.mjs` was restructured, not just appended to.**
Three of its four `fn`s build their own `Database`, so their `counters()` must too. Rather
than write a second copy of each populate loop, the row-tuple builders and the batch-insert
helper are now shared between `fn` and `counters()` (`batchInsert`, `bulkRow`, `updRow`,
`delRow`, `singleRowInsert`), and the schema/statement strings are named constants. This
touches the timed path of all four benchmarks.

**What to check:** that the timed `fn`s still issue exactly the SQL they did before. The
medians in run A/B are consistent with the pre-change ones recorded in `execution.bench.mjs`'s
own comments (bulk-insert 105/108 ms vs the "121-173 ms" noted there, on a quieter machine),
but that is weak evidence — read the diff.

# Per-suite notes

**execution** — one `snapshotStatement` per benchmark against the `setup` database.
`correlated-subquery` carries an extra comment: its counters catch a
`scalar-agg-decorrelation` regression *before* the existing `ratioGuards` entry does, because
an N+1 regression multiplies `queryCalls` and `rowsScanned` on `main.bench_t` exactly, with
no second benchmark needed and no variance to tolerate.

**mutation** — `update-where-1k` reuses the `setup` database via `snapshotStatements` for its
apply/reverse pair. The other three build, populate and close their own. Both insert
benchmarks snapshot the **first and last** batch as two named entries, per the ticket.

Measured result of that: **the first and last snapshots come out identical** — 6 instruction
executions and 500 `updateCalls` for bulk, 1 `updateCall` for single-row, `rowsScanned: 0`
both ends. Insert work does not grow with table depth at the granularity these counters
record. Both are kept anyway and the comment says why: the equality is now asserted on every
run, so a change that starts scanning or re-probing on insert moves `lastBatch` away from
`firstBatch` and the diff prints it. A reviewer could reasonably argue the second snapshot is
redundant duplication — that is the honest counter-argument, and the answer is that it is a
free invariant, not free duplication.

**planner** — `snapshotPlanShape` only, with a comment at the top of the benchmarks array
explaining that this is the whole counter surface available to a prepare-only benchmark and
that the node-type tallies are what would catch a hash join regressing to a nested loop.

**parser** — comment only, as specified.

# Known gaps — read these before signing off

- **`yarn lint` is red, and it was red before this ticket.** Seven `tsc` errors in
  `bench/lib/compare.mjs` and `bench/lib/counters.mjs`, both landed by the previous ticket
  (`9e6bbcd2f`). `tsconfig.test.json` type-checks `bench/lib/**/*` but not `bench/suites/**`,
  so nothing in this diff can reach them. Written up in full, with a per-error root-cause
  sketch, in `tickets/.pre-existing-error.md`. **Not fixed here** — the runner's triage pass
  owns it. Do not re-file it.

- **Stability was proven on one machine, one Node version, two consecutive runs.** Windows 11,
  Node v24.2.0, AMD Ryzen AI 9 HX 370. The counters are *designed* to be machine-independent
  and the per-benchmark process isolation makes the A/B comparison a genuine
  separate-process check — but "identical across Node versions / OSes / architectures" is
  **not** tested by anything here. If the downstream regression gate is meant to compare a
  developer's laptop against CI, that cross-machine claim still needs its own evidence.

- **Two runs is a thin sample.** The stability check is n=2. A counter that varies once in
  twenty runs would have passed this.

- **`update-where-1k`'s pass depends on `fn` being its own inverse.** The apply/reverse pair
  leaves `upd_t` as it found it, which is what makes the counters independent of how many
  iterations calibration chose. That reasoning is written at the site, but it is an invariant
  a future edit could break silently — a non-idempotent `fn` there would make the counters
  iteration-count-dependent, and the first symptom would be a mystery `changed` verdict.

- **Tripwire parked in code, not filed as a ticket:** the three own-database mutation passes
  each populate a full 10K-row table, ~340 ms of the ~830 ms total. Fine at four benchmarks;
  if this file grows to a dozen, the untimed pass becomes a visible share of the run. `NOTE:`
  at the top of `mutation.bench.mjs` records the condition and the fix (populate fewer rows in
  `counters()` than in `fn` — the counts do not need the timed row count to be meaningful,
  only to be the same every run).

- **Not exercised:** the `dropped` counter verdict. `new` was seen incidentally (comparing a
  filtered run against a `--no-counters` baseline correctly reported 4 new); `same` was seen
  23 times; `changed` and `dropped` were never produced by a real run here.
