# What was built

`ANALYZE` computes per-column distinct counts, null counts, min/max and histograms and
writes them onto `TableSchema.statistics`, which is memory-only. The store already persisted
each table's ROW COUNT (a `TableStats` record per table in the unified `__stats__` store,
keyed by `schema.table`); the column numbers now ride in that same record.

Three seams:

**The hook.** `VirtualTable.saveStatistics?(stats)` is optional and **advisory** — `ANALYZE`
calls it after writing statistics onto the schema, and a rejection is logged and swallowed
rather than failing the statement. The memory backend does not implement it and is
unaffected. `IsolatedTable` forwards `getStatistics` and `saveStatistics` as optional
*fields*, wired only when the underlying implements them, so "this module declines" survives
the wrapping.

**The record.** `TableStats` gained three optional fields: `columnStats` (keyed by lowercase
column name), `analyzedRowCount`, `lastAnalyzed`. Optional means a record written before this
change reads back as "no column statistics" — no migration, no version field.
`serializeStats`/`deserializeStats` now route through the row codec's `replacer`/`reviver`
instead of bare `JSON.stringify`, because min/max and histogram bounds are `SqlValue`s (bare
stringify throws on `bigint` and silently mangles `Uint8Array`).

**The read-back.** `StoreTableBase.primeStats` is the single owner of the stamp: it loads the
record and calls `publishPersistedStatistics`, which writes the snapshot onto the REGISTERED
`TableSchema` (silently — `schema.addTable` with no `notifyChange`, since rehydration must not
drive the module's own listener). `rehydrateCatalog`'s reconcile loop calls `primeStats`
directly, and `initializeStore` calls it on first storage access — so the stamp lands whether
or not a table happened to be connected during rehydration, and it never overwrites a fresher
in-memory `ANALYZE`.

Two deliberate scope decisions worth checking:

- **`getStatistics()` still reports an empty `columnStats`** even though the table now holds a
  snapshot. `collectTableStatistics` reads a non-empty `columnStats` as "module answered
  cheaply, skip the scan", so echoing the snapshot would make `ANALYZE` a no-op that re-saves
  numbers it never recomputed.
- **Histograms are persisted only for a PK member or an index's LEADING column**
  (`histogramColumns` in serialization.ts, with the size arithmetic in its comment: ~100
  buckets × ~40 bytes ≈ 4 KB per column, and the whole record is read/written as one value).
  Scalars persist for every column. A dropped histogram costs a re-`ANALYZE` and nothing else.

# How to exercise it

```sql
-- against any store-backed database (leveldb / indexeddb / the in-memory KV provider)
create table t (id integer primary key, k integer not null, plain text) using store;
create index ix_k on t (k, plain);
-- ...insert rows...
analyze t;
-- close the database, reopen it over the same storage, then:
select * from query_plan('select id from t where k = 2');
```
The access node's `est_cost` should match what it was before the close. Before this change it
reverted to the unanalyzed cost.

Automated: `packages/quereus-store/test/stats-persistence.spec.ts` (9 cases) and the third
case in `rename-stats-migration.spec.ts`. Run them alone with:

```
node --import ./packages/quereus-store/register.mjs node_modules/mocha/bin/mocha.js \
  "packages/quereus-store/test/stats-persistence.spec.ts" \
  "packages/quereus-store/test/rename-stats-migration.spec.ts" --reporter spec
```

Covered: survives reopen (values + plan cost); bigint-past-2^53 and blob min/max round-trip;
histogram kept for PK and leading-index column, dropped for a non-seekable one while its
scalars stay; a hand-written pre-change `{rowCount, updatedAt}` record reopens without
throwing and yields no statistics; re-`ANALYZE` after a reopen still scans (the regression
guard for the `getStatistics()` decision); a table never connected during rehydration still
gets its statistics; a disk snapshot does not displace a fresher in-memory one; the same
survives-reopen assertion through `@quereus/isolation`; rename carries the snapshot.

# Known gaps — treat the tests as a floor

- **No test for a column renamed or dropped between `ANALYZE` and the reopen.** The ticket
  asked for an assertion that `columnStats` stays NAME-keyed (a positional key would silently
  match a different column). The keying is name-based in code and documented as such in
  `TableStats.columnStats`, but nothing pins it. This is the most valuable missing test.
- **Histogram scale is never exercised.** The spec seeds 24 rows; `collectStatisticsFromScan`
  samples up to 1000 and builds up to 100 buckets. Nothing tests a record near the size the
  `histogramColumns` arithmetic is defending against, so the size claim in that comment is
  reasoned, not measured.
- **Only the in-memory KV provider is tested.** No leveldb/indexeddb-backed reopen assertion;
  the shipped providers share the unified-`__stats__` layout the test provider mirrors, but
  that equivalence is asserted by reading, not by running.
- **`getEstimatedRowCount` still reports the delta-tracked live count**, which `ANALYZE` does
  not reconcile — `saveStatistics` writes the scan's exact count to `analyzedRowCount` only,
  deliberately, so no existing caller's behaviour changes. Whether `ANALYZE` *should* also
  correct a drifted live count is a real open question, out of scope here.
- **`bug-drop-table-leaves-stale-stats-entry`** (backlog) still applies: `DROP TABLE` leaves
  the `__stats__` entry behind. This change makes that orphan BIGGER, not differently wrong.
  Not fixed here, per the ticket.
- **Cross-connection visibility is unchanged and untested.** Connection A's `ANALYZE` is
  invisible to connection B until B reopens or re-analyzes — same model the row count already
  has. Documented in `docs/module-authoring.md`; no test asserts it.
- **A crash between the schema write and the flush** leaves memory and disk disagreeing. By
  design (statistics are advisory, the next `ANALYZE` reconciles) — no transaction was added.
