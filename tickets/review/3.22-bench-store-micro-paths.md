# What landed

The `store` benchmark suite grew from 11 to 25 entries. The 11 existing rows price key
encoding by calling `@quereus/store` functions directly. The 14 new rows each drive one
storage hot path through a `Database` opened over the store module, and their `counters()`
pass **asserts** the exact expected storage round trips — an exact-integer claim, identical
on every machine — rather than only reporting them:

- `scan-10k` — full scan: 10 000 index-free `iterateEntries`, nothing else anywhere.
- `point-read-pk` — exactly one `singleGets`; a point read that became a range scan or a
  one-key batch fails the pass.
- `multi-seek-pk-10` / `multi-seek-pk-over-batch` — IN-list seeks batch into
  `ceil(k / ROW_RESOLUTION_BATCH)` `getMany` calls carrying k keys.
- `index-resolve-{quarter,one,two,four}-batch(es)` — secondary-index range of width n:
  n index `iterateEntries`, then `ceil(n / B)` batched data-store reads carrying n keys,
  zero data iterates. Widths derive from the imported `ROW_RESOLUTION_BATCH`, never a
  restated 256.
- `commit-update-{1,10,100,1000}` — `begin; update; commit` timed as a unit. The four
  sizes carry the flat-batch claim: `batchWrites` stays 1 per touched store while
  `batchOps` scales N (data) / 2N (index); `directPuts`/`directDeletes` asserted 0.
- `index-build-5k` — create index over 5 000 rows, verify 5 000 physical entries, drop.
- `catalog-rehydrate-54t` — reopen cost: fresh `Database` + module over a kept provider,
  `rehydrateCatalog`, asserting 54 tables / 9 indexes / 14 views / 0 errors per call.

Harness widening (`bench/lib/store-counters.mjs`): handles now carry `module`,
`storeModule`, `provider`, `closeDbOnly()` (release the db, keep module + provider) and
`close()`; `openStoreDatabase(existingProvider?)` supports the reopen-shaped rows. Rule
documented at the source: one `close()` per shared provider, `closeDbOnly()` on every
other handle over it.

# Fixed during this run

`catalog-rehydrate-54t` failed in setup: its fixture inserted `(id, name)` only, but
quereus columns default to **NOT NULL** (`columnDefToSchema`'s Third-Manifesto default),
so `email text` is NOT NULL with no DEFAULT and the insert violated it. Fixed by naming
every column in the fixture insert (`parent_id` gets 1, satisfying the FK to the previous
table's row). The earlier run's probe claim that this fixture worked did not hold for the
landed code — worth a skeptical eye on the fixture in review; note `fn` re-asserts the
rehydration counts on every timed call, so a silently wrong fixture cannot pass.

# Known gaps and accepted shapes (honest list for the reviewer)

- **Commit rows time a point read too**: `fn` reads row 0 back and asserts the flipped
  constant, inside the timed number — largest relative share at N=1. Accepted in a code
  comment: it is what stops the row from timing a commit that stopped writing.
- **`index-build-5k`'s timed number covers build + drop + two entry-count scans**, not the
  build alone. Stated at the benchmark. Its counters pass does a single create (no drop —
  the counting provider implements no index-store erase) and reads counters BEFORE the
  verification scan so the scan cannot pollute the block.
- **Commit N = 10 000 deliberately dropped**: the flat-batch shape is visible across three
  decades; a fourth adds hundreds of ms per timed call for no additional claim.
- **Catalog row abandons per-call modules un-closed by design** — an in-memory module
  holds no OS handles (probe-verified, no leaked-handle exit trip), and closing one would
  close the shared provider under the next call. Reasoning is in the benchmark's doc block.
- **Commit reads are reported, not asserted**: commits provoke data-store reads
  (read-modify-write, index maintenance lookups) that are linear in N by nature; only the
  write-side counts are pinned.
- **`__stats__` / `__catalog__` blocks are never hard-asserted**; the catalog row reports
  `__catalog__.iterateEntries` as a catalog-layout fact, not a contract.
- **Wall-clock on several rows is noisy on the run machine**: `commit-update-{1,10,100}`,
  `index-resolve-quarter-batch`, `multi-seek-pk-over-batch` hover at 18-27% spread and
  intermittently get marked `unstable`. The counter blocks are the stable signal — that is
  the design — but a reviewer eyeing timing tables should expect flicker on those rows.
- **`batchWrites: 1` per store is a store-LAYER fact over the counting provider** (no
  `beginAtomicBatch`, so the coordinator takes its per-store fallback); a provider with a
  shared commit domain commits one cross-store atomic write instead. Documented in
  docs/benchmarking.md § Storage round trips.
