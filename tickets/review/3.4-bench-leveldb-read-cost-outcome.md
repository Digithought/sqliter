# What the work was

The predecessor (`bench-leveldb-read-cost`) built and ran the benchmark; this ticket was only
ever the write-up and the declare-or-defer decision. The measured ratios, at the key-value
layer over 200-byte values on a 24-core Ryzen AI 9 HX 370 / NVMe / node v24.2.0 machine:

```
20k rows:   pointRead 1.26   seekPositioning 18.78    (median of 13 rounds)
200k rows:  pointRead 1.44   seekPositioning 15.55    (median of 7 rounds)
```

**The decision recorded was to declare nothing**, and the reasoning is the part most worth
attacking:

- `pointRead` is near the 1.0 parity default *and* an over-statement of it, because the
  planner's 1.0 unit is a scanned row including engine work while these arms measured the
  key-value layer alone. The engine-inclusive value sits somewhere in [1.0, 1.44].
- `seekPositioning` is 31-38x from its 0.5 default and still cannot be declared, because the
  one knob prices two access paths whose costs differ by roughly 12x on this backend: the
  secondary-index multi-seek opens one `iterate()` window per key, while the primary-key
  multi-seek batches through `readEffectiveRowsByKeys`. That is now filed as
  `debt-store-seek-positioning-conflates-two-arms`.

# What to check

- **The declare-nothing call itself.** It is the substance of the ticket, it was made by a run
  that was killed, and no second pair of eyes has seen it. The predecessor ticket's own
  instruction was "far from parity ⇒ declare"; this run declined to, for reasons written into
  the `provider.ts` NOTE. Either the reasoning holds or a profile should be declared — decide,
  don't defer again.
- **The `[1.0, 1.44]` interval argument.** It asserts that engine cost lands on both sides of
  the ratio and compresses it toward 1.0. Confirm that is true of the code paths named, not
  just plausible.
- **The 12x two-arms claim.** `StoreTableScan.scanMultiSeek` versus `scanMultiSeekPrimary` —
  verify both shapes are what the NOTE says they are, since the whole deferral rests on it.
- **Every count in `docs/benchmarking.md`.** They were edited by hand across at least six
  sites (lines 22, 31, 324, 326 and the prose around 131-182). Load the suites and count.
- **The cold/warm precision claim** at lines 169-172: 20 000 rows (~4 MB) fits `classic-level`'s
  8 MB block cache and 200 000 (~40 MB) does not, so the large size is a block-cache miss and a
  probable page-cache *hit* — deliberately not called "cold". Check the arithmetic and that no
  other sentence in the file contradicts it.
- **Anchors.** The new prose adds `#read-cost-on-real-disk` and cross-links it from several
  places; `docs:check` validates links, so run it.
- **Nothing may be added to `docs/benchmarking.md`.** It is at 11511 words against a hard
  12000-word cap with no grace band, and `docs:check` is the first step of `yarn check`.
  `debt-docs-split-benchmarking` covers that; if this review needs more prose there, it needs
  the split first.

# Known gaps, stated plainly

- **`yarn test:store` was never run for this ticket** and does not need to be — no cost profile
  was declared, so no plan choice changed. If the review *does* declare one, `seekPositioning`
  moves plan selection on exactly the backend that suite exercises, and the run is over the
  ten-minute agent ceiling. In that case say so and leave it to a human rather than truncating
  it. Do not repeat the mistake that killed both implement runs: no foreground command that
  can exceed the idle timeout.
- **`bench/suites/**` is outside the `tsconfig.test.json` type pass**, so `yarn lint` will not
  catch an error in the benchmark code. `debt-bench-suites-outside-type-pass` tracks that.
- The benchmark rows are `informational: true` and enter no gate verdict — intentional, since a
  wall-clock ratio has no noise floor, but worth confirming the gate agrees.
