# What shipped

Two unrelated-looking symptoms, one theme: a foreign key that **cannot be enforced** must say
so at the moment it matters, instead of failing obscurely or falling silent.

## Arm A — parent table does not exist: the message names it

`buildChildSideFKChecks` still emits the same null-guard chain when it cannot resolve the
parent (behaviour unchanged: MATCH SIMPLE admits a row with any NULL FK column, everything
else is rejected). What changed is the text. Previously:

```
CHECK constraint failed: _fk_ghost_c_c (NEW.c is null or 0)
```

both halves engine-synthesized and meaningless to whoever wrote the schema. Now:

```
CHECK constraint failed: _fk_ghost_c_c — referenced table 'main.ghost_parent' does not exist
```

Mechanism: `ConstraintCheck` gained an optional `violationMessage`, carried into
`ConstraintMetadataEntry` by `buildConstraintMetadata`, and returned verbatim by
`constraintViolationMessage` when set. That function is the single source of truth for the
immediate (row-time) and deferred (commit-time) report paths, so both report identically —
the test file pins both.

Only one producer today: the `!parentSchema` branch of `buildChildSideFKChecks`. The
`CHECK constraint failed:` prefix is kept deliberately (downstream consumers key off it and
identify the key by name); only the expression hint is replaced.

Naming the **schema** is the load-bearing part. An unqualified parent binds to the child's
own schema — documented, matches SQLite, and left alone — so a child in an attached schema
referencing a `main` table resolves to nothing. The schema in the message is what makes that
diagnosable; the remedy is to qualify the parent.

**Not** a `CREATE TABLE` refusal: forward references stay legal, and the test file pins that
end to end (create child → insert fails naming the parent → create parent → the same insert
succeeds), plus the reverse (drop the parent → back to the missing-parent message), proving
resolution is per plan and never cached from creation.

## Arm B — column-count mismatch: raise instead of skip

Both builders used to `continue` past a foreign key whose child column count did not match
the resolved parent key, leaving it **declared but not enforced** — orphans accepted on the
child, parent-side RESTRICT silently bypassed.

Confirmed the declaration path does not already refuse it: `buildForeignKeyConstraintSchema`
and `SchemaManager.extractForeignKeys` compare counts only when the declaration *writes* a
parent column list. The `references <parent>` form with no list defaults to the parent's
primary key, whose arity is unknowable at declaration time (forward references are legal and
the key can change later). So the enforcement seam is the right place, not a
declaration-time refusal.

New shared helper `resolveReferencedColumnsForEnforcement(fk, parentSchema, childSchema)` in
`schema/table.ts` wraps `resolveReferencedColumns` with the arity check and raises:

```
Foreign key '_fk_mm_c_x' on table 'main.mm_c': 1 column(s) reference the primary key of 'main.mm_p', which has 2 column(s).
```

(A different wording when an explicit parent column list is present, which only a path that
bypassed the declaration check could produce.)

Every **enforcement** site now routes through it — the audit the ticket asked for:

| site | was | now |
|---|---|---|
| `buildChildSideFKChecks` | `continue` | raises |
| `buildParentSideFKChecks` | `continue` | raises |
| `getBatchableRestrictFks` | `continue` | raises |
| `foreign-key-actions.ts` cascade dispatch (~271) | `continue` | raises |
| `foreign-key-actions.ts` transitive pre-walk (~429) | `continue` | raises |
| `foreign-key-actions.ts` RESTRICT pre-check (~566) | `continue` | raises |
| `constraint-builder.ts` `validateForeignKeyOverExistingRows` | threw its own wording | raises, shared wording |

`getBatchableRestrictFks` mattered most: when batching applies, the per-row parent-side
checks are **not built** (see the `=== undefined` gates in `building/delete.ts` and
`building/update.ts`), so the batch is the only enforcement on that route — a skip there
left the key unenforced with nothing else covering it.

**Introspection and optimization callers were deliberately left on the lenient
`resolveReferencedColumns`** — `planner/util/key-utils.ts`, `planner/util/ind-utils.ts`,
`schema/lens-fk-discovery.ts`, `planner/mutation/multi-source.ts`,
`func/builtins/schema.ts` (`foreign_key_info`), and `validateForeignKeyCollations`. A
malformed key must not make a read query or a catalog listing fail. **This split is the main
thing worth a reviewer's skepticism** (see gaps below).

# How to exercise it

`packages/quereus/test/logic/41.16-fk-unenforceable.sqllogic` (runs on both backends under
`yarn test:store`). Arms, in file order:

- **A1** missing parent → error naming `'main.ghost_parent'`; NULL FK column still accepted;
  the UPDATE path reports the same thing.
- **A2** composite FK, one column NULL → accepted (MATCH SIMPLE); both non-NULL → rejected.
- **A3** deferred vs immediate. A child-side FK auto-defers under ABORT, so every plain
  insert in this file already exercises the deferred path; `insert or fail` forces row-time
  evaluation. Both assert the identical full string.
- **A4** `pragma foreign_keys = off` → the insert goes through; nothing raises.
- **A5** forward reference end to end (the regression a create-time refusal would have
  broken), then a genuine orphan against the now-present parent still gives the ordinary
  `CHECK constraint failed: _fk_fwd_c_p`.
- **A6** drop the parent → back to the missing-parent message.
- **A7** cross-schema: `xs.xs_child` with an unqualified `references xs_parent(pid)` while
  the parent lives in `main` → error names `'xs.xs_parent'`; qualifying it
  (`references main.xs_parent(pid)`) then works and genuinely enforces.
- **B1/B2** `references mm_p` where `mm_p` has a two-column primary key and the child FK has
  one: child insert raises, parent DELETE raises (this is the silent bypass), parent UPDATE
  raises, and a join over both tables still plans and runs.
- **B3** controls — correctly-shaped composite `references ok_p` and single-column
  `references ok1_p` both work end to end, RESTRICT included, so B1/B2 are not rejecting
  every defaulted `references <parent>`.

Note for anyone extending the file: Quereus columns default to **NOT NULL**, so a nullable
FK column must be written `x integer null references …` or the row dies on NOT NULL before
the FK check is ever reached.

# Known gaps / where to push

- **The lenient-vs-strict split is a judgement call, not a proof.** I classified each of the
  ~14 `resolveReferencedColumns` callers by hand into "enforcement" (strict) and
  "introspection/optimization" (lenient). The risk is a caller I read as optimization that
  is actually load-bearing for correctness — e.g. `planner/util/ind-utils.ts` (~98, ~181)
  and `planner/util/key-utils.ts` (~600) feed index/key selection, and
  `planner/mutation/multi-source.ts` (~3253) is in the view-decomposition path. If one of
  those silently *narrows* a plan on a malformed key rather than merely failing to optimize
  it, it belongs on the strict side. I did not trace their consequences.
- **`schema/lens-fk-discovery.ts` (~138) was left lenient and is untested here.** No lens
  test exercises a malformed key. Lens-routed writes have their own FK duals; whether a
  count mismatch can reach a lens enforcement path is unverified.
- **Arm B's parent-side coverage is single-shaped.** B2 tests RESTRICT (the default action).
  The CASCADE / SET NULL / SET DEFAULT raises at `foreign-key-actions.ts` ~271 and ~429 are
  reasoned-about, not covered by a test — a mismatched-arity key with `on delete cascade`
  would be the direct probe.
- **`validateForeignKeyOverExistingRows` message change is untested.** Its old wording
  (`child column count (n) does not match parent column count (m)`) is gone; I grepped and
  found nothing asserting it, but the ALTER-ADD-CONSTRAINT path that reaches it has no test
  for the mismatch case either way.
- **The maintained-table path deliberately drops `violationMessage`.** `derived-row-validator.ts`
  uses its own `maintainedTableFkViolationError` instead, which already names the missing
  parent — correct today, and recorded as a `NOTE:` at the site. A second `violationMessage`
  producer would be silently dropped there.
- **Arm B changes behaviour from "silently unenforced" to "statement fails."** That is the
  direction the ticket specified and the direction I believe is right, but any existing
  schema in the wild carrying a mismatched defaulted `references <parent>` now breaks on its
  next write. Nothing in-repo hit it (full suite green on both backends), but that is
  evidence, not proof.
- **A3's explicit-transaction arm doesn't isolate COMMIT.** The sqllogic runner executes
  `begin; … commit;` as one block and matches the error anywhere in it, so that arm proves
  the transaction aborted with the right text, not specifically that the throw came from the
  deferred queue. The deferred path *is* covered — A1's plain insert defers by construction
  (`needsDeferred` is always true for a child-side FK under ABORT) — but if you want the
  COMMIT seam pinned directly, that needs a spec-level test.
