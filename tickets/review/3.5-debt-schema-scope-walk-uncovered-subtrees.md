# Review: the schema expression scope walk now reaches every sub-expression

## What the walk is, in one paragraph

`CHECK (…)` and `GENERATED ALWAYS AS (…)` bodies are expressions stored in a table
definition. Two schema-time analyses read them, and both run over **one** traversal
(`src/schema/expr-scope/walk.ts`), which hands each name-bearing leaf to a handler
along with a stack of FROM scopes:

- the **self-qualifier strip** rewrites `check (t.qty > 0)` into `check (qty > 0)` when
  nothing inside the body could have rebound `t`;
- the **generated-column reference collector** classifies each name as binding the row
  being written (`own`), an inner FROM source (`foreign`), nothing at all (`unbound`),
  or undecidable (`unknown`).

A reference the walk never reaches is a reference the collector records **no dependency
edge** for. A missing edge means a generated column computes before the column it reads
and silently stores NULL. That is why closing traversal gaps matters even for shapes
nobody writes today.

## What changed

### 1. Window frame bound expressions are now visited

`sum(x) over (rows between y preceding and current row)` — `y` was invisible. Now
visited in the same scope as `partition by` / `order by` (a frame bound is an ordinary
correlated expression). `WindowFrame` / `WindowFrameBound` are not AST nodes, so they
are handled structurally in `visitWindowDefinition` + a new `visitWindowFrameBound`;
only the `preceding` / `following` bound kinds carry a `value`, and `frame.end` is
explicitly `null` for the `rows <bound>` shorthand.

`parser/visitor.ts`'s `traverseAst` still does not descend frame bounds (it has other
consumers); its `TODO` was left alone and both files' cross-reference `NOTE:` now say
the two walks are no longer equal in reach.

### 2. A new frame kind: `sealed`

`with inverse (…)` on a result column and a select's trailing `with defaults (…)` are
**view write-through metadata**: they are evaluated against the row being written
*through a view*, where `new.<output column>` names that row — a naming environment
this walk does not model at all. Descending them under normal rules would be worse than
skipping them, because `new.a` would hit the collector's `qualifier === 'new'` arm and
come back `'own'`, inventing a dependency on the table being defined.

An opaque (barrier) frame does not fix that: the classifiers check the `new.` /
owning-table spellings *after* the frame loop. So `frame.ts` gained a third frame kind —
`sealedScopeFrame()` (implies `hasOpaque`) plus `hasSealedFrame(stack)` — and each
analysis honours it in exactly one place, before any seed matching:

- `stripColumnQualifier` → return (no rewrite);
- `classifyUnqualified` / `classifyQualified` → return `'unknown'`.

`'unknown'` is the safe answer: `table.ts` records a dependency edge for a known column
name and raises nothing for an unknown one.

### 3. `with inverse` and `with defaults` are now visited, sealed

`inverse` is visited from the shared `visitResultColumns` helper, so a DML `returning`
list carrying its own `with inverse` inherits it. `defaults` is visited in the select
arm next to the result columns.

### 4. DML sub-parts are now visited (behaviour-visible — see below)

Inside the single opaque frame each DML arm already pushed: `returning` (through
`visitResultColumns`), `upsertClauses[].assignments[].value`, `upsertClauses[].where`,
and `contextValues[].value`, for all three of insert / update / delete.

### 5. Compound legs no longer inherit the leading leg's FROM scope

`select … from s1 union select … from s2` used to analyse the second leg with `s1`'s
sources still on the stack. Each leg is a self-contained relation, so the leg visits
moved out of the leading leg's FROM-frame push (still inside the `with`-clause push — a
leading `with` scopes over the whole compound, a `from` does not).

## The one behaviour change a user can hit

**Change 4 can turn a previously-accepted `alter table … add column … generated always
as (…)` into an error.** Everything under the DML barrier classifies `'unknown'`, and
`validateAddColumnGeneratedRefs` (`src/schema/table.ts:1605`) treats *any* binding —
including `'unknown'` — whose name equals the column being added as a self-cycle. So a
body that names the new column only inside an inner DML's `returning` list / upsert
assignment / context assignment now raises
`Cyclic dependency in generated columns: '<col>'` at ALTER time instead of being
accepted. That is the correct answer (the name really is in the body, and the emitter's
own re-analysis reaches the same conclusion once it sees the reference), and reaching it
requires writing DML inside a generated expression. There is no test for it — see gaps.

## What to exercise as a reviewer

The walk-level spec (`test/schema/expr-scope-walk.spec.ts`) is where the traversal
contract lives; each record is `{ shape, name, qualifier, depth, sawOpaque, sawSealed,
realSources, bound }`. Cases added:

**Window frame bounds** — `sum(x) over (rows between y preceding and current row)`
reaches `x` and `y`, neither opaque nor sealed; both bounds reached START-before-END;
`unbounded preceding` / `current row` / literal bounds produce nothing extra; the
`rows y preceding` shorthand (`frame.end === null`) works.

**Sealed subtrees** — `select a with inverse (b = new.a) from other`: `a` unsealed,
`new.a` sealed. `select a from other with defaults (c = d)`: `d` sealed, `a` not. Seal
does not leak to a sibling after the clause. Seal *stacks on* an enclosing CTE barrier
without disturbing it (the CTE body's own askable source survives). Through the
collector, `new.a` under a seal classifies `'unknown'`, never `'own'`. The strip
rewrites nothing inside a seal.

**Compound legs** — the second leg's stack carries `s2`'s sources and not `s1`'s; a
leading `with` clause still scopes over both legs (so a CTE name stays opaque in the
second leg); and through the collector, a bare name in the second leg that only the
*first* leg's source exposes now classifies `'own'` (it was `'foreign'`).

**DML** — the four flipped cases (`returning` is now reached in insert / update / delete
and with a DML-attached `with` clause), plus upsert `set` / `where` and `with context`
assignments, all opaque and none sealed. Note `with context` takes **no parentheses**
in DML position (`insert into other with context c = qty values (1)`).

**The strip on frame bounds** — `sum(v) over (rows between t.y preceding and current
row)` now *does* get rewritten to `y`. Intended, and consistent with how the strip
already treats `partition by` / `order by`.

**SQL-level** — `test/logic/41-generated-column-scope.sqllogic` § 13 covers the compound
leg fix end to end: `cs_src` exposes a column named `b`, the second leg's source does
not, `g` is declared *before* `b`, so only a recorded dependency edge gets `b` computed
first. I confirmed this case is not vacuous by reverting the leg split and re-running:
it fails with `NOT NULL constraint failed: cs.g` (the pre-fix path computes `g` against
`b`'s NULL placeholder).

## Known gaps — please treat the tests as a floor

- **Changes 1–3 have no sqllogic coverage, by design.** Window frame bounds, `with
  inverse`, and `with defaults` inside a `check` / generated body have no clean SQL-level
  assertion that is not itself contrived — the only observable difference is an error
  message or an unobservable classification. The walk-level spec is the honest place for
  them. I did not invent a sqllogic case to pad this.
- **Change 4's user-visible consequence is untested.** The new
  `Cyclic dependency in generated columns` error for `alter table … add column g
  generated always as (<body naming g inside an inner DML's returning list>)` is argued
  from `table.ts:1605` and the classification path, not observed. A reviewer wanting it
  pinned should add the ALTER to `41-generated-column-errors.sqllogic`; I judged the
  shape too contrived to be worth a permanent guard, which is a judgement call worth
  second-guessing.
- **`upsertClauses` / `contextValues` / `with inverse`-inside-`returning` are covered
  only at walk level**, same reasoning.
- **`sealed` currently has exactly one producer** (`sealedScopeFrame`) and two consumer
  sites. If a third write-through clause appears on the AST, nothing forces it to be
  sealed — there is no exhaustiveness check over "clauses that resolve in the written-row
  environment", unlike the `EXPRESSION_KINDS` ledger in the spec which does force a
  decision for every new *expression* node kind.

## Tripwire parked

One conditional concern, recorded as a `NOTE:` at the site
(`src/schema/expr-scope/walk.ts`, in `visitSelect` above the `orderBy` / `limit` /
`offset` visits) rather than filed as a ticket: on a compound, those three clauses bind
to the **whole compound**, not the leading leg, but the parser folds them onto the
leading leg's AST node, so the walk visits them inside that leg's FROM scope. Harmless
for a non-compound select and for every shape reachable today; untangling it needs the
AST to distinguish leg-level from compound-level clauses, which it does not. The ticket
explicitly asked for this to stay a note.
