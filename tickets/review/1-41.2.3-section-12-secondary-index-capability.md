# `41.2.3` § 12 no longer needs standalone index DDL

## What changed

`41.2.3-alter-column-set-not-null-pk-backfill.sqllogic` § 12 ("A SECONDARY INDEX over an
untouched column still resolves after the re-key") used a standalone `create index` statement,
which requires the `standalone-index-ddl` capability the file itself never declared. On a
backend lacking that capability the whole file (12 sections, 11 of which have nothing to do
with indexes) would die at that one statement.

**Arm 1** — § 12 now builds its secondary index via a table-level `y integer null unique`
column instead of `create index ix_bf13 on t_bf13 (y)`. A prose comment above the
`create table` explains the substitution, backtick-quoting the directive name so it doesn't
trip `logic-capabilities.ts`'s `NEAR_MISS_RE` guard (which hard-errors any comment line that
*opens* with something resembling `-- requires-capability:`). Verified via `query_plan()`
before writing the fix: `unique` produces a real `INDEX SEEK ... USING _uc_y`, not a table
scan, and does not touch `findPKDefinition` — the table keeps its synthesized `(x, y)` primary
key, so the backfill re-key semantics § 12 is actually testing are unaffected. Rest of § 12
(statement sequence, expected results) is byte-identical to before.

**Arm 2** — new sibling file `41.2.3.1-alter-column-set-not-null-pk-backfill-secondary-index.sqllogic`
carries `-- requires-capability: standalone-index-ddl` and the original § 12 statements
verbatim (the `create index` form). Header follows the carve-out precedent set by
`06.9.1.1-json-coerce-once-index.sqllogic` and `10.1.2.1-add-constraint-in-transaction.sqllogic`.

No harness bookkeeping changes: `logic.spec.ts`'s `MEMORY_ONLY_FILES` set gets no entry for
either file (both run on both backends), and `logic-capabilities.spec.ts`'s `subjectFiles` list
(files whose *subject* is index DDL) gets no entry for the new file either — same as its two
sibling carve-outs, since the new file's subject is a primary-key re-key, not index DDL itself.

  absent from `subjectFiles` (its subject isn't index DDL).
- Full `yarn test` run clean (~7m15s wall clock): all workspaces passing, no failures. Some
  `[Sync]` stderr lines in quereus-sync/quereus-sync-client test output are deliberate
  error-injection test noise (`Error: boom`, `socket write failed`, etc.), not real failures —
  pre-existing and unrelated to this change.
