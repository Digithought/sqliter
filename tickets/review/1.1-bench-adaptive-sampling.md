# What landed

Every benchmark used to be timed by the same recipe — a hand-written warmup count and
iteration count, 3 and 10 by default. A 4 µs parser call and a 190 ms bulk insert got the
same ten samples, so the fast ones measured mostly clock and the slow ones wasted seconds.
Nothing reported how noisy any result was, and the `P95` column printed the same number as
`Max` on every benchmark with 20 or fewer iterations.

Now each worker sizes its own timing loop, and every row carries a dispersion figure.

## Calibration (`bench/child.mjs`)

Four steps, in this order, all inside the worker after `setup`:

1. **Warm up by elapsed duration** — call `fn` untimed until 250 ms has passed
   (`minWarmup: 2` runs first regardless; `maxWarmup` is a backstop, not a knob).
2. **Size the inner batch on the warmed function** — grow a burst until it clears 1 ms,
   multiplicatively by the observed shortfall. A sample then times `batch` consecutive
   calls and divides by `batch`.
3. **Buy samples from a time target** — `ceil(1000 ms / (batch × perCall))`, clamped to
   5..500.
4. **Stop early on a 5 s ceiling** — checked only after `minSamples` are in hand, sample
   count first and elapsed second.

All knobs live in one commented exported `CALIBRATION` object. An explicit `iterations` or
`warmup` still wins, skips calibration entirely, and is reported as `pinned`.

## Dispersion (`bench/lib/stats.mjs`)

`relativeIqr` = `(p75 - p25) / median`. Chosen over coefficient of variation because these
distributions carry GC and tier-up outliers that inflate a standard deviation without
describing the typical iteration; the reasoning is recorded in a comment at the computation
so it does not get swapped back on aesthetic grounds.

`summarize` gained `spread_pct`, `stable`, `samples`, `batch`, `warmup`, `pinned`, and
renamed `min_ms`/`max_ms` to `min_sample_ms`/`max_sample_ms` — because for a batched
benchmark those extrema are batch means, not per-call extremes. `p95_ms` is gone.

# Two deliberate deviations from the plan ticket — please scrutinise these first

The plan specified a single pilot measurement (two untimed calls, then one timed) feeding
`warmupIterations = clamp(ceil(250 / pilotMs), 2, 50)` and a batch size from the same
pilot. **Both halves of that were implemented, measured, and found to produce a worse
result than the fixed counts they replaced.** What is in the tree differs:

**A cold pilot is the wrong input for a batch size.** On `parser/simple-select` the third
call took ~91 µs against a warmed steady state of ~4 µs. Batch came out 18× too small, each
"sample" was 55 µs of work read through a timer of comparable resolution, and the benchmark
reported **54.5% spread** — almost entirely clock. Batch sizing therefore moved to *after*
warmup, on the warmed function.

**A 50-call warmup cap silently defeats the 250 ms warmup target.** 50 calls of a 4 µs
parser is 0.25 ms of warmup where 250 ms was asked for, so `fn` was still climbing V8's
tiers when the batch was sized. Warmup is now a duration loop. A controlled probe over
warmup targets of 10 / 50 / 250 / 1000 ms (3 runs each, `parser/simple-select`) gave:

| warmupTargetMs | warm calls | median | spread |
| ---: | ---: | ---: | ---: |
| 10 | ~330 | 4.33-4.37 µs | 6.9 / 37.4 / 8.9% |
| 50 | ~5 000 | 4.22-4.40 µs | 6.8 / 6.7 / 8.6% |
| 250 | ~50 000 | 4.14-4.23 µs | 4.9 / 5.5 / 4.4% |
| 1000 | ~215 000 | 4.13-4.28 µs | 4.9 / 3.2 / 5.7% |

250 ms is where the curve flattens; 1000 ms buys nothing for 4× the warmup cost.

Both changes are documented at their sites with the measurements above. **A reviewer should
decide whether the deviation is right, not just whether the code matches the comment.**

# Acceptance evidence

**Five repeats of `yarn bench --filter full-scan-10k`** (each a fresh process):
**9.52, 9.30, 9.09, 9.71, 9.19 ms** — a **1.07× range**, against **14.20-25.44 ms (1.79×)**
measured at the fixed counts during planning. Within-run spreads were 8.9-12.2%. No outlier
run this time, but see the honest limits below — that is not the same as the problem being
solved.

**Parser benchmarks batch and sample as intended** — batch 156-438, 500 samples each,
spread 3.2-12.0% on a settled machine.

**Every row carries a spread figure.** All 27 rows populated; the results JSON was scanned
programmatically for `NaN`, `Infinity` and null spread — none.

**Full-run wall-clock: 47.4 s and 48.3 s** on two settled runs (27 isolated processes). The
plan predicted 60-90 s and set a 3-minute ceiling; well under, so `targetTotalMs` was left
at 1000.

**No benchmark definition carries `iterations` or `warmup`** — 54 lines removed across 27
definitions in the four suite files. Each suite file gained a header documenting the
override as an escape hatch and the back-to-back-repeatability requirement batching imposes.

**Ratio guard re-confirmed both ways.** Passes at 0.96× and 0.97× against `maxRatio: 10` on
settled runs. Forced to `maxRatio: 0.1`, it printed
`ratio guard FAILED: execution/correlated-subquery is 1.2× ...` and the process exited 1.
The suite file was restored (`maxRatio: 10` — worth confirming in the diff).

**Pinned escape hatch works end-to-end.** `full-scan-10k` temporarily pinned to
`iterations: 4, warmup: 1` reported `4 pinned iters`, carried the `pinned` marker, and read
**13.74 ms against the calibrated 9.2 ms** — the tier-up contamination the old fixed-count
model suffered from, visible side by side. Reverted.

**Degenerate cases exercised directly** against `relativeIqr` / `summarize`: all-zero
samples, zero median with a non-zero tail, a single sample, identical samples, and an empty
array. Zero-median cases yield `spread_pct: null` and `stable: false`; nothing emits a
non-finite number. The table prints `?` rather than an empty cell for a null spread.

# Known gaps — treat the tests above as a floor

- **No automated test covers any of the calibration logic.** `warmUp`, `sizeBatch`,
  `samplesFor` and `collectSamples` were verified by running the harness and by a
  throwaway probe script (since deleted), not by anything that will catch a regression.
  The degenerate-case checks were likewise one-shot, not committed. This is the largest
  gap and the most likely thing to want a `debt-` ticket: the stats functions are pure and
  trivially testable, and the calibration functions are testable against a synthetic `fn`
  with a controllable duration.
- **Two code paths never ran in anger.** The `maxTotalMs` 5-second early stop was never
  triggered (no benchmark gets near it) and the `maxBatch` ceiling was never reached
  (highest observed batch was 494). Both were reasoned through, neither was observed.
- **The stability flag is not itself stable between runs.** Settled runs flagged 3 and 6
  rows unstable; a run contaminated by background load flagged 16. Which benchmarks get
  flagged varies run to run, so `unstable` is a property of a run, not of a benchmark. The
  downstream comparison ticket should not assume a fixed exclusion set.
- **`execution/full-scan-10k` read 55.4% spread in the final full run** despite a sane
  12.46 ms median, and 3.2-12.2% everywhere else. It is the noisiest entry in the suite and
  the ticket's own headline example; the five-repeat result above is much better than the
  planning baseline but this benchmark is not cured.
- **The documented limitation was observed live, not just theorised.** On a run taken while
  the machine was loaded, `temporal-arith-scan-10k` reported **335 ms with a spread of only
  8.6%** — a tight distribution around a centre 3.5× too high, next to a settled-run value
  of 95 ms. A low spread is not evidence that two runs are comparable. This is recorded as
  a `NOTE:` at the `stable:` computation in `stats.mjs`; the environment capture and
  comparison rules that would actually address it are the next ticket's job.
- **Wall-clock is now load-sensitive in a way the old harness was not**, because sample
  counts are derived from a live measurement: the loaded run took 61.6 s against 47.4 s
  settled. Not a defect, but a CI runner under contention will not take 47 s.
- The `bench/results/*.json` files written during validation are gitignored; several
  accumulated and were left in place, consistent with prior runs.

# Suggested review focus

- The two deviations above — is duration-driven warmup plus post-warmup batch sizing the
  right call, or should the plan's literal formula be restored and the measurements
  re-examined?
- `sizeBatch`'s termination argument: `maxBatch` is accepted even when still short of
  `minSampleMs`, so the ceiling always wins. Confirm there is no input that loops.
- The `samples.length >= MIN_STABILITY_SAMPLES` condition added to `stable` — it exists so
  a benchmark pinned to 2 iterations cannot report itself as the tightest in the suite.
  Confirm the constant genuinely shares one definition with `CALIBRATION.minSamples`
  (it is imported, not duplicated) and that the import direction creates no cycle.
- Whether renaming `min_ms`/`max_ms` to `min_sample_ms`/`max_sample_ms` and dropping
  `p95_ms` breaks anything reading old results files. Nothing in the repo does — only
  `median_ms` is consumed, by the baseline comparison and the ratio guards — but the
  downstream comparison ticket will be reading this JSON.
- `run.mjs` prints `unstable` and `pinned` as line-end markers rather than columns, so they
  do not participate in the padded layout. Check the table still reads cleanly with a
  `--baseline` delta column present (that combination was not exercised — no baseline file
  comparison was run).
