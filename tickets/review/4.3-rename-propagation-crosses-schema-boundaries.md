# What changed

`ALTER TABLE … RENAME` and `… RENAME COLUMN` used to rewrite dependent **views,
materialized views and assertions** only while iterating the renamed table's own
schema, while dependent **tables** (foreign keys, CHECK expressions, partial-index
predicates, column `DEFAULT` / `GENERATED` bodies) were always walked across every
schema. A view in `temp` over `main.t` therefore kept naming a table that no longer
existed; an assertion in that position broke every subsequent write to the database.

The gate is gone. All four dependent kinds are now walked in every schema, and the
per-home-schema resolver introduced by `debt-rename-walkers-resolve-names-like-the-planner`
is what keeps that from over-matching: a reference is rewritten only when it *resolves*,
under the walked body's own home schema path, to the renamed object's canonical key.

## Three substantive edits

**1. Gate removed (`alter-table.ts`).** `propagateTableRenameInSchema` and
`propagateColumnRenameInSchema` lost their `schema.name.toLowerCase() === renamedSchemaLower`
gate and one level of indentation. `propagateColumnRename` / `…InSchema` lost the now-dead
`renamedSchemaName` parameter (the table verb still needs it, to re-key an assertion's
`dependentTables` and an MV's `sourceTables`).

**2. Two global passes, not one combined per-schema pass** — the one design decision
here that goes beyond deleting the gate. The materialized-view pass **re-plans** each
body it rewrites, so every plain view in *every* schema must already carry the new name
before the first MV re-plans. Schemas iterate `main` first, so a combined per-schema pass
would re-plan `main.mv` while `temp.vt` still named the vanished `main.t`. `propagateTableRename`
now runs tables+views+assertions over all schemas, then MVs over all schemas, then the
existing `restoreUnaffectedMaterializedViews` sweep. Same for the column verb. Pinned by
*"a main MV reading through a temp view survives the rename"*.

**3. Pre-flight widened to match (`catalog-persistability.ts`).**
`assertRenameDependentsPersistable` lost its `schema` parameter and takes a new
`BodyRewriteFor = (homeSchemaName: string) => BodyRewrite` factory instead of a single
`BodyRewrite`; its view/MV arm now walks `_getAllSchemas()`, asking for a rewrite bound
to each body owner's home schema. Without this a cross-schema dependent would be rewritten
without ever being offered to a storage module's veto hook, and its persisted catalog entry
would silently diverge. Both call sites in `alter-table.ts` pass
`home => ast => rename…InAst(ast, …, objectResolvers.forHomeSchema(home), targetKey)`.

# How to exercise it

```sql
create table main.t (id integer primary key, x integer);
create view temp.vt as select id, x from main.t;
alter table main.t rename to t2;
select * from temp.vt;              -- was: "Table not found: main.t"; now returns rows
```

Swap the view for `create assertion temp.a check (not exists (select 1 from main.t where x < 0))`
and every write to the database used to fail after the rename; now the rule keeps enforcing.
Same for `create materialized view temp.mv as select id, x from main.t`.

## The four cases that decide whether the resolver is doing its job

These are the ones to attack — three of them are ways the change could over-reach.

- **Must NOT rewrite.** `create table temp.t (…); create view temp.vt as select * from t;`
  then `alter table main.t rename to t2` → `temp.vt` unchanged (its bare `t` is `temp.t`).
- **Must rewrite (home-path fallthrough).** `temp` holds no `t`, so a `temp`-owned view's
  bare `t` legally resolves to `main.t` and must follow the rename. A naive "only rewrite
  qualified cross-schema references" shortcut gets this wrong.
- **Must rewrite (explicit qualifier).** A `temp`-owned body naming `main.t` explicitly,
  both verbs, all three object kinds.
- **Event count.** A rewritten dependent fires exactly one `view_modified` /
  `materialized_view_modified`, not one per schema iterated.

# Known gaps and things worth a second look

- **The DROP guards were deliberately NOT widened.** `assertNoAssertionDependsOn` and
  `assertNoAssertionNamesColumn` are still scoped to the dropped object's own schema —
  that is ticket `assertion-guards-follow-view-chains-and-schemas` (4.5). Their doc comments
  were repointed to that slug and no longer cite the rename loops as precedent for the limit.
  So there is a live asymmetry today: a rename follows a cross-schema assertion, a drop does
  not refuse for one.
- **The pre-flight only fires when some module implements `assertCatalogObjectPersistable`.**
  A memory-only database never pays it and never exercises it, so the three store tests are
  the whole safety net for that arm.
- **Cross-schema MV chains and the restore sweep.** `restoreUnaffectedMaterializedViews`
  walks schema-by-schema then creation order, which is topological for a same-schema chain
  but not necessarily across schemas. Verified harmless for both verbs (a consumer that does
  not itself name the renamed object is skipped by the propagation and only reaches the
  sweep; a producer whose own name did not change re-plans fine). Parked as a `NOTE:` on that
  function rather than filed — it only becomes work if a producer's *output* names can shift
  while its consumer lives in an earlier-iterated schema.
- **`propagateTableRenameInSchema` still takes `renamedSchemaName`** purely to compute the
  `<schema>.<old>` → `<schema>.<new>` base strings the assertion and MV helpers re-key with.
  That is a string map, not a resolution decision; worth confirming it is right for a
  dependent whose own schema differs from the renamed table's.
- **Assertion propagation has no per-assertion rollback.** Pre-existing (documented in
  `reregisterRewrittenAssertion`), but the blast radius grew: a throw mid-loop now leaves
  assertions in *earlier schemas* rewritten too. Still unreachable by the same argument as
  before (the only plausible throw is `buildAssertionViolationSql` on an AST that already
  stringified at create time).
- Nothing was `skip`ped, loosened, or disabled. No pre-existing failures surfaced.
