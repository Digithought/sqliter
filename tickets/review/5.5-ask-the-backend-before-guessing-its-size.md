# What landed

`BestAccessPlanRequest.estimatedRows` now carries three distinct spellings, all the way
from the planner to the module:

| spelling | meaning |
|---|---|
| `undefined` | nobody has measured this table |
| `0` | measured, and empty |
| `n > 0` | measured |

Five planner sites build that request. Three already honored the contract; two
(`rule-grow-retrieve`, both arms) sent `tableRef.estimatedRows || context.stats.tableRows(schema) || 1000`
and so handed every never-analyzed table a fabricated `1000`. Both now call a
`measuredRows(tableRef)` helper that returns the catalog count or `undefined`, with the
reasoning in its doc comment. Three `|| undefined` spellings became `?? undefined` so a
measured `0` survives.

## The one judgment call the ticket asked for — answered

**Yes, `context.stats.tableRows` returns a naive default at these sites, so it is no longer
consulted.** `CatalogStatsProvider.tableRows` reads `catalogRowCount(table)` — the same
thing `TableReferenceNode.estimatedRows` reads — and when that is absent it delegates to
`NaiveStatsProvider`, whose `tableRows` is documented as "naive by definition: always the
configured default", i.e. 1000. So `tableRef.estimatedRows ?? context.stats.tableRows(schema)`
would have been `catalog ?? (catalog ?? 1000)` — the fabricated number by a longer route.
The catalog count is passed through directly instead, exactly as the ticket instructed.

Nothing in the engine installs a non-catalog `StatsProvider` (`Optimizer`'s constructor
accepts one; only `CatalogStatsProvider` is ever passed), so no production path loses a
number it previously had.

## Also changed, and why

**`validateAccessPlanRequest` now checks `estimatedRows`.** It validated nothing about the
field before. It rejects a negative or non-integer value and accepts `undefined` and `0` —
the ticket's "confirm `undefined` remains valid" item, made enforceable rather than merely
observed.

**`sizeRequestFromLiveCount` gained exactly one exception.** A hint of `0` that the
module's own live count contradicts is a stale `ANALYZE`-before-the-data-load snapshot, not
a measurement, and the module now substitutes its live count there. This is **not** scope
creep — it is a defect the ticket's own required behavior created. Sending a measured `0`
through (which the ticket demanded, correctly) made a 2000-row table that had been analyzed
while empty price every arm and every scan at zero; `column-statistics-plan.spec.ts`'s
"a snapshot taken while the table was empty is ignored once rows arrive" caught it. The
module already refuses a `rowCount <= 0` snapshot for *selectivity* (`resolveArmEstimate`,
whose comment names this exact bootstrap-script case); the size path now refuses it
consistently. A `0` the live count **agrees** with is a genuinely empty table and stays `0`.

# What did NOT happen — two ticket predictions that measurement contradicted

Both are pinned as tests so the next change to either area reports itself.

## 1. The 55%-range case does not flip. The un-analyzed veto is scale-invariant.

The ticket expected feeding the live count to move a 55%-selectivity range query from an
`IndexSeek` to an `IndexScan` while leaving a 10% range alone. **Neither moves.**

While an arm's estimate is an `ARM_SELECTIVITY` shape constant — which is what
"un-analyzed" means — the store's seek-versus-scan comparison judges it at *parity*
`pointRead` against a scan costing exactly `estimatedRows`. Both sides are then the same
linear function of the size, so the verdict cannot depend on it: `0.3 + 1.3·⌊0.1N⌋` stays
below `N` for every N ≥ 2. A bigger honest number moves every cost and no verdict.

The discrimination the parent plan ticket measured needs `ANALYZE` — only a
statistics-backed estimate is per-query, and only then is the veto judged at the backend's
*declared* `pointRead`. Measured here at 2000 rows with the IndexedDB profile
(`pointRead: 3.0`): un-analyzed, both ranges seek and cost the same; analyzed, the 55%
range becomes an `IndexScan` and the 10% range keeps its seek. Both states are pinned in
`live-row-count-plans.spec.ts` → `plan shape`.

So this ticket changes what un-analyzed range queries **cost**, not which plan they get.

## 2. The key-set-seek merge gate does not start firing. A second relay bug is in the way.

The ticket expected `rule-key-set-seek`'s gate (~618) to decline for the first time once
the key source carried a real live count. **It still never declines.** Measured: a 3000-row
key source against a 200-row target advertising `breakEvenKeys: 343` — nearly 9× over the
threshold — still takes the rewrite.

Root cause, found and named: the gate reads `node.right.physical.estimatedRows`, and
`IndexScanNode.computePhysical` (`table-access-nodes.ts` ~277, and `SeqScanNode` ~177)
publishes `this.source.estimatedRows` — the **catalog** count, `undefined` on an
un-analyzed table — while its sibling `IndexSeekNode` (~545) publishes the **module's own**
`filterInfo.indexInfoOutput.estimatedRows`. The live count this ticket unlocks reaches the
module, prices its plan, and is then discarded one level up.

Filed as an arm on `backlog/debt-row-estimate-relay-has-no-guard` (the existing theme
ticket for exactly this class — a step that has a row count and fails to publish it), with
the measurement and the two sibling nodes' disagreement written out. Not fixed here: which
of the two numbers a scan node should publish is a design question, and changing it moves
plans on both backends. A `NOTE:` at the gate points at the arm; the current behavior is
pinned by `live-row-count-plans.spec.ts` → `the key-set semi join merge gate`, deliberately
as *observed* not *desired*, so the fix will announce itself there.

# Plan churn on the store backend — four existing tests resized

Expected by the ticket ("plan churn on the store backend is the expected outcome"). Every
one is a cost crossover from feeding true sizes into constants calibrated around the 1000
placeholder, and in each the new plan is the arithmetically right one. **No assertion was
weakened, skipped, or removed** — only fixture row counts moved, each with a comment at the
site explaining the crossover. Reviewers should sanity-check these four judgment calls:

| test | was | now | why |
|---|---|---|---|
| `pushdown.spec.ts` "ANY column with a declared COLLATE seeks" | 1 row | 20 rows | on a 1-row table a seek costs 1.6 against a scan's 1.0, so the arm is dropped and there is no seek left to check for collation-correctness. An **ANALYZEd** 1-row table has always scanned (`column-statistics-plan.spec.ts` pins that as intended), so the un-analyzed case now merely agrees with it. |
| `lone-surrogate-keys.spec.ts` "EQUALITY probe on a json SECONDARY index" | 1 row | 20 rows | same cliff; with no seek, no probe is built and there is nothing for the encoder to refuse. |
| `index-column-collation.spec.ts` "ALTER COLUMN … SET COLLATE" | 1 row | 20 rows | same cliff; the subject is the re-encoded index key, not the cost model. |
| `index-ordering.spec.ts` "a pushed filter the walk leaves unhandled" | 300 rows | 1200 rows | the ordering walk (≈ `1.9N` with two residual filters) only beats scan-then-sort (`N + 0.1·N·log₂N`) above ~512 rows. At 300 rows scan-then-sort is genuinely cheaper now. Its unfiltered neighbours still win at 300 because they pay no residual term — which is why only this one moved. |

**The memory backend is unaffected**, as required. Its module keeps no live row count, so
its `?? 1000` default still answers; asserted directly (two un-analyzed memory tables of 6
and 4000 rows price identically) and broadly by the full suite.

# Prepared-statement staleness — confirmed, as the ticket asked

The recompile trigger exists and covers growth, but only indirectly. `core/statement.ts`
subscribes each compiled plan to the schema-change notifier and drops the plan when an
event touches a table it depends on. Plain INSERTs fire no such event, so growth alone
never recompiles; what does is the `table_modified` that `ANALYZE` emits
(`runtime/emit/analyze.ts`), and `auto_analyze` — **on by default** — re-analyzes once a
table's mutation counters cross `auto_analyze_min_mutations` / `auto_analyze_ratio`. So the
window is bounded by those thresholds rather than closed. Not fixed here (the ticket said
not to); recorded at `sizeRequestFromLiveCount`'s existing NOTE, which already said the fix
belongs at the recompile trigger. No follow-up ticket filed: the mechanism exists and the
residue is a bounded staleness window, not a defect.

# Known gaps — where to push hardest

- **The two negative findings above are the highest-value things to re-derive.** Both were
  the ticket's stated expectations and both are contradicted by measurement; if either
  analysis is wrong, a real behavior change is being recorded as "no change". The
  scale-invariance argument in particular rests on the veto being judged at parity for an
  unbacked estimate — check `store-module-access-plan.ts` ~741 and the `vetoCost` at ~1399.
- **The four resized fixtures.** Each is a judgment that the new plan is correct and the old
  one was an artifact of the 1000-row placeholder. The `index-ordering` one (300 → 1200) is
  the least obvious and the arithmetic is quoted at the site; check it.
- **The `sizeRequestFromLiveCount` exception** widens a documented "a supplied hint always
  wins" rule. The narrower alternative — never sending a measured `0` from the planner —
  was rejected because the ticket required `0` to reach the module, and because the module
  already refuses a vacuous snapshot for selectivity. Worth a second opinion on whether the
  exception belongs at this seam or in `ANALYZE` (which arguably should not stamp a
  `rowCount: 0` snapshot it knows carries no column statistics at all).
- **`createSeqScan` in `rule-select-access-path.ts` (~1232) still reads
  `tableRef.estimatedRows || 1000`.** Deliberately untouched: it feeds `seqScanCost`, not a
  module request, and switching it to `??` would cost a measured-empty table at `0`, which
  is a separate cost-model question outside this ticket's scope. Flagging rather than
  hiding it.
- **No coverage of a third-party module that sizes itself.** Only `quereus-store` does, so
  the "a self-sizing module now gets the chance" claim is exercised through exactly one
  implementation.
- **Only the `range` and `eq` arms were reasoned about for scale-invariance.** The
  `prefixRange` and multi-seek arms have their own selectivity constants and clamps; the
  full suite covers them behaviorally, but no test states the invariance for them.
