# Review: rename rewrite preserves what a reference resolves to

## What was wrong

A stored body (view, materialized view, assertion, CHECK, column DEFAULT) can
name a table without a schema qualifier; the name resolves against the body's
home schema first, then the session search path. `renameTableInAst` rewrote such
a reference in place — new name, still unqualified — so if an earlier schema on
the body's home path already held a table with the *new* name, the reference
silently re-bound to that other table. Verified symptoms: a view returning the
wrong rows, `refresh materialized view` replacing correct contents with the
wrong table's rows, an assertion silently ceasing to enforce.

## What was built

The invariant enforced: **after rewriting a reference, re-resolving it under the
same home schema path against the catalog as it will be after the rename must
yield the renamed object's key.** All at one code site — `renameTableInAst`'s
rewrite sink.

- `ObjectRefResolvers.withTableRenamed(schema, old, new)` — a sibling snapshot
  with the one rename applied to the copied name-set map. No live-catalog
  lookup; base snapshot keeps answering pre-rename. Internal `buildResolvers`
  builder shared by both.
- `TableRenameTarget` (`rename/shared.ts`) — `{oldName, newName, schemaName,
  resolve, resolveAfter}`, one **required** argument replacing the old
  `(oldName, newName, resolve, targetKey)` positionals on `renameTableInAst` and
  the three collection entry points, so no caller can skip the post-rename
  answer. `targetKey`/`newTargetKey` derived inside.
- `TableRef.qualify?` — present at exactly the three sites where a reference
  re-resolves through the catalog: DML target, FROM `TableSource`, seedless bare
  column qualifier. Absent (with site comments saying why) at the
  schema-qualified column site (post-condition holds by construction) and the
  FROM-frame-bound column-qualifier site (binds through the frame; qualifying
  the source is the fix).
- Sink logic: after `setName(newName)`, if `qualify` present and
  `resolveAfter(ref.schema, newName) !== newTargetKey`, call
  `qualify(schemaName)`. **Conditional, not eager** — the no-collision rename
  leaves body text (and MV `bodyHash`) byte-identical to before.
- `tableRenameTargetsFor(resolvers, schema, old, new)` (object-ref-resolver.ts,
  exported): per-home-schema target factory; `runRenameTable` builds it once and
  threads it through the pre-flight persistability closure,
  `rewriteTableForTableRename`, `propagateTableRename(InSchema)`, and the
  assertion/MV helpers (whose signatures collapsed to take the target).
- Single-schema worlds — schema-differ's three inverse-reconcile sites and
  `store-module-rename.ts`'s own-table rewrite — pass the same resolver for both
  `resolve` and `resolveAfter` with a one-line why (a bare name there always
  resolves back to the one schema, so qualification can never fire).
- `tableReferencedInAst` / `collectTableRefsInAst` (the DROP-guard probe and the
  closure collector) are untouched — same one-traversal invariant, post-condition
  logic lives only in the rewrite sink.
- Docs: the "Known limitation" paragraph in `docs/sql-alter.md` replaced with
  the post-condition statement.

## Known gaps / notes for the reviewer

- **Seedless bare column-qualifier qualify path** is tested only at the walker
  level. It is engine-unreachable on a valid body: a CHECK/DEFAULT plans under
  its owning schema only (`schemaAuthoredContext`), so a bare qualifier that
  resolves by fallthrough — the only way that site's post-condition can fail —
  belongs to a body the planner already rejects. Documented at the site.
- **Own-table CHECK self-qualifiers never qualify** (a body's home schema is
  always first on its own path), so `self-qualifier-strip.ts` never sees a
  schema-qualified form it would decline; its line-287 owning-schema check
  covers the qualified spelling anyway. Confirmed by reading, not by a new test.
- **Declarative differ**: qualification fires only when the body's home schema
  differs from the renamed table's, and the differ diffs one schema at a time —
  so a cross-schema qualification is outside its rename-record scope by
  construction. Confirmed indirectly via the store-mode 41.3/50/51 runs; there
  is no dedicated differ test for re-diffing a persisted qualified body.
- **Store rollback-arm residual** in `store-module-rename.ts` (~lines 225-236,
  reverse pass reusing the forward snapshot) is a separate documented latent gap,
  deliberately untouched; its comment block is intact.
- `propagateTableRename` and the assertion/MV helper signatures shrank (names
  and resolvers now ride the target). `tableRenameTargetsFor` and the
  `TableRenameTarget` type are newly exported from the package root; the store
  package does not need them (single-schema world). Backwards compat was
  explicitly out of scope per the ticket.
