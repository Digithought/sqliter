# What landed

A fifth benchmark suite, `packages/quereus/bench/suites/store.bench.mjs`, with ten
benchmarks. It calls `@quereus/store` key functions directly — no `Database`, no provider,
no query — so a regression in key building gets its own number instead of showing up as
"the full scan got slower".

| Benchmark | What it times | Median (this machine) |
| --- | --- | --- |
| `data-key-int` | `buildDataKey` over one bigint column | 342 µs |
| `data-key-text-binary` | one text column, `BINARY` — the control for the row below | 504 µs |
| `data-key-text-nocase` | the same text under `NOCASE`, which routes through a key normalizer | 551 µs |
| `data-key-text-astral` | the same text plus four astral-plane characters | 692 µs |
| `data-key-json` | a plain object through the generic OBJECT path (canonical JSON) | 1.06 ms |
| `data-key-asc-2col` | `[bigint, text]` ascending — the control for the row below | 866 µs |
| `data-key-desc-2col` | the same two columns descending (encoder bit-inverts every byte) | 894 µs |
| `data-key-composite-4col` | `[bigint, text, real, null]` | 1.53 ms |
| `index-key-text-int` | `buildIndexKey` — index half plus PK half | 939 µs |
| `decode-composite-4col` | `decodeCompositeKey` over the 4-column key | 1.38 ms |

**Every figure is 1 000 key builds, not one** (`KEYS_PER_CALL`). One build is on the order
of a hundred nanoseconds and the `await` around `fn` costs a microtask tick, so a
one-build-per-call benchmark would report mostly harness overhead. The constant is shared
across every entry so the shapes stay comparable.

## What each benchmark asserts, and why the split

Ticket-mandated and worth re-checking, because getting it wrong makes the numbers lie:

- **`setup` round-trips every distinct fixture row** through
  `decodeCompositeKey(encodeCompositeKey(v))` and throws on mismatch. This is what stops
  the suite from happily measuring a broken encoder. Untimed, so free.
- **`fn` asserts only the total encoded byte length** against what `setup` recorded. Cheap,
  and enough to catch an encoder that stopped producing bytes. A full decode inside an
  encode benchmark's timed body would cost about as much as the encode and halve the
  resolution of the thing being measured.
- **`decode-composite-4col` asserts value equality on every column inside `fn`**, because
  there the decode *is* the subject. Its fixture is all-scalar so the check is a typed
  `===` per value, small against a decode that allocates and runs a `TextDecoder`.
- **Fixtures are built in `setup`, never in `fn`** — calibration batches sub-millisecond
  work, so an `fn` that allocated its input would be timing the allocation.

Deliberate design points a reviewer should push on:

- `decodesTo` is **stated per fixture, not derived**. Deriving it would mean
  re-implementing the encoder's own normalization in the bench (NOCASE folds to lower case;
  an integer-valued numeric decodes as `bigint` whatever it was encoded from), and a mirror
  of the thing under test verifies nothing.
- `KeyShape.descending` is **all columns or none**, so `setup` can un-invert the whole key
  with one XOR pass before decoding (`decodeCompositeKey` takes no `directions`). A
  mixed-direction shape would need per-column byte offsets, which the public API does not
  hand out.
- Every shape states its collation explicitly. `encodeValue`'s default is `NOCASE`, not
  `BINARY`, so an omitted collation would silently measure the normalizer path and make the
  `NOCASE` row a duplicate of the `BINARY` one.

# Known gaps — treat these as the floor, not the finish line

- **`data-key-text-astral` is not a controlled A/B.** It is the plain text fixture with four
  astral characters appended, so its delta over `data-key-text-binary` is the surrogate scan
  **plus** 8 extra UTF-16 code units and 16 extra UTF-8 bytes. Two strings cannot match on
  both counts while one is astral and the other is not, so this is a stated limitation
  rather than a fixable one — but if a reviewer wants the scan isolated, a fixture pair
  matched on UTF-8 byte count (accepting a code-unit mismatch) would narrow it. The caveat
  is written into the fixture's doc comment and into `docs/benchmarking.md`.
- **`bench/suites/` is outside the type pass.** `tsconfig.test.json` includes
  `bench/lib/**` and `bench/workloads/**` but not `bench/suites/**`. `store.bench.mjs` was
  written to compile clean under `strict` + `checkJs` and **verified** to (added to the
  include, ran `tsc -p tsconfig.test.json --noEmit`, zero errors attributed to it, reverted
  the include). Widening the include for real is blocked by **21 pre-existing errors** in
  the other four suite files — mostly `TS7005/TS7034` implicit-`any` on their `let db` /
  `let handle` state — which are not this ticket's to fix. Recorded as a bullet in
  `docs/benchmarking.md` § Adding a benchmark. **This is the most likely thing a reviewer
  will want turned into a `debt-` ticket**; it was left un-filed because the fix is four
  other files' annotations, not this one's.
- **No ratio guards.** `data-key-asc-2col` / `data-key-desc-2col` and
  `data-key-text-binary` / `data-key-text-nocase` are exactly the control pairs a
  `ratioGuards` entry wants, but the observed ratios are small (1.03× and 1.09×) and sit
  inside the 5–9% measured spread, so any bound tight enough to catch a lost fast path
  would also fire on noise. Left off deliberately. A guard becomes worth adding if a future
  change makes either path meaningfully more expensive.
- **No coverage of per-column `collations` or `transforms`.** `buildDataKey` takes both;
  the suite only exercises the whole-key `options.collation`. Per-column collations build a
  fresh options object per column, which is a real allocation the suite does not price.
  Out of the ticket's stated scope; `bench-store-micro-paths` may be the right home.
- **The suite prices `BUILTIN_KEY_NORMALIZER_RESOLVER`, not a `Database` resolver.**
  Production encode sites that hold a `Database` pass `db.getKeyNormalizerResolver()`, which
  consults the collation registry. If those two ever diverge in cost, this suite measures
  the cheaper one. Noted as a `NOTE:` at the `options` assignment in `setup`.
- **`RTRIM` is not covered** even though it is the third built-in normalizer. `NOCASE` was
  the shape the ticket named.
- **Numbers are from one machine, one run each** (AMD Ryzen AI 9 HX 370, node v24.2.0,
  Windows). The wall-clock figure in the docs is the mean of two runs (15.1 s, 14.3 s).
