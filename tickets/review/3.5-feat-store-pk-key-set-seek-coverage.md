# Review: store coverage for `pk in (select …)`, plain and isolation-wrapped

Coverage-and-verification ticket. The prereq (`feat-store-pk-in-list-multiseek`) built the
planner/module arm and covered the literal `pk in (1,2,3)` shape; this one covers the
**second caller** — subquery decorrelation → semi join → `rule-key-set-seek` rewrites the
target leaf into the same `_primary_` `plan=5` multi-seek — and the transaction-visibility
case behind the isolation layer.

**No production code changed.** The arm from the prereq turned out to be right on both
open questions, so the only non-test edit is one comment (see *Findings* below).

## The two open questions, answered

Both were settled by probing the real planner (`query_plan()` plus the rule's own debug
log, `DEBUG=quereus:optimizer:rule:key-set-seek`), then pinned with tests.

**1. `seekPreservesTargetOrder` on a store primary-key target: it HOLDS.** A store leaf
arrives as an ordering-only `IndexScan` over `_primary_` (`plan=0`, advertising
`[{column: 0, desc: false}]`), and the pushdown claims that same single-column
`_primary_` index — so the predicate's every clause passes. Consequences, all now pinned:

- `select … where pk in (select …) order by pk` keeps its seek. The `order by` is absorbed
  into the leaf's walk (marking its emission order load-bearing), which is a *decline* for
  a secondary-index target, but here the node claims the leaf's order and **no `Sort`
  reappears**.
- The node's `preservesTargetOrder` logical attribute reads `true`.
- Because the claim is only sound if the store really emits in key order, the tests assert
  **row order**, not just the absence of the `Sort`.

**2. The merge arm fires, and its second gate is vacuous.** `pk in (select id from src)`
— where the key-source column is that table's own primary key, so both sides walk in key
order — arrives as a MERGE semi join and takes `rule-key-set-seek`'s merge anchor.
(`pk in (select k from src)`, an ordinary key column, arrives as a hash semi join. Both
arms are covered.) Of the merge anchor's two extra gates:

- gate 1 (`seekPreservesTargetOrder`) genuinely passes, per question 1;
- gate 2 (key-source row estimate under `min(maxKeys, breakEvenKeys)`) passes
  **vacuously**: a store leaf's PHYSICAL `estimatedRows` reads `0` no matter how many rows
  are committed (measured: 7 committed rows, estimate 0 on both the leaf and the `Project`
  above it), so `0 > threshold` is never true. The rule's comment already said this of the
  memory backend; it is now known to be true of the store too.

## What to exercise when reviewing

`yarn workspace @quereus/store test`, or the single file:

```
node --import ./packages/quereus-store/register.mjs node_modules/mocha/bin/mocha.js \
  "packages/quereus-store/test/key-set-seek-store.spec.ts" --reporter spec
```

Two new blocks, 17 tests:

**`store module, no isolation` → `primary-key target`** (11 tests). Fixture: `pkt` with 4
rows (break-even lands at 6 keys, so every set here seeks — no padding needed) and a key
source `psrc`. The single pre-existing PK test moved into this block unchanged in intent.
Covers: basic set with `inCount`; duplicate + NULL inner values collapsing before
`inCount` is stamped; an empty key set never opening the target; a one-key set; a set
matching nothing still seeking; the merge arm; `order by pk` on **both** arms (plan shape,
`preservesTargetOrder`, and actual ascending rows); a composite primary key declining with
the `MERGEJOIN` surviving and the query still answering; `delete` and `update` driven by
the set reading their victims through the seek; and the store's own pending-op
read-your-own-writes (staged insert + staged in-place update + staged delete, read through
one seek, then committed).

**`store behind the isolation layer` → `primary-key target`** (7 tests). This is the case
`bug-isolation-multiseek-merge-order` was filed for, now reached through the store instead
of the memory backend: the isolation layer merges the underlying stream with its overlay
**by primary key**, assuming both ascend, and `scanMultiSeekPrimary`'s ascending-encoded-
data-key emission is what satisfies that. Covers: a staged insert whose key is in the set;
a staged in-place update of an in-set row appearing exactly once in its new form (both
streams carry it — a merge slip emits it twice); a staged delete not resurfacing; staged
rows outside the key list excluded by the overlay predicate; several staged rows
straddling the committed keys interleaving in key order; `delete … where pk in (select …)`
inside a transaction, read back, then committed; and a rolled-back change leaving the
committed answer intact.

**Every assertion in the isolation block reads RAW emission order — nothing is sorted in
JS.** That is deliberate and it is what makes the block load-bearing (see below).

## Are the tests actually load-bearing? Mutation-checked, yes

Reversing one line in `scanMultiSeekPrimary` (`sort((a, b) => compareBytes(...))` →
`-compareBytes(...)`, i.e. emit descending) turns **11 of the new tests red**, and one of
those failures is not an ordering complaint at all: *a staged delete of an in-set row does
not resurface* fails with the deleted row **present in the output**. So the ascending-
emission contract really is what keeps the isolation merge correct, and these tests catch
its loss as a wrong-rows bug rather than a cosmetic one. The mutation was reverted; the
working tree carries no production change beyond the comment.

## Review findings

- **Merge-arm gate 2 is inert on the store backend too** (measured, above). Recorded two
  ways: the `NOTE:` at the gate in `rule-key-set-seek.ts` was corrected — it claimed only
  the memory backend — and an **Arm 4** was appended to the existing backlog theme ticket
  `bug-row-estimate-conflates-unknown-and-zero`, which already owns the
  unknown-spelled-as-zero root cause. No new ticket filed: this is the Nth instance of a
  class that already has one, and it costs performance only (the rewritten node returns
  identical rows).
- **The file header's "no `order by`" rule now has a documented exception.** The header
  said flatly that `order by pk` makes the rule decline, which is true only for a
  secondary-index target. Corrected in place, pointing at the new block.
- Nothing else surfaced. No tripwires recorded beyond the above.

## Known gaps — treat the tests as a floor

- **The merge arm is pinned indirectly.** `MergeJoinNode` is not exported from
  `@quereus/quereus`, and once the rewrite fires the `MERGEJOIN` op is gone from
  `query_plan()`, so no assertion in the store package can say "*this* query arrived as a
  merge join". The evidence in the file is the composite-key test, where the identical
  query shape declines and the `MERGEJOIN` survives; the direct confirmation was the
  rule's debug log during implementation, which is not captured by any test. The engine
  package's `test/optimizer/key-set-seek.spec.ts` pins the merge arm properly, but against
  the memory backend.
- **One primary-key shape only.** Every new test uses a single-column ascending INTEGER
  primary key. No `primary key (pk desc)`, no TEXT/collated primary key, and no composite
  key under the isolation layer (the composite case is only tested un-wrapped, where it
  declines). The isolation package covers a DESC primary key against the *memory*
  backend (`key-set-seek-merge.spec.ts`), not the store.
- **No NULL / cross-type key-source values on the isolation-wrapped PK path.** Both are
  covered on the un-wrapped path and on the secondary-index path, not on the intersection.
- **No `limit` over the ordered PK seek in this file.** The prereq's review verified
  `limit`/`offset` over the ordered literal-list seek; the `in (select …)` form of that
  combination is untested here.
- **No performance measurement.** "Reads only the listed rows" is asserted through the
  captured `idxStr` (`plan=5`, `inCount=K`), not through KV-operation counts on this path
  and not through timings. The `CountingKVStore` machinery in the file is used only by the
  pre-existing `limit 1` batching test.
- **`store-index-seek-batched-row-resolution`** (also in `implement/`) makes
  `scanMultiSeekPrimary` fetch rows in one batched read. Independent of this work, but if
  both have landed, the combined path is what the downstream ledger case needs — worth
  measuring together. Nothing here blocks it; these tests do not assert round-trip counts,
  so they should survive that change untouched.
