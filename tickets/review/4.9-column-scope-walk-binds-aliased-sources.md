# What changed

`ALTER TABLE … RENAME COLUMN` and `ALTER TABLE … DROP COLUMN` both decide "does
this stored expression reference this column?" with one scope-aware walk in
`schema/rename/column-rename.ts`. That walk used to treat a FROM source carrying
an alias (`from t as a`) as contributing **no columns to unqualified name
resolution**, so a bare `x` written against `from t a` was invisible to both
verbs. Dropping the column was then allowed even while a live rule read it —
and because assertions are recompiled on every commit, the orphaned rule went on
to reject every write to the whole database.

The fix is a representation change rather than a widened predicate. `ScopeFrame`
carried two maps — `unaliased` (bare names) and `aliasMap` (aliases) — and four
sites read `unaliased` as if it meant "what an unqualified name can bind to",
which is wrong the moment any source is aliased. Every FROM source exposes
exactly one qualifier: its alias when it has one, its bare name otherwise. The
two maps are now one:

```ts
interface ScopeFrame {
	/** Lowercase qualifier → resolved object key, one entry per FROM source. */
	qualifiers: Map<string, string>;
	…
}

/** Whether any source bound in `frame` resolves to `targetKey`. */
function frameBindsTarget(frame: ScopeFrame, targetKey: string): boolean;
```

After the merge there is no second map for a future edit to consult "the
unaliased ones" — the wrong question can no longer be asked.
`isTableInUnaliasedScope` is now `unqualifiedRefBindsTarget`;
`frameBindsTargetUnaliased` is now `frameBindsTarget`.

# How to exercise it

The headline shapes, all now correct where all six were broken before:

```sql
create table t (id integer primary key, x integer);
create assertion a1 check (not exists (select 1 from t a where x < 0));
alter table t drop column x;      -- REFUSED (was accepted; database then unwritable)
```

```sql
create table t (id integer primary key, x integer);
create view v as select * from t a;   -- republishes x through a star over an alias
create view w as select x from v;
alter table t rename column x to z;
select * from w;                  -- returns a `z` column (was: Column not found: x)
```

Validation to re-run:

- `yarn workspace @quereus/quereus run test` → **8976 passing, 16 pending, 0 failing**
  (baseline the plan measured: 8918 / 13 / 0; the delta is the new spec's 58 + 3).
- `yarn workspace @quereus/quereus run test:store` → **8968 passing, 24 pending, 0 failing**.
  Run because ALTER is exactly what the store module re-exercises.
- `yarn lint` → clean.

# Where the coverage is

**`test/schema/column-scope-body-spellings.spec.ts` (new)** — a generalized
spelling × verb matrix, not one case per reproduction. One table `t(id, x)`;
fifteen ways a stored body can read or republish `x` (bare projection, star,
`t.*`, `a.*`, each over an unaliased and an aliased source; under a join; under
an exposing CTE, aliased and not; under an alias that collides with another real
table's name; through a subquery source). Each spelling is driven through three
arms:

- **RENAME** — create a view on the spelling, rename, then *run a query against
  the view*. The assertion is planability, deliberately not rewritten body text.
- **DROP refuses** — twice per spelling: an assertion reading the column directly
  through that FROM shape, and an assertion reading it through a view that
  republishes via that shape.
- **DROP accepts** — the same view, plus a live assertion reading a *different*
  column. Pins that the refusal is about the column a rule reads, not about "a
  republisher exists" or "some assertion exists".

That is what makes rename/drop parity a property rather than paired hand-written
cases. All seven edge cases from the plan's table are in it.

**sqllogic** — the two user-visible headlines: `41.10.2 § 38` (an aliased source
blocking `DROP COLUMN`, including the "database still writable" check that is
the point of refusing, plus a guard rail where the bare name legitimately binds
a *different* aliased source and the drop stays legal) and `41.3 § 65` (rename
following through `select * from t a` and through a two-level cascade, plus the
matching guard rail).

**Docs** — the known limit was documented in three places and all three said
"aliased FROM source". All now describe the narrower residual (subquery /
function sources) and state the rule positively: an alias adds a qualifier, it
does not take the source's columns out of scope.

# Honest gaps — read these first

**1. A mid-flight correction the plan did not anticipate.** The plan predicted
the merge would make a duplicate qualifier in one FROM (`from t join u as t`)
last-write-wins instead of alias-wins, and asked for a `NOTE:` saying the SQL is
ill-formed either way. That premise was wrong, and I checked rather than wrote it
down: the planner **accepts** that spelling and resolves a qualified ref to the
**first** such source in FROM order (`select t.k from t join u as t` reads `t`;
`from u as t join t` reads `u`; a bare `k` is rejected as ambiguous). So the walk
now binds first-write-wins via a `bindQualifier` helper, which also *fixes* a
latent disagreement — the old alias-first lookup read `from t join u as t` as
`u` where the planner reads it as `t`. Pinned by the new spec's
"a duplicated qualifier follows the planner" case.
**This is the part of the diff with the least prior art — worth an independent
read of both the planner claim and the helper.**

**2. A second arm of the residual, found while writing the matrix.** The plan
scoped the residual to a *star* over a subquery source. It is wider: an outer
**bare column ref** over a subquery source is equally invisible, and the two
verbs disagree on it. `create view v as select id, x from (select id, x from t) s`
— the DROP guard sees the column (the inner select is walked in its own frame)
but RENAME rewrites only the inner reference, leaving the view naming a column
its own source no longer publishes. Pre-existing, unrelated to this diff, same
root site and same fix, so it is appended as an arm to
`bug-column-verbs-blind-to-star-over-subquery-source` rather than filed fresh.
Pinned in the spec as a rename-arm-only `pending` cell.

**3. No function-source cell in the matrix.** A function source never carries
`t`'s columns at all, so it can neither bind a bare `x` nor republish one — it
sits beside the subquery source in the walk only because both are equally
unaskable. Writing a cell for it would have meant inventing a shape no user can
author. The spec header says so rather than leaving the absence unexplained.

**4. Nothing re-proves the pre-fix failures.** The plan's fix-stage run verified
all six reproductions fail on `main`; I did not re-verify that (it would mean
reverting the fix, and the working tree is not mine to sanitize). The new tests
pass now; that they *would* have failed before rests on the plan's evidence plus
reading the diff.

**5. Test floor, not ceiling.** The matrix covers view bodies and assertion
bodies. It does not drive the aliased spelling through every *site* the walk
serves — column DEFAULTs, generated-column bodies, partial-index predicates,
`with inverse` / `with defaults` clauses, or materialized views. Those share the
same walk and the existing suites cover them for unaliased spellings, so the risk
is low, but the aliased × site product is genuinely untested.
