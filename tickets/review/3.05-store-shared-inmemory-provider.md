# What landed

`createInMemoryProvider(options?)` in `packages/quereus-store/src/testing/memory-provider.ts`,
exported from `@quereus/store/testing`. An all-`InMemoryKVStore` `KVStoreProvider`, built to
match `createCountingProvider`'s settled conventions:

- Store names via `buildDataStoreName` / `buildIndexStoreName` / `CATALOG_STORE_NAME` /
  `STATS_STORE_NAME` — never hand-composed strings.
- `getStatsStore` returns one unified `__stats__` store regardless of the schema/table
  arguments it is called with (per the `KVStoreProvider` interface).
- `options.costProfile` is spread in only when present — `createInMemoryProvider()` and
  `createInMemoryProvider({})` both produce a provider with NO `costProfile` property at all
  (`'costProfile' in provider === false`), matching what a genuine pre-profile third-party
  provider looks like. `cost-profile.spec.ts` and `key-set-seek-store.spec.ts` depend on this
  same shape from their own private copies — this factory did not touch those specs.

Unlike `createCountingProvider` (which deliberately omits both delete hooks), this one
implements `deleteIndexStore` and `deleteTableStores`, and both ERASE:

- A store that was never created → no-op.
- A live store → `clear()`ed (so a caller still holding the handle sees the erase), then its
  map entry dropped so the name re-opens fresh.
- An already-closed store (the order `StoreModuleIndex.tearDownIndexStore` actually takes:
  close the cached handle, then ask the provider to delete) → `clear()` is skipped (it would
  throw — `InMemoryKVStore.checkOpen()` rejects a closed store) and the map entry is dropped
  directly, since `close()` already dropped the bytes.
- The unified `__stats__` store is never touched by `deleteTableStores` — a table's row count
  is one entry there, not a store.

That closed-vs-live distinction needed a way to ask an `InMemoryKVStore` whether it's closed
without provoking the throw. Added a small `get isClosed(): boolean` to `InMemoryKVStore`
(`common/memory-store.ts`) rather than local bookkeeping in the factory, since the store
already tracks the flag internally and a bare `try { clear() } catch {}` is what the project's
exception rules forbid.

`renameTableStores` is deliberately NOT implemented — `StoreModule` falls back to its generic
copy for a provider without it, and nothing that needs this factory renames yet.

# How it was tested

`packages/quereus-store/test/memory-provider.spec.ts`:

- `runStoreNameDistinctness('createInMemoryProvider store names', lifecycle)` and
  `runStoreReclaimConformance('createInMemoryProvider store reclaim', lifecycle)`, sharing one
  `KVProviderLifecycle` closure. Ran standalone with the `spec` reporter to confirm both delete
  hooks actually exercised (no "SKIPPED" warning) and all 15 cases across both batteries pass,
  including "erases a store whose handle the caller already closed" and the 1100-row bulk
  erase case.
- Three `costProfile` shape cases: absent with no args, absent with `{}`, and a declared
  profile surfaced by reference (`provider.costProfile === costProfile`, not just a
  truthiness check).

Full package validation, both clean:

```
yarn workspace @quereus/store run build
yarn workspace @quereus/store run typecheck   # tsc --noEmit + tsc -p tsconfig.test.json --noEmit
yarn workspace @quereus/store run test        # 1827 passing (up from the pre-change baseline
                                               # by the 15 new cases here)
```

# What a reviewer should look at

- The `isClosed` getter is a new public-surface addition to `InMemoryKVStore`, which is
  itself exported from the main `@quereus/store` entry point (not just `/testing`) — worth
  confirming that's an acceptable surface growth rather than something that should live only
  in the testing subpath. It's a plain boolean accessor with no side effects, so the exposure
  risk looked low to me, but it's a judgment call.
- I did not add `createInMemoryProvider` calls anywhere outside its own spec — no existing
  spec was pointed at it. That sweep is explicitly out of scope per the ticket and is what's
  left of `debt-store-test-shared-inmemory-provider` (backlog); I appended an arm there
  recording this landed.
- I did not touch `tickets/implement/3.1-bench-store-workloads.md` (its `prereq:
  store-shared-inmemory-provider` is now satisfied) — leaving that for the runner to pick up
  rather than editing another ticket's file from in here.
- No negative-control test drives the erase logic against a double built to violate it (the
  way `test/store-name-distinctness.spec.ts` does for the naming guard) — the shared
  `runStoreReclaimConformance` battery itself is what's exercised, and it already has
  LevelDB/IndexedDB as reference implementations. I judged a third redundant negative-control
  spec not worth it for a ~30-line erase function, but flagging the asymmetry.
