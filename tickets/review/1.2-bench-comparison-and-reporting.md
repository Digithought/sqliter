# What landed

## Environment capture (`bench/lib/environment.mjs`, new)

Every results file now carries an `environment` block: CPU model, logical core count,
total memory, platform, OS release, architecture, Node version, V8 version, commit hash,
and a tri-state `dirty` flag for the working tree (`true` / `false` / `"unknown"` outside a
git checkout). `commit` and `node` are also lifted to the top level of the file, derived
from the same capture rather than read twice, because those are the two fields a human
skims for.

Both git lookups go through one helper that returns `null` on any failure, with
`windowsHide: true` and a 5 s timeout. Outside a checkout the harness still runs.

`compareEnvironments()` reports material differences only: CPU model, core count, platform,
architecture, Node **major** version. OS point release and memory are recorded but not
warned about — warning on a Windows patch bump would train everyone to ignore the banner.
A baseline with no `environment` block at all is itself reported as a mismatch.

## Noise-aware comparison (`bench/lib/compare.mjs`, new; `stats.mjs` gains the floor)

```
noiseFloor% = max(5, sqrt(currentSpread² + baselineSpread²))
```

Verdicts: `no-change` (within the floor), `regression` (clears the floor **and** >10%,
red, gates), `improvement` (mirror image, green), `changed` (clears the floor, under the
10% minimum — printed plainly, never gated). The floor prints in a `Noise` column beside
every delta so the judgement is legible.

A benchmark unstable in **either** run is never gated; its delta still prints and its row
says `not gated`. A baseline median that rounds to zero yields no delta at all rather than
`Infinity`. A baseline entry with no `spread_pct` gets `ASSUMED_SPREAD_PCT` (20%) and the
banner says how many entries needed it.

`compare.mjs` is pure — `compareRun(rows, baselineBenchmarks, filter)` in, records out.
Nothing in it prints or touches the filesystem, so the rules are testable without running a
benchmark.

## Four non-delta outcomes, plus a counted summary

`new`, `missing`, `filtered` (in the baseline, excluded by `--filter` — reported separately
from `missing` so a narrowed run does not look like a deletion) and `failed`. Every name in
either run appears exactly once. The summary counts all nine statuses and then names each
excluded benchmark individually with the reason.

## Ergonomics

- `--baseline latest` resolves the newest file in `bench/results/`, **during argument
  handling**, before this run writes its own. Lexicographic sort on the ISO-timestamp
  filenames, deliberately not mtime; the assumption is commented at the sort. Empty or
  missing directory is a clean `UsageError`.
- `--json` moves every human line to stderr and writes the result object to stdout, last,
  after everything else has succeeded. Child stdout is forwarded to the human stream too,
  so a chatty benchmark cannot corrupt it.
- ANSI is suppressed whenever the human stream is not a TTY. Colour helpers replaced the
  inline escapes; padding now happens before colouring (the old code hand-compensated for
  escape width in one place and would have misaligned in others).
- `checkRatioGuards` was refactored to return verdict records; `reportRatioGuards` prints
  them. Same behaviour, but the verdicts now also land in the JSON as `ratio_guards`.

## Rounding precision — an unplanned but necessary fix

`round()` in `stats.mjs` rounded every duration to the microsecond. A 4 µs parser median
can then only move in 25% steps, so two identical runs differ by exactly 0% or exactly 25%
and nothing between — with an ~8% noise floor, that manufactures a gated regression out of
the rounding alone. Precision raised to nanoseconds (`PRECISION = 1e6`); percentages keep
their own coarser `PERCENT_PRECISION = 1e3` so the JSON does not print six decimals of a
spread. The table's µs format gained one decimal for the same reason — at whole µs, 4.2 and
4.4 both printed `4 µs` next to a Delta column claiming +5%.

Two spec assertions in `test/bench-calibration.spec.ts` moved with it, plus one new
assertion that two medians a fraction of a microsecond apart stay distinct.

# **The acceptance run did NOT come out green — read this first**

The ticket's headline acceptance criterion is: two consecutive `--baseline latest` runs on
an unchanged tree report no change or sub-threshold deltas and exit zero. **It did not.**
Reporting the actual output as the ticket instructs, rather than tuning until it passes:

```
Comparison: 4 no change, 0 changed below the gate, 4 improved, 2 REGRESSED,
            17 unstable (not gated), 0 new, 0 missing, 0 filtered, 0 failed

regression   execution/temporal-arith-scan-10k      +48.8%  floor ±11.5%
regression   execution/group-by-10k                 +26.2%  floor ±14.4%
improvement  execution/order-by-text-unicode-10k    -19.1%  floor ±15.9%
improvement  execution/group-by-text-10k            -38.0%  floor ±12.3%
improvement  execution/correlated-subquery          -29.4%  floor ±19.3%
improvement  mutation/single-row-insert-1k          -24.9%  floor ±22.6%
```

Both runs were 27-benchmark full runs, minutes apart, same commit, same machine — a machine
that was simultaneously running an agent session, which is the point.

**What this shows, precisely:** almost every benchmark moved in the *same direction* between
the two runs (nearly all deltas negative — the second run was broadly faster). That is a
run-level displacement, not per-benchmark noise. The flagged benchmarks each had a **tight**
within-run spread in both runs (3-6% rIQR): a narrow distribution around a centre that
moved. `stats.mjs` already documents this exact failure mode in a comment on `stable`, and
the ticket's own design brief acknowledges it ("This measures within-run noise only").

So the implemented rule is the specified rule, and it is a strict improvement over the flat
20% — but **a noise floor derived from within-run spread cannot see between-run drift**, and
on a loaded machine that drift is larger than the floor. Anyone treating this as a gate
today will get false reds. Candidate fixes, none of them attempted here:

- take the median of N repeated runs per benchmark rather than one run's median (costs N×
  wall-clock; the honest fix),
- add a between-run displacement estimate — if most benchmarks moved the same direction by a
  similar amount, subtract the common-mode shift before judging any individual one,
- require a regression to reproduce across two consecutive comparison runs before gating.

The downstream `bench-regression-gate` ticket builds on the exit-code contract this ticket
documents; whoever picks it up has to resolve this first, or the gate will be ignored within
a week. **This is the single most important thing for the reviewer to weigh.** I did not
file a separate ticket for it because it is squarely the next ticket's problem and filing it
separately would fragment the decision.

# Use cases for testing and validation

## Passed here

- `yarn docs:check` → `Docs OK: links resolve, invariants well-formed, sizes within ratchet,
  doc and package tiers declared.`
- `node test-runner.mjs --grep "bench/lib"` → 45 passing.
- `node bench/run.mjs --filter planner/simple --json 2>/dev/null | <parser>` → parses;
  keys `timestamp, commit, node, environment, wall_clock_ms, benchmarks, failures,
  ratio_guards, baseline, comparison`.
- Baseline hand-edited to a fictional CPU and core count → the mismatch banner prints above
  the table, naming both differences.
- Old-format baselines (the pre-existing files in `bench/results/`, which have no
  `environment` and no `spread_pct`) → compared without crashing, banner reports the missing
  environment, and the assumed-spread note fires.
- Non-TTY output → no ANSI escapes in any of the captured output above.

## Worth a reviewer's attention

- **`--filter` + `--baseline`**: exercised (`filtered` count was 0 in the runs above because
  the baseline was itself a filtered run). Worth running `--baseline <full run> --filter
  parser/` to see the `filtered` bucket populated with 23 entries and confirm it does not
  drown the summary.
- **A failing benchmark under `--baseline`**: the `failed` status path is written but was
  never exercised — no benchmark failed in any run here. Break one deliberately (throw in an
  `fn`) and check it reports as `failed`, not as `missing`, and that the run exits non-zero.
- **`--baseline latest` with an empty `bench/results/`**: the error path is written but the
  directory was never empty here.
- **`--json` when a benchmark fails**: stdout should still be exactly one parseable object,
  written after the failure report.

## Not run — flag honestly

- **`yarn test` and `yarn lint` in full were not run** (budget). Only the bench specs were
  executed. The changed TypeScript is limited to two assertions in
  `test/bench-calibration.spec.ts`; everything else is `bench/*.mjs`, which nothing else
  imports. Low risk, but unverified.
- **Whether eslint covers `bench/**/*.mjs`** was not checked. If it does, the new files have
  not been linted.
- **`yarn bench` on a quiet machine.** Every measurement above came from a machine running an
  agent session. A reviewer with an idle machine should repeat the two-run acceptance test —
  the result may well be green there, which would itself be informative: it would confirm the
  failure is load-induced rather than a bug in the floor.
