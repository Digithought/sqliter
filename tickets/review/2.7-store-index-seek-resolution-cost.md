# Charge the cost model for resolving an index entry to its row — review handoff

## What landed

**`AccessPlanBuilder.addCost(delta)`** (engine). Adds to the cost a shape constructor
already set, so a module can price an extra per-row term without restating (and drifting
from) `eqMatch` / `rangeScan`'s formula. Throws if no cost was set first.

**`ROW_RESOLUTION_COST = 1.0`** (store). Charged per estimated returned row on the `eq`,
`prefixRange` and `range` secondary-index arms, on top of the shape's own per-row term. The
constant's reasoning is written at its declaration: a secondary-index path reads the index
entry AND then the row it names, batched 256 at a time by `store-index-seek-batched-scan`,
so parity with one sequential row read is the starting point; nothing was measured against
real storage. The declaration also records the arithmetic that makes it non-tunable upward:
because selectivity is a fixed FRACTION, each arm's cost and the scan's are both linear in
the row count, so a constant either flips an arm always or never — `range` flips at 2.83,
`prefixRange` at 6.17, `eq` at 9.7.

**Seek-versus-scan comparison** in `computeBestAccessPlan`. The module now builds the
sequential-scan plan and returns it when the best seek prices strictly above it (ties keep
the seek). A vetoed seek returns the scan directly rather than falling through to the
cost-only fallback, which would have advertised an index arm's cheaper cost for the same
sequential work. Losing the seek claims no filters, so the residual is retained and rows
are identical.

**Two NOTEs** at the sites a future reader will meet them: on `ARM_SELECTIVITY` (the
missing selectivity estimate, and precisely what would have to change — the store keeping a
value distribution AND `BestAccessPlanRequest` carrying it, neither of which exists, so an
analyzed table plans identically today), and on the multi-seek arm (below).

## The decision the ticket asked me to make, and which way it went

The ticket asked for the resolution term on the multi-seek arm too, and asked me to judge
whether the resulting flip was correct or an artifact. **It is an artifact, measured twice,
so the multi-seek arm carries neither the term nor the comparison.** Both exemptions are
documented at the site with this arithmetic:

- `multiRows = min(estimatedRows, inCount × rows)` saturates at the whole table from ten
  seek keys up (and at two or three on a tiny table), because `rows` is the fixed 0.1 × N
  equality constant. Charging 1.0 per row against that clamp **failed 16 tests** in
  `key-set-seek-store.spec.ts` — every one a runtime key-set semi join over a 3-to-4-row
  table that stopped seeking. Worse, the engine's `rule-key-set-seek` interpolates a
  break-even from this cost, and with the term `cost(1000 keys) = 500 + 1.3 × N` exceeds a
  scan's `N` for EVERY N, so key sets above ~710 keys would stop seeking on a table of any
  size — including the large tables the feature exists for.
- The comparison itself must also skip the arm: `rule-key-set-seek` probes the module with
  SYNTHESIZED runtime-set filters at 2 and 1000 keys purely to read a cost slope, and
  abandons the rewrite if a probe answer stops naming an index. Nothing in the module
  distinguishes a probe from a user's own `col in (…)`. Applying the veto **failed 11 more
  tests** (200- and 300-row tables where the seek is unambiguously right at the key counts
  actually used).

The cost of leaving the term off is recorded honestly in the code: against another index's
`eq` arm (which does pay it) a small-key IN now looks relatively cheaper than it is —
`where a in (x, y) and b = ?` on a 1000-row table prices ix_a at 61 and ix_b at 130 and
picks ix_a, though ix_a's own estimate says it fetches 200 rows to ix_b's 100. Fixing that
ranking and keeping the feature both require the union estimate to stop clamping, which is
filed as `backlog/debt-store-multi-seek-union-row-estimate` and referenced from the NOTE.

Per the ticket, `bug-store-pk-range-preempts-cheaper-index` (PK arms returning by position)
is untouched — no PK arm's precedence or pricing changed here.

## The honest limitation

**This ticket closes the per-row-cost half of the mispricing and NOT the selectivity half.**
A predicate matching most of a large table is still modelled at the arm's fixed 10% / 15% /
30%, so it still prices below a sequential scan and the new comparison never fires for it —
which is the shape the downstream project actually hit. The comparison is reachable today
only where the fraction's `max(1, …)` floor makes an arm's estimate the whole table, i.e. a
one-row table. It becomes discriminating the moment real statistics land.

  passing, 0 failing** across all workspaces.

  `tsc -b` covers the two source files.

New tests, in `pushdown.spec.ts` under `row-resolution cost and the seek-versus-scan
comparison` (module-level, so the cost arithmetic is asserted directly rather than inferred
from a plan shape):

- one per arm — `eq` / `range` / `prefixRange` — asserting `rows` and the exact cost
  `indexCost + rows × (perRow + 1.0)`. Each arm gets its OWN table: `a = ?` suits both a
  single-column and a composite index's leading prefix and the two price identically, so a
  shared table would leave the winner to declaration order.
- a cost-only decline (partial index) pays no resolution term.
- a selective indexed predicate still beats the scan (SQL level, plan + rows).
- the reachable veto case: a one-row table's `eq` arm prices at 1.6 against a 1.0 scan,
  loses, claims no filters, and the residual returns identical rows for both a matching and
  a non-matching predicate. **`analyze` is required for the SQL half of that test** — an
  un-analyzed store table reaches the module carrying the catalog's 1000-row placeholder,
  because the planner's hint wins over the live row count the store maintains.
- the multi-seek exemption: a synthesized 1000-key probe on a 200-row table prices above
  the scan and still advertises `indexName` + `seekColumnIndexes`.

## Known gaps for the reviewer

- **No measurement behind 1.0.** It is a shape constant chosen for parity with a sequential
  row read, argued from the batching that `store-index-seek-batched-scan` introduced. If
  you think a random point read in an LSM/B-tree store deserves more, note that anything
  above 2.83 disables the `range` arm entirely — the model has no room between "no effect"
  and "off".
- **The comparison is near-dead code today** (one-row tables only), by construction of the
  fraction-based selectivity. I did not manufacture reachability for it.
- **`estimatedRows` now decides plan SHAPE, not just cost.** `StoreModule`'s own NOTE says
  "harmless while this only moves costs"; that sentence is now weaker. A prepared statement
  holds its compiled plan across row-count changes, so a statement compiled when a table
  held one row keeps the scan. Left as-is (the fix belongs at the recompile trigger), not
  re-noted in code — worth a reviewer's opinion on whether that NOTE should be updated.
- **Cost-only index plans still under-advertise.** They price and size themselves as an
  index arm while performing a full sequential scan; the new comparison deliberately does
  not route through them, but their own advertisement is still a pre-existing lie to the
  optimizer. Out of scope here; not filed.
- The `IndexPlanCandidate` wrapper exists solely to carry `isMultiSeek` out of
  `tryIndexAccessPlan`. If the follow-up ticket lands, both the flag and the wrapper should
  disappear.
