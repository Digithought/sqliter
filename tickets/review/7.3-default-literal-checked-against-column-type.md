# What changed

Three call sites now fold a literal DEFAULT through the existing `foldDefaultToType(expr,
logicalType, columnName)` helper (`packages/quereus/src/types/validation.ts` ~185), which
returns `undefined` for a non-literal (function call, `new.<col>`, bare column — deferred to
write time, unchanged), returns the converted value for a literal that folds, and **throws**
`QuereusError(MISMATCH)` for a literal that folds but cannot convert. Every call site
discards the return value — the throw is the whole point.

1. **`SchemaManager.createTable`** (`schema/manager.ts` ~2824): a loop over every column,
   right after the existing `validateDefaultDeterminism` call and before `module.create` /
   `createBacking`, so a refusal leaves no storage behind. Not on the import/rehydrate path
   (`buildTableSchemaFromAST`, `importTable`/`importDDL`) — a catalog written before this
   guard must still open.

2. **`runAlterColumn`'s SET DEFAULT arm** (`runtime/emit/alter-table.ts` ~1494): folds the
   *new* default against the column's *current* logical type, right after the existing
   `validateAlterColumnDefault` call (which checks bind-params/bare-columns/determinism but
   says nothing about type).

3. **`runAlterColumn`'s SET DATA TYPE arm** (~1481): folds the column's *existing* stored
   default against the **new** type, beside the existing `validateCollationForType` check
   that guards the analogous "the retype would mint a column CREATE TABLE would refuse" case
   for collation. Placed after the PRIMARY KEY refusal (~1459), so on a PK column that refusal
   fires first with its own clearer message.

Both ALTER call sites live in the engine-side `runAlterColumn`, ahead of `module.alterTable`
— one change covers both the memory module and the store module. Neither backend's own
`alterTable`/`layer/alter-column.ts` was touched.

`ALTER TABLE … ADD COLUMN … DEFAULT` already had this check (a prior ticket,
`bug-add-column-default-not-coerced`), and `SET NOT NULL`'s backfill already had it too — this
ticket closes the two remaining gaps (CREATE TABLE, SET DEFAULT) plus one the ticket
specifically called out (SET DATA TYPE against the *existing* default).

# A pre-existing test relied on the old (wrong) behavior — fixed, not worked around

`yarn test`'s property-based suite (`test/property.spec.ts`, "Declarative-schema equivalence
(property)") failed after this change: its `tableShapeArb()` generator picked a literal
DEFAULT (integer or text) **independent of the generated column's type**, so it could (and,
under a fixed seed, did) generate an `INTEGER` column defaulting to a text literal like
`'a'` — exactly the case this ticket now refuses. That's not a false positive; it's the
generator exercising the exact bug this ticket fixes and getting a *different, now-correct*
answer (CREATE TABLE throws) than before. Fixed the generator (`literalArbFor(type)`,
`test/property.spec.ts` ~1568) to pick a literal matching the column's own declared type, so
the two DDL-equivalence arms (canonical `CREATE TABLE` vs `declare schema {…} / apply
schema`) stay comparable rather than both being expected to throw on a shape that's now
illegal by design. This was the only test in the full suite affected.

New sqllogic (both run under `yarn test` and `yarn test:store` — no memory/store split):

- `10.1.7-create-table-default-type-check.sqllogic` — CREATE TABLE: an unconvertible literal
  default rejects across INTEGER/REAL/DATE/JSON columns and leaves the table unregistered
  (`select name from schema() where type='table' and name='…'` → `[]`); a convertible literal

  three non-foldable shapes stay deferred exactly as before (function call, `new.<col>`, a

  migration (`endSchemaBatch`'s existing abort arm — no new machinery) and the table never
  registers.
- `41.15-alter-column-default-type-check.sqllogic` — `SET DEFAULT` with an unconvertible

  the type nor stored row values moved; the stated remedy (`DROP DEFAULT` then retype)
  verified to work; `SET DATA TYPE` still succeeds when the existing default *is* convertible,
  and a later insert under the new type stores the default already converted; the PRIMARY KEY
  SET-DATA-TYPE refusal still wins over (i.e. is checked before) the new fold.
- `test/schema-manager.spec.ts` — one new unit test: a table is created for real (valid

  not `module.create`, and is not gated by this ticket's change, so the rehydrate succeeds and
  the table is registered with its (now theoretically-impossible-to-declare-fresh) bad

# Use cases for review / validation

- `create table a (id integer primary key, n integer default 'abc')` → throws `Type
  conversion failed for column 'n': Cannot convert 'abc' to INTEGER`, table not registered.
- `create table … (n date default 'not-a-date')`, `(n json default '{')` → same shape, generic
  parse failure.
- `create table … (n integer default '7')` → accepted, stored as `7` (integer), not `'7'`.
- `alter table t alter column n set default 'abc'` where `n` is `integer` → throws, column
  keeps its prior default.
- `alter table t alter column n set data type integer` where `n` is `text default 'abc'` →
  throws; `alter table t alter column n drop default` then the same retype succeeds.
- `alter table t alter column n set data type integer` where `n` is `text default '7'` →
  succeeds; a later insert omitting `n` stores `7` (integer).
- `default (some_function())`, `default (new.other_col)`, a mutation-context variable default
  — all still deferred to write time, unaffected by this change.
- `default null` on any column type — always accepted, never confused with a deferred
  (non-foldable) default.
- A pre-existing (pre-guard) catalog entry with an unconvertible default — still opens via
  `importCatalog`/`importTable`; only fresh `CREATE TABLE`/`ALTER COLUMN` are gated.

# Known gaps / not independently re-verified this pass

- The ticket's TODO asked for "every type family that can reject a literal" including a
  temporal column; I covered `DATE` and `JSON` with a generic `-- error:` (no substring
  match on the exact parse-failure text) rather than pinning the exact message for each type
  family — the CREATE-TABLE-time guard reuses the same `validateAndParse`/`parseValue` every
  other call site already relies on for its error text, so this isn't new surface, but a
  reviewer wanting per-family message pins could add them.
- I did not add a dedicated sqllogic case for `ALTER COLUMN SET DATA TYPE` combined with a
  CHECK constraint on the same column (the ticket doesn't ask for one, and the fold runs
  before any CHECK re-validation regardless), but it's an adjacent interaction I didn't
  explicitly probe.
- The `apply schema` / `endSchemaBatch(error)` abort path is exercised by one sqllogic case
  (§6 of `10.1.7-…`) asserting the table never registers; I did not additionally verify that
  a *partially-applied* multi-table migration (some tables created before the bad one) rolls
  those back too — that's existing `endSchemaBatch` machinery this ticket doesn't touch, same
  posture the sibling `7.1` ticket's handoff took on the same question.
