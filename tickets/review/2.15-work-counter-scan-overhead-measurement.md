# What this is

Measurement-only ticket. No code change. `work-counter-vtab-boundary` (now in
`tickets/complete/`) added one per-scan local and one per-row `if (tableCounters)`
branch to `emitSeqScan` in `packages/quereus/src/runtime/emit/scan.ts`. This ticket
runs the benchmark suite before and after that change, on the same machine in one
sitting, to put a number behind the "counters are free when off" claim.

# Methodology

`yarn bench` (`node bench/run.mjs`) requires the built `dist/` — suites `import` from
`../../dist/src/index.js`, not the TypeScript source — so each side of the comparison
is `yarn build` then `node bench/run.mjs` from `packages/quereus`, one after the other
in the same shell session, same machine (AMD Ryzen AI 9 HX 370, 24 cores, win32).

**Commit choice, and a false start worth recording:** the ticket says "this commit and
its parent." The first attempt used the last commit that touched `scan.ts` before the
ticket (`a268fbd0f`, found via `git log -- scan.ts`) as "parent." That was wrong — eight
unrelated commits sit between `a268fbd0f` and the actual change (`work-counter-core`,
`bench-work-counters`, two unrelated bug fixes), and comparing against it produced
nonsense deltas: -50% to -80% on `parser/*` and `planner/*` benchmarks that
`emitSeqScan` cannot touch at all. That comparison also had no baseline `environment`
block (recorded before the harness captured one), which was the tell.

The correct parent is the **literal git parent** of the commit that touched
`scan.ts`: `git rev-parse e47a1a7f6^` → `1287905a1` (`ticket(review):
work-counter-core`). `git diff --stat 1287905a1 ea5f8ddae` confirms this isolates
exactly the `work-counter-vtab-boundary` diff (`scan.ts`, `dml-executor.ts`,
`work-counters.ts`, tests, docs) plus this ticket's own file — nothing else.

- **Baseline**: `1287905a1` (parent of the scan.ts change)
- **Current**: `ea5f8ddae` (HEAD — includes the review-stage rework of the same code,
  same logic reordered)
- Both built with `yarn build` (plain `tsc`, no workspace deps) immediately before
  their `bench` run.

**No regression. No gated change of any kind** — "Comparison: 24 no change, 1 changed
below the gate, 0 improved, 0 REGRESSED, 2 unstable (not gated), 0 new, 0 missing, 0
failed." The scan-heavy rows most relevant to `emitSeqScan` — `full-scan-10k`,
`filtered-scan-index-10k`, `text-pk-range-scan-10k`, `text-pk-point-seek-10k`,
`join-1kx1k`, `correlated-subquery`, `hand-batched-peer-count` (the last three are
nested-loop-join shapes, i.e. the ones that exercise the per-row branch hardest via
one `queryCalls++` per re-scan) — all land inside their noise floor or improve. This
matches the ticket's prediction: the change removed a per-connect string allocation
(the deferred-rename key, now built once in the emitter closure) and added one
already-undefined property read plus one constant-false branch per row, so if
anything the net is a hair cheaper, not slower.

`join-1kx1k` shows a -10.3% delta, which clears the 10% minimum but is excluded from
gating because the *baseline* run was itself unstable (20.6% spread, `join-1kx1k`
tagged `unstable` in the raw baseline table) — per `docs/benchmarking.md`, "a benchmark
unstable in either run is never a regression [or improvement]." Read as a data point,
not a verdict: it's an improvement-direction number on a noisy benchmark, not a
regression.

# Not in scope / not touched

Metrics-*on* execution was explicitly out of scope per the ticket and was not

## Review findings

- No regression found; nothing to file. The default (counters-off) scan path costs
  the same or slightly less than before the change, within noise, across all 27
  benchmarks.
- Process note for future before/after benchmark tickets: when isolating a change's
  cost, use the literal git parent of the commit that introduced it
  (`git rev-parse <commit>^`), not the last commit touching the same file found via
  `git log -- <path>` — the latter can skip many unrelated intervening commits and
  produce comparisons that look like regressions (or improvements) but are actually
  measuring everything that landed in between. Worth a line in
  `docs/benchmarking.md` if this trips up another ticket; not adding it here since
  this ticket's scope was the measurement, not the doc.
