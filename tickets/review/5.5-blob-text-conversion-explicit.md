# What changed

**`BLOB_TYPE.parse`** (`types/builtin-types.ts`): removed the hex-sniff branch
(even-length, all-hex-chars → decode as hex). A string now always becomes its
literal UTF-8 bytes via `TextEncoder`. This is reached by `cast(x as blob)`,
`blob(x)`, `validateAndParse` on INSERT/UPDATE into a BLOB column, and
`alter table … alter column … set data type blob` backfill — all four now
agree.

**`blob(value)`** (`func/builtins/conversion.ts`, `BLOB_FUNC`): new, mirrors
`TEXT_FUNC`/`INTEGER_FUNC` exactly — `BLOB_TYPE.parse`, null-in/null-out,
failure wrapped as `QuereusError(StatusCode.MISMATCH)`. `docs/types.md` had
already listed it in the five-function conversion list; it just didn't exist
until now.

**`hex(X)`** (`func/builtins/string.ts`): uppercase hex spelling of X's bytes,
no separator. A non-blob argument converts to bytes through `BLOB_TYPE.parse`
first — same path `cast(X as blob)` takes. That means `hex(json_col)` throws
(wrapped as `QuereusError` MISMATCH) rather than returning NULL, matching
`blob()`'s own behavior on a JSON object/array; documented as a deliberate
choice in the code comment, not an oversight.

**`unhex(X)`** (`func/builtins/string.ts`): inverse — hex string to bytes.
Returns `NULL` (not an error) for anything that isn't a whole number of
hex-digit pairs, matching SQLite. One-argument form only (no "ignore these
characters" second argument). `unhex('')` is the empty blob, not null.

Both registered in `func/builtins/index.ts` (`BLOB_FUNC` under Type Conversion
Functions, `hexFunc`/`unhexFunc` under String Functions).

# Why

A prior ticket (`canonical-value-to-text`) made `cast(x as text)` on a blob
render its bytes as UTF-8 text (`x'6162'` → `'ab'`) instead of hex digits.
That exposed a latent bug in the old `BLOB_TYPE.parse`: it guessed that any
even-length, all-hex-character string was meant as hex. `'ab'` is even length
and both characters are valid hex digits, so the old parse re-decoded it as
hex bytes (`0xab`) instead of taking it literally — `cast(cast(x'6162' as
text) as blob)` went in as two bytes and came back as one different byte.
The guess was already inconsistent on its own terms (`'abc'` vs `'abcd'` took
different branches purely on string length), and it silently ate the only
way to ask for a hex round-trip on purpose. Now text-to-binary is always
literal UTF-8 in both directions (lossy for non-UTF-8 bytes, which is honest
and tested), and hex is something you opt into with `hex()`/`unhex()`.

# Test coverage (what's proven, what isn't)

`test/logic/06.5.1-conversion-functions.sqllogic` covers: `blob()` literal
UTF-8 (including the "looks like hex" case), `blob(null)`, `typeof(blob(...))`;
`hex()` on a blob literal, uppercase-no-separator, non-blob argument path,
`hex(null)`, `hex(x'')` (empty-but-not-null); `unhex()` basic case,
case-insensitivity, odd-length → null, non-hex-char → null, `unhex(null)`,
`unhex('')` (empty blob, not null, asserted both ways), and a
`hex()`/`unhex()` round trip. It also adds a BLOB-column insert/read-back
case (`cast('abc' as blob)` and `cast('6162' as blob)` both stored and read
back correctly).

`test/logic/99.1-cast-syntax-extras.sqllogic` adds: the lossless round trip
`cast(cast(x'6162' as text) as blob) = x'6162'`; the **lossy** round trip for
non-UTF-8 bytes (`x'ff'` → text → back is `x'efbfbd'`, asserted as that value,
not as `= x'ff'` which would be wrong); and `cast('6162' as blob) =
x'36313632'` (the new answer — four UTF-8 bytes, not two hex-decoded bytes).
The pre-existing `cast('hello' as blob)` assertion at the top of that file
(odd-length string, already took the UTF-8 branch pre-change) is untouched
and still green — confirms nothing regressed for the always-was-UTF-8 case.

**Gaps a reviewer should know about:**
- `hex()`/`unhex()` are tested only through `06.5.1`; I did not add a
  logic test exercising `hex()` on a bigint/boolean argument (the ticket only
  required deciding + testing the JSON-object-throws choice, which is
  covered — `hex(x'')`, `hex('abc')`, `hex(null)` are covered, but e.g.
  `hex(42)` or `hex(true)` are not explicitly asserted, even though they go
  through the same well-tested `BLOB_TYPE.parse` path as `blob(42)`/`blob(true)`
  elsewhere in the suite).
- No test for `unhex()` on a non-string, non-null argument (e.g. `unhex(42)`)
  — implemented as `typeof value !== 'string' → null`, following the same
  null-safe pattern as `reverseFunc` elsewhere in `string.ts`, but not asserted
  in logic tests.
- Did not add a test for inserting through `alter table … alter column … set
  data type blob` backfill specifically (the ticket's "same for" case) —
  confirmed by code inspection that it reaches `BLOB_TYPE.parse` via the same
  `validateAndParse` path the new INSERT test exercises, and the existing
  `41.7.4-alter-column-retype-semantic-memory.sqllogic:310` retype test
  (`'abc'` → blob) still passes unchanged, but there's no *new* assertion
  targeting the backfill path with a hex-shaped source string specifically.

# Fallout fixed

`test/type-system.spec.ts` had a unit test (`BLOB_TYPE > should parse hex
strings to blobs`) asserting the exact old hex-sniff behavior
(`BLOB_TYPE.parse!('ff00')` → bytes `0xff 0x00`). Updated it to assert the new
literal-UTF-8 behavior instead — this was the only test in the whole suite
that depended on the old sniff (verified via `find_references`/`grep` across
`test/` for `as blob)` and `cast('<hex-looking-string>' as blob)` patterns
before making the change).
