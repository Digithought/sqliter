# Drop guard now follows column republication (star re-exposure)

`ALTER TABLE … DROP COLUMN` refused only when some body in the rule's reach spelled the
column's name. `create view v as select * from t` spells it nowhere, so a rule reading
`v.x` did not block the drop — after which the assertion arm broke every write to the
whole database. Fixed by consulting the same lineage `RENAME COLUMN` already computes.

## What was built

**`schema/column-republication.ts` (new).** `scanShiftedPublishers` +
`ColumnRenameCascadeTarget` moved here verbatim from `runtime/emit/column-rename-cascade.ts`
(the cascade imports them; its behavior is untouched — verified by a green run before any
guard changed). On top of the scan, `collectColumnRepublication(db, seed, columnName,
resolvers, resolveColumnInSource)` — the read-only fixpoint: breadth-first over
`probeOnClone: true` with the sentinel `PROBE_COLUMN_NAME` (now exported from
`rename/column-rename.ts`), seed first. It returns `{ targets, brokenListed }`, not the
bare targets array the source ticket sketched, because the explicit-column-list arm needs
the second set from the same scan: `brokenListed` holds views/MVs with an explicit column
list whose body stars over the column — never targets (a pinned list publishes no shifted
name) but broken OUTRIGHT by the drop (the star's arity changes).

**Both guard families consult it.** `columnProbe` (`schema/expression-dependents.ts`) and
`assertNoAssertionNamesColumn` (`runtime/emit/drop-column-guards.ts`) now probe each
reached body against every target. Sweep order is deliberate: **targets outer (base table
first), bodies inner** — so every match the base sweep finds lands on the body it always
did and no existing message spelling moves (a naive bodies-outer order would have moved
§26/§29's "reaches it through view" matches to a direct-spelling message). After the
target sweep, a reach that *names* any `brokenListed` object refuses with a distinct
message ("…whose explicit column list would no longer match its body once '*' expands
without the column — dropping the column breaks it outright").

**Seeded/unseeded split kept, narrowed to the base target.** The seeded probe (implicit
owning-table binding, `new.`/`old.` namespace) applies only to (own root body × base
target). Republication targets are probed unseeded even at the root: no CHECK ever
implicitly binds a *view*, so a reference to a view target can only sit inside a subquery
FROM, which the unseeded walk owns.

**`buildColumnSourceResolver` sees views.** Signature changed `SchemaManager → Database`
(all four call sites had one). A view answers from its explicit column list first, else
`bodyPublishesColumnNamed` over its body, recursing through the resolver itself with a
per-question in-flight set as cycle insurance. Unqualified names in a view body resolve
LIVE down the view's home schema path (`db._homeSchemaPath`) — live is this function's
documented contract.

**Materialized-view decision (made explicitly, encoded in the module doc):** an MV is
treated exactly like a view — staleness is not consulted (`isMvExcluded: () => false`).
This is deliberately conservative: the MV's backing keeps the column, so the rule would
have kept working against frozen contents; the engine refuses anyway — one rule for both
object kinds, matching §27's pinned named-projection refusal and `DROP TABLE`'s
direction. The docs state the conservatism honestly (sql-ddl § 2.6.1, sql-alter § DROP
COLUMN).

## Deviations from the source ticket

- **API shape:** `collectColumnRepublication` returning `{ targets, brokenListed }`
  instead of `columnRepublicationTargets` returning an array — one scan feeds both arms.
- **No cross-call memo in the resolver.** The ticket suggested memoizing the per-view
  answer per resolver instance. Rejected: the rename propagation shares ONE instance
  across its pre-flight and live cascade rounds, and rounds rewrite view bodies in place —
  a memoized "does v expose x?" from before a round is stale after it. A per-question
  in-flight set bounds recursion instead; the NOTE at the site records the tripwire (add a
  catalog-generation-counter memo if constraint-build ever profiles hot).
- **§29 did not "flip".** The false refusal the source ticket demonstrated (unqualified
  `v` binding a view over ANOTHER table) was described in §29's comment but never pinned
  as an executable expectation — §29's executable statements (qualified spelling) still
  refuse with the identical message. The flip is now pinned as a new §36 case; §29 gained
  the unqualified own-table-view spelling (still refused — correctly now, via the
  republication target — same message) and a rewritten comment.

## Behavior changes a reviewer should probe

Beyond the four the ticket ordered (star assertion leak, star CHECK leak, chain leak,
§29-direction false refusal — all fixed and pinned in 41.10.2 §31–§36):

- **Self-qualifier strip (plan-build time).** `constraint-builder.ts` shares the
  resolver, so a qualified self-ref inside a CHECK subquery whose FROM is a view exposing
  the same name is no longer stripped: previously it was silently rewritten to a bare
  name the view then captured (constraint compared the view's column to itself — silent
  wrong answer); now the ref stays qualified and fails loudly at write-plan time
  (`t.col isn't a column`), the strip's documented conservative policy for
  uncapturable-name frames. Pinned in 40.2-check-extras (new strip-under-view section).
  This converts a silent misbinding into a loud error for pre-existing schemas of that
  shape — judged correct, but it is user-visible.
- **RENAME COLUMN scope-awareness widened the same way** (shared resolver, parity is the
  design): an unqualified inner ref binding a view-over-another-table exposing the old
  name is no longer false-captured by the rename. NOT separately pinned in 41.3 — the
  existing rename suite is green, but a reviewer may want a 41.3 case for this mirror.
- **Rename cascade pre-flight collision check** (`bodyPublishesColumnNamed`) now sees
  publications arriving through a star over a VIEW, so strictly more two-same-name
  collisions are refused up front. No existing test moved; unpinned.

## Known gaps (honest list)

- `bodyPublishesColumnNamed` still cannot see through an aliased subquery source, a
  function source, or a CTE (no askable column set) — a star over one of those hides a
  publication from BOTH the rename cascade and the drop fixpoint. Pre-existing, shared,
  documented on the predicate; parity between the two verbs is preserved, which is the
  invariant that matters.
- The fixpoint runs once per guard entry — three times per drop (CHECK arm, DEFAULT /
  generated arm, assertion arm), each on its own pre-mutation snapshot (identical
  answers). Cost NOTEs at the sites; DDL-rare.
- A star-reference match at the rule's own ROOT body reports the direct spelling
  (`it is referenced by assertion 'a'`) without naming the view the reference travels
  through — the reach path is empty because the match is on the rule's own text, which
  DOES spell the column, so the message is actionable. Naming the target view there would
  be a phrasing improvement, not a correctness fix.
