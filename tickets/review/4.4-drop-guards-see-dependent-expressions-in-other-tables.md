# What landed

A CHECK constraint, a column `DEFAULT`, and a `GENERATED ALWAYS AS` body may all contain
a subquery, so any of them can legitimately read a column or a table belonging to some
*other* table, in some other schema. `ALTER TABLE … RENAME` has always known this — it
rewrites those expressions across every table in every schema — while the DROP guards
scanned only the altered table's own constraints and columns. That gap let both of these
succeed and leave the referencing table impossible to write to:

```sql
create table T (id integer primary key, v integer);
create table X (id integer primary key, n integer, check (n < (select max(v) from T)));

alter table T drop column v;   -- was accepted; X then failed with "Column not found: v"
drop table T;                  -- was accepted; X then failed with "Table 'T' not found…"
```

Both now refuse, `StatusCode.CONSTRAINT`, with a message naming the dropped object, the
referencing table (schema-qualified when it lives elsewhere), and the constraint (by name,
or by expression when unnamed).

## Shape

One new catalog query, `packages/quereus/src/schema/expression-dependents.ts`, that every
guard calls instead of hand-rolling a scan:

- `findColumnExpressionDependent(db, tableSchema, columnName, arm)` — `arm` is `'check'`
  or `'columnExpression'` (DEFAULT + generated).
- `findTableExpressionDependent(db, schemaName, objectName)`.

Both walk `_getAllSchemas()`, build one `snapshotObjectRefResolvers(db)` snapshot and take
`forHomeSchema(table.schemaName)` per scanned table, and reuse the existing scope-aware
probes — so "the drop refuses exactly what a rename would have rewritten" holds by sharing
the walk rather than by comment. The own-table / other-table probe split mirrors
`rewriteTableForColumnRename`'s `isRenamedTable` branch: seeded
(`columnReferencedInCheckExpression`) on the probed table, unseeded
(`columnReferencedInAst`) everywhere else.

Callers:

| Verb | Guard | Called from |
| --- | --- | --- |
| `DROP COLUMN` | `assertNoColumnExpressionNamesColumn`, `assertNoCheckConstraintNamesColumn` | `runDropColumn` (`alter-table.ts` ~1180) |
| `DROP TABLE` / `VIEW` / `MATERIALIZED VIEW` | `assertNoExpressionDependsOn` (`expression-drop-guard.ts`) | `emitDropTable`, `emitDropView`, `emitDropMaterializedView` |

Emitters only — never `SchemaManager.dropTable`, which also drives rollback, catalog
import and the declarative differ's drop/recreate.

### Deviations from the ticket, deliberate

- The finders return **the first** dependent (`ExpressionDependent | undefined`), not an
  array. Every caller is a guard that throws on the first hit, so returning one keeps the
  walk off the remaining schemas. Names are singular accordingly.
- `assertNoColumnDefaultNamesColumn` was **renamed** to
  `assertNoColumnExpressionNamesColumn`, because it now also reports a *generated* body on
  another table. Single call site; no other references existed.
- **`DROP VIEW` / `DROP MATERIALIZED VIEW` do get the guard**, on the ticket's own
  argument: a CHECK subquery can read a view, and losing the view breaks the referencing
  table exactly as losing a table would. The asymmetry the engine documents is on the other
  side and is unchanged — dropping a *table* out from under a plain view is still allowed
  and still breaks the view (pinned by §5 of the new sqllogic file).

## Use cases to exercise

Refusals (all `StatusCode.CONSTRAINT`, nothing applied — the object survives and the
referencing table stays writable):

- `alter table T drop column v` when another table's CHECK / DEFAULT / generated body reads
  `T.v` through a subquery. Message names the referencing table.
- `drop table T` / `drop view V` / `drop materialized view MV` under the same three.
- `drop table if exists T` — `IF EXISTS` governs absence, not dependency.
- Cross-schema: a CHECK in `temp` naming `main.T` explicitly is caught; message says
  `on table 'temp.X'`.

Must still be **allowed** (these are the false-refusal shapes):

- Another table simply has a like-named column and constrains its own — bare (`check (v > 0)`),
  self-qualified (`check (X.v > 0)`), or via a subquery over a third table
  (`check ((select min(v) from U) >= 0)`).
- Another table's `default (new.v + 1)` naming *its own* row image.
- A bare name in `temp` that resolves to `temp.T`, when `main.T` is what is being dropped.
- A CTE or FROM alias that merely shadows the dropped name
  (`(with T as (select 1 as v) select max(v) from T)`, `from U as T`).
- A table's own self-referencing CHECK never blocks its own `DROP TABLE` (it goes with the
  table). The COLUMN verb is the opposite and keeps the altered table in scope.
- Dropping the dropped column's own DEFAULT; every own-table generated body (still refused
  earlier, by `generatedColumnDependencies`, with its own message).

Escape hatches: `alter table <referencing> drop constraint <name>`, or
`alter table <referencing> alter column <c> drop default`. An **unnamed table-level** CHECK
has no name for `DROP CONSTRAINT` to resolve, so the referencing table must be rebuilt —
accepted cost, same as the pre-existing CHECK guard, and the message quotes the expression.

## Honest gaps — start here

1. **Four pre-existing tests changed because the new guard refuses what they relied on.**
   Worth a look that each rewrite kept the coverage it was carrying:
   - `13.8-insert-with-clause-visibility.sqllogic`, `13.9.1-schema-authored-schema-path-isolation.sqllogic`
     — cleanup reordering only (`drop table q9` / `drop table temp.sp_acbf` moved ahead of
     their CHECK/DEFAULT target). No assertion changed.
   - `51.8-maintained-table-declared-constraints.sqllogic` + `maintained-table-declared-constraints.spec.ts`
     — the "subquery-CHECK target drop poisons the validator" case is now a refusal case, and
     the "self-heal on dependency re-create" **CHECK arm was deleted**: the drop half is
     refused, and a maintained table cannot be declared against an absent CHECK target
     either (`create table … check ((select … from hquota …)) maintained as …` fails at build
     time), so no SQL sequence reaches the `table_added` rebuild through a CHECK. The FK-parent
     arm of that rebuild is untouched and still covered. **That is a real coverage loss** —
     the poisoned-validator fallback in `derived-row-validator.ts` is now defensive-only,
     exercised by no test. If the reviewer wants it kept live, it needs a unit-level test
     that drives `SchemaManager.dropTable` directly rather than through the emitter.
2. **Assertion bodies are still single-schema.** `assertNoAssertionNamesColumn` and
   `assertNoAssertionDependsOn` were NOT widened here — that is
   `assertion-guards-follow-view-chains-and-schemas`. So a cross-schema *assertion* still
   slips through while a cross-schema *CHECK* no longer does. Deliberate scope split, but
   the two guards now disagree about how wide "any schema" is; worth confirming that reads
   as intentional rather than as an oversight.
3. **Partial-index predicates have no arm**, on the ticket's reasoning that the parser
   rejects a subquery there. Verified only by reading the ticket's claim and the existing
   comment in `schema/catalog-persistability.ts` — not re-verified by running a
   `create index … where (select …)` in this session.
4. **Two catalog walks per `DROP COLUMN`**, since the CHECK arm and the column-expression
   arm are separate guards with separate messages and ordering. Accepted per the ticket;
   recorded as a `NOTE:` in `expression-dependents.ts`'s header rather than optimised.
5. **Ordering within a walk is `_getAllSchemas()` × `getAllTables()` order** once the probed
   table is past. With two referencing tables, which one the message names is therefore
   insertion-ordered, not deterministic by any user-visible rule. No test depends on it, but
   nothing pins it either.
6. **No test for a `DROP COLUMN` refused by a dependent on a table in a schema that the
   session search path does not include** — only `main`/`temp` pairs. The resolver logic is
   shared with the rename (which does have that coverage in `41.3` §48–§49), but this
   ticket's arms did not re-pin it.
