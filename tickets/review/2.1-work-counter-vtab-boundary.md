# What landed

`WorkCounterSnapshot` gained a `tables` block and three new totals:

```ts
tables: Record<string, {          // key: lowercased `<schema>.<table>`, keys sorted
	queryCalls: number;           // query() calls the engine issued
	rowsScanned: number;          // rows the engine pulled out of them
	updateCalls: number;          // update() calls — insert, update, delete alike
}>;
totals: { ..., queryCalls, rowsScanned, updateCalls };
```

Counted at engine-owned call sites, not inside modules, so the numbers work for the
memory module, the store module, the isolation wrapper and any third-party module with
no interface change:

- `runtime/emit/scan.ts` — one `queryCalls` per `vtabInstance.query()` call, one
  `rowsScanned` per row pulled from it. One door for `SeqScan`, `IndexScan`, `IndexSeek`.
- `runtime/emit/dml-executor.ts` — one `updateCalls` per `vtab.update()`, at all four
  sites (insert, the UPSERT `do update` arm, update, delete) via a `countUpdateCall`
  helper in the emitter closure.

`TableWorkCounters` is exported from the package root alongside `WorkCounterSnapshot`.

## The distinction a reviewer should hold onto

These measure the **engine-to-module** boundary, not the **module-to-storage** boundary.
A module that swaps 1000 single-key reads for one batched multi-key read moves neither
number — the engine issued the same one `query()` either way. That deeper layer is the
counting key-value store double in `@quereus/store/testing` (the store-counting-double
ticket). Two layers, two instruments. Documented in `docs/runtime.md` and `docs/usage.md`
so nobody expects the engine counters to catch a batching regression inside a module.

# Use cases for testing and validation

Turn metrics on (`db.setOption('runtime_metrics', true)`), prepare, **drain fully**,
then read `stmt.getWorkCounters().tables`. Observed values on a 5-row table `t`:

| Statement | `main.t` |
| --- | --- |
| `select a, b from t` | `{queryCalls: 1, rowsScanned: 5, updateCalls: 0}` |
| `select a, b from t where a = 3` (PK seek) | `{1, 1, 0}` |
| `select a from t where b = 10` (no index) | `{1, 5, 0}` — filter's `out` is 2 |
| `select a from t limit 2` | `{1, 3, 0}` — partial, on purpose |
| self-join on `t` | `{2, 10, 0}` — two sites, ONE entry |
| correlated subquery with `limit 1` (undecorrelated) | `queryCalls: 6` = 1 + 5 |
| same shape without `limit 1` (decorrelated) | `queryCalls: 2` — constant |
| `insert into u values (…), (…), (…)` | `main.u = {0, 0, 3}` |
| `update t set b = b + 0` | `{1, 5, 5}` |
| `delete from u where x = 1` | `{1, 1, 1}` |
| `insert … on conflict do update` | `updateCalls: 2` (attempt + arm) |

The decorrelated-vs-not pair is the money shot: the row count barely moves (10 vs 10)
while the call count goes 2 → 6. That is the N+1 signal this block exists for.

## Where to attack it

- **The counting-module cross-check** (`work-counter-tables.spec.ts`, last describe):
  a cross join over a module that tallies its own `query()`/`update()` calls, asserting
  the engine's count equals the module's own — and separately that the *connect* count
  (2) differs from the *call* count (4), so the assertion is not accidentally counting
  connects. This is the test that would catch counting at the wrong seam.
- **Renamed tables.** The scan resolves `runtimeCtx.tableNameRemap` on **every**
  invocation now (previously only on the connect path), and keys the counter by the
  effective post-remap name. **Not directly tested** — see gaps below.
- **Zero cost when off.** `runtimeCtx.workCounters` is undefined by default; the scan
  resolves one local per invocation and does `if (tableCounters) …` per row. The rename
  lookup key is now pre-built in the emitter closure (`emittedQualifiedNameLower`), so
  the run path allocates no string where it previously built one per connect.

# Known gaps — read these before trusting the diff

- **The before/after benchmark comparison was NOT run.** The ticket asked for it and I
  ran out of budget. The per-row site is the hottest loop in the engine, so this is the
  one measurement that actually matters. Carried as its own implement ticket:
  `work-counter-scan-overhead-measurement`. Treat the "zero cost when off" claim above
  as *designed for*, not *measured*.
- **The rename path has no test.** Keying by the effective name is asserted only by
  reading the code. Reaching it needs a deferred constraint evaluating a plan frozen
  before an `ALTER TABLE … RENAME TO` in the same transaction — the same setup
  `deferred-constraint-queue.ts` exercises. Worth building; I did not.
- **`ANALYZE`'s own sampling scan is uncounted** (`planner/stats/analyze.ts:48` calls
  `vtab.query` outside the instruction pipeline, with no `RuntimeContext`). Documented
  as deliberate in `docs/runtime.md`; if a benchmark ever wants ANALYZE's cost, that is
  a third call site to instrument.
- **Partial-drain counts are asserted only loosely** (`limit 2` gives `rowsScanned` ≥ 2
  and < 5 — it is actually 3). Pinning 3 exactly would test the scheduler's pull order
  rather than the counter, so it is left as a range. Same reasoning the core ticket
  used for partial snapshots.
- **`docs/runtime.md` is 5 words from its 12000-word cap** — `check-docs` passes with a
  near-cap notice, but the next section to land there fails the build. It was already
  392 from the cap at HEAD; this change made it acute. Filed as
  `backlog/debt-docs-split-runtime`. I trimmed my own section to fit rather than
  force-ratcheting.

## Refactor included (flag if you disagree)

`nlj-inner-connection-reuse.spec.ts` into `test/runtime/counting-vtab.ts` so the new
spec could cross-check against it rather than duplicate ~120 lines. Its `update()` now
records the call and echoes the written row back (previously `{status: 'ok'}` with no
row) — no NLJ test does DML against the counting module, and that spec still passes
unchanged (6 passing).
