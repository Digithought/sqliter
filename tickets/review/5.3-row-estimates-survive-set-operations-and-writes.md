# What landed

`debt-join-rows-from-physical-children` had moved the single-source operators and the
join family onto `physicalSourceRows(childPhysical, source)`. This ticket filled the
remaining holes, so a row estimate now survives set operations, async gathers, common
table expressions, remote-query boundaries and the whole write pipeline.

## Composition rules implemented

Three new exports in `planner/util/row-estimates.ts`, each a pure function of the
children's counts, each called TWICE — once from the node's logical `estimatedRows`
getter and once from its `computePhysical` over the physical child counts — so the two
views cannot drift (the discipline `aggregateRowsFrom` already established):

| helper | rule |
|---|---|
| `setOperationRowsFrom(op, l, r)` | `unionAll`/`union` → sum; `intersect` → min; `except` → left |
| `gatherRowsFrom(kind, branches)` | `unionAll` → sum; `zipByKey` → max; `crossProduct` → product |
| `clampRowEstimate(n)` | floor to a whole row, saturate at `Number.MAX_SAFE_INTEGER`, never `Infinity`/`NaN`/negative |

Pass-throughs (source count unchanged): `CTENode`, `CTEReferenceNode`, `RemoteQueryNode`,
`InsertNode`, `UpdateNode`, `DeleteNode`, `ConstraintCheckNode`, `DmlExecutorNode`,
`ReturningNode`. `DeleteNode` and `ReturningNode` already looked correct but read the
**logical** source getter; both now read the physical child.

Two nodes deliberately do not follow the source: `SinkNode` reports 1 (the statement's
changes-count row) and `RecursiveCTENode` reports `undefined`.

## Scope added beyond the ticket — read this first

The ticket's node list was **incomplete for its own goal**. With only the listed nodes
patched, an `insert … select` still reported `undefined` at the executor: the write
pipeline is `Insert → ConstraintCheck → UpdateExecutor → (Returning) → Sink`, and
`ConstraintCheckNode` — not in the ticket — stamps nothing, so the relay died one node
short. It now relays (1:1: it validates each row and passes it through, or throws).

`SinkNode` was added for consistency: it already reported 1 from its logical getter but
stamped no physical value, so the documented "statement boundary" claim was only half
true. It now stamps 1 in both views.

Both additions are ~5 lines each and covered by tests. If the reviewer thinks either is
out of scope, they are cleanly separable — but dropping `ConstraintCheckNode` re-opens
the ticket's own headline case.

## Judgement calls a reviewer should weigh

- **`except` with an unknown right branch reports the left count, not `undefined`.**
  The ticket states two rules that collide: "any unknown input ⇒ unknown output" and
  "`except` — the left branch's count". The formula does not read the right branch at
  all, so there is no unknown *input* to propagate, and blanking would discard a sound
  bound. Documented at the helper and locked by a named test. If the reviewer prefers
  strict propagation it is a one-line change plus one test.
- **`union` reports the sum**, per the ticket — the honest upper bound, since the dedup
  factor is unknown. The `Distinct` above a `union` is what narrows the claim.
- **The write family's estimate is an upper bound, not exact.** `DmlExecutorNode` yields
  nothing for a row it did not write (`insert or ignore` onto an existing key,
  `on conflict do nothing`, an update whose row vanished). The skip rate is a property of
  the data, not of the plan, so no discount is applied; the deviation is documented at the
  helper, on the node, and in `docs/optimizer-costing.md`. Verified by reading
  `runtime/emit/dml-executor.ts` (`if (rowToYield !== undefined) yield rowToYield`), not
  by an executed test — **a reviewer wanting certainty should run an `insert or ignore`
  that skips rows and compare the estimate to the actual count.**
- **`crossProduct` saturates at every step, not just at the end.** An overflowed
  `Infinity` intermediate followed by a provably-empty branch would otherwise fold to
  `NaN`. Tested.
- **Emitted vs processed** is settled as **rows emitted** and documented on
  `row-estimates.ts` under "Data-modifying nodes". For this family the two coincide
  (modulo the executor skip above); they part only at `SinkNode`.

## Testing / validation

New: `packages/quereus/test/optimizer/set-op-row-estimates.spec.ts` — 35 tests, all
passing. Run just this file from the repo root:

```
node --import ./packages/quereus/register.mjs node_modules/mocha/bin/mocha.js "packages/quereus/test/optimizer/set-op-row-estimates.spec.ts"
```

Unit coverage: `clampRowEstimate` (floor, keep a genuine 0, saturate `Infinity`, saturate
`NaN`, never negative); `setOperationRowsFrom` (each operator, `except` with a larger
right side, `undefined` propagation per operator, unknown ≠ zero, genuine-0 branches);
`gatherRowsFrom` (each combinator, `unionAll` agreeing with `setOperationRowsFrom`,
overflow saturation, empty-branch-after-overflow, unknown propagation).

End-to-end coverage against a real `Database` (`big` = 100 analyzed rows, `small` = 10,
`unmeasured` = never `ANALYZE`d):

- `union all` reports 110 at the `SetOperation` node **and** at a `Sort` above it
- `intersect` reports 10; `except` reports the left branch either way round
- a never-analyzed scan is asserted `undefined` first (anchors the next case), then a
  `union all` with that branch reports `undefined` — not 100, not 0
- a high-latency `union all` folded into an `AsyncGather` (via a `MemoryTableModule`
  subclass declaring `expectedLatencyMs = 25`, the `parallel-async-gather.spec.ts`
  pattern) keeps its count in the physical view
- a CTE relays its body count to its reference; a twice-referenced CTE reports the body
  count at **both** references (shared `CTENode` identity intact)
- a recursive CTE still reports `undefined`
- `insert … select` relays 100 at `Insert`, `ConstraintCheck` and `UpdateExecutor`; the
  `Sink` above reports 1; `delete … returning` relays 100 at `Delete` and `Returning`;
  `update … where` relays a number

Full suite: `yarn build`, `yarn lint`, `yarn typecheck`, `yarn test` all clean —
10348 + 755 + … passing, 0 failing. **No golden plan file changed** (`git status` shows no
`.plan.json` modified), so the anticipated plan churn did not materialise on the existing
goldens.

## Known gaps — treat the tests as a floor

- **Plan churn is untested beyond the existing goldens.** Nodes above a set operation now
  get a real count where they had a default, so sort strategy, cache thresholds and
  enclosing join costs *can* move. No golden changed and no test failed, but no test
  deliberately exercises "a cache node above a `union all` now sizes differently".
  A reviewer looking for behaviour change should probe there.
- **`RemoteQueryNode`'s relay is untested end-to-end.** No in-tree module produces one in
  a test; the change is a two-line pass-through mirroring the others, verified only by
  reading. Same for the `zipByKey` and `crossProduct` gather arms at the *plan* level —
  those arms are unit-tested through `gatherRowsFrom`, but only `unionAll` is exercised
  through a real optimized plan.
- **`except all` is not covered** — `SetOperationNode.op` has no such member in this
  codebase (`'union' | 'unionAll' | 'intersect' | 'except'`), so the ticket's mention of
  it has no implementation site.
- **Membership-flag set operations** (`hasMembershipColumns`) get the stamp in that branch
  too, but no test builds a flagged set operation and checks its count — the assertion is
  the shared `physicalRows()` call site, not a test.
- **`SetOperationNode.estimatedRows` is a NEW logical getter.** Nothing read it before, so
  any consumer that walks logical estimates now sees numbers where it saw `undefined`.
  Nothing in the suite regressed, but that is a behaviour surface worth a second look.
