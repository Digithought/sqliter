# Two-phase schema apply: row-validating DDL runs after the batch's rows

## What was wrong, in one line

A receiving device applied **all** of a sync batch's schema changes before **any** of its
row changes. That order is right for a change that loosens or extends a table (the rows
need the new shape to land in) and wrong for one that tightens it (the tightening is only
legal against rows still queued behind it), so an ordinary "fill the column, then forbid
empties" sequence failed its first sync round with:

```
apply-to-store failed for 1 change(s): main.orders (alter_column): column note contains NULL values
```

## What now happens

`applyToStore` splits each batch's schema changes into two phases:

```
non-validating DDL  →  row writes  →  row-validating DDL  →  engine ingestion seam
```

Both phases run through the same accounting closure, so a validating alteration's failure
lands in `ApplyToStoreResult.errors` exactly as a pre-data one always did — an
unsatisfiable tightening still aborts the batch and still retries.

**Row-validating** (moved after the data) — confirmed empirically, each throws against
violating rows:

| migration | observed failure |
|---|---|
| `alter column … set not null` | `column note contains NULL values` |
| `add constraint` (unique / check / FK) | `UNIQUE constraint failed: orders (note)` |
| **unique** `create index` | `createIndex failed for index 'idx_note' on table 'orders': UNIQUE constraint failed: orders (note)` |

The unique-index arm was the ticket's open question; it was probed directly and does fail
the same way, so it is included. Non-unique index creation inspects nothing and stays in
the early phase.

**Deliberately NOT moved**, both documented at the classifier and in `docs/sync-schema.md`:
`alter primary key` (the key definition in force decides how the batch's rows are
addressed, so deferring it would file them under the old key) and `alter column … set data
type` (a type change rewrites stored values, so rows applied first would be stored under
the old type and converted).

## The one place this deviates from the ticket's design — please look here first

The ticket proposed a plain two-way partition of the whole list and argued "no batch that
succeeds today can fail after the change." **That argument has a hole**, and the
implementation closes it rather than shipping the plain partition:

A batch is a whole resolved `ChangeSet[]` — *many* source transactions, not one — so it
can legitimately carry `add constraint u1` from Monday and `drop constraint u1` from
Tuesday. Under a plain partition the (validating) add defers and the drop runs first,
against a constraint that does not exist yet; `decideAlterTable`'s `dropConstraint` arm
converges silently, and then the deferred add installs a constraint the origin no longer
has. Silent schema divergence, newly introduced by the fix.

So `partitionSchemaChanges` defers a validating change only when **every later change on
the same object in the batch also defers**. Per-object DDL order is therefore never
rearranged; an object with a later pinned change simply keeps today's behaviour (the
pre-existing spurious-error case), rather than acquiring a new divergence.

One exception: a trailing **`drop_table`** does not pin. The table is discarded either
way, so nothing earlier on it can be reordered into a wrong end state, and letting it pin
would hold the tightening in the pre-data phase where it aborts a batch whose own last
word is "this table is gone." Deferred instead, the tightening meets an absent table and
converges through `decideAlterTable`'s absent-table warning — which is the outcome the
ticket asked to confirm.

**This pinning rule is the part most worth an adversarial read.** It is a judgment call
layered on the ticket's design, and it trades away the fix for one shape (a tightening
followed by another alteration of the same table in one batch) to protect correctness for
another.

## Use cases to exercise

Run: `yarn workspace @quereus/sync test` (752 passing). The new block is
`alter table replication › a tightening alteration applies after the batch's rows` in
`packages/quereus-sync/test/sync/schema-alter-replication.spec.ts` — two real engines,
one relay each, via `makePeer` / `relayAll`.

- **Headline** — both peers hold a row with a NULL `note`; the origin fills it and runs
  `set not null` in the same relay; the relay succeeds on the **first** round and both
  peers converge.
- **Negative** — the receiver holds a second NULL row the batch never fixes; the relay
  must still throw. Proves the guard is not merely disabled.
- **Ordering around the data** — `add column sku`, then an update filling `sku` on a row
  the receiver already holds, then `set not null sku`, all in one batch: the add must land
  before the update and the tightening after it.
- **`add constraint`** and **unique `create index`** each satisfied by the same batch's
  rows, applying on the first round.
- **`add constraint u1` then `drop constraint u1` in one batch** — the constraint must end
  up gone. This is the pinning-rule guard.
- **Tightening plus `drop table` in one batch** — converges (table dropped) instead of
  failing.

## Honest gaps

- **Test sensitivity was measured, not assumed.** With the classifier stubbed to return
  `false`, 5 of the 7 new cases fail with the ticket's exact error. The remaining two are
  guard tests that must pass both ways; each was verified to bite against the specific
  regression it guards — disabling the pinning rule fails the add/drop-constraint case,
  and disabling the `drop_table` exception fails the drop case. So every branch of the
  classifier is load-bearing under test. Nothing here is a vacuous assertion.
- **`add constraint` coverage is the `unique` form only.** The classifier returns true for
  every `addConstraint` arm — `check` and foreign-key forms included — but only `unique`
  is exercised end to end. The check/FK forms are asserted by reading the code, not by a
  test.
- **Index migrations key by index name, not owner table.** `migrationOrderKey` uses
  `change.table`, which for an index migration holds the *index* name (the wire format's
  own convention). A create/drop pair for one index therefore keys together correctly, but
  a unique index create followed in the same batch by an alteration of its **owner** (e.g.
  dropping the indexed column) is not held back by that alteration and the two can be
  reordered. Recorded as a `NOTE:` on `partitionSchemaChanges` with the fix (resolve the
  owner from the parsed DDL) — not filed as a ticket, since it needs both statements in
  one batch touching the same column.
- **`alter primary key` and `set data type` keep their pre-data position**, so their own
  tightening failure modes (duplicate values under the new key; a narrowing conversion)
  still cost a spurious error and a retry. That is the ticket's deliberate scope boundary,
  now stated in the code and the docs rather than left implicit.
- **Full interleaving was not attempted**, per the ticket. Two phases cover the cases that
  occur; replaying the origin's history step by step would mean unpicking `buildRowOp`'s
  batch-wide collapse and the single seam call.
- **`decideAlterTable` was refactored** to share `parseMigrationDDL` with the classifier
  (one parse helper, each caller deciding what a failure means for it). Behaviour is
  unchanged — same `console.error` on a parse failure, same `execute` on a non-`ALTER`
  statement — but it is a touched code path worth a glance.
