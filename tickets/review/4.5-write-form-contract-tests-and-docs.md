# Pin the declared-form contract: what landed

The prereq (`4-generated-and-default-exprs-see-unconverted-row-on-insert`, landed in
commits `af80df49a`/`3499dccd5`) made INSERT evaluate DEFAULT and GENERATED expressions
against the *converted* row, so all write paths agree. This ticket pinned that agreement
in a test and wrote the rule down. No engine source changed — this is test + docs only.

## The rule being pinned

Every expression the engine evaluates against a row being written sees that row in its
columns' **declared form** — the values that will actually be stored — never the form the
statement spelled. That covers:

- CHECK, both immediate and deferred (subquery-bearing),
- a column `DEFAULT`, including one reading a sibling through `new.<column>`,
- a `GENERATED ALWAYS AS` body,

at all four write sites: `INSERT`, `UPDATE`, `ON CONFLICT … DO UPDATE`, and the
`ALTER TABLE … ADD COLUMN` backfill.

The witness is `datetime`, where the two forms differ visibly:
`'2099-01-01T00:00:00.000Z'` is accepted, canonicalized through UTC, and **stored** as
`'2099-01-01T00:00:00'`. Anything still seeing the trailing `Z` is reading the written
form and is wrong.

### The new test file, section by section

`15.1.3-declared-form-write-contract.sqllogic` — 11 sections, mundane → exotic:

1. **Baseline** — what the declared form of a `datetime` actually is. Every other
   expectation in the file depends on this one value.
2. **Immediate CHECK** — positive (a CHECK written against the declared spelling admits a
   row the INSERT spelled differently), plus an UPDATE that must be rejected (the CHECK is
   not vacuous), plus a **control**: a CHECK written against the *written* form matches
   nothing. That control is the sharp end — if the CHECK read raw statement text it would
   pass.
3. **Deferred CHECK** — the same positive/control pair, plus the shape that motivated the
   whole thing: a subquery comparing `new.<column>` against a value already stored in
   another table (already in declared form). Unconverted, the two would never compare
   equal and a valid row would be rejected. This is GH #25.
4. **DEFAULT reading `new.<column>`** — lands in a `text` column so what it read is visible
   verbatim; plus a written-form literal DEFAULT feeding a generated column.
5. **GENERATED** — same, through a generated column.
6. **agreement: INSERT vs UPDATE** — one value written two ways must yield one computed
   result. Asserted as `count(distinct g) = 1`, so the test names the *property*, not the
   value. **This is the assertion that caught the original bug.**
7. **agreement: unrelated column** — touching a sibling must not move a computed column.
8. **agreement: `add column … generated` backfill == later INSERT.**
9. **agreement: `add column … default (new.<col>)` backfill == later INSERT** — this is the
   parity claim `docs/sql-alter.md` § ADD COLUMN makes in prose ("a backfilled row and a
   row inserted afterwards under the same DEFAULT hold the same value"); it now has a
   guard, which is what the ticket asked for. `sql-alter.md`'s text was deliberately left
   alone.
10. **agreement: `on conflict … do update` recompute == plain UPDATE**, via both a
    written-form literal assignment and `excluded.<col>`.
11. **`OR REPLACE` NOT NULL DEFAULT substitution is not an exception** — the most
    out-of-band expression (fires during constraint checking, after the emitters' pass).

Deliberately **not** duplicated: JSON's version of the contract
(`15.1.1-json-check-coercion.sqllogic`), conversion-happens-once
(`06.9.1-json-coerce-once.sqllogic`), backfill mechanics
(`41.13-alter-add-column-generated-backfill.sqllogic`), and what storage receives
(`test/dml-write-representation.spec.ts`).

### A correction worth a close look

`15.1.1-json-check-coercion.sqllogic` carried a comment asserting the **opposite** of the
now-true contract: *"`new.<col>` in that DEFAULT must read the RAW value"*, under a heading
reading *"a substituted DEFAULT stays raw"*. Once the prereq landed, that is false — the
substitution reads the already-converted row like everything else.

Verified directly rather than inferred:

```sql
create table q1 (id integer primary key, j json null,
                 k text not null default (new.j), check (id > 0));
insert or replace into q1 values (1, '"Bob"', null);
select id, j, k from q1;   -- => k is "Bob" (parsed document), not "\"Bob\"" (raw text)
```

The comment was rewritten to separate the two things that path does: what it **reads** is
the declared form (the contract); what it **writes** is its own injected cell, whose
conversion must not re-apply `JSON_TYPE.parse` (not idempotent for a string scalar) —
which the identity-plus-conformance guard in `buildCellCoercion` handles. The test's
assertions are unchanged; only the explanation moved. **Reviewer: confirm the new wording
is right, since the old one read confidently and was wrong.**

### Docs

- **`docs/types.md` § Where coercion happens** — the gap the ticket identified was that the
  bullet list enumerated *where* each site converts but never said where DEFAULT/GENERATED
  evaluation sat in that order, which is exactly how the paths drifted. Three changes:
  (a) a new paragraph stating the contract positively up front, naming both guarding tests
  and back-linking to RT-001; (b) the INSERT bullet now describes the row-expansion
  projection as a **chain of stages** with conversion interleaved *into* it — supplied and
  literal-DEFAULT cells, then expression DEFAULTs, then generated columns in topological

## Known gaps — read these before signing off

1. **The release note is in a gitignored file and will not appear in the commit.**
   `docs/releasing.md` designates `.release-notes.pending.md` at the repo root as the place
   release notes live during a cycle; it is untracked by design (`.gitignore:23`) and
   `yarn gh-release` consumes and deletes it. So the note was written there, per the
   documented process — but the consequence is that it exists **only in this working tree**
   and no commit carries it. If the runner's commit is the durable artifact here, this note
   is one `git clean` from gone. That is a process question, not a code one: either accept
   it, or decide release notes need a tracked home. Not resolved unilaterally.
2. **The "4.4.1" attribution in the release note is unverified.** The ticket said the change
   ran "4.3.1→4.4.1" per GH #28; the repo is at **4.17.1**, so that pair is historical, not
   current. The note repeats 4.4.1 as the release where an immediate CHECK started seeing
   the declared form. That was **not** confirmed against git history or the tags — only
   carried across from the ticket. Worth five minutes with `git log v4.3.1..v4.4.1` before
   the note ships, or drop the version and say "an earlier release".
3. **Only DATETIME witnesses the non-JSON case.** `date`, `time` and `timespan` also rewrite
   values on the way in and have no contract coverage. Parked as a `NOTE:` tripwire in the
   new test file's header (the reasoning: fine while all write sites share
   `buildCellCoercion`, since one witness exercises the shared path; add a section if a type
   ever converts through its own route).
4. **Not run:** `yarn test:store` in full, `yarn test:full`, `yarn typecheck`,
   `yarn bench:gate`, and the strict-mode passes (`test:fork-strict`, `test:context-strict`,
   `test:repr-strict`). The new file was run under store mode individually and passes; the
   rest were skipped as out of proportion to a test-plus-docs change that touches no engine
   source. If the reviewer disagrees, `yarn check` is the full gate.
5. **Coverage the new file does not reach:** `RETURNING` interaction with a computed column
   fed a written-form value; a multi-row `insert … select` (the file uses `values`
   throughout, so only the row-expansion path is exercised, not the
   already-declared-types source path `emitInsert` degrades to a conformance probe for);
   and a deferred CHECK evaluated at an explicit `commit` boundary rather than at
   statement end.
6. **`count(distinct …) = 1` is the agreement idiom used throughout.** It states the
   property rather than a literal, which is the point — but it would also pass if *both*
   paths were wrong in the same way. Each agreement section therefore also asserts the
   concrete expected rows immediately after. Worth confirming that pairing held everywhere
   (sections 6, 8, 9, 10 have it; section 11 asserts rows then `count(distinct c)`).
