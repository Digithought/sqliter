# What shipped

A literal DEFAULT is now folded through `foldDefaultToType(expr, logicalType, columnName)` at
every point one can be *declared*, and an unconvertible literal is refused there instead of at
the first INSERT that relies on it:

- **`SchemaManager.createTable`** — a loop over every column, before `module.create`, so a
  refusal leaves no storage behind. Deliberately **not** on the import/rehydrate path
  (`importCatalog`/`importTable` use `module.connect`), so a catalog written before this guard
  still opens.
- **`runAlterColumn` SET DEFAULT** — the new default against the column's current type.
- **`runAlterColumn` SET DATA TYPE** — the column's *existing* default against the new type,
  beside the analogous collation check, and after the PRIMARY KEY refusal so that clearer
  error still wins.

Both ALTER sites are engine-side, ahead of `module.alterTable`, so the memory and store
backends agree without either module changing. Non-literal defaults (function call,
`new.<col>`, mutation-context variable) fold to `undefined` and stay deferred to write time.

# Review findings

## Major — one regression found and fixed in this pass

**The declarative schema differ could no longer migrate a column that changes both its type
and its DEFAULT.** `generateMigrationDDL` emits the comparison-domain statements (`SET DATA
TYPE`, `SET COLLATE`) *before* `SET/DROP DEFAULT`. With the new SET-DATA-TYPE guard in place,
the retype folds the column's outgoing default — the one the very next statement replaces —
against the new type and refuses. Reproduced (`text default 'abc'` → `integer default 0`
through `apply schema`): `Failed to execute DDL: ALTER TABLE t ALTER COLUMN n SET DATA TYPE
INTEGER / Type conversion failed for column 'n': Cannot convert 'abc' to INTEGER`. The same
shape broke when the migration merely *drops* the default.

Fixed at the one site that owns the ordering rather than by weakening the guard: a new
`ColumnAttributeChange.dropStaleDefaultFirst` flag, set only when a retype and a DEFAULT
change land on the same column *and* the column currently has a default, hoists a single
`DROP DEFAULT` ahead of the retype (the trailing `SET DEFAULT` still follows it, and the
drop is not emitted twice). A column whose default is *unchanged* keeps the refusal — that
declaration really does ask for a shape `CREATE TABLE` refuses. `docs/sql-alter.md` § ALTER
COLUMN records the exception to the "comparison domain first" ordering.

No ticket filed: root cause named, one site, fixed and covered.

## Minor — fixed inline

- `inferType(action.setDataType)` was computed twice in the SET DATA TYPE arm; hoisted to one
  `newLogicalType` const shared with the collation check.
- Test gap: the SET DEFAULT refusal was only asserted on a column with *no* prior default, so
  "the previous default survives" was untested. Added a case with an existing `default 3`.

## Tripwire — recorded, not ticketed

An accepted retype leaves the default's AST in its **old type's spelling** (`text default '7'`
retyped to `INTEGER` keeps the literal `'7'`, not `7`). Harmless today — the DDL re-parses and
re-folds to the same value — but the generated DDL is non-canonical. Parked as a `NOTE:` at the
fold site in `runtime/emit/alter-table.ts` (~1494), with the condition that would make it real
(a schema-hash or DDL compare across a retype) and the fix (rewrite the AST from the fold's
return value).

## Checked and clean — no findings

- **Guard placement / no partial state.** The CREATE TABLE loop runs before `module.create`;
  the sqllogic asserts the table is absent from `schema()` after each refusal. Both ALTER folds
  run before `module.alterTable`; the sqllogic asserts type and stored rows are unmoved.
- **Other producers of `SET DATA TYPE` DDL.** Grepped every package: `schema-differ.ts` is the
  only emitter (the store and isolation hits are consumers of the parsed action). The differ fix
  therefore covers the whole class.
- **Other callers of `createTable`.** Only `emit/create-table.ts` and the materialized-view
  backing-table build; neither synthesizes literal defaults, so no path is newly gated by
  accident. Rehydration goes through `importTable`, unaffected — pinned by the new
  `schema-manager.spec.ts` case.
- **DRY across fold sites.** All eight call sites route through the one helper; no duplicated
  convert-or-throw logic was introduced.
- **Docs.** Read `docs/sql-ddl.md` § 7.5 and `docs/sql-alter.md` § ALTER COLUMN against the
  code; both describe the shipped behavior, and the differ-ordering paragraph now matches the
  fixed emission order.
- **Source hygiene.** The change is three short guarded blocks plus one differ flag; no function
  grew past its purpose and no file was materially enlarged.
- **The implementer's stated gaps.** The `apply schema` abort path is now covered from the
  other direction too (the §4 cases assert a migration that *should* succeed does). Per-type
  message pinning for DATE/JSON was deliberately left generic — the fold reuses the same
  `validateAndParse` text every other call site relies on, so pinning it here would only
  duplicate coverage.
