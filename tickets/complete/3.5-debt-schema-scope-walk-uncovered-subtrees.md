# The schema expression scope walk now reaches every sub-expression

## What the walk is

`CHECK (…)` and `GENERATED ALWAYS AS (…)` bodies are expressions stored in a table
definition. Two schema-time analyses read them, and both run over one traversal
(`src/schema/expr-scope/walk.ts`), which hands each name-bearing leaf to a handler
along with a stack of FROM scopes:

- the **self-qualifier strip** rewrites `check (t.qty > 0)` into `check (qty > 0)`
  when nothing inside the body could have rebound `t`;
- the **generated-column reference collector** classifies each name as binding the
  row being written (`own`), an inner FROM source (`foreign`), nothing at all
  (`unbound`), or undecidable (`unknown`).

A reference the walk never reaches is a reference the collector records no dependency
edge for, and a missing edge means a generated column computes before the column it
reads and silently stores NULL.

## What shipped

**Window frame bound expressions are visited.** `sum(x) over (rows between y
preceding and current row)` — `y` was invisible; now visited in the same frame as
`partition by` / `order by`. `WindowFrame` / `WindowFrameBound` are not AST nodes, so
they are handled structurally.

**A new frame kind, `sealed`.** `with inverse (…)` on a result column and a select's
trailing `with defaults (…)` are view write-through metadata: evaluated against the
row written *through a view*, where `new.<output column>` is the naming environment —
one this walk does not model. Descending them under normal rules would make `new.a`
classify `'own'`, inventing a dependency on the table being defined. A plain opaque
(barrier) frame does not prevent that, because the classifiers check the `new.` /
owning-table spellings *after* the frame loop. So `frame.ts` gained
`sealedScopeFrame()` (implies `hasOpaque`) plus `hasSealedFrame(stack)`, and each
analysis honours it in one place, before any seed matching.

**`with inverse` and `with defaults` are visited, sealed.** `inverse` is visited from
the shared `visitResultColumns` helper, so a DML `returning` list carrying its own
`with inverse` inherits it.

**DML sub-parts are visited.** Inside the single opaque frame each DML arm already
pushed: `returning`, `upsertClauses[].assignments[].value`, `upsertClauses[].where`,
and `contextValues[].value`, for insert / update / delete alike.

**Compound legs no longer inherit the leading leg's FROM scope.** `select … from s1
union select … from s2` used to analyse the second leg with `s1`'s sources still on
the stack. The leg visits moved out of the leading leg's FROM-frame push (still inside
the `with`-clause push — a leading `with` scopes over the whole compound, a `from`
does not).

## Behaviour a user can hit

**A generated body that names its own column inside a nested DML is now a cycle.**
Everything under the DML barrier classifies `'unknown'`, and
`validateAddColumnGeneratedRefs` treats any non-`'foreign'` binding whose name equals
the column being added as a self-cycle. So `alter table t add column g generated
always as (<body naming g inside a nested statement's returning list / upsert
assignment / context assignment>)` raises `Cyclic dependency in generated columns:
'g'` at ALTER time instead of being accepted. That is the correct answer — the walk
genuinely cannot tell whether the nested statement's target is this very table — and
qualifying the reference does not avoid it. Documented in `docs/sql-ddl.md` and
guarded by § 6 of `41-generated-column-errors.sqllogic`.

**A bare name in a later compound leg now binds the written row** where the leading
leg's source happened to expose it. That is the fix; it also means such a name is now
rejected at DDL time when it is not a column of the table being defined.

## Found and fixed in this pass

**A regression the handoff did not identify: sealed references classified `'unknown'`,
which raises a false cycle error.** `'unknown'` means "an opaque source *might* be this
row", and both consumers hedge by recording a dependency edge for it. A sealed subtree
is definitively not this row, so that edge is spurious — and a spurious self-edge is a
`Cyclic dependency in generated columns` error at `CREATE TABLE`. Verified against the
engine: three shapes that were accepted before this ticket's diff were rejected after
it, including two generated columns whose bodies name each other only inside a
`with inverse` clause. The handoff called out only the DML arm as behaviour-visible;
this arm has the same mechanism and the wrong answer. Fixed by classifying a sealed
reference `'foreign'` — the one binding both consumers ignore outright — behind a named
constant carrying the reasoning (`sealedBinding`, `generated-column-refs.ts`). Guarded
at both levels: § 14 of `41-generated-column-scope.sqllogic` and two walk-spec cases.
Both guards confirmed non-vacuous (they fail with the constant flipped back).

**The cross-reference NOTE undercounted the divergence.** Both `walk.ts` and
`visitor.ts` gained a note claiming window frame bounds were the only place the two
traversals now differ in reach. There are five (see the filed ticket below). The whole
purpose of that comment pair is to keep the two traversals in step, so an inaccurate
divergence list defeats it. Corrected in both files, with the consequence stated and
the owning ticket named.

**Docs were out of date on two points.** `docs/sql-ddl.md` enumerated the bodies whose
qualifiers are undecidable as "a CTE body or a derived table" — nested DML belongs on
that list (true before this ticket too), and the new ALTER-time cycle rejection was
undocumented. Both fixed, including the fact that qualifying the reference is not a
workaround (verified, not assumed).

## Found and filed

**`bug-ast-traversal-misses-expression-subtrees`** (`tickets/backlog/`). Checking the
divergence claim turned up that `traverseAst` (`src/parser/visitor.ts`) skips five
expression-bearing subtrees, and that `manager.ts`'s declaration-time determinism gate
walks with it — so `random()` hidden in a window frame bound, a `with defaults` clause,
a nested statement's `returning` list, an upsert assignment, or a `with context`
assignment is accepted at `CREATE TABLE` for both `CHECK` and `GENERATED ALWAYS AS`
bodies. Verified: four `create table` statements accepted that the control case
(`random()` in a plain subquery) correctly refuses. Not fixed here — widening
`traverseAst` widens what four `manager.ts` validators see, three of which *reject*
DDL, and that blast radius needs its own pass; that is exactly why the implementer left
the `TODO` alone. Filed at the class level per the architecture ladder: the ticket asks
for a coverage ledger (the shape the walk spec's `EXPRESSION_KINDS` already
demonstrates) alongside the five arms, so a sixth cannot appear silently. Site-claim
grep found no open ticket touching `visitor.ts`; `bug-unknown-function-not-caught-at-
declaration` is a disjoint hole in the same gate and is cross-referenced from both.

## Tripwires parked (not tickets)

- **Frame-bound analysis is unobservable today.** The planner rejects any frame offset
  that is not a constant numeric literal ("Window frame offsets must be constant
  numeric literals"), so a bound naming a column never executes whether or not an edge
  was recorded for it. This is *why* change 1 has no SQL-level test, and it changes if
  correlated or foldable bounds are ever accepted. `NOTE:` at
  `walk.ts`'s `visitWindowFrameBound` call site.
- **Nothing forces a new write-through clause to be sealed.** The handoff's own gap 5,
  demoted to a tripwire because it is conditional on a third such clause appearing.
  `NOTE:` at `frame.ts`'s `sealedScopeFrame`, explaining why "clauses resolved in the
  written-row environment" cannot get the same compile-time ledger the expression node
  kinds get.
- The handoff's own parked tripwire — a compound's `order by` / `limit` / `offset` are
  visited inside the leading leg's FROM frame because the parser folds them there — was
  re-checked and is accurate; the compound-leg split neither improves nor worsens it.
  Left as-is.

  rejected earns a permanent guard even when the shape is contrived. Added § 6 of
  `41-generated-column-errors.sqllogic`, two arms (`returning` list and upsert
  assignment) plus an assertion that the rejected ALTER left the table untouched.
- *"Changes 1–3 have no sqllogic coverage, by design."* Half agreed. Change 3 turned
  out to be very much SQL-observable (it is the regression above) and now has § 14.
  Change 1 is genuinely untestable at SQL level, for the measured reason in the
  tripwire above rather than because it is contrived. Change 2 is the mechanism behind
  change 3 and is covered through it.
- *"`upsertClauses` / `contextValues` / `with inverse`-inside-`returning` are covered
  only at walk level."* `upsertClauses` now has a SQL-level arm (§ 6b). The other two
  stay walk-level: both sit under the same DML barrier as the `returning` case now
  covered, so a SQL-level case would assert the same classification twice.
- *"`sealed` has one producer and no exhaustiveness check."* Agreed, and it is
  conditional — parked as a tripwire rather than filed.
