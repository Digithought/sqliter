# Rename rewrite preserves what a reference resolves to

## What shipped

A stored body (view, materialized view, assertion, CHECK, column DEFAULT) can
name a table without a schema qualifier; the name resolves against the body's
home schema first, then the session search path. The rewrite used to replace
such a reference in place — new name, still unqualified — so if an earlier
schema on the body's path already held a table with the *new* name, the
reference silently re-bound to that other table.

The implementation added a post-condition at the one rewrite sink
(`renameTableInAst`): after renaming a reference, re-resolving it under the same
home schema path *against the catalog as it will be after the rename* must still
yield the renamed object's key; when it would not, the reference is
schema-qualified. Conditional, not eager — a rename with no collision leaves
body text (and a materialized view's `bodyHash`) byte-identical.

Supporting pieces: `ObjectRefResolvers.withTableRenamed` (a sibling snapshot with
the one rename applied), `TableRenameTarget` (one required argument bundling
`resolve` + `resolveAfter`, so no caller can supply the before-answer without the
after-answer), `tableRenameTargetsFor` (per-home-schema target factory), and
`TableRef.qualify` present at exactly the three sites where a reference
re-resolves through the catalog.

## Review findings

### Checked and clean

- **The one-traversal invariant holds.** `tableReferencedInAst` (DROP-guard
  probe) and `collectTableRefsInAst` (closure collector) are untouched; all of
  the post-condition logic lives in the rewrite sink, so "would have been
  rewritten" and "is a reference" cannot drift.
- **No qualification leaks from the pre-flight.** `assertRenameDependentsPersistable`
  runs the rewrite over `spineCloneAst` copies, so a vetoed statement leaves no
  qualifier behind.
- **Frame-bound column qualifiers stay correct.** `collectFromBindings` copies a
  source's schema/name *by value* before anything under the `FROM` is visited, so
  qualifying the source afterwards cannot disturb the qualifiers bound through
  it. Pinned by a walker test and by the grid.
- **A qualified reference cannot double-qualify** — it only matches when its
  written schema is the renamed schema, and a qualified name resolves by
  passthrough, so the post-condition holds by construction.
- **MV derived fields agree with the qualified text**: `bodyHash` and the
  regenerated `sql` are both recomputed from the rewritten body.
- **The schema-differ's three inverse sites** are correct passing the same
  resolver twice — `singleSchemaObjectRefResolver` keys every bare name under the
  one schema, so the post-condition is an identity there.
- **Source hygiene**: `table-rename.ts` is 728 lines (`wc -l`), under the ~1,000
  threshold `debt-oversized-source-files` uses; `alter-table.ts` (2,534) is
  already listed in that ticket, so no new size ticket.

### Fixed in this pass

- **Committed debris from the interrupted prior review run.** The runner's
  `714137a0` ("agent error … added resume note") committed a leftover
  `console.error('DBG target', …)` inside `store-module-rename.ts`'s rewrite
  closure and a scratch test asserting `expect(ddl, 'SHOWME').to.equal('SHOWME')`
  — so `yarn test` failed at HEAD in `@quereus/store`. Debug line removed; the

- **The store path answered the post-condition with the *pre*-rename snapshot.**
  `store-module-rename.ts` passed `resolveAfter: resolveRef` with a comment
  claiming qualification could never fire there. It can: `buildObjectRefResolver`
  is the catalog-backed home-path resolver, not a single-schema one, so with
  `pragma schema_path = 'main,temp'` and a `temp.t_q2` present, renaming
  `main.t_q → t_q2` made the store write `default (select count(*) from main.t_q2)`
  into the persisted DDL while the engine's own pass left the same expression
  bare `t_q2` — same statement, two backends, divergent text. Verified both
  sides directly. Fixed by deriving the sibling snapshot through the newly
  exported `tableRenameTargetsFor` (which is also correct for the rollback arm:
  un-renaming back to the old name lands on the base snapshot, which *is* the
  pre-rename catalog), and the comment now says why deriving it is load-bearing.
- **Closed the handoff's stated test gap.** The own-table self-reference case was
  "confirmed by reading, not by a test"; it is now pinned on both sides — a store
  test (`does not schema-qualify an own-table self-reference …`) and an engine
  parity cell in the collision grid.

### Filed as a new ticket

- `fix/rename-preserves-the-meaning-of-every-name-in-a-body` (major, `repro:
  verified`). The shipped post-condition covers the references the rename
  *rewrites*; two verified arms show the rename changing the meaning of names it
  never touched. (a) A body reading a table by short name re-binds to the newly
  created name: `create view temp.v as select * from k` meaning `main.k`, then
  `alter table temp.other rename to k`, and the view returns the other table's
  rows — reproduced for views, materialized-view `REFRESH`, and an assertion that
  stops enforcing. (b) Renaming a `FROM` source onto a name a sibling source in
  the same `FROM` already exposes collapses the two column qualifiers, turning a
  join condition self-referential and returning no rows with no error; this arm
  predates the qualification work. Both resolve at the same site — the walk sink
  in `table-rename.ts` — so they are one ticket with two arms, filed at the
  invariant level ("every reference must mean after the statement what it meant
  before") rather than as two instances. `CREATE TABLE` / `DROP TABLE` re-bind the
  same way and are named in the ticket as the same class, explicitly out of its
  scope (no propagation pass to hang a fix on).

### Recorded as a tripwire, not a ticket

- The declarative differ has no declared counterpart for a body the forward
  rename schema-qualified: a declared form reads bare `t2` where the live body
  now reads `main.t2`, which would re-diff as a body change and emit a recreate
  back to the re-binding spelling. Unreachable today — qualification only fires
  when the body's home schema differs from the renamed table's, and a diff covers
  one schema at a time. Parked as a `NOTE:` in `inverseRenamedViewParts`
  (`schema-differ.ts`) with the condition that would trip it.

### Considered and deliberately not changed

- `TableRenameTarget` does not precompute its `targetKey` / `newTargetKey`; three
  sites re-derive them with `objectRefKey`. It is two string concatenations over
  handfuls of names, and keeping the interface plain-literal-constructible is
  what lets the differ and the store build a target inline. Not worth the churn.
- `ResolveObjectRef` may return `undefined` by type, which on the `resolveAfter`
  side would produce a spurious (but semantically harmless) qualifier. Neither
  builder can return it, and the conservative direction is the right one for a
  hypothetical partial resolver.

### Documentation

- `docs/sql-alter.md` § RENAME TO gained a **Known limitation** paragraph for the
  two arms above, in plain terms with a runnable example and the tracking slug.
