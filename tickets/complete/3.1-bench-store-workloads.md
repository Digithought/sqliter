# What landed

`yarn bench` runs every `execution` and `mutation` workload twice: once on the memory vtab
module (bare name, unchanged) and once on `@store-mem` — `StoreModule` wrapped by the
isolation layer, over an in-memory key-value provider. 19 new rows, 46 benchmarks total.

Each `@store-mem` row also reports **storage round trips**: its `counters()` block nests
`{ engine, store }`, where `store` is keyed by built store name and carries four counts per
store — `iterateEntries`, `getManyCalls` (round trips), `getManyKeys`, `singleGets`.

The pieces: `bench/lib/store-counters.mjs` (the harness's one dynamic-import site for
`@quereus/store`, both store databases, and `readStoreCounters`); `STORE_MEM_BACKEND` plus
two new optional `BenchBackend` members, `skipWorkload(workload)` and `openCounting()`,
wired in by `expandBackends`; and `MutationWorkload.counters(db, ctx)`, whose
`ctx.beginMeasured()` marks where a pass's own fixture ends and its subject begins.

The storage counters are the metric none of this had coverage for: if secondary-index row
resolution ever stopped batching, `filtered-scan-index-10k@store-mem`'s `getManyCalls`
goes 1 → 10 and `singleGets` takes the keys, with no engine counter moving and no
dependence on the machine that ran it.

# Review findings

Reviewed the implement diff (`2e6b289c8`) file by file before reading the handoff, then
read the surrounding harness (`run.mjs`, `child.mjs`, `compare.mjs`, `counters.mjs`), the
storage package's counting and in-memory providers, and the recorded results files.

## Verified rather than assumed

- **The skip probe, which the handoff correctly flagged as an untested claim.** Rather than
  renaming `packages/quereus-store/dist` (a shared build artifact a concurrent runner may
  be using), made `@quereus/store` unresolvable with a node resolve hook via `NODE_OPTIONS`,
  which the forked benchmark workers inherit. Result: suite enumeration survived (46
  benchmarks enumerated), all 19 `@store-mem` rows printed `skipped — <reason>`, parser and
  planner suites ran normally, exit code 0. The lazy import does what it is there for.
- **The counter blocks.** Read the recorded store blocks directly. `filtered-scan-index-10k`
  is 10 index `iterateEntries` + exactly 1 `getManyCalls` carrying 10 keys;
  `text-pk-point-seek-10k` is a single `singleGets`; the decorrelation twins both sit at
  10 100 `iterateEntries`. `join-1kx1k`'s left-side scan of 100 entries looked wrong until
  the workload's `where l.id <= 100` explained it — a primary-key range stop, not a
  truncated scan.
- **`beginMeasured` actually moves the boundary.** `delete-where-100@store-mem` reports 100
  `singleGets`, not the ~30 000 its 10 000-row fixture would contribute. The call is load
  bearing, not decorative.
- **The two providers do not diverge on capability.** The timed database and the counted
  one use different providers, so a capability present on one and absent on the other would
  silently measure two code paths. Checked: neither implements `beginAtomicBatch`, so both
  commit per store, and neither declares a cost profile. The counting provider's missing
  `deleteTableStores` never matters because no benchmark drops a table.

## Fixed in this pass (minor)

- **`attach()` leaked the store module when `db.close()` threw.** `closeAll()` ran only on
  the success path; a throwing `db.close()` turned one reportable error into the worker's
  leaked-handle exit, which presents as a hang. Now in a `finally`.
- **`readCounters()` after `close()` returned an empty block.** The counting provider's
  `closeAll` clears the map it is keyed by, so a future caller reordering the two would
  publish "no storage traffic" instead of failing. Both current call sites read first; the
  contract was a comment. Now throws.
- **`ctx.beginMeasured()` was unenforced** — the handoff named this. A mutation workload
  that forgets it reports a store block describing its own fixture: a wrong number
  indistinguishable from a right one, which would poison every baseline diff after it.
  `mutationCounters` now tracks the call and fails the pass naming the workload. No
  sensible default boundary exists to fall back to, so failing is the right outcome.
- **A renamed export in `@quereus/store` would have failed at `setup`, not declined.**
  `loadStoreModules` resolved whatever the package gave it, so a moved export surfaced as
  `createIsolatedStoreModule is not a function` mid-benchmark. It now checks the three
  functions it names, which routes that case through `storeLoadFailure` into a stated skip
  reason. The reason's prefix changed from "did not load" to "is not usable here" so it
  reads correctly for both causes.
- **Stale comment in `run.mjs`** asserting "nothing in the repo declares `skip()`" — this
  change made that false. Reworded to say why the bare denominator is still fine (every
  declining row printed its own reason above).
- **`docs/architecture.md` was not updated by the implement pass.** It still said 27
  benchmarks and described `counters()` as returning a flat `WorkCounterSnapshot`. Both
  corrected, plus a bullet on the backend dimension — one paragraph, deferring detail to
  `benchmarking.md` as that file's own instruction requires.
- **`docs/benchmarking.md`'s `skip()` example** showed a hand-written `skip()` using a
  fictional helper, with no pointer to the only real one. Added a cross-reference to
  `skipWorkload`.

## Test coverage added

`test/bench-store-counters.spec.ts` (new, 5 cases) covers `readStoreCounters`, the one
piece of arithmetic in the change and the only place it can produce a wrong number that
looks right: `singleGets = getCount - getManyKeyCount`. Cases pin the derivation on the
real batched-read shape, the partially-batched case, the opened-but-never-read store
keeping its four zeros, name ordering, and the negative-value guard — which the handoff
correctly described as never having been watched fail. It fails now, in a test.

Not covered, deliberately: the new `beginMeasured` guard lives in a private function inside
a binder file, and exporting it purely for a test would thicken a file whose whole job is
to stay thin. Its failure mode is a loud throw naming the workload.

## Filed (major)

- `backlog/debt-store-write-counters` — the storage counters are **reads only**, so every
  mutation row's block describes the reads its writes provoked and never the writes. The
  handoff parked this as a `NOTE:` and asked whether stopping short of widening
  `@quereus/store`'s testing surface was right. It was right for the ticket, but it is a
  standing partial view rather than a conditional one, so it is filed as a ticket rather
  than left as a tripwire. Grepped the board first: nothing open claims
  `kv-counting-store.ts` for this.

## Considered and declined

- **Pruning the all-zero `__catalog__` / `__stats__` entries.** The handoff offered this. A
  store opened but never read is a genuinely different claim from one never opened (absent),
  and the comparison reports an appeared path as loudly as a changed count — pruning would
  erase that distinction to save four lines per store. Kept, and now pinned by a test case
  so a future prune has to argue with an assertion.
- **Renaming `store-counters.mjs`.** It hosts the plain, non-counting database builder too,
  so the name under-describes it. But the file's header explains exactly why both builders
  share one file (one dynamic-import site), and the rename would be churn against a
  well-documented decision.
- **The skip output is verbose** — a backend-wide decline prints the same ~200-character
  reason 19 times, twice each. It is correct and actionable, appears only in a broken-checkout
  state, and de-duplicating it would mean teaching `run.mjs`'s printer to group skip reasons.
  Not worth it for a transient state.
- **`distinct-text-10k` reading as regressed against an old baseline.** Re-checked the
  handoff's reasoning: that baseline's 23.93 ms is the lowest of 33 recorded runs and
  nothing in the diff touches the memory execution path. Baseline-selection drift, agreed.

# Known gaps carried forward

- **Store counters are reads only** — now `backlog/debt-store-write-counters`, with the
  `NOTE:` still at the site naming the fix.
- **`bulk-insert-10k@store-mem`'s store block covers all 20 batches** while its engine block
  covers the first and last, so the two halves describe the same body at different
  granularities. Commented at the site; defensible and unchanged.
- **`mutation/single-row-insert-1k@store-mem` spread is unsettled** — 105% in one run, ~6%
  in three others (16% in this pass's run). Attributed to machine load. If it proves
  genuinely unstable the fix is a per-backend row count with the count in the name, not
  pinning.
- **No cross-machine check.** Counter portability remains an assumption; store round trips
  are reported as facts about the run that produced them, and there is deliberately no gate
  on them.
- **Wall-clock roughly doubled**: 48 s / 27 rows before, ~102 s / 46 rows after. No row is
  near the 120 s per-benchmark timeout.
