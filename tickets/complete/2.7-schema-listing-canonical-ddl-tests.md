# Complete: schema() canonical DDL — catalog fix + round-trip tests (reviewed)

## What the implement stage delivered

- `packages/quereus/test/schema-func-ddl-roundtrip.spec.ts` (new): two tests driving
  canonical DDL through the `schema()` table-valued function itself — a table with a key,
  NOT NULL, defaults, collation, CHECK, UNIQUE, FOREIGN KEY and tags; and a unique partial
  index with tags. Each reads the DDL back, replays it into a fresh `Database`, compares the
  introspection views, and checks the re-emitted DDL is byte-identical (a fixed point).
- A comment in `schema.ts` flagging that `table_info().dflt_value` was meaningless.
- The shared `syntheticExposedIndexToIndexSchema` helper the ticket describes landed in the
  **previous** commit (`70c3fa118`, ticket `schema-listing-canonical-ddl-followup`), not this
  one — this ticket's diff is the tests plus that comment. Worth knowing if you are reading
  the ticket body against `git show` and wondering where the catalog change went.

## Review findings

### Fixed in this pass

- **`table_info().dflt_value` returned the literal string `"[object Object]"` for every column
  with a default.** The column stringified an AST node with `.toString()`. Verified live: a
  table with `default 'anon'` and `default 5` reported `"[object Object]"` for both. This is
  user-visible — `quoomb-cli`'s `.schema` command prints the column straight into its output
  table. Fixed by rendering through `expressionToString`, the same emitter the DDL generator
  already uses for the `DEFAULT` clause. No test asserted on the old value, so nothing else
  moved; `docs/functions.md`'s description of the column was stale in the same way and is
  updated.
- **The new spec was routing *around* that bug rather than exposing it** — it stripped
  `dflt_value` out of both sides before comparing, via a helper existing only for that purpose.
  With the underlying column fixed, the helper is gone and the comparison now covers defaults
  like every other column attribute.
- **Coverage gaps the implement stage flagged as out of scope are now closed** (they were cheap
  once the file existed): the table test carries an *expression* default (`default (1 + 1)`,
  asserted behaviorally as well as textually), a *composite* foreign key, and foreign-key
  actions (`on delete cascade on update set null`). Previously it had one literal default and
  one single-column action-free FK.

### Filed as a new ticket

- **`tickets/fix/5-bug-exposed-implicit-index-ddl-diverges-across-backends.md`** — the change
  this ticket chain was fundamentally about (making the DDL for a UNIQUE constraint's exposed
  backing index say `UNIQUE`) was applied to the store backend's code path only. The memory
  backend reaches the same index by a different route and still emits a plain `CREATE INDEX`,
  so the two backends now disagree on the DDL text for an identical schema — and inside the
  store backend, the DDL says `UNIQUE` while `index_info()` reports `unique = 0`. Verified by
  running both backends directly (memory `Database`, and a store-backed `Database` over the
  LevelDB provider). No existing test would have caught it: the tests around exposed implicit
  indexes assert that they are *listed*, never what their DDL says. The ticket states the one
  decision to make, recommends an answer, and asks for the two paths to be collapsed into a
  single rendering decision so they cannot drift again.

### Checked, nothing found

- **Test-tree sweep for stale DDL assertions.** Re-checked the implement stage's claim that no
  other test pins the old hand-rolled DDL text. Confirmed — the remaining `schema()` consumers
  select `name`/`tags`/`count(*)` or use substring checks.
- **The shared-helper refactor** (`syntheticExposedIndexToIndexSchema` living in `catalog.ts`,
  imported by the `schema()` function) is right: one definition, both call sites, the type it
  belongs to. The problem filed above is not that the helper is duplicated — it is that a
  *third* path, in the other backend, was never brought into it.
- **Resource cleanup** in the new spec — every `Database` is closed in a `finally`, including
  the inner one.
- **Source hygiene** — the spec is ~150 lines, two tests, three small helpers, no dead code.
  Nothing in the diff is oversized or in need of decomposition.
