# What shipped

`ANALYZE`'s per-column distinct counts, null counts, min/max and histograms now ride in the
same per-table `__stats__` record the store already used for the live row count, and are
loaded and stamped back onto the registered `TableSchema` when the database reopens.

Three seams:

- **The hook.** `VirtualTable.saveStatistics?(stats)` — optional and advisory; `ANALYZE`
  calls it after writing statistics onto the schema and swallows (logs) a rejection. The
  memory backend does not implement it. `IsolatedTable` forwards `getStatistics` and
  `saveStatistics` as optional *fields*, wired only when the underlying implements them, so
  "this module declines" survives the wrapping.
- **The record.** `TableStats` gained optional `columnStats` (lowercase-column-name keyed),
  `analyzedRowCount` and `lastAnalyzed`. Optional means a pre-change record reads back as "no
  column statistics" — no migration, no version field. `serializeStats`/`deserializeStats`
  route through the row codec's `replacer`/`reviver` because min/max and histogram bounds are
  `SqlValue`s. Histograms persist only for a PK member or an index's leading column
  (`histogramColumns`); scalars persist for every column.
- **The read-back.** `StoreTableBase.primeStats` owns the stamp; `rehydrateCatalog` calls it
  per table and `initializeStore` calls it on first storage access, so the snapshot lands
  regardless of connection order and never displaces a fresher in-memory `ANALYZE`.

Two deliberate scope decisions, both still standing after review:

- `getStatistics()` continues to report an EMPTY `columnStats`, because
  `collectTableStatistics` reads a non-empty one as "module answered cheaply, skip the scan".
  Pinned by a regression test.
- `getEstimatedRowCount` still reports the live delta-tracked count; `ANALYZE`'s exact count
  lands in `analyzedRowCount` only, so no existing caller's behaviour changed.

## Fixed in this pass (minor)

- **`primeStats` could skip its own stamp.** The `publishPersistedStatistics()` call sat below
  the once-per-instance `if (this.cachedStats) return` guard, conflating two different
  lifetimes: the *record read* is per instance, but the *stamp* is a property of the
  REGISTERED schema. A table whose storage opens from inside `module.create`/`connect` — which
  runs before `SchemaManager.finalizeCreatedTableSchema` registers the schema — primes with
  nothing to stamp, and the rehydrate loop's explicit `primeStats()`, whose entire job is to
  land that stamp, would then early-return and never publish. Made the stamp unconditional; it
  is idempotent (no-ops on a schema that already carries statistics) and costs two map
  lookups. The existing tests were passing on the ordering that happens to hold today, so this
  is a removed hazard rather than a fixed observable bug.
- **`getPersistedStatistics` was public with no caller outside the class.** Narrowed to
  `private` (its only consumer is `publishPersistedStatistics`, which is already private).
- **`resetStats` silently gained new behaviour.** It replaces the whole `TableStats` record, so
  since this change it also discards any persisted `ANALYZE` snapshot. That is correct — its
  only caller is the host's `replaceContents`, which substitutes every row — but its comment
  still described a row-count-only reset. Documented the discard and why it is right.
- **The rename-column test the handoff called its most valuable gap.** Added
  `keeps the snapshot keyed by column NAME across a rename…` to `stats-persistence.spec.ts`:
  `ANALYZE`, rename `plain` (6 distinct text values) to `renamed`, reopen, assert `renamed`
  has NO entry while `k` keeps its own numbers and the table still plans. A positional key
  would have handed `renamed` a live entry, so this is the assertion that pins the keying.

## Filed as tickets (major)

- **`backlog/bug-alter-column-leaves-stale-column-statistics`** — new. All six module-side
  schema builders for ADD/DROP/RENAME COLUMN (memory and store), plus the engine's rename
  fallback, copy `TableSchema.statistics` across by reference and never prune or re-key it.
  Rename `k`→`k2` then ADD COLUMN `k` and the brand-new all-NULL column inherits the old
  column's distinct count, min/max and histogram. Pre-existing engine behaviour — identical
  in memory today — but persistence lets a mis-attributed entry outlive the session that
  made it, which is why it surfaced here. Filed at the invariant rung rather than as three
  point fixes: one filter at the schema-install seam, guarded by one property-style test
  ("every statistics key names a surviving column"), retires the class including future ALTER
  forms. Effect is bounded to plan choice, never wrong rows — hence `severity: edge-case`,
  `likelihood: contrived`.
- **`backlog/bug-drop-table-leaves-stale-stats-entry`** — existing ticket, second arm appended
  rather than re-filed (same root cause, same one-line fix site). The orphaned `__stats__`
  entry a dropped table leaves behind now carries the per-column snapshot too, so a table
  re-created under the same name inherits the old table's value distribution and not merely
  its size. The ticket's proposed "nothing keyed to the dropped table survives" assertion
  already covers the arm as written.

## Recorded as tripwires, not tickets

- **`ANALYZE` inside a transaction that rolls back leaves the snapshot on disk.**
  `saveStatistics` flushes immediately rather than through the coordinator's commit callback.
  Deliberate and symmetric — the in-memory schema stamp is not rolled back either, and
  statistics are advisory — so it is conditional on statistics ever gaining a non-advisory
  consumer. `NOTE:` at `StoreTableBase.saveStatistics`.

## Checked and clean — nothing to fix

- **Serialization round trip.** `bigint` past 2^53, `Uint8Array` min/max, and marker-colliding
  column names (`$bigint`, `$blob`) all survive: `serializeStats` goes through the row codec's
  `replacer`, whose key escaping reaches arbitrary depth, and `deserializeStats` uses the same
  `needsReviver` gate. Histogram buckets are inside arrays and are still visited per member.
  Covered by the bigint/blob test and `serialization.spec.ts`.
- **The histogram scope rule reads the right schema.** `saveStatistics` passes
  `this.tableSchema`, which is the ENGINE-facing schema; the store's hidden `_uc_*`
  UNIQUE-enforcement indexes live on the separate `materializedSchema`, so they cannot widen
  the set the way the comment warns against.
- **The isolation forwarding is genuinely conditional.** Optional fields assigned in the
  constructor only when the underlying implements each hook, with `this` bound via `.call`.
  Asserted end-to-end through the wrapper.
- **`analyzedRowCount` vs the live count.** Stamping `statistics` means
  `catalogRowCount` (`table.statistics?.rowCount ?? table.estimatedRows`) reports the
  ANALYZE-time count for a reopened table. That is the same snapshot semantics an in-session
  `ANALYZE` already has, and `table-cardinality.ts` already carries a `NOTE:` saying so — not
  a new class of staleness, so left alone.
- **Docs.** `docs/module-authoring.md:189` still claimed `tableInfo.statistics` "is
  `undefined` until someone runs `ANALYZE`", which a persisting module now falsifies at open.
  Corrected and cross-linked to the new section. The new "Persisting statistics across a
  reopen" section itself is accurate, including its wrapper-forwarding snippet.
- **Source hygiene.** No new file; the additions are short, single-purpose methods
  (`primeStats`, `getPersistedStatistics`, `publishPersistedStatistics`, `saveStatistics`,
  `histogramColumns`, `toPersistedColumnStats`). `store-table-base.ts` is large, but it is
  already named in `backlog/debt-oversized-source-files` — no new arm needed, since this
  change adds ~90 lines to a file that ticket already covers.

## Gaps knowingly left open

Each is called out in the handoff, each was weighed, and none warranted a ticket:

- **Histogram scale is never exercised.** The spec seeds 24 rows; the ~4 KB-per-column
  arithmetic in `histogramColumns`'s comment is reasoned, not measured. The comment states it
  as approximate, and the rule is conservative in the safe direction (drop more, not less).
- **Only the in-memory KV provider is tested.** No LevelDB/IndexedDB reopen assertion. The
  test provider mirrors the unified `__stats__` layout the shipped providers use, and the
  persistence path is provider-agnostic (one `get`/`put` of one value), so the equivalence is
  asserted by reading rather than by running.
- **Cross-connection visibility is unchanged and untested** — connection A's `ANALYZE` is
  invisible to B until B reopens or re-analyzes. Same model the row count already had;
  documented in `docs/module-authoring.md`.
- **A crash between the schema write and the flush** leaves memory and disk disagreeing. By
  design; the next `ANALYZE` reconciles.
- **Whether `ANALYZE` should also correct a drifted live row count** is a real open question
  and deliberately out of scope — answering it would change what every existing
  `getEstimatedRowCount` caller sees.
