# Completed: column rename cascades through dependent views

`ALTER TABLE … RENAME COLUMN` used to rewrite only the objects reading the
renamed table directly. When that rewrite shifted the name a view *publishes*
(`select id, x from t` starts publishing `y`), anything reading the view kept
naming a column that no longer existed — a second view broke on next read, and
an assertion in that position broke **every write** to the database.

## What shipped

- **Worklist driver** (`runtime/emit/column-rename-cascade.ts`,
  `runColumnRenameCascade`): breadth-first fixpoint seeded with the renamed
  table. Each round re-enters the *existing* all-schema propagation
  (threaded in as a callback from `propagateColumnRename` to avoid an import
  cycle), so tables' CHECK/DEFAULT/GENERATED expressions, views, materialized
  views, and assertions are covered at every depth.
  `restoreUnaffectedMaterializedViews` runs once, after the whole cascade.
- **Exposure predicate** (`bodyExposesRenamedColumn`): shares the CTE exposure
  internals — `cteExposesRenamedColumn` was split into a query-level core.
  An alias suppresses the cascade; a bare projection and `*` / `t.*` over the
  target continue it. An explicit view/MV column list is the call site's guard.
- **Collision refusal** (`assertColumnRenameCascadePublishable`): a read-only
  pre-flight, before the first side effect, that walks the same fixpoint on
  spine clones and refuses a rename that would make a dependent publish two
  columns of the new name.
- **Pre-stale MVs are excluded from the cascade** — their backing columns are
  not renamed, so their published names don't shift.
- **Persistability veto stays round-1-only**, with a `NOTE:` and its revisit
  condition in `catalog-persistability.ts`.
- Docs: `docs/sql-alter.md` § RENAME COLUMN rewritten (propagation transitive,
  the two cascade stoppers, the collision refusal); `docs/mv-schema-change.md`
  rename section and its "rejected alternative" bullet flipped, since a chained
  MV now follows the rename instead of going stale (53.2 §6 updated to match).

### Fixed in this pass

- **A case-only rename was falsely refused.** `alter table t rename column x to X`
  threw `cannot rename column 't.x' to 'X': view 'main.v' already publishes a
  column named 'X' …` whenever any dependent view or materialized view
  republished the column. Reproduced against the implement commit, both for a
  plain view and for an MV. Root cause: the collision pre-flight's stated
  premise — "before the rename the target cannot publish `newCol`, so anything
  found is a different column" — is false when old and new names differ only by
  case, where the thing found *is* the renamed column. Fixed with an early
  return in `assertColumnRenameCascadePublishable`
  (`column-rename-cascade.ts`); the cascade itself still runs, so both levels
  follow the respelling. Regressions pinned in
  `column-rename-cascade.spec.ts` ("a case-only respelling is not a collision")
  and `41.3-alter-rename-propagation.sqllogic` §59, and the genuine-collision
  refusal is re-verified unchanged.

### Investigated and dismissed — the two open questions in the handoff

Both were checked by repro, not by reading:

- **"The veto may miss a collision that an earlier round created in the same
  body."** Real behavior confirmed: `create view v2 as select v1.x, t.x from
  v1 join t` does become `select v1.y, t.y` with no refusal. But this is not a
  missed collision. That body *already* published two columns under one name
  (`x` and `x:1`) before the rename, so the rename merges no two previously
  distinct names — it only respells a duplicate that predates the statement.
  Generalizing: any `newCol` publication an earlier round can create must have
  come from an `oldCol` publication, so it is never a distinct name class.
  Measuring the collision on the pristine body is therefore *correct*, not
  merely convenient. Wrote that reasoning into the function's doc comment,
  replacing the previous "argued, not proven" hedge.
- **"`resolveColumnInSource` answers only for tables, so a `select *` over a
  view source can't be seen."** True of the *collision* predicate only.
  Verified `t → v1 → (select * from v1) v2 → v3` cascades correctly: the
  exposure predicate's star arm goes through `frameBindsTargetUnaliased`, which
  never consults `resolveColumnInSource`. The limitation is already documented
  on `bodyPublishesColumnNamed` and is correctly scoped there.

Related: the engine tolerates duplicate published column names by design —
`create view v as select t.y, t.y from t` succeeds and reads back as `y` /
`y:1`. So the collision refusal is a usability guard over a state the engine
otherwise accepts, which is the right severity to read it at.

### Tripwires recorded (not tickets)

- **Per-round cost** — `NOTE:` at the top of `column-rename-cascade.ts`: one
  `RENAME COLUMN` costs O(chain depth × catalog size) AST walks (each round is a
  full all-schema propagation plus a full scan of every schema's views and
  maintained tables), and the pre-flight additionally spine-clones every scanned
  body per round. Depth is 1–3 for realistic catalogs and DDL is rare, so this
  is fine now; the fix direction if it ever shows up is an object-dependency
  index to narrow each round to the objects that name the round's target.

  mutates nothing: it probes spine clones, and the analysis it reuses
  (`analyzeWithFrame` / `queryExposesRenamedColumn`) is read-only. Verified the
  refusal leaves the base column and every view body untouched.

### Known limitations carried forward (unchanged, all pre-existing)

  which is what names the output; untested for unions.
- Cross-schema `select *` MV chains still ride the single-pass

  note already records the fix direction.

  comparison, which this ticket never touched.
