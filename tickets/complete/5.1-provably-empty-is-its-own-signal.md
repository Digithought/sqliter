# Complete: "provably empty" is its own signal, separate from a zero row estimate

## What shipped

`BestAccessPlanResult.rows` was documented as an estimate, but `selectPhysicalNode` read
`rows === 0` (plus "every claimed filter handled") as a PROOF that nothing could match and
replaced the whole table read with a static empty relation. An honest estimate could
therefore delete a read that must happen: planning precedes execution, so a table empty at
plan time can still be written and read back by the same statement.

The proof now has its own channel:

- `BestAccessPlanResult.provablyEmpty?: boolean` — set only when the module has proven no row
  can satisfy the filters it claimed. `rows` is an estimate with no exception.
- `AccessPlanBuilder.empty(handledFilters)` builds the whole answer (cost 0, rows 0, the
  filter claims, the flag) and throws if the claims are all false. `setProvablyEmpty()`
  exists for a module that built its plan another way.
- `validateAccessPlan(request, result, moduleName?)` rejects (`StatusCode.INTERNAL`) a
  `provablyEmpty` plan that claims no filter, and one whose `rows` is anything but 0
  (`undefined` included). Rejected, never normalized. The optional module name sharpens the
  message; the memory module and both planner probe sites pass it.
- `provesEmpty(result)` (added in review) is the single well-formedness test — flag set,
  `rows === 0`, at least one filter claimed — used by the planner fold. It mirrors what
  `validateAccessPlan` enforces, so a module that never validates its own plan (the store
  module does not) still cannot fold an access away with a half-expressed proof.
- The memory module's `IS NULL` on a NOT NULL column arm builds its answer with
  `AccessPlanBuilder.empty(...)`. It is the one shipped producer of the flag.
- Three `Math.max(1, ...)` floors were re-commented, not removed: they are now conservative
  cost-model guards rather than load-bearing correctness guards.
- `docs/module-authoring.md` rewrites the row-count contract with an explicit "contract
  change" callout; `docs/optimizer-costing.md` and `docs/store.md` were stale on the same
  protocol and were corrected.

## Behavior change

A third-party module that returned `rows: 0` with every filter claimed and no flag used to
have its access folded away. It is now READ and its filters enforced normally — the correct
new behavior (the old one could return nothing for rows the same statement wrote), and called
out in the docs.

## Review findings

**Checked:** the whole implement diff read before the handoff summary; every producer and
consumer of `BestAccessPlanResult` (a search for `rows === 0` / `rows: 0` across all package
sources found no remaining site reading a zero estimate as a proof; a search for
`getBestAccessPlan` found the isolation layer's delegation and its one fallback build, both
safe, and no spread-and-rebuild site that would drop the new flag); the fold's interaction
with `reattachUnconsumedConstraints` and `rebuildPipelineWithNewLeaf`; the `index-nested-loop`
caller, which declines anything that is not an `IndexSeek` and so is unaffected; all four
docs files that describe the protocol; `yarn build`, `yarn lint`, `yarn test`.

**Minor — fixed in this pass:** the fold's guard and the validation disagreed. Validation,
`AccessPlanBuilder.empty` and `docs/module-authoring.md` all require *at least one* claimed
filter; the fold required *every* filter claimed. A module author following the documented
contract — claim the filter you proved unsatisfiable, leave the rest to the engine — passed
validation and then silently got no fold. `test/vtab/best-access-plan.spec.ts` even asserts
`empty([true, false])` is a legal plan. The relaxed guard is sound: the proof is about the
claimed filter and holds whatever the engine does with the unclaimed ones, which can only
remove more rows, and the residual filters that survive sit above a relation already known to
be empty. Fixed by extracting `provesEmpty()` next to `validateAccessPlan` and calling it
from the rule, so the fold and the validation are one statement of the invariant rather than
two that can drift. `provesEmpty` also tests `rows === 0`, which the old inline guard did not
— a module that calls `setProvablyEmpty(true)` on a plan reporting rows and never validates
now declines instead of folding.

**Minor — fixed in this pass:** three planner-level tests added to
`test/optimizer/empty-relation.spec.ts` for cases nothing covered — a proof claiming one of
two filters (folds), a proof claiming no filter (does not fold, rows come back), and a proof
reporting `rows: 7` (does not fold, rows come back). The last two go through modules that
deliberately skip `validateAccessPlan`, which is what the store module does, so they exercise
the planner's own backstop rather than the validation.

**Major — one ticket filed:** `backlog/debt-access-path-seek-selection-is-one-giant-function`.
`rule-select-access-path.ts` is 1643 lines and `selectPhysicalNodeFromPlan` is one ~569-line
function (lines 480-1048) with no nested named helpers, against the repo standard in
`AGENTS.md` ("small single-purpose funcs"). Pre-existing and untouched by this diff, and no
open ticket claimed the site. Filed at the file/function level rather than as a point
complaint because the concern is structural, and the ticket names the `consumed` bookkeeping
as the invariant any split must preserve.

**Tripwires:** none newly recorded. The implement stage already left `NOTE:` comments at the
three `Math.max(1, ...)` floors (`vtab/memory/module.ts` `estimateEqualityRows`,
`quereus-store/src/common/store-module-access-plan.ts`,
`quereus-store/src/common/store-module.ts` `sizeRequestFromLiveCount`) recording that each is
now a conservative cost-model guard with a stated revisit condition; those were checked and
are accurate.

**Accepted tradeoffs respected:** `store-module.ts:688` already carries a `NOTE:` explaining
that the store module deliberately does not call `validateAccessPlan` and degrades safely
instead. That is exactly the gap the fold's inline guard covers, so the finding was not
re-filed; the guard was strengthened instead.

**Considered and not filed:** the engine does not call `validateAccessPlan` on the main
`createIndexBasedAccess` path either — only the two probe rules and the memory module itself
validate. Adding a boundary call there would reject third-party modules that are tolerated
today, and the accepted-tradeoff `NOTE:` above already documents the decision for the one
in-tree module it would affect. `setProvablyEmpty()` still has no in-tree producer and is
covered by the builder unit test alone; that is coverage of an API affordance, not a defect.
`schema/lens-prover.ts:2472`'s `rows === 0` was re-checked and is a cardinality band for a
fingerprint, unrelated to access plans.

**Nothing found in:** resource cleanup (the change adds no lifetimes), error handling (the new
rejections use `quereusError` with `StatusCode.INTERNAL`, matching the surrounding
validation), type safety (`provablyEmpty?: boolean`, no casts, no `any`), and the isolation
layer (it delegates `getBestAccessPlan` verbatim, so the flag is carried through unmodified).
