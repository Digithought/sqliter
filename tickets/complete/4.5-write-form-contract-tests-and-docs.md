# Declared-form write contract — pinned in a test and written down

## What landed

The prereq (`4-generated-and-default-exprs-see-unconverted-row-on-insert`, commits
`af80df49a` / `3499dccd5`) made INSERT evaluate DEFAULT and GENERATED expressions against
the *converted* row, so all write paths agree. This ticket pinned that agreement in a test
and wrote the rule down. **No engine source changed** — test plus documentation only.

The rule: every expression the engine evaluates against a row being written sees that row
in its columns' **declared form** — the values that will actually be stored — never the
form the statement spelled. It covers CHECK (immediate and deferred), a column `DEFAULT`
(including one reading a sibling through `new.<column>`), and a `GENERATED ALWAYS AS`
body, at all four write sites: `INSERT`, `UPDATE`, `ON CONFLICT … DO UPDATE`, and the
`ALTER TABLE … ADD COLUMN` backfill.

The witness is `datetime`, where the two forms differ visibly: `'2099-01-01T00:00:00.000Z'`
is accepted, canonicalized through UTC, and stored as `'2099-01-01T00:00:00'`. Anything
still seeing the trailing `Z` is reading the written form and is wrong.

## Review findings

### Verified rather than trusted

The implement handoff flagged three things it had not confirmed. All three were checked:

- **The rewritten 15.1.1 comment is correct.** It claims a `NOT NULL` DEFAULT substituted
  under `OR REPLACE` reads the *converted* row while converting only its own injected cell.
  Ran the shape directly: `k json not null default (new.j)` with `j` holding `'"Bob"'`
  yields `k` = the parsed document `Bob`, not the raw text. Read `buildCellCoercion`
  (`types/validation.ts:175`) and confirmed the identity-plus-conformance branch is what
  keeps the injected cell from being re-parsed. The old comment read confidently and was
  wrong; the new one holds.
- **The release note's "4.4.1" attribution is correct.** Traced it rather than carrying it
  across: `git tag --contains c4749ca0b` puts `ticket(implement): json-coerce-once-at-dml-source`
  — the commit that moved conversion to the top of the DML pipeline and rewrote
  `runtime/emit/constraint-check.ts` — first in **v4.4.1**. No change needed to the note.
- **The docs' description of INSERT matches the code.** Read
  `planner/building/insert.ts` (`coerceToDeclared`, `buildBaseExpansion`,
  `buildExpressionDefaultProjection`, `createGeneratedColumnProjection`): the stage order
  and the in-place wrapping the docs describe are what the code does. RT-001's five `code:`
  pointers each name a symbol that exists at the named path.

### Fixed in this pass (minor)

- **A comment in section 11 of the new test file was factually wrong.** It read "A plain
  INSERT supplying the same NULL takes the same substitution and agrees", but the statement
  under it was `insert or replace`, and a plain `INSERT` does **not** take the substitution
  — verified: it throws `NOT NULL constraint failed`. Substitution requires REPLACE conflict
  resolution (`pickAction(stmtOR, column.defaultConflict)` in `runtime/row-constraints.ts`).
  Reworded, and a new assertion added showing that without REPLACE the row is simply
  rejected — so the file now says which form the DEFAULT reads *and* when it fires.
- **Two coverage gaps the handoff listed as unreached were closed** (new sections 12 and 13):
  - **Section 12 — a multi-row `insert … select` agrees with `values`.** Sections 1-11 all
    write through `values`. A relational source whose static type is already the declared
    type takes the branch where `coerceToDeclared` skips the wrap and `emitInsert`'s pass
    degrades to a bare conformance probe — a different code path with no coverage. The
    section writes four rows through three source spellings (a `datetime`-typed source, a
    `text`-typed source, and `values`) into one table carrying both a CHECK and a generated
    column, and asserts one computed result.
  - **Section 13 — `RETURNING` hands back the declared form**, at all three write sites that
    can carry the clause (INSERT, UPDATE, `ON CONFLICT … DO UPDATE`), each cross-checked
    against a later `SELECT`.

### Filed as a new ticket (major)

- **`backlog/bug-not-null-default-substitution-invisible-to-later-column`** — probing the
  substitution path turned up a real, reproducible defect next door to the contract. When two
  `not null` columns are both written NULL under `OR REPLACE` and the second one's DEFAULT
  reads the first through `new.<column>`, it reads the pre-substitution NULL rather than the
  value just substituted, so the write fails with a spurious `NOT NULL constraint failed`.
  Root cause is one site: `checkNotNullConstraints` writes each substituted value into a row
  copy but never re-shows that copy to the next column's DEFAULT evaluator. `repro: verified`.
  Filed rather than fixed here because there is a genuine semantics question behind it — the
  INSERT path deliberately *forbids* one default reading another (it rejects `new.<other>` at
  plan time), so a maintainer may prefer a better error message to a value change; the ticket
  states both resolutions. Site-claim grep over the open board found two other tickets naming
  `row-constraints.ts` (`bug-lens-check-skipped-when-write-uses-a-conflict-clause`,
  `feat-not-null-error-never-says-the-not-null-was-implicit`); neither claims this site or
  this behavior, so it is a fresh ticket, not an arm.

  test, and the doc is near its word cap. A second pointer would duplicate that link.
  Upholding the call.
- **The release note living only in the working tree is not a defect.** `docs/releasing.md`
  designates `.release-notes.pending.md` as the place notes live during a cycle, and
  `.gitignore:23` keeps it untracked by design — `yarn gh-release` consumes and deletes it.
  The implementer followed the documented process, so this is not a finding against the work.
  Whether release notes should have a tracked home is a separate process question for a human;
  no ticket filed, since filing one against a documented process would be re-litigating it.
- **The `count(distinct …) = 1` idiom.** The handoff worried it would pass if both paths were
  wrong in the same way. Checked every agreement section (6, 8, 9, 10, and now 12): each
  pairs the property assertion with a concrete expected-row assertion, so a jointly-wrong
  pair would still fail. Section 11 asserts rows first, then the count. The pairing holds
  throughout; no change needed.
