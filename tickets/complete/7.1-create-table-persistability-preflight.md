# What shipped

`SchemaManager.createTable` calls `assertCatalogObjectPersistable(this.db, 'table', baseTableSchema)`
immediately after the duplicate-UNIQUE guard and before `module.create` / `createBacking`. Every
registered virtual-table module is asked whether it could durably write the resulting catalog
entry; the first refusal propagates out of the statement, so the table is never created and no
storage is left behind. This is the same synchronous pre-flight `CREATE VIEW`, `CREATE
MATERIALIZED VIEW` and the `ALTER TABLE … RENAME` dependent scan already ran.

No store-side change was needed: the `'table'` kind, `ownsTableCatalogEntry` (the self-filter
that keeps a `using memory` table from being vetoed on the store's behalf) and
`prospectiveCatalogEntry`'s `'table'` arm all already existed for the RENAME pre-flight.

Deliberately **not** gated: the import / rehydrate path (`importTable`, `importCatalog`,
`buildTableSchemaFromAST` on its own), so a catalog written before this guard existed still opens.

# Review findings

**Checked:** the implement diff read cold before its handoff summary; placement of the new call
relative to every other guard in `createTable` and to `module.create` / `finalizeCreatedTableSchema`;
the store's ownership self-filter for a pre-`module.create` schema (`vtabModule` is set by
`buildTableSchemaFromAST`, so ownership resolves — and the wrapper arm covers isolation);
whether any other table-creating path bypasses the guard (`createBackingTable`,
`createMaintainedTable`, CTAS); whether the sibling DDL paths (`CREATE INDEX`, `ALTER`) carry the
same silent-loss shape; every doc and doc-comment that describes when this hook is consulted.
Ran `yarn workspace @quereus/store test` (1580 passing), `yarn test` (full workspace, green),
`yarn lint` and `yarn typecheck` — all clean.

**Fixed in this pass (minor):**

- `packages/quereus/src/vtab/module.ts` — the hook's own doc still said "`'table'` is a
  RENAME-propagation kind only: `create table` is not gated here". Corrected, along with the
  call-site list and the `CatalogObjectKind` doc, and it now states the two deliberate
  exclusions (import/rehydrate, and `CREATE INDEX` whose catalog write is awaited).
- `packages/quereus-store/src/common/store-module-catalog.ts` — "The `'table'` kind arrives only
  from the RENAME pre-flight scan" was likewise stale; the adjacent `NOTE:` on duplicate DDL
  rendering now names `CREATE TABLE` among the paths that pay it.
- `packages/quereus-store/test/lone-surrogate-keys.spec.ts` — the rewritten block header still
  credited `buildDataStoreName` with refusing a lone-surrogate TABLE name. That is no longer the
  guard that fires first: the pre-flight's catalog-key derivation now runs ahead of
  `module.create`. Comment corrected (the claim stays true for INDEX names).

**Closed the two coverage gaps the handoff declared** (both were listed as known and untested):

- `refuses a MAINTAINED table before any backing store is built` — `create table … using store
  maintained as …` with an unencodable column name is refused, no backing table survives, and the
  catalog holds only the base table. This is the ordering requirement the plan called out
  explicitly and it was previously only argued from code reading.
- `an isolation-wrapped store still vetoes a CREATE TABLE` — pins that `IsolationModule`'s
  forward covers this path, not just the view/rename paths.

**Filed (major, separate site):** `tickets/backlog/bug-create-index-failure-leaves-orphan-index-store.md`.
`StoreModule.createIndex`'s teardown arm wraps only the index BUILD; a throw from the later
`saveTableDDL` (reachable today with a partial-index predicate carrying unencodable text, and in
general on any catalog-write IO error) leaves the populated index store on disk and the connected
table's cached schema listing an index the engine never registered. The error does reach the user
— no silent loss — so it is not this ticket's bug class, but it is a real cleanup-path defect at a
site no open ticket claimed. Verified the error path by running it; the residue itself is read off
the code, which the ticket states.

**Tripwires:** none new. The one performance concern here — the veto re-renders the table's full
DDL text and the persist that follows renders it again — already had a `NOTE:` at
`store-module-catalog.ts`; it now names `CREATE TABLE` too rather than getting a second note.

**Accepted tradeoffs encountered:** none at any site touched.

**Not filed, and why:** the handoff's remaining gap — no dedicated test for `apply schema`
aborting mid-batch on this guard — is genuinely a straight-line consequence of `createTable`
throwing synchronously, which every other guard in that function (duplicate UNIQUE, duplicate
constraint names, FK collation) already produces and the batch path already handles. A test there
would pin the batch machinery, not this change.
