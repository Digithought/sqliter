# Charge the cost model for resolving an index entry to its row

## What shipped

**`AccessPlanBuilder.addCost(delta)`** (engine) — adds to the cost a shape factory already
set, so a module can price an extra per-row term without restating `eqMatch` / `rangeScan`'s
formula. Throws if no cost was set first.

**`ROW_RESOLUTION_COST = 1.0`** (store) — charged per estimated returned row on the `eq`,
`prefixRange` and `range` secondary-index arms, on top of the shape's own per-row term. A
secondary-index path reads the index entry AND the row it names (batched 256 at a time), so
parity with one sequential row read is the starting point; nothing was measured against real
storage. The constant is not tunable upward: because selectivity is a fixed fraction, each
arm's cost and the scan's are both linear in the row count, so a constant flips an arm always
or never — `range` at 2.83, `prefixRange` at 6.17, `eq` at 9.7.

**Seek-versus-scan comparison** in `computeBestAccessPlan` — the module now returns the
sequential scan when the best seek prices strictly above it (ties keep the seek). The scan
claims no filters, so the residual keeps the predicate and the rows are identical.

**Multi-seek arm exempt** from both the term and the comparison, measured during implement:
`multiRows` clamps at the whole table from ten seek keys up, and `rule-key-set-seek` probes
the module with synthesized 2-key and 1000-key filters to read a cost slope — charging the
term failed 16 tests and applying the veto failed 11 more, and the term would have capped
key-set seeks at ~710 keys on a table of any size. Both exemptions are argued at their sites;
the root cause (the clamped union estimate) is filed as
`backlog/debt-store-multi-seek-union-row-estimate`.

## Review findings

### Checked

Implement diff read first, then the handoff. Every arithmetic claim in the new comments was
re-derived independently and holds: the three flip points (2.83 / 6.17 / 9.7), the ten-key
clamp saturation, `cost(1000 keys) = 500 + 1.3 × N > N` for all N, the one-row veto case at
1.6 against 1.0, and `ROW_RESOLUTION_BATCH = 256` in `store-table-scan.ts`.

Primary-key arms: correctly exempt from the resolution term (the PK index *is* the row
store, so there is no second read) and un-vetoable by construction — a PK point lookup costs
0.4 and a PK range `0.2 + 0.15 × N`, both below the scan's `N` for every N. Their
by-position precedence is unchanged, as the ticket required
(`backlog/bug-store-pk-range-preempts-cheaper-index` untouched).

Correctness of the veto: it returns a plan claiming no filters, so `ruleGrowRetrieve` keeps
every predicate as a residual — a lost seek is a speed change, never a wrong answer. Confirmed
at the SQL level (matching and non-matching predicate) and across the full LevelDB logic run.

Size: `store-module-access-plan.ts` is 723 lines (`wc -l`), under the ~1,000-line threshold
`docs/store.md` sets for the store chain, and it is not in `debt-oversized-source-files`'
inventory — no size finding. Comment volume in this diff is high (~90 lines of prose for
~15 lines of code) but matches the file's established style, and the two exemptions it argues
are genuinely distinct, so it was left alone.

### Fixed in this pass (minor)

- **The scan cost was re-derived by hand.** The comparison used a literal
  `estimatedRows * 1.0` restating `AccessPlanBuilder.fullScan`'s formula — the exact drift
  `addCost` was introduced to prevent. The scan plan is now built once and its own `cost` is
  the comparison operand; the veto path re-explains that plan instead of rebuilding it, and
  the final fallback returns it directly (the `fullScan` closure is gone).
- **A test asserted something it never exercised.** `a cost-only decline pays no resolution
  term` used a partial index, but `tryIndexAccessPlan` returns `null` for partial indexes —
  the plan under assertion was the plain full scan, not a cost-only plan. Retargeted at a
  real cost-only path (an `IN` above the 1000-seek cap: keeps the `eq` arm's shape at 30.3,
  not the 130.3 a seeking arm would price) and the partial-index fact kept as its own test.
- **`armShape` / `seekingArm` took arguments that never varied**, and both call sites
  repeated the `isRange ? 0.2 : 0.3` index-cost pair. Both helpers now close over the arm's
  own `rows` and index cost, so the pair has one home.
- **A NOTE had gone false.** `sizeRequestFromLiveCount` in `store-module.ts` said a prepared
  statement's stale row count is "harmless while this only moves costs, not plan shape" —
  the comparison makes plan shape depend on `estimatedRows`. Rewritten to state the new fact
  and that it stays performance-only.
- **`addCost` had no test.** Three added to `best-access-plan.spec.ts`: adds to a factory's
  cost, accumulates after `setCost`, and throws when no cost was set (the error path the
  implementation carries).
- **Docs.** `docs/plugins.md`'s `AccessPlanBuilder` surface listing gained `addCost`;
  `docs/module-authoring.md` § *Estimate honestly* gained the two generalizable rules this
  ticket discovered (charge the second read a secondary index implies, and *nothing compares
  your plan with an alternative* — a module must veto its own over-priced seek);
  `packages/quereus-store/README.md`'s seek-shapes section gained a paragraph on the new
  decline and why it is per-index-shape rather than per-query today.

### Tripwires (parked, not filed)

- A vetoed seek is indistinguishable from a decline, and `rule-key-set-seek` abandons its
  rewrite when a probe answer names no index. Harmless while the veto only fires where an
  arm's estimate is the whole table; if real statistics make it fire on tables worth seeking,
  the comparison must exempt any request carrying a runtime-valued set rather than only the
  arm the module happens to pick. `NOTE:` at the comparison site.
- Prepared-statement plan staleness — `NOTE:` in `store-module.ts` (above).
- The `cost <= scanCost` tie branch is arithmetically unreachable with the current constants
  (`0.3 + 1.3⌊0.1N⌋ = N` has no integer solution, likewise for the other arms), so it has no
  test; noted here rather than in code, where the flip-point arithmetic already lives.

### New tickets: none, deliberately

The one major concern — the comparison is near-dead code until per-column statistics exist,
which is the half of the original mispricing this ticket does *not* close — resolves at a site
already claimed by `backlog/debt-store-multi-seek-union-row-estimate`, whose "what done looks
like" names exactly that fix (the store keeping a value distribution and
`BestAccessPlanRequest` carrying it). Per *architecture first*, this is evidence for that
ticket, not a second one. The gap is stated at the `ARM_SELECTIVITY` NOTE where a reader
meets it.

Cost-only index plans still advertising an index arm's cheaper cost while performing a full
scan is pre-existing, out of this diff's scope, and unchanged by it — the comparison routes
around them deliberately. Not filed; it is one arm of the same statistics theme.
