# What landed

Three independent bits of shared plumbing the two micro-benchmark tickets
(`bench-store-micro-keys`, `bench-store-micro-paths`) depend on. No benchmark content —
API surface, a test double, and documentation.

## 1. `ROW_RESOLUTION_BATCH` is a public export of `@quereus/store`

One additive re-export in `packages/quereus-store/src/common/index.ts`, so a caller that
must derive an expected round-trip count reads the constant instead of restating `256`. No
import cycle (`yarn build` clean); `store-table-scan.ts` imports only sibling modules.

## 2. The benchmark harness's single door into `@quereus/store` is wider

`packages/quereus/bench/lib/store-counters.mjs` still holds exactly ONE dynamic import of
the store package. What it resolves grew from three names to ten: the three database
builders, plus `encodeValue`, `encodeCompositeKey`, `decodeCompositeKey`, `buildDataKey`,
`buildIndexKey`, `BUILTIN_KEY_NORMALIZER_RESOLVER`, and `ROW_RESOLUTION_BATCH`.

- `loadStoreKeyApi()` hands the seven key/encoding names to a suite, so no suite needs its
  own `import('@quereus/store')`.
- `openStoreDatabase()` returns `{ db, close, provider }` — additive.
- Every resolved name is shape-checked at import: a function, or a number for the names in
  `NUMERIC_EXPORTS`. A missing constant would otherwise arrive as `undefined` and silently
  size a benchmark to `NaN`; instead it reaches `storeLoadFailure` as a stated skip reason.

## 3. `CountingKVStore` counts writes

Four new counters — `directPutCount`, `directDeleteCount`, `batchWriteCalls`,
`batchOpCount` — alongside the four read ones; `reset()` zeroes all eight, and
`readStoreCounters` surfaces them as `directPuts` / `directDeletes` / `batchWrites` /
`batchOps`.

The structural part: `DelegatingKVStore.batch()` hands back the INNER store's batch, whose
`put`/`delete`/`write` never pass through the wrapper, so `CountingKVStore` overrides
`batch()` to return a module-private `CountingWriteBatch`. Operations are attributed to the
`write()` that carried them, not to the moment they were queued — a batch that is `clear()`ed
or abandoned contributes nothing, and a commit whose inner write throws still counts as a
round trip issued.

# Review findings

Implement diff (`693ce5cbf`) read first, with the handoff consulted afterwards.

## Verified against the implementation

- **`ROW_RESOLUTION_BATCH` reachability and cycles.** Constant declared at
  `store-table-scan.ts:83`, re-exported through `common/index.ts` → `src/index.ts`; resolves
  at runtime through the harness as `256`. `yarn build` clean, so no cycle.
- **Every name `loadStoreModules` resolves actually exists.**
  `BUILTIN_KEY_NORMALIZER_RESOLVER` is the one that could have failed the function-shape
  check by being a plain object — it is an arrow function (`encoding.ts:48`), so it passes.
  Smoke-ran the harness end to end: all seven key-API names resolve, the provider is on the
  plain handle, and a three-row commit reports `batchWrites: 1 / batchOps: 3`.
- **Write-counter attribution.** `write()` snapshots and zeroes `pending` before awaiting
  the inner write, so a failed commit counts once and a reused batch cannot double-count.
  `clear()` drops queued operations. Both behaviors are pinned by the spec.
- **`has()` is a read that is not counted.** Checked whether that understates the read
  block: no `KVStore.has()` call exists anywhere in `packages/quereus-store/src`, so it is
  not a gap. Not filed.
- **The `reset()` conversions the handoff flagged.** All nine `pushdown.spec.ts` sites and
  the one in `key-set-seek-store.spec.ts` zero strictly MORE than they used to, so no
  assertion could be weakened; the two sites (~1496, ~1519) that previously asserted on
  `getManyCalls`/`getManyKeyCount` without zeroing them are now sound rather than
  accidentally correct. `unique-constraints.spec.ts:55` is a class field declaration on an
  unrelated double and is correctly untouched — grep confirms it is the only remaining
  direct-assignment hit in the repo.
- **The shared `NO_WRITES` spread in `bench-store-counters.spec.ts`** does not hide a field
  that should be non-zero: it is used only on read-only doubles, and the two new tests set
  the write fields explicitly and deep-equal the whole entry.
- **Commands.** `yarn build`, `yarn typecheck`, `yarn lint`, `yarn test` (9867 + 1843 +
  the rest, 25 pending, no failures), and `node bench/run.mjs --filter "@store-mem"`
  (19/19 rows, 57.9 s) all pass after the changes below.

## Fixed in this pass (minor)

- **`loadStoreKeyApi` re-projected the seven names into a fresh object** — a second copy of
  the name list, with no shape check on the copy. A name added to `loadStoreModules` but
  missed in the projection would have reached a suite as `undefined`. It now returns the
  resolved bundle itself, narrowed by its declared return type.
- **The key API was typed as bare `Function`.** A suite calling `encodeCompositeKey` got no
  argument or return checking at all — the thing that made this an accessor rather than a
  raw import bought nothing. The typedefs are now `Pick<typeof import('@quereus/store'), …>`,
  and the resolved object is annotated rather than inferred, so a renamed store export fails
  the `yarn lint` type pass as well as the runtime shape check.
- **`packages/quereus-store/README.md` was stale.** Its counting-doubles section still read
  "for asserting on read traffic" and listed only the four read counters — wrong the moment
  the write counters landed. It now covers both sides, the write-attribution rule, and the
  `AtomicBatch` limit. (`docs/benchmarking.md` and `src/testing/index.ts` were updated by
  the implementer; this was the third place and the one that was missed.)
- **`docs/benchmarking.md` explained the one-import-site rule but never said what that site
  hands out.** Added the helper list — `openStoreDatabase()` and its provider,
  `openCountingStoreDatabase()`, `loadStoreKeyApi()` and the read-the-constant rule — so the
  downstream suites widen the door instead of opening a second one.

## Tests added

The implementer's 11 tests cover the counting rules and the flat-commit claim. Two gaps in
the integration block, both now filled in `counting-store-writes.spec.ts` (13 tests total):

- **The delete path through `StoreModule`** — a committed `delete from` is one batch round
  trip carrying one operation per row, with `directDeleteCount` at zero. Previously only
  bench output supported this.
- **One write-side round trip per TOUCHED store** — a table with a secondary index commits
  once on its data store and once on its index store. This is the per-store-fallback claim
  both `docs/benchmarking.md` and the harness header make, and nothing pinned it.

## Tripwire parked (not a ticket)

- **`AtomicBatch` is not counted.** `CountingKVStore` wraps `WriteBatch` only. Dormant
  today — `createCountingProvider` exposes no `beginAtomicBatch`, so the coordinator always
  takes its per-store fallback — and an `AtomicBatch` wrapper nothing exercises would be
  dead weight. Conditional, so it is a `NOTE:` at `CountingKVStore.batch()` rather than a
  ticket: if the counting provider ever gains a shared commit domain, wrap `AtomicBatch` at
  the same time, because until then such a commit would report zero writes rather than fail
  loudly. The handoff raised this and declined to decide; this is the decision.

## Considered and not filed

- **`batchOpCount` counts a same-key supersede as two operations.** Accurate at the call
  boundary and accurate about the physical batch too (LevelDB's chained batch carries both
  queued operations), so not a defect.
- **One-time bench report noise.** Every `@store-mem` row's counter block gained four
  fields, so a comparison against a pre-change results file reports appeared paths on all
  nineteen rows. Correctly stated in the handoff; counter deltas never contribute to the
  exit code and `bench/results/` is gitignored.
- **`loadStoreKeyApi` still has no caller.** Intentional — it exists for the two downstream
  micro tickets. It is now shape-checked at runtime AND type-checked at lint time, which is
  as much cover as it can have before a caller exists.

## Major findings

**None.** Nothing in the diff needed a new `fix/`, `plan/`, or `backlog/` ticket: the
scope was three additive pieces of plumbing, each landed as specified, and every problem
found was small enough to resolve in this pass.
