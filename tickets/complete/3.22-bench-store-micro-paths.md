# What shipped

The `store` benchmark suite went from 11 entries to 25. The original 11 price key encoding
by calling `@quereus/store` functions directly. The 14 new ones each drive one storage hot
path through a real `Database` opened over the store module, and each one's untimed
`counters()` pass **asserts** how many times the engine went to storage — an exact integer,
identical on every machine, where a wall-clock median only describes one CPU:

- `scan-10k` — full scan is one pass over the data store, 10 000 entries, nothing else.
- `point-read-pk` — exactly one single-key read; a point read that became a range scan or
  a one-key batch fails.
- `multi-seek-pk-10`, `multi-seek-pk-over-batch` — IN-list seeks batch into
  `ceil(k / ROW_RESOLUTION_BATCH)` reads carrying k keys.
- `index-resolve-{quarter,one,two,four}-batch(es)` — a secondary-index range of width n
  reads n index entries, then fetches the rows in `ceil(n / B)` batched reads, never a scan.
- `commit-update-{1,10,100,1000}` — committing N queued writes costs a flat number of
  write round trips (one batch per touched store) while the operations inside scale N.
- `index-build-5k` — one pass over the table, one batch carrying 5 000 index entries.
- `catalog-rehydrate-54t` — reopen cost over a database that already holds 54 tables,
  9 indexes and 14 views.

Harness (`bench/lib/store-counters.mjs`) gained `closeDbOnly()`, a `storeModule` handle and
`openStoreDatabase(existingProvider)` so a benchmark can build a schema, drop the database
and reopen over the same storage — the shape catalog rehydration needs.

# Validation

- `yarn bench --filter store/` — 25/25 pass, no skips, ~50 s. Run before and after the
  review edits.
- `yarn bench --filter execution/` — 30/30 pass, ratio guard ok (0.96x). Run because the
  review touched `execution.bench.mjs` too.
- `yarn lint` in `packages/quereus` — clean, exit 0.
- The implement stage additionally ran the full `yarn bench` (71/71) and confirmed the
  counter blocks are byte-identical across two consecutive runs, which was the ticket's
  acceptance criterion.

# Review findings

## Checked and clean

- **Counter blocks read, not just green-lit.** Every assertion was confirmed against the
  actual numbers in the results file rather than trusted because the run passed: full scan
  10 000 iterates and zero of everything else; point read exactly one single-key get; index
  resolve 256 index entries then one batched fetch of 256 keys; all four commit sizes at one
  batch per store carrying N and 2N operations; index build 5 000 table reads and one batch
  of 5 000 index writes. The assertions bite — they are not vacuous.
- **Abandoned per-call modules.** `catalog-rehydrate-54t` deliberately leaves one module per
  timed call unclosed. Confirmed safe: `packages/quereus-store/src` contains no
  `setInterval`, `setTimeout` or `process.on`, so an abandoned in-memory module holds nothing
  that keeps the process alive.
- **Counter identity across a reopen.** The reopen path opens a second module over the first
  one's provider. `createCountingProvider` caches its counted stores by name, so the second
  module reaches the same counters — the numbers survive the reopen rather than restarting
  at zero.
- **Fixture correctness.** The catalog fixture names every column because quereus columns
  default to NOT NULL; the implement stage had already found and fixed that. Re-checked, and
  the rehydration counts are re-asserted on every timed call, so a silently wrong fixture
  could not pass anyway.
- **Lifecycle discipline.** One `close()` per shared provider with `closeDbOnly()` on the
  rest, `readCounters()` refused after close (the provider clears its counted stores there),
  teardown guarded against a setup that threw. All correct.

## Fixed in this pass

- **Two rows claimed an assertion they did not make.** The suite header and
  `docs/benchmarking.md` both said all 14 hot-path rows assert their storage round trips.
  `index-build-5k` and `catalog-rehydrate-54t` asserted none — only an entry count and a
  rehydration result. Rather than weaken the claim, both now assert real ones: the index
  build pins one pass over the table and one batch carrying every entry, and the
  rehydration pins that **no table store is touched at all**, which is the invariant the
  store's own code comments state about reopening (it reads the catalog and one statistics
  record per table, never table storage). The rehydration assertion also refuses to pass
  vacuously if the counter block holds no table stores. Docs and header updated to state
  exactly what is and is not asserted — the reserved `__catalog__` / `__stats__` blocks are
  reported, never pinned, because their counts are a catalog-layout fact.
- **Duplicated helper.** `collect()` — drain an async iterable into an array — was copied
  into both `store.bench.mjs` and `execution.bench.mjs`. Both now use the engine's own
  exported `asyncIterableToArray`.
- **Fixture size restated three times.** The 10 000-row figure appeared as a literal in the
  fixture builder, in `scan-10k`'s expectations, and in the index-resolve width guard. Now
  one `BENCH_T_ROWS` constant, so resizing the fixture cannot leave a stale expectation
  behind.

## Recorded as tripwires (not tickets)

- **Reopening reads statistics one table at a time.** The new benchmark measures exactly 54
  serial single-key reads against the shared statistics store for its 54-table catalog — one
  per table. Free in memory and cheap on LevelDB, but it is one round trip per table on any
  backend where a read is a network or IPC hop. Parked as a `NOTE:` at the site that issues
  them, in `packages/quereus-store/src/common/store-module-schema-sync.ts`, naming the fix
  (collect the keys, issue one batched read) and the condition that would make it worth
  doing. Not filed as a ticket: nothing is wrong today, and the site already documented the
  behaviour neutrally — what it lacked was the measured number and a revisit condition.
- **Suite file size.** `store.bench.mjs` is 1 138 lines (measured with `wc -l`; roughly 600
  code lines, 500 comment, against 150 code lines in the next-largest suite). It is not a
  god-object — 25 independent benchmark factories with no shared mutable state — and
  splitting it is not free: `bench/lib/discover.mjs` names a suite after its file, so two
  files means two suites and every published row name changes. Parked as a `NOTE:` in the
  file header pointing at the split that would preserve the suite name (a `suites/store/`
  directory this file re-exports) and the condition for doing it.

## Noted, no action

- **The rehydration row's counter block lists 63 stores**, 62 of them all-zero table stores
  the fixture opened. Before this pass that was 500 lines of padding in the results file;
  it is now load-bearing, because the new assertion is precisely over those zeros.
- **`store.bench.mjs` is still outside the type-checking pass** — a known gap already tracked
  as `debt-bench-suites-outside-type-pass`. This pass's edits were therefore lint-checked and
  run, but not type-checked. Not re-filed.
- **Several rows are timing-noisy on the run machine** — the three smaller commit sizes and
  the narrower index-resolve widths sit at 20-24% spread and get marked `unstable` from run
  to run. This is the design working as intended: the counter blocks are the stable signal
  and they are identical across runs. Anyone reading the timing table should expect flicker
  on those rows.

## Empty categories

No new bug, fix or plan tickets were filed. Every defect found was small enough to fix in
this pass, and the two remaining concerns are conditional rather than wrong today, so both
became tripwires at their sites. No accepted-tradeoff `NOTE:` at any site touched here had
its revisit condition trip.
