# Drop guard follows column republication (star re-exposure)

`ALTER TABLE … DROP COLUMN` refused only when some body in a rule's reach spelled
the dropped column's name. `create view v as select * from t` spells it nowhere,
so a rule reading `v.x` did not block the drop — and the orphaned assertion then
failed every write to the whole database. The drop guards now consult the same
column-republication lineage `RENAME COLUMN`'s cascade already computes.

## What shipped

**`schema/column-republication.ts`** holds the lineage both verbs share:
`scanShiftedPublishers` (moved verbatim out of the rename cascade) plus
`collectColumnRepublication` — a read-only breadth-first fixpoint that probes
exposure with a sentinel rename on a spine clone. It returns `{ targets,
brokenListed }`: the views / materialized views that republish the column, and
those with an explicit column list over a covering `*`, which a drop breaks
outright because the star's arity changes.

**Both guard families consult it.** `columnProbe` and
`assertNoAssertionNamesColumn` probe each reached body against every target,
targets swept outer and base table first so no existing refusal message moved.
A reach that merely *names* a `brokenListed` object refuses with its own message.

**`buildColumnSourceResolver` answers for views** — explicit column list first,
else the body's published columns, recursing through itself with a per-question
in-flight set. That is what fixes the opposite direction: an unqualified name
binding a view over *another* table no longer false-refuses this table's drop.

**Materialized views are treated exactly like views**, staleness not consulted —
deliberately conservative and stated as such in the docs.

Full design rationale lives in the module doc comments; the behaviours are pinned
by 41.10.2 §31–§36, 41.3 §61, 40.2's strip-under-view section, and the 7-case
`column-republication.spec.ts`.

## Review findings

Diff read first, with fresh eyes, before the handoff summary.

### Major — found and fixed in this pass

**The fix introduced a memory-vs-store behaviour divergence.** Both vtab modules
build their *own* inline `ResolveColumnInSource` — a hand-rolled copy of what
`buildColumnSourceResolver` used to be, blind to views. Widening the shared
builder left those copies stale, and the store module rewrites the catalog's
shared CHECK `Expression` nodes *in place* inside its own hook. So for a CHECK
whose subquery reads a view exposing the renamed name, the engine's walk left the
reference alone and the store module's walk rewrote it — same SQL, two answers,
and under the store backend the table was left unwritable.

Verified: the new 41.3 §61 case passes under `yarn test` and, on the pre-fix tree,
fails under `yarn test:store` with
`CHECK constraint failed: ck_c61 (id < (select max(z) from uv_c61))` — the store
path had rewritten the view-bound `v` to `z`.

Fixed by removing the copies rather than updating them: `buildColumnSourceResolver`
is now exported from the package index (with a comment saying not to hand-roll it),
and both `store-module-alter.ts` and the memory `manager.ts` call it. The schema
differ's `resolveDeclaredColumn` is the one legitimately different answer — it has
no live catalog to ask — and now says so at the site so the next reader does not
"unify" it by mistake.

### Major — found, root-caused, filed

**An alias on a FROM source hides every unqualified column reference under it** →
`fix/4.9-rename-column-scope-walk-blind-to-aliased-sources`. Six verified
reproductions, the sharpest needing no view at all:

```sql
create assertion a1 check (not exists (select 1 from t a where x < 0));
alter table t drop column x;      -- accepted; every write then fails
```

`create view v as select * from t a` is likewise not recognised as a republisher,
so this ticket's own headline case still slips through with an alias added, and
`RENAME COLUMN` leaves such bodies broken from the same site. The alias-qualified
spelling (`a.x`) is handled correctly throughout.

Root cause is one site: `ScopeFrame.unaliased` in `schema/rename/column-rename.ts`
is read as "the sources an unqualified name can bind to", which is what
`realSources` holds. Filed at the representation rung rather than as six point
bugs — the same file already spells the question correctly twice
(`starCoversRenamed`, `resultColumnPublishesName`), so three spellings of one
question is the defect, not any single call. The ticket asks for one named
accessor plus a generalized body-spelling test driving both verbs, which is what
would catch the next instance. The aliased-subquery / CTE residual the implementer
documented is folded in as a separately-scoped second arm, since it needs
recursive column-set inference rather than a representation change.

### Minor — fixed in this pass

- **The rename-side mirror was unpinned.** The implementer flagged that the
  widened scope-awareness (an inner ref binding a view over another table is no
  longer false-captured) had no 41.3 case. Added §61, and negative-checked that it
  actually executes — it is the case that then exposed the store divergence above.
- **Docs overclaimed.** Both `sql-alter.md` § DROP COLUMN and `sql-ddl.md` § 2.6.1
  stated flatly that a star re-exposure blocks the drop. Added the honest
  aliased-source limit to each, naming the tracking ticket.

### Verified correct — no action

- Sweep order: targets-outer / bodies-inner with the seed at index 0 reproduces the
  pre-change first-match exactly, so no existing refusal message moved. Confirmed
  by reading, and by the 41.10.2 / 41.10.x suites staying green unmodified.
- `liveHomePathResolver` matches `snapshotObjectRefResolvers`' rule on all three
  arms (qualified passthrough, home-path scan, home-key fallback), and both
  lowercase through `objectRefKey`.
- `buildColumnSourceResolver`'s recursion is bounded by a per-question in-flight
  set released in `finally`.
- `ViewSchema.columns` / `TableDerivation.columns` hold only the *explicit* list,
  so the listed-object arm is not silently skipping every view.
- `brokenListed` is deduped, transitive, and never also a target.
- No `any`, no swallowed exceptions, no unreleased resources in the diff.
- `docs/schema.md` carries no drop-column guard rules, so leaving it untouched was
  right; `sql-alter.md` and `sql-ddl.md` are the two that do and both were updated.

### Tripwires — none newly parked

The two conditional concerns in this change (the fixpoint running once per guard
entry — three times per drop; and the deliberate absence of a cross-call memo in
the resolver) already carry `NOTE:` comments at their sites from the implement
stage, and both remain genuinely conditional. Nothing to add.

### Considered and declined

- `column-rename.ts` is 1,257 lines, already claimed by
  `backlog/debt-oversized-source-files`. This change added ~10 lines to it and
  removed 97 from the cascade file, so it is not new evidence worth appending.
- The self-qualifier strip's user-visible change (a silently wrong constraint
  becomes a loud plan-time error when a CHECK subquery's FROM is a view exposing
  the same name) is correct, pinned in 40.2, and already covered by the strip's
  documented conservative policy for uncapturable-name frames.
