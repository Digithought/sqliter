# Run a high-latency index-nested-loop join's seeks concurrently - complete

## What shipped

An **index-nested-loop join** (one index seek into the inner table per outer
row) whose seek provably returns at most one row per outer row is now also
offered, inside `ruleJoinPhysicalSelection`'s cost comparison, as a
**one-branch `FanOutLookupJoinNode` in `batched` outer mode**. The fan-out's
existing batched driver (`runFanOutLookupJoinBatched`) keeps many seeks in
flight under a shared budget and re-orders finished rows back into outer order,
so the output is identical to the one-at-a-time plan while a remote module's
round trip is paid once per batch rather than once per row. No runtime code
changed; the driver is reused verbatim.

The pieces:

1. **The at-most-one proof** - `provesAtMostOne(tableSchema, combined)` in
   `index-nested-loop.ts`, exported, with `atMostOne` (plus `rowsPerSeek` and
   `perSeekLatencyMs`, so the caller can re-price without re-probing) on
   `IndexNestedLoopCandidate`. It holds when some enforced key - primary key,
   non-partial UNIQUE constraint, or non-partial UNIQUE index - has every
   column pinned by a deterministic equality whose comparison collation is at
   least as fine as the key's enforcement collation. Key collations come from
   `uniqueEnforcementCollations` (an index's per-column COLLATE for an
   index-derived constraint, else the column's), so a
   `create unique index ... (b collate nocase)` is read as NOCASE-enforced even
   over a BINARY column.
2. **`toBatchedOuter(node, tuning.parallel)`** extracted from
   `rule-fanout-batched-outer.ts` - every gate, the `EagerPrefetchNode` wrap
   and the rebuild; `ruleFanOutBatchedOuter` is a two-line wrapper. Its
   idempotence gate lets the rule re-visit a node the selection rule flipped.
3. **`batchedIndexNestedLoopJoinCost(outerRows, rowsPerSeek, perSeekLatencyMs,
   inFlight)`** in `cost/index.ts`, with `inFlight = min(outerBatchConcurrency,
   maxOuterReadAhead)`. `tryBatchedIndexNestedLoop` in the selection rule builds
   the serial one-branch node (branch = `Filter(ON)` over the rebuilt inner),
   hands it to `toBatchedOuter`, and prices the result only if it came back.
   Two new candidates: `index-nl-batched` after `index-nl`,
   `index-nl-mirrored-batched` after `index-nl-mirrored`, all strict `<`.

**Inert in-tree by construction:** at `perSeekLatencyMs === 0` the selection
rule does not even build the node, so the golden-plan sweep is unchanged.

## Review findings

### Read first, summary second

The implement diff (`db919217e`) was read end to end - both planner rules, the
cost function, the runtime doc comment, the tuning comments, both specs, both
docs files - before the handoff summary, and the surrounding machinery it leans
on was read too: `shared/access-leaf.ts`, `probeModule` /
`reapplyDeclinedPushed` / `resolvePairs`, `rule-select-access-path`'s collation
and reattach paths, `constraint-extractor`'s covered-key gates,
`schema/unique-enforcement.ts`, `planner/type-utils.ts`,
`join-utils.buildJoinAttributes`, `FanOutLookupJoinNode`, and both fan-out
drivers in `runtime/emit/fanout-lookup-join.ts`.

### What was checked and held

- **The proof lifts from the leaf to the whole rebuilt inner.**
  `peelToSeekableAccessLeaf` admits only Alias, trivial Project and Filter
  between the chain root and the leaf, all row-preserving, so "at most one row
  from the leaf" really is "at most one row from `newInner`".
- **Index spaces line up.** The constraint `columnIndex`, `seekColumnIndexes`,
  `primaryKeyDefinition[].index`, `uc.columns` and `index.columns[].index` are
  all indices into `tableSchema.columns`. Nothing compares an output position
  against a schema position.
- **NULL keys cannot produce a second match**, which matters because the proof
  deliberately does *not* require the key columns to be NOT NULL (SQL UNIQUE
  permits many NULLs). `col = NULL` is UNKNOWN; a dynamic NULL seek key is
  caught by the scan layer's `seekKeyHasNull` guard; and the branch counts rows
  *after* `Filter(ON)`, so even an over-fetching seek cannot hand the
  `atMostOne-*` mode a second row. This was the one leg of the proof with no
  test - see the fix list.
- **The priced in-flight count is the one that actually runs.**
  `emitFanOutLookupJoin` ignores `concurrencyCap` in batched mode and drives
  `runFanOutLookupJoinBatched` with `globalCap = outerBatchConcurrency` and
  `readAhead = deriveReadAhead(globalCap, 1, maxOuterReadAhead)`, so the
  planner's `min(16, 64) = 16` is real. (Had the driver used `concurrencyCap`,
  which the rule sets to 1, the feature would have priced a win and executed
  serially - the sharpest thing in the diff to try to disprove.)
- **The docs' magnitudes re-derive.** From the shipped constants at 20,000
  outer rows, one row per seek and `expectedLatencyMs = 25`: serial index-NL
  536,000 vs hash `16,000 + 0.4N + 25` crosses at N ~ 1.30 M; batched 67,250
  crosses at N ~ 128,000. Both match the doc's stated figures and its stated
  method (evaluated from the formulas, not benchmarked).
- **Attribute layout.** `buildJoinAttributes` nullable-widens the right side for
  a LEFT join, so pinning `node.getAttributes()` on the un-mirrored fan-out is
  exact rather than approximately right; the mirrored orientation's derived
  `[...right, ...leftRebuilt]` matches what `rebuildWithMirroredNL` produces.
  `mayMirrorIndexNestedLoop` is inner-join-only, so the mirrored candidate's
  hard-coded `'inner'` cannot be reached with a LEFT join.
- **Side-effect gating covers the ON condition.** The branch spec's
  `concurrencySafe: inner.physical.concurrencySafe !== false` reads the inner
  only, but `toBatchedOuter` runs `PlanNodeCharacteristics.isConcurrencySafe`
  over the branch *child* - the `Filter(ON)` - so a side-effecting ON condition
  declines the flip rather than being run concurrently.
- **Seek-predicate vs ON-condition collation.** The rule seeks on a synthesized
  `innerCol = outerCol` while the user may have spelled `outerCol = innerCol`.
  Not a hazard: `effectiveComparisonCollation` is symmetric and raises on a
  same-rank declared conflict, so the two spellings cannot resolve differently.
- **Cross-type equality over a TEXT unique key** (the handoff's open question):
  `=` and UNIQUE enforcement both route through `compareSqlValuesFast` under the
  same collation, and semantic-ordering types are excluded upstream by
  `resolvePairs`' own gate - so the comparison cannot be coarser than the key's.
  Closed, not carried forward.

### Fixed in this pass

- **An unsafe default inside the proof.** `equalityRefinesKey` called
  `effectivePredicateCollation`, which answers `'BINARY'` for any constraint
  source shape it does not recognize. That is a *safe decline* for its original
  caller (a BINARY-read predicate over a coarser index over-fetches and keeps a
  residual Filter), but BINARY is the *strongest* claim in the proof - it
  refines every collation - so an unrecognized `=` producer would have been
  proved unique on a default. Unreachable today (every `op: '='` constraint is
  minted by `extractBinaryConstraint` carrying its `BinaryOpNode`), so this was
  a dormant soundness hole rather than a live bug. Fixed by requiring a real
  comparison node: `equalityRefinesKey` declines any other shape.
- **A fourth copy of the same collation test (DRY).** The new
  `equalityRefinesKey` restated a two-name refinement test that already existed
  three times - `coveringMvHonorsIndexCollation`
  (`schema/unique-enforcement.ts`), `equalityConstraintCollationOk` /
  `inConstraintCollationOk` (`analysis/constraint-extractor.ts`) and
  `enforcementCollationCoversDeclared` (`planner/type-utils.ts`) - each written
  in its own direction. Extracted one exported `collationRefines(finer, coarser)`
  into `util/comparison.ts` and routed all four through it; each site's own doc
  now names the direction and defers the test. Every substitution is
  behaviour-identical, including the one asymmetric case
  (`equalityConstraintCollationOk` admits a BINARY comparison whose column side
  cannot be identified - preserved explicitly rather than folded away).
- **The proof's premise, argued -> cited.** The handoff asked whether a cheap
  assertion belonged at the construction site to protect the invariant "every
  constraint in `combined` is enforced somewhere in the rebuilt inner". No
  assertion is needed: the invariant is *total* for equalities by construction.
  A pushed constraint is either module-declined, and `reapplyDeclinedPushed`
  re-applies every declined one, or module-handled, and a handled one is either
  consumed into the seek's bounds or recovered by
  `reattachUnconsumedConstraints` - whose `RECLAIMABLE_OPS` set contains `'='`,
  so no equality can fall through it; join-key leftovers are covered by the
  retained ON condition. The doc comment now cites that chain instead of
  asserting the conclusion.
- **The one untested leg of the proof.** Added
  `a nullable UNIQUE inner key holding several NULL rows` to
  `test/optimizer/index-nested-loop-batched.spec.ts`: a high-latency inner with
  a nullable UNIQUE text column holding two NULL rows, joined on a NULL-bearing
  outer key. Asserts the candidate still forms (`atMostOne-left`) and that
  execution matches no stored NULL row - the failure mode being a runtime
  `CONSTRAINT` error, i.e. a working query turned into an error rather than a
  wrong answer.

### Considered and declined

- **Splitting the proof out of `index-nested-loop.ts`.** The file is 749 lines
  (`wc -l`), in band for its neighbours - `rule-fanout-lookup-join.ts` 690,
  `rule-semijoin-existence-recovery.ts` 618, `rule-select-access-path.ts` 1624.
  Moving ~120 lines would be churn without a size problem to solve.
- **`FanOutLookupJoinNode.getType()` returns `keys: []`**, so a join whose keys
  the `JoinNode` would have propagated loses them when this rule picks the
  fan-out. Not filed: the node documents this as deliberate v1 conservatism
  ("Key/FD propagation is conservative"), it costs downstream optimization
  precision only - never correctness - and it is the fan-out node's decision,
  not this ticket's.
