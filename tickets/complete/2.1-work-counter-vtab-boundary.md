# What shipped

`WorkCounterSnapshot` gained a `tables` block plus three matching totals:

```ts
tables: Record<string, {          // key: lowercased `<schema>.<table>`, keys sorted
	queryCalls: number;           // query() calls the engine issued
	rowsScanned: number;          // rows the engine pulled out of them
	updateCalls: number;          // update() calls — insert, update, delete alike
}>;
totals: { ..., queryCalls, rowsScanned, updateCalls };
```

Counted at engine-owned call sites rather than inside modules, so the numbers work for
the memory module, the store module, the isolation wrapper and any third-party module
with no interface change:

- `runtime/emit/scan.ts` — one `queryCalls` per `vtabInstance.query()` call, one
  `rowsScanned` per row pulled from it. One door for `SeqScan`, `IndexScan`, `IndexSeek`
  (`key-set-semi-join.ts` and `ordinal-slice.ts` both route their leaf through it).
- `runtime/emit/dml-executor.ts` — one `updateCalls` per `vtab.update()`, at all four
  sites (insert, the UPSERT `do update` arm, update, delete).

`TableWorkCounters` is exported from the package root alongside `WorkCounterSnapshot`.

## The distinction to hold onto

These measure the **engine-to-module** boundary, not the **module-to-storage** boundary.
A module that swaps 1000 single-key reads for one batched multi-key read moves neither
number — the engine issued the same one `query()` either way. That deeper layer is the
counting key-value store double in `@quereus/store/testing`. Two layers, two instruments;
documented in `docs/runtime.md` and `docs/usage.md`.

Observed values on a 5-row table `t` (metrics on, statement fully drained):

| Statement | `main.t` |
| --- | --- |
| `select a, b from t` | `{queryCalls: 1, rowsScanned: 5, updateCalls: 0}` |
| `select a, b from t where a = 3` (PK seek) | `{1, 1, 0}` |
| `select a from t where b = 10` (no index) | `{1, 5, 0}` — filter's `out` is 2 |
| self-join on `t` | `{2, 10, 0}` — two sites, ONE entry |
| correlated subquery with `limit 1` (undecorrelated) | `queryCalls: 6` = 1 + 5 |
| same shape without `limit 1` (decorrelated) | `queryCalls: 2` — constant |
| `update t set b = b + 0` | `{1, 5, 5}` |
| `insert … on conflict do update` | `updateCalls: 2` (attempt + arm) |

The decorrelated-vs-not pair is the point: the row count barely moves while the call
count goes 2 → 6. That is the N+1 signal this block exists for.

# Review findings

## Fixed in this pass

- **An all-zero table entry appeared for a scan that never called `query()`.**
  `scan.ts` resolved the counter cell at the top of the scan generator, before the
  module connect. A connect that threw therefore minted a `{0, 0, 0}` entry —
  contradicting the rule the rest of the snapshot follows, and that this ticket's own
  docs state, that an absent entry and a zeroed one are different claims. Moved the
  resolution to immediately after a `query()` call that returned, so an entry exists
  exactly when `queryCalls >= 1`. The new test (`leaves no all-zero entry for a table
  the engine never got to call`) was verified to FAIL against the pre-fix code before
  being kept, so it is a real guard rather than a passing assertion.

- **Two claims about the rename path were wrong, and a whole class of table access was
  silently uncounted.** `RuntimeContext.tableNameRemap` is written in exactly one place
  — `runtime/deferred-constraint-queue.ts` `runDeferredRows` — and that method builds
  its own `RuntimeContext` with no `workCounters` field. Two consequences the handoff
  missed:
  - The effective-name (post-rename) counter key is **unreachable today**, not merely
    untested. The handoff listed "the rename path has no test" as a gap and described
    the fixture that would reach it; no fixture can, because the only context that sets
    the remap has no collector to report to.
  - Every table read a **deferred CHECK constraint** performs is invisible to these
    counters — the same shape as the already-documented `ANALYZE` gap, but undocumented.

  Resolution: no code change (the remap arm is correct, costs nothing when metrics are
  off, and is what that context would need if it ever gains a collector). Instead the
  `docs/runtime.md` sentence asserting post-rename keying as live behaviour was removed,
  the deferred-constraint gap was added beside `ANALYZE` under **Not counted**, and a
  `NOTE:` at each counter site records why the arm is dormant — including that
  `dml-executor.ts`'s key would need the same remap treatment if it ever activates,
  since it currently keys by the emitted name only.

- **Coverage added** to `work-counter-tables.spec.ts` (17 → 20 tests): a mixed-case
  table name produces one lowercased canonical key; re-executing a prepared statement
  reports one execution rather than the running sum across executions (a fresh collector
  per execution — without this a benchmark that warms up before measuring would read
  inflated counts); plus the failing-connect case above.

## Recorded as tripwires, not tickets

- **Engine/module tally agreement is drain-dependent.** The counting module's `query()`
  is an async generator, so it records a call on the first row pulled, while the engine
  increments at the call itself. A test that stops a scan early (`limit 0`, an immediate
  `break`) will see the engine one ahead of the module. Not a defect in either — the
  engine did issue the call — but a trap for the next test author. `NOTE:` in
  `packages/quereus/test/runtime/counting-vtab.ts`.

## Checked and clean — no finding

- **Call-site completeness.** Grep over `packages/quereus/src` for vtab `query`/`update`
  invocations finds exactly two query doors (`runtime/emit/scan.ts`, and
  `planner/stats/analyze.ts` which is documented as uncounted) and four update sites,
  all four instrumented. `key-set-semi-join.ts` and `ordinal-slice.ts` emit their leaf
  through `emitSeqScan`, so their access is counted through the same door. No table
  access bypasses the instrumented sites.
- **Zero cost when metrics are off** holds structurally: `runtimeCtx.workCounters?.tableCounters(...)`
  short-circuits the entire chain, so neither the key ternary nor the fallback template
  string is evaluated when the collector is absent. This is a structural argument, not a
  measurement — see the deferral below.
- **`ctx` shadowing at the four `countUpdateCall` sites.** All four enclosing functions
  declare their own `ctx`/`rctx` of type `RuntimeContext`, so none accidentally passes
  the emitter's `EmissionContext`. Verified by reading each signature, not just by the
  fact that it compiles.
- **Fork/parallel behaviour.** `parallel-driver.ts` propagates the collector by
  reference (fork policy `shared-sink`), so counts from forked branches roll up with no
  merge step and cannot double-count.
- **Snapshot immutability.** `snapshot()` copies each table cell by value and sorts keys,
  so a held snapshot never mutates and two snapshots of one execution serialize
  identically. Pinned by the JSON round-trip and stability tests.
- **The counting-module extraction** out of `nlj-inner-connection-reuse.spec.ts` into
  `counting-vtab.ts` is the right call — the alternative was duplicating ~120 lines. Its
  `update()` now echoes the written row back; no NLJ test does DML against it and that
  spec still passes unchanged.
- **The loose partial-drain assertion** (`limit 2` gives `rowsScanned` in [2, 5)) is
  correct as written: pinning the exact 3 would test the scheduler's pull order rather
  than the counter. Agreed with the implementer's reasoning; left alone.
- **Source hygiene.** `scan.ts` is 254 lines, `work-counters.ts` 317 — both well inside
  normal range for this codebase. Comment density in `scan.ts` is high, but every block
  carries a non-obvious invariant (why the counter cell is minted at the call site, why
  the row count is in the loop body and not the `finally`, why the connect cache key is
  per-site).
