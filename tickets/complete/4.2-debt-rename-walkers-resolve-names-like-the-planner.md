# What shipped

Every rename/probe walker (`renameTableInAst`, `tableReferencedInAst`,
`renameColumnInAst`, `renameColumnInCheckExpression`, both column probes, all
six collection helpers) takes a `ResolveObjectRef` callback plus a `targetKey`
(`objectRefKey(schema, name)` — canonical lowercase `<schema>.<name>`) instead
of a `defaultSchemaName`. A reference matches when its resolution equals the
target key. `schemaMatches` is gone.

Two resolver builders:

- `snapshotObjectRefResolvers(db)` / `buildObjectRefResolver(db, homeSchema)`
  (new `schema/object-ref-resolver.ts`): qualified names pass through;
  unqualified names resolve through `db._homeSchemaPath(home)` against a
  **name-set snapshot of the catalog taken at build time**; a miss everywhere
  falls back to the home schema's key so probe/rewrite stay total. Snapshot
  (not live lookup) is load-bearing — propagation runs after the catalog swap.
- `singleSchemaObjectRefResolver(schemaName)` for the schema differ's declared
  world, which is single-schema by construction.

Every call site builds its resolver before the statement's first catalog
mutation and threads it through.

Second arm: `rewriteTableForTableRename` no longer hand-rolls the CHECK /
index-predicate / column-expression loops — it calls the same
`renameTableIn{CheckConstraints,IndexPredicates,ColumnExpressions}` helpers
the store module's catalog rewrite calls.

## Behavior changes

- **False negative fixed**: a CHECK / column DEFAULT / generated expression in
  any schema naming `temp.t` explicitly now follows `alter table temp.t rename
  …` (both verbs).
- **False positive fixed**: a bare `t` that resolves to `main.t` no longer
  follows a rename of `temp.t`, and vice versa — including through unaliased
  cross-schema FROM sources and aliases.
- Column walker's qualified-ref resolution is a unified innermost-first
  binding walk (`resolveQualifierBinding`); row image (`new.` / `old.`) is
  consulted only for unbound qualifiers.
- DML targets in the column walker (INSERT/UPDATE) respect the statement's own
  WITH clause.

## Validation

`yarn build`, `yarn lint`, `yarn test` — all green (8802 quereus tests + all
other workspaces, 0 failing).

# Review findings

Reviewed the implement diff (21 files) before reading the handoff summary.

## Checked and clean — nothing found

- **Snapshot discipline at every call site.** Traced all nine resolver builds
  (`runRenameTable`, `runRenameColumn`, three DROP-COLUMN guards, the assertion
  drop guard, the memory module's `renameColumn`, the store module's
  `renameTable` and `renameColumn`) against the first catalog mutation on each
  path. All are pre-mutation. The one that reuses a snapshot across a
  forward/reverse pair had a wrong comment — see below.
- **Collapse of `rewriteTableForTableRename` onto the shared helpers.** The
  dropped per-item `{...cc}` / `{...idx}` copies and the `Object.freeze` on
  those two arrays are genuinely inert: `assertRenameDependentsPersistable`
  probes a `cloneTableRewritableAsts` copy, so the pre-flight never touches
  live ASTs, and the `changed` flag (not array identity) is what re-registers
  the table. Verified in `schema/catalog-persistability.ts`.
- **Scope-frame rework in the column walker.** Walked `ScopeFrame.unaliased`
  Set→Map, `resolveQualifierBinding`'s innermost-first order, the row-image
  ordering change, `isQualifierReboundAboveSeed`, `frameBindsTargetUnaliased`,
  and `isResultColumnExposure`. Two silent improvements over the old code that
  the handoff did not claim: an exposing CTE now keys `unaliased` by the CTE's
  name rather than the renamed table's, so `isQualifierReboundAboveSeed` no
  longer reports a spurious rebind of `new`/`old`; and an UPDATE/DELETE target
  in another schema no longer binds as the renamed table.
- **Differ parity.** `singleSchemaObjectRefResolver` reproduces the old
  `schemaMatches` equality exactly for a single-schema declared world, and
  matches the CHECK/DEFAULT planner rule (owning schema only) precisely.
- **`self-qualifier-strip.ts` keeping `defaultSchemaName`** is correct, not an
  oversight: it walks CHECK expressions only, and a CHECK plans under the
  owning schema alone.
- No new resource handles, subscriptions, or catch-and-swallow paths; no `any`;
  no inline `import()`. `object-ref-resolver.ts` is ~100 lines including its
  doc block — no size concern.

## Found and fixed in this pass (minor)

- **`docs/sql-alter.md` was never updated for the behavior change** (the diff
  touched no docs). Added a paragraph stating the actual resolution rule —
  qualified means what it says, unqualified resolves against the body owner's
  home schema path over a pre-statement snapshot, foreign keys always mean the
  child table's own schema — with the `main.t` / `temp.t` worked example.
  Also corrected line 21, which claimed cross-schema table dependents "are
  unaffected because they are walked across every schema": they were walked
  but never matched; that is precisely what this change fixed.
- **Over-stated planner-parity claim on `snapshotObjectRefResolvers`.** The
  resolver uses `Database._homeSchemaPath` for every body kind. That is exact
  for view bodies, MV bodies and assertion checks, but a CHECK constraint and a
  column DEFAULT / generated expression plan under
  `planner/building/schema-authored-context.ts` — the owning schema and nothing
  else, no session-path fallthrough. The two rules can only disagree when the
  home schema lacks the name, and such a CHECK/DEFAULT cannot be evaluated by
  the planner at all, so no valid body is matched or missed differently — the
  divergence is safe, but the comment claimed exactness. Replaced with a `NOTE:`
  stating the real rule, why it is inert, and the condition for tightening.
- **Factually wrong comment on the store module's reverse pass**
  (`store-module-rename.ts`). It claimed the new name "resolves nowhere in the
  snapshot, so the resolver's miss→home fallback keys it under this schema".
  That holds only while no other schema on the home path already has an object
  called `newName`; when one does, the bare name resolves there, the reverse
  walk matches nothing, and a rollback leaves a self-reference spelled with the
  new name. Comment replaced with an accurate statement of the residual — see
  the declined-finding note below for why the behavior itself is left alone.
- **Open-coded inverse of `objectRefKey`.** `column-rename.ts` recovered the
  schema half of a key with `key.slice(0, key.length - name.length - 1)`,
  putting knowledge of the key format in a second file. Extracted
  `objectRefKeySchema` next to `objectRefKey` in `rename/shared.ts`.
- **Dead ticket slug in five comments.** `bug-rename-not-propagated-across-schemas`
  was absorbed into `bug-schema-object-dependency-tracking` during garden
  cleanup; four source comments and a test header still pointed a reader at a
  slug that is nowhere on the board. Repointed. (Only one of the five was in
  this diff; the rest were adjacent and cost nothing to fix.)
- **Test gaps for the deltas the handoff itself flagged as reviewer-worthy but
  did not cover.** Added seven tests to
  `test/schema/rename-cross-schema.spec.ts`: a FROM alias on another schema's
  same-named table not following the rename; an inner unaliased cross-schema
  source winning over the outer same-named renamed table, and the converse
  (the same shape *does* follow when the inner source is the renamed table);
  and four DML-target cases — INSERT and UPDATE targets named by the
  statement's own WITH, an INSERT target that really is the renamed table, and
  an UPDATE target in another schema.

## Found and deliberately not filed

- The store reverse-pass gap above is a **new instance of a class already
  declined at that exact site**: the file carries three `NOTE:` blocks stating
  that the reverse pass is approximate, that closing it needs a per-walk
  changed-set threaded through every arm, and that this is "not worth it for a
  failed-persist-only path". Same site, same fix, same rationale, and the
  stated revisit condition has not tripped. Recorded as a fourth residual
  `NOTE:` at the site rather than as a ticket.

## Tripwires (recorded at the site, not filed)

- Resolver-vs-planner path divergence for CHECK / DEFAULT bodies — `NOTE:` in
  `schema/object-ref-resolver.ts`, with the condition that would make it real
  (a rename needing to be right about a body the planner itself rejects).
- Snapshot cost — the implementer's existing `NOTE:` in the same file already
  covers it. Worth knowing that a single `ALTER … DROP COLUMN` now builds three
  independent snapshots (one per guard); same order of magnitude, same fix
  (snapshot lazily per consulted schema) if it ever shows up hot.

## Known gaps carried forward

- **Full `yarn test:store` was not run.** It exceeds the agent's 10-minute
  command budget; unchanged from the implement stage. This review's own source
  changes to `quereus-store` are comment-only, so the risk is no higher than
  what the implement stage already measured with its targeted store subsets
  (ALTER / schema / declarative / rename suites, all passing).
- View / MV / assertion propagation loops remain gated to the renamed object's
  own schema. The resolver and target key are already threaded through them, so
  widening the loops is the remaining work — tracked by
  `bug-schema-object-dependency-tracking` (in `plan/`). The added test
  `the same inner source DOES follow when it is the renamed table` documents
  this boundary explicitly: it puts the view in the renamed table's schema
  because a `main`-owned view naming `temp.t` is not reached at all.
- Subquery / function-source aliases are still not recorded in the column
  walker's scope frames — pre-existing, documented on `resolveQualifierBinding`.
