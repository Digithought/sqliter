# Two UNIQUE constraints may not derive one backing structure name

## What was wrong

Every `UNIQUE` rule is enforced through a hidden backing structure whose name is the
constraint's own name when it has one, and `_uc_<covered column names joined by _>` when
it does not. Nothing stopped two rules on one table deriving the *same* name:

```sql
-- 1. a constraint name written with the engine's reserved `_uc_` prefix
create table t (id integer primary key, c integer, b integer,
                constraint _uc_c unique (b), unique (c));        -- both derive `_uc_c`

-- 2. no reserved prefix — the `_`-joined auto-name colliding on ordinary names
create table t (id integer primary key, a_b integer, a integer, b integer,
                unique (a_b), unique (a, b));                    -- both derive `_uc_a_b`
```

On the memory backend the second constraint adopted the first's structure and was then
enforced by one keyed on the *other* constraint's columns — silently accepting duplicates
it should reject. `ALTER TABLE` already refused the same declaration, but only on memory
and only by accident (the guard compared against `tableSchema.indexes`, where the memory
module happens to materialize a constraint's structure and the store module does not).

## What changed

**`schema/catalog.ts`** — a constraint-side twin of the existing index-side search:

- `findUniqueConstraintSharingBackingName(tableSchema, constraintName, columnNames)`
  searches `tableSchema.uniqueConstraints` (which *both* backends carry) for a constraint
  whose own derived structure name case-folds equal to the prospective one. Skips
  `derivedFromIndex` constraints — their structure *is* the `CREATE UNIQUE INDEX` that
  synthesized them, already compared by the index arm.
- `assertUniqueConstraintIndexNameFree` runs that arm **before** the `.indexes` arm, so a
  collision both arms can see reports identically on memory and store. Existing message
  (`would collide with existing index '<name>'`) is byte-unchanged for index collisions.
- `assertUniqueConstraintBackingNamesDistinct(declared, operation)` is the pairwise form
  for callers holding a whole declaration with no table to compare against;
  `assertNoDuplicateUniqueConstraintBackingNames(constraints, columns, operation)` is the
  built-constraint wrapper over it. `DeclaredUniqueConstraint` is the shared shape they
  take (`{ name?, columnNames }`).

**`schema/manager.ts` `createTable`** — calls the wrapper immediately after
`assertNoDuplicateUniqueConstraints` (so a genuine duplicate keeps its constraint-worded
message) and before `module.create` (so a refusal leaves no storage behind). Not on
`importTable` / `importDDL`.

**`runtime/emit/alter-table.ts` `runAddColumn`** — two inline `unique` constraints on one
*new* column can derive one name without duplicating each other
(`add column c text constraint _uc_c unique unique`), and neither is on the table yet, so
no per-constraint check could see the pair. The pairwise form runs once after the existing
per-constraint loop (after, so a plain duplicate still reports as a duplicate).

### Messages

```
Cannot <op>: its backing structure '<name>' would collide with the backing structure
of the UNIQUE constraint <other> on the same table. Name or rename one of the two
constraints — an unnamed one derives its structure name from the columns it covers.

Cannot <op>: the UNIQUE constraint <a> and the UNIQUE constraint <b> both derive
backing structure name '<name>'. Name or rename one of them — an unnamed one derives
its structure name from the columns it covers.
```

`<other>` / `<a>` / `<b>` name each side the way the user wrote it — `'<name>'` when
named, `on (<cols>)` when not.

### Checked and correct — no finding

- **Guard coverage is complete over the paths that can move a derived name.**
  Walked every one: `CREATE TABLE`, `ADD CONSTRAINT`, `ADD COLUMN … unique` (both against
  the table and pairwise within the statement), `RENAME CONSTRAINT`, `RENAME COLUMN`,
  `CREATE UNIQUE INDEX` (refused from the index side by `isImplicitCoveringIndex`), and
  the statements `apply schema` emits. `DROP COLUMN` cannot produce a collision — a UNIQUE
  spanning the dropped column is removed outright and a survivor keeps its whole column
  set, so no derived name changes. `ALTER PRIMARY KEY` and the tag arms change no name.
- **Ordering is right at every call site.** Duplicate-constraint guards run before the
  structure-name guards (a genuine duplicate keeps its constraint-worded message), and
  every guard runs ahead of `module.create` / `module.alterTable` (a refusal persists
  nothing). Confirmed by reading each site, not just the comments.
- **The constraint-arm-first ordering causes no message regression.** A collision only the
  index arm can explain (a real user index holding the name) still produces the old
  `would collide with existing index '<name>'` text — re-confirmed by the full suite,
  which carries those assertions, on both backends.
- **`RENAME COLUMN` self-comparison and cross-comparison hold.** The renamed constraint is
  in the searched set under its pre-rename name; a non-case-only rename always changes the
  joined name at the renamed position, and case-only renames return early. Two constraints
  both covering the renamed column can only produce equal post-rename names when they
  cover the same column *set*, which the duplicate guard already refuses. Worked through
  the string algebra rather than taking the doc comment's word for it.
- **`derivedFromIndex` skip is proven by test, not asserted.** §11g refuses a declaration
  onto such a name with the *index* message, which is only reachable if the constraint arm
  skipped it.

### Found and fixed in this pass (minor)

- **`docs/sql-alter.md` was never updated and is the ALTER reference.** Four passages
  described the UNIQUE backing-structure name as needing to be free only of an *index*:
  the `RENAME COLUMN` paragraph, the `ADD COLUMN` UNIQUE bullet, the `ADD CONSTRAINT`
  bullet, and the `RENAME CONSTRAINT` bullet. All four now state the constraint-vs-
  constraint half too, and the `ADD COLUMN` bullet names the within-statement pairwise
  case. (`docs/schema.md` and `docs/sql-ddl.md` were correct as landed.)
- **Both new messages advised an action one side may not have.** "Rename the constraint" /
  "Rename one of them" is not performable when the colliding constraint is unnamed — the
  fix there is to *name* it. Both messages now say so. No assertion depended on the
  changed clause; the asserted prefixes are unchanged.
- **`_uc_<cols>` has a third out-of-package mirror the docs did not name.**
  `quereus-isolation`'s `installOverlayUniqueConstraint` spells the rule inline (it names
  the overlay's narrowed unique index so DROP / RENAME CONSTRAINT forwards resolve), so
  the "must stay equal to it" set in `implicitIndexNameForColumns`'s doc comment and in
  `docs/schema.md` was incomplete — a future change to the naming rule would have missed
  it. Both now list all three.
- **`ensureUniqueConstraintIndexes`'s adoption comment went stale.** It claimed the only
  producer of a held name was a duplicate unnamed UNIQUE and described the degradation as
  double enforcement. It now names both producers and both degradations — for the
  derived-name collision, adoption means enforcement under the *other* constraint's key,
  which is the defect this ticket closes.
- **DRY / readability in the new code.** The `{ name?, columnNames }` shape was spelled
  three times inline; extracted as the exported `DeclaredUniqueConstraint` interface.
  `runAddColumn` filtered the inline constraints and re-derived their column names twice
  (once in the per-constraint loop, once for the pairwise call); hoisted to one
  `inlineUniques` array used by both.
- **Test gap: the `CREATE TABLE` twin of the tested `ADD COLUMN` case.** Two inline
  `unique` constraints on one column (`c integer constraint _uc_cn_c unique unique`) is a
  pure within-declaration collision with no table to compare against — the same shape
  §11d pins for `ADD COLUMN`, unpinned for `CREATE TABLE`. Added to §11a with the
  no-table-left-behind assertion. Passes on both backends.
- **Added invariant `SCH-005 — One table, one backing structure name`** to
  `docs/invariants.md`, beside `SCH-001` (which explicitly excludes implicit covering
  structures from the schema-wide index-name guarantee and so left the per-table half
  unstated). The rule is now complete enough to be normative text, and the register
  machine-checks its code/guard/doc pointers on every `yarn docs:check`.

### Found and not fixed — no ticket, with reasons

- **The `_uc_<cols>` name rule stays ambiguous by construction** (`(a_b)` and `(a, b)`
  derive one name). Disambiguating it would break every persisted catalog that already
  carries the name and all three out-of-package mirrors; refusing the collision is the
  correct trade and is what landed. Not a defect, not a ticket.
- **Legacy-catalog reopen is pinned store-side only.** The memory module cannot rehydrate
  a table it never created (`importCatalog` fails in `module.connect` before any of this
  code runs), so the memory half is unreachable rather than untested. Verified by reading
  the import path, not just by trusting the handoff note.
- **`apply schema` is pinned for the `CREATE TABLE` arm only** (§12). The differ emits
  ordinary `ALTER TABLE …` statements through the same pipeline the §11c–11f cases already
  cover, so an ALTER-arm apply-schema case would re-test the pipeline, not the guard.
  Deliberate omission, stated here rather than left silent.

### Tripwires recorded (conditional — not tickets)

- **The legacy-catalog store test rewrites the persisted bundle by regex.** It is brittle
  against DDL-generator format drift, but asserts the rewrite actually changed the text, so
  drift fails loudly instead of silently passing. Left as-is; the assertion is the
  tripwire. Noted in the test's own comment.
- **Partial UNIQUE constraints are covered only through the index arm.** A *declared*
  `UNIQUE` is never partial (`AST.TableConstraint` carries no predicate field), so every
  partial UNIQUE today is `derivedFromIndex` and owns its index. The constraint arm already
  handles a declared partial correctly (it compares names, not rules), but nothing pins
  that. Recorded in the existing doc comment on `findUniqueConstraintSharingBackingName`;
  becomes work only if a declared partial UNIQUE ever becomes expressible.
