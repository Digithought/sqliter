# Complete: batched row fetches behind secondary-index scans

## What shipped

One mechanism in `store-table-scan.ts`, split producer/consumer, serving all three
index-backed scan arms:

- **`ROW_RESOLUTION_BATCH = 256`** (exported) — index entries per row-resolution batch,
  matching `paged-iterate.ts`'s `DEFAULT_BATCH_SIZE`. This is the caller-side bound
  `KVStore.getMany`'s "bounded by the caller" note already referred to.
- **`produceIndexEntries`** walks one byte window via `iterateEffective`
  (read-your-own-writes merge, index-key order) and yields each surviving entry's data key
  plus its window's `FilterInfo` list. Entry-only defenses live here: the zero-length
  legacy-value skip, and the multi-seek `seen` pre-check.
- **`resolveIndexEntries` / `resolveRowBatch`** collect up to 256 entries and resolve them
  with one `readEffectiveRowsByKeys` (pending overlay applied before the store batch,
  positional nulls), then in entry order skip null rows, re-check `seen` (catches a
  duplicate *inside* one batch, which the pre-check cannot see), accept on a match against
  any of the entry's `FilterInfo`s, and add to `seen` on yield only.
- **`scanIndex`** = the consumer over one window's producer.
- **`scanMultiSeek`** = the same consumer over the concatenation of every disjoint
  window's producer, so batches are bounded by entry count rather than window count and a
  hundred single-row windows collapse into one round trip. The old
  `MultiSeekWindowContext` parameter and interface are gone, replaced by
  `PendingIndexEntry`.
- **`scanMultiSeekPrimary`** = bounded slices over its sorted, deduplicated point-key list,
  one `readEffectiveRowsByKeys` per slice.

Deliberately unchanged: `readEffectiveRowByKey` and its other callers (constraint probes,
backing host), all window derivation, all residual/collation logic, the
only-add-`seen`-on-yield rule, and emission order everywhere.

## Deliberate behavior change (weighed and kept)

`limit 1` now reads one *batch*, not one row. `key-set-seek-store.spec.ts`'s laziness test
was rewritten from a per-window bound (`getCount ≤ 3`) to the new one: at most one
`getMany`, at most `ROW_RESOLUTION_BATCH` keys, over a 300-window seek.

The review weighed pushing back on this and kept it. The cost is charged against round
trips, which is what dominates on the backends the ticket exists for: the index side
already pages 256 entries per read, so a stopped scan costs one data round trip either way
— what actually changes is that up to 256 rows get decoded and held to yield one. That is
CPU and allocation, not IO. Recorded as a tripwire at the constant (see below) rather than
reverted or ticketed.

## Review findings

### Read first, then the handoff

The implement-stage diff (`82b375fd`) was read before the handoff summary, along with the
current state of `store-table-scan.ts`, `store-table-base.ts` (`readEffectiveRowsByKeys`,
`iterateEffective`, `pendingRowFor`), `kv-store.ts` (the `getMany` and `iterate`
contracts), `store-table-constraints.ts`, `packages/quereus-store/README.md`, and
`docs/store.md`.

### Correctness — nothing found, and why

The three claims batching could plausibly break were each traced to the code, not taken
from the summary:

- **Ordering** holds: entries stay in visit order through the producer, batches resolve
  positionally, and `resolveRowBatch` yields in entry order. A null row cannot shift a
  later position because the read answers by position.
- **Cross-batch dedup** holds for a non-obvious reason worth writing down: `yield*` in
  `resolveIndexEntries` suspends the collecting `for await` until the batch is fully
  drained, so `seen` is complete before the next batch's entries are pulled. This was
  untested; a test now pins it (below).
- **Early termination** holds: a downstream `break` finishes the consumer generator, whose
  `for await` closes the producer and the iterate cursor under it. No further batch is
  collected or read.

The `getMany` positional contract, the buffer-ownership rule a batch leans on, and the
overlay-precedence ordering inside `readEffectiveRowsByKeys` were each re-read against the
interface docs and match what the batch path assumes.

### Fixed in this pass (minor)

- **Non-null assertions on the dedup set.** `produceIndexEntries` and `resolveRowBatch`
  both wrote `seen!`, relying on an unenforced invariant ("`dataKeyHex` is defined ⇒ `seen`
  is defined"). Rewritten to gate on `seen` directly — no assertions, same behavior, and
  the invariant no longer has to hold for the code to be type-safe. (`AGENTS.md`: type it
  right.)
- **Two stale cross-references in `store-table-constraints.ts`.** One pointed at
  "`scanIndex` → `readEffectiveRowByKey(entry.value)`" (now `resolveRowBatch` →
  `readEffectiveRowsByKeys`); the other sent the reader to "the NOTE in `scanIndex`" for
  the legacy empty-index-value fix, which moved to `produceIndexEntries`. Both were left
  pointing at code that no longer exists in that shape.
- **`packages/quereus-store/README.md` was stale on the cost model.** Its index-value entry
  still said a scan resolves each matched entry "with one data-store read at this key" —
  the exact claim this ticket invalidated. Rewritten to describe batched resolution, the
  cross-window collapse, and the early-termination trade.
- **`docs/store.md`'s `StoreTable` size NOTE was stale twice over**: it cited
  `store-table-scan.ts` at 1,113 lines (now 1,401) and named a backlog slug
  (`debt-split-store-table-scan-and-base`) that no longer exists — that ticket was absorbed
  into `debt-oversized-source-files`. Re-measured, re-pointed, and the row-resolution group
  added as a second named seam.

### Test gaps closed (minor)

The implementer's suite covered in-batch dedup, a 300-row drain across the batch boundary
on the single-window arm, the limit-1 bound, and a 100-window multi-seek collapse. Two
gaps in `index-scan-batching.spec.ts`, both now covered:

- **Cross-batch dedup.** A forged duplicate index entry placed so the duplicate lands in a
  *later* batch than the row it duplicates — the producer pre-check path across a batch
  boundary, which nothing exercised. Pins the `yield*` suspension property above.
- **Multi-seek drain past the batch boundary.** Every prior multi-seek test fit in one
  batch or stopped at `limit 1`. A 300-value `IN` drain now asserts full row set, order,
  and exactly `ceil(300 / 256) = 2` round trips — the arm where batches are bounded by
  entry count across windows rather than per window.

Still uncovered, deliberately: `scanMultiSeekPrimary` past its batch boundary (the arm is
unreachable from the module's own plans and the slice loop is a plain `for` over a
pre-materialized array), and the throw path out of `readEffectiveRowsByKeys` (the generator
propagation is language-level, not logic under test).

### Tripwires recorded (not ticketed)

- **`limit 1` decodes up to 256 rows to yield one.** Fine now — round trips are the cost
  that matters on the target backends and they are unchanged — but the decode/allocation
  cost is real if a `limit`-shaped query (a correlated `EXISTS`, a semi-join probe) ever
  shows up in a profile. Parked as a `NOTE:` on `ROW_RESOLUTION_BATCH` in
  `store-table-scan.ts`, naming the mitigation: a smaller first batch that ramps toward the
  bound, which keeps a drain's round-trip count within a log factor while making a stopped
  scan cost about one row again.

### Filed / appended (major)

No new tickets. One arm appended to an existing one:

- **`tickets/backlog/debt-oversized-source-files.md`** already claims

### Declined

- **The `limit 1` behavior change** the handoff explicitly invited pushback on. Weighed
  above and kept; recorded as a tripwire instead.
- **Docblock density.** Several new docblocks run longer than the function they document
  (`resolveRowBatch`: ~26 comment lines over ~16 code lines). This matches the prevailing
  style of the surrounding file and of `kv-store.ts`, and every paragraph states a
  non-obvious invariant rather than restating the code. Churning it would be a style
  disagreement, not a fix.
- **Single-window scans still have no duplicate dedup** (only multi-seek carries `seen`),
  so two index entries pointing at one row in a plain `scanIndex` window yield the row
  twice. Unchanged by this ticket and corrupt-index territory; not a regression, so not
  re-opened here.
