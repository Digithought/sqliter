# What shipped

`cast(x as blob)` — and every other path that turns a value into binary — used to
guess. If a string had an even number of characters and they all happened to be
hex digits, it was decoded as hex; otherwise it was taken as literal text. So
`'abc'` became three bytes but `'abcd'` became two, and the branch was invisible
until a string crossed the length/alphabet line.

Now text-to-binary is **always** the string's literal UTF-8 bytes, on all four
paths that reach it: `cast(x as blob)`, the new `blob(x)` function, an
INSERT/UPDATE into a BLOB column, and the `alter table … alter column … set data
type blob` backfill. Hex is something a user asks for on purpose, with the two
new functions:

- **`hex(X)`** — uppercase hex spelling of X's bytes, no separator. A non-blob
  argument converts to bytes first, through the same path `cast(X as blob)`
  takes.
- **`unhex(X)`** — the inverse. Text only; `NULL` (not an error) for anything
  that is not a whole number of hex digit pairs, matching SQLite.

`blob(X)` was already listed in `docs/types.md`'s conversion-function list and
simply did not exist; it now does, mirroring `text()`/`integer()`.

The bug this fixes was latent until `canonical-value-to-text` made
`cast(<blob> as text)` render bytes as UTF-8 text: `x'6162'` → `'ab'` → back
through the old sniff → the single byte `0xab`. The round trip is now lossless
for UTF-8-clean bytes, and honestly lossy (U+FFFD) for bytes that are not — both
asserted.

## Minor — fixed in this pass

- **`hex()` lied about its nullability.** It was declared with the string
  family's shared `textReturnTypeInference`, which reports `nullable: false`,
  while `hex(null)` returns null. That flag is not decorative: the lens prover
  (`schema/lens-prover.ts` `checkTypeAndNullability`) raises
  `lens.nullability-mismatch` only when a basis expression reports
  `nullable === true`, so a false `false` lets a NOT NULL logical column deploy
  over an expression that can produce NULL. Switched `hexFunc` to `TEXT_RETURN`
  with a comment saying why. (The same lie across nine pre-existing functions is
  a major finding — see below.)
- **`docs/types.md` § Binary types said something untrue about `unhex`** — that
  "a non-blob argument to either goes through the same blob conversion first".
  True for `hex`, false for `unhex`, which takes text only and answers NULL for
  everything else. Corrected, and the same omission fixed in
  `docs/sql-functions.md`.
- **`docs/functions.md` did not mention that `blob(X)` throws where
  `cast(X as blob)` does not.** A JSON document raises from `blob()`/`hex()` but
  yields the document's own text as bytes from `cast`. This asymmetry is correct
  and deliberate — it is the established conversion-function family rule that
  `integer()`/`real()` already follow, strict function vs lenient CAST — but it
  was undocumented and surprising. Stated in the table row, and both sides are
  now asserted in `06.5.1`.
- **`docs/functions.md`'s "the rest of the table above" paragraph** swept the two
  newly-added rows into the not-yet-canonical set by position. Added a sentence
  putting `hex`/`unhex` explicitly on the one blob conversion.
- **Pre-existing broken markdown table row** in the same file (`instr` and
  `reverse` collapsed onto one line, rendering as a single malformed cell).
  Trivial, in a file this ticket touched, fixed.
- **`unhex`'s validation regex was a literal inside the implementation**, so a
  fresh `RegExp` was constructed on every row. Hoisted to a module constant.

## Minor — test gaps the handoff flagged, now closed

The handoff was honest about what it had not asserted. All of it is covered now,
in `06.5.1-conversion-functions.sqllogic` unless noted:

- `hex(42)` / `hex(true)` and `blob(42)` / `blob(true)` — the number/boolean arm
  of the conversion, which spells the value as text and takes *those* bytes
  (`hex(42)` is `'3432'`, not the hex of the integer 42 — the surprising answer,
  so worth pinning).
- `hex(json(…))` and `blob(json(…))` raise, with `cast(json(…) as blob)`
  asserted alongside as the lenient contrast.
- `unhex(42)` and `unhex(x'6162')` → NULL. The blob case matters: `unhex` is the
  inverse of `hex` only for `hex`'s *output*, never for its input.
- The `alter table … alter column … set data type blob` backfill, with a
  hex-shaped source string (`'6162'`), confirming the retype path agrees with
  the INSERT path rather than being inferred from code inspection.
- `BLOB_TYPE.parse` in `test/type-system.spec.ts` generalized from the single
  `'ff00'` case to both sides of each condition the removed sniff branched on
  (odd/even length, hex/non-hex alphabet, empty, non-ASCII) — so a future
  reintroduction of the guess fails the unit test regardless of which shape it
  guesses on.

Deliberately not added: a bigint case. `sqllogic` bigint assertions are lossy
(`debt-sqllogic-bigint-assertions-lossy`), so the test would assert the wrong
thing for the wrong reason.

## Major — filed

- **`textReturnTypeInference` declares `nullable: false` for nine functions that
  all return NULL** (`trim`, `ltrim`, `rtrim`, `replace`, `lower`, `upper`,
  `reverse`, `lpad`, `rpad`), and the lens prover consumes that flag — same
  unsoundness described above, nine more instances. Root cause is one shared
  helper in `func/builtins/string.ts`, and the real fix is at the registration
  seam (derive nullability rather than let each function assert it), which is
  exactly the seam `debt-string-builtins-coerce-three-different-ways` already
  proposes for the coercion problem in the same file. Site-claim grep found that
  ticket, so this was **appended to it as a second arm** rather than filed
  fresh — the two arms must be sequenced, not resolved independently (if the
  coercion arm stops these functions refusing input, some of the declarations
  become true on their own). No new ticket.

## Tripwire — recorded, not filed

- There are now two byte→hex encoders in the monorepo: `hexFunc` here and
  `bytesToHex` in `@quereus/quereus-store`. They cannot be naively unified —
  the store's must stay lowercase because `InMemoryKVStore` orders keys by
  string comparison and only `[0-9a-f]` matches unsigned-byte order, while SQL
  `hex()` must be uppercase. `@quereus/quereus` also cannot import from
  `quereus-store` (the dependency runs the other way). Recorded as a `NOTE:` at
  `hexFunc`, following the precedent of the existing `toBase64Url` note in
  `quereus-sync/src/clock/site.ts`: if a third copy appears, promote a
  case-parameterized one to a shared export.
