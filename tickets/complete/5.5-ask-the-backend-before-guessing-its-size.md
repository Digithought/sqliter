# What landed

`BestAccessPlanRequest.estimatedRows` now carries three distinct spellings all the way from
the planner to the module: `undefined` (nobody measured), `0` (measured, and empty),
`n > 0` (measured).

Five planner sites build that request. Two of them —
`rule-grow-retrieve`'s filter arm and its sort-absorption arm — sent
`tableRef.estimatedRows || context.stats.tableRows(schema) || 1000`, handing every
never-analyzed table a fabricated `1000`. Both now relay the catalog count or `undefined`
via a `measuredRows(tableRef)` helper carrying the reasoning. The other three relayed
`|| undefined`, which spelt a measured `0` as unknown; all three now relay the value as-is.

The ticket's one stated judgment call was answered correctly: `context.stats.tableRows`
reads the same `catalogRowCount` and then falls through to `NaiveStatsProvider`'s fixed
1000, so consulting it would have been "the fabricated number by a longer route". It is no
longer consulted at those sites, and the catalog count is passed through directly.

`validateAccessPlanRequest` now rejects a negative or non-integer `estimatedRows` and
accepts `undefined` and `0`. `StoreModule.sizeRequestFromLiveCount` gained one exception —
a hint of `0` its own live count contradicts is a stale pre-data-load `ANALYZE` snapshot and
is overridden — mirroring the refusal `resolveArmEstimate` already makes for selectivity.

Two of the ticket's predictions were contradicted by measurement, and the implementer
pinned both as tests rather than quietly dropping them. Both were re-derived in this review
and both hold — see below.

# Review findings

## Verified, not changed — the two negative findings the handoff flagged as highest-risk

- **"An un-analyzed range query's plan does not move; only its price does" — CONFIRMED, and
  the codebase already said so.** `store-module-access-plan.ts` lines 108-115 document that
  an arm priced by an `ARM_SELECTIVITY` shape constant is linear in `estimatedRows` and
  therefore "either ALWAYS prices above a sequential scan or never does, for every query on
  every table", listing the exact flip points (`range` at `pointRead > 2.83`, judged at
  parity `1.0` for an unbacked estimate). The scale-invariance claim is that comment's
  direct consequence. The arithmetic quoted in the new spec's doc comment was a
  mis-transcription (`0.5 + 0.3·N·1.5`, which has a spurious constant term); corrected in
  place to the module's own form, `0.3·N·(0.5 + R)` against a scan's `N`.
- **"The key-set-seek merge gate still never declines, and a second relay bug is why" —
  CONFIRMED.** `IndexScanNode.computePhysical` (~277) and `SeqScanNode` (~177) publish
  `this.source.estimatedRows` (the catalog count, `undefined` un-analyzed) where their
  sibling `IndexSeekNode` (~545) publishes the module's own
  `filterInfo.indexInfoOutput.estimatedRows`. Read in the source; the two siblings do
  disagree. Correctly filed as an arm on the existing theme ticket
  `debt-row-estimate-relay-has-no-guard` rather than as a new point ticket, and pinned as
  *observed* behavior.

## Verified, not changed — the rest of the handoff's "push hardest" list

- **The four resized store fixtures.** Each keeps its plan-shape assertion
  (`to.match(SEEK)`, `to.match(/INDEXSEEK/)`), so none went vacuous — a future cost-model
  change makes them fail rather than pass silently. The three 1→20-row resizes are the same
  cliff: at one row the arm's `Math.max(1, …)` floor breaks the linearity the veto relies
  on, so a seek genuinely costs more than reading the single row. The 300→1200 resize's
  arithmetic is quoted at the site and checks out (walk `≈1.9N` vs scan-then-sort
  `N + 0.1·N·log₂N`, crossover ≈512; at 1200 the walk wins by ~6%). That margin is thin but
  no thinner than the test had before.
- **The `sizeRequestFromLiveCount` exception.** Accepted. It is asymmetric by design — a
  stale *large* hint is not corrected — and that asymmetry is the documented "a supplied
  hint wins" rule holding everywhere except the one case where the hint is provably a
  snapshot of a table that did not exist yet. Moving it into `ANALYZE` was considered and is
  worse: a genuinely empty table *should* stamp `rowCount: 0`; the staleness is inherent to
  snapshots, not to how the snapshot is taken.
- **Every request-building site is accounted for.** Grepped `BestAccessPlanRequest` across
  the planner: exactly five sites (`rule-grow-retrieve` ×2, `rule-select-access-path`,
  `rule-lateral-top1-asof`, `access-leaf.buildProbeRequest` with its two callers). None was
  missed. `docs/module-authoring.md`'s new claim that *every* site now sends `undefined` for
  an un-analyzed table is true as written.

## Fixed in this pass

- **Three `x ?? undefined` expressions were no-ops.** `estimatedRows` is typed
  `number | undefined` on every node involved, so `?? undefined` does nothing; the change
  from `|| undefined` was correct but left a confusing operator behind that reads as if it
  normalizes something. Replaced with plain relays at
  `rule-select-access-path.ts` ~266, `index-nested-loop.ts` ~405, `rule-key-set-seek.ts`
  ~409, keeping the explanation of why the `||` was wrong.
- **`vtab/memory/module.ts` asserted something false.** Its new NOTE said "This module keeps
  no live row count, so it cannot [size itself]". It can:
  `MemoryTableManager.getBaseLayerStats()` is the committed primary B-tree's node count in
  O(1), `MemoryTable.getStatistics()` already reads it, and the module holds every manager
  in its public `tables` map. Rewritten to say what is actually true — it *could* and
  deliberately does not yet — with the reason (plan churn under the default backend) and a
  pointer to the new ticket. The same false claim was in the new engine spec's file header
  and in the implement ticket it was inherited from; the spec header is corrected too.
- **`rule-key-set-seek.ts`'s gate comment had become a changelog.** Three tickets' worth of
  archaeology stacked up, whose first paragraph stated facts ("the physical row estimate
  reads 0") that the second paragraph contradicted, so a reader had to get to the end to
  learn the current state. Collapsed to current state plus the tracking pointer.
- **One new engine test was near-vacuous.** `leaves the module free to answer with a size of
  its own` re-asserted what the six parametrized tests above it already asserted, used
  `.every()` on an array that would pass trivially if empty, and did not test the behavior
  its name promised. Now records what the module *answered* (`result.rows`, mirroring the
  store spec's recorder) and asserts an arm claims more rows than the table holds — which is
  only possible if the module sized from its own 1000.

## Filed

- **`backlog/feat-memory-backend-sizes-itself`** (major). The engine's default backend is
  precisely the "module that can size itself" this ticket exists to enable, and it declines,
  so the ticket's central claim is exercised through exactly one implementation. Making it
  answer is a large change (it re-prices the backend nearly the whole suite runs on), which
  is why it is a ticket and not a review fix. Filed at the point-fix rung deliberately: the
  contract says a module *may* substitute its own size, so there is no invariant to assert
  and no class of instances behind it — two shipped modules, one of which already complies.
- **`backlog/bug-measured-empty-table-costed-as-thousand-rows`** (minor, disclosed by the
  handoff). `createSeqScan` (`rule-select-access-path.ts` ~1235) still reads
  `tableRef.estimatedRows || 1000`, so an `ANALYZE`d-empty table's scan is costed at 1000
  rows. Reachable today, never a wrong row — only a wrong plan choice. Not fixed inline
  because `?? 1000` alone gives an empty table a zero cost, which is a cost-model decision
  outside a review pass. A `NOTE:` at the site points at the ticket so it is not re-filed.

## Tripwires recorded, not filed

- **`store-module.ts` `sizeRequestFromLiveCount`'s `Math.max(1, liveRows)` floor.** An
  un-analyzed store table the module knows is empty is substituted as `1`, not `0` — in
  mild tension with the three-spellings contract this ticket just wrote down, and previously
  unexplained. `NOTE:` added at the site stating why the floor exists (a `0` prices every
  arm and the scan at zero and the comparison decides on rounding), that it is deliberately
  not the same case as an honored hint of `0`, and what to fix first if it ever needs
  removing. Pre-existing line, unchanged.

## Checked, nothing found

- **Unused parameters after the `context.stats` removal.** `fallbackIndexSupports` and
  `trySortAbsorbViaIndexOrdering` still use `context.db`, so no dead parameter was left.
- **Docs.** Read every doc mentioning `estimatedRows` — `module-authoring.md` §§ row counts,
  `optimizer-costing.md` §§ *Base-table row estimates* / *Where a module's own size fits* /
  *What a physical seek node reports*. All three were already written to the
  "`undefined` is unknown, `0` is measured-empty" contract and none was made stale by this
  change; `optimizer-costing.md`'s account of where a module's own size fits is now simply
  true of every request site rather than one.
- **The `measuredRows` identity helper.** Considered and left: it is a one-line wrapper, but
  it is the single home for the reasoning that two call sites need, which is what keeps that
  reasoning from being copy-pasted or lost.
- **Site-claim grep before filing.** Both new tickets' sites (`vtab/memory/module.ts`,
  `rule-select-access-path.ts` `createSeqScan`) were checked against every open ticket;
  `debt-node-self-cost-reads-the-blank-estimate` is the nearest neighbour and is about a
  different thing (a node's constructor-time self-cost, not a table's row count).
- **No accepted-tradeoff `NOTE:` was overridden.** The one at the memory module's default
  was read and left standing; the change there is to the factual claim beside it, not to the
  decision.
