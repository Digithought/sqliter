# Store coverage for `pk in (select …)`, plain and isolation-wrapped

Coverage-and-verification ticket. The prereq (`feat-store-pk-in-list-multiseek`) built the
planner/module arm and covered the literal `pk in (1,2,3)` shape; this one covers the
**second caller** — subquery decorrelation → semi join → `rule-key-set-seek` rewrites the
target leaf into the same `_primary_` `plan=5` multi-seek — and the transaction-visibility
case behind the isolation layer.

**No production behaviour changed**, at implement or at review. The only non-test edits are
comments and documentation.

## The two open questions, answered

Both were settled by probing the real planner (`query_plan()` plus the rule's own debug
log, `DEBUG=quereus:optimizer:rule:key-set-seek`), then pinned with tests.

**1. `seekPreservesTargetOrder` on a store primary-key target: it HOLDS.** A store leaf
arrives as an ordering-only `IndexScan` over `_primary_` (`plan=0`, advertising
`[{column: 0, desc: false}]`), and the pushdown claims that same single-column
`_primary_` index — so the predicate's every clause passes. Consequences, all pinned:

- `select … where pk in (select …) order by pk` keeps its seek. The `order by` is absorbed
  into the leaf's walk (marking its emission order load-bearing), which is a *decline* for
  a secondary-index target, but here the node claims the leaf's order and **no `Sort`
  reappears**.
- The node's `preservesTargetOrder` logical attribute reads `true`.
- Because the claim is only sound if the store really emits in key order, the tests assert
  **row order**, not just the absence of the `Sort`.

**2. The merge arm fires, and its second gate is vacuous.** `pk in (select id from src)`
— where the key-source column is that table's own primary key, so both sides walk in key
order — arrives as a MERGE semi join and takes `rule-key-set-seek`'s merge anchor.
(`pk in (select k from src)`, an ordinary key column, arrives as a hash semi join. Both
arms are covered.) Of the merge anchor's two extra gates:

- gate 1 (`seekPreservesTargetOrder`) genuinely passes, per question 1;
- gate 2 (key-source row estimate under `min(maxKeys, breakEvenKeys)`) passes
  **vacuously**: a store leaf's PHYSICAL `estimatedRows` reads `0` no matter how many rows
  are committed (measured: 7 committed rows, estimate 0 on both the leaf and the `Project`
  above it), so `0 > threshold` is never true.

## What the tests cover

`yarn workspace @quereus/store test`, or the single file:

```
node --import ./packages/quereus-store/register.mjs node_modules/mocha/bin/mocha.js \
  "packages/quereus-store/test/key-set-seek-store.spec.ts" --reporter spec
```

52 tests in the file, 22 of them in the two new blocks (17 from implement, 5 added at
review).

**`store module, no isolation` → `primary-key target`** (14 tests). Fixture: `pkt` with 4
rows (break-even lands at 6 keys, so every set here seeks) and a key source `psrc`.
Covers: basic set with `inCount`; duplicate + NULL inner values collapsing before
`inCount` is stamped; an empty key set never opening the target; a one-key set; a set
matching nothing still seeking; the merge arm; `order by pk` on **both** arms (plan shape,
`preservesTargetOrder`, and actual ascending rows); `limit`/`offset` over the ordered
seek; a DESC primary key; a `collate nocase` TEXT primary key; a composite primary key
declining with the `MERGEJOIN` surviving and the query still answering; `delete` and
`update` driven by the set reading their victims through the seek; and the store's own
pending-op read-your-own-writes.

**`store behind the isolation layer` → `primary-key target`** (9 tests). The case
`bug-isolation-multiseek-merge-order` was filed for, now reached through the store: the
isolation layer merges the underlying stream with its overlay **by primary key**, and
`scanMultiSeekPrimary`'s ascending-encoded-data-key emission is what satisfies that.
Covers: a staged insert whose key is in the set; a staged in-place update of an in-set row
appearing exactly once in its new form; a staged delete not resurfacing; staged rows
outside the key list excluded by the overlay predicate; several staged rows straddling the
committed keys interleaving in key order; NULL and duplicate key-source values collapsing;
a DESC primary key merging in descending key order; `delete … where pk in (select …)`
inside a transaction, read back, then committed; and a rolled-back change leaving the
committed answer intact.

**Every assertion in the isolation block reads RAW emission order — nothing is sorted in
JS.** That is deliberate and it is what makes the block load-bearing.

## Are the tests load-bearing? Mutation-checked, yes

Reversing one line in `scanMultiSeekPrimary` (`sort((a, b) => compareBytes(...))` →
`-compareBytes(...)`, i.e. emit descending) turns **16 of the 22 tests red** (11 before the
review's additions, so all 5 new tests are load-bearing too). One of those failures is not
an ordering complaint at all: *a staged delete of an in-set row does not resurface* fails
with the deleted row **present in the output**. So the ascending-emission contract is what
keeps the isolation merge correct, and these tests catch its loss as a wrong-rows bug
rather than a cosmetic one. The mutation was reverted; the working tree carries no
production change.

### Verified sound (no change needed)

- **The ordering claim is real, not just plan-shaped.** `seekPreservesTargetOrder`
  compares the leaf's advertised direction against the index key column's rather than
  assuming ascending, and `scanMultiSeekPrimary` sorts by *encoded* key with per-column
  DESC inversion already baked into the bytes. Confirmed by probe and now by test on a
  DESC key, where the same code emits descending.
- **The mutation check reproduces.** Re-ran it against the enlarged block; 16 red.
- **Test fixtures are per-test.** Each test gets a fresh `Database` and provider, so the
  tables created inside individual tests cannot leak across them.

### Minor — fixed in this pass

- **The `order by pk` test's hash arm never asserted any rows.** Its key source was
  `insert into psrc values (3, 0), (1, 0), (4, 0)` — every `k` is `0`, so that arm's key
  set was `{0}` and matched nothing. The test asserted plan shape and
  `preservesTargetOrder` for both arms but rows for the `id` arm only, so the hash arm's
  *row-order* claim — the whole point of the test — was vacuous. `k` now mirrors `id`, both
  arms carry the key set `{3,1,4}`, and both assert `[1, 3, 4]` in raw emission order.
- **Five named coverage gaps closed** (all were listed as "known gaps" in the handoff, all
  turned out to behave correctly — no defect found, but nothing was pinning them):
  - **DESC primary key**, un-wrapped: seeks, emits descending, `order by pk desc` keeps the
    seek with no `Sort`, and `order by pk asc` correctly grows a real `Sort` with the seek
    still taken underneath.
  - **DESC primary key under the isolation layer**: staged insert and staged update
    interleave with committed rows in *descending* key order. This is the sharpest of the
    five — the overlay merge follows the key's own direction, and nothing was covering that
    intersection on the store.
  - **`collate nocase` TEXT primary key**: seek keys are encoded under the key's own
    collation, so a case-differing key-source value still lands on the row.
  - **`limit`/`offset` over the ordered PK seek**: trims above the node, `inCount`
    unchanged.
  - **NULL + duplicate key-source values on the isolation-wrapped PK path**: collapse to
    three distinct keys with the staged row still surfacing. Required widening that block's
    `pksrc.k` to nullable (it was NOT NULL, unlike the un-wrapped block's `psrc.k`);
    strictly looser and no other test in the block inserts NULL.
- **`docs/module-authoring.md` contradicted the shipped store.** Its runtime-set section
  told module authors to "never claim `providesOrdering` or `monotonicOn`" over a
  multi-seek column — but the store's `_primary_` arm does exactly that, and it is what
  makes `where pk in (select …) order by pk` drop its `Sort`. The same page's later "Key
  Ordering" section already flagged the tension without resolving it. Rewritten: claim
  ordering only if the multi-seek emits in the index's own key order (which the hard
  requirement below it obliges anyway), with the store's arm named as the worked example.
- **`docs/optimizer-rules.md` § `ruleKeySetSeek` was stale on the same point the
  implementer corrected in code.** It still said the merge arm's row-estimate gate "is
  inert on the memory backend"; the implementer measured it inert on the store too and
  fixed the code `NOTE:` but not the doc. Doc now says both shipped backends and points at
  the theme ticket. (`docs/store.md`, `docs/design-isolation-layer.md`,
  `docs/optimizer.md`, `docs/optimizer-fd.md` and `docs/optimizer-joins.md` were each read
  against the new behaviour and are accurate as written — no change needed.)

### Evidence appended to an existing ticket (no new ticket filed)

- **`bug-row-estimate-conflates-unknown-and-zero`, Arm 4** — the implementer had already
  appended the store measurement. Added one more: **`analyze` does not rescue the gate**,
  so it cannot be covered by a test today. With a 30-row key source, `analyze` makes the
  optimizer drop the semi join entirely and pick an index-nested-loop join (target walked
  at `plan=0`, key source seeked per outer row), so `rule-key-set-seek` never runs and the
  gate is never consulted. Any test aimed at this gate would pin an unrelated plan choice
  instead. This is why no test was added for it.

## Remaining gaps — treat the tests as a floor

- **The merge arm is pinned indirectly.** `MergeJoinNode` is not exported from
  `@quereus/quereus`, and once the rewrite fires the `MERGEJOIN` op is gone from
  `query_plan()`, so no assertion in the store package can say "*this* query arrived as a
  merge join". The evidence in the file is the composite-key test, where the identical
  query shape declines and the `MERGEJOIN` survives. The engine package's
  `test/optimizer/key-set-seek.spec.ts` pins the merge arm properly, against the memory
  backend.
- **No composite key under the isolation layer** (see above — declines, so low value).
- **No performance measurement.** "Reads only the listed rows" is asserted through the
  captured `idxStr` (`plan=5`, `inCount=K`), not through KV-operation counts or timings on
  this path. The `CountingKVStore` machinery in the file is used only by the pre-existing
  `limit 1` batching test.
- **`store-index-seek-batched-row-resolution`** makes `scanMultiSeekPrimary` fetch rows in
  one batched read. These tests do not assert round-trip counts, so they should survive
  that change untouched; if both have landed, the combined path is worth measuring
  together.
