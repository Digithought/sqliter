# What landed

Both join-ordering rules now read a row count through
`physicalSourceRows(child.physical, child)` — the child's physical row estimate,
falling back to its logical `estimatedRows` getter. Before, both read the logical
getter directly, which is `undefined` for every table-backed input (the physical
access nodes stamp their catalog count into `computePhysical` only), so each rule
fell through to a sentinel that made its own comparison meaningless.

**`rule-join-greedy-commute`** — the `?? Number.POSITIVE_INFINITY` is gone. An
unknown estimate on either side is an explicit "do not swap"; only the
singleton-functional-dependency arm applies then. Strict `<`, so equal estimates
never swap and a re-run cannot oscillate. The rule now fires for real: a two-table
inner join reads the smaller table first however the query names the two tables.

**`rule-quickpick-enumeration`** — the `1e9` magic number is gone. The base-order
computation is an exported `quickPickBaseOrder(relations)`: ascending physical row
count, unknown last (`UNKNOWN_RELATION_ROWS = MAX_ROW_ESTIMATE`, finite so two
unknowns subtract to 0 rather than `NaN`), ties broken by relation index.

# Review findings

Reviewed the implement diff (`40a01abb`) first, then the surrounding rule,
node, doc and test files.

## Fixed in this pass (minor)

- **`rule-join-greedy-commute` rebuilt the swapped join with `new JoinNode(...)`
  and dropped the `existence` argument.** Two sibling rules
  (`rule-join-predicate-pushdown`, `rule-semi-join-pushdown`) carry explicit
  comments saying to use `withChildren` for exactly this reason — a dropped
  existence spec strands every upstream reference to the flag's attribute id. Not
  reachable today (the parser rejects `exists … as` on INNER/CROSS, and the rule
  guards on join type), so this was a latent hazard rather than a live defect.
  Rebuilt through `withChildren`, plus an explicit `hasExistenceColumns` refusal:
  a commute would have to flip each spec's `side`, which `withChildren` alone
  would not do, so refusing is the honest posture.
- **`docs/optimizer-joins.md` pointed at a ticket slug that does not exist.**
  The prose said `bug-join-self-cost-cannot-see-its-inputs`; the ticket that was
  actually filed is `debt-node-self-cost-reads-the-blank-estimate`.
- **`docs/optimizer-joins.md` had a broken cross-reference and a claim this very
  change made false.** The index-nested-loop section linked to
  `#two-table-joins-are-not-reordered-here`, an anchor the implement pass renamed
  out of existence, and argued the mirror is needed because "two-table joins are
  not reordered". They are now. Both corrected; the mirror's actual justification
  (the orientation was chosen before anything knew which side had an index) still
  holds and is stated directly.
- **A comment in `rule-join-physical-selection.ts`, repeated verbatim in
  `docs/optimizer-joins.md`, asserted that "`withChildren` … cannot express the
  swap".** That is not true — it is precisely how the commute rule now rebuilds.
  The mirrored rebuild does have real reasons to construct a fresh node (it forces
  the join type to `inner` and deliberately drops `existence`); the comment and
  the doc now say those instead. No behaviour change at that site.

## Tests added (the implementer's spec was rule-level only)

The implement spec called `ruleJoinGreedyCommute` directly on hand-built nodes.
Added two query-level tests to the same spec, so the rule is pinned through a real
compile: that a `big join little` query plans `little` first however the two
tables are named (the commute genuinely reaches real queries and its inputs carry
real counts by the Structural pass), and that a commuted `select * … using (id)`
returns the same column order and the same rows — which is also the guard on the
`withChildren` rebuild above. 15 tests in the spec now, all passing.

## Findings raised as arms on existing tickets, not new tickets

Both resolve at sites already claimed by open backlog tickets, so they were
appended there as arms per the "Nth instance is evidence" rule.

- **QuickPick cannot adopt any plan at all today — the base-order fix is
  currently unobservable.** The implement handoff called the payoff "throttled" by
  the flat `JoinNode` self-cost; measuring it, the accurate statement is stronger.
  The rule adopts only when `bestCost < baselineCost * 0.9`, but every candidate
  ordering reuses the *same* already-optimized leaf subtrees, so leaf costs are a
  shared constant, and the N-1 join self-costs are a flat 10000 each; every
  candidate therefore scores within a rounding error of the baseline. Measured on
  a three-table chain: `{"tours":100,"bestCost":23553.05}` = `3000+500+50` of
  leaves + `2 x 10000` of join constants + 3.05 of condition nodes — exactly the
  baseline it had to beat. A four-table star join planned in written order under
  both spellings, the 5-row dimension never promoted. Appended to
  `backlog/debt-node-self-cost-reads-the-blank-estimate`, which is the site.
  **This answers the implementer's question of whether that ticket should have
  blocked this one: no.** Reading the estimate that exists is a correct and
  necessary change on its own, and it is already observable through the commute
  rule; it is only QuickPick's half that waits on the self-cost work. Sequencing
  them the other way round would have meant fixing the cost model against a
  base order that was still reading a blank.
- **QuickPick's "100 tours" are only 2 distinct plans.** The loop varies only the
  start relation and picks it with `tours % 2`, and the walk after it is fully
  deterministic (despite a comment claiming randomness), so iterations 2..99
  reproduce 0 and 1 exactly. This both narrows the reproducibility risk described
  in `backlog/bug-join-order-depends-on-wall-clock` (once two iterations finish the
  answer is final) and identifies ~98% of that loop as wasted work on every compile
  of a 3+-relation join. Appended there — same site, same fix.

## Recorded as a tripwire, not a ticket

- **The commute is a Structural-pass heuristic that fixes the orientation the
  Physical pass then costs**, so it can pre-empt a cost comparison — the churn in
  `index-nested-loop.spec.ts` is exactly that (a tiny left side made a nested loop
  beat a hash join). Benign today: hash cost builds on `min(leftRows, rightRows)`
  regardless of orientation, and index-nested-loop elects its seek side in both
  orientations. `NOTE:` at the commute site with its revisit condition — a
  physical algorithm whose cost is asymmetric in the sides and is *not*
  re-elected.

## Checked and found nothing

  concatenates both sides' `Attribute` objects verbatim); only attribute *order*
  changes, and `select *` expands to explicit projections at build time, long
  before the rule runs. Verified by test, not only by reading.
- **Guard ordering in both rules.** Join type, correlation and side-effect

## Answers to the implementer's review checklist

- *"Unknown means do not swap" the right posture?* Yes. A fabricated default is
  indistinguishable from a measurement to everything downstream, and the singleton
  arm still covers the case where one side is provably tiny without stats.
- *Should unknown sort strictly after every known count?* The tie with a saturated
  known count is unreachable in practice (`MAX_ROW_ESTIMATE` is
  `Number.MAX_SAFE_INTEGER`) and the index tie-break makes it deterministic either
  way. Leave it.
- *`quickPickBaseOrder` exported purely for the unit test?* Acceptable, and it is
  the only part of the QuickPick change that is testable at all right now (see the
  adoption-gate finding). Extracting it also removed the `1e9` literal from the
  rule body, which is worth the export on its own.
- *Does this worsen `bug-join-order-depends-on-wall-clock`?* No — the new tie-break
  is deterministic. It in fact narrows that bug; see the arm appended there.

- **No `.sqllogic` coverage added.** Row-level correctness of a commuted join is
  covered by existing logic tests; the new coverage is plan-shape plus one
  end-to-end result check, which is the right level for an ordering rule.
- **`docs/quickpick-design.md` left alone.** It is a pre-implementation design and
