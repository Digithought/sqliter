# What shipped

`ALTER TABLE … RENAME` and `… RENAME COLUMN` used to rewrite dependent **views,
materialized views and assertions** only while iterating the renamed table's own
schema, while dependent **tables** (foreign keys, CHECK expressions, partial-index
predicates, column `DEFAULT` / `GENERATED` bodies) were always walked across every
schema. A view in `temp` over `main.t` therefore kept naming a table that no longer
existed; an assertion in that position broke every subsequent write to the database.

The gate is gone. All four dependent kinds are now walked in every schema, and the
per-home-schema resolver from `debt-rename-walkers-resolve-names-like-the-planner`
is what keeps that from over-matching: a reference is rewritten only when it
*resolves*, under the walked body's own home schema path, to the renamed object's
canonical key.

Three substantive edits:

1. **Gate removed** in `alter-table.ts` — `propagateTableRenameInSchema` and
   `propagateColumnRenameInSchema` lost their `schema.name === renamedSchema` gate
   and one level of indentation; the column verb lost the now-dead
   `renamedSchemaName` parameter.
2. **Two global passes, not one combined per-schema pass.** The materialized-view
   pass re-plans each body it rewrites, so every plain view in *every* schema must
   already carry the new name before the first MV re-plans. Schemas iterate `main`
   first, so a combined per-schema pass would re-plan `main.mv` while `temp.vt`
   still named the vanished `main.t`.
3. **Pre-flight widened to match** (`catalog-persistability.ts`).
   `assertRenameDependentsPersistable` takes a `BodyRewriteFor =
   (homeSchemaName) => BodyRewrite` factory instead of a single `BodyRewrite`, and
   its view/MV arm walks every schema. Without it a cross-schema dependent would be
   rewritten without ever being offered to a storage module's veto hook.

# Review findings

## Verified defect — filed

**A rewritten reference can silently re-bind to a different table.** Confirmed by
running it, not inferred. `renameTableInAst`'s rewrite sink calls
`ref.setName(newName)` and nothing else — the `TableRef` it is handed exposes no way
to add a schema qualifier. So a `temp`-owned body whose bare `t` legally falls
through to `main.t` is rewritten to bare `t2`, which re-resolves under
`[temp, main]` to `temp.t2` whenever `temp` holds a `t2`. Reproduced for all three
body kinds:

- view: `select * from temp.vt` returns `temp.t2`'s rows instead of `main.t2`'s;
- materialized view: reads stay correct (source list and row-time maintenance were
  re-keyed to `main.t2`) but `refresh materialized view` replaces the contents with
  `temp.t2`'s rows — record and body disagree;
- assertion: the regenerated violation query watches `temp.t2`, so a write that
  violates the rule against the renamed table commits cleanly.

This is reachable only through the fallthrough rewrite this ticket newly enabled for
views / MVs / assertions, so it is new here rather than pre-existing. Filed as
`tickets/fix/4.35-bug-rename-rewrite-can-rebind-to-a-different-table.md`, at the
invariant rung rather than as three point bugs: the ticket asks for a post-condition
on the rewrite ("re-resolving a rewritten reference against the post-rename catalog
must yield the renamed object's key") plus the collision half of the existing
test grid, not a cross-schema special case. Site-claim grep over the open board
found `4.4` / `4.5` / `4.6` touching the same files but none claiming the rewrite
sink. Recorded as a "Known limitation" paragraph in `docs/sql-alter.md` § 2.7 so
the doc matches reality until the fix lands.

## Checked and clean

- **The four resolver cases the handoff named.** Must-not-rewrite, home-path
  fallthrough, explicit qualifier, and the one-event-per-dependent count are each
  pinned by a test in `test/schema/rename-cross-schema.spec.ts` and by §48/§49 of
  `41.3-alter-rename-propagation.sqllogic`. Read them; they assert the right thing.
- **The two-pass ordering claim.** Verified by reading the call sites: within a
  schema the relative order is still tables → views → assertions, and MVs are a
  strictly later global pass, so no MV re-plans before every view is rewritten.
  Pinned by *"a main MV reading through a temp view survives the rename"*.
- **`propagateTableRenameInSchema` still taking `renamedSchemaName`** (the handoff
  asked for a second look). It is correct. The parameter only builds the
  `<renamed schema>.<old>` → `<renamed schema>.<new>` strings that re-key an
  assertion's `dependentTables` and an MV's `sourceTables`, and those are keyed by
  the *renamed table's* canonical base — not by the dependent's own schema. Confirmed
  `dependentTables[].base` is produced from the plan at `CREATE ASSERTION` time and
  is fully qualified, so a `temp` assertion over `main.t` carries `main.t` and maps
  correctly.
- **Docs.** Read every doc the change touched and the ones it should have:
  `sql-alter.md` § 2.7 (both verbs), `sql-ddl.md` § 2.6.1, `view-persistence.md`,
  plus `materialized-views.md`, `schema.md`, `sql-views.md`, `sql-txn.md`,
  `usage.md`, `schema-rename-detection.md`. No stale "own schema only" claim about
  rename propagation survives; the remaining own-schema statements are about
  *resolution* (still true) or about the DROP guards (still true — see below).
- **Pre-flight widening.** `assertRenameDependentViewsPersistable` asks
  `rewriteFor(schema.name)` per schema, matching what the propagation will actually
  rewrite; both `alter-table.ts` call sites pass a factory bound to the body owner's
  home schema. Its cost NOTE was updated to say "every schema".
- **The DROP-guard asymmetry the handoff flagged** is real and deliberate: a rename
  now follows a cross-schema assertion, a drop still does not refuse for one. Ticket
  `4.5-assertion-guards-follow-view-chains-and-schemas` exists in `implement/` and
  the repointed doc comments in `assertion-drop-guard.ts` / `drop-column-guards.ts`
  cite it correctly.

## Considered and not filed

- **Cross-schema MV chain ordering in `restoreUnaffectedMaterializedViews`.** The
  sweep walks schema-by-schema then creation order, which is not topological across
  schemas. Genuinely conditional — it only becomes work if a producer's *output*
  names can shift while its consumer lives in an earlier-iterated schema. Already
  parked by the implementer as a `NOTE:` on that function; left as a tripwire, not a
  ticket, which is the correct disposition.
- **Assertion propagation has no per-assertion rollback**, and the blast radius grew
  (a throw mid-loop now leaves assertions in earlier schemas rewritten). The site
  carries an accepted-tradeoff `NOTE:` in `reregisterRewrittenAssertion` explaining
  why a catch would be worse, with its revisit condition ("if that ever becomes
  reachable, a dry-run probe"). Not tripped — the only plausible throw remains
  `buildAssertionViolationSql` on an AST that already stringified at create time.
- **`alter-table.ts` size** (2524 lines, `wc -l`). Already named in
  `backlog/debt-oversized-source-files`; not re-filed.
- **Pre-flight cost.** Now clones and re-renders every view and maintained table in
  every schema on every rename, versus one schema before. Not measured as hot and
  it costs literally nothing when no module can veto (the `anyModuleCanVeto` early
  return); the existing cost `NOTE:` in `catalog-persistability.ts` already carries
  the caching escape hatch and was updated to say "every schema". Left alone.
