# What was broken

`new` and `old` are not reserved words, so `create table "new" (…)` is legal — and a bare
`new.<col>` / `old.<col>` inside a CHECK, DEFAULT, or a result column's `with inverse (…)`
clause names a **written row**, never a catalog table. The column-rename walker decided
which meaning applied with a boolean chosen at the walk's *entry point*, but the answer is
a property of the **position in the tree**, and the domain has three values, not two.
Three verified corruption arms:

- **Arm A** — `alter table "new" rename column v to w` rewrote every OTHER table's `new.v`,
  leaving those tables permanently unwritable; `alter table "new" drop column v` was
  false-refused by the same qualifiers.
- **Arm B** — a `with inverse` expression's `new.<output-col>` refs were treated as
  references to a table called `new` by both walkers: corrupted by `rename column` AND
  `rename to`, and they put a table called `new` into the drop-guard reach.
- **Arm C** — the depth-blind output-name-shift pass (`renameNewQualifiedRefs`) reached
  into a NESTED select's own `with inverse` clause and moved `new.` refs belonging to the
  nested select's outputs.

# What was done

`RowImageContext = 'none' | 'own' | 'foreign'` in `rename/shared.ts`; the column walker's
state carries it and the four public entry points take it as a **required** parameter (a
compile error at every call site was the point). Unbound-bare decision (`matchesRowImage`):
`'own'` matches, `'foreign'` is ignored (neither rewritten nor resolved as a table),
`'none'` falls through to catalog resolution. In-scope bindings and schema qualifiers still
decide first. Both walkers force the suppression over `with inverse` **and**
`with defaults` subtrees unconditionally, save/restore — so reached view bodies
self-suppress and `reachableObjects`' root-only `rootOpts` stays correct.
`renameNewQualifiedRefs` skips `inverse` keys during its depth-blind walk. The three
collection helpers keep their signatures and hardcode their documented mode, so
`@quereus/quereus-store` needed no change.

# Review findings

Implement-stage diff read first, before the handoff summary. Build, lint, `yarn test`
(8918 passing / 0 failing) and `yarn test:store` (8910 passing / 0 failing) all green,
before and after the review edits.

## Checked and clean — no finding

- **Every call site of the four widened entry points** was swept (`grep` over
  `packages/**`, excluding `dist`): all 17 production sites plus the three test specs pass
  an explicit mode, and each mode matches the site's semantics. `@quereus/quereus-store`
  reaches the walkers only through the three collection helpers (which hardcode their
  mode), so its untouched state is correct, not an oversight.
- **`columnProbe`'s one non-constant mode** (`expression-dependents.ts:319`) was re-derived
  from scratch against all four reachable combinations (own/other table × base/republication
  target × root/reached body). Each lands on the mode the forward rename would use.
- **The `'foreign'` suppression does not over-reach.** It fires only on a bare, unbound
  `new` / `old` qualifier: a subquery-bound `"new".v`, a schema-qualified `main."new".v`,
  and any other table's qualifier all still resolve and rewrite normally. Both control
  columns of the matrix spec pin this.
- **The nested-`inverse` skip in `renameNewQualifiedRefs` is sound** — `authored-inverse.ts`
  validation requires every `new.<x>` in an inverse expression to resolve to an output
  column of *its own* enclosing select, so a nested clause's refs can never be outer refs.
  Ordinary (non-clause) subqueries are still reached.
- **No missing suppression site.** The only written-row-context-of-an-enclosing-relation
  positions in a stored AST are `select.columns[].inverse` and `select.defaults`; both are
  covered by both walkers. Quereus has no triggers, and stored DML row clauses
  (`visitDmlTargetRowClauses`) carry no `new.` / `old.` namespace.
- **Source hygiene.** `column-rename.ts` grew 60 lines net (1331 total, `wc -l`); oversize
  is already claimed by `tickets/backlog/debt-oversized-source-files.md`, so no new ticket.
  The new helpers (`visitRowImageForeignSubtree`, `visitRowImageSubtree`) are 8 lines each,
  single-purpose, save/restore in `finally`.

## Fixed in this pass (minor)

- **`expression-dependents.ts` module header was stale** — it still explained the
  `new.` / `old.` namespace as a property the *seed* owns, which is exactly the conflation
  this ticket retired. Rewritten to separate the two questions (the seed answers unqualified
  binding; `RowImageContext` answers what a bare qualifier names) and to state the three
  modes the probe actually passes.
- **`docs/vu-inverses.md` was out of date at both clause sections.** § Authored inverses
  claimed the clause "rides RENAME propagation" without either new boundary; § View
  defaults likewise. Added the two facts to § Authored inverses (a `new.<col>` ref is never
  a table reference under either verb; the output-name retargeting stops at a nested
  select's own clause) and one clause to § View defaults.
- **`docs/schema-rename-detection.md` § constraint reconcile** described the differ's two
  inverse passes without the row-image modes they now thread. Added, with the pin.
- **`docs/sql-alter.md` § RENAME COLUMN** said the inverse clause is inert to "this
  propagation", reading as column-verb-only when Arm B covers `RENAME TO` too. Now says
  both verbs, and links the deep doc.
- **The differ's inverse reconcile had no test** — the handoff flagged it as covered only
  by "existing suites + store round trip", and it is the one arm whose failure is silent
  (a spurious constraint drop+recreate rather than an error). Added
  `test/logic/50.2-declare-schema-renames.sqllogic` §25: a table called `"new"` gets a
  column renamed in the same diff as another table carrying `check (new.w > 0)` over its
  own row. Asserts the diff emits **only** the rename, converges to empty on re-diff, and
  leaves the other table writable with its CHECK enforcing. Verified it pins the arm: under
  the old two-state walk the declared `new.w` would inverse-rewrite to `new.v`, mismatch,
  and emit an extra statement.

## Found and dispositioned — not a defect

- **The handoff's "generated-body Arm A has no sqllogic case" gap is not a gap.** Attempted
  to close it end-to-end and found the engine rejects the shape outright:
  `g integer generated always as (new.v * 2)` fails with `new.v isn't a column`. A generated
  body therefore cannot carry a foreign row-image qualifier at all, so there is nothing to
  corrupt. Recorded as a comment on the affected sqllogic section and on the matrix spec's
  generated cell (which pins the walker helper's contract, not an authorable shape).
- **`matchesRowImage`'s `col.schema !== undefined` guard is unreachable** — the caller
  handles schema-qualified refs in an earlier branch (`column-rename.ts:1089`). Left in
  place: it sits beside `isQualifierReboundAboveSeed`, which the implementer already
  documented as a deliberate belt-and-braces guard for future call sites, and the same
  argument covers it.
- **The declarative differ emits unquoted identifiers for a table named `new`**
  (`ALTER TABLE new RENAME COLUMN v TO w`, observed while writing §25). `new` is not a
  reserved word in this parser, so the statement round-trips and applies; the general
  identifier-quoting question is out of this ticket's scope and belongs to whoever owns DDL
  rendering. Noted here rather than filed, since nothing is broken today.

## Tripwires (recorded, not ticketed)

- `renameNewQualifiedRefs` skips `inverse` subtrees but deliberately not `defaults`: a
  nested select's `with defaults` entry expression owns no written-row scope (the inverse
  validator never descends one), so shifting a `new.` ref inside one is inert either way.
  If `with defaults` ever gains a written-row scope, that walk needs the same skip. Parked
  as a `NOTE:` on `renameNewQualifiedRefs` in `schema/rename/column-rename.ts`.
