# What landed

`ALTER TABLE … RENAME TO` already guaranteed that a reference it **rewrites**
still resolves to the renamed table. It now guarantees the other half: a
reference it does **not** rewrite still resolves to whatever it resolved to
before.

A rename also *creates* a name, and that new name can capture a reference in a
body whose text never mentions the renamed table:

```sql
create table main.k (id integer primary key, x integer);      -- 1, 10
create table temp.other (id integer primary key, x integer);  -- 99, 999
create view temp.v as select id, x from k;   -- bare `k` falls through to main.k

select * from temp.v;                -- [{"id":1,"x":10}]
alter table temp.other rename to k;  -- temp now holds a `k`
select * from temp.v;                -- was [{"id":99,"x":999}] — now [{"id":1,"x":10}]
```

One new arm at `renameTableInAst`'s sink: for a reference the walk did **not**
match, compare `resolve(ref.schema, ref.name)` with `resolveAfter(...)`; when
they differ, schema-qualify the reference to the schema its *before*-answer
named. Qualification stays conditional in both arms, so an unrelated rename
still leaves every body byte-identical and no materialized view's `bodyHash`
churns.

The arm is turned OFF for schema-authored expressions (CHECK constraints, column
DEFAULT / generated bodies, partial-index predicates) via
`TableRenameOpts.schemaAuthoredBody`, because those ASTs are deliberately walked
more than once by the rename and the untouched arm is not idempotent.

### Major — one filed (as an arm on an existing ticket)

**The declarative schema differ does not converge after this fix, and its second
apply undoes the pin.** `repro: verified` — reproduced end to end, with the
default session `schema_path` and no pragma, then confirmed by stubbing the new
arm out (the divergence disappears, and the original silent re-bind returns).

```sql
create table main.k (…); create table temp.other (…);
create view temp.v as select id, x from k;        -- means main.k

declare schema temp {
  table k { … } with tags ("quereus.previous_name" = 'other')
  view v as select id, x from k
}
diff schema temp;   -- [ALTER TABLE "temp".other RENAME TO k]            ← correct
apply schema temp;  -- live body becomes `select id, x from main.k`      ← the pin works
diff schema temp;   -- [DROP VIEW IF EXISTS "temp".v, create view "temp".v as select id, x from k]
```

`apply schema` no longer converges in one pass, and applying that second diff
restores the bare `k` — which now binds `temp.k`, so the view silently starts
reading the other table again.

Not filed as a new ticket. The root cause is one code site —
`inverseRenamedViewParts` in `schema-differ.ts` — and
`tickets/implement/5-rename-preserves-qualifier-meaning.md` is already open
against exactly that site for the *alias* artifact the same forward walk will
add. Per the site-claim rule, the finding was appended there as a second arm,
with the measured repro, why the alias rule and the old "accept a qualifier equal
to `schemaName`" idea both fail to cover it, the two candidate resolutions, and
its own TODO items. That ticket has this one as a `prereq`, so it lands next.

Net effect is still an improvement: before this ticket the view re-bound
silently and immediately; now it re-binds only if a second `apply schema` runs.

### Verified, no defect found

- **The `schemaAuthoredBody` claim is airtight** — the thing the handoff asked to
  attack hardest. `schemaAuthoredContext` pins `schemaPath = [schemaName]` for
  all four schema-authored kinds, and a column DEFAULT set via `ALTER TABLE …
  ALTER COLUMN … SET DEFAULT` writes the same `col.defaultValue` field the walk
  covers, so it takes the same path; generated columns likewise
  (`building/insert.ts:352`). A second, independent reason turned up for the
  predicate arm: `compilePredicate` rejects a schema-qualified column reference
  outright, so the arm could never have produced a legal predicate there anyway.
- **No fourth re-walk of a home-path body.** Enumerated every `renameTableInAst`
  caller across all packages: view bodies (once, per-schema loop), assertion
  checks (once), MV bodies (once, second global pass), the pre-flight probe (on
  `spineCloneAst` copies — and `spineCloneAst` deep-copies plain objects, so the
  new `.schema` assignment cannot reach the live AST), and the differ's inverse
  pass (same function for `resolve` and `resolveAfter`, so the arm is inert by
  construction). The store module reaches only the three collection helpers, all
  of which now carry the flag.
- **`objectRefKeySchema(before, ref.name.toLowerCase())` is a safe split** — the
  resolver echoes the name it is given into the key at every site that carries
  `qualify`, so the known-length split is exact even for a schema name
  containing a dot.
- **The rejected alternative (eager qualification) was right to reject** — it
  would qualify every cross-schema dependent on every rename, breaking the
  no-churn tests and reversing a decision documented in `store-module-rename.ts`.
- **`assertRenameDependentsPersistable` now vets more bodies**, which is correct
  rather than a regression: those bodies genuinely get rewritten and re-persisted
  now, so a module that would refuse one must still refuse the statement.
- **Source hygiene.** `table-rename.ts` is 855 lines, below the files
  `debt-oversized-source-files` tracks (`schema-differ.ts` at 2,846,
  `alter-table.ts` at 2,419); not worth an arm.

### Test coverage added

Both gaps the handoff listed honestly are now closed:

- **Walk-order hazard across all three helpers.** The re-apply-is-a-no-op test
  covered only `renameTableInCheckConstraints`. Generalized to a case list over
  all four schema-authored shapes (CHECK, partial-index predicate, column
  DEFAULT, generated column), so a refactor that drops `schemaAuthoredBody` from
  any single helper fails here rather than only in whichever shape some engine
  test happens to exercise.
- **MV reading the captured name through a view chain** (`main` MV → `temp` view
  → captured bare name), asserted after a `refresh` so the already-materialized
  rows cannot mask a re-bind. The chain is correct only because the view was
  pinned — the MV itself is never rewritten.

Two gaps stay open, deliberately:

- **`RENAME COLUMN` has no analogue of this arm** — out of scope here, and not
  investigated by either pass. Not filed: nobody has established there is a
  reachable defect, and filing an uninvestigated suspicion as a ticket is worse
  than not filing it.
- **`CREATE TABLE` / `DROP TABLE` shift bare names identically** with no
  propagation pass to hang a fix on. Recorded as a Known limitation in
  `docs/sql-alter.md` by the implement pass; left there.

### Tripwires

One recorded, as a `NOTE:` at the sink in `table-rename.ts`: the untouched arm
asks the resolvers about every reference, where the rewrite arm short-circuits on
a bare-name compare first. The arm can in fact only fire on a reference spelling
the NEW name (the two resolvers differ only over the renamed schema's name set,
and the old-name direction is either the rewrite arm's or unchanged), so an
`eq(ref.name, newName)` guard would be equivalent and cheaper. Declined for now —
it trades two Set lookups per reference on a DDL-only path for a claim that
silently loses coverage if the `resolve`/`resolveAfter` pair ever differs more
broadly than one table rename. The NOTE says to add the guard if rename
propagation over a schema-heavy catalog ever measures hot.
