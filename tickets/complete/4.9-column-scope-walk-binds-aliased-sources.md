# What changed

`ALTER TABLE … RENAME COLUMN` and `ALTER TABLE … DROP COLUMN` share one
scope-aware walk (`schema/rename/column-rename.ts`) that decides "does this
stored expression reference this column?". That walk used to treat a FROM source
carrying an alias (`from t as a`) as contributing **no columns to unqualified
name resolution**, so a bare `x` written against `from t a` was invisible to both
verbs. Dropping the column was then allowed while a live rule read it, and
because assertions recompile on every commit, the orphaned rule went on to reject
every write to the whole database.

The fix is a representation change, not a widened predicate. `ScopeFrame`'s two
maps — `unaliased` (bare names) and `aliasMap` (aliases) — became one:

```ts
interface ScopeFrame {
	/** Lowercase qualifier → resolved object key, one entry per FROM source. */
	qualifiers: Map<string, string>;
	…
}
```

Every FROM source exposes exactly one qualifier: its alias when it has one, its
bare name otherwise, and every entry binds unqualified names. After the merge
there is no second map for a future edit to consult "the unaliased ones" — the
wrong question can no longer be asked. `isTableInUnaliasedScope` is now
`unqualifiedRefBindsTarget`; `frameBindsTargetUnaliased` is now
`frameBindsTarget`. Duplicate qualifiers inside one FROM bind first-write-wins
via `bindQualifier`, matching how the planner resolves a qualified column.

Headline shapes, all correct now and all broken before:

```sql
create assertion a1 check (not exists (select 1 from t a where x < 0));
alter table t drop column x;      -- REFUSED (was accepted; database then unwritable)

create view v as select * from t a;   -- republishes x through a star over an alias
create view w as select x from v;
alter table t rename column x to z;
select * from w;                  -- returns a `z` column (was: Column not found: x)
```

### Major — one, already filed

*(first pass)* The handoff flagged its `bindQualifier` ordering claim as the part
of the diff with the least prior art, and the independent check found the claim
correct but incomplete. The planner resolves a qualified **column** over a
duplicated FROM qualifier to the first such source, which is what `bindQualifier`
now matches — but it expands a qualified **star** by name-matching *every*
source, so `select t.* from u as t join t` yields both sources' columns. The
engine disagrees with itself, and a view built that way is missed by the rename
cascade (verified end-to-end: the view's published name shifts, its reader is
never re-targeted, and `select * from w` then errors).

Climbing to the invariant rather than the instance: the fix is to reject a
duplicated source name where a FROM clause's sources are collected, after which
the question stops existing. Filed as
`backlog/bug-duplicate-from-qualifier-resolves-inconsistently` (severity
`wrong-result`, likelihood `contrived`, `repro: verified`). Not fixed in this
pass — it is a planner-side change, pre-existing, and out of this ticket's scope.

The handoff's other two honest gaps needed no new ticket: the subquery-source
residual (gap 2) was already appended as an arm to
`backlog/bug-column-verbs-blind-to-star-over-subquery-source` during implement,
and the missing function-source cell (gap 3) is unauthorable rather than
untested.
