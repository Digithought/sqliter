# What landed

## 1. `yarn bench:gate` is in `yarn check`

Root `package.json` gains a `"bench:gate": "cd packages/quereus && yarn bench:gate"`
passthrough, matching the existing `test:store` / `test:fork-strict` pattern, and the
`check` chain becomes:

`docs:check → lint → build → typecheck → bench:gate → test:full → fork-strict →
context-strict → repr-strict`

The gate sits **after `typecheck`, before `test:full`** — a deliberate departure from the
plan ticket, which assumed the end of the chain. The chain is `&&`-chained, `test:full` is
by far its longest step, and the gate needs only the `dist/` that `build` two steps earlier
produced, so a changed counter surfaces in about a minute instead of after the whole test
run. The reason is recorded in the `//check` NOTE in `package.json`, in
`docs/architecture.md` section 6, and in `docs/benchmarking.md`.

## 2. Four ratio guards (three new)

All bounds set from a full `yarn bench` on an unchanged tree; the measured ratio is
recorded in a comment beside each guard.

| Guard | Measured | Bound | Headroom | Catches |
| --- | --- | --- | --- | --- |
| `execution/correlated-subquery` / `hand-batched-peer-count` (pre-existing; gained a `note`) | 1.00× | 10× | 10× | `scalar-agg-decorrelation` failing to fire |
| `execution/filtered-scan-index-10k` / `full-scan-10k` | 0.010× | 0.1× | 10× | index access selection collapsing to a full scan |
| `store/multi-seek-pk-10` / `store/point-read-pk` | 2.00× | 8× | 4× | per-key cost creeping into batched multi-key resolution |
| `store/index-resolve-four-batches` / `store/index-resolve-one-batch` | 2.37× | 8× | 3.4× | index-then-fetch resolution going superlinear in row count |

`store.bench.mjs` had no `ratioGuards` export before; it has one now, with a header
comment explaining why a ratio guard is worth having on rows that already assert exact
storage round trips (the counter asserts see *changed* round trips; a ratio sees the
round-trip count staying right while the work behind each one gets more expensive).

## 3. Documentation

`docs/benchmarking.md`: intro no longer claims the suite is outside `yarn check`; benchmark
counts corrected (73 → 92 total, `execution` 30 → 45, `mutation` 8 → 12, "two backends" →
three); *Regression gate* rewritten as two passes with `--report-only`, the `yarn check`
placement and its cost; *Ratio guards* gains a field reference, sub-1 bounds, cross-suite
names, load-time validation and the measure-then-bound rule; a new
*Which check catches what* section stating the division of labour between the performance
sentinels, the gate and `yarn bench`; *Exit-code contract* rewritten.

`docs/architecture.md`: benchmark count 90 → 92 in both places in section 5; the
`ratioGuards` bullet expanded into a real description of the guard pass; section 6's chain
updated with `bench:gate` and the ordering rationale.

# Measured cost (AMD Ryzen AI 9 HX 370 / NVMe / Windows 11, node 24.2)

- Gate counters pass: 25 s. Gate guard pass: 9 s across 8 forked processes.
- Total added to `yarn check`: ~35 s, confirmed on three separate review runs

## Filed as a ticket (major)

- **`docs/benchmarking.md` is 489 words from a hard 12000-word cap with no grace band, and
  this change is what put it there** (10322 words before the commit, 11511 after).
  `docs:check` is the *first* step of `yarn check`, so whoever trips the cap gets a build
  failure before anything else runs, and `bench-leveldb-read-cost-outcome` — still in
  `implement/` — adds to this same file. Filed `debt-docs-split-benchmarking` in the
  backlog, as a sibling of the existing `debt-docs-split-runtime`, which describes the same
  problem for `docs/runtime.md`. Not fixable inside this ticket: choosing the seam is real
  design work and every inbound anchor link has to keep resolving.

## Recorded as a tripwire, not a ticket

- **The degenerate-median fallback in `guards.mjs` assumes a bound above 1.** When both
  medians round to zero the code collapses the ratio to 1, which reads as `ok` under a
  bound above 1 and as a **failure** under the sub-1 bound this ticket introduced. It is
  unreachable rather than wrong — calibration batches a benchmark until one sample clears
  clock resolution, so no median reaches zero — so a `NOTE:` at the site now says what to
  change (make the degenerate case `not-evaluated`) and the one condition that would make
  it matter: a *pinned* benchmark (`iterations` set, skipping calibration) at sub-clock cost
  with a sub-1 guard over it.

## Considered and declined

- **A test asserting the real suites' guards name benchmarks that exist.** It would catch a
  guard typo or a benchmark rename in `yarn test` instead of in the gate. Declined because
  loading the real suites imports `packages/quereus/dist/`, which `yarn test` does not
  build — `bench-backends.spec.ts` states that synthetic-fixtures-only rule explicitly and
  the whole `bench-*.spec.ts` family follows it. The invariant is already mechanized
  anyway: a guard naming a benchmark that does not exist is a `misconfigured` verdict, which
  fails the gate, which now runs in `yarn check`.
- **Dropping the `store/multi-seek-pk-10` guard** (the implementer asked for a judgement
  call on it). Kept. Across three review runs at the gate's reduced calibration it read
  3.16×, 2.31× and 2.30× against a bound of 8× — wider than the other three, but still 2.5×
  clear at its worst, with the full-calibration re-measure (2.00×) as the backstop. It costs
  two forks and covers the one thing the exact counter asserts structurally cannot see:
  round-trip counts staying right while the work behind each round trip grows. The `NOTE:`
  at the site already says the fix for chronic re-measuring is more samples, not a higher
  bound.
- **A regression test that `yarn check` still contains `bench:gate`.** No test in this
  repository asserts anything about root `package.json` scripts, the chain is one visibly
  readable line, and inventing a package-manifest test harness for one string is more
  machinery than the risk warrants.

## Not fixed, and why

- **`yarn check` has still never been run end to end.** A clean `build` plus `test:full`
  plus the three strict passes runs well past the 10-minute ceiling for a single agent
  command, so it is not agent-runnable. The residual risk was narrowed rather than removed:
  the exact new adjacency `yarn typecheck && yarn bench:gate` was run as one chained command
  from the repo root and passed, which exercises both yarn-script resolution across the
  `&&` and the new passthrough; `docs:check`, `lint`, `typecheck` and `yarn test` each pass
  individually. Unproven: `build`, `test:store`, and the three strict passes in one
  uninterrupted chain. **A human should run `yarn check` once on a clean tree.**
- **`execution/filtered-scan-index-10k` has a very wide spread** at the gate's reduced
  calibration (104% on one review run, 85 µs row batched ×4). Its ratio read 0.01× and 0.02×
  against a 0.1× bound, so it is 5-10× clear and poses no false-red risk; left alone. It is
  a poor choice if anyone ever wants a guard member that is merely *stable*.
- **`store.bench.mjs` is 1690 lines** and this change added 55 to it. Not filed:
  `debt-split-store-bench-suite` already owns that site.
