# What shipped

Two symptoms of one theme: a foreign key that **cannot be enforced** must say so at the
moment it matters, instead of failing obscurely or falling silent.

## Arm A — parent table does not exist: the message names it

Behaviour is unchanged (MATCH SIMPLE admits a row with any NULL FK column; everything
else is rejected). The text changed, from

```
CHECK constraint failed: _fk_ghost_c_c (NEW.c is null or 0)
```

— both halves engine-synthesized, meaningless to whoever wrote the schema — to

```
CHECK constraint failed: _fk_ghost_c_c — referenced table 'main.ghost_parent' does not exist
```

`ConstraintCheck` gained an optional `violationMessage`, carried into
`ConstraintMetadataEntry` and returned verbatim by `constraintViolationMessage`, which is
the single source of truth for both the immediate (row-time) and deferred (commit-time)
report paths. One producer today: the `!parentSchema` branch of `buildChildSideFKChecks`.
The `CHECK constraint failed:` prefix is kept deliberately — downstream consumers key off
it — and only the expression hint is replaced.

Naming the **schema** is load-bearing: an unqualified parent binds to the child's own
schema, so a child in an attached schema referencing a `main` table resolves to nothing.
The schema in the message is what makes that diagnosable; the remedy is to qualify.

Not a `CREATE TABLE` refusal — forward references stay legal, and resolution is per plan,
never cached from creation.

## Arm B — column-count mismatch: raise instead of skip

Enforcement sites used to `continue` past a foreign key whose child column count did not
match the resolved parent key, leaving it **declared but not enforced**. The defaulted
`references <parent>` form is the gap: it resolves to the parent's primary key, whose
arity is not knowable at declaration time (forward references are legal, the key can
change later), so the declaration builders cannot catch it — only the enforcement seam
can.

New shared `resolveReferencedColumnsForEnforcement(fk, parentSchema, childSchema)` in
`schema/table.ts` wraps `resolveReferencedColumns` with the arity check and raises:

```
Foreign key '_fk_mm_c_x' on table 'main.mm_c': 1 column(s) reference the primary key of 'main.mm_p', which has 2 column(s).
```

Every enforcement site routes through it: both FK check builders, the batchability gate,
the three `foreign-key-actions.ts` sites (cascade dispatch, transitive pre-walk, RESTRICT
pre-check), and `validateForeignKeyOverExistingRows`. Introspection and optimization
callers stay on the lenient resolver — a malformed key must not break a read query or a
catalog listing.

## Review-stage additions

- The batchability gate `getBatchableRestrictFks` now takes the `Database` and checks
  `pragma foreign_keys` itself (see findings — it was raising with enforcement off).
- `docs/sql-ddl.md` § 7.1 documents the all-columns primary key a table with no declared
  key receives, and § 7.6 warns that `references <parent>` against such a parent is a
  reference to *every* column.
- `docs/runtime.md` § Batched RESTRICT states the gate's pragma and raise contract.
- Test file grew arms B4 (pragma off on both sides), B5 (CASCADE / SET NULL dispatch),
  B6 (`alter table … add constraint`).

# Review findings

## Fixed in this pass

- **`pragma foreign_keys = off` did not silence arm B on the parent side.** The runtime
  DML executor (`runDelete` / `runUpdate`) calls `getBatchableRestrictFks` with no pragma
  check in front of it — the pragma was re-checked only at flush — so after the implement
  change, a `delete from parent` raised the arity-mismatch error while enforcement was
  supposed to be off entirely. Reproduced as a failing test before fixing (stack:
  `resolveReferencedColumnsForEnforcement` ← `getBatchableRestrictFks` ← `runDelete`).
  Fixed at the rung above the instance: the gate now takes `db` rather than a bare
  `SchemaManager` and checks the pragma itself, so no caller can forget it — the three
  plan-side callers already did, the two runtime ones did not. Pinned by arm B4, which
  covers both parent-side ops and the child side with the pragma off.

- **Documentation of the primary-key default.** Quereus gives a table declared with no
  `primary key` an all-columns key. That is what a defaulted `references <parent>`
  resolves against, so `references p` against a three-column PK-less parent is a
  three-column reference — a realistic way to meet arm B's new hard failure, and it was
  documented nowhere. Added to § 7.1 with a pointer from § 7.6.

## New coverage for gaps the implement stage flagged

- **Arm B on the propagating actions.** B5 covers `on delete cascade` and
  `on update set null` against a mismatched key: both raise, neither cascades nowhere.
  Note the raise arrives from the runtime `foreign-key-actions.ts` dispatch, not the
  plan-time parent-side builder — that builder filters non-RESTRICT actions out *before*
  resolving, so the runtime site is the only one covering these two actions.

- **`validateForeignKeyOverExistingRows`.** B6 pins the ALTER-ADD-CONSTRAINT path onto the
  shared wording, and that the refusal leaves nothing behind (a correctly-shaped ADD over
  the same rows then succeeds and enforces).

## Checked and cleared

- **The lenient-vs-strict caller split**, which the implement stage named as the main thing
  to be skeptical of. Read each of the three optimization callers it was least sure about:
  `planner/util/ind-utils.ts` (~98, ~181) and `planner/util/key-utils.ts` (~600) `continue`
  past a mismatched key, which drops an inclusion-dependency / key claim — strictly less
  information, never a narrower plan; `planner/mutation/multi-source.ts` (~3253) returns
  `false`, which makes the view decomposition *more* conservative. All three fail safe, so
  the split holds. (Unrelated observation, pre-existing and out of this diff:
  `multi-source.ts` does not wrap the resolver in `try`, unlike the other two, so a
  foreign key naming a parent column that does not exist would throw on a read path there.)

- **Cross-backend.** The 41.x logic files, including the new one, pass under `test:store`
  as well as memory.

## Tripwires recorded, not filed

- `getBatchableRestrictFks` — a `NOTE:` at the gate records that the trust-the-origin
  RESTRICT suppression (`db._isFkRestrictSuppressed()`) is deliberately **not** part of it:
  a malformed key is malformed on both ends of a sync pair. If an apply-path write ever
  needs to survive a receiver-only malformed foreign key, that is the site to widen.
- `core/derived-row-validator.ts` (~264) — the implement stage's own `NOTE:` stands: the
  maintained-table loop ignores `violationMessage` in favour of its table-attributed error,
  which already names the missing parent. Correct while there is one producer.

## Filed

- `tickets/backlog/debt-lens-logical-fk-arity-mismatch-silently-unenforced.md` — the same
  class survives on the lens path: `findLogicalParentFkRefs`
  (`schema/lens-fk-discovery.ts` ~254) logs and skips a logical foreign key whose arity
  does not match, so its parent-side RESTRICT and cascade are silently unenforced. It
  resolves parent columns by name through a different function, so this ticket's resolver
  could not sweep it along. Filed at the higher rung — refuse it at `apply schema`, where
  both logical tables are already known — rather than as a point fix at the skip.

## Nothing found

- **Message plumbing.** `violationMessage` reaches both the immediate and deferred report
  paths through the single `constraintViolationMessage` seam; the test file asserts the
  identical full string on both. No second producer exists to disagree with it.
- **Resource cleanup / async correctness.** The diff adds no resource ownership; the
  schema-switch `try/finally` in `buildChildSideFKChecks` is untouched and still restores
  the current schema on the new raise path.
- **Source hygiene.** No file grew materially: `foreign-key-builder.ts` 536 lines,
  `row-constraints.ts` 383, `schema/table.ts` 1617 (already the largest, +38 for the shared
  resolver, which belongs beside the lenient one it wraps). Functions stayed short and
  single-purpose.

# Known residuals

- **Arm B changes behaviour from "silently unenforced" to "statement fails."** That is the
  direction the ticket specified. Any existing schema carrying a mismatched defaulted
  `references <parent>` now breaks on its next write. Nothing in-repo hit it on either
  backend — evidence, not proof.
- **`schema/lens-fk-discovery.ts` stays lenient**, now tracked by the backlog ticket above.
- **A3's explicit-transaction arm does not isolate COMMIT.** The sqllogic runner executes
  `begin; … commit;` as one block and matches the error anywhere in it, so that arm proves
  the transaction aborted with the right text, not that the throw came from the deferred
  queue specifically. The deferred path is covered by construction (a child-side FK
  auto-defers under ABORT); pinning the COMMIT seam itself needs a spec-level test.
