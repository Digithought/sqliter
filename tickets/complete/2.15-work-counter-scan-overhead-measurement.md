# What this was

Measurement-only ticket. No engine code changed. `work-counter-vtab-boundary` (in
`tickets/complete/`) added one per-scan local and one per-row `if (tableCounters)`
branch to `emitSeqScan` in `packages/quereus/src/runtime/emit/scan.ts`. This ticket ran
the benchmark suite before and after that change to put a number behind the "counters
are free when off" claim.

# Methodology

`yarn bench` (`node bench/run.mjs`) requires the built `dist/` — suites `import` from
`../../dist/src/index.js`, not the TypeScript source — so each side of the comparison
was `yarn build` then `node bench/run.mjs` from `packages/quereus`, one after the other
in the same shell session on one machine (AMD Ryzen AI 9 HX 370, 24 cores, win32).

- **Baseline**: `1287905a1` — the literal git parent of `e47a1a7f6`, the commit that
  touched `scan.ts` (`git rev-parse e47a1a7f6^`).
- **Current**: `ea5f8ddae` (HEAD at the time — includes the review-stage rework of the
  same code, same logic reordered).
- `git diff --stat 1287905a1 ea5f8ddae` confirms this isolates exactly the
  `work-counter-vtab-boundary` diff (`scan.ts`, `dml-executor.ts`, `work-counters.ts`,
  tests, docs) plus this ticket's own file — nothing else.

**False start worth recording:** the first attempt used the last commit that touched
`scan.ts` before the change (`a268fbd0f`, found via `git log -- scan.ts`) as "parent".
Eight unrelated commits sit between it and the change, and the comparison produced
nonsense deltas — -50% to -80% on `parser/*` and `planner/*` benchmarks that
`emitSeqScan` cannot touch. That run also had no baseline `environment` block, which was
the tell. This lesson is now written into `docs/benchmarking.md` (see review findings).

**No regression. No gated change of any kind** — the run's own summary:
`{"no-change":24,"changed":1,"improvement":0,"regression":0,"unstable":2,"new":0,
"missing":0,"filtered":0,"failed":0}`, `regressions: 0`, `failures: []` in both runs,
and the `correlated-subquery / hand-batched-peer-count` ratio guard passed both sides
(1.02× and 1.01× against a 10× bound).

The scan-heavy rows most relevant to `emitSeqScan` — `full-scan-10k`,
`filtered-scan-index-10k`, `text-pk-range-scan-10k`, `text-pk-point-seek-10k`,
`join-1kx1k`, `correlated-subquery`, `hand-batched-peer-count` (the last three are
nested-loop-join shapes, i.e. the ones that exercise the per-row branch hardest via one
`queryCalls++` per re-scan) — all land inside their noise floor or improve. This matches
the prediction: the change removed a per-connect string allocation (the deferred-rename
key, now built once in the emitter closure) and added one already-undefined property
read plus one constant-false branch per row, so if anything the net is a hair cheaper.

`join-1kx1k` shows a -10.3% delta, which clears the 10% minimum but is excluded from
gating because the *baseline* run was itself unstable (20.6% spread) — per
`docs/benchmarking.md`, "a benchmark unstable in either run is never a regression [or
improvement]". Read as a data point, not a verdict: an improvement-direction number on a
noisy benchmark.

`parser/insert-values` is the one `changed` row: +5.7% against a 5.0% floor, below the
10% gate. `emitSeqScan` is not on the parser's path at all, so this is run-to-run drift,
not a cost of the change.

## Review findings

**Verified, not re-run.** The claims were checked against the two result files on disk
rather than by re-benchmarking, because a re-run on a differently-loaded machine
measures the machine, not the change (`docs/benchmarking.md` § "What the floor cannot
see"). Every checkable claim held:

- `git rev-parse e47a1a7f6^` = `1287905a1`, matching the stated baseline; both result
  files record the commit the ticket claims and `dirty: false`, so neither side was
  measured against a modified tree.
- Both runs contain the same 27 benchmarks — no `new`, `missing` or `filtered` rows
  hiding a coverage gap between the two sides — and `failures: []` in both.
- The summary counts, `regressions: 0`, and the two `unstable` exclusions in the ticket
  match the JSON exactly. The ratio guard passed in both runs.
- The narrative claim about *why* the change should be free matches the actual diff
  (`git diff 1287905a1 ea5f8ddae -- .../scan.ts`): the qualified-name string moved into
  the emitter closure, and the added per-row work is one `if (tableCounters)` on a local
  that is undefined whenever metrics are off.

**Corrected in this pass (minor):** the implement-stage table folded all eight `parser/*`
and `planner/*` rows into one "no change" line, but `parser/insert-values` was actually
classified `changed` (+5.7% vs a 5.0% floor, still below the 10% gate). The overall
verdict is unaffected — no gated change, no regression — but the table now reports that
row honestly.

**Fixed inline (minor):** the implement stage flagged its false start as "worth a line in
`docs/benchmarking.md`" and left it undone. Added `### Measuring one commit's cost` to
`docs/benchmarking.md` — use `git rev-parse <commit>^` for the "before" side, never the
previous entry from `git log -- <path>`; confirm the isolation with `git diff --stat`;
build and run both sides back to back on one machine.

**Major findings: none.** No ticket filed. This ticket changed no engine code, so there
is no implementation to find defects in; the measurement's methodology and its arithmetic
both check out against the recorded data.

**Tripwires: none recorded.** Nothing here is conditional-on-a-future-state. The one
durable lesson (how to pick a baseline commit) is a procedure, so it went into the
benchmarking doc where the next person running a before/after comparison will meet it,
rather than into a `NOTE:` at a code site.

**Validation.** `yarn lint` clean. `yarn test` clean (exit 0, 10m49s). The only
working-tree change from this review is markdown (`docs/benchmarking.md`), which neither
can be broken by.
