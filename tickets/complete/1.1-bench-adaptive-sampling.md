# What shipped

Every benchmark used to be timed by the same recipe — a hand-written warmup count
and iteration count, 3 and 10 by default. A 4 µs parser call and a 190 ms bulk
insert got the same ten samples, so the fast ones measured mostly clock and the slow
ones wasted seconds. Nothing reported how noisy any result was.

Now each worker sizes its own timing loop and every row carries a dispersion figure.

**Calibration** (`bench/lib/calibrate.mjs`), in order, inside the worker after `setup`:
warm up by elapsed duration (250 ms target, `minWarmup: 2` runs first regardless) →
size an inner batch on the *warmed* function until one sample clears 1 ms → buy
`ceil(1000 ms / sampleMs)` samples, clamped 5..500 → stop early on a 5 s ceiling,
but only once 5 samples are in hand. Every knob is one commented `CALIBRATION`
object. An explicit `iterations`/`warmup` still wins, skips calibration, and is
reported as `pinned`.

**Dispersion** (`bench/lib/stats.mjs`): `relativeIqr` = `(p75 - p25) / median`, chosen
over coefficient of variation because these distributions carry GC and tier-up
outliers that inflate a standard deviation without describing the typical iteration.
`summarize` gained `spread_pct`, `stable`, `samples`, `batch`, `warmup`, `pinned`;
`min_ms`/`max_ms` became `min_sample_ms`/`max_sample_ms` (for a batched benchmark
those extrema are batch means); `p95_ms` is gone, because at these sample counts
nearest-rank p95 printed the same number as `Max`.

**Two deliberate deviations from the plan**, both measured, both upheld on review:
warmup is a duration loop rather than a call count derived from a cold pilot (a
50-call cap gave a 4 µs benchmark 0.2 ms of warmup where 250 ms was asked for), and
the batch is sized *after* warmup rather than from that cold pilot (a cold third call
of ~91 µs against a 4 µs steady state sized the batch 18× too small and reported
54.5% spread, almost entirely clock).

# Review findings

## Checked

Read the implement diff before the handoff summary. Scrutinised: the two plan
deviations and their evidence; `sizeBatch` termination; the pinned escape hatch;
`stable`'s sample-count floor and the direction of the `MIN_STABILITY_SAMPLES`
import; source hygiene and module boundaries; whether de-pinning 27 definitions is
safe now that `fn` runs orders of magnitude more times; results-JSON field renames
against every consumer in the repo; docs against the code they describe.

Ran: `yarn lint` (clean), `yarn build` (clean), `yarn typecheck` (clean),
`yarn test` (**13,406 passing, 0 failing** — 13,362 before, plus the 44 added here),
`yarn bench` (**27/27, ratio guard 1.04× against max 10×, 46.8 s**), plus a
`--baseline` run with pinned and unstable markers present.

**The two deviations are the right call and stay.** The evidence in the handoff
holds up and the alternative is worse for exactly the benchmarks calibration exists
to help. Two tests now pin the property rather than the anecdote: warmup must exceed
any plausible call cap on a fast function, and must still run `minWarmup` calls when
one call exceeds the whole target.

**`sizeBatch` cannot loop.** Each iteration either returns or sets
`batch = ceil(batch × max(2, shortfall))` clamped to `maxBatch` — strictly increasing,
and `maxBatch` is accepted unconditionally. Covered by a test using a free function
and an unreachable `minSampleMs`.

**De-pinning is safe for all 27 definitions.** Every execution and planner/parser
benchmark is a read against a `setup`-built database or a pure parse; the four
mutation benchmarks either build and close their own database inside `fn`
(`bulk-insert-10k`, `single-row-insert-1k`, `delete-where-100`) or update and then
reset (`update-where-1k`). None grows state across calls, so batching and a
much larger call count do not change what they measure.

**The results-JSON renames break nothing.** `median_ms` is the only field any
consumer reads (`--baseline` deltas, ratio guards), and it did not change; an old
results file still compares correctly.

**`MIN_STABILITY_SAMPLES` is genuinely one definition** — `CALIBRATION.minSamples`
imports it from `stats.mjs`, and `stats.mjs` imports nothing, so no cycle. A test
asserts the two are equal, so a future edit that duplicates the constant fails.

## Fixed in this pass (minor)

- **A pinned benchmark was silently truncated by the 5 s ceiling.** `collectSamples`
  read `maxTotalMs` from the global config for every plan, so a benchmark pinned to
  more iterations than fit in 5 s would have quietly reported a median for the cheap
  part of its run — in exactly the case (`fn` whose cost grows) the escape hatch
  exists for, and contradicting the code's own claim that a pinned benchmark "keeps
  behaving exactly as it did". The ceiling now lives on the plan, and `pinnedPlan`
  sets it to `Infinity`. Latent, not observed: no benchmark is pinned today.
  Regression test: `runs a pinned plan to completion past any ceiling the same config
  would impose`.
- **Five doc sites described the design that was measured and rejected.** All four
  suite-file `TIMING` headers and `run.mjs`'s module comment said calibration derives
  its numbers "from a pilot measurement of `fn`" — the thing the implementer
  deliberately did *not* do. Rewritten to say warmup is a duration loop and the batch
  is measured on the warmed function. `CALIBRATION.pilotFloorMs` renamed
  `durationFloorMs` for the same reason, and every `CALIBRATION`-lives-in-`child.mjs`
  pointer now names `lib/calibrate.mjs`.
- **`summarize`'s non-empty precondition was undocumented.** `median` of nothing is
  `NaN` and `Math.min` of nothing is `Infinity`; `classify` rejects an empty set
  upstream, but nothing said so at the function. Documented.

## Fixed in this pass (the handoff's largest gap)

**No automated test covered any of the calibration logic** — and none could, because
`child.mjs` runs a benchmark the moment it is imported. Rather than file a `debt-`
ticket for tests against an untestable module, the seam moved:

- **`bench/lib/calibrate.mjs` is new** and owns the whole timing policy (`CALIBRATION`,
  `warmUp`, `sizeBatch`, `samplesFor`, `calibrate`, `pinnedPlan`, `runPinnedWarmup`,
  `collectSamples`). Every function takes an explicit config, so a test can shrink the
  time targets instead of waiting on production ones. `child.mjs` drops from 308 to
  148 lines and goes back to one job: run one benchmark, report samples.
- **`test/bench-calibration.spec.ts` is new** — 44 tests, 144 ms. Stats: median,
  nearest-rank percentile, `relativeIqr` (known value, identical samples, single
  sample, empty, all-zero, zero median with non-zero tail, negative median, non-finite
  quartile), and `summarize` (spread as percentage, stable/unstable either side of the
  threshold, the sample-count floor either side, never-stable-when-null, a sweep
  asserting no field is non-finite, metadata recorded and defaulted). Calibration:
  warmup floor / duration-driven / `maxWarmup` backstop, batch left at 1 / grown /
  terminating at `maxBatch`, `samplesFor` arithmetic and both clamps, plan shape,
  pinned plan defaults and its `Infinity` ceiling, and `collectSamples` counting
  calls, reporting a mean rather than a total, stopping early, and never truncating
  below the stability floor.
- **`bench/lib/` is now inside the type-check.** Added to `tsconfig.test.json` and
  `tsconfig.eslint.json`, which put `stats.mjs`, `calibrate.mjs` and `discover.mjs`
  under `checkJs` for the first time. That surfaced four real `object`-typed holes in
  `discover.mjs`; it now carries `Benchmark`, `RatioGuard` and `Suite` typedefs, so
  the suite-definition shape is stated once and a malformed benchmark definition is a
  type error rather than a runtime surprise. `yarn lint` covers all of this from here.

## Verified, not changed

- **The `--baseline` + markers combination the handoff flagged as unexercised works.**
  Ran a baseline comparison with one benchmark temporarily pinned to 3 iterations: it
  reported `3 pinned iters`, 81.0% spread, and printed
  `+2450.0%  unstable  pinned` with the `Delta` column still aligned — markers trail
  the padded layout and do not disturb it. The temporary pin was reverted; no
  definition carries `iterations` or `warmup`.
- **The `maxTotalMs` early stop and the `maxBatch` ceiling still never fire in the
  real suite** — highest observed batch this run was 610, against a 10,000 ceiling.
  Both are now covered by tests against synthetic functions instead, which is where
  they were always going to be exercised.
- **`execution/full-scan-10k` read 6.5% spread this run**, not the 55.4% the handoff
  saw, with a 9.38 ms median. Consistent with the handoff's own point that
  `unstable` is a property of a run, not of a benchmark — three rows were flagged
  this run (`filtered-scan-index-10k` 21.3%, `text-pk-range-scan-10k` 28.3%,
  `delete-where-100` 22.2%), a different set than the handoff's.

## Tripwires recorded (not tickets)

- **The results JSON has no schema version**, and its field set has already changed
  once. Harmless today because `median_ms` is the only field read and it did not
  change. `NOTE:` at `writeResults` in `run.mjs`: add a `schema` field the moment a
  consumer reads anything else.
- **`bench/results/` is never pruned** — one gitignored file per run, a few KB each.
  `NOTE:` at the same site.
- The `stable` flag measures within-run noise only; a whole run displaced by
  background load still reads as tight. Already carried as a `NOTE:` at the `stable:`
  computation in `stats.mjs` by the implementer, with a live observation
  (`temporal-arith-scan-10k` at 335 ms with 8.6% spread against a settled 95 ms).
  Left as written — environment capture and comparison rules are the next ticket's job.

## Tickets filed

**None.** Everything found was either minor enough to fix here or was the testability
gap, which was better answered by moving the module seam than by queuing a ticket
against code no test could reach. The one thing that would have been a ticket — the
missing calibration tests — is done.

## Not covered

- **`yarn test:store` was not run.** Nothing in this change touches the store path;
  the diff is confined to `bench/`, two tsconfig `include` lists, and one test file.
- **No cross-machine or CI measurement.** Wall-clock is now load-sensitive because
  sample counts derive from a live measurement (the handoff measured 61.6 s loaded
  against 47.4 s settled; this review measured 46.8 s settled). A contended CI runner
  will not take 47 s. That is inherent to adaptive sampling, not a defect.
