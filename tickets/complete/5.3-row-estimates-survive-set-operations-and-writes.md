# What landed

A row-count estimate now survives set operations, async gathers, common table
expressions, remote-query boundaries, the write pipeline, and (added during review)
write-through-a-view.

## Composition rules

Three exports in `planner/util/row-estimates.ts`, each a pure function of the
children's counts and each called twice — once from the node's logical
`estimatedRows` getter, once from its `computePhysical` over the physical child
counts — so the two views cannot drift:

| helper | rule |
|---|---|
| `setOperationRowsFrom(op, l, r)` | `unionAll`/`union` → sum; `intersect` → min; `except` → left |
| `gatherRowsFrom(kind, branches)` | `unionAll` → sum; `zipByKey` → max; `crossProduct` → product |
| `clampRowEstimate(n)` | floor to a whole row, saturate at `Number.MAX_SAFE_INTEGER`, never `Infinity`/`NaN`/negative |

Pass-throughs: `CTENode`, `CTEReferenceNode`, `RemoteQueryNode`, `InsertNode`,
`UpdateNode`, `DeleteNode`, `ConstraintCheckNode`, `DmlExecutorNode`,
`ReturningNode`, and `ViewMutationNode` (its RETURNING relation's count).
Deliberate non-relays: `SinkNode` reports 1 (the statement's changes-count row),
`ViewMutationNode` reports 1 when the mutation is void, `RecursiveCTENode` reports
`undefined`.

## Judgement calls kept

- **`except` with an unknown right branch reports the left count**, not `undefined`
  — the formula never reads the right branch, so there is no unknown input to
  propagate and blanking would discard a sound bound. Locked by a named test.
- **`union` reports the sum.** Correct as an upper bound. Note the implement-stage
  rationale ("a `Distinct` above the union narrows it") was wrong for this
  codebase — `union` deduplicates inside its own emitter, so nothing downstream
  narrows the claim. Corrected in the comments and in `docs/optimizer-costing.md`;
  the number itself is unchanged and still sound.
- **The write family's estimate is an upper bound.** Now verified by a test rather
  than by reading, and the reason is broader than the implement stage recorded —
  see the findings below.

## Review findings

### Verified first, before reading the handoff

Read the implement diff cold, then traced each documented claim to the code that
implements it (the insert / update / delete / constraint-check / dml-executor /
returning / set-operation emitters, `runtime/row-constraints.ts`, and
`PlanNode.computePhysicalFromChildren`). Checked that every new
`computePhysical(childrenPhysical)` reads the index that `getChildren()` actually
puts its source at — all eleven do, including the four nodes whose child list
appends scalar expressions after the source.

### Major — one ticket filed

- **The relay has no guard, and holes remain.** Three tickets in a row have fixed
  this same class by hand, and a sweep of `planner/nodes/*.ts` for a logical
  row-count getter with no matching physical stamp still finds `SequencingNode`
  (no `computePhysical` at all), `SequenceNode` (its `computePhysical()` is
  declared with no parameters, so it cannot see its children) and `BlockNode`.
  Filed `backlog/debt-row-estimate-relay-has-no-guard` at the invariant rung — a
  test asserting the rule for every node class — rather than a point ticket per
  node, with the three nodes listed as its arms.

### Minor — fixed in this pass

- **`ViewMutationNode` never stamped a physical count**, so a write through a view
  lost the estimate. This is inside the ticket's own stated scope ("the whole write
  pipeline") and was missed alongside `ConstraintCheckNode`, which the implementer
  did catch. Fixed: a new `resultChildIndex()` maps `resultRelation()` to its slot
  in `getChildren()` (the separate RETURNING re-query sits after the base ops;
  otherwise the result is the first relational base op), and `computePhysical` now
  relays that child's physical count, or 1 for a void mutation. Two new tests.
- **`ConstraintCheckNode` does drop rows**, contradicting the comment the implement
  stage added to it and to `row-estimates.ts` ("passes each row through or
  throws"). A NOT NULL / CHECK violation whose conflict action is IGNORE makes
  `evaluateRowConstraints` return a skip verdict and the emitter continues past the
  row (`runtime/emit/constraint-check.ts:159`). The number is still a sound upper
  bound, so no behaviour changed — but the write family has two skipping members,
  not one. Corrected at both comment sites and in `docs/optimizer-costing.md`.
- **`docs/optimizer-costing.md` claimed `except all` sums.** No such operator exists
  here — the node's `op` field admits only union, union all, intersect and except —
  and the rule would be wrong if it did. Removed.
- **Two in-code comments went stale with this change and were not updated.**
  `rule-filter-selectivity.ts` still said a Filter "has nothing to multiply above a
  `union`", citing a backlog ticket this work closed;
  `rule-nested-loop-right-cache.ts` still listed set operations, gathers and CTE
  references as nodes that stamp nothing. Both rewritten to the new reality (the
  latter now names the nodes that are genuinely still holes).
- **Optional chaining on a non-optional array at ten new call sites.** The
  `childrenPhysical` parameter is always an array, so `childrenPhysical?.[0]` is
  dead and implies a nullability the contract does not have; all twenty-five
  pre-existing `physicalSourceRows` call sites index it directly. Normalized.
- **A conditional assertion in the new spec** (`if (cte) expect(...)`) would have
  passed silently if the CTE node disappeared from the plan. Made unconditional via
  the existing `rowsAt` helper, which fails when the node is absent.

### Gaps closed with tests

- **The `insert or ignore` upper bound was asserted only by reading the emitter.**
  Now executed: an `insert or ignore` over a table with one colliding key writes 99
  of 100 rows, and the test pins written ≤ estimate and written < 100, so the bound
  direction is verified and the skip is proven to actually happen.
- **Write-through-a-view** — two tests, one for the RETURNING relay and one for the
  void statement's single count row.

Spec is now 38 tests (was 35).

### Gaps deliberately left open

- **`RemoteQueryNode`'s relay is still untested end-to-end** — no in-tree module
  produces one in a test. It is a two-line pass-through identical to the others,
  and building a fake remote module to cover it would test the fixture more than
  the relay.
- **The `zipByKey` and `crossProduct` gather arms** are unit-tested through
  `gatherRowsFrom` but only `unionAll` is exercised through a real optimized plan;
  same reasoning — the arms are pure functions, and the plan-level test would only
  re-check the shared `physicalRows()` call site that `unionAll` already covers.
- **Membership-flag set operations** get the stamp through the same shared
  `physicalRows()` call as the plain shape, so there is no separate code path to
  cover.
- **Plan churn beyond the existing goldens** remains unprobed. No golden `.plan.json`
  changed and no test failed, but no test deliberately exercises "a cache node above
  a `union all` now sizes differently". Worth noting that this direction is now
  *more* live than at implement time: `estimateRightRows` in
  `rule-nested-loop-right-cache.ts` takes the maximum over the right subtree, so a
  `union all` there now contributes the sum of its branches where it previously
  contributed the largest branch, which can push a subtree past
  `maxRightRowsForCaching` and decline a cache it used to take. That is the more
  correct number — a `union all` really does buffer the sum.

### Tripwires parked

- `planner/util/row-estimates.ts`, at the `zipByKey` arm of `gatherRowsFrom` —
  `NOTE:` recording that this is the only arm reporting the LOW end of its
  max-to-sum range while every other arm reports the upper bound, and that now the
  number is stamped physically a low-key-overlap workload could under-size a buffer
  above the gather. Fine today (heavy key overlap is the normal case); move it to
  the sum if it ever shows up.
- `planner/nodes/recursive-cte-node.ts` — the implement stage's `NOTE:` explaining
  why a recursive CTE reports no estimate. Verified accurate and left in place.

### Checked, nothing found

- Child-index alignment for every new `computePhysical` (see above).
- Property loss: each new `computePhysical` returns a partial that is merged over
  the child-derived defaults, so no node dropped its `readonly`, `idempotent` or
  `deterministic` flags by adding a row stamp.
- The other node types in the write pipeline (`SequencingNode`,
  `SetObjectTagsNode`, the materialized-view nodes) — none sits between a write's
  source and its executor, so none was a hole for this ticket's goal.
