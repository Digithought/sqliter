# What landed

## Implement stage

`packages/quereus-store/src/testing/kv-counting-store.ts` collapsed four near-identical
counting test doubles (three subclassing `InMemoryKVStore`, one delegating) into one
`CountingKVStore`, and three near-identical provider factories into one
`createCountingProvider(countedStores, scope?)` - `scope: 'data'` (default) counts only
each table's data store, `'all'` counts every store the provider hands out. The
pass-through base `DelegatingKVStore` moved out of `test/kv-store-doubles.ts` alongside it
and is re-exported from there so existing importers are unaffected. All four symbols are
exported from the `@quereus/store/testing` entry point.

The one subtlety, carried in the class doc comment: `CountingKVStore.getMany` routes
through `defaultGetMany(this, keys)`, NOT `this.inner.getMany(keys)`. Passing `this` keeps
each per-key `get` inside the wrapper's own counted `get`, so a `getMany` of N keys also
advances `getCount` by N - which is what every existing assertion was written against. The
obvious-looking `this.inner.getMany(keys)` would leave `getCount` unchanged after a batched
read, and because most affected assertions are upper bounds rather than exact equalities,
it would have passed almost everywhere and failed only the single exact-equality canary in
`pushdown.spec.ts` (`'and nothing beyond them is read'`).

## Review stage (changes made in this pass)

- **`createCountingProvider` now builds its store names with the shared builders**
  (`buildDataStoreName` / `buildIndexStoreName`) and the reserved `CATALOG_STORE_NAME` /
  `STATS_STORE_NAME` constants, instead of hand-composed template strings.
- **`getStatsStore` now returns ONE unified `__stats__` store** for every table, as the
  `KVStoreProvider` interface specifies, instead of a per-table `schema.table.__stats__`.
- **`DelegatingKVStore` split into its own `src/testing/kv-delegating-store.ts`** - it is
  the base for every double in the package, not a counting-specific class, and
  `test/kv-store-doubles.ts` was importing a general-purpose base out of a file named for
  one specific double.
- **README documents the new exports** with a worked example, in the same
  `@quereus/store/testing` section that already catalogues the conformance batteries.
- A `NOTE:` tripwire on the provider, plus small hygiene fixes (duplicate import/re-export
  pair in `kv-store-doubles.ts`, stray double blank line in `key-set-seek-store.spec.ts`).

## Review findings

**Checked:** the full implement diff, read before the handoff summary; the `KVStore` /
`KVStoreProvider` contracts the new double claims to implement (every interface member,
optional members included); every call site of the moved/renamed counter fields across the
five touched specs; the specs' own leftover imports for staleness; whether the extraction
left other duplicates behind; `README.md` and `docs/store.md` against the new exports;
tickets across all stages for a prior claim on these files.

**Fixed in this pass (minor):**

- *Store names were hand-composed.* `createCountingProvider` built the `schema.table` and
  `schema.table_idx_index` names itself with template strings. The real builders also
  lowercase, and every real provider is held to using them by the `runStoreNameDistinctness`
  battery published from this very directory. A mixed-case table name would have put the
  double on a store no real backend would have used, and two spellings of one table would
  have got two stores. No current spec uses a mixed-case name, so nothing was failing - but
  this is published test-support code now, not a private copy inside one spec. Switched to
  the builders.
- *Per-table statistics stores.* `getStatsStore` handed out one store per table; the
  interface documents a single unified `__stats__` store whose schema/table arguments are
  ignored, and the rename path (`store-module-rename.ts`) re-keys a table's stats entry
  assuming it stays in that one store. Any future spec using this provider to exercise
  rename would have silently lost stats. Now returns one store.
- *File named for the wrong thing.* `DelegatingKVStore` - the base for all six doubles in
  the package - lived in `kv-counting-store.ts`, so `test/kv-store-doubles.ts` imported its
  general base from a counting-specific module. Split into `kv-delegating-store.ts`.
- *Docs were stale.* The README section that catalogues `@quereus/store/testing` export by
  export said nothing about the three new public exports. Added a paragraph with a worked
  example, including the `getMany`-through-`get` caveat a benchmark author needs.
- *Hygiene.* `kv-store-doubles.ts` both imported and separately re-exported
  `DelegatingKVStore` from the same path; `key-set-seek-store.spec.ts` was left with a
  double blank line where the deleted class had been.

**Filed as a ticket arm (major, already-claimed site):** the same package still has ~44
copies of a plain `createInMemoryProvider()` across its specs (counted with
`grep -rn "function createInMemoryProvider" packages/quereus-store/test`) - a far bigger
instance of exactly the duplication this ticket attacked.
`tickets/backlog/debt-store-test-shared-inmemory-provider.md` already owns that site, so
per the "Nth instance is evidence, not a new ticket" rule an arm was appended to it rather
than a new ticket filed. That arm records the two variant questions this review settled
(use the name builders; one unified stats store) and carries forward the third
counting-double shape still sitting in `test/unique-constraints.spec.ts`, which the
implement stage flagged and deliberately left alone.

**Recorded as a tripwire, not a ticket:** `createCountingProvider` implements neither
`deleteIndexStore` nor `deleteTableStores` (both optional on the interface), so a spec that
drops a table or index and recreates it under the same name would read the dropped store's
entries back. Every spec using it today creates its tables once, so this is conditional,
not a defect. Parked as a `NOTE:` on the factory in `kv-counting-store.ts`.

**Checked and found nothing:** no stale or now-unused imports in any of the five touched
specs (each remaining type import still has live uses - verified by counting occurrences,
not by eye); no resource-cleanup regression (`closeAll` closes both the counted and the
auxiliary maps, as each local copy did); no accepted-tradeoff `NOTE:` at any site touched
here, so nothing was re-litigated; `docs/store.md` mentions `@quereus/store/testing` only
as the home of the conformance batteries and carries no export list, so it needed no
change.

**Not re-verified:** the ~30 individual counter assertions across the five specs were not
hand-traced a second time. The implement handoff is right that a full green Mocha run -
which includes the two assertions specifically constructed to fail if the counters were
wired wrong - is the stronger signal, and that run is green both before and after this
pass's edits.
