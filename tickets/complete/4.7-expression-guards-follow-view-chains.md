# What shipped

`DROP TABLE`, `DROP VIEW`, `DROP MATERIALIZED VIEW` and `ALTER TABLE … DROP
COLUMN` already refused when another table's CHECK constraint, column `DEFAULT`
or `GENERATED ALWAYS AS` body **named** the dropped object. They now also refuse
when that body **reaches** it through any chain of view / materialized-view
bodies, and the refusal quotes the chain:

```
direct    cannot drop table 'main.t': it is referenced by CHECK constraint 'ck' on table 'x' — drop or redefine it first
indirect  cannot drop table 'main.t': CHECK constraint 'ck' on table 'x' reaches it through view 'vv' — drop or redefine it first
direct    Cannot drop column 'v' from 't': it is referenced by CHECK constraint 'ck' on table 'x'
indirect  Cannot drop column 'v' from 't': CHECK constraint 'ck' on table 'x' reaches it through view 'v2' -> view 'v1'
```

The reachability closure was not written here — `schema/object-dependency-closure.ts`
already existed for the assertion guards. This ticket moved the CHECK / DEFAULT /
generated family onto it, so the catalog holds one definition of "reaches" instead
of two. `reachableObjects` gained a root-only `rootOpts` parameter, because a
table's CHECK / DEFAULT owns the `new.` / `old.` namespace and a view body below it
does not.

# Review findings

## Verified correct (checked, nothing to change)

- **The seeded/unseeded split in `columnProbe`** — the implementer's headline
  "push here". `seeded = ownTable && reached.ownerKey === undefined` is right, and
  the *too-seeded* direction turns out to be nearly unobservable rather than
  merely untested: a view body's every column reference binds through its own
  FROM/WITH frame before any seed applies, so seeding a reached body would change
  no answer in any shape reachable through valid DDL. The *unseeded* direction is
  pinned by the pre-existing own-table sections (§1-§3 of 41.10.2), not by the new
  §29 — §29's match lands on the view's body, which is unseeded either way. Noted
  because the §29 comment reads as though it pins both halves.
- **Direct-match equivalence with the pre-change probe.** The table verb swapped
  `tableReferencedInAst` for `collectTableRefsInAst`; both key a reference as
  `resolve(ref.schema, ref.name)` and compare to `targetKey`, so the direct answer
  is unchanged. That is why no existing test section needed editing — confirmed by
  reading both sinks, not just by the green run.
- **Closure termination and shortest-path.** `visited` bounds a cyclic or
  malformed catalog; `namer.set` before the `visited` check keeps the breadth-first
  shortest chain. Correct.
- **Every consumer of the drop verbs routes through the guard** — `drop-table.ts`,
  `drop-view.ts`, `materialized-view.ts` all call `assertNoExpressionDependsOn`.

## Fixed in this pass (minor)

- **Two doc comments claimed a message consistency that does not exist.** Both
  `refersTo` helpers said they mirror `assertNoAssertionNamesColumn` so "all four
  guard families phrase an indirect refusal identically". They do not: the DROP
  COLUMN assertion guard says `it is referenced by assertion 'a' through view 'v'`
  while the three others say `… reaches it through view 'v'`. Rewrote both to name
  the guard actually mirrored (`assertNoAssertionDependsOn`) and to record the one
  divergence and why it was left alone (it was already in tests when the closure
  landed; both spellings read).
- **The cost `NOTE:` overstated the result.** "An expression naming no view still
  costs one walk" is true of the table verb but not the column verb, which now
  pays `collectTableRefsInAst` to build the reach *and then* the column probe on
  top — two walks where there was one. Rewritten to say that, and marked reasoned
  rather than measured.
- **`expression-drop-guard.ts`'s `refersTo` took an inline structural type**
  (`{ describe, path }`) instead of the exported `ExpressionDependent`. Typed it.
- **Empty-path truthiness made explicit.** `findInChecks` / `findInColumnExpressions`
  tested `if (path)`, which works only because `[]` is truthy — and `[]` is the
  direct-match signal. Changed to `!== undefined` with a one-line reason, so a
  later `path?.length` guard cannot silently drop every direct refusal.
- **Two docs the change should have touched but did not.** `docs/sql-views.md`
  § DROP VIEW and `docs/materialized-views.md` § `drop materialized view` both
  still said the drop is refused only "while an assertion's stored CHECK body still
  names" the object — stale in two ways (the assertion guard has followed chains
  since the previous ticket, and the CHECK / DEFAULT / generated family was never
  mentioned at all). Both rewritten.
- **One coverage cell missing.** 41.10.4 §12 tested a materialized view *in* a
  chain but never the `drop materialized view` verb refusing *indirectly* — the
  only verb × directness cell left empty, and the one where the protected object is
  itself a maintained table. Added; passes memory and store legs.

## Major — filed as a new ticket

- **`fix/4.9-rename-column-corrupts-other-tables-row-image-qualifier`** — found
  while auditing the `rootOpts` mechanism, and it is worse than the drop-guard
  question that led to it. With a real table called `"new"`,
  `alter table "new" rename column v to w` silently rewrites *another* table's
  `check (new.v > 0)` — where `new.` is that table's own written-row image, not a
  table reference — into `new.w > 0`, after which every write to that table fails
  with `new.w isn't a column`. Verified in-session, and the damage persists with
  the schema. The same root cause false-refuses
  `alter table "new" drop column v`. Root cause is one site: the column-rename
  walk's `matchRowImageQualifier` is two-state where the domain has three, missing
  "written-row context whose image belongs to some *other* table". The table
  walker already has that mode (`TableRenameOpts.rowImageContext`), which is
  exactly why the table verbs get the same SQL right and the column verbs do not.
  Filed at the representation rung (make the mode an explicit argument) rather than
  as two point fixes. A `KNOWN GAP` note now sits at the site.

## Tripwires (parked in code, not filed)

- **`rootOpts` root-only-ness cannot be pinned by a test today.** Measured rather
  than assumed: the suppression fires at exactly one place — a bare `new.` / `old.`
  column qualifier that nothing in scope binds — and `CREATE VIEW` rejects such a
  body outright (`create view v as select new.a from "new" as x` →
  `new.a isn't a column`, run in-session). So a reached body can never contain one,
  and leaking `rootOpts` downward would change no answer. Recorded as a `NOTE:` in
  `object-dependency-closure.ts` with the condition that retires it: if the
  suppression ever widens beyond seedless column qualifiers, this needs a test.
  (This supersedes the implementer's weaker claim that 41.10.4 §15 "passes either
  way" — true, but the reason is stronger than stated.)
- **Equal-length chain tie-breaking** and **first-dependent-only reporting** already
  carry `NOTE:`s at their sites (`ObjectReach.namerOf`,
  `tablesProbedTargetFirst`). Re-read both; still accurate, still advisory-only.
  Nothing added.

## Considered and declined

- **Aligning `assertNoAssertionNamesColumn`'s indirect wording** with the other
  three guards. It would churn pinned messages in 41.10.2 §23 and
  95-assertions.sqllogic to buy nothing a user notices. Recorded in the comment at
  the site instead, so the next reviewer does not re-derive it.
- **Optimising the column verb's extra walk.** The existing `NOTE:` already names
  the cheap gate (literal name scan of the stored SQL before the AST walk) and DDL
  is rare. Left as written, now with an honest magnitude.

## Known gaps carried forward, not re-filed

- **Column lineage through a `select *` projection is still blind** — the CHECK /
  DEFAULT / generated family now has the same hole the assertion family already
  had. Owned by `fix/4.8-drop-column-guard-blind-to-star-reexposure`, which is
  sequenced next and already carries the arm.
- **An own-table CHECK whose subquery reads a VIEW and names a column
  *unqualified* still false-refuses** (`buildColumnSourceResolver` looks a source up
  as a TABLE, so a view exposes no columns and the seeded probe binds the bare name
  to the owning table). Same missing capability as 4.8, same ticket. Honoured in
  the tests: every own-table-through-a-view case uses a qualified reference, and no
  control depends on the unqualified spelling being allowed.
