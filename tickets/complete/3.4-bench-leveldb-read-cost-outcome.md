# What this was

Two earlier agent runs on this ticket were killed by the runner's idle timeout, and their
edits were swept into the commits of unrelated tickets. So there was no implement-stage diff
to read; the work had to be reconstructed from the files above and treated as
claimed-and-unreviewed throughout.

The work itself: a benchmark had already measured, on a real on-disk LevelDB store, how much
more a random read costs than a sequential one. This ticket was the write-up and the
declare-or-defer decision. It decided to declare nothing and leave the storage backend on the
framework's default cost numbers.

# The decision, upheld

**Leave both numbers undeclared.** Confirmed, with the reasoning re-derived rather than
inherited:

- *Point read.* The benchmark measures the key-value layer alone, while the planner's unit of
  1.0 is a scanned row including engine work. Engine cost lands on both sides of the ratio and
  compresses it toward 1.0, so the value the planner would actually want is strictly between
  1.0 and the measured ratio — an interval whose bottom is already the default. Declaring the
  top of it picks the pessimistic end on no evidence.
- *Seek positioning.* One knob prices two access paths that are an order of magnitude apart on
  this backend. Verified both shapes in the code rather than taking the claim on trust: the
  secondary-index path opens one bounded iterator per distinct key, the primary-key path pages
  its keys and fetches each page in one round trip. Also verified that the primary-key path's
  cost is what the engine's key-set-seek rewrite reads at 2 and 1 000 keys to interpolate a
  seek-versus-scan break-even, so declaring the expensive (iterator) number would move that
  break-even about ten-fold in the wrong direction on a query shape that runs today. A
  compromise value makes both paths roughly 3.5× wrong and could only be validated by the
  slower store-backed test suite, which is beyond an agent's time budget. Splitting the knob is
  the real fix and is already filed.

# Review findings

## Checked and correct — no change

- **Every benchmark count in `docs/benchmarking.md`.** Loaded all five suite files and counted
  rather than reading the prose: 92 benchmarks / 54 entries / 19 expanded across three
  backends, and the `store` suite's 27 = 11 key-encoding + 14 hot-path + 2 read-cost. Every
  figure at every site matched, including the per-shape list.
- **The block-cache arithmetic.** 20 000 × 200 bytes ≈ 4 MB fits the 8 MB block cache the
  provider does not override; 200 000 × 200 ≈ 40 MB does not. Grepped for every "cold" claim in
  both files — nothing contradicts the deliberate refusal to call the large size cold.
- **Anchors and cross-links.** `docs:check` passes.
- **The read-cost rows never gate.** `informational: true` is a literal (the discovery code
  tests it strictly), the rows are absent from every ratio guard, and the gate deletes the
  opt-in environment variable before loading suites, so the rows skip there unconditionally.
- **Lint, typecheck, build, and the full test suite all pass.** No pre-existing failures
  surfaced.

## Found and fixed in this pass

- **The recorded numbers do not reproduce, and one stated interval is falsified.** Re-ran the
  benchmark on the same machine and the same commit. Three of the four ratios moved 10-26%,
  and the point-read ratio came back *above* the upper bound the write-up had stated as its
  interval. The decision survives — the new value is still near parity and still an
  over-statement — but the bound was one run's reading presented as a measured fact. Rewrote
  every conclusion to quote bands rather than decimals, and added the second run to the README
  as a table beside the first.
- **The same decimals were restated at four durable sites**, which is how they came to
  disagree. The README is now the single record; the three code comments carry the decision and
  the magnitude and point at it.
- **The seek arm runs against the data store, not an index store.** The benchmark's own header
  hedges this; the README — the durable record — presented the figure as an index-store
  measurement. Added the argument that makes it a fair proxy anyway: the cost is dominated by
  fixed iterator setup, so the payload size barely moves it.
- **The secondary-index path also pays a batched row resolution on top of its per-key window**,
  which the two-arms table omitted. It understates the gap the whole deferral rests on, so
  nothing flips, but the table now says it.
- **A stale ticket cross-reference** describing an already-landed benchmark ticket as still in
  progress.

## Recorded as a tripwire, not a ticket

- **These ratios are not reproducible to the decimal.** Parked at the README section that holds
  the tables and again at the provider's decision comment, both stating that any future
  decision needing a specific number must re-measure across several runs. It is not a defect —
  the rows are informational precisely because a wall-clock ratio has no noise floor — but the
  next reader would otherwise quote a digit out of the table.
