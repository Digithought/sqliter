# Two-phase schema apply: row-validating DDL runs after the batch's rows

## What was wrong

A receiving device applied **all** of a sync batch's schema changes before **any** of its
row changes. That order is right for a change that loosens or extends a table (the rows
need the new shape to land in) and wrong for one that tightens it (the tightening is only
legal against rows still queued behind it), so an ordinary "fill the column, then forbid
empties" sequence failed its first sync round with:

```
apply-to-store failed for 1 change(s): main.orders (alter_column): column note contains NULL values
```

## What now happens

`applyToStore` splits each batch's schema changes into two phases:

```
non-validating DDL  →  row writes  →  row-validating DDL  →  engine ingestion seam
```

Both phases run through the same accounting closure, so a validating alteration's failure
lands in `ApplyToStoreResult.errors` exactly as a pre-data one always did — an
unsatisfiable tightening still aborts the batch and still retries.

**Row-validating** (moved after the data): `alter column … set not null`, `add
constraint`, and a **unique** `create index`. Non-unique index creation inspects nothing
and stays in the early phase.

**Deliberately NOT moved**: `alter primary key` (the key definition in force decides how
the batch's rows are addressed) and `alter column … set data type` (a type change rewrites
stored values). Both keep their pre-data position and their existing spurious-error-plus-
retry failure mode; documented at the classifier and in `docs/sync-schema.md`.

**Ordering guard.** A batch is a whole resolved `ChangeSet[]` — many source transactions —
so it can carry `add constraint u1` from one transaction and `drop constraint u1` from a
later one. `partitionSchemaChanges` therefore defers a validating change only when every
later change on the same object in the batch also defers, so per-object DDL order is never
rearranged. A trailing `drop_table` is the one exception: the table is discarded either
way, so it does not pin, and the deferred tightening meets an absent table and converges.

## Review findings

Reviewed the implement diff (`68178ce92`) against the code, then re-derived the ordering
rule from `partitionSchemaChanges` independently before reading the handoff's argument for
it. The implementer's stated open question — whether the pinning rule is sound — is where
the two real defects were, and both were in the interaction it did not cover: an index
migration is filed under the **index** name, so the pinning rule could not see its owner
table at all.

### Major — fixed in this pass

**1. A unique index create plus a drop of its owner table in one batch wedged the peer
permanently.** `create unique index idx_note on orders (note)` followed by `drop table
orders`, one relay: the create defers (it validates rows), the drop does not and is exempt
from pinning, so the drop ran first and the deferred create hit
`add_index … : no such table: orders`. Verified against the implement commit, and verified
absent with the split disabled — a regression this ticket introduced, not a pre-existing
gap. It does not self-heal: the drop commits on round one, so every retry re-runs a create
that can never succeed.

Fixed at the decision, not the ordering. `decideSchemaChange`'s `add_index` arm now routes
an absent index through `decideAbsentIndexCreate`, which converges with a warning when the
table the create names is absent — an index cannot outlive what it indexes, so the wanted
end state has already arrived. That is the posture `drop_index` and `decideAlterTable`
already take for an absent object, and it is what makes the `drop_table` pinning exception
safe for *every* migration type the classifier can defer, not just `alter_column`. It also
retires the general case of an index migration arriving for a table this peer does not
have. Regression test: `a unique index created and its owner table dropped in ONE batch
converges`.

**2. A unique index create plus a drop of the indexed column in one batch failed.** The
handoff recorded this as a `NOTE:` tripwire ("would have to arrive in one batch AND touch
the same column"). It is not conditional — it is a defect that fires the moment that batch
shape occurs, and it did: `add_index … : Column 'note' not found in table 'orders'`.
Verified reproducing, and verified absent before the change.

Fixed by the mechanism the NOTE itself proposed: `migrationOrderKey` became
`migrationOrderKeys`, and an `add_index` now keys under **both** its index name (which
pairs a create with its drop) and its owner table read out of its own DDL (`createIndexOwner`).
Pinning is set-membership over that key list. The narrowing is conservative — a validating
change held by either key simply keeps today's pre-data position. Regression test: `a
unique index create is held before the data by a later drop of the indexed column`. The
NOTE is gone from the source, replaced by a statement of the rule that now holds.

**3. `add constraint … check` does not validate existing rows, contradicting the
classifier's comment, the docs table, and the handoff.** All three claimed "the `unique`,
`check` and foreign-key forms all check existing rows". Probed all three directly against
violating rows: `unique` throws `UNIQUE constraint failed`, foreign key throws `FOREIGN KEY
constraint failed`, `check` is **accepted silently**. Both backends implement the CHECK arm
schema-only on purpose (`manager.ts` `addCheckConstraint`, `store-module-alter.ts`
`alterAddConstraint`).

Classifying CHECK as validating is still right — deferring a statement that inspects
nothing is harmless and it is the correct position once the gap closes — so the code was
left alone and the two inaccurate claims corrected instead. The engine-side gap is a real
integrity hole outside this diff (a table ends up holding rows its own CHECK constraint
says cannot exist) and is filed as `backlog/bug-add-check-constraint-skips-existing-rows`
(severity `wrong-result`, likelihood `normal-use`), asking for the per-backend scan **and**
a table-driven test over every tightening form — the arm fell out of a set of siblings that
otherwise agree, and only a generalized test stops the next one doing the same.

### Minor — fixed in this pass

- **A vacuous coverage claim, replaced with real coverage.** The handoff's stated gap was
  that only the `unique` arm of `add constraint` was exercised end to end. A `check`-arm
  test was written first and found to pass with the split disabled — because of finding 3,
  it can never fail. It was replaced with a **foreign-key** case (`a foreign key the batch
  satisfies applies on the FIRST round`), which does bite: the receiver's row is an orphan
  until the batch's own update re-points it. The FK arm is now covered end to end and the
  stated gap is closed for the two arms that actually validate.
- **A test comment that misdescribed its own setup.** The drop-table case said the
  tightening "is unsatisfiable against b's rows" when the batch's own update satisfies it;
  what makes the case bite is that it is unsatisfiable *at the moment the pre-data phase
  would run it*. Reworded.

### Conditional / speculative — recorded, not filed

None. Every concern that survived investigation was either reproducible now (findings 1–3)
or resolved by reading the code, so nothing was parked as a tripwire. The one `NOTE:` the
implement pass left behind was re-examined and turned out to be finding 2 — a live defect,
not a conditional one — so it was fixed and the NOTE removed rather than kept.

### Checked and found sound

- **The pinning rule itself**, which the handoff flagged as the part most worth an
  adversarial read. Re-derived independently: walking backwards and pinning an object the
  first time a change on it stays put does make "every later change on this object also
  defers" a single set lookup, and a deferred change correctly does not pin. Constructed
  and traced the shapes that could break it — `create_table` then a validating change,
  `drop_table` then `create_table` of the same name, a create/drop-index pair, a validating
  change followed by a non-validating one — and each holds. The add/drop-constraint case
  the rule exists for is covered by an existing test that bites when the rule is disabled.
- **Cross-object ordering.** Probed `add constraint … foreign key` on a child followed by
  `drop table` of the parent in one batch, the most plausible shape the same-object pinning
  rule cannot see. No failure — the engine does not reject the deferred add. Not a defect.
- **The `alterColumn` AST cannot carry `setNotNull` and `setDataType` together** (parser
  emits each arm singly, `parser.ts:3413`/`3453`), so classifying on `setNotNull === true`
  cannot accidentally defer a type change.
- **Error accounting and the seam.** Both phases share one closure; a deferred failure
  reaches `result.errors` identically, and the after-data phase precedes the single seam
  call so the seam observes the batch's final schema. The bootstrap-flush path is
  unaffected.
- **`change.table` really is the table name for `alter_column`.** Confirmed at the emit
  sites (`alter-table.ts`, `alter-event-shape.ts` — column events carry the table in
  `objectName`), so `migrationOrderKeys` keys those correctly.
- **The em-dash mojibake incident the handoff flagged.** Scanned all touched files for
  `Ã` / `â€`: clean. `git diff --numstat` shows only intended hunks.
- **Repeated parsing, considered and left alone.** An index migration's DDL is now parsed up
  to three times per batch (classifier, order key, apply decision). Not memoized: schema
  migrations are a handful per batch against thousands of row changes, and a `WeakMap` cache
  would add machinery for an unmeasured cost. Noted here rather than as a `NOTE:`, since
  there is no condition that would make it matter.
- **File size.** `store-adapter.ts` is 1261 lines, up from 1047 before the implement pass.
  Growth is almost entirely doc comment in the file's established house style; no split
  filed.
