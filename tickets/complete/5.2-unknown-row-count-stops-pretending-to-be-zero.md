# `undefined` is the only spelling of "unknown" — landed

`TableSchema.estimatedRows` is deleted. A table's row count now lives in exactly one
place, `TableSchema.statistics.rowCount`, read through `catalogRowCount(table)`:
`undefined` means nobody has measured it, a number — including a real `0` from
`ANALYZE` of an empty table — is a measurement. All seven writers of the hardcoded
zero are gone (schema manager x3, materialized-view backing helpers x3, the store
module, the sample json-table plugin).

The behavior that was the point: `CatalogStatsProvider.tableRows` now actually reaches
its `NaiveStatsProvider` fallback (default 1000) for a never-analyzed table — that path
was unreachable while `catalogRowCount` always returned a number.

Three consequences the fake zero had been masking, fixed in the same pass:

- The fan-out **cross-branch memory guard** documents "unknown estimates refuse to
  cluster" but never saw an unknown, so the product cap always passed with zero
  information. It now refuses. Optimizer fixtures that pin a cross-mode plan shape run
  `analyze` so those shapes stay reachable.
- The materialized-view **residual↔rebuild crossover** modeled a key-filtered residual
  as touching only its own group's rows. With no index on the binding key each run
  actually scans the whole source, so with honest estimates a 100-row statement paid
  ~100 full scans. `compileResidual` now returns the optimized residual plan's real
  cost and the arm builders stamp it into `MaintenanceSourceStats.residualExecutionCost`,
  so the crossover judges the residual by what it does. A `MIN_DEGRADE_DISTINCT_KEYS = 3`
  floor keeps 1–2-key statements on the targeted residual (a rebuild rewrites the whole
  backing — write amplification the formulas do not carry).
- **Adopting** a pre-existing materialized-view backing carries its measured statistics
  forward instead of stamping a zero.

Source-breaking for third-party code that constructed a `TableSchema` with
`estimatedRows` — accepted per AGENTS.md (backwards compat not yet a concern).

## Review findings

**Read first, handoff second.** The implement diff (`7779a8023`, 34 files) was read
end-to-end before the handoff summary, then its claims were re-derived independently.

### Verified, not taken on trust

- **Every unguarded consumer of a row estimate.** Swept `src/` for arithmetic and
  comparisons on `estimatedRows` that would produce `NaN` or a wrong branch on
  `undefined`: `materialization-advisory` (`selectStrategy`/`calculateThreshold`),
  `PlanNodeCharacteristics.isExpensive`/`getCacheThreshold`, `reference-graph`,
  `rule-nested-loop-right-cache`, `explain`, `plan-validator`, `table-function-call`.
  All read through a defaulting helper or an explicit guard. One behavior flip worth
  naming and checked: the nested-loop right-cache size gate now sees 1000 instead of 0
  for an un-analyzed right side, still far below its 50000 cap, so caching decisions are
  unchanged.
- **The golden-plan claim.** Diffed the six regenerated plan files mechanically: every
  changed line is an `estimates`/`estimatedRows` field. Zero plan-shape changes, as
  claimed.
- **Field really is gone.** Repo-wide sweep for `TableSchema.estimatedRows` finds only
  stale `dist/` build artifacts.
- **`cardinalityBand(undefined)`** returns `'unknown'` — the lens fingerprint has a real
  arm for the new value, not a fall-through.
- **The residual/rebuild crossover units.** `residualExecutionCost` is a real optimized
  plan cost; `'full-rebuild'` is a synthetic formula. Both are built from the same
  `COST_CONSTANTS`, so the comparison is meaningful — parked as a tripwire below.

### Fixed in this pass (minor)

- **Docs that document the exact behavior this ticket changed were left stale.**
  `docs/optimizer-joins.md` still carried two claims that "synthetic memory-vtab leaves
  resolve `estimatedRows` to 0" — one on the cross-branch memory guard (the very guard
  the implement pass says it un-deadened) and one on the batched-outer cardinality gate.
  Both rewritten to the new reality. The same stale sentence lived in two code comments
  (`optimizer-tuning.ts` `batchedOuterMinRows`, `optimizer.ts` fan-out rule registration)
  and one test comment (`parallel-fanout-batched.spec.ts`) — all corrected.
- **`stalenessThreshold`'s doc comment** in `database-auto-analyze.ts` still said
  "`SchemaManager` hardcodes `estimatedRows` to 0 at create". The implement pass rewrote
  two NOTEs in that file and missed this third one. Also corrected the matching
  user-facing sentence in `docs/usage.md` (`auto_analyze_row_limit`) and a test comment
  in `auto-analyze-refresh.spec.ts`.
- **Dead ternary.** `CatalogStatsProvider.tableRows` logged
  `table.statistics ? 'catalog' : 'schema'`; with the schema field gone, a defined row
  count implies statistics, so the `'schema'` branch is unreachable. Collapsed.
- **Orphaned JSDoc.** `MIN_DEGRADE_DISTINCT_KEYS` was inserted *between*
  `shouldDegradeToRebuild`'s doc comment and the function, so each comment documented
  the wrong symbol (visible in editor hover and generated docs). Reordered; the function
  doc now names the floor.

### Test gaps closed (minor)

The implementer's tests covered the spelling change well (`catalogRowCount`,
`NaiveStatsProvider`, the end-to-end estimate path). Two *new behaviors* shipped with no
test at all:

- **`residualExecutionCost` and the `MIN_DEGRADE_DISTINCT_KEYS` floor** — neither had any
  coverage in `test/incremental/maintenance-cost.spec.ts`, which the implement pass never
  touched. The pre-existing "does not degrade for low cardinality" case passes with or
  without the floor, so the constant could have been deleted silently. Added three cases:
  the stamped cost overriding both the with-stats and no-stats residual formulas, its
  effect on the `'delta-aggregate'` cap in both directions, and a floor case using a
  residual that alone outprices a rebuild (would demote at every cardinality without the
  floor).
- **The fan-out guard's newly live refusal** — the implement pass added `analyze` to
  every cross-mode fixture to restore the old shapes, but nothing pinned the behavior
  that made those edits necessary. Added `does NOT cluster when the fixture is
  un-analyzed` to `parallel-fanout.spec.ts`: same fixture, same latency, statistics
  withheld, no cluster.

### Tripwires (recorded at the site, not filed)

- **Asymmetric maintenance costing** — `NOTE:` at the `'full-rebuild'` arm in
  `planner/cost/index.ts`: the residual arm can now be priced from a real optimized plan
  cost while the rebuild arm stays a synthetic formula. Fine today (same cost units); the
  fix, if they ever disagree, is stamping `buildFullRebuildPlan`'s own `getTotalCost()`
  the same way.
- **`MIN_DEGRADE_DISTINCT_KEYS = 3`** — the implementer's justification at the site was
  re-tagged `NOTE:` (so it sweeps with the rest) and given a revisit condition: it stands
  in for a cost term the model cannot express, and its principled replacement needs a
  backing-size statistic that does not exist yet.
- **`estimatedRows || 1000` at `createSeqScan`** — an analyzed-*empty* source still
  prices as a 1000-row scan. Left alone: the pre-existing `NOTE:` in
  `planner/stats/table-cardinality.ts` already owns this exact collapse and is still
  accurate.

### No major findings — and why

Nothing reached the "file a ticket" bar. The change removes a representation rather than
adding one — the fake zero was the bad state, and deleting the field makes it
unrepresentable, which is the top rung of the ladder a major finding would have had to
climb. The two behavior *activations* (the fan-out guard, the delta-executor
per-binding→global demotion) both move in the conservative direction: refuse to cluster,
recompute more than the minimum. The delta-executor demotion mechanism itself is already
unit-tested at the `DeltaExecutor` level with a stubbed `getRowCount`, so wiring it to
real catalog counts needed no new machinery.

### Known behavior change, accepted

Lens acknowledgments recorded against a never-analyzed basis fingerprinted its
cardinality band as `'empty'`; it is now `'unknown'`, so those acknowledgments re-prompt
once. The old band was a lie about an unmeasured table, so the churn is the correction
landing, not a regression.
