# What landed

## Tests — `packages/quereus/test/bench-comparison.spec.ts`

24 tests, all pure over hand-built plain objects (no benchmark runs), matching the
file's existing style.

- `describe('flattenCounters', ...)` — 7 tests. A full `WorkCounterSnapshot` flattens
  across `plan` / `instructions` / `tables` / `totals`. An instruction inserted at the
  front of the `instructions` array is addressed by its `key` and reports exactly one
  added path rather than shifting every later instruction. A bare `PlanShape` and a
  named bag of two snapshots both flatten with no special-casing. An explicit
  `nodeType: undefined` is skipped, and the result survives a JSON round-trip
  unchanged. *(Review added:)* a shape with nothing to address — a bare primitive, or
  an empty instruction list — records nothing; a malformed non-primitive leaf is
  recorded by its string form so it surfaces as a difference instead of comparing equal.
- `describe('diffCounters', ...)` — 5 tests. A difference of one is reported with no
  tolerance; changes come back sorted by path; a path present on one side only is
  reported with `null` on the other, in both directions; two identical blocks produce
  no changes. *(Review added:)* a path whose value is literally `null` is treated as
  absent, not as a difference — the behaviour the `??` in `diffCounters` is commented
  for, previously unasserted.
- `describe('counter verdict', ...)`, nested in the existing `describe('compareRun')` —
  12 tests. Every `CounterStatus` the `compare.mjs` JSDoc documents: `same`, `changed`
  (with the exact diff), `new`, `dropped`, `none`, `skipped` (`--no-counters`), and
  `none` for a `--filter`-excluded or failed benchmark. One test confirms a `changed`
  counter never sets `gated` and never counts as a regression. *(Review added:)* a
  nested `describe('the counter summary')` over a six-benchmark mixed run asserting
  `counterCounts` exactly (including the zero entries and the `COUNTER_STATUS_ORDER`
  key order), that the counts sum to the number of comparisons so no benchmark is
  missing a verdict, and that `counterChanges === counterCounts.changed` while
  `regressions` stays zero.

## Verified rather than taken on trust

- **The fixture matches reality.** `counterBlock()` in the spec was checked field by
  field against the real `WorkCounterSnapshot` interface
  (`src/runtime/work-counters.ts:48`) — `plan` / `instructions` / `tables` / `totals`,
  and the optional `nodeType`. It does not describe a shape the engine cannot produce.
- **The load-bearing test is genuinely load-bearing.** The implementer flagged that
  they had reasoned through the front-insertion test but not mutation-tested it. Ran it:
  with `key` addressing, inserting an instruction at the front yields
  `[{path: 'instructions.r#new.executions', before: null, after: 1}]`; strip the `key`
  fields so the same input takes the positional branch and it yields three changes
  (`instructions.0`, `instructions.1`, `instructions.2`). The test fails without the
  special case, exactly as claimed.
- **Every number in the docs was checked against the code**, not against the handoff:
  the suite counts (`execution` 15/15, `mutation` 4/4, `planner` 4/4, `parser` 0/4)
  against the suite files; `COUNTER_CHANGES_SHOWN = 12` against `run.mjs:64`; the column
  values against `fmtCounters` (`run.mjs:357`); `counters_collected` against
  `run.mjs:765`; and the `runtime.md#work-counters-...` anchor against the heading it
  points at. The suite counts, the cap and `counters_collected` were all correct. The
  column values and the difference block were not — below.

## Minor — fixed in this pass

- **`docs/benchmarking.md` had the `--no-counters` comparison backwards.** It said
  "comparing *against* a `--no-counters` run reports every benchmark's counter status
  as `skipped`". The flag is read off *this* run, not the baseline: `run.mjs:831` passes
  `{ counters: collectCounters }` from the current run's argument parse. Comparing a
  counter-collecting run against a `--no-counters` *baseline* is the opposite direction
  and reports `new` per benchmark, since the baseline entries carry no counters.
  Rewritten to state both directions.
- **The `Counters` column value list was incomplete** — it omitted `skipped`, which
  `fmtCounters` emits and which is precisely what a `--no-counters` run prints. Added.
- **The difference block was described as covering `dropped` too.** It does not:
  `printCounterChanges` (`run.mjs:405-409`) gives a `dropped` benchmark a single line
  and no path list, because there is nothing to diff against a run that collected none.
  Corrected, and the reason stated.
- **The `counters()` example duplicated the *Adding a benchmark* example verbatim**,
  differing only by the added member — two copies free to drift apart, and neither
  showed the import a reader actually needs. Replaced with the import line plus the one
  added member, pointing at the full object below.
- **Nothing in *Adding a benchmark* mentioned `counters()`.** That section is where
  someone writing a new benchmark reads; the counters section is not. Added a
  requirement bullet there pointing at it.
- **`docs/architecture.md` never mentioned work counters at all**, despite the feature
  having landed across four tickets. Its Benchmark Suite section explicitly delegates
  detail to `benchmarking.md` ("do not duplicate it here"), so what was owed was a
  pointer, not a copy: one bullet on exact-integer comparison with no floor, reported
  and never gated, with `--no-counters` named and the detail left where it lives.
- **Test gaps closed** (four tests). Three were documented behaviours in `compare.mjs`
  with no coverage: the `??` in `diffCounters` treating a literal `null` as absent; the
  `asCounterLeaf` default branch recording a malformed leaf by its string form so it
  "shows up as a visible difference instead of silently comparing equal"; and the two
  shapes that address nothing (a root primitive, an empty keyed array). The fourth is
  the aggregate the implementer explicitly flagged as unasserted —
  `counterCounts` / `counterChanges` / `COUNTER_STATUS_ORDER`.

## Tripwires — none recorded

Two candidates were considered and both dismissed on inspection rather than parked:

- `flattenCounters` builds paths by joining on `.`, and table keys are themselves
  `<schema>.<table>` — so `tables['main.t'].rowsScanned` flattens to
  `tables.main.t.rowsScanned`, which *looks* ambiguous. It is not reachable: a
  `tables` value is always a fixed-field `TableWorkCounters`, never another table map,
  so no two distinct inputs can collide on one path. Not a conditional concern, just a
  path that reads oddly.
- Duplicate keys in a keyed array collapsing, last one winning, is a real limitation —
  but `compare.mjs:139` already carries a `NOTE:` at that exact site stating it and its
  revisit condition. Already recorded; not re-recorded here.
