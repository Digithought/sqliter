# Table rename is scope-aware (was: rewrote CTE/alias-bound names and `new.`/`old.` row images)

## What shipped

`visitTableRename` (a depth-blind name match) was replaced by a scope-aware
**table-reference walk** in `packages/quereus/src/schema/rename/table-rename.ts`.
The walk reports every REAL table reference to a sink over **one traversal**;
`renameTableInAst` (rewrite sink) and `tableReferencedInAst` (probe sink with
early-out) are both expressed over it, so the DROP guard refuses exactly what a
rename would rewrite — pinned by a test, not just a comment.

Scope rules:

- **WITH frames** register CTE names in planner visibility order (a
  `with recursive` member's name before its body, a non-recursive member's
  after — mirrors `buildCommonTableExpr`). A FROM source naming an in-scope CTE
  (unqualified only) is not a reference.
- **FROM frames** bind qualifiers: an unaliased real source binds its name to the
  source's identity (schema-as-written + name); aliases, CTE sources, subquery /
  function sources bind to "not a table". A qualified column ref resolves
  innermost-first; bound-to-non-table → skipped; unbound → direct reference (the
  CHECK / index self-qualifier case). Schema-qualified `main.zap.k` bypasses the
  frames entirely.
- **DML targets** mirror `resolveCteTarget`: an unqualified target naming a
  member of the statement's OWN leading WITH is the CTE (skipped);
  schema-qualified never is; enclosing WITHs deliberately do not shadow a write
  target. An UPDATE / DELETE target's **correlation name** binds as a qualifier
  (added in review — see findings).
- **Row image** (`rowImageContext`): threaded from
  `renameTableInCheckConstraints`, `renameTableInColumnExpressions`, the
  equivalent per-check loop in `alter-table.ts`, and the differ's inverse CHECK
  reconcile — NOT from `renameTableInIndexPredicates` (a predicate has no
  written-row context). Suppression is scope-aware: only an UNBOUND bare `new.` /
  `old.` qualifier is a row image.

The size-NOTE tripwire on `rename-rewriter.ts` tripped, so the file was split:
it is now a 34-line barrel over `rename/table-rename.ts` (628),
`rename/column-rename.ts` (1,057, verbatim), `rename/self-qualifier-strip.ts`
(296, verbatim), `rename/shared.ts` (51). No import site changed.

Behavior improvements beyond the ticket's literal list: a qualified column ref
bound by an unaliased FROM source now matches by the SOURCE's identity, so
renaming `main.zap` no longer rewrites `zap.k` in
`select zap.k from other_schema.zap`.

## Review findings

### Checked

- **The walk against its predecessor.** Every AST arm the old `visitTableRename`
  handled is handled by `visitTableRefs`; no case was dropped in the rewrite.
  `AST.FromClause`'s full union (table / join / functionSource / subquerySource)
  is covered by `collectFromBindings`.
- **The "moved verbatim" claim** for `column-rename.ts` and
  `self-qualifier-strip.ts` — verified mechanically, not by eye: every
  non-comment, non-import line of both new files exists byte-identically in the
  pre-split `rename-rewriter.ts`. No edits were smuggled into the move.
- **Every `renameTableInAst` / `tableReferencedInAst` call site** against the
  row-image rule (11 sites). All consistent: view / MV bodies and assertion
  bodies carry no written-row context and correctly pass no flag; the assertion
  drop guard and the differ's assertion probe match their rewriting twins; the
  differ's index-predicate inverse correctly omits the flag, mirroring the
  forward path. `alter-table.ts:232`'s pre-flight callback runs only over view /
  MV bodies, so its missing flag is correct rather than an oversight.
- **The planner-mirror claims.** `resolveCteTarget` does consult only the
  statement's own `withClause` and does exclude schema-qualified targets, exactly
  as `visitDmlTarget` asserts. `buildCommonTableExpr`'s sibling visibility
  matches `pushWithFrame`'s registration order.
- **Docs.** `docs/sql-alter.md`, `assertion-drop-guard.ts` and the differ
  reconcile comment all match the new reality. `docs/vu-inverses.md:86` names
  `schema/rename-rewriter.ts` — still a valid path (the barrel) and its
  "scope-aware" claim about `renameTableInAst` became true with this change
  rather than stale. `docs/architecture.md`'s layout listing is directory-level
  and needed nothing.
- **Public surface.** `src/index.ts` exports the three collection helpers, which
  encapsulate the row-context decision; `TableRenameOpts` correctly stays
  internal, so no external module can get the flag wrong.
- **Adversarial AST probes** over 17 shapes the spec did not cover: joins,
  function sources, set-op legs in both directions, correlated subqueries,
  group-by/having/order-by, nested DML inside a subquery source, schema-qualified
  DML targets, and row images inside subqueries with their own FROM.
- **Validation.** `yarn build`, `yarn lint` (eslint + `tsc -p tsconfig.test.json`)
  and `yarn test` green — 8,782 passing, 0 failing across all workspaces.
  `yarn workspace @quereus/quereus run test:store --grep "41.3"` green, covering
  the LevelDB path through `store-module-rename.ts`.

### Found and fixed in this pass (minor)

- **The inline-subquery DML target's correlation name was not bound** —
  `packages/quereus/src/schema/rename/table-rename.ts`. The implementation
  skipped the synthetic placeholder in `stmt.table` and descended
  `targetSource`, but never bound the alias, so
  `update (select k from other) as v set k = 1 where v.k > 0` had `v.k` rewritten
  when a table named `v` was renamed — while `as v` stayed put, leaving a
  reference to a correlation name that no longer existed. That is precisely the
  defect class this ticket set out to remove, fixed on one side only. Now bound
  via `stmt.alias`, which also covers the collision-proof alias the view-mutation
  lowering synthesizes for a *named* target. The UPDATE and DELETE arms were
  near-identical; extracting `visitDmlTargetRowClauses` merged them into one.
- **Test gaps** — `packages/quereus/test/schema/table-rename-scope.spec.ts`, now
  25 cases (was 18). Added: schema-qualified DML target under a same-named CTE;
  an enclosing WITH failing to shadow a nested DML target (the deliberate
  planner mirror, previously unpinned); the inline-target alias, negative and
  positive; the join arm of `collectFromBindings` binding a real source and
  binding an aliased subquery source; an aliased function source. The
  probe/rename-equivalence and idempotence loops cover all 25 automatically.
- **Doc drift** — `docs/sql-alter.md` listed the self-bound names a rename skips
  but omitted the UPDATE/DELETE target correlation name.

### Found and routed to an existing ticket (no new ticket filed)

- **"Rewrite a table's own definition for a table rename" exists twice** —
  `rewriteTableForTableRename` in `runtime/emit/alter-table.ts` hand-rolls the
  CHECK and index-predicate loops that the `renameTableIn*` collection helpers
  wrap, and `quereus-store`'s `store-module-rename.ts` calls the helpers. Nothing
  makes the two agree on which arms get a written-row context — this very ticket
  had to add `rowImageContext` to the helper *and*, separately, to the
  hand-rolled loop. Climbing the architecture ladder, the fix is the invariant
  (one place owns the per-arm row-context decision), not a point fix. Appended as
  a **second arm to `debt-rename-walkers-resolve-names-like-the-planner`**
  (already in `implement/`), which rewrites the signature of every one of those
  call sites anyway — filing separately would churn the same function twice. That
  ticket's `files:` header was also refreshed: it still pointed at line numbers
  in the now-split `rename-rewriter.ts`.
- **`rename/column-rename.ts` is 1,057 lines** (`wc -l`), the residue of the
  1,759-line split. Appended as an arm to the existing
  `backlog/debt-oversized-source-files` theme ticket rather than filed fresh.

### Recorded as a tripwire, not a ticket

- `packages/quereus-store/src/common/store-module-rename.ts` — the reverse pass
  that undoes a rewrite when `saveTableDDL` throws is a *partial* undo for the
  CHECK arm when the new name is literally `new` or `old`: the forward pass turns
  a self-qualifier `t.b` into `new.b`, which the reverse walk reads as the
  written-row image and leaves alone. Harmless today (in a CHECK on its own table
  the two spellings denote the same row), so it is a spelling residual, not a
  semantic one. `NOTE:` at the site, next to the sibling residual already
  documented there, with the revisit condition: a CHECK gaining a legal bare
  qualifier that names a table other than its own.

### Considered and not filed

- **Set-op legs are visited inside the first leg's FROM frame.** A qualifier in
  leg 2 unbound by its own FROM could resolve against leg 1's bindings.
  Reproduced deliberately; every shape that reaches it is invalid SQL either way,
  and the placement mirrors the existing column walker rather than inventing a
  second convention. Already documented in the walk.
- **Renaming a table TO the name `new`** converts a rewritten self-qualifier
  (`x.a` → `new.a`) into row-image spelling. Traced through both directions: for
  a CHECK on its own table the two spellings are semantically identical, and a
  later rename away from `new` leaves the row image intact and still correct. No
  defect behind it.
- **`from zap z` leaves `zap.k` matchable as a direct reference** (the alias
  hides the source name, so the walk sees it as unbound). Pre-existing, and
  rewriting it keeps the reference consistent with the renamed FROM source rather
  than breaking it.
