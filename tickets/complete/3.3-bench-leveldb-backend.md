# What shipped

`yarn bench` can now run every `execution` and `mutation` workload against **LevelDB on a
real temporary directory** — the storage a Node deployment actually uses — in addition to
the in-memory paths it already measured.

```bash
yarn workspace @quereus/quereus bench:leveldb                       # every suite, disk rows included
QUEREUS_BENCH_LEVELDB=1 yarn workspace @quereus/quereus bench --filter @store-leveldb
yarn workspace @quereus/quereus bench                               # disk rows print a skip reason
```

Those rows are **opt-in** and **advisory**: printed, recorded, compared against a
baseline, and never allowed to fail a build, because a timing dominated by the machine's
disk is not a property of this repository's code. Three shapes carry that rule — the
`informational` flag is declared once on the backend and stamped onto every row it
produces, `compare.mjs` never marks such a row `gated`, and a ratio guard naming one is
refused as a misconfiguration before every other guard case.

`STORE_LEVELDB_BACKEND` is in `BACKENDS`, on measurement rather than preference: the
19-row opted-in arm costs 84 s, the slowest single row is ~14 s of wall clock against a
120 s timeout, and a default run pays 9.2 s of a 163 s / 90-benchmark run for those rows
to print a skip reason instead of vanishing.

Temporary databases are removed in three layers (benchmark teardown, a process `exit`
hook, and a PID-owned sweep in the parent), because a `SIGKILL`ed worker runs no handler
and a LevelDB database left behind would make the *next* run measure something else.

# Review findings

## Fixed in this pass

- **`leveldb-backend.mjs` leaked an open database and its directory when setup failed.**
  `openLevelDBDatabase` built a LevelDB provider and then called `openStoreDatabase`
  with no failure path: a throw there left the provider open, holding LevelDB's exclusive
  directory lock, for the life of the worker — and the exit hook's removal would then fail
  against that live lock, leaving exactly the stale directory the whole tempdir layer
  exists to prevent. Now the setup failure closes the provider and removes the directory in
  the same order the teardown uses, then rethrows the original error.
- **The sweep reported a lost race as a failure.** Two parents sweeping the same dead
  worker's leftovers is the expected shape when runs overlap; the loser's `statSync` raised
  `ENOENT` and printed a scary line about a directory that was already gone — the outcome
  the sweep wanted. `ENOENT` is now skipped, matching what `rmSync`'s `force` already did.
- **A false claim in a doc comment.** `createBenchLevelDBProvider` said it was "exported
  because `bench/suites/store.bench.mjs` measures the key-value layer DIRECTLY". That suite
  contains no reference to it — the intended consumer is the *next* ticket
  (`bench-leveldb-read-cost`, in `implement/`, which names this file as "the provider
  builder to reuse"). The export is kept, since that ticket needs it; the comment now says
  what is true today and states the close-order contract a caller takes on.
- **`docs/architecture.md` was not updated by the change and should have been.** Its
  benchmark-suite section named two backends and claimed "57 benchmarks from 38 entries".
  Measured with `node -e` over `loadSuites()`: **90 benchmarks**, of which 57 are 19
  workloads × 3 backends. (The 57 was already stale before this ticket, from the store
  suite's growth in `bench-store-micro-paths`.) The backend-dimension paragraph now
  describes `store-leveldb` — opt-in, informational, its own lazy import, PID-swept temp
  directories — and points at `benchmarking.md` for detail rather than duplicating it.

## Test coverage added

**`packages/quereus/test/bench-tempdir.spec.ts` — 15 cases, new.** The handoff named this
as the biggest gap and it was: `tempdir.mjs` is the layer standing between a killed worker
and a corrupted next measurement, and nothing automated touched it. It is pure enough to
test — it needs only a directory and a PID — so the two dangerous properties are now
pinned by machine rather than by one hand-run session on one machine:

- the sweep **removes** a directory whose owning process has exited, recursively, contents
  and all (a dead PID is obtained by running a node process to completion via `spawnSync`);
- the sweep **never touches a live owner's** directory, which is what makes two concurrent
  `yarn bench` runs on one machine safe;
- the caller's force list is **per-PID**, not a global override — a forced sweep still
  leaves another owner's directory alone;
- a non-prefixed path, a prefixed name whose owner field is not a PID, and a *file* that
  merely looks like one of our directories are all left alone (the sweep deletes
  recursively, so never widening from "directories this harness made" to "paths that match
  a prefix" is the property that matters);
- sweeping twice is idempotent and reports no failure; the sweep never throws;
- `createBenchTempDir` gives every call its own directory, sanitizes a hostile label
  (`../../Evil Label!!`) into the name rather than the path, reports a forward-slash
  `basePath`, and has an idempotent `remove()` that also un-registers the path.

Every case asserts only about paths it planted itself, because the same sweep legitimately
collects any real leftovers the machine is holding.

## Verified, not changed

- `module.closeAll()` really does close the provider and release LevelDB's directory lock
  (`packages/quereus-store/src/common/store-module.ts:745`), so the close order the
  teardown comment calls load-bearing is the order it needs to be.
- The opt-in and skip paths both work end to end after the edits: one row run with
  `QUEREUS_BENCH_LEVELDB=1` reported `193.5 µs … informational`, the same row without the
  variable printed `skipped — disk-backed rows are opt-in and advisory — set
  QUEREUS_BENCH_LEVELDB=1 to run them  informational`, and `%TEMP%` held no
  `quereus-bench-*` afterwards.
- The ratio-guard refusal was **not** re-verified. It needs a deliberately-bad guard added
  to a real suite file and reverted; the implementer verified it by hand with the exact
  output quoted, and no edit in this pass touches that path.

## Tripwires parked (conditional — not tickets)

- `bench/run.mjs`, at the results file's `informational` field: the array is every advisory
  name in the *suite set*, not only the ones this run selected, so a `--filter parser` run
  still writes all 19. Correct for its stated use as a lookup set; if a consumer ever reads
  it as "the advisory rows in this run", intersect it with `benchmarks` there.
- `bench/lib/tempdir.mjs`, in `remove()`: untracking before deleting means a removal that
  exhausts its retries is never retried at exit, when the lock holding it may be gone. Fine
  while such a failure is rare enough to be an investigated error; if retry-exhausted
  removals start appearing on some filesystem, keep the path tracked and make the exit hook
  the retry rather than a duplicate report.
- The implementer's own tripwire on `BACKENDS` stands: the ~0.5 s-per-row fork cost of
  printing a skip reason scales linearly with always-skipped backends (9.2 s for 19 rows
  today). If a default `yarn bench` ever pays 20-30 s to print skip reasons, move a
  backend-level skip question into the parent rather than dropping the rows.

## Filed as an arm on an existing ticket

`tickets/backlog/debt-bench-harness-self-test.md` already owns "the benchmark runner has no
tests of its own", including `bench/run.mjs`. Per the site-claim rule this pass appended an
arm rather than filing a fresh ticket, covering what is still unverified by machine:

- the runner's half of the `informational` flag — the cyan marker, the yellow
  advisory-regression summary, and **the ratio-guard refusal**, which is a build gate that
  could silently stop firing;
- `run.mjs`'s signal handler, which now kills the active worker and sweeps before exiting.
  The sweep is covered as of this review and the timeout path exercises the same sequence,
  but the handler itself has never run in a test, and Windows cannot deliver `SIGINT`
  programmatically;
- re-measured static-check coverage: `bench/run.mjs` gained ~110 lines here and is
  type-checked by nothing (`tsconfig.test.json` includes only `bench/lib/**` and
  `bench/workloads/**`; eslint globs `src`/`test` `.ts` only). The two new modules ARE
  inside the checked include, and that is what caught `tempdir.mjs` shipping with
  `TS2339: Property 'code' does not exist on type '{}'` in commit `9dd90e02d`, breaking
  `yarn lint` until the implementer's second commit fixed it. The same slip in `run.mjs`
  would still ship green.

The blocker that arm needs is already stated on that ticket: `discover.mjs` hardcodes the
suites directory, so a fixture suite cannot be pointed at without writing into the real
`bench/suites/`.

## Checked and found nothing worth filing

- **Source file size.** `bench/run.mjs` is 1018 lines (`wc -l`), the largest file in the
  bench tree, and this ticket added ~110 to it. Not filed: `packages/quereus/src` routinely
  carries 2 500-5 000-line files (`parser.ts` 5011, `vtab/memory/layer/manager.ts` 3915),
  so 1018 is well inside house norms and a split ticket would be noise. Re-measure if it
  passes the pack.
- **Comment density.** These bench files are essay-commented far past the project's stated
  "short purposeful functions with naming and composition over comment blocks". Not filed:
  it is the established house style across the whole `bench/` tree over several tickets, so
  re-litigating it inside one review would be scope creep against "match the surrounding
  code". A deliberate decision to change it belongs in `blocked/`, not a review finding.
- **Gating correctness of the flag.** Traced end to end — `expandBackends` stamps strict
  `true`, `loadSuite` and `validateBackends` reject a truthy non-boolean in both directions,
  `selectBenchmarks` normalizes, `informationalNames` reads the whole suite set (so a
  `--filter` cannot hide a bad guard), `compareOne` gates on `status === 'regression' &&
  !informational`, and `regressions` counts `gated` rows only. Non-delta statuses
  (`new`/`missing`/`filtered`/`skipped`/`failed`) were already ungated, so the flag has no
  interaction to get wrong there. No defect found.
- **Counter comparison on advisory rows.** `store-leveldb` declares no `openCounting`, so
  it reports engine work counters only — machine-independent integers. Counter changes
  never gate anyway. No issue.
- **Pre-existing failures.** None surfaced; `tickets/.pre-existing-error.md` was not
  written.
