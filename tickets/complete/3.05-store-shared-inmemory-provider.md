# What landed

`createInMemoryProvider(options?)` in `packages/quereus-store/src/testing/memory-provider.ts`,
exported from `@quereus/store/testing`. An all-`InMemoryKVStore` `KVStoreProvider` built to
`createCountingProvider`'s conventions: store names from the shared builders, one unified
`__stats__` store whatever schema/table it is asked for, and `costProfile` spread in only
when the caller supplies one (so a bare `createInMemoryProvider()` has no such property at
all — the shape a genuine pre-profile third-party provider has).

Unlike the counting sibling it implements `deleteIndexStore` and `deleteTableStores`, and
both ERASE: never-created is a no-op, a live store is `clear()`ed then dropped from the map,
an already-closed store skips the `clear()` (which would throw) and is dropped directly, and
the unified `__stats__` store is never touched. Telling live from closed needed a new
`get isClosed()` on `InMemoryKVStore`. `renameTableStores` and `beginAtomicBatch` are not
implemented.

Validation after the review pass: `yarn lint` clean, `yarn workspace @quereus/store run
build` / `typecheck` clean, `yarn workspace @quereus/store run test` → **1830 passing, 0
failing** (1827 baseline + 15 battery cases from implement + 3 added in review). No
`SKIPPED` line in the run, so both delete hooks were genuinely exercised by the reclaim
battery.

# Review findings

## Correctness — nothing broken found

Read the erase logic against the `KVStoreProvider` delete contract
(`src/common/kv-store.ts` lines ~400-450) and against every case in
`runStoreReclaimConformance`, and re-derived the closed-handle path rather than trusting the
handoff: `StoreTableBase.releaseIndexStore` is the *only* place in `packages/quereus-store`
that closes a store handle, and its single caller
(`StoreModuleIndex.tearDownIndexStore`) always asks the provider to delete immediately
after — so the closed-store branch is on the real `drop index` path and no engine path
leaves a closed store cached for reuse. Also checked the `costProfile` spread against an
explicit `undefined` and against `{}`, the duplicate-name case in `deleteTableStores`, and
the `getStatsStore` argument-ignoring contract. No defect.

## Fixed in this pass

- **Undocumented `beginAtomicBatch` omission, and it is not cosmetic.**
  `StoreModuleBase` sets its `atomicProvider` flag from that method's presence
  (`store-module-base.ts:238`) and takes a different commit path accordingly. A benchmark
  putting this provider next to LevelDB is therefore comparing two commit *paths*, not one
  path over two backends — exactly the misreading `bench-store-workloads` could make.
  Stated in the factory's header comment and in the README paragraph.
- **README overclaimed in the present tense** — it said this is what "most specs in this
  package reach for instead of pasting a private copy". Nothing uses it yet; the sweep is
  still open. Reworded to say so.
- **Three test gaps closed** in `test/memory-provider.spec.ts`: one handle per built store
  name (the caching the interface requires), the unified stats store returned for
  *different* schema/table arguments (documented behavior, asserted by neither battery), and
  `closeAll` actually closing handed-out stores with the name re-opening fresh afterwards.

## Tripwires (parked as `NOTE:` at the site, not filed)

- `getOrCreate` hands back a store the *caller* closed directly, so the next operation
  throws instead of re-opening the way a real backend would. Unreachable today (see the
  close-path check above). `NOTE:` at `getOrCreate`.
- After `erase`, a caller still holding the live handle can keep `put`ting into a store the
  provider has forgotten, and those writes vanish silently. Closing instead would break the
  contract line requiring a live handle to read back EMPTY rather than throw. `NOTE:` at
  `erase`.

## Reviewed and accepted as-is

- **`InMemoryKVStore.isClosed` on the main entry point's public surface** (the implementer
  flagged this for a second opinion). Keeping it: the provider cannot know that a *caller*
  closed a handle, so local bookkeeping in the factory cannot answer the question, and the
  alternative the project's exception rules forbid is `try { clear() } catch {}`. Plain
  side-effect-free boolean accessor over a flag the class already maintains.
- **No negative-control spec for the erase logic**, unlike `store-name-distinctness.spec.ts`
  for the naming guard. Agreed with the implementer's call: the shared reclaim battery
  already has four real backends as reference implementations, and a deliberately-broken
  fifth double would pin ~30 lines of map manipulation.
