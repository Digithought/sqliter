# What landed

A CHECK constraint, a column `DEFAULT`, and a `GENERATED ALWAYS AS` body may all contain
a subquery, so any of them can legitimately read a column or a table belonging to some
*other* table, in some other schema. `ALTER TABLE … RENAME` has always known this — it
rewrites those expressions across every table in every schema — while the DROP guards
scanned only the altered table's own constraints and columns. That gap let both of these
succeed and leave the referencing table impossible to write to:

```sql
create table T (id integer primary key, v integer);
create table X (id integer primary key, n integer, check (n < (select max(v) from T)));

alter table T drop column v;   -- was accepted; X then failed with "Column not found: v"
drop table T;                  -- was accepted; X then failed with "Table 'T' not found…"
```

Both now refuse, `StatusCode.CONSTRAINT`, with a message naming the dropped object, the
referencing table (schema-qualified when it lives elsewhere), and the constraint (by name,
or by expression when unnamed).

## Shape

One new catalog query, `packages/quereus/src/schema/expression-dependents.ts`, that every
guard calls instead of hand-rolling a scan:

- `findColumnExpressionDependent(db, tableSchema, columnName, arm)` — `arm` is `'check'`
  or `'columnExpression'` (DEFAULT + generated).
- `findTableExpressionDependent(db, schemaName, objectName)`.

Both walk `_getAllSchemas()`, build one `snapshotObjectRefResolvers(db)` snapshot and take
`forHomeSchema(table.schemaName)` per scanned table, and reuse the existing scope-aware
probes — so "the drop refuses exactly what a rename would have rewritten" holds by sharing
the walk rather than by comment. The own-table / other-table probe split mirrors
`rewriteTableForColumnRename`'s `isRenamedTable` branch: seeded
(`columnReferencedInCheckExpression`) on the probed table, unseeded
(`columnReferencedInAst`) everywhere else.

| Verb | Guard | Called from |
| --- | --- | --- |
| `DROP COLUMN` | `assertNoColumnExpressionNamesColumn`, `assertNoCheckConstraintNamesColumn` | `runDropColumn` (`alter-table.ts` ~1180) |
| `DROP TABLE` / `VIEW` / `MATERIALIZED VIEW` | `assertNoExpressionDependsOn` (`expression-drop-guard.ts`) | `emitDropTable`, `emitDropView`, `emitDropMaterializedView` |

Emitters only — never `SchemaManager.dropTable`, which also drives rollback, catalog
import and the declarative differ's drop/recreate.

Deliberate deviations from the implement ticket: the finders return the **first** dependent
rather than an array (every caller throws on it); `assertNoColumnDefaultNamesColumn` was
renamed `assertNoColumnExpressionNamesColumn` (it now also reports a generated body);
`DROP VIEW` / `DROP MATERIALIZED VIEW` **do** get the guard, since a CHECK subquery can read
a view and losing it breaks the referencing table exactly as losing a table would. The
asymmetry the engine documents is on the other side and is unchanged — dropping a *table*
out from under a plain view is still allowed and still breaks the view (pinned by §5 of
`41.10.4`).

### Major — filed as tickets

- **The refusal stops one hop short: a dependent reached through a view is not seen.**
  Found by probe, verified in-session against the landed code:

  ```sql
  create table t (id integer primary key, v integer);
  create view vv as select v from t;
  create table x (id integer primary key, n integer, check (n < (select max(v) from vv)));
  drop table t;                 -- ACCEPTED
  insert into x values (1, 1);  -- Table 't' not found in schema path: main
  ```

  and identically for `alter table t drop column v` → `Column not found: v`. That is the
  exact damage this ticket exists to prevent, one indirection out, and the handoff does not
  mention it. It is not covered by `assertion-guards-follow-view-chains-and-schemas`, whose
  closure is scoped to assertion bodies. Filed `fix/4.7-expression-guards-follow-view-chains`
  with `prereq: assertion-guards-follow-view-chains-and-schemas`, filed at the shared-primitive
  rung rather than as two point fixes: that ticket builds
  `schema/object-dependency-closure.ts`, and the expression guards must consume it rather
  than grow a second reachability definition. Documented as a known limit inline (see
  *Fixed in this pass*) so the gap is not silently shipped.

- **Real coverage loss in the maintained-table validator rebuild**, as the handoff honestly
  flagged (gap 1). Confirmed by reading `database-materialized-views.ts`
  `rebuildConstraintValidatorsFor`: the poisoned-validator catch and the `table_added`
  self-heal branch are both live code on internal drop paths (rollback, catalog import,
  declarative differ) but are now reachable by no test, because the SQL sequence that drove
  them is correctly a refusal. Filed
  `backlog/debt-maintained-validator-rebuild-fallbacks-untested` — unit-level, driving
  `SchemaManager.dropTable` directly, since SQL genuinely cannot get there any more. The
  four rewritten pre-existing tests were each read against their originals: `13.8` and
  `13.9.1` are cleanup reordering with no assertion changed, and `51.8` /
  `maintained-table-declared-constraints.spec.ts` gained stronger arms (nothing-applied,
  CHECK-still-enforces, escape hatch) in exchange for the deleted one.

### Tripwires parked (not tickets)

- **First-hit ordering past the probed table** is `_getAllSchemas()` × `getAllTables()`
  insertion order, so with two referencing tables which one the message names is not
  determined by any user-visible rule (verified: two dependents → the first-created is
  named). Harmless while the message is advisory. `NOTE:` at `tablesProbedTargetFirst` in
  `expression-dependents.ts`, saying what to do instead if a caller ever needs to *list*
  dependents (a `CASCADE` arm, an introspection function).
- **Two catalog walks per `DROP COLUMN`** — already a `NOTE:` in the module header from the
  implement pass, with the "gate on a cheap literal name scan of the stored SQL" remedy.
  Left as is; the condition has not tripped.

### Checked and clear — with the reason

- **Partial-index predicates need no arm** (handoff gap 3, verified only by reading).
  Re-verified by running it: `create index ix on q (v) where (select count(*) from p) > 0`
  → `Unsupported expression in partial-index predicate: subquery`. The parser rejection is
  real, so such a predicate can only name its own table. Claim holds; no ticket.
- **Mutual-dependency lock-out** — could two tables' unnamed table-level CHECKs reference
  each other, leaving neither droppable and neither constraint addressable? No. An inline
  unnamed CHECK requires its target to already exist, so the cycle can only be closed by
  `alter table … add check (…)`, which auto-names the constraint (`check_0`) and therefore
  leaves `DROP CONSTRAINT` as an escape hatch. Verified both halves. No new dead end.
- **Message spelling.** `drop table MAIN.CS` reports `'main.CS'` — the catalog's spelling,
  not the caller's, as the guard's comment claims. Same-schema referencing tables are named
  bare, cross-schema ones qualified (`'temp.DtCsRef'`). Verified.
- **Rename-then-drop.** After `alter table rs rename to rs2`, the guard sees the rewritten
  CHECK and refuses `drop table rs2` — the shared-walk claim holds across a rename.
- **Self-reference does not block its own `DROP TABLE`**, including when a *second* table
  also references it (the second is what gets named). Verified.
- **Cross-schema assertion asymmetry** (handoff gap 2) is intentional and correctly scoped
  out: `drop table main.at` with a `temp`-owned assertion naming it is still accepted, and
  that is precisely `assertion-guards-follow-view-chains-and-schemas`' Miss 2. Verified the
  in-code comment points at that slug rather than reading as an oversight.
- **`DROP SCHEMA` is not a statement** in this engine, so there is no bulk-drop path that
  routes around the guard.
- **Source hygiene.** New files are 251 / 67 lines; `drop-column-guards.ts` 279. Comment
  density is high but matches the surrounding emit/ and schema/ files, and every long block
  carries a decision rather than a restatement of the code. `alter-table.ts` grew to 2526
  lines (from the 2419 recorded in `debt-oversized-source-files`) — that site is already
  claimed by that ticket, and +107 lines is evidence, not a new arm.
