# What landed

23 of the 27 benchmarks declare a `counters()` pass. The remaining 4 are the parser
benchmarks, which declare none on purpose and say so in a comment.

| suite | declares `counters()` | what it snapshots |
|---|---|---|
| execution | 15 / 15 | `snapshotStatement` — the same query `fn` times |
| mutation | 4 / 4 | `snapshotStatement` / `snapshotStatements` |
| planner | 4 / 4 | `snapshotPlanShape` only — these never execute |
| parser | 0 / 4 | nothing to count; no `Database`, no plan, no runtime |

Execution SQL was hoisted into a module-level `SQL` map so each query is named once and
referenced twice (by `fn` and by `counters()`) rather than duplicated, and
`mutation.bench.mjs` shares its row-tuple builders and batch-insert helper between the
timed and untimed paths for the same reason. Both deviate from the ticket's sketch, and
both were verified during review — see below.

The counters pass costs +834 ms on a ~48 s run (+1.8%), measured with and without
`--no-counters` and corroborated against an 858 ms prediction summed from per-benchmark
medians.

# Review findings

## Verified rather than taken on trust

**The stability claim, re-measured independently.** Two fresh runs
(`node bench/run.mjs`, then `node bench/run.mjs --baseline latest`) reproduced
`Counters: 23 identical, 0 changed, 0 new, 0 dropped`. Then a stronger check the handoff
did not do: a direct `JSON.stringify` diff of this review's run against the implementer's
run from ~25 minutes earlier — a different session, different process tree, different
machine load — came back **23 identical, 0 differing, 4 with no counters on either side**.
A third run after this review's own edits reported 23 identical again. The claim holds on
n=3 same-machine runs across two sessions.

**Both timed paths survived their refactor.** All 15 execution benchmarks were checked
mechanically: each benchmark's `db.eval(SQL.x)` and its `snapshotStatement(db, SQL.x)`
reference the same key, 15/15, no mismatches — so no counters pass can be describing a
statement its `fn` no longer runs. Every hoisted literal is visible on both sides of the
implement diff and matches, including the two multi-line template literals whose
indentation changed when they moved. The four `mutation.bench.mjs` `fn`s were read
statement by statement against their pre-change forms: `batchInsert` + `bulkRow` /
`updRow` / `delRow` reconstruct byte-identical SQL to the inline loops they replaced, and
the schema and statement constants are unchanged strings.

**The counters describe what the benchmarks actually run.** `db.eval` and `db.exec` both
route through `Database.prepare`, which is what `snapshotStatement` calls, so the timed and
counted paths compile the same plan rather than merely the same text.

**Off-by-one check on the two-snapshot passes.** `bulk-insert-10k` inserts batches
0 / 1–18 / 19 and `single-row-insert-1k` inserts rows 1 / 2–999 / 1000 — both cover their
full row count with no gap and no double-insert.

**Lint and tests.** `yarn lint` passes across all workspaces. `yarn test` — 9810 passing,
25 pending, 0 failing. The seven pre-existing `tsc` errors the handoff flagged were already
resolved by the runner's triage pass (commit `2c768943c`); `tickets/.pre-existing-error.md`
is gone and nothing was re-reported.

## Fixed in this pass

**`snapshotStatement` silently counted only the first statement of a multi-statement
string.** A `Statement` iterates only the batch entry it is positioned on, so
`snapshotStatement(db, 'a; b')` would run and count `a`, ignore `b`, and return a snapshot
that looks perfectly stable while describing a fraction of the work — the exact failure
mode the helper's own doc comment warns about for drift. No current caller passes
multi-statement SQL, so nothing was mismeasured, but the boundary was one typo away from a
silent wrong answer that no verdict would flag. Added a guard that throws on
`astBatch.length !== 1`, pointing at `snapshotStatements` for sequences, and verified both
directions: the guard fires on a two-statement string and single-statement passes are
untouched (23 identical counters after the change).

**`update-where-1k`'s comment asserted an invariant that is false.** It claimed `fn` "is
its own inverse: the pair leaves `upd_t` in the state it found it". It does not — the first
call rewrites `label` from `label_N` to `reset` and never restores `setup`'s labels. The
property that actually matters is weaker and true: `fn` reaches a fixed point after its
first call, and `val` (which the predicate reads) is never touched, so the counters pass
sees the same 1,000 rows regardless of how many iterations calibration chose. Reworded to
state the real invariant, since a future reader hardening this benchmark would otherwise be
reasoning from a false premise.

**`docs/runtime.md` stated machine independence without its one exception.** The § *Work
counters* section says snapshots are "byte-identical on every machine, every run, and every
process". Qualified with the QuickPick exception found below, and pointed at the ticket.

## Filed as new tickets

**`backlog/bug-join-order-depends-on-wall-clock`** — the one major finding, and it is in
the engine rather than in this diff. `ruleQuickPickJoinEnumeration` bounds its search with
`while (tours < maxTours && elapsed <= timeLimitMs)`, defaults `maxTours: 100`,
`timeLimitMs: 100`, `enabled: true`, `minTriggerCost: 0`. Individual candidate orderings
are deterministic; *how many* of them finish inside 100 ms is not. A slower or busier
machine can therefore choose a different join order — a different plan, a different plan
shape, different row counts — for the identical query and data. The rule only engages on
joins of three or more relations, and every join in the current benchmark suite is
two-relation, which is why three runs came back byte-identical: the mechanism is real but
this suite does not reach it. Filed at the representation rung rather than as a benchmark
patch — the fix is a search budget denominated in candidates rather than milliseconds, which
makes the whole class of "plan depends on how fast the machine was" unrepresentable, instead
of a per-benchmark workaround.

**Arm appended to `plan/4-bench-regression-gate`** rather than a second ticket, matching the
precedent already in that file. That ticket's design rests on "work counters do not vary by
machine, so they are checked in as exact values and any difference is a failure" — stated as
fact, never measured. What this ticket verified is narrower: repeated runs, separate
processes, one machine, one Node version, one OS. The arm records both the gap and the
concrete mechanism above, and asks for one real two-machine diff before the reference set is
trusted. Not a separate ticket because the decision it forces is that ticket's.

## Checked and deliberately not filed

**Docs are stale for the counters feature, and that is already owned.**
`docs/benchmarking.md` has no work-counter section, does not document `--no-counters` or
`counters_collected`, and its "Where the code lives" table omits `bench/lib/counters.mjs`.
Every one of those is an explicit TODO in `implement/2.22-bench-counter-tests-and-docs`,
which is sequenced directly after this ticket with `prereq: bench-counter-suite-passes`.
Re-filing would duplicate it. The one doc statement that was *wrong* rather than merely
missing — the machine-independence claim in `runtime.md` — was fixed here instead of
deferred, because 2.22 documents the premise and should not document it uncorrected.

**Nothing tests the counter comparison rules.** Same ticket, same reason — that is 2.22's
first TODO. Noted, not re-filed.

**The first/last double snapshots are provably identical today, and that is defensible.**
Confirmed from the results JSON: `bulk-insert-10k`'s `firstBatch` and `lastBatch` are
byte-identical (6 instruction executions, 500 `updateCalls`, `rowsScanned: 0`), as are
`single-row-insert-1k`'s `firstRow` / `lastRow`. A reviewer could call the second snapshot
redundant. It is not: `rowsScanned` on the target table is in the snapshot, so a change that
starts probing by scan on insert moves `lastBatch` away from `firstBatch` and the diff
prints it. The equality is an asserted invariant, not idle duplication, and the code says so.

**`execution.bench.mjs` has no file-level `COUNTERS:` header** while the other three suites
do. Its rationale lives on the `SQL` map's doc comment and on the first benchmark instead.
Left alone — adding a fourth copy of the same paragraph would trade a small inconsistency
for real duplication.

## Tripwires

**No new tripwires were recorded by this review**, and one was inherited intact: the `NOTE:`
at the top of `mutation.bench.mjs` recording that the three own-database counters passes
populate a full 10K-row table each (~340 ms of the ~830 ms total), fine at four benchmarks,
worth shrinking if the file reaches a dozen. Verified it is at the right site, states its
condition and its fix, and is tagged so it greps with the rest.

## Known limits this review did not close

- **Cross-machine, cross-OS and cross-Node-version stability is still unmeasured.** Now
  recorded where the decision lives (the arm on `bench-regression-gate`) rather than only in
  a handoff note, and with a named mechanism that could break it.
- **The `dropped` counter verdict has still never been produced by a real run.** `same` was
  seen 23 times per run across three runs, `new` incidentally; `changed` and `dropped` come
  from 2.22's unit coverage, not from the harness.
