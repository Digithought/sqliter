# What shipped

Both assertion DROP guards moved from *"does this one assertion body mention this
one object, in this one schema?"* to *"can this assertion — in any schema — reach
this object?"*, where reach is the breadth-first closure over stored view and
materialized-view bodies.

- `schema/object-dependency-closure.ts` — `reachableObjects(db, root, homeSchema,
  resolvers)`. Each body walked under its OWN home-schema resolver; `resolvers` is
  a required parameter so a caller looping over many roots shares one pre-mutation
  snapshot. Terminates on a visited set of object keys. Returns the walked bodies
  (root first, then breadth-first, each carrying the described chain from the root)
  and `namerOf(key)`.
- `collectTableRefsInAst` (`schema/rename/table-rename.ts`) — a third sink over the
  same traversal the rename rewrite and the read-only probe already share, so the
  closure inherits scope-awareness (a CTE or FROM alias that merely shadows a name
  contributes no key) rather than re-deriving it.
- `assertNoAssertionDependsOn` (table / view / materialized view) and
  `assertNoAssertionNamesColumn` (DROP COLUMN) both scan assertions in every
  schema, home schema first, and refuse on the reach. Messages keep the old wording
  for a direct reference, add the chain for an indirect one, and schema-qualify the
  assertion when it lives elsewhere.

Docs: `docs/sql-ddl.md` § 2.6.1 and `docs/sql-alter.md` (RENAME paragraph, DROP
COLUMN bullets, and the CHECK-family one-hop paragraph, now scoped to that family).

**Major — one, filed.** `tickets/fix/4.8-drop-column-guard-blind-to-star-reexposure.md`.
The column verb probes each reached body for the column **by name**, and a view
that re-exposes the column with a star spells it nowhere. Verified: `create view v
as select * from t` plus `create assertion a check (… from v where x < 0)` accepts
`alter table t drop column x`, after which an insert into an *unrelated* table
fails `Column not found: x` at commit — the exact harm this ticket exists to
prevent. `select t.*` and a materialized view of either leak identically; the
named-projection spelling (`select id, x from t`) is correctly refused, which is
what makes this a projection-lineage gap rather than a missing guard. Not fixed
inline: the precise answer needs the view body's output column set, which
`ViewSchema` does not carry, and the cheap over-approximation ("a star re-exposes
everything") reverses a documented, tested asymmetry — a design call, not an edit.
The ticket takes `expression-guards-follow-view-chains` as a prereq so one lineage
rule covers both guard families; two would restart the disagreement this 4.x
sequence has been closing. Site-claim check: `4.7` already claims
`drop-column-guards.ts` and the closure, but for a different root cause (name-vs-
reach at the object level); this is lineage at the projection level, so it is a
separate ticket that cross-references it rather than an arm on it.
