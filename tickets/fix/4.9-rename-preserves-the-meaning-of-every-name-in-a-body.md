# What a name means must survive the rename — all names, not just the rewritten ones

`rename-rewrite-preserves-what-a-reference-resolves-to` established half an
invariant: after the rename rewrites a reference, re-resolving that reference
must still land on the renamed table, and the rewrite adds a schema qualifier
when it otherwise would not. That covers the references the walk *rewrites*.

The other half is unguarded. A rename introduces a new name and frees an old
one, and both of those can change the meaning of names the rewrite never
touches. Two verified arms, both silent — no error, just different rows.

## Arm 1 — an untouched reference re-binds to the newly created name

A saved query that reads a table by its short name finds it by searching a list
of schemas in order. Renaming a table *into* an earlier schema on that list
makes the short name find the new arrival instead.

```sql
create table main.k (id integer primary key, x integer);
insert into main.k values (1, 10);
create table temp.other (id integer primary key, x integer);
insert into temp.other values (99, 999);

-- temp-owned body; bare `k` resolves to main.k, because temp holds no `k`.
create view temp.v as select id, x from k;
select * from temp.v;                   -- {id: 1, x: 10}

alter table temp.other rename to k;     -- temp now holds a `k`

select * from temp.v;                   -- {id: 99, x: 999}  ← re-bound
```

The view's text never mentions the renamed table, so the rename walk never
matches it and never rewrites it. Verified the same way for a materialized view
(`refresh materialized view` swaps in the other table's rows) and for an
assertion (it stops watching the table it was written against — a violating
write to `main.k` is accepted after the rename).

`CREATE TABLE` and `DROP TABLE` re-bind the same reference the same way; they
are the same class but have no propagation pass to hang a fix on, so they are
out of scope here. Fixing rename first is what makes the rule statable.

## Arm 2 — two sources in one body collapse onto one qualifier

Inside a single body, the name a `FROM` source exposes as a column qualifier is
its table name. Renaming a source onto a name a *sibling* source in the same
`FROM` already exposes leaves both spelled the same, and every qualifier in the
body then points at whichever one wins.

```sql
create table main.t (id integer primary key, x integer);
insert into main.t values (1, 10);
create table temp.t2 (id integer primary key, x integer);
insert into temp.t2 values (2, 20);

create view temp.v as
  select t.x as a, t2.x as b from t join temp.t2 on t.id = t2.id - 1;
select * from temp.v;                   -- {a: 10, b: 20}

alter table main.t rename to t2;
select * from temp.v;                   -- []  ← no error, no rows
```

The rewritten body reads
`select t2.x as a, t2.x as b from main.t2 inner join "temp".t2 on t2.id = t2.id - 1`
— the schema qualifier on the source is correct and does not help, because a
qualifier is matched against the source's bare name. The join condition has
become self-referential and the projection reads one table twice.

This arm predates the qualification work: without the qualifier the body would
read `from t2 inner join "temp".t2` and collapse identically.

## The invariant to aim for

Both arms resolve at the same code site — the sink `renameTableInAst` runs for
every reference the walk reports. Today that sink acts only on references that
*match* the renamed table. The rule it should enforce instead:

> Walking a body for a rename, **every** reference must mean after the statement
> exactly what it meant before — whether or not the rename rewrote it.

The machinery is already in place: each walk carries a before-resolver and an
after-resolver (`TableRenameTarget.resolve` / `.resolveAfter`), so arm 1 is a
comparison the sink can already make on every reference, qualifying with the
schema the *before* answer named when the two disagree. Arm 2 needs the same
question asked of the body's own `FROM` frame rather than the catalog: when the
new bare name is already bound in the frame the source sits in, preserve the old
qualifier by aliasing the source (`from main.t2 as t`) instead of letting the
two collapse.

Both must stay **conditional**, like the qualification already is — a rename
with no collision must leave every body byte-identical, or every materialized
view's stored body hash churns on every unrelated rename.

## Watch out for

- The read-only DROP-guard probe and the closure collector share this traversal
  on purpose (one traversal, three sinks). Whatever is added must not change
  what counts as *a reference*, only what the rewrite sink does with one.
- The declarative differ inverse-rewrites bodies with a single-schema resolver
  and has no declared counterpart for a qualifier or an added alias; see the
  `NOTE:` in `inverseRenamedViewParts`.
- A body may legitimately already alias its sources; arm 2's fix must not
  overwrite an alias the author wrote.
