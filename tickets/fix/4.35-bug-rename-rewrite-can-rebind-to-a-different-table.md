# A rename can move a reference onto the wrong table

A stored body (a view, a materialized view, an integrity assertion) may name a
table without a schema qualifier. Such a name is resolved against the body's own
schema first and then the session search path, so a body living in `temp` can
legitimately mean a table in `main` — `temp` simply has no table of that name.

When that table is renamed, the propagation rewrites the reference **in place**:
it swaps the name and leaves the reference unqualified. But the new name is
resolved from scratch the next time the body is planned, and by then the answer
may be a different table. If the body's own schema happens to hold a table with
the *new* name, the reference now points there instead — no error, no warning.

The reference used to resolve to the renamed object. After the rewrite it does
not. That is the whole defect: **the rewrite is not required to preserve what the
reference resolves to.**

## Reproduction (verified at `0da1f8cd`)

All three cases share one setup: `main.t` is the table being renamed, `temp.t2`
already exists, and a `temp`-owned body reads a bare `t` (which means `main.t`,
because `temp` holds no `t`).

**View — wrong rows, silently.**

```sql
create table main.t  (id integer primary key, x integer);
insert into main.t values (1, 10);
create table temp.t2 (id integer primary key, x integer);
insert into temp.t2 values (99, 999);
create view temp.vt as select id, x from t;

alter table main.t rename to t2;

select * from temp.vt;   -- expected {1, 10}; actually returns {99, 999}
```

The stored body reads `select id, x from t2`, and bare `t2` now resolves to
`temp.t2`.

**Materialized view — the stored rows and the definition disagree.**

Same setup with `create materialized view temp.mv as select id, x from t`. After
the rename the record is internally inconsistent: its recorded source list says
`main.t2` and row-time maintenance is registered against `main.t2`, so reads keep
returning the right rows — but the body says bare `t2`. `refresh materialized
view temp.mv` re-runs the body and replaces the contents with `temp.t2`'s rows.

**Assertion — integrity enforcement silently stops.**

Same setup with
`create assertion temp.a check (not exists (select 1 from t where x < 0))`.
After the rename the regenerated violation query reads
`select 1 where not (not exists (select 1 from t2 where x < 0))`, which now
watches `temp.t2`. `insert into main.t2 values (2, -1)` commits cleanly; before
the rename the equivalent write was refused.

## Why it is worth fixing at the walker, not at each caller

Every one of the three symptoms is one code site: the rewrite sink in
`renameTableInAst` (`packages/quereus/src/schema/rename/table-rename.ts`), which
calls `ref.setName(newName)` and nothing else. The `TableRef` the walk hands its
sink exposes only `setName`, so a rewrite physically *cannot* add a schema
qualifier even where one is needed.

The invariant that retires the class is a post-condition on the rewrite rather
than a fix for the cross-schema instance:

> after rewriting a reference, re-resolving it — under the same home schema path,
> against the catalog **as it will be after the rename** — must yield the renamed
> object's key.

Anything that satisfies that post-condition fixes all three symptoms at once and
keeps satisfying it when new body kinds are added. The obvious way to satisfy it
is to let the sink write a schema qualifier when the bare new name would not
resolve back, but the shape is the fix agent's call.

## What the work needs to settle

- **Where the post-rename name set comes from.** The walker deliberately resolves
  against a *pre-mutation* snapshot (`snapshotObjectRefResolvers`, and the
  SNAPSHOT DISCIPLINE comment there explains why). The post-rename set is that
  snapshot with the old name removed and the new one added in the renamed
  schema — derivable without touching the live catalog, but it is a second
  resolver the callers have to thread through.
- **How to express the fix on the reference.** `TableRef` currently reports
  `schema` and `setName`. Three of the five emit sites are *column qualifiers*
  (`t.x`), which cannot carry a schema qualifier at all — those bind through the
  FROM source, so qualifying the source is enough and the qualifier sites need
  nothing. Only the identifier-reference and FROM-source sites do.
- **Whether qualifying changes anything downstream.** A rewritten body is
  re-rendered to SQL and re-persisted; a newly-qualified name flows into
  `schema-rename-detection`'s canonicalization (which elides an own-schema
  qualifier) and into `rename/self-qualifier-strip.ts`. Confirm neither reads a
  cross-schema qualifier as a spurious change.
- **The read-only probe must not drift.** `renameTableInAst` and the DROP guards'
  "does this AST reference X?" probe are deliberately one traversal so the guard
  refuses exactly what a rename rewrites. A post-condition on the rewrite sink
  must not change what the probe sink reports.
- **The pre-flight inherits the defect.** `assertRenameDependentsPersistable`
  vetoes prospective catalog entries using the same rewrite, so it currently
  renders the mis-bound body too. Whatever fixes the walker fixes it, but the
  store-path tests should confirm it.

## Expected behavior

After `alter table <schema>.<old> rename to <new>`, every dependent body the
propagation rewrote must still read the renamed table — regardless of what other
tables named `<new>` exist in any schema on that body's home path. Bodies whose
reference did *not* resolve to the renamed object must still be left untouched
(the existing `test/logic/41.3-alter-rename-propagation.sqllogic` §49 pair).

## Coverage the fix should leave behind

The natural home is a generalized test rather than three point tests: for each
body kind (view, materialized view, assertion) and each combination of
{qualified reference, bare same-schema reference, bare fallthrough reference} ×
{new name free, new name already taken in an earlier schema on the home path},
assert the body still resolves to the intended table after the rename. The
existing fallthrough tests in `test/schema/rename-cross-schema.spec.ts` and
§49 of `41.3-alter-rename-propagation.sqllogic` cover exactly the "new name free"
half of that grid; the collision half is what is missing.

For the materialized view, assert on `refresh materialized view` and not only on
reads — the stale-rows path is what exposes the mis-bound body.
