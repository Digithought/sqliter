# A star hides the column the guard is looking for

`ALTER TABLE … DROP COLUMN` refuses when a live integrity rule can reach the
column. Reach is computed over view and materialized-view bodies, and each body
in the chain is probed for the column **by name**. A view that re-exposes the
column with a star names it nowhere, so the chain reads clean and the drop is
accepted.

Verified in-session against the code as it stands after
`assertion-guards-follow-view-chains-and-schemas` landed. All three star spellings
leak, and the failure is not local — it is every write to the whole database,
because the assertion evaluator recompiles every live assertion on any commit:

```sql
create table t (id integer primary key, x integer);
create view v as select * from t;
create assertion a check (not exists (select 1 from v where x < 0));

alter table t drop column x;      -- ACCEPTED

create table unrelated (i integer primary key);
insert into unrelated values (1);
commit;                            -- Column not found: x
```

`create view vq as select t.* from t` and `create materialized view m as select *
from t` behave identically. The named-projection spelling — `create view v as
select id, x from t` — is correctly refused today, which is what makes this a
lineage gap rather than a missing guard.

## Root cause, and why it is one site

The probe asks *"does this body spell `t.x`?"*. The question is *"can a reference
in this body's consumer resolve back to `t.x`?"*. A star projects the source's
column set without spelling any of it, so the two questions diverge exactly where
a star sits between the rule and the table.

The site is the per-body loop in `assertNoAssertionNamesColumn`
(`runtime/emit/drop-column-guards.ts`), which carries a `KNOWN GAP` note pointing
here. `schema/expression-dependents.ts` reaches the same loop shape for CHECK /
DEFAULT / generated bodies once `expression-guards-follow-view-chains` widens it
onto the same closure — hence the prereq. **One answer must cover both families**;
two lineage rules in the catalog is how the guards start disagreeing again, which
is the family of bug this whole 4.x sequence has been closing.

`ViewSchema` carries only the optional explicit `create view v(a, b)` column list,
not the body's resolved output columns, so nothing in the catalog can answer
"which columns does `v` expose?" without planning the body. That is the real
decision in this ticket and why it is not a small one.

## Expected behavior

Refused, `StatusCode.CONSTRAINT`, nothing applied:

- `alter table t drop column x` when a live assertion reads `x` through a view
  whose body is `select * from t`, `select t.*`, or a materialized view of either.
- The same through a chain of two or more views, with a star at any position.
- The same for a CHECK / DEFAULT / generated body once the prereq has widened that
  family onto the closure.
- Cross-schema, both directions, matching what the name probe already does.

Still allowed — the false-refusal shapes any fix must not break:

- A rule that reads the star view but never names the dropped column
  (`create view v as select * from t` + `check (… from v where id < 0)`, dropping
  `t.x`). This is the shape a blunt "a star re-exposes everything, refuse" rule
  gets wrong, and it is common.
- An assertion whose own body is `select * from t` and names no column at all —
  pinned by `41.10.2` §7, still legal, still unaffected by the drop.
- A CTE or FROM alias that merely shadows the name anywhere in the chain
  (`41.10.2` §25).
- A like-named column on a third table reached by a different branch of the same
  chain (`41.10.2` §21).

## Notes for whoever picks this up

- The cheap over-approximation ("any body in the reach stars over the target table
  ⇒ every column of that table is referenced") is sound but refuses the first
  still-allowed shape above, which reverses a documented and tested asymmetry. If
  it is chosen anyway, that is a deliberate policy change and both docs sections
  and `41.10.2` §7's neighbourhood need to say so.
- The precise answer needs the view body's output column set. Whether that comes
  from planning the body at guard time (DDL is rare; the body is already parsed),
  from caching a resolved column list on `ViewSchema`, or from a narrower
  star-expansion walk is the design call.
- The table verb (`DROP TABLE` / `DROP VIEW` / `DROP MATERIALIZED VIEW`) has no
  equivalent hole — it matches the object, not a column — so nothing there changes.
- `docs/sql-ddl.md` § 2.6.1 and `docs/sql-alter.md` § DROP COLUMN each document
  this limit as known. Both come out when it closes.
