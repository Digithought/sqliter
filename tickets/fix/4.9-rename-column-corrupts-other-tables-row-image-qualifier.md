# What goes wrong

`new` and `old` are not reserved words in Quereus, so a user may create a table
called `"new"`. Inside a CHECK constraint, a column `DEFAULT`, or a
`GENERATED ALWAYS AS` body, a bare `new.<col>` / `old.<col>` qualifier means **the
row being written** — never a table. The engine knows this and gets it right
almost everywhere: `drop table "new"` is correctly allowed even while some other
table's `check (new.n > 0)` exists, and that case is pinned
(41.10.4 §15, `docs/sql-alter.md` § DROP COLUMN).

The **column** verbs miss it. Verified in-session against `main` at
c68861b5:

```sql
create table "new" (id integer primary key, v integer);
create table NwCk (id integer primary key, v integer,
                   constraint ck_nw check (new.v > 0));
insert into NwCk values (1, 5);            -- fine

alter table "new" rename column v to w;    -- ACCEPTED, silently

insert into NwCk values (2, 7);
-- QuereusError: new.w isn't a column
```

`NwCk`'s CHECK was rewritten to `new.w > 0`. `NwCk` has no column `w`, so **every
subsequent write to `NwCk` fails**, and the statement that broke it named neither
`NwCk` nor its constraint. The damage is persisted with the schema — on a store
backend it survives a restart, and the only recovery is rebuilding `NwCk`.

The same root cause has a milder second symptom, a refusal instead of a
corruption:

```sql
create table "new" (id integer primary key, v integer);
create table NwCk (id integer primary key, v integer,
                   constraint ck_nw check (new.v > 0));

alter table "new" drop column v;
-- Cannot drop column 'v' from 'new': it is referenced by CHECK constraint 'ck_nw' on table 'NwCk'
```

That drop is legal — `ck_nw` is about `NwCk`'s own written row and has nothing to
say about the table called `new`. It is refused anyway.

# Root cause — one site, and it is a missing third state

The column-rename walk models only **two** row-image contexts, chosen by which
entry point a caller uses (`schema/rename/column-rename.ts`, the
`matchRowImageQualifier` field on the walk state):

| entry point | what `new.x` means to the walk |
|---|---|
| `renameColumnInCheckExpression` (seeded) | the row image of the table being renamed — match it |
| `renameColumnInAst` (unseeded) | nothing binds the qualifier, so fall through and treat `new` as a **catalog table reference** |

There is a third context, and every cross-table CHECK / DEFAULT / generated body
is in it: *this expression IS written-row context, but the row image belongs to
some OTHER table, so `new.` / `old.` names nothing this walk cares about and must
be ignored entirely.* Falling through to "table reference" is what produces both
symptoms above.

The **table** walker already has exactly this mode —
`TableRenameOpts.rowImageContext` in `schema/rename/table-rename.ts`, whose
suppression fires on a bare, unbound `new.` / `old.` qualifier. That is why the
table verb gets `drop table "new"` right and the column verb does not. The two
walkers disagree about the same SQL, which is the family of divergence the whole
4.x guard sequence has been closing.

Two call sites consume the missing mode once it exists:

- rename propagation into **other** tables' CHECK / DEFAULT / generated bodies
  (`renameColumnInCheckConstraints` / `renameColumnInColumnExpressions`, and
  whatever drives them for non-renamed tables) — the corruption arm;
- `columnProbe`'s unseeded branch in `schema/expression-dependents.ts`, for a
  scanned table's **root** body only — the false-refusal arm. Reached view /
  materialized-view bodies must NOT get it: a stored view body cannot legally
  contain a bare `new.` qualifier at all (`CREATE VIEW` rejects it — see the
  `NOTE:` in `schema/object-dependency-closure.ts`).

Prefer making the row-image context an **explicit argument** over adding a third
entry point. Two entry points already encode the state implicitly and that is how
the third one got lost; a named parameter with three values makes the missing case
impossible to overlook at a call site.

# Expected behavior

- `alter table "new" rename column v to w` leaves every OTHER table's
  `new.` / `old.` qualifier untouched. `NwCk`'s CHECK still reads `new.v > 0` and
  `NwCk` stays writable.
- `alter table "new" drop column v` is **allowed** when the only thing "naming" it
  is another table's row-image qualifier.
- A genuine cross-table reference to the table called `new` — schema-qualified
  (`main.new.v`), or a subquery whose FROM really selects from `"new"` — keeps
  behaving exactly as it does today: the rename rewrites it, and the drop refuses.
  This is the same scope-awareness `TableRenameOpts.rowImageContext` already
  documents, so the boundary is settled, not open.
- `old.` behaves identically to `new.` in all of the above.
- The table verbs (`drop table "new"`, `alter table "new" rename to …`) are already
  correct and must stay so — 41.10.4 §15 is the guard on that.

# Relationship to the other open guard work

Independent of `drop-column-guard-blind-to-star-reexposure` (sequenced 4.8), which
is about a *different* missing capability — a view's output column list, so a
`select *` in a chain stops hiding the column. That one makes the probe see more;
this one makes it see less. They touch `column-rename.ts` from opposite ends and
neither blocks the other.
