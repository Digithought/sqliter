# The refusal stops one hop short

`drop-guards-see-dependent-expressions-in-other-tables` taught `DROP TABLE`,
`DROP VIEW`, `DROP MATERIALIZED VIEW` and `ALTER TABLE … DROP COLUMN` to refuse
when a CHECK constraint, a column `DEFAULT` or a `GENERATED ALWAYS AS` body on
some other table reads the dropped object. That works when the expression names
the object itself. It does not when the expression names a **view** that reads
the object.

Verified in-session against the code as it stands after that ticket landed:

```sql
create table t (id integer primary key, v integer);
create view vv as select v from t;
create table x (id integer primary key, n integer,
                constraint ck check (n < (select max(v) from vv)));

drop table t;                 -- ACCEPTED
insert into x values (1, 1);  -- Table 't' not found in schema path: main
```

and the column verb has the identical hole:

```sql
alter table t drop column v;  -- ACCEPTED
insert into x values (1, 1);  -- Column not found: v
```

The outcome is exactly the one the guard exists to prevent — `x` is unwritable,
and the error names neither the object the user dropped nor the constraint that
broke. Inserting a view between the constraint and its target is not an exotic
shape; it is how anyone factors a shared subquery.

## Root cause, and why it is one site

`findColumnExpressionDependent` and `findTableExpressionDependent` in
`schema/expression-dependents.ts` ask *"does this stored expression mention this
object?"*. The question is *"can this stored expression reach this object?"* —
the same substitution `assertion-guards-follow-view-chains-and-schemas` is
making for the assertion guards, one layer up from the same walk.

That is why this ticket has a prereq rather than a design of its own. That
ticket creates `schema/object-dependency-closure.ts` with a
`reachableObjects(db, body, homeSchema)` breadth-first expansion over stored
view / materialized-view bodies, each walked under its own home-schema resolver,
with a visited set for termination. **The expression guards should consume that
closure, not grow a second one.** Two reachability definitions in the catalog is
how the guards start disagreeing about what "reaches" means — which is the
family of bug this whole 4.x sequence has been closing.

Scope-awareness must survive the widening in both directions, which is the risk
here: the one-hop probes already refuse to be fooled by a CTE or FROM alias that
merely shadows the dropped name (`41.10.4` §8) or by a like-named column on a
third table (`41.10.2` §21). A closure that collects names instead of resolving
them loses both, and turns a missed refusal into a false refusal.

## Expected behavior

Refused, `StatusCode.CONSTRAINT`, nothing applied:

- `drop table t` and `alter table t drop column v` when another table's CHECK /
  DEFAULT / generated body reads `t` (or `t.v`) through a view.
- The same through a chain of two or more views, and through a materialized
  view.
- `drop view vv` itself when a CHECK reads it — already refused today; must stay
  refused, and must also be refused when the CHECK reaches `vv` only through a
  further view.
- Cross-schema, both directions, matching what the direct probes already do.

Still allowed (the false-refusal shapes the widening must not break):

- A plain view over the dropped table with **no** constraint reading that view —
  the engine's stated asymmetry, pinned by `41.10.4` §5. The view breaks; the
  drop stands.
- A CTE or FROM alias that merely shadows the dropped name, anywhere in the
  chain.
- Another table's constraint over a like-named column of a *third* table.

The refusal message needs to name the path, not just the endpoints — a user told
that `ck` on `x` blocks `drop table t` will read `ck`'s body, find no mention of
`t`, and be stuck. Something of the shape *"CHECK constraint 'ck' on table 'x'
reaches it through view 'vv'"*.
