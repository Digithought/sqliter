## Why this is pre-existing

The ticket being worked (`bug-upsert-do-update-skips-constraint-checks`) adds UPDATE-shaped
row validation to the `on conflict ... do update` arm. The failure was isolated by disabling
each of that ticket's three new code paths in turn and re-running this file in store mode:

1. `upsertUpdateValidation` forced `undefined` in `emitDmlExecutor` (no validation runs) — still fails.
2. Plus the new `assertTransitiveRestrictsForParentMutation` call in `executeUpsertUpdate`
   short-circuited — still fails.
3. Plus `buildUpsertUpdateValidation` disabled in `buildInsertStmt` (the plan carries no
   validation at all, so `DmlExecutorNode.getChildren()` is byte-for-byte its pre-ticket
   shape) — **still fails, identically.**

With all three off, the only remaining delta is the Phase-1 extraction of the row-validation
algorithm from `runtime/emit/constraint-check.ts` into `runtime/row-constraints.ts` — a pure
code move that the whole memory suite and the other 2909 store-mode tests pass over unchanged.

Independently: `t_pk_up` has no CHECK constraints, no NOT NULL column with a DEFAULT, and no
foreign keys, so the validation the ticket adds is an **empty** set for this table — it emits
no evaluators and contributes no plan children here.

The failure itself is in the store/isolation write path (`StoreTable.encodeDataKey` receives
an `undefined` PK cell while flushing the overlay), not in anything the engine's DML executor
composes: the `undefined` appears for a row whose generated **stored PK** was relocated
(`k` recomputes 101 → 102) by the DO UPDATE arm.
