# Pre-existing test failure: store-mode IN-list over a TIMESPAN primary key

## Command

From repo root (also reproduced via `yarn test:store`):

```
cd packages/quereus && QUEREUS_TEST_STORE=true node test-runner.mjs --filter 15.1-semantic-ordering
```

## Failing test

- Suite: `SQL Logic Tests (Store Mode)` — `packages/quereus/test/logic.spec.ts`
- File/line: `packages/quereus/test/logic/15.1-semantic-ordering.sqllogic:134`

```

create table il (d timespan primary key);
insert into il values ('PT2H'), ('PT90M');
select d from il where d in ('PT120M', 'PT30M');
```

Store-mode plan for the failing query (from `--show-plan`):

```
Filter: WHERE d in ('PT120M', 'PT30M')
  SeqScan: SEQ SCAN il
  In: d IN (values)
```

## Why pre-existing

Reproduced identically on `main` at the same SHA (2b39ba4f) in a clean `git worktree`
(fresh install + build) with none of this ticket's changes present. It is the single
failing test in the full `yarn test:store` run both before and after this ticket's diff.

## Likely root cause (for triage)

The engine's `In` plan-node evaluation compares/serializes its operands without routing
a semantic-ordering logical type (TIMESPAN — `LogicalType.semanticOrdering`) through the
type's `compare`/`groupKey`, so `'PT2H' IN ('PT120M', …)` misses even though
`timespan('PT2H') = timespan('PT120M')` is true. Memory mode masks it: the planner turns
the IN over a memory-table PK into typed multi-seeks, so the `In` residual never runs
there. The store declines those seeks for semantic-ordering PK members (by design), which
is what exposes the residual path. Fix belongs in the engine's IN evaluation (make it
semantic-ordering-aware, mirroring the comparison operators fixed by
`duration-json-semantic-ordering-engine`), not in the store.
