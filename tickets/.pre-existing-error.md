# Pre-existing test failure: ANALYZE on an isolated table stops seeing its own overlay

## Command

From the repo root:

```
yarn test
```

Package: `@quereus/isolation` (`packages/quereus-isolation`). Reproduces on its own with:

```
cd packages/quereus-isolation && yarn test
```

## Failing test

`packages/quereus-isolation/test/isolation-layer.spec.ts:5269`

```
IsolationModule concurrency + latency forwarding
  accessPath merge-order: index named like the primary key, analyze, multi-table commit
    ANALYZE on an isolated table inside an open transaction with a dirty overlay succeeds
```

Error:

```
AssertionError: expected 2 to equal 3
+ expected - actual

-2
+3

at Context.<anonymous> (packages/quereus-isolation/test/isolation-layer.spec.ts:4518:87)
```

The assertion is `adb.schemaManager.findTable('t', 'main')?.statistics?.rowCount` — 2 committed
rows plus 1 uncommitted insert staged in the open transaction's overlay.

385 of 386 tests in that package pass.

## Why this is pre-existing

Broken at HEAD (`7471536d`, "tess: triage pre-existing test failure"), before any edit in this
ticket. That commit added statistics delegation to `IsolatedTable`
(`packages/quereus-isolation/src/isolated-table.ts:174-178`): the wrapper now exposes
`getStatistics` whenever the wrapped table implements it. `MemoryTable` does
(`packages/quereus/src/vtab/memory/table.ts:184`), and it reports the committed base layer only.

`collectTableStatistics` (`packages/quereus/src/runtime/emit/analyze.ts`) reads a present
`getStatistics` as a cheap real answer and skips the scan. Before the delegation existed the
isolated table had no `getStatistics`, so `ANALYZE` scanned — and the scan goes through the
overlay merge, which is what saw the uncommitted third row. The delegation's own doc comment
states the new behaviour deliberately ("Neither is overlay-aware… folding the delta in would
buy a difference no plan choice depends on"), so this is a genuine collision between that
decision and the behaviour this test pins, not an accident of wiring.

This ticket (`store-per-predicate-selectivity`) touches only
`packages/quereus-store/src/common/store-module-access-plan.ts`, three specs under
`packages/quereus-store/test/`, and two files under `docs/`. The failing test builds
`new IsolationModule({ underlying: new MemoryTableModule() })` and never loads the store
package at all.

## Note for triage

The two sides disagree about what `ANALYZE` inside a transaction means, so fixing it is a
decision, not just a wiring change:

- make `IsolatedTable.getStatistics` overlay-aware (costs a full overlay scan per call), or
- have it decline (return `undefined` / stay unwired) while an overlay is dirty, so `ANALYZE`
  falls back to the merged scan, or
- accept the new behaviour and re-pin the test on committed rows.

The `saveStatistics` half of the same delegation is independent and is exercised green by
`packages/quereus-store/test/stats-persistence.spec.ts`.
