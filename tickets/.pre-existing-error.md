# Pre-existing failure: `join-latency-cost.spec.ts` executes a prefetch-wrapped hash join under `QUEREUS_FORK_STRICT=1`

Surfaced while implementing `feat-index-nested-loop-batched-seeks`. Not caused by
that ticket — the failing plans contain no fan-out, only the pre-existing
`eager-prefetch-probe` wrap — and `yarn test` (non-strict) is green.

## Command

From the repo root:

```
QUEREUS_FORK_STRICT=1 node --import ./packages/quereus/register.mjs node_modules/mocha/bin/mocha.js "packages/quereus/test/optimizer/**/*.spec.ts"
```

(equivalently `yarn workspace @quereus/quereus test:fork-strict`, which is not part
of the default `yarn test`).

## Why pre-existing

The `chosenAlgo` helper in that spec **executes** (`drain`) a query whose plan,
for a high-latency right side, is `LimitOffset / Sort / Project / HashJoin /
EagerPrefetch(probe)` — the `eager-prefetch-probe` rule's wrap, which forks.
Executing a forking node under a Sort/Project trips the documented strict-harness
false positive (`createRowSlot` on the parent context while the prefetch fork is
live — see the guard comments in `test/optimizer/parallel-fanout.spec.ts` and
`docs/runtime-parallel.md` § Strict-fork interaction). The spec landed with
`feat-join-latency-cost-symmetry` (commits `c8f017036` / `319fb2d11`) without the
`forkExecTest` skip-under-strict convention the other parallel specs use, and the
rows-equality assertion is the only execution in it. The plans asserted on in
those two tests contain **no** `FanOutLookupJoin` (verified by printing
`query_plan` for the 45-row / hi_lat case at the current tree), so the batched
index-nested-loop work cannot be the cause.

Likely fix: in `join-latency-cost.spec.ts`, guard the `drain` inside `chosenAlgo`
(or the two tests) with the existing `forkExecTest` / `strictFork` convention, the
way `parallel-fanout.spec.ts` and `parallel-fanout-batched.spec.ts` do, keeping the
plan-shape assertions running under strict fork.
