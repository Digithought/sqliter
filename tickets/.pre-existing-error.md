# Pre-existing failures surfaced while implementing `isolation-alter-forward-column-shape`

Two distinct memory-module defects (both in `packages/quereus/src/vtab/memory/`, a
subsystem the ticket's diff — which touches only `packages/quereus-isolation` plus new
tests — never modifies). Both were surfaced by NEW coverage written for that ticket; no
previously-green test regressed. The new tests were scoped so the suite stays green
(details below), so these defects are currently **latent in the test suite** — the two
tightening points are marked with comments referencing this file.

## 1. RENAME COLUMN + savepoint loses the transaction's pending rows at COMMIT (memory module, no isolation involved)

Command that surfaced it: `cd packages/quereus && node test-runner.mjs --grep 41.8`
(memory leg of the new `test/logic/41.8-alter-savepoint-staged-rows.sqllogic`, before the
RENAME block was pulled out of the file).

Minimal repro against a plain memory table (no isolation layer, default module):

```sql
create table t (id integer primary key, v text);
begin;
insert into t values (1, 'a');
savepoint s;                              -- savepoint is required; rollback is NOT
alter table t rename column v to vv;
commit;
select id, vv from t;                     -- []  — pending row (1,'a') gone
```

Without the savepoint the row survives. `rollback to savepoint` is not needed — the mere
existence of a savepoint across the RENAME makes COMMIT drop the pending rows.

Why (pointer, not a full root-cause): `MemoryTableManager.renameColumn`
(`packages/quereus/src/vtab/memory/layer/manager.ts` ~2084) rewrites the base schema and
calls `baseLayer.handleColumnRename()`, but — unlike `addColumn` / `dropColumn`, which got
the two-phase `prepareReshapeOnOpenLayers` / `installReshapeOnOpenLayers` treatment in
`bug-memory-add-column-loses-pending-rows` — it never touches the open transaction
layers, so the commit-time rebase of a layer with a savepoint snapshot loses the rows.

Believed pre-existing because the repro touches only `packages/quereus` memory-module
code, none of which the ticket's diff modifies.

Where the suite is deliberately not asserting this: the RENAME block was removed from
`packages/quereus/test/logic/41.8-alter-savepoint-staged-rows.sqllogic` (a NOTE comment
in the file marks the spot; re-add the block when fixing this).

## 2. `rollback to savepoint` reverts an ALTERed memory table's committed rows to the PRE-alter layout (reachable through the isolation wrapper)

Command that surfaced it: `yarn workspace @quereus/isolation run test`
(new savepoint cases in `packages/quereus-isolation/test/isolation-layer.spec.ts`,
before they were scoped down).

Repro (isolation wrapper over the memory module; the overlay write before the savepoint
matters — it lazily registers the underlying connection, which replays `begin` + the
savepoint onto the underlying table):

```sql
create table t (id integer primary key, v text, x integer) using isolated;
insert into t values (0, 'base', 100);    -- committed row
begin;
insert into t values (1, 'a', 10);        -- staged in the overlay; registers underlying txn
savepoint s;
alter table t drop column v;
rollback to savepoint s;
commit;
select * from t;                          -- committed row is back to 3-wide (0,'base',100)
                                          -- in a 2-column table; permanently corrupted
```

The isolation layer forwards `savepoint`/`rollbackTo` to the underlying `MemoryTable`.
That connection's savepoint snapshot pre-dates the ALTER and pins the pre-reshape
primary tree; `rollback to savepoint` restores it wholesale, undoing the committed-row
reshape `dropColumnFromBase` / `addColumnToBase` performed (the schema stays post-alter,
so rows and schema disagree — the same failure ADD COLUMN shows as the backfilled value
vanishing). Notably the memory module handles this correctly when the SAME connection
also owns staged rows (the native leg of 41.8 passes); the corruption needs a connection
whose open transaction has no own writes on that table — exactly what the isolation
wrapper's forwarded begin/savepoint produces.

Believed pre-existing because the corrupting flow (forwarded begin/savepoint,
`underlying.alterTable`, forwarded rollbackTo) is byte-identical before and after the
ticket's diff — the old overlay-rebuild path never wrote to the underlying between those
steps either. Verified the no-overlay and no-rollback variants behave correctly, so the
trigger is specifically the pre-ALTER savepoint snapshot being restored.

Where the suite is deliberately not asserting this
(`packages/quereus-isolation/test/isolation-layer.spec.ts`, comments reference this
file):
- "DROP COLUMN (middle) keeps pre-savepoint rows..." runs against an EMPTY underlying
  (no committed row) — restore the committed row when fixing.
- "a staged tombstone survives an ADD COLUMN under a savepoint..." asserts `id, v` but
  not the backfilled `w` — tighten to include `w` when fixing.
