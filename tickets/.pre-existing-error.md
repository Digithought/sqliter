# Pre-existing failure: memory-NATIVE metadata-only ALTER across a savepoint loses the transaction's staged rows

Surfaced while extending `packages/quereus/test/logic/41.8-alter-savepoint-staged-rows.sqllogic`
for ticket `isolation-alter-forward-constraints-and-retype`. Two blocks fail on the **memory-native
leg** (no isolation wrapper involved — the staged rows live in the memory module's own transaction
layers), so they were left out of the shared sqllogic file with a NOTE above the `t5b` section, and
the savepoint coverage for those shapes lives in
`packages/quereus-isolation/test/isolation-layer.spec.ts`
("constraint & retype ALTER inside a transaction preserves the overlay savepoint chain"), where the
isolation leg passes.

## Command

```
cd packages/quereus && node test-runner.mjs --grep 41.8
```

(with the failing blocks present in `41.8-alter-savepoint-staged-rows.sqllogic`; they are currently
excluded so the file stays green — re-add either block below to reproduce.)

## Failing shape A — `alter column … set not null` (no backfill needed)

```sql
create table t5 (id integer primary key, v text null);
begin;
insert into t5 values (1, 'a');
savepoint s;
insert into t5 values (2, 'b');
alter table t5 alter column v set not null;
insert into t5 values (3, 'c');
rollback to savepoint s;
select id, v from t5 order by id;   -- expected [{"id":1,"v":"a"}]
```

Observed: `Row count mismatch. Expected 1, got 0` — the rollback to `s` discards **every** staged
row, including row 1 staged before the savepoint.

## Failing shape B — `rename constraint` under a savepoint

```sql
create table t10 (id integer primary key, v text, constraint u_old unique (v));
begin;
insert into t10 values (1, 'a');
savepoint s;
insert into t10 values (2, 'b');
alter table t10 rename constraint u_old to u_new;
rollback to savepoint s;
commit;
select id, v from t10 order by id;  -- expected [{"id":1,"v":"a"}]
```

Observed: `Row count mismatch. Expected 1, got 0`.

Notable non-failures that bound the defect: the same shape with `set default` (kept in the file as
`t7`) passes, as does `rename constraint` with no savepoint across it (kept as `t10`), and the
backfilling `set not null` flavor (`t5b`, which routes through the value-conversion path).

## Suspected vicinity (not verified)

`packages/quereus/src/vtab/memory/layer/manager.ts`: the metadata-only `alterColumn` outcomes
deliberately skip `adoptSchemaOnOpenLayers` (see the NOTE after the `structuresRekeyed` propagation
block, ~line 2572: "the remaining changes … fall through with the open layers still holding their
creation-time schema — verified not observable today"), and `renameConstraint` never calls it at
all (unlike `dropConstraint`, which does). With an eager savepoint snapshot across the ALTER that
fall-through appears to be observable after all: the `rollback to savepoint` restores a layer whose
frozen schema no longer matches, and the transaction's own staged rows are dropped.

## Why pre-existing

This ticket's diff touches `packages/quereus-isolation/src/isolation-module.ts`, the test files,
and one line in `packages/quereus/src/vtab/memory/table.ts` (`MemoryTable.alterSchema` now passes
`setCollation` through to `manager.alterColumn`). The failing leg runs memory-native through
**module-level** `MemoryTableModule.alterTable` (`vtab/memory/module.ts`), which already passed
`setCollation` and is untouched — nothing in this diff is on the failing path. The failure is in
the memory layer manager's savepoint/schema-adoption machinery, which this ticket never modifies.
Same family as the two memory-native savepoint reports the `isolation-alter-forward-column-shape`
ticket filed (both since resolved), but a distinct arm: metadata-only ALTER COLUMN / RENAME
CONSTRAINT rather than column-shape changes.
