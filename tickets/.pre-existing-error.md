# Pre-existing test failures observed during `bug-filter-row-estimate-lost-when-predicate-rewritten`

Command (from repo root):

```
yarn workspace @quereus/quereus run test --no-bail
```

(`test-runner.mjs` hardcodes `--bail`; `--no-bail` appended after it wins, which is
how both failures were seen in one run. The default bailing run stops at the first.)

Result: **8322 passing, 13 pending, 2 failing.**

## 1) `rulePredicateInferenceEquivalence` → "Inferred predicate is pushed to the vtab access leaf when supported"

Path: `packages/quereus/test/optimizer/rule-predicate-inference-equivalence.spec.ts:232`

```
expected more INDEXSEEKs with rule enabled (with=2, without=2)
  at Context.<anonymous> (packages\quereus\test\optimizer\rule-predicate-inference-equivalence.spec.ts:232:11)
```

The test asserts a *delta*: `SELECT t.v, u.v FROM t JOIN u ON t.k = u.k WHERE t.k = 5`
should produce strictly more `INDEXSEEK`s with `predicate-inference-equivalence` enabled
than with it disabled. Today both counts are 2 — with the rule disabled, something else
already seeks `u` on its primary key, so the delta the test measures is gone.

Why pre-existing: this ticket touched only `rule-filter-selectivity`'s registration and
comments/docs. A throwaway probe re-planned that exact query with `filter-selectivity`
and `filter-selectivity-restamp` disabled in every combination; the seek count was 2 in
all six combinations, and the access ops were byte-identical
(`INDEX SEEK t USING primary` + `INDEX SEEK u USING primary`). The failure is therefore
independent of filter selectivity. It also reproduces in isolation
(`node test-runner.mjs --grep "Inferred predicate is pushed"`), so it is not cross-spec
tuning pollution. Most likely a newer access-path/join rule now derives the `u`-side seek
from the equi-join itself, which makes the test's delta assertion stale rather than the
optimizer wrong — but that has not been confirmed and should be checked, not assumed.

## 2) `Plan shape: scalar-aggregate subquery decorrelation (filter site)` → "rewrites a HAVING comparison (Filter over Aggregate) into a grouped left join"

Path: `packages/quereus/test/plan/scalar-agg-decorrelation.spec.ts:393`

```
expected hash/merge join in [BLOCK, PROJECT, FILTER, JOIN, HASHAGGREGATE, INDEXSCAN,
TABLEREFERENCE, ..., CACHE, HASHAGGREGATE, INDEXSCAN, ...]
- false
+ true
```

Query:
`SELECT ord.k, sum(ord.amt) AS s FROM ord GROUP BY ord.k HAVING sum(ord.amt) > (SELECT min(lim.cap) FROM lim WHERE lim.gk = ord.k)`

The decorrelation itself still happens (no `ScalarSubquery` in the plan; a grouped
`HASHAGGREGATE` sits under the join). Only the *physical* join choice regressed: the plan
carries a logical `JOIN`, not `HASHJOIN`/`MERGEJOIN`, so `join-physical-selection` did not
convert it.

Why pre-existing: the same throwaway probe re-planned this query with
`filter-selectivity-restamp` disabled, and then with **both** `filter-selectivity` and
`filter-selectivity-restamp` disabled. The op list was character-for-character identical in
all three cases, so the unconverted join is not caused by the selectivity stamp this ticket
adds or by the stamp it re-derives.

Neither failure is listed in `tickets/.pre-existing-known.md`.
