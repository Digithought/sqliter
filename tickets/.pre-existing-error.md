## Why this is pre-existing, and why it is a flake rather than a hard failure

- It is a wall-clock timing assertion. The test hands `sizeBatch` a fake
  `costing(FAST.minSampleMs / 8)` function and asserts the batch grew past 1.
  Under concurrent load the very first measured call can overshoot
  `minSampleMs`, so `sizeBatch` legitimately leaves the batch at 1 and the
  assertion fails. The other machine was busy at the time (ticket runner).
- It exercises `bench/lib/calibrate.mjs`, a benchmark batch-sizing helper. The
  ticket being worked (`bug-no-group-by-aggregate-skips-subquery-coverage-check`)
  touches only `packages/quereus/src/planner/building/select.ts`,
  `packages/quereus/src/planner/building/select-aggregates.ts`, two
  `test/logic/*.sqllogic` files and `docs/sql-select.md`. No shared code path.
- Re-run in isolation: `45 passing`, green.
- Full suite re-run immediately after: `10191 passing, 25 pending, 0 failing`.

So there is no reproducible failure at this SHA — the signal is that the
assertion is load-sensitive, not that `sizeBatch` is broken. Nothing was skipped
or loosened.
