# `41.2.3` § 12 needs standalone index DDL; the other eleven sections do not

## Background

`test/logic/*.sqllogic` is a **shared corpus**: sibling projects run the same files against their
own storage engine. A file whose *subject* is a feature some backend deliberately does not
implement declares that with a `-- requires-capability:` line, and a backend lacking the feature
skips the file. There is exactly one token today, `standalone-index-ddl`, meaning `create index` /
`create unique index` / `drop index` written as their own statements. The directive is **whole
file** — there is no per-section form — and `test/README.md` § "`-- requires-capability:` directive"
tells authors to split the file when only part of it needs the capability.

`41.2.3-alter-column-set-not-null-pk-backfill.sqllogic` declares no capability, but its § 12
("A SECONDARY INDEX over an untouched column still resolves after the re-key") opens at line 289
with a standalone `create index`. So on a backend without standalone index DDL the file has only
two outcomes, both lossy: run it and die at line 289 after §§ 1-11 pass, or annotate the file and
lose §§ 1-11 — eleven sections of primary-key-backfill semantics that have nothing to do with
secondary indexes.

The sibling file `43.3-nullable-primary-key.sqllogic` § 12 faced the same choice and resolved it by
reaching a secondary index through a **table-level `unique`** instead, with prose saying exactly
why. That is the precedent to follow here.

## What the investigation established

Measured in this repo, not assumed.

**A `unique` column really does produce a secondary index, on both backends.** `query_plan()` for
`select x, y from t_bf13 where y = 1` under three table shapes:

| § 12 table shape                     | plan                                    |
| ------------------------------------ | --------------------------------------- |
| `create index ix_bf13 on t_bf13 (y)` | `INDEX SEEK t_bf13 USING ix_bf13`       |
| `y integer null unique`              | `INDEX SEEK t_bf13 USING _uc_y`         |
| neither                              | `INDEX SCAN … USING _primary_` + FILTER |

The third row is the failure mode to avoid — with no index at all the section is vacuous, since a
full scan reads the row values directly and never consults a stale index. The `unique` form is not
vacuous: it is a genuine index seek.

**The `unique` form does not steal the primary key.** `findPKDefinition`
(`packages/quereus/src/schema/table.ts:1217`) derives the key from a declared `PRIMARY KEY` only — a
column-level one or a table-level constraint. With neither present it synthesizes the all-columns
key. A `unique` constraint is never consulted. So `t_bf13` keeps its `(x, y)` key and the
`set not null` backfill still moves key values, which is the whole point of § 12.

**Both index shapes ride the same re-key code.** Store: `store-module-alter-column.ts:273` rebuilds
indexes via `rebuildSecondaryIndexes(…, withImplicitUniqueIndexes(updatedSchema), …)` — the
materialized set that includes the hidden `_uc_*` structure a plain `unique` gets. Memory:
`convertColumn` "installs the new schema and rebuilds every one of the layer's secondary indexes
from it" (`vtab/memory/layer/manager.ts:2717`). Both legs of § 12's stated subject — the committed
base rebuild and the open-layer rebuild — are exercised either way.

**The rewritten section passes on both backends.** § 12's statement sequence with
`y integer null unique` in place of the `create index` was run as a throwaway `.sqllogic` file
through `logic.spec.ts` in default mode and with `QUEREUS_TEST_STORE=true`; both passed, asserting
the same expected rows the section asserts today. The throwaway file was deleted.

## Shape of the fix

Two arms. The first is the one that matters; the second preserves what exists today.

**Arm 1 — rewrite § 12 in place so it runs everywhere.** Change lines 288-289 from

```sql
create table t_bf13 (x integer null default 7, y integer null);
create index ix_bf13 on t_bf13 (y);
```

to a single `create table t_bf13 (x integer null default 7, y integer null unique);`, and add a
short prose line above it in the style of `43.3` § 12 saying that a table-level `unique` is used
deliberately so the file needs no `-- requires-capability: standalone-index-ddl` and runs on every
backend. The rest of § 12 (lines 290-307) is unchanged. `41.2.3` still declares no directive.

Watch the near-miss guard: `logic-capabilities.ts`'s `NEAR_MISS_RE` hard-errors any comment line
that *opens* with something resembling the directive name. The prose must keep the directive name
backtick-quoted mid-sentence, exactly as `43.3` § 12 and the other carve-out headers do — a comment
line starting with the directive name fails the file.

**Arm 2 — carve the non-unique index variant into a sibling.** A plain `create index` is a
different schema shape from the hidden `_uc_*` a `unique` builds (non-unique, always PK-suffixed),
so keeping a case for it costs one small file and loses nothing. New file
`41.2.3.1-alter-column-set-not-null-pk-backfill-secondary-index.sqllogic` carrying
`-- requires-capability: standalone-index-ddl` and the original § 12 statements verbatim, with a
header explaining it was carved out of `41.2.3` — copy the header shape from
`06.9.1.1-json-coerce-once-index.sqllogic` or `10.1.2.1-add-constraint-in-transaction.sqllogic`,
both of which do exactly this.

No harness bookkeeping is needed for either arm:

- `logic.spec.ts`'s `MEMORY_ONLY_FILES` gets no entry — both files run on both backends.
- `logic-capabilities.spec.ts`'s `subjectFiles` list gets no entry either. That list names files
  whose *subject* is index DDL; the new sibling's subject is a primary-key re-key, and the existing
  carve-outs (`06.9.1.1`, `10.1.2.1`) are likewise absent from it.
- `test/README.md` needs no edit — it already prescribes this split.
