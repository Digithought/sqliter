# Make the one walk reach every sub-expression it currently skips

## Background

`debt-one-schema-expression-scope-walker` merged two hand-written traversals into one
(`schema/expr-scope/walk.ts`). It deliberately preserved every gap both copies had.
This ticket closes those gaps. Because there is now one walk, each fix lands once and
both analyses — the CHECK self-qualifier rewrite and the generated-column reference
collector — inherit it.

Four gaps, plus one scoping fault the merge exposed. All are dormant today: none is
reachable by anything a person is likely to write in a `check (...)` or
`generated always as (...)` body. They are worth closing anyway because a reference
the walk does not see is a reference the generated-column analysis records **no
dependency edge** for — and a missing edge computes a generated column before the
column it reads and silently writes NULL. That is the unsafe half of the analysis's
deliberate asymmetry (see the header comment in `generated-column-refs.ts`).

## The new frame kind: `sealed`

Two of the four gaps (`with inverse (...)`, `with defaults (...)`) are expressions
that do not resolve in the surrounding body's scope **at all** — they are view
write-through metadata, evaluated against the written view row, where `new.<output
column>` is the naming environment. Descending into them under the walk's normal
rules is worse than skipping them: `new.a` would hit `classifyQualified`'s
`qualifier === 'new'` arm and come back `'own'`, claiming a reference to the row of
the table being defined that is not there — which then raises a bogus
"Column 'a' … not found" or a bogus cycle.

The existing `opaqueScopeFrame()` does not fix that, because `classifyQualified`
checks the `'new'` / owning-table spellings *after* the frame loop, and opaque frames
bind nothing.

So add a third frame kind to `expr-scope/frame.ts`:

```ts
export interface ScopeFrame {
	// … existing fields …
	/**
	 * Marks a subtree whose names resolve in a naming environment this walk does not
	 * model at all (view write-through metadata: a result column's `with inverse`
	 * clause, a select's trailing `with defaults` clause). NOTHING below a sealed
	 * frame can reach the seed — not even the `new.` / owning-table spellings that
	 * an opaque frame still lets through. Implies `hasOpaque`.
	 */
	sealed: boolean;
}

/** A frame nothing below can see past. */
export function sealedScopeFrame(): ScopeFrame;

/** Whether any frame above the seed is sealed. */
export function hasSealedFrame(stack: ReadonlyArray<ScopeFrame>): boolean;
```

`sealedScopeFrame()` sets both `sealed` and `hasOpaque`. `emptyScopeFrame()` and
`opaqueScopeFrame()` set `sealed: false`.

`hasSealedFrame` is a flat scan of `stack[1..]` rather than a position-relative check,
and that is correct precisely because a sealed frame blocks *unconditionally*: it is
only ever on the stack while the walk is inside such a subtree.

Each analysis then honours it in one place:

- `stripColumnQualifier` — `if (hasSealedFrame(stack)) return;` at the top. No rewrite
  inside write-through metadata.
- `classifyUnqualified` and `classifyQualified` — `if (hasSealedFrame(stack)) return
  'unknown';` at the top, **before** any seed / `'new'` matching. `'unknown'` is the
  safe answer: the consumers in `table.ts` record a dependency edge for a known column
  name and raise nothing for an unknown one.

## The five changes

### 1. Window frame bound expressions

`WindowDefinition.frame` is a `WindowFrame` whose `start` / `end` bounds may be
`{ type: 'preceding' | 'following', value: Expression }`. Neither copy ever looked at
`value`, so a reference appearing *only* in `rows between <expr> preceding and …` is
invisible. Descend both bounds inside `visitWindowDefinition`, in the same frame as
`partitionBy` / `orderBy` — a frame bound is an ordinary correlated expression, not a
different naming environment, so no barrier and no seal.

Note the shapes: `WindowFrame` and `WindowFrameBound` do **not** extend `AstNode`
(`WindowFrame.type` is `'rows' | 'range'`, not a node kind), so they cannot go through
the walk's `switch` — handle them structurally inside `visitWindowDefinition` and
recurse into `value` only.

`parser/visitor.ts`'s `traverseAst` carries the same gap as a `// TODO` at its
`windowDefinition` arm. **Leave that TODO alone** — `traverseAst` has other consumers
(`schema/manager.ts`) and widening it is not this ticket's blast radius. Update the
`NOTE:` cross-reference the prereq ticket added so it says the scope walk covers frame
bounds and `traverseAst` still does not.

### 2. A result column's `with inverse (...)` clause

`ResultColumnExpr.inverse` is `ReadonlyArray<{ column, expr }>`. Visit each `expr`
under a `sealedScopeFrame()`, from the shared `visitResultColumns` helper so both the
select arm and DML `returning` (change 4) inherit it.

### 3. A select's trailing `with defaults (...)` clause

`SelectStmt.defaults` is `ReadonlyArray<{ column, expr }>`. Visit each `expr` under a
`sealedScopeFrame()`, inside the select's FROM frame push (position does not matter
semantically — the seal blocks everything — but keep it next to the result-column
visit so the two write-through clauses read together).

### 4. The DML sub-parts the walk skips

Inside the single `opaqueScopeFrame()` each DML arm already pushes, add the sub-parts
that carry expressions and are currently dropped:

- `insert`: `returning` result columns, `upsertClauses[].assignments[].value`,
  `upsertClauses[].where`, `contextValues[].value`
- `update`: `returning`, `contextValues[].value`
- `delete`: `returning`, `contextValues[].value`

Still **not** descended, and still listed in the walk's "deliberately not descended"
comment: `stmt.table` on any DML (an object name, not a column reference).

**This is a real widening, and it can turn accepted DDL into an error.** Everything
under the opaque frame classifies `'unknown'`, and `table.ts`'s
`validateAddColumnGeneratedRefs` raises `Cyclic dependency in generated columns` for
*any* binding — including `'unknown'` — whose name equals the column being added
(table.ts:1605). So `alter table t add column g generated always as (<body naming g
only inside an inner DML's returning list>)` starts erroring. That is the correct
answer (the name really is in the body, and the emitter's own re-analysis would reach
the same conclusion once it saw the reference), and reaching it requires DML written
inside a generated expression. Call it out in the review handoff.

### 5. Compound legs must not inherit the leading leg's FROM frame

Both original copies visited `stmt.union` and `stmt.compound.select` *inside* the
`withScopeFrame(fromFrame, …)` push, so a compound's second leg is analysed with the
first leg's `from` sources on the stack. Each leg is a self-contained relation that
builds its own frame, so this is wrong in a way that matters:

- For the collector: a bare name in the second leg that should fall through to the
  seed can be captured by the *first* leg's source instead and come back `'foreign'`
  — no dependency edge, so the generated column may compute before the column it
  reads and write NULL.
- For the strip: an extra frame only ever blocks a rewrite, so the failure mode is a
  reference left qualified and a resolution error — noisy, not silent.

Move the `union` / `compound.select` visits out of the FROM-frame push but keep them
**inside** the `withFrame` push: a leading `with` clause scopes over the whole
compound, a `from` clause does not.

Leave `orderBy` / `limit` / `offset` where they are (inside the FROM frame) even
though on a compound they bind to the whole compound rather than the leading leg.
Record that as a `NOTE:` at the site — it is conditional, not wrong today, and
untangling it needs the AST to distinguish leg-level from compound-level clauses,
which it does not.

## Edge cases & interactions

- **`new.` under a seal.** The whole point: `new.a` inside `with inverse (...)` must
  come back `'unknown'`, never `'own'`. Pin it directly in the unit spec.
- **Seal nested inside a barrier and vice versa.** A `with inverse` clause inside a
  CTE body already sits under an opaque frame; pushing a sealed frame on top must not
  disturb the barrier, and `hasSealedFrame` must still fire. Frames stack, never
  replace.
- **Seal must not leak upward.** After the sealed subtree is popped, a sibling
  reference in the same result-column list must classify normally. The `try/finally`
  in `withScopeFrame` already guarantees the pop; assert it anyway with a spec case
  that has a ref before and after an `inverse` clause.
- **`opaqueScopeFrame()` callers unaffected.** Adding `sealed: false` must not change
  any existing classification. `hasOpaque` semantics stay exactly as they are.
- **Frame bounds that are literals.** `rows between 1 preceding and current row` —
  the common case — must produce no records at all (a `literal` node is a terminal).
  Guard against accidentally recording something for `currentRow` /
  `unboundedPreceding` / `unboundedFollowing`, which carry no `value` field.
- **`end: null`.** `WindowFrame.end` is `WindowFrameBound | null`, not `undefined` —
  a `?.` guard on it is not enough if the code destructures; handle the explicit null.
- **DML `returning` carrying its own `with inverse`.** Route `returning` through the
  same `visitResultColumns` helper so change 2 applies there too.
- **Strip still mutates in place.** Every subtree this ticket newly reaches is either
  sealed (no rewrite) or opaque (no rewrite) — except window frame bounds, which the
  strip *will* now rewrite. That is intended and matches how it already treats
  `partition by` / `order by`. `test/schema/clone-expr-isolation.spec.ts` must stay
  green.
- **Compound-leg move and the strip.** Removing a frame makes the strip rewrite
  *more*. Confirm no guard-rail test asserts a compound inside a CHECK or generated
  body relying on the old blocking. If one does, stop — that is a signal the move is
  wrong, not a test to loosen.

## Tests

Extend `packages/quereus/test/schema/expr-scope-walk.spec.ts` (created by the prereq
ticket) — the walk-level spec is where these belong, since both analyses inherit from
it. Expected records, as `{ shape, name, qualifier, sealed, opaque }`:

- `sum(x) over (rows between y preceding and current row)` → records for both `x` and
  `y`, neither sealed nor opaque.
- `count(*) over (rows between unbounded preceding and current row)` → no record from
  the frame at all.
- `(select a with inverse (b = new.a) from other)` → the `new.a` record is **sealed**;
  the projected `a` record is not.
- `(select a from other with defaults (c = d))` → the `d` record is sealed, the `a`
  record is not.
- `exists (insert into other values (1) returning k)` → the `k` record is reached and
  opaque (change 4).
- `(select a from s1 union select b from s2)` → the `b` record's stack contains
  `s2`'s frame and **not** `s1`'s (change 5).

Add sqllogic coverage for the one change with a user-visible consequence — the
compound-leg fix — in `packages/quereus/test/logic/41-generated-column-scope.sqllogic`
(it already owns this subject and its header prose describes exactly this analysis):
a generated column whose body is a compound whose *second* leg names an own column
that the *first* leg's source also exposes. Assert the computed value is right, which
it can only be if the dependency edge was recorded.

The other three changes have no clean SQL-level assertion that is not itself
contrived; the walk-level spec is the honest place for them. Say so in the review
handoff rather than inventing a sqllogic case that only exercises an error message.
