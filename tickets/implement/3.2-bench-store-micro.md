# Why

`bench-store-workloads` measures whole queries against the store. That is the right top-level
signal and a poor diagnostic: a full scan blends key decoding, iteration, row deserialization
and the isolation overlay into one number, so a regression in any one of them shows up as "the
scan got slower" with no way to tell which.

These are the paths that run per row, per index, per commit - the ones where a per-operation
cost that should have been per-batch can hide.

# Architecture

A new suite, `bench/suites/store.bench.mjs`. It is a store-only suite: unlike `execution` and
`mutation` it has no memory-backend reading, because these benchmarks call store code
directly. It therefore does **not** use the backend-dimension expansion; its names are bare
and carry no `@` suffix, and the docs must say why so the asymmetry does not read as an
oversight.

Where a benchmark can reach the code under test directly (key building, encoding), it should -
that is what makes it a micro-benchmark. Where it cannot without white-boxing, drive it through
a `Database` and report round trips, which is the honest measurement anyway.

## Key encoding and decoding

`encodeValue`, `encodeCompositeKey`, `decodeCompositeKey`, `buildDataKey`, `buildIndexKey` run
per row per index. Cover the cases the correctness suite already treats as hazardous, because
those are where a fast path can be lost silently:

- plain integer and plain text keys (the baseline),
- astral-plane text - surrogate pairs take the surrogate-aware slow path, the same distinction
  `execution/order-by-text-unicode-10k` exists to price at the comparator level,
- JSON keys,
- a collation-affected key (`NOCASE`), which routes through a key normalizer,
- a descending key,
- a composite key of several columns.

These are microsecond-scale, so calibration will batch them; each `fn` must be repeatable
back-to-back and must assert something about its output (a byte length, a round-trip equality)
so a builder that starts returning empty does not read as an improvement.

Round-trip equality (`decodeCompositeKey(encodeCompositeKey(v)) === v`) is worth asserting
inside these benchmarks even though it is a correctness property: it costs nothing at this
scale and it is the assertion that stops the benchmark from measuring a broken encoder.

## Scan, seek, and batched row resolution

Driven through a `Database` on the `store-mem` backend, reported in round trips as well as
time:

- sequential iterate throughput over a populated table,
- a point read on the primary key,
- a multi-key seek (`where pk in (...)`) at a few key counts,
- **the batched row resolution behind a secondary index** - the path
  `StoreTableScan.resolveRowBatch` pages at `ROW_RESOLUTION_BATCH` (256). Choose match-set
  sizes that straddle that boundary (well under 256, exactly 256, and a few multiples of it),
  because the interesting failure is a batch that stops batching: the round-trip count would
  jump from `ceil(n/256)` to `n` while the wall-clock on an in-memory provider barely moves.
  The `getManyCalls` count is what catches it, which is why this suite exists.

State the expected round-trip counts in comments next to each size. A benchmark whose expected
count is written down is a benchmark whose regression is readable without a baseline.

## Transaction commit

`TransactionCoordinator` batches queued operations into one atomic write. Queue N operations
and commit, across a range of N (say 1, 10, 100, 1000, 10000). The shape of round-trips-versus-N
is the measurement: flat-per-commit is correct, linear-in-N means a per-operation cost that
should have been per-batch. Report both the time and the counts; the counts are what carry
across machines.

## Index build

Building a secondary index over an existing table (`create index` on a populated table)
streams through `buildIndexEntries`. One benchmark at one table size, reported in round trips.
This is the workload that most needs the erasing `deleteIndexStore` the previous ticket
specified - a repeatable `fn` here creates and drops the index each call, and without erase the
second call reads the first call's entries back.

## Catalog rehydration

Reopening a database with a non-trivial schema: build a schema over a store-backed `Database`,
close it, then open a fresh `Database` over the **same provider instance** and measure the cost
of rebuilding the schema from `__catalog__`. Reported in round trips against the catalog store,
which is the count that would catch a rehydration that reads per-table instead of scanning
once.

The schema should be non-trivial in the way a real one is - tens of tables, some with secondary
indexes, some views - rather than one wide table. `bench/apply-schema-unchanged.mjs` already
contains a 54-table / 14-view declaration generator; reuse its shape rather than inventing a
second one.

## `apply-schema-unchanged.mjs` stays ad hoc - decided

The upstream plan asked whether to fold it into the suite. **It stays where it is**, for a
reason that should be recorded at the file rather than re-litigated:

It is not an end-to-end benchmark. It decomposes a no-op `apply schema` into the internal
functions the fast path removed (`computeSchemaDiff`, `generateMigrationPlan`), added
(`renderCatalogForComparison`, an exact string compare) and still pays
(`collectSchemaCatalog`), and it deliberately poisons the applied-state snapshot between runs
to measure the pre-fast-path shape warm and in-process. The bench framework measures one `fn`
per benchmark and cannot express a decomposition; forcing it in would keep one number and lose
the five that make it useful. Its figures are quoted in `docs/schema.md` as a one-off
measurement, not as a tracked series.

The catalog-rehydration benchmark above is **not** a replacement - it measures store round
trips on reopen, a different question.

Record this as a `NOTE:` at the top of `apply-schema-unchanged.mjs` (it already says "NOT part
of the bench suite"; this says *why*, so the question stops recurring) and one line in
`docs/benchmarking.md`. Giving the applied-state fast path a standing ratio-guarded benchmark
is real work and is parked separately as `feat-bench-apply-schema-fastpath-guard` (backlog).

# Edge cases & interactions

- **Micro-benchmarks reaching into `@quereus/store` internals bind this suite to those
  exports.** `encodeCompositeKey`, `buildIndexKey`, `ROW_RESOLUTION_BATCH` and friends are all
  public exports of `@quereus/store` today; use only public exports, so the suite breaks at a
  deliberate API change rather than at an internal refactor.
- **`ROW_RESOLUTION_BATCH` is a constant that may change.** Import it rather than writing 256,
  and derive the expected round-trip counts from it, so a change to the constant moves the
  expectation with it instead of turning every sizing comment into a lie.
- **Batching hides per-call setup.** Calibration times several consecutive `fn` calls as one
  sample for sub-millisecond work, so an `fn` that allocates a large fixture per call measures
  the allocation. Build fixtures in `setup`.
- **The commit benchmark at N=10000 is not repeatable back-to-back for free** - it grows the
  store. Either reset inside `fn` (and accept that the reset is in the number, stated in a
  comment) or pin it out of calibration with the reason written down. Do not leave a benchmark
  whose cost climbs across its own samples.
- **Index build and drop must actually erase.** If `deleteIndexStore` is a no-op, the second
  `fn` call builds an index over a store that already has entries and the benchmark measures
  something else entirely. Assert the entry count after the drop inside the benchmark.
- **Catalog rehydration needs the same provider, a new `Database`.** Reusing the `Database`
  measures nothing; building a new provider measures an empty catalog. Assert the rehydrated
  schema has the expected table count, or the benchmark can pass while reading nothing.
- **Wall-clock budget.** This suite adds a dozen-plus benchmarks to a run that is currently
  ~35 s. Measure and report the added time. If it is large, the lever is
  `CALIBRATION.targetTotalMs` (which shortens every benchmark evenly), not silently shrinking
  these workloads.

# Tests

- Every benchmark asserts its own result, as `docs/benchmarking.md` requires - a byte length, a
  row count, a round-trip equality, an entry count after a drop.
- Two consecutive runs produce byte-identical counter blocks for this suite. That is the
  acceptance criterion; identical timings is not.
- The stated expected round-trip counts hold: `ceil(n / ROW_RESOLUTION_BATCH)` batched reads
  for a match set of n, and a commit round-trip count that does not grow with the queued
  operation count.
