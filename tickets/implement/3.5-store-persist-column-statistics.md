# What is wrong today

`ANALYZE` scans a table, computes per-column distinct counts, null counts, min/max and
histograms, and writes them onto `TableSchema.statistics`
(`packages/quereus/src/runtime/emit/analyze.ts`). That object lives only in the running
`SchemaManager`. Close the database and reopen it and every one of those numbers is gone —
even though the store already persists the table's ROW COUNT for exactly this reason (a
`TableStats` record per table in the unified `__stats__` store, keyed by `schema.table`).

The consequence, once `store-per-predicate-selectivity` lands: a persistent database plans
well for as long as the process lives and reverts to fixed-fraction guesses on the next open,
with no way for a user to tell which state they are in short of re-running `ANALYZE`.

# Design

## The write path: a new optional module hook

Statistics collection stays where it is; only the *saving* is new.

```ts
// packages/quereus/src/vtab/table.ts, alongside getStatistics
/**
 * Persist statistics the engine just collected, so a later open can read them back
 * without re-scanning. Optional; a module that cannot store them simply omits it.
 * ANALYZE calls this after it has written the statistics onto the schema.
 */
saveStatistics?(stats: TableStatistics): Promise<void>;
```

`emitAnalyze` calls it for each table right after `schema.addTable(updatedTableSchema)`. It
must be **advisory**: a throw is logged and swallowed, exactly as the surrounding per-table
`try` already treats an unreadable table. `ANALYZE` succeeding with statistics in memory but
not on disk is strictly better than `ANALYZE` failing.

`packages/quereus-isolation/src/isolated-table.ts` forwards **neither** `getStatistics` nor
`saveStatistics` to the table it wraps today. Add both delegations, or an isolated store
table can never persist what `ANALYZE` collects for it.

## What gets persisted, and how much

Extend the `__stats__` record (`TableStats` in
`packages/quereus-store/src/common/serialization.ts`) with an optional column-statistics map.
The field is optional, so an existing record written before this ticket reads back as "no
column statistics" and the module falls back — no migration step, no version field.

**Bound what goes in.** `collectStatisticsFromScan` builds up to 100 histogram buckets per
column from a 1000-row sample; three fields per bucket at roughly 40 bytes of JSON is ~4 KB
of histogram per column, and the whole record is read and written as one value. So:

- `distinctCount`, `nullCount`, `minValue`, `maxValue` — persisted for **every** column. These
  are what the engine's equality, IS NULL and join estimates use.
- `histogram` — persisted only for columns that are a **primary-key member or the leading
  column of a secondary index**. Those are the only columns whose range predicates the store
  can turn into a seek, and they are the columns the engine's range estimates matter most for.
  Everything else drops its histogram on the way to disk, which costs a re-`ANALYZE` to
  recover and nothing else.

State that rule as a named constant/predicate with the size arithmetic in its comment, so the
next reader can widen it deliberately.

**Serialization.** `serializeStats` is `JSON.stringify` today, which is correct for two
numbers and wrong for `minValue` / `maxValue` / `HistogramBucket.upperBound` — those are
`SqlValue`s and may be `bigint` or `Uint8Array`, which plain `JSON.stringify` throws on or
silently mangles. The same file already has the `replacer` / `reviver` pair that
`serializeValue` / `deserializeValue` use. Route the whole stats payload through those, and
add a round-trip test over every `SqlValue` shape (null, integer, bigint past 2^53, real,
text, blob, JSON, the temporal types) — this is the kind of thing that only fails on the one
column type nobody tried.

## The read path: load at prime, stamp at rehydrate

- `StoreTableBase.primeStats` already loads the persisted record when storage is first opened.
  Have it keep the column statistics alongside `cachedStats.rowCount`, and expose them
  through a getter.
- `StoreModuleSchemaSync.rehydrateCatalog` already ends with a per-table loop that refreshes
  each connected `StoreTable` from the freshly-registered schema. That loop has both the
  `StoreTable` and `db.schemaManager` in hand — stamp the loaded statistics onto the
  registered `TableSchema` there, via a direct `schema.addTable({...fresh, statistics})`.
  Use the SILENT path (no `notifyChange`): phase 3's `importCatalog` deliberately fires no
  schema-change events, and emitting one here would drive the module's own listener during
  its own rehydration.
- Pair the loaded `rowCount` with the persisted `columnStats` into one `TableStatistics`, and
  carry `lastAnalyzed` through so a staleness check can see how old they are. The rowCount
  written into `TableStatistics` is the ANALYZE-time count, not the live delta-tracked one —
  the two column counts and the row count must describe the same moment or every `1/D`
  estimate is computed against a denominator from a different era.

## What deliberately does NOT change

- **`StoreTable.getStatistics()` keeps reporting an empty `columnStats`.**
  `collectTableStatistics` in `runtime/emit/analyze.ts` reads a non-empty `columnStats` as
  "the module answered cheaply, skip the scan" — so returning the persisted snapshot there
  would make `ANALYZE` a no-op refresh that re-saves numbers it never recomputed. A cached
  snapshot is not an answer to "analyze me". Say so in that method's doc comment, which today
  explains the emptiness by "the store keeps no value distribution" — a reason that stops
  being true with this ticket.
- The `__stats__` re-key on `ALTER TABLE … RENAME TO`
  (`store-module-rename.ts`) copies the whole value, so column statistics ride along for free.
  Confirm with a test rather than by reading; `rename-stats-migration.spec.ts` is the place.
- `STATS_FLUSH_INTERVAL` and the mutation-driven row-count flush are untouched. Column
  statistics change only at `ANALYZE`.

# Edge cases & interactions

- **A record written before this ticket** (`{rowCount, updatedAt}`) must read back cleanly as
  "no column statistics". Test it by hand-writing the old shape into a durable provider and
  reopening.
- **Column renamed or dropped between `ANALYZE` and reopen.** `columnStats` is keyed by
  lowercase column name, and the rehydrated schema is built from the persisted DDL — so a
  renamed column's entry is simply never looked up, and a dropped column's entry is dead
  weight. Both degrade to the fallback. What must NOT happen is a stats entry being matched to
  a different column; the name key makes that impossible, so assert it stays name-keyed.
- **Statistics for a table that no longer exists.** `bug-drop-table-leaves-stale-stats-entry`
  (backlog) already records that `DROP TABLE` leaves the `__stats__` entry behind. This ticket
  makes that entry bigger, not differently wrong. Do not fix it here; note it in the handoff.
- **A crash between the `ANALYZE` schema write and the `saveStatistics` flush** leaves memory
  and disk disagreeing. Harmless — statistics are advisory and the next `ANALYZE` reconciles.
  Do not add a transaction around it.
- **Two connections over one provider.** Connection A runs `ANALYZE` and persists; connection
  B's in-memory schema keeps its own (possibly absent) statistics until it re-opens or
  re-analyzes. That is the same visibility model the row count already has. State it; do not
  build cross-connection propagation.
- **A module that implements `saveStatistics` but not durably** (the memory backend does not
  implement it at all) must be unaffected — the hook is optional and unimplemented is the
  default.
- **Isolation layer.** With the two delegations added, an isolated store table persists and
  reloads identically. Without them it silently does not — which is why a test must go through
  the isolated path, not only the bare module.
- **Reopen ordering.** `primeStats` is lazy (first storage open). The rehydrate loop only
  stamps tables that are CONNECTED at rehydrate time; a table first touched later must still
  pick up its statistics. Decide and state which of the two paths owns the stamp for a
  lazily-reconnected table (`ensureTableConnected` in `store-module-schema-sync.ts` is the
  counterpart site) and cover it — a table that only gets statistics when it happens to be
  connected during rehydration is a plan that depends on access order.

# Key tests

New `packages/quereus-store/test/stats-persistence.spec.ts`, using the durable in-memory
provider pattern from `store-row-count-to-planner.spec.ts` (whose `closeAll` keeps the byte
stores alive so a second `Database` over the same provider is a genuine reopen).

- **Survives reopen.** Create, populate, `analyze`, close, reopen: the rehydrated
  `TableSchema.statistics` carries the same per-column distinct counts, and a plan over the
  reopened database matches the pre-close plan.
- **Value round-trip.** min/max and histogram bounds survive for every `SqlValue` shape,
  including a bigint past 2^53 and a blob.
- **Histogram scope.** After reopen, an indexed/PK column has its histogram and a plain
  column does not — while the plain column still has its distinct and null counts.
- **Old record shape.** A hand-written `{rowCount, updatedAt}` entry reopens without throwing
  and yields no column statistics.
- **Rename carries them.** `alter table … rename to`, reopen, statistics intact under the new
  name (extend `rename-stats-migration.spec.ts`).
- **`ANALYZE` still scans.** Reopen a database that already has persisted statistics, change
  the data substantially, re-`analyze`: the distinct counts move. (This is the regression
  guard for the `getStatistics()` emptiness decision above.)
- **Through the isolation layer.** The same survives-reopen assertion with
  `@quereus/isolation` wrapping the store module.
- **Lazily-connected table.** Reopen, then touch a table that was NOT connected during
  rehydration: it plans with its persisted statistics.
