# Why

Everything so far measures the store layer over an in-memory key-value provider, which is
deliberate - it isolates store-layer cost from disk cost and it is deterministic enough to
run on every `yarn bench`. But the backend a real Node deployment uses is LevelDB, and it
has no measured numbers at all.

That gap has a concrete consequence today. Storage backends declare what their basic reads
cost relative to one sequentially-scanned row, and the query planner prices access paths
with those numbers. IndexedDB's come from a real browser benchmark. LevelDB declares
nothing, so it takes the framework's parity default - "a random read costs about what a
sequential read costs", `pointRead: 1.0` / `seekPositioning: 0.5` - chosen by assumption
years ago and never measured. `debt-leveldb-cost-profile-measurement` (backlog) asks for
exactly the measurement this suite makes routine.

# Architecture

## Opt-in, never gated

Disk-backed numbers are not reproducible: page cache, filesystem and disk type dominate, and
none of them is a property of this repository's code. So:

- The LevelDB backend runs only when explicitly asked for - an environment variable
  (`QUEREUS_BENCH_LEVELDB=1`) is enough, and matches how `yarn test:store` is already
  selected. A `bench:leveldb` script wiring it up is a convenience, not a requirement.
- When not asked for, every LevelDB benchmark **skips visibly** via the `skip()` entry point
  from `bench-backend-dimension`, with a reason naming the variable. A missing row reads as
  "unchanged" to anyone diffing two runs; that is the failure mode `skip()` exists to
  prevent.
- Its rows are marked informational in the printed output and must never contribute to a
  pass/fail verdict - not the ratio guards, not the regression gate that
  `bench-regression-gate` will build on top of this.

## Temporary directories

Fresh directory per run, inside the OS temp directory - **never inside the repository working
tree** - and removed in teardown. A LevelDB database left behind silently changes the next
run's numbers and litters the machine.

`logic.spec.ts` already does this correctly and is the pattern to copy: build the path under
`os.tmpdir()` with a timestamp-plus-random suffix, `mkdirSync` it, and on teardown close the
module first (ignoring close errors, which LevelDB lock contention can produce) and then
`rmSync(dir, { recursive: true, force: true })`. Put it in `bench/lib/tempdir.mjs` once
rather than in each benchmark.

**Windows.** The provider takes its `basePath` with forward slashes - `logic.spec.ts` passes
`dir.replace(/\\/g, '/')` and this must do the same. Removal must also survive a file still
being held: teardown runs in a worker that is about to exit, and a failure to remove must be
reported, not swallowed. Register a process-level last-resort cleanup so a worker killed by
the parent's timeout does not leave a database behind.

## Cache-warm versus cache-cold, made explicit

The cold/warm distinction is the whole question for a disk-backed store, and it must be a
declared property of each benchmark rather than an accident of run order. Two dataset sizes:
one comfortably inside the OS page cache and one well outside it. The IndexedDB run found the
small size hid the effect entirely, which is exactly why both are needed.

There is no portable way to drop the OS page cache from Node, so "cold" here means *first
touch of a freshly-written dataset large enough that it cannot all be resident* - not a truly
evicted cache. Say that in the benchmark's comment and in the docs. A claim of "cold" that is
really "warm" is worse than no claim.

## The two ratios

The measurement `debt-leveldb-cost-profile-measurement` needs, in the units
`cost-profile.ts` defines - both are ratios against one sequentially-iterated row, which is
1.0 by definition:

- **`pointRead`** - milliseconds per row for a full sequential iterate over N rows, against
  milliseconds per row for N random point reads. The point reads must go through the batched
  `getMany` path the index resolver actually uses (`StoreTableScan` pages at
  `ROW_RESOLUTION_BATCH`), not a naive `get` loop, or the number prices a path the engine
  never takes.
- **`seekPositioning`** - milliseconds per key for N single-key seeks, against the same
  sequential baseline.

Match the IndexedDB harness's 200-byte row values so the two backends' numbers are
comparable; `packages/quereus-plugin-indexeddb/bench/README.md` documents that shape and is
worth reading before choosing one.

Report the ratios explicitly, not just the component timings. A reader should not have to
divide two table cells to get the number the planner consumes.

## Then decide, and record the decision either way

The output is two ratios at two dataset sizes. Both outcomes are a result:

- **Near parity** (~1.0 and ~0.5): declare nothing, and record the measurement in
  `packages/quereus-plugin-leveldb/README.md` with the date, machine and dataset sizes, so
  the next person does not re-ask. LevelDB reads in-process through a block cache, so this is
  the likely outcome and it is not a wasted measurement.
- **Far from parity**: declare the measured `costProfile` on the LevelDB provider.

Either way, cross-reference `debt-leveldb-cost-profile-measurement` rather than duplicating
its reasoning, and note in the handoff that it collapses to "read the numbers and decide".
Do not close that ticket from here - the decision is a separate, deliberate act.

# Edge cases & interactions

- **Wall-clock.** A 10k-row bulk insert on real disk can take seconds per call. Calibration
  checks `minSamples` (5) *before* `maxTotalMs`, so five samples plus warmup is the floor, and
  `BENCH_TIMEOUT_MS` (120 s) covers `setup` as well. Size the LevelDB workloads smaller than
  their in-memory twins where needed, put the row count in the name, and pin anything that
  still runs long with the reason written down.
- **A killed worker leaves a database directory.** The parent kills a worker on timeout with
  `SIGKILL`, which runs no teardown. The last-resort cleanup above is what covers it; verify
  by killing a run mid-benchmark and checking the temp directory.
- **LevelDB holds a lock.** Two concurrent bench runs on the same machine must not collide -
  the per-run random suffix handles it, but only if it is per *worker*, not per suite import.
- **The plugin may fail to load** (native binding, platform). That is a `skip()` with the load
  error as the reason, not a benchmark failure - a machine that cannot run LevelDB should
  still complete `yarn bench`.
- **Do not compare a LevelDB number against an in-memory number as a ratio guard.** The
  backend-dimension ticket already forbids cross-backend guards; this is the case that makes
  the rule concrete.
- **Nothing here enters `yarn check`.** `bench-regression-gate` explicitly budgets its fast
  mode around the memory backend plus the in-memory store provider. Say so in the docs so the
  gate ticket does not have to rediscover it.

# Tests

- With the variable unset, `yarn bench` completes and every LevelDB row prints a skip reason
  naming the variable.
- With it set, a full run completes, and afterwards the OS temp directory contains no
  `quereus-bench-*` directories.
- A run interrupted mid-benchmark also leaves none.
- The two ratios are produced at both dataset sizes and appear in the run output.
