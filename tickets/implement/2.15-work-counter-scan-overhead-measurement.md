# What this is

The per-table work counters landed (`work-counter-vtab-boundary`, now in review). The
code is in the tree and all tests pass, but the **before/after benchmark comparison the
ticket asked for was never run** — the implementing agent hit its token budget first.

This ticket is that measurement, nothing else. No code change is expected.

# Why it matters here specifically

The counting added one branch per row inside the scan generator's `for await` loop —
the hottest loop in the engine. Everywhere else in this change the added work is once
per `query()` call, which is noise. The per-row site is the one place where a branch in
the wrong spot is genuinely measurable, and "counters are free when off" is currently a
design claim with no number behind it.

Two things changed on the default (metrics-off) path in `runtime/emit/scan.ts`:

- **Added**: one local resolved per scan invocation, and one `if (tableCounters)` test
  per row. `runtimeCtx.workCounters` is undefined by default, so the local is undefined
  and the per-row test is a constant-false branch.
- **Removed**: the deferred-rename lookup key (`` `${schema.schemaName}.${schema.name}`
  .toLowerCase() ``) used to be built per connect and is now built once in the emitter
  closure. So the scan path allocates *less* than before, not more.

The expectation is therefore no regression, possibly a hair faster. The point of the
ticket is to find out, not to confirm.

# What "done" looks like

Run the benchmark suite against this change and against the commit before it, on the
same machine in one sitting, and record the scan-heavy benchmark numbers. See
`docs/benchmarking.md` for the runner, the noise floor (a delta inside it is not a
change), and the process-isolation rules that make two runs comparable.

If a scan benchmark did move outside the noise floor, that is a real finding: say which
benchmark, by how much, and hand it to a fix ticket rather than absorbing it here.

# Not in scope

Benchmarking metrics-*on* execution. Metrics mode already inserts a counting generator
per instruction (from the core ticket) and is a debug mode with no default-on path; its
cost is a known, accepted property, not a regression to hunt.
