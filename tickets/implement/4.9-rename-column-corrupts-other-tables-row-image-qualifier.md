# One question, answered in the wrong place

Inside a CHECK constraint, a column `DEFAULT`, a `GENERATED ALWAYS AS` body, or a
result column's `with inverse (…)` clause, a bare `new.<col>` / `old.<col>`
qualifier names **the row being written** — never a table. `new` and `old` are
not reserved words in this parser, so `create table "new" (…)` is legal and the
two spellings genuinely collide.

The rename/probe walkers decide which meaning applies with a **flag chosen at the
walk's entry point**. But the answer is not a property of the walk — it is a
property of the **position in the tree**. Three consequences, all verified
in-session against `main` at `4f1b724c`.

## Arm A — the column walker has two states where the domain has three

`schema/rename/column-rename.ts` carries `matchRowImageQualifier: boolean` on its
walk state. `true` (the seeded entry point, `renameColumnInCheckExpression`) means
"`new.` names MY target table's row image — match it". `false` (the unseeded
`renameColumnInAst`) falls through to treating `new` as a **catalog table
reference**.

The missing third state is the one that actually occurs: *this expression IS
written-row context, but the row image belongs to some OTHER table, so `new.` /
`old.` names nothing this walk cares about and must be ignored.*

**Corruption.** Renaming a column of a table called `new` rewrites every other
table's row-image qualifier:

```sql
create table "new" (id integer primary key, v integer);
create table NwCk (id integer primary key, v integer,
                   constraint ck_nw check (new.v > 0));
insert into NwCk values (1, 5);            -- fine

alter table "new" rename column v to w;    -- ACCEPTED, silently

insert into NwCk values (2, 7);
-- QuereusError: new.w isn't a column
```

`NwCk`'s CHECK now reads `new.w > 0`, `NwCk` has no column `w`, and **every**
subsequent write to `NwCk` fails with an error naming neither `NwCk` nor the
statement that broke it. The damage persists with the schema; on a store backend
it survives a restart and the only recovery is rebuilding `NwCk`. Verified
identically for `old.`, for a column `DEFAULT` (`d integer default (new.v + 1)`
→ `new.w + 1`), and for a `GENERATED ALWAYS AS` body.

**False refusal.** The same missing state, read-only:

```sql
alter table "new" drop column v;
-- Cannot drop column 'v' from 'new': it is referenced by CHECK constraint 'ck_nw' on table 'NwCk'
```

That drop is legal — `ck_nw` is about `NwCk`'s own written row. Verified for the
DEFAULT arm too (`…referenced by the DEFAULT of column 'd' on table 'NwDf'`).

The **table** walker already has the missing mode
(`TableRenameOpts.rowImageContext` in `schema/rename/table-rename.ts`), which is
why `drop table "new"` is correctly allowed under the same schema (pinned at
41.10.4 §15). The two walkers disagree about the same SQL.

## Arm B — `with inverse` is written-row context that neither walker recognizes

A result column may carry `with inverse (base_col = expr-over-NEW)`
(`docs/sql-select.md` § Result-column inverses). Inside that expression `new.<x>`
names an **output column of the enclosing select** — mandatory spelling, validated
at build time. It is written-row context *sitting inside a view body*, which is
otherwise not written-row context at all. Both walkers descend it with ordinary
table scope, so a bare `new.` there is treated as a reference to a table called
`new`.

Column verb:

```sql
create table "new" (id integer primary key, v integer);
create table People (id integer primary key, code5 text);
create view VP as
  select id, case code5 when 'A1' then 'A' end as v
    with inverse (code5 = case new.v when 'A' then 'A1' end)
  from People;
insert into VP (id, v) values (1, 'A');    -- fine

alter table "new" rename column v to w;    -- ACCEPTED, silently

insert into VP (id, v) values (2, 'A');
-- QuereusError: result column 'v': WITH INVERSE reference 'new.w' does not
--   resolve to an output column of this select
```

Table verb, same view, same corruption:

```sql
alter table "new" rename to fresh;
insert into VP (id, v) values (1, 'A');
-- QuereusError: result column 'v': WITH INVERSE expression references 'fresh.v'
--   without the NEW qualifier; an inverse expression is over the written view row only
```

And the read-only side, through the dependency closure:

```sql
create table R (id integer primary key, n integer,
                constraint ck_r check (n < (select count(*) from VP)));
drop table "new";
-- cannot drop table 'main.new': CHECK constraint 'ck_r' on table 'R'
--   reaches it through view 'VP' — drop or redefine it first
```

This one also **falsifies a documented invariant**. `schema/object-dependency-closure.ts`
carries a `NOTE:` arguing that `rootOpts` may be root-only "by construction",
because `CREATE VIEW` rejects a body containing a bare unbound `new.` qualifier
and therefore a reached body can never hold one. `with inverse` is the
counterexample — `CREATE VIEW` accepts it, and the reached body does hold one.
The NOTE's stated revisit condition ("if the suppression ever widens beyond
seedless column qualifiers … this needs a test") has tripped.

The same shape fires one level in from a seeded CHECK, so Arm B is not
view-specific:

```sql
create table Src (id integer primary key, a integer);
create table Ck8 (id integer primary key, a integer,
  constraint c8 check (a < (select count(*)
                            from (select id as a with inverse (id = new.a) from Src))));

alter table Ck8 rename column a to b;
-- c8 becomes: b < (select count(*) from (select id as a with inverse (id = new.b) …))
```

The inner `new.a` named the inner select's output column `a`, which did not move.

## Arm C — the output-name pass reaches into a nested select's own inverse clause

`renameNewQualifiedRefs` (bottom of `column-rename.ts`) rewrites `new.<old>` →
`new.<new>` inside `with inverse` expressions when the enclosing select's OUTPUT
name shifted. It is deliberately depth-blind, on the documented reasoning that an
inverse expression's grammar admits no FROM clause that could rebind `new`. True
as far as it goes — but an inverse expression may contain a **subquery that is
itself a select with its own `with inverse` clause**, whose `new.` refs belong to
that inner select's outputs, not the outer one's:

```sql
create table B (id integer primary key, v integer);
create table C (id integer primary key, v integer);
create view VW as
  select id, v
    with inverse (v = new.v + (select count(*)
                               from (select v with inverse (v = new.v) from C)))
  from B;

alter table B rename column v to w;
-- inner clause becomes `with inverse (v = new.w)` — the inner output is still `v`
```

The inner target `v` correctly stayed put (it rides the scope-aware synthetic
probe); only the depth-blind pass corrupted the inner `new.v`.

# Expected behavior

- `alter table "new" rename column v to w` leaves every OTHER table's `new.` /
  `old.` qualifier untouched, and `alter table "new" drop column v` is allowed
  when the only thing "naming" it is another table's row-image qualifier.
- A genuine cross-table reference to a table called `new` keeps behaving exactly
  as today. Verified controls, all of which must stay green:
  - `check (n < (select max(v) from "new"))` → rewritten to `max(w)`;
  - `check (n < (select max("new".v) from "new"))` → rewritten, and
    `drop column w` still refused;
  - a subquery inside the OWN table's CHECK selecting from a real `"new"` →
    rewritten (the qualifier is FROM-bound, so it never reaches the row-image
    decision);
  - `check (new.v > 0)` on its own table → still rewritten, still enforced.
- `old.` behaves identically to `new.` everywhere above.
- A `with inverse` expression's `new.<output-column>` refs are **inert** to every
  table rename and to every column rename of a *base* table — they name the
  enclosing select's output row. They still follow a shift of that select's own
  published output name, which is what `renameNewQualifiedRefs` exists for, and
  that pass must stop at a nested select's own inverse clause.
- The table verbs stay correct — 41.10.4 §15 is the guard.

# Design

Row-image context becomes an explicit, three-valued argument threaded to the
position in the tree, not a boolean chosen at the entry point.

```ts
// schema/rename/shared.ts — shared vocabulary, next to ResolveObjectRef
/**
 * What a bare, unbound `new.` / `old.` column qualifier names AT THIS POINT in a
 * rename walk. Three-valued because the domain is: the walk's own target's row
 * image, some OTHER relation's row image, or no written-row context at all.
 */
export type RowImageContext =
	/** No written-row context here — `new.x` is an ordinary table reference. */
	| 'none'
	/** Written-row context whose image IS the walk's target table — match it. */
	| 'own'
	/** Written-row context whose image belongs to another relation — ignore it. */
	| 'foreign';
```

`ColumnRewriteState.matchRowImageQualifier: boolean` becomes
`rowImage: RowImageContext`. The qualified-`column` arm of `visitColumnRename`
keeps its existing precedence — an in-scope binding still decides first, and a
schema-qualified `main.new.a` is still a real three-part reference — and only the
*unbound bare* case consults the mode: `'own'` matches, `'foreign'` ignores,
`'none'` falls through to `resolveRef(undefined, qualifier)` as today.

**Signature shape.** Insert `rowImage: RowImageContext` as a required parameter
immediately after `targetKey` and before the optional `resolveColumnInSource`, on
`renameColumnInAst`, `renameColumnInCheckExpression`, `columnReferencedInAst` and
`columnReferencedInCheckExpression`. Required, so every existing call site is a
compile error until it answers — that is the whole point, and it is why this is
*not* a third entry point. Do **not** bundle the other six positional arguments
into a `ColumnRenameTarget` this cycle: two sibling tickets are editing this same
file, and a ~25-call-site signature churn maximizes conflict for no behavior gain.
`bodyExposesRenamedColumn` / `bodyPublishesColumnNamed` are exposure probes with
no row-image question; they keep `'none'` internally and their signatures
unchanged.

The three collection helpers keep their signatures and hardcode the mode their
doc comments already promise, so the `@quereus/quereus-store` package needs no
change:

| helper | mode | why |
|---|---|---|
| `renameColumnInCheckConstraints` | `'own'` | documented "only pass the renamed table's OWN checks" |
| `renameColumnInColumnExpressions` | `'own'` | same contract for DEFAULT / generated |
| `renameColumnInIndexPredicates` | `'none'` | a predicate describes rows already stored — no written-row context. This discharges the "inert here" paragraph in its doc comment and puts it in parity with `renameTableInIndexPredicates`, which already passes no `rowImageContext`. Behavior is unchanged: an indexed table called `"new"` with `where "new".v > 0` matches through `resolveRef` instead of through the row image, same answer. |

**The table walker keeps its boolean.** `TableRenameOpts.rowImageContext` is
complete for that walker — it never *matches* a row image, only suppresses one —
so `false`/`true` map to `'none'`/`'foreign'`. Re-document the mapping; do not
churn the type.

**`with inverse` is a subtree override in both walkers.** While descending a
`with inverse` assignment's `expr`, force the row-image mode to `'foreign'`
(column walker) / `rowImage = true` (table walker), saving and restoring around
the visit. Ambient mode is irrelevant: an inverse expression is *always* over the
enclosing select's output row. The legitimate rewrite in that position — the
output-name shift — is not lost, because `renameNewQualifiedRefs` performs it
separately after the body walk.

This subtree override also means reached view bodies self-suppress, so
`reachableObjects`' `rootOpts` stays root-only and stays correct — but for a new
reason. Rewrite the NOTE accordingly and pin the reached-body case with a test,
which is now possible.

**Per-call-site modes.** Every unseeded/seeded site in `packages/quereus/src`:

| site | mode |
|---|---|
| `alter-table.ts` persistability pre-flight (view / MV bodies) | `'none'` |
| `alter-table.ts` `propagateColumnRename` view-body loop | `'none'` |
| `alter-table.ts` `rewriteTableForColumnRename` — own CHECK / other CHECK | `'own'` / `'foreign'` |
| `alter-table.ts` `rewriteTableForColumnRename` — index predicates (both arms) | `'none'` |
| `alter-table.ts` own column expressions / `rewriteOtherTableColumnExpressions` | `'own'` / `'foreign'` |
| `assertion-rename-helpers.ts` assertion bodies | `'none'` |
| `materialized-view-helpers.ts` MV bodies | `'none'` |
| `drop-column-guards.ts` assertion bodies and their reach | `'none'` |
| `column-republication.ts` view / MV body probe | `'none'` |
| `expression-dependents.ts` `columnProbe` | `reached.ownerKey === undefined ? (seeded ? 'own' : 'foreign') : 'none'` |
| `schema-differ.ts` view-body inverse reconcile | `'none'` |
| `schema-differ.ts` index-predicate inverse reconcile (both arms) | `'none'` |
| `schema-differ.ts` own CHECK inverse / cross-table CHECK inverse | `'own'` / `'foreign'` |

The `columnProbe` rule is worth stating in prose at the site, because it is the
only one that is not a constant: a **root** body is a table's CHECK / DEFAULT /
generated body and therefore always written-row context — `'own'` only for the
seeded base-target case, `'foreign'` otherwise (including a republication target
at the root, where the qualifier names the owning table's image and not the view
being probed); anything **reached** below the root is a view / MV body, a relation
with no written row, so `'none'`.

**Arm C** is local to `renameNewQualifiedRefs`: keep the depth-blind object-graph
walk, but stop descending when the traversal enters a nested select's own
`with inverse` clause — those `new.` refs belong to that select's outputs. A
correlated `new.<outer-output>` inside an ordinary subquery in the inverse expr
must still be reached, so this cannot be a blanket "stop at any nested select".
