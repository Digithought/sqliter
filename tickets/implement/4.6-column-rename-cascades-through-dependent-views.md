# A rename that changes what a view publishes has to keep going

`ALTER TABLE … RENAME COLUMN` rewrites the body of every view that reads the
renamed column. That rewrite also changes the **name the view publishes**.
Nothing revisits the objects reading the view, so propagation stops one level
deep.

Verified at HEAD:

```sql
create table w3 (id integer primary key, x integer);
create view v1 as select id, x from w3;
create view v2 as select id, x from v1;
alter table w3 rename column x to y;   -- succeeds
-- v1 body becomes: select id, y from w3   (correct — v1 now publishes `y`)
-- v2 body unchanged: select id, x from v1 (now names a column v1 no longer has)
select * from v2;                       -- Column not found: x
```

With an assertion in place of `v2` the damage is worse — every write to the
whole database fails, because assertion evaluation recompiles every live
assertion on any commit:

```sql
create view v1 as select id, x from w;
create assertion a1 check (not exists (select 1 from v1 where x < 0));
alter table w rename column x to y;    -- succeeds
insert into w values (1, 1);           -- Column not found: x
```

Note this is a **column-verb-only** defect. Renaming a *table* changes no
dependent's published names, so table renames need no cascade.

## Shape of the fix: a worklist, not a second pass

Turn `propagateColumnRename` from a single sweep into a fixpoint:

```
queue := [ (targetKey = <schema>.<renamed table>, oldCol, newCol) ]
visited := {}
while queue not empty:
    item := queue.pop()
    if item in visited: continue ; visited.add(item)
    run the existing per-schema propagation for item          # tables, views, MVs, assertions
    for each view / materialized view whose body was rewritten:
        if it now PUBLISHES newCol where it published oldCol:
            queue.push( (objectRefKey(owner, its name), oldCol, newCol) )
```

Key `visited` on `` `${targetKey}:${oldColLower}` ``. Views cannot be recursive
and a maintained table cannot derive from itself, so the set is insurance
against a malformed catalog rather than an expected cycle — but it must be
there, because the loop is unbounded without it.

Because the cascade re-enters the *same* per-schema propagation, every arm the
first round covers — dependent tables' CHECK / DEFAULT / GENERATED expressions,
views, materialized views, assertions — is covered at every depth for free.

## "Publishes the renamed column" already exists

Do not write a new resolver for this. `column-rename.ts` already answers the
question for CTEs: `cteExposesRenamedColumn` / `isResultColumnExposure` decide
whether a body re-exposes the renamed column under the new name, handling the
cases that matter — an explicit alias suppresses exposure, an explicit column
list on the CTE suppresses it, a bare projection exposes it, and `*` / `t.*`
exposes it when the frame binds the target unaliased.

Lift that to a public entry point over a whole body:

```ts
/**
 * Whether `body`'s top-level result columns publish the renamed column under
 * `newCol` — i.e. whether rewriting this body shifted the name its readers see.
 * Call AFTER the body rewrite: the predicate compares against the NEW name,
 * exactly as the CTE exposure analysis does.
 */
export function bodyExposesRenamedColumn(
    body: AST.QueryExpr,
    tableName: string, oldCol: string, newCol: string,
    resolve: ResolveObjectRef, targetKey: string,
    resolveColumnInSource: ResolveColumnInSource,
): boolean;
```

A view created with an explicit column list (`create view v(a, b) as …`) never
shifts its published names — `ViewSchema.columns` is the same guard
`cte.columns` already is. Handle it at the call site, not inside the predicate.

For a materialized view the cascade is not optional bookkeeping:
`applyMaterializedViewRewrite(..., renamedColumns = true)` already renames the
backing columns to follow the body's output names, so an MV's **own catalog
columns** change and its readers are as broken as `v2` above.

## Decision: the persistability pre-flight stays round-1 only

`assertRenameDependentsPersistable` runs before the first catalog mutation and
vetoes prospective bodies a storage module could not persist. Simulating the
whole cascade there would mean either running the fixpoint twice or vetoing
mid-cascade after the catalog swap — the latter inventing a partial-rename
failure mode the engine does not have today.

Leave the veto where it is, and record why at the site as a `NOTE:`: the only
thing a module refuses is an unencodable name/literal, and every cascade round
introduces **the same `newCol` string** that round 1 already vetted. A cascaded
body can therefore only be unpersistable for a reason that predates the
statement. Revisit if the veto hook ever grows a check that depends on the body
as a whole rather than on the names introduced.

## Edge cases & interactions

- **Alias suppresses the cascade.** `create view v1 as select id, x as x from w`
  still publishes `x` after the rename — dependents must NOT be rewritten. This
  is the false-positive case and the sharpest test.
- **Explicit view column list.** `create view v1(a, b) as select id, x from w`
  publishes `a, b` regardless — no cascade.
- **`select *`.** `create view v1 as select * from w` publishes `y` after the
  rename; `v2` over it must follow. This is the case a syntactic
  "look for a bare `x` in the result columns" shortcut gets wrong.
- **The dependent already has a column of the new name.** `create view v2 as
  select x, y from v1` where `v1` publishes both — renaming `w.x` to `y` makes
  `v1` publish two `y`s. Decide and document: the rename should fail with a
  clear message rather than produce a duplicate-name body, mirroring how the
  base-table verb refuses a rename that collides with an existing column.
- **Diamond.** `v3` reads both `v1` and `v2`, both of which republish the
  column. The visited set must keep `v3` from being rewritten twice; if it is
  rewritten twice, `oldCol` no longer appears the second time so the body is
  unchanged — but the `view_modified` event would fire twice. Assert the event
  count.
- **Double rewrite of one object across rounds.** An object can legitimately be
  touched in round 1 (as a reader of the base table) and round 2 (as a reader of
  a view). Confirm the second pass is a no-op on the body and does not emit a
  spurious event, and that `applyMaterializedViewRewrite` tolerates re-entry
  within one statement (its `preStale` snapshot is taken once, before the
  statement).
- **Staleness restore.** `restoreUnaffectedMaterializedViews` runs once after
  the whole cascade, not per round.
- **Cross-schema.** With `rename-propagation-crosses-schema-boundaries` landed,
  a cascade round must reach dependents in every schema — the round is just the
  existing propagation, so this should be automatic; test it anyway
  (`main.t` → `main.v1` → `temp.v2`).
- **Assertions at depth.** The `a1` repro above must pass: after the rename, a
  write succeeds and the assertion still enforces the same rule.
- **A dependent that reads the view but not the renamed column** must not be
  touched at all.
- **Ordering within a round.** A view and its reader may be visited in either
  order inside one round; correctness must not depend on the order, because the
  reader's reference to the view is only rewritten in a *later* round. Add a
  test where the dependent sorts before its dependency by name.

## Expected test outcomes

- `w3 → v1 → v2` chain: after `rename column x to y`, `v2`'s body reads `y` and
  `select * from v2` returns rows.
- `w → v1 → assertion a1`: after the rename, `insert into w` succeeds and the
  assertion still fires on a violating row.
- Aliased republish (`x as x`) and explicit-column-list views: bodies unchanged.
- `select *` chain: follows.
- Three-level chain `t → v1 → v2 → v3`: all three bodies correct.
- MV in the chain: its backing columns and every reader follow.
- Collision case: rename refused with a message naming the dependent view and
  the conflicting column.
- Event counts: one `view_modified` per body actually changed.
