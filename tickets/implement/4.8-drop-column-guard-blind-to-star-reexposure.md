# A star hides the column the drop guard is looking for

`ALTER TABLE … DROP COLUMN` refuses when a live integrity rule can reach the column.
Reach is computed over view and materialized-view bodies, and each body in the chain
is probed for the column **by name**. A view that re-exposes the column with a star
names it nowhere, so the chain reads clean and the drop is accepted.

Everything below was re-verified in-session against `main` at `f7f4ee79`, by driving a
`Database` directly. The source `fix/` ticket's claims are confirmed except for the
materialized-view one, which is corrected here.

## What actually happens

**Leaks (drop accepted, rule left broken).** Both star spellings, on the assertion arm:

```sql
create table t (id integer primary key, x integer);
create view v as select * from t;          -- or: select t.* from t
create assertion a check (not exists (select 1 from v where x < 0));

alter table t drop column x;               -- ACCEPTED

create table unrelated (i integer primary key);
insert into unrelated values (1);          -- Column not found: x
```

The blast radius really is the whole database: `AssertionEvaluator` recompiles every
live assertion on any commit, so a write to a table that has nothing to do with `t`
fails. The named-projection spelling (`create view v as select id, x from t`) is
correctly refused today, which is what makes this a lineage gap rather than a missing
guard.

The same hole on the CHECK arm, blast radius one table instead of the database:

```sql
create table t (id integer primary key, x integer);
create view v as select * from t;
create table r (id integer primary key, n integer,
                check (n < (select max(v.x) from v)));

alter table t drop column x;               -- ACCEPTED
insert into r values (1, 1);               -- v.x isn't a column
```

And through a chain, with the star anywhere below the top:

```sql
create view v1 as select * from t;
create view v2 as select id, x from v1;
create assertion a check (not exists (select 1 from v2 where x < 0));
alter table t drop column x;               -- ACCEPTED
```

(The mirror chain — star at the *top*, `v1` naming the column — is already refused,
because `v1`'s body spells `t.x`.)

**Materialized views do NOT leak — correcting the source ticket.** `create
materialized view m as select * from t` plus an assertion reading `m.x` survives the
drop with no error at all: the drop marks `m` stale (verified: `derivation.stale`
flips `false` → `true`) and `m`'s **backing table keeps its own `x` column**, so the
assertion still compiles and still runs, against frozen contents. Nothing breaks. See
*The materialized-view decision* below — this is a policy question, not a leak.

**False refusal, same missing capability, opposite direction.** Because the catalog
thinks a view exposes no columns at all, a legal drop is refused:

```sql
create table t (id integer primary key, v integer);
create table u (id integer primary key, v integer);
create view uv as select v from u;
alter table t add constraint ck check (id < (select max(v) from uv));

alter table t drop column v;
-- Cannot drop column 'v' from 't': it is referenced by CHECK constraint 'ck'   ← wrong
```

`t.v` is read by nothing; the `v` inside the subquery binds to `uv`. The qualified
spelling (`max(uv.v)`) is correctly allowed. `buildColumnSourceResolver` answers "does
source `s.t` expose column `col`?" with `getTable(t)?.columnIndexMap.has(col)`, and a
view is not a table there, so the seeded walk falls back to the implicit own-table
binding. Pinned as a known wrong answer by `41.10.2` §29's comment.

**A third arm found while reproducing: an explicit column list over a star body.**

```sql
create view v(a, b) as select * from t;
create assertion a check (not exists (select 1 from v where b < 0));
alter table t drop column x;               -- ACCEPTED
insert into unrelated values (1);          -- View 'v' has more explicit column names than SELECT columns
```

Here the lineage is *positional*, not by name: dropping any column of `t` changes the
star's arity and breaks `v` outright, so every reader of `v` breaks — same whole-database
blast radius. `RENAME COLUMN` correctly ignores such views (a pinned column list means no
published name shifts), so this arm is the one place the drop rule must NOT simply mirror
the rename rule.

# The fix: reuse the lineage RENAME COLUMN already computes

The decisive finding. `ALTER TABLE … RENAME COLUMN` gets every one of these shapes
right today — verified by inspecting the rewritten assertion body afterwards:

| shape | rename result |
|---|---|
| `v as select * from t`, assertion reads `v.x` | body rewritten to `y` ✅ |
| `v as select * from t`, assertion reads only `v.id` | left alone ✅ |
| `v1 as select * from t`, `v2 as select id, x from v1`, assertion reads `v2.x` | rewritten to `y` ✅ |

It gets them right because it does not ask a one-target name question. It runs a
**republication fixpoint** (`runtime/emit/column-rename-cascade.ts`): rewriting a view
body can shift the name that view *publishes*, so each round re-targets on the views
whose published names shifted and runs again, breadth-first until nothing shifts. A
`select *` body republishes without naming anything, and `bodyExposesRenamedColumn`'s
`col.type === 'all'` arm already sees that.

So this is not a missing capability — it is a capability the drop guards do not
consult. That matters because the invariant these modules are built on, repeated in
three doc comments, is that **the drop refuses exactly the references a rename would
have rewritten**. Today it does not, and this ticket restores it rather than inventing
a second lineage rule.

## Shape of the change

**Extract the fixpoint into `schema/`.** `scanShiftedPublishers` is private to
`runtime/emit/column-rename-cascade.ts`, and `schema/expression-dependents.ts` cannot
import from `runtime/emit/` without inverting the layering. Move the scan (and a new
read-only driver over it) into `schema/column-republication.ts`; have the cascade
import it. The read-only driver is very nearly
`assertColumnRenameCascadePublishable`'s loop with the collision arm removed:

```ts
/** The seed, plus every view / MV that republishes the column, transitively. */
export function columnRepublicationTargets(
	db: Database,
	seed: ColumnRenameCascadeTarget,          // { targetKey, tableName }
	columnName: string,
	resolvers: ObjectRefResolvers,
	resolveColumnInSource: ResolveColumnInSource,
): ReadonlyArray<ColumnRenameCascadeTarget>;
```

There is no rename here, so the probe needs a **sentinel** new name — the same trick
`columnReferencedInAst` already uses (`PROBE_COLUMN_NAME`). `scanShiftedPublishers`'s
`probeOnClone: true` path applies the sentinel rename to a spine clone and asks
`bodyExposesRenamedColumn` against it, mutating nothing; that is exactly what the
pre-flight does, and its doc comment already argues why a read-only fixpoint over the
pristine catalog gives the same answers the live rounds would. Downstream rounds keep
asking about `columnName` (unchanged — nothing is being renamed).

**Consume it in both guard families.** Today each family loops the reach's bodies
against ONE target:

```
for (const reached of reach.bodies)
    if (columnReferencedInAst(reached.body, tableSchema.name, columnName, …, tableKey, …)) refuse
```

It becomes the same loop crossed with the republication targets:

```
for (const reached of reach.bodies)
    for (const target of republicationTargets)
        if (columnReferencedInAst(reached.body, target.tableName, columnName, …, target.targetKey, …)) refuse
```

The base table is the first target, so every currently-refused case is refused
unchanged and the existing message spellings do not move. Both call sites —
`assertNoAssertionNamesColumn` (`runtime/emit/drop-column-guards.ts`) and `columnProbe`
(`schema/expression-dependents.ts`) — take the same widening, from the same helper, so
the two families cannot end up with different lineage rules. That "one answer covers
both families" requirement is the whole reason this is one ticket.

Worked through by hand against the still-allowed shapes: the assertion that reads
`v.id` finds no target it names; the `select *` assertion body of §7 names no column at
all; §21/§25's shadowing cases go through the same scope-aware walker they already do.

**Make the column-source resolver see views.** `buildColumnSourceResolver` must answer
"does source `s.t` expose `col`?" for a view. The predicate already exists:
`bodyPublishesColumnNamed(view.selectAst, col, resolve, resolveColumnInSource)`
(`schema/rename/column-rename.ts`) answers it for an alias, a bare projection, or a
star over a real source. Three notes:

- An explicit `ViewSchema.columns` list (and `TableDerivation.columns`) pins the answer
  and must be checked first.
- The recursion is self-referential — a view over a view — so the resolver has to pass
  *itself* down and carry a visited set. Views cannot be recursive, so the set is
  insurance against a malformed catalog, the same role it plays in `reachableObjects`.
- A maintained table already answers correctly through `columnIndexMap` (its backing
  columns are real), so the maintained arm needs no change.

This is what fixes the false refusal, and it also lets `bodyPublishesColumnNamed` see
through a star over a *view* rather than only over a base table.

**Signature change, four callers.** The view arm needs a `ResolveObjectRef` per view
home schema, i.e. an `ObjectRefResolvers`, which `snapshotObjectRefResolvers` builds
from a `Database` (it needs `db._homeSchemaPath`). So `buildColumnSourceResolver` takes
a `Database` instead of a `SchemaManager`. All four call sites have one to hand:
`drop-column-guards.ts:208`, `expression-dependents.ts:138`, `alter-table.ts:395`
(`rctx.db`), `constraint-builder.ts:70` (`ctx.db`). Re-check the two rename callers and
the constraint-builder strip: they inherit the widened answer by design (parity is the
point), but `constraint-builder.ts` is the one **plan-build-time** caller, so its
behavior change wants its own test.

## The materialized-view decision — please make it explicitly

`41.10.2` §27 pins today's behavior: a *named-projection* MV in the chain refuses the
drop. By the reasoning above that refusal is arguably already conservative — the MV's
backing keeps the column and the rule keeps working — but it is the pinned, safe
direction and it is what `DROP TABLE` does for the same object.

Recommendation: **treat an MV exactly like a view in the republication fixpoint**, so
the star spelling refuses too. It keeps one rule for both object kinds, matches §27, and
errs toward refusing. Be honest about the cost in the doc update: the refusal is
conservative — an MV's backing column survives the drop, so the rule it feeds would in
fact have kept working (against frozen data, with the MV marked stale and its next
`refresh materialized view` failing).

The alternative — lineage *terminates* at an MV, because a drop does not remove the
backing column the way a rename renames it — is defensible and strictly more precise,
but it reverses §27 and is a documented policy change. If it is chosen, say so in both
docs sections and rewrite §27.

Do not gate on staleness: the cascade excludes pre-stale MVs because their backing
columns are not renamed, which is a rename-specific reason with no drop analogue.

## The explicit-column-list arm

The republication fixpoint skips views with an explicit column list, correctly for the
rename. For the drop they need the opposite treatment: if such a view's body stars over
the dropped column's table, the drop changes the body's arity and breaks the view
outright, so **every** reference to it breaks — not just references to one column.

Suggested rule, which the reach already has the information for: when a view (or MV)
has an explicit column list and its body republishes the dropped column, refuse if any
body in the reach names that view at all — `ObjectReach.namerOf(viewKey)` answers that
directly. No still-allowed counter-shape exists here: any column drop on the source
breaks such a view.

This arm is separable from the other two if it turns out to fight the design; if you
drop it, say so in the handoff and leave the `NOTE:` at the site rather than silently
narrowing scope.

## Cost

Each guard now runs the republication fixpoint once per drop, and probes
`bodies × targets` instead of `bodies × 1`. Targets is the number of views republishing
the dropped column — zero for the overwhelmingly common case, so the common path adds
one catalog sweep and nothing else. This is reasoned from the call shape, not measured;
DDL is rare, and the neighbouring modules carry the same reasoning in their NOTEs.
The view-aware resolver adds a body walk per `(view, column)` question, on a path
`constraint-builder.ts` reaches at plan-build time — memoize the per-view answer inside
one resolver instance and leave a `NOTE:` saying so.
