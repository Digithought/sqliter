# What this is

The core ticket counts instructions and rows. This one adds the other half a benchmark
needs: **how many times the execution asked a table for data, and how much came back.**

A row count alone cannot distinguish a narrow index seek from a full scan that
post-filters to the same rows — that is precisely why the store package's specs count
store visits today. Lifting the same idea to the engine boundary makes it available to
every benchmark without any per-module cooperation.

## Where the counting happens, and why there

**Decision: count at engine-owned call sites, not inside modules.**

The engine calls a virtual table in exactly two places:

- `runtime/emit/scan.ts` — one `vtabInstance.query(effectiveFilterInfo)` per scan
  invocation, and the `for await` loop that drains it. This is the single door for
  `SeqScan`, `IndexScan` and `IndexSeek` alike.
- `runtime/emit/dml-executor.ts` — the per-row `vtab.update()` await.

Counting there means the numbers work for the memory module, the store module, the
isolation wrapper and any third-party module, with no interface change and nothing for a
module author to implement. The alternative — a counting module wrapper installed by the
benchmark harness — only ever counts the one module it wraps, and would need a fresh copy
per plugin. A counter that works for one module is worth less than one that works for
every module.

**The trade-off, stated plainly so nobody is surprised by it:** these counters measure
the **engine-to-module** boundary, not the **module-to-storage** boundary. If a module
changes from issuing 1000 single key reads to one batched multi-key read, these counters
do not move — the engine issued the same one `query()` either way. That deeper layer is
measured by the counting key-value store double in `@quereus/store/testing` (see the
store-counting-double ticket) and consumed by the store benchmark suite. Two layers, two
instruments; say so in the docs so a reader does not expect the engine counters to catch
a batching regression inside a module.

## Shape

Add to `WorkCounterSnapshot`:

```ts
/** Engine-to-module access, keyed `<schema>.<table>` (lowercased). Keys sorted. */
tables: Record<string, {
	/** `query()` calls the engine issued against this table. */
	queryCalls: number;
	/** Rows the engine pulled out of those calls. */
	rowsScanned: number;
	/** `update()` calls the engine issued (insert, update and delete alike). */
	updateCalls: number;
}>;
```

Plus `totals.queryCalls`, `totals.rowsScanned`, `totals.updateCalls`.

`queryCalls` is the one that makes an N+1 regression obvious: a correlated subquery that
the optimizer failed to decorrelate issues one `query()` per outer row, so the count
jumps from 2 to 101 while the row count barely moves.

# Edge cases & interactions

- **Key by the table name, not the scan site.** A self-join scans one table from two
  sites; both roll into that table's single entry. This is deliberate — the per-site
  breakdown is already in the per-instruction block.
- **Renamed tables.** The scan emitter resolves through `runtimeCtx.tableNameRemap` when
  a deferred constraint evaluates a plan frozen before an `ALTER TABLE ... RENAME TO`.
  Use the **effective** (post-remap) name as the counter key, so one table never appears
  under two keys within one execution.
- **Re-scans reuse a cached connection.** `RuntimeContext.scanConnections` caches the
  connected instance per scan site, so a nested-loop-join inner re-scan connects once but
  calls `query()` once per outer row. Count the `query()` calls, not the connects — the
  connect count is a caching artifact, the call count is the work.
- **Rows scanned vs rows out.** A scan that yields 10000 rows into a filter that passes 3
  must report `rowsScanned: 10000` for the table and `out: 3` for the filter instruction.
  Count at the `for await` inside the scan generator, before any downstream operator.
- **Aborted or partially drained scans.** A `LIMIT` that stops a scan early, or an
  `AbortSignal` firing mid-scan, leaves a partial `rowsScanned`. That is the truth of what
  the execution did — do not try to complete it. But it does mean an early-terminating
  benchmark must fully drain its result for its counters to be reproducible; note that in
  the benchmark-authoring docs.
- **Counting must not perturb cancellation or error paths.** The scan generator's
  `finally` disconnects owned instances and closes the row slot; increment counters in the
  loop body, never in a way that can throw or that a `finally` depends on.
- **Forks.** The scan and DML emitters read `runtimeCtx.workCounters`, which forks share
  by reference, so a scan driven inside a fork rolls up to the same table entry.
  No new fork-contract entry is needed — the field already has one.
- **Zero cost when off.** `runtimeCtx.workCounters` is undefined on the default path; the
  added work must be a single optional-chained call per `query()` and per row. Re-run the
  same before/after benchmark comparison the core ticket used and confirm the scan
  benchmarks did not move — the per-row site is the hottest loop in the engine, so this is
  the one place where an optional-chain in the wrong spot is genuinely measurable.

# Not in scope

Counting inside a module (key-value round trips, batching), and gating.
