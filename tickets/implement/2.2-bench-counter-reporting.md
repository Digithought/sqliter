# What this is

The engine can now report what work an execution did. This ticket makes the benchmark
harness collect those counts, write them into the results file, and show their deltas in
the comparison — as exact integers with **no tolerance band**, in a column distinct from
the noise-aware timing delta.

A timing delta says "this might be slower". A counter delta says "this does different
work". They are different claims and must not share a column.

## Counters are collected in a separate, untimed pass

Turning metrics on changes what the scheduler does: it wraps every async iterable in a
counting generator. Collecting counters inside the timed `fn` would corrupt exactly the
number the harness exists to measure.

So a benchmark declares an **optional second entry point**:

```js
{
	name: 'full-scan-10k',
	async setup() { db = await createPopulatedDb(); },
	async teardown() { await db.close(); db = null; },
	async fn() { /* timed, metrics off, unchanged */ },
	/** Optional. Run ONCE, after timing, with metrics on. Returns a work-counter snapshot. */
	async counters() {
		db.setOption('runtime_stats', true);
		const stmt = db.prepare('select * from bench_t');
		for await (const _row of stmt.iterateRows()) { /* must fully drain */ }
		return stmt.getWorkCounters();
	},
}
```

The worker (`bench/child.mjs`) runs `counters()` after `collectSamples` and before
`teardown`, and ships the snapshot back over IPC beside the timings. A benchmark with no
`counters()` reports none — every existing benchmark keeps working untouched.

Exact API shape of the option toggle and the drain loop is for the implementer to
confirm against the surface the core ticket landed; the constraint is that the counters
pass must (a) be outside the timed loop, (b) fully drain its result, and (c) return a
plain JSON snapshot.

## Results file

Each benchmark entry gains a `counters` field holding the snapshot verbatim, or is
absent when the benchmark declares no counters pass. The file already carries a `NOTE:`
saying it has no schema version and that a consumer needing to *reject* an old file
should add one; a missing `counters` field must read as "not collected", never as zero.

## Comparison output

`bench/lib/compare.mjs` gains a counter comparison that is deliberately unlike the timing
one:

- **No noise floor, no minimum delta.** Any difference is reported.
- Reported as `before -> after` integers, not percentages.
- Its own column in the table (or its own block below it when there are many changes —
  a wide per-instruction diff will not fit a terminal column).
- A benchmark whose baseline entry has no `counters` block is `counters: new`, not
  `counters: changed`.
- A changed counter does **not** set a non-zero exit code in this ticket. The gate is the
  downstream ticket; reporting first, gating second, so the counters can be observed for
  a while before anything fails a build over them.

## Which benchmarks qualify

Counters are only meaningful for a workload whose work is deterministic. Audited across
the current 27 benchmarks (15 execution, 4 mutation, 4 planner, 4 parser):

- **execution (15)** — all qualify. Fixed 10K-row datasets built from arithmetic, no
  timestamps, no random values, no dependence on hash iteration order for any *count*.
- **mutation (4)** — all qualify. `bulk-insert-10k`, `single-row-insert-1k` and
  `delete-where-100` build a fresh `Database` per call; `update-where-1k` applies and then
  reverses its own change.
- **planner (4)** — qualify for **plan-shape counters only** (`Statement.getPlanShape()`).
  They prepare a statement and finalize it; nothing executes, so there are no row or
  table counts to collect. This is a real signal in its own right: it is the pass that
  would catch a rule regression turning a hash join back into a nested loop.
- **parser (4)** — do **not** qualify. They call `parser.parseAll` directly and never
  build a plan or a runtime, so there is nothing to count.

Verify the audit rather than trusting it: the stability requirement below is what
actually settles which benchmarks qualify.

# Edge cases & interactions

- **Stability is the acceptance criterion, and it is measured here too.** Run the full
  counter-collecting suite twice and diff the `counters` blocks of the two results files;
  every counter must be byte-identical. Combined with the engine-level stability spec
  (same process, fresh database, separate process), that is the four-way check the
  original design called for — the harness already runs every benchmark in its own child
  process, so a suite-to-suite diff *is* the separate-process leg. Any benchmark whose
  counters differ between the two runs gets its `counters()` removed and a comment saying
  why. A counter that varies is worse than no counter, because something downstream will
  gate on it.
- **`--filter` and counters.** A filtered run must not report every unselected benchmark's
  counters as deleted. `matchesFilter` in `lib/discover.mjs` is already the single
  definition the comparison uses for exactly this reason — route the counter comparison
  through it rather than adding a second substring test.
- **A failed benchmark reports no counters.** Do not emit an empty or zero `counters`
  block for a benchmark that failed; that is indistinguishable from a benchmark that did
  no work.
- **A `counters()` that throws must fail loudly**, not silently drop the block. Report it
  as a benchmark failure phase (`counters`) the same way `setup` / `fn` / `teardown`
  failures are reported, so a broken counters pass cannot masquerade as a benchmark that
  simply declares none.
- **Result-file size.** Per-instruction detail across 23 benchmarks will grow the results
  file from a few KB to tens of KB. Acceptable — it is a diagnostic file, and the
  downstream gate needs the detail to say *where* a count changed. `bench/results/` is
  gitignored and unpruned; if the size ever becomes a nuisance the existing `NOTE:` about
  a retention sweep is the place to act.
- **The counters pass adds wall-clock to every run.** One extra execution per benchmark,
  untimed. Measure it and report the delta in the handoff; if it is material, `counters()`
  should be skippable with a flag (`--no-counters`) rather than silently slow.
- **`teardown` ordering.** `counters()` runs before `teardown` and may need its own
  statement finalized; a leaked prepared statement will hold a database open and trip the
  worker's leaked-handle exit path.

# Not in scope

Failing a run over a changed counter — that is the regression-gate ticket.
