# A FROM alias must add a qualifier, not remove the source's columns from scope

`ALTER TABLE … RENAME COLUMN` and `ALTER TABLE … DROP COLUMN` both decide "does
this stored expression reference this column?" with one scope-aware walk in
`schema/rename/column-rename.ts`. That walk treats a FROM source carrying an
alias (`from t as a`) as contributing **no columns to unqualified name
resolution**. SQL says the opposite: an alias adds a qualifier, it does not take
the source's columns out of scope, so a bare `x` written against `from t a`
binds `t.x` exactly as it would against `from t`.

The alias-*qualified* spelling (`a.x`) is handled correctly throughout. Only the
unqualified one is lost, and everything downstream — the DROP guards, the
rename cascade, the republication fixpoint — inherits the blind spot.

## What the fix-stage run established

All six reproductions in the source ticket were re-run against `main` and
confirmed: an assertion / another table's CHECK reading `x` under `from t a`
does not block `alter table t drop column x` (the database then rejects every
write with `Column not found: x`); a view republishing through `select * from t a`
is not recognised as a republisher by either verb; and `RENAME COLUMN` leaves
view and assertion bodies unplanable wherever the reference sits under an alias.

A **trial patch** was then applied — widening the frame's "binds the target"
predicate to scan `aliasMap` as well as `unaliased` — and:

- all six reproductions were fixed, with the correct refusal messages
  (including the broken-listed spelling for `create view v (p, q) as select * from t a`);
- the full suite passed: `yarn workspace @quereus/quereus run test` → **8918 passing,
  13 pending, 0 failing** (~3 min);
- seven hand-written edge cases behaved correctly — see *Edge cases already
  checked* below.

The trial patch was reverted; the tree is clean. It is **not** the deliverable —
it is evidence that the widening is behaviourally safe. The deliverable is the
representation change that makes the mistake unrepeatable.

## The representation change

`ScopeFrame` today carries two maps that between them answer one question badly:

- `unaliased: Map<lowercase bare name → resolved key>` — sources with no alias.
- `aliasMap: Map<lowercase alias → resolved key>` — sources with an alias.

`unaliased` is then read at four sites as if it meant "the sources an unqualified
column name can bind to", which is wrong the moment any source is aliased:

- `isTableInUnaliasedScope` — whether a bare column ref is captured at all (the
  arm behind every reproduction).
- `frameBindsTargetUnaliased` — the shared predicate the other three call.
- `isResultColumnExposure`, star arm — whether a bare `*` republishes.
- `isResultColumnExposure`, bare-column arm — same question for `select x from t a`.

Every FROM source exposes **exactly one** qualifier: its alias when it has one,
its bare name otherwise. That is already how both maps are populated, and the
planner agrees — `create view v as select t.x from t a` is rejected today with
`t.x isn't a column`, so an aliased real table must keep not registering its bare
name. So the two maps are one map with an artificial split down the middle, and
the split is the bug.

**Collapse them into a single `qualifiers: Map<string, string>`** — lowercase
qualifier → resolved object key — and expose **one** accessor for the binding
question:

```ts
interface ScopeFrame {
	/**
	 * Lowercase qualifier → resolved object key, one entry per FROM source:
	 * the source's alias when it carries one, its bare table / exposing-CTE
	 * name otherwise. Every entry BINDS unqualified column names in this frame
	 * (an alias adds a qualifier; it does not remove the source's columns from
	 * scope) and every entry is usable AS a qualifier.
	 */
	qualifiers: Map<string, string>;
	ctesExposingRenamed: Set<string>;
	ctesInScope: Set<string>;
	ctesShadowingSource: Set<string>;
	realSources: Array<{ key: string; schemaLower: string; nameLower: string }>;
}

/** Whether any source bound in `frame` resolves to `targetKey`. */
function frameBindsTarget(frame: ScopeFrame, targetKey: string): boolean;
```

After the collapse there is no second map for a future edit to consult "the
unaliased ones" — the wrong question can no longer be asked.

Two interactions the walk already handles must survive unchanged:

- An **exposing CTE** bound unaliased registers its name once (today it writes
  the same name/key into *both* maps — line ~545, so the merge is a plain
  collapse, not a semantic choice); an aliased exposing CTE registers its alias.
  Both must keep binding unqualified refs.
- `isTableInUnaliasedScope` consults `resolveColumnInSource` over `realSources`
  to stop an outer binding from capturing a name an inner frame legitimately
  binds. `realSources` already records aliased and unaliased real sources alike,
  so the shadow check widens in step with the binding set — that is the intent,
  and edge cases 1 and 2 below confirm it holds.

## Edge cases already checked (under the trial patch)

Each behaved correctly; keep them as cases in the new spec.

| Shape | Expected | Observed |
| --- | --- | --- |
| `assertion … (select 1 from u b where x < 0)`, drop `t.x` | allowed (bare `x` binds `u`) | allowed |
| `view … select (select max(x) from u b) as m from t`, rename `t.x` | inner ref untouched, view still queryable | correct |
| `view … select n, (select max(x) from t a) as m from u`, rename `t.x` | inner ref rewritten | correct |
| `create view v (p, q) as select * from t a` + assertion on `v`, drop `t.x` | refuse, "breaks it outright" message | correct |
| `view … select x, n from t a join u on a.id = u.id`, rename | rewritten, view queryable | correct |
| `select t.x from t a` | planner rejects at CREATE VIEW (`t.x isn't a column`) | correct — bare name is NOT a qualifier once aliased |
| `with c as (select x from t) select x from c a` (aliased exposing CTE), rename | rewritten, view queryable | correct |

## The test that should outlive the fix

A **generalized** spec over body spellings, not one case per reproduction — new
file `packages/quereus/test/schema/column-scope-body-spellings.spec.ts`, driven
against a real `Database` (mirroring how `table-rename-scope.spec.ts` and
`row-image-context-matrix.spec.ts` drive their matrices, but end-to-end rather
than over the walker's API, because the assertion is *planability*, not text).

One table `t(id, x)`, one list of ways a body can read or republish `x`:
`select x from t`, `select x from t a`, `select *` , `select t.*`, `select a.*`,
`select * from t a`, the same under a join, under a CTE, under an alias that
shadows, plus the currently-unsupported aliased-subquery and function sources
(marked `pending` — see the sibling backlog ticket). Drive each through both
verbs and assert:

- `RENAME COLUMN` leaves every dependent body **planable** — actually run a query
  against it, do not compare body text; and
- `DROP COLUMN` **refuses** whenever a live rule reads the column through that
  spelling, and **accepts** whenever no rule does.

That one generator pins rename/drop parity as a property rather than as paired
hand-written cases, and would have caught every instance here.

## Docs to correct

The known limit is documented in four places and all four become wrong:

- `docs/sql-alter.md` § RENAME COLUMN (the paragraph beginning "Inside dependent
  SELECTs the rewrite follows scope"): "resolve when the renamed table … is in
  the unaliased FROM scope; qualified references resolve via the alias map" —
  restate as *any* FROM source in scope, aliased or not.
- `docs/sql-alter.md` § DROP COLUMN — the whole **"Known limit — an aliased FROM
  source"** paragraph goes; the two bullets above it that say "see the
  aliased-source limit below" need their cross-reference repointed at the
  narrower residual.
- `docs/sql-ddl.md` § 2.6.1 — the matching known-limit bullet, same treatment.

## Out of scope — the residual, re-verified

A star over an **aliased subquery source** or a **function source** still has no
askable column set, so a republication arriving only that way stays invisible to
both verbs. Re-verified on `main` this run:

```sql
create table t (id integer primary key, x integer);
create view v as select * from (select * from t) s;
create view w as select x from v;
alter table t rename column x to z;
select * from w;                  -- ERROR: Column not found: x
```

A star over a **CTE** source (`with c as (select * from t) select * from c`) was
also tested and is **already correct** — the CTE exposure analysis covers it, so
the residual is narrower than the source ticket assumed. Filed as
`bug-column-verbs-blind-to-star-over-subquery-source`; do not fold it in — it
needs recursive column-set inference on the inner body, not a representation fix.
