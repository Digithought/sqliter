# Read the physical estimate, not the logical getter

Both join-ordering rules read the **logical** `estimatedRows` getter on their inputs.
Neither `AliasNode` nor `RetrieveNode` defines that getter — both stamp a row count only
into `computePhysical`, via `physicalSourceRows` — so for any table-backed input the read
is `undefined`, and each rule substitutes a sentinel that makes its own comparison
meaningless.

**`rule-join-greedy-commute`** (~57):

```ts
const leftRows  = node.getLeftSource().estimatedRows ?? Number.POSITIVE_INFINITY;
const rightRows = node.getRightSource().estimatedRows ?? Number.POSITIVE_INFINITY;
// …
const shouldSwap = … || (!rightIsSingleton && !leftIsSingleton && rightRows < leftRows);
```

`Infinity < Infinity` is always false. **The rule's row-count arm has never fired for a
table-backed input.** Its singleton-functional-dependency arm still works, so the rule is
not dead — it simply never does the thing its own comment advertises ("prefer the smaller
input on the left"). The rule already carries a NOTE saying so and pointing at the parent
plan ticket; this ticket is where that NOTE is discharged.

**`rule-quickpick-enumeration`** (~257):

```ts
const sizes = graph.relations.map(r => r.estimatedRows ?? 1e9);
const baseOrder = [...graph.relations.keys()].sort((a, b) => (sizes[a] - sizes[b]));
```

Every relation reads `1e9`, so `baseOrder` — the order the greedy tours start from — is
whatever the input order happened to be. This rule runs in the **Physical** pass, *after*
access-path selection, so the real counts are sitting on `physical.estimatedRows` one node
down and are simply not read.

Verified in-process on the memory backend: two tables of 2,000 and 4,000 rows, joined and
then `analyze`d, written `from entry e join txn t` (4,000-row side named first). The
commute rule leaves the order untouched and the resulting hash join reads all 4,000 rows.
Naming the tables in the other order produces a plan roughly 20x cheaper *by the rule's
own cost model*. Nothing between the two spellings differs except the order the tables
were written in.

Cost is performance only — both rules return identical rows either way.

## Decision

Route both reads through `physicalSourceRows(child.physical, child)`, the helper
`debt-join-rows-from-physical-children` introduced for exactly this producer/consumer
mismatch: physical count first, logical getter as the fallback.

Keep each rule's **absent-estimate posture** unchanged when the helper still returns
`undefined` — that is now a genuine "nobody knows", not an artifact:

- `rule-join-greedy-commute`: an unknown side must not trigger a swap. `Infinity` gives
  that today by accident; keep the behavior deliberately (`if either side is undefined,
  fall through to the singleton arm only`), and say so in a comment. Do **not** substitute
  a default row count — swapping on a fabricated number is worse than not swapping.
- `rule-quickpick-enumeration`: an unknown relation should sort **last** (it may be
  large), which `1e9` approximates. Replace the magic number with a named constant and a
  comment stating the intent, or sort unknowns to the end explicitly.

## Edge cases & interactions

- **Mixed known/unknown sides.** A 10-row known side against an unknown side must not
  swap. Test it.
- **Equal estimates.** `rightRows < leftRows` is strict, so equal counts never swap —
  which keeps the rule deterministic. Preserve that; `<=` would make the rule oscillate
  against any pass that re-runs it.
- **QuickPick's sort stability.** `Array.prototype.sort` is stable in modern engines, but
  the comparator must not return `NaN` for two unknowns. `bug-join-order-depends-on-wall-clock`
  (backlog) already covers this rule's `Date.now()` time limit — do not fix that here, and
  do not let this change make the nondeterminism worse; if a new tie-break is needed, make
  it a deterministic one (relation index), not arrival order.
- **Outer joins.** Commuting a `left join` is not sound. Confirm the rule's existing join-
  type guard runs before the row-count arm and is not weakened by this change.
- **Side effects and correlation.** The rule already declines when either side has side
  effects; the new read must not run before those guards.
- **Three-way and larger joins.** `feat-index-nested-loop-seek-side-election` (complete)
  elects the seek side inside `rule-join-physical-selection`, which does read
  `physicalSourceRows`, so two-table joins already get their orientation decided later.
  The payoff of this ticket is concentrated in three-way and larger joins, where
  QuickPick's base order is what decides. Write the regression test at three tables, not
  two, or it will pass for the wrong reason.
- **Golden plans.** Join order changes are exactly the kind of churn the golden plans
  capture. Re-derive each changed expectation and justify the new shape.
