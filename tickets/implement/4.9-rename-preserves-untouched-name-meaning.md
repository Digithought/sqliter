# A rename must not change what an *untouched* reference resolves to

`rename-rewrite-preserves-what-a-reference-resolves-to` established half an
invariant: after the rename rewrites a reference, re-resolving that reference
must still land on the renamed table, and the rewrite adds a schema qualifier
when it otherwise would not. That covers the references the walk **rewrites**.

This ticket covers the other direction: a rename also *creates* a name, and that
new name can capture a reference the walk never touched.

## What was measured

Ran against the engine as it stands (`node --import ./packages/quereus/register.mjs`,
a scratch script driving `Database.exec` / `Database.eval`):

```sql
create table main.k (id integer primary key, x integer);
insert into main.k values (1, 10);
create table temp.other (id integer primary key, x integer);
insert into temp.other values (99, 999);

-- temp-owned body; bare `k` resolves to main.k, because temp holds no `k`.
create view temp.v as select id, x from k;
select * from temp.v;                   -- [{"id":1,"x":10}]

alter table temp.other rename to k;     -- temp now holds a `k`

select * from temp.v;                   -- [{"id":99,"x":999}]   ← re-bound, silently
```

The stored body is unchanged (`select id, x from k`) — the view's text never
mentions the renamed table, so the walk never matches it. What changed is what
`k` *means* under the view's home schema path `[temp, main]`.

The same rename re-binds an **assertion** the same way. Verified:

```sql
create table main.k (id integer primary key, x integer);
create table temp.other (id integer primary key, x integer);
create assertion temp.a check (not exists (select 1 from k where x > 100));

insert into main.k values (1, 500);   -- ERROR: Integrity assertion failed: temp.a
alter table temp.other rename to k;
insert into main.k values (2, 500);   -- accepted   ← assertion stopped watching main.k
```

And a **materialized view**'s stored body re-binds identically (the already-materialized
rows mask it until the next `refresh materialized view`, which then swaps in the
other table's rows).

`CREATE TABLE` and `DROP TABLE` shift the same references the same way; they have
no propagation pass to hang a fix on and are out of scope. Fixing rename first is
what makes the rule statable.

## The rule

The walk already reports *every* real table reference in a body to a sink, and
the sink already holds both halves of the answer it needs: `TableRenameTarget`
carries `resolve` (the catalog as the body planned it) **and** `resolveAfter`
(the catalog as it will be once the rename lands), both bound to the walked
body's home schema. Today the sink consults `resolveAfter` only for references
it just rewrote.

> Walking a body for a rename, **every** reference must mean after the statement
> exactly what it meant before — whether or not the rename rewrote it.

Mechanically, at `renameTableInAst`'s sink, for a reference that does **not**
match the renamed table:

```
const before = resolve(ref.schema, ref.name);
const after  = resolveAfter(ref.schema, ref.name);
if (before !== after) ref.qualify?.(objectRefKeySchema(before, ref.name.toLowerCase()));
```

`objectRefKeySchema` (in `rename/shared.ts`) exists for exactly this split — it
slices by the known name's length rather than scanning for a separator, because a
schema name may itself contain a dot.

### Why this stays conditional

A qualified reference resolves by passthrough, so `before === after` always and
the branch cannot fire on one. An unqualified reference can only change answer
when it is spelled the **new** name *and* the renamed schema sits earlier on the
body's home path than the schema the before-answer named. Removing the old name
can only push a resolution later, and the references that resolved to the removed
entry are exactly the ones the rewrite already matches — so there is no
freed-name direction to handle. The common no-collision rename therefore still
leaves every body byte-identical, which is what keeps a materialized view's
stored body hash from churning on every unrelated rename.

### Where `qualify` is and is not present

`TableRef.qualify` is already present at exactly the sites that **re-resolve
through the catalog** the next time the body is planned — a DML target, a FROM
table source, a seedless bare column qualifier — and absent where a reference
binds through a FROM frame instead. That is the right split here unchanged: a
column qualifier bound to an unaliased source needs nothing, because the source
itself is reported separately and carries `qualify`; qualifying the source is
what preserves resolution.

### The already-broken body

The resolver answers a total function: a name that exists in no schema on the
path still gets a stable key (the home schema's). So a body naming an object that
does not exist anywhere reads `before = <home>.<name>`, and a rename that
introduces that name in an earlier schema flips `after`. The branch will then
qualify the reference to the home schema — pinning the pre-existing "no such
table" failure rather than letting the body silently start reading the new
arrival. That is the invariant-faithful answer and matches the reasoning already
recorded at the seedless-qualifier emit site ("only ever fires on an
already-unevaluable body … harmless, arguably an improvement"). Say so in a
comment at the new branch rather than adding an existence probe.

## What needs no plumbing

- `propagateTableRename` (`runtime/emit/alter-table.ts:2143`) already walks every
  table, view, assertion and materialized view in **every** schema
  unconditionally, and gates re-registration and persistence on the walker's
  `changed` return. Returning `true` for a body that gained only a qualifier is
  therefore enough to persist it. No caller changes.
- The pre-flight `assertRenameDependentsPersistable` shares the same sink over
  `spineCloneAst` copies, so the new branch is vetted for persistability for free.
- The read-only DROP-guard probe (`tableReferencedInAst`) and the closure
  collector (`collectTableRefsInAst`) are the other two sinks over the SAME
  traversal. Only the rewrite sink's *action* changes — what counts as a
  reference must not.
- The declarative differ's inverse pass (`inverseRenamedViewParts`) passes one
  single-schema resolver as both `resolve` and `resolveAfter`, so the new branch
  is inert there by construction.

## Watch out for

- The differ's existing `NOTE:` at `schema-differ.ts:1475` records that the
  forward rename can leave a qualifier the inverse walk has no declared
  counterpart for, and argues it is unreachable because qualification needs the
  body's home schema to differ from the renamed table's while a diff covers one
  schema at a time. That argument covers this branch too (it likewise needs two
  schemas) — extend the note to say so rather than writing a second one.
- `renameTableInAst` is exported through `schema/rename-rewriter.ts` and called
  from the assertion, view and materialized-view propagation helpers as well as
  the pre-flight. All take the same `TableRenameTarget`; none needs a signature
  change.
