# Why

Nearly every spec under `packages/quereus-store/test/` opens with its own private copy of
the same in-memory `KVStoreProvider` factory — over twenty of them, which is the subject of
`debt-store-test-shared-inmemory-provider` in the backlog. The benchmark work
(`bench-store-workloads`) needs one to measure the persistent code path against, and
writing a twenty-first copy inside `bench/` would be the wrong move.

This ticket creates the shared factory and nothing else. It deliberately does **not** sweep
the twenty existing copies onto it — that stays the backlog ticket's job, and doing it here
would make this a merge-conflict magnet across the whole store test suite.

# Architecture

`createInMemoryProvider(options?)` lands in `packages/quereus-store/src/testing/`, next to
the `createCountingProvider` that the `store-counting-double-extraction` review already
collapsed, and is exported from `@quereus/store/testing`.

It must match that sibling's settled conventions, because they are the same conventions and
a divergence here re-opens a question that has been answered:

- Store names come from `buildDataStoreName` / `buildIndexStoreName` and the reserved
  `CATALOG_STORE_NAME` / `STATS_STORE_NAME` constants — never hand-composed template
  strings, which drop the builders' lowercasing and reach a store no real backend would
  have used.
- `getStatsStore` returns ONE unified `__stats__` store for every table, as the
  `KVStoreProvider` interface specifies (its schema/table arguments are documented as
  ignored). The per-table `schema.table.__stats__` spelling most local copies use is the
  accidental variant.
- `options.costProfile` is spread in **only when present**, so a provider that declares
  nothing has no such property at all. `test/cost-profile.spec.ts` (lines ~57-60) and
  `test/key-set-seek-store.spec.ts` both depend on exactly that shape, and the
  "declares nothing plans byte-identically to before" property is what it pins.

## What it has that the counting sibling deliberately lacks

`createCountingProvider` carries a `NOTE:` saying it implements neither `deleteIndexStore`
nor `deleteTableStores`. This one **implements both, and they ERASE** rather than dropping
the handle: a caller still holding a live handle to a dropped store must see it empty, which
removing the map entry alone would not accomplish. The benchmark suite's index-build
workload drops and recreates an index on every iteration and would otherwise read the
dropped index's entries back.

There is one trap worth stating up front, found while reading the code:

- `InMemoryKVStore.clear()` calls `checkOpen()` and **throws on a closed store**, and
  `InMemoryKVStore.close()` both marks the store closed and drops its entries. The reclaim
  battery's case *"erases a store whose handle the caller already closed"* exercises exactly
  that, and it is not exotic — it is the order every `drop index` actually takes
  (`StoreModuleIndex.tearDownIndexStore` closes the cached handle first, then asks the
  provider to delete).
- There is no public accessor on `InMemoryKVStore` saying whether it is closed, so the
  factory needs one of: a small `get isClosed()` added to `memory-store.ts`, or its own
  bookkeeping. Pick one deliberately and say why in a comment — do not reach for a bare
  `try { clear() } catch {}`, which the project's exception rules forbid.
- The shape that satisfies the battery: a store that was never created is a **no-op**
  (not an error); a live store is **cleared** (live handles see the erase); a closed store
  has already dropped its bytes, so what remains is to let the name re-open — dropping the
  map entry is that re-open.
- `deleteTableStores` must **not** touch the unified `__stats__` store. The interface says
  so explicitly: a table's row count lives as one ENTRY there, and removing that entry is
  the caller's business, not a store deletion.

`renameTableStores` is deliberately out of scope — `StoreModule` has a copy fallback for a
provider without the hook (`test/rename-store-copy-fallback.spec.ts`), and nothing in the
benchmark path renames. The eventual sweep will need it; note it rather than build it.

# Tests

New `packages/quereus-store/test/memory-provider.spec.ts`:

- Registers `runStoreNameDistinctness` and `runStoreReclaimConformance` against the new
  factory. Both take the same `KVProviderLifecycle` adapter (`{ open, teardown }`), so one
  closure serves both — `packages/quereus-plugin-leveldb/test/conformance.spec.ts` lines
  ~165-170 is the worked precedent. The reclaim battery is what pins the erase semantics
  above; note that it *prints a skip* rather than failing when a delete hook is missing, so
  read its output and confirm both hooks were actually exercised.
- A case that `costProfile` is absent — `'costProfile' in provider === false` — both when
  the factory is called with no argument and when called with `{}`. A truthiness check is
  not enough; the property must not exist.
- A case that a declared `costProfile` is surfaced.

`yarn workspace @quereus/store test` and `yarn workspace @quereus/store typecheck` clean.
