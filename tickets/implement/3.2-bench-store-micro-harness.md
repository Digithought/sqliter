# Why

The micro-benchmark work (now `bench-store-micro-keys` and `bench-store-micro-paths`) wants
to price the storage layer's hot paths individually. Three things block it, and all three
are shared plumbing rather than benchmark content — so they land first, on their own, where
they can be reviewed as API changes instead of as benchmark noise.

# What blocks the micro suite

## 1. `ROW_RESOLUTION_BATCH` is not a public export

The upstream ticket asserted it was. It is not. It is declared at
`packages/quereus-store/src/common/store-table-scan.ts:83`
(`export const ROW_RESOLUTION_BATCH = 256`), and
`packages/quereus-store/src/common/index.ts` — which is everything `@quereus/store`
re-exports — does not name it.

The micro suite must derive its expected round-trip counts from the constant rather than
writing `256`, so a change to the constant moves the expectation with it instead of turning
every sizing comment into a lie. That means the constant has to be reachable from outside
the package.

Add it as a one-line additive re-export. Nothing else in `store-table-scan.ts` needs to
become public — `StoreTableScan` itself is already reachable transitively through
`StoreTable`.

## 2. The benchmark harness has exactly one door into `@quereus/store`, and it is too narrow

`packages/quereus/bench/lib/store-counters.mjs` holds the harness's single dynamic import
of the store package (`loadStoreModules`, cached per process). Its file header explains why
there must be exactly one: the parent process imports every suite file just to enumerate
benchmark names, so a static import of `@quereus/store` anywhere reachable from a suite
would let an unbuilt `packages/quereus-store/dist` kill the whole `yarn bench` run — parser
and planner suites included.

Today that door resolves exactly three names: `createIsolatedStoreModule`,
`createInMemoryProvider`, `createCountingProvider`. The micro suite additionally needs the
key-encoding and key-building functions (`encodeValue`, `encodeCompositeKey`,
`decodeCompositeKey`, `buildDataKey`, `buildIndexKey`,
`BUILTIN_KEY_NORMALIZER_RESOLVER` — all already public) and the batch constant from item 1.

Two changes:

- **Widen the resolved set and expose it**, so a suite can reach the store's encoding and
  key-building API without opening a second import site. Keep the existing shape of the
  check that every resolved name is actually callable (and, for the constant, a number):
  that check is what turns "this checkout cannot run the store rows" into a stated skip
  reason rather than a `... is not a function` thrown inside `setup`.
- **Expose the provider on the plain store-database handle.** `openStoreDatabase()`
  currently returns `{ db, close }`. A benchmark that needs to assert on physical store
  contents — the index-build one, see `bench-store-micro-paths` — has no way to reach the
  provider its database was built over. Adding it to the handle is additive and costs
  nothing.

## 3. `CountingKVStore` counts reads only, and the commit benchmark asks a write question

`store-counters.mjs`'s own header already records the decision and its trigger:

> NOTE: no write counters, because `CountingKVStore` has none. If a mutation regression
> ever needs pinning down to "the store now issues N more `set` calls per row", the fix is
> to add `setCount`/`deleteCount`/`batchCalls` to `CountingKVStore` in
> `@quereus/store/testing` (additive — its existing specs assert on the read counters only)
> and surface them here, not to work around it in a benchmark.

The commit benchmark trips that trigger exactly. Its stated measurement is "does committing
N queued operations cost a number of storage round trips that is flat per commit, or one
per operation" — a claim about writes. It cannot be recovered from the read counters by
picking a cleverer workload either: any workload that queues N operations must touch N
rows, so the read counts are linear in N whatever the commit path does. Without write
counters that benchmark's counter block describes only the reads its writes provoked, and
says nothing about the commit.

### What adding them involves

`CountingKVStore` extends `DelegatingKVStore`, whose `batch()` forwards straight to the
inner store — so the `WriteBatch` a caller gets back is the inner one, and its
`put`/`delete`/`write` never pass through the wrapper. Counting the commit path therefore
needs `batch()` overridden to hand back a counting `WriteBatch` wrapper, not merely new
fields on the store.

`WriteBatch` (`packages/quereus-store/src/common/kv-store.ts`) is four methods:
`put(key, value)`, `delete(key)`, `write()`, `clear()`.

The counts worth having, named for what they mean rather than after the method that
produced them, matching how the four read counters are already named:

| Field | Means |
| --- | --- |
| direct puts / deletes | writes issued one at a time, outside any batch |
| batch round trips | `write()` calls — the write-side round-trip count, the number that must stay flat per commit |
| batch operations | put/delete operations those `write()` calls carried |

Then surface them in `readStoreCounters` in `store-counters.mjs` alongside the four read
counts, and update `docs/benchmarking.md` section "Storage round trips: what a `store-mem`
row counts" — including its "**Reads only.**" paragraph, which this makes wrong.

# Edge cases & interactions

- **`reset()` must zero the new fields too.** Note that
  `packages/quereus-store/test/key-set-seek-store.spec.ts` (~line 403) zeroes counters by
  assigning the fields directly rather than calling `reset()` — exactly the place a newly
  added counter is missed. Prefer pointing those call sites at `reset()`.
- **Existing specs assert on the read counters only** and must keep passing untouched:
  `packages/quereus-store/test/index-scan-batching.spec.ts`,
  `test/bounded-iterate.spec.ts`, `test/key-set-seek-store.spec.ts`.
- **Every existing `@store-mem` benchmark's counter block gains fields.** Comparing a run
  made after this change against a results file written before it reports the new paths as
  appeared-path counter changes on all nineteen store rows. That is one-time report noise,
  not a failure: counter deltas never contribute to the exit code (docs/benchmarking.md
  section "Exit-code contract"), and `bench/results/` is gitignored. Say so in the handoff
  so a reviewer does not read it as a regression.
- **`createCountingProvider` implements neither `deleteIndexStore` nor
  `deleteTableStores`** — a deliberate, documented NOTE on that function. Leave it that
  way; the micro suite's `counters()` passes are designed around it. Its sibling
  `createInMemoryProvider` does implement both, and erases rather than merely dropping the
  map entry.

# Tests

- `yarn workspace @quereus/store test` passes, with the three read-counter specs above
  untouched.
- A new spec pinning the write counters: a batched commit advances the batch-round-trip
  count by one and the batch-operation count by the number of queued operations; a direct
  `put` advances the direct-put count and neither batch count.
- `yarn build` succeeds — the new re-export must not create an import cycle.
- `yarn bench --filter @store-mem` still runs, and its counter blocks now carry the write
  fields.
