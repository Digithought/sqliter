# `schemaMatches` is not name resolution

Every match in `rename-rewriter.ts` is gated by one helper:

```ts
const schemaMatches = (nodeSchema: string | undefined, defaultSchema: string): boolean =>
    nodeSchema === undefined || eq(nodeSchema, defaultSchema);
```

An **unqualified** name in a stored body matches whatever `defaultSchema` the
caller happened to pass. That is not how the body is planned. A view /
materialized-view / assertion body resolves its unqualified names against the
**owning object's home schema path** — `Database._homeSchemaPath(homeSchema)` =
`[homeSchema, ...session default path]` — and is planned that way at create time,
at every reference, and on refresh (`test/view-home-schema.spec.ts`,
`test/assertion-home-schema.spec.ts`).

Two consequences, both live:

- **False positive.** Rewriting a body that lives in schema `A` while renaming
  `temp.t` passes `defaultSchema = 'temp'`. A bare `from t` in that body, which
  actually resolves to `A.t`, matches and is rewritten. The current code avoids
  this only because the view / MV / assertion loops are gated to the renamed
  object's own schema — a gate that exists *because* the matcher is wrong, and
  that is itself the bug `bug-rename-not-propagated-across-schemas` has to remove.
- **False negative.** A body in schema `A` naming `temp.t` explicitly, walked with
  `defaultSchema = 'A'`, does not match. `rewriteTableForTableRename` /
  `rewriteTableForColumnRename` already run over **every** schema's tables, so this
  one is reachable today: a CHECK expression or column DEFAULT in schema `A`
  with a subquery reading `temp.t` is missed by the rename.

The column walker has the same defect in `collectFromBindings`, which records a
FROM source's schema as `ts.table.schema ?? state.defaultSchema` and adds a
source to `frame.unaliased` when the schema is absent — so an unqualified `from t`
binds as the renamed table regardless of which schema it really resolves to.

# Design

Replace `defaultSchema` equality with **resolution against a home schema path**,
using a catalog callback so `rename-rewriter.ts` stays free of catalog imports —
the pattern `ResolveColumnInSource` / `buildColumnSourceResolver` already
established, and the new resolver belongs beside it.

## Interface

```ts
/** Canonical `<schema>.<name>` key (both lowercase) for a table / view / MV
 *  reference as written in a stored body, or undefined when nothing in the
 *  home path carries the name. */
export type ResolveObjectRef = (schema: string | undefined, name: string) => string | undefined;
```

Built in `schema/object-ref-resolver.ts` (new, next to `column-source-resolver.ts`):

```ts
export function buildObjectRefResolver(db: Database, homeSchemaName: string): ResolveObjectRef;
```

- Qualified (`schema` present) → `` `${schema.toLowerCase()}.${name.toLowerCase()}` ``
  with no catalog lookup. A qualified name means what it says even if the object
  does not exist (it may be the one about to be created, or the one just renamed
  away).
- Unqualified → first schema in `db._homeSchemaPath(homeSchemaName)` that holds a
  **table or view** of that name; the catalog lookup is `Schema.getTable` /
  `Schema.getView` (a materialized view is a table). Miss in every schema → fall
  back to the home schema itself, so a body naming an object that does not exist
  still gets a stable key rather than `undefined`. Reserve `undefined` for the
  case the resolver cannot be consulted at all.

## Threading it

`renameTableInAst`, `tableReferencedInAst`, `renameColumnInAst`,
`renameColumnInCheckExpression`, `columnReferencedInAst`,
`columnReferencedInCheckExpression` and the four `rename*In*` collection helpers
take the resolver plus the **target key** (`` `${schema}.${name}` `` of the object
being renamed / probed) in place of `defaultSchemaName`. A match is
`resolve(node.schema, node.name) === targetKey`.

In the column walker, `collectFromBindings` resolves each FROM source the same
way and compares the resolved key, rather than comparing bare names against
`state.tableName`. `frame.realSources` already carries `{schema, name}`; it
becomes the resolved key.

## Snapshot discipline — resolve before mutating

The resolver reads the **live** catalog, and rename propagation runs *after* the
catalog swap: by then the old name resolves to nothing and the new one to the
renamed table. So every caller must build its resolver and resolve its target key
**before the first catalog mutation of the statement**, and pass the same
resolver through the whole statement. State this in the resolver's doc comment;
it is the single most likely way to get this wrong.

The unqualified fallback above ("miss → home schema") is what keeps a
post-mutation resolve of a vanished old name from silently becoming `undefined`.

## Scope of this ticket

Mechanism only. The view / MV / assertion loops stay gated to the renamed
object's own schema — widening them is `bug-rename-not-propagated-across-schemas`.
What *does* change behavior here is the table loop, which already walks every
schema: cross-schema CHECK / DEFAULT / generated / partial-index references start
being followed correctly, in both directions.

# Edge cases & interactions

- **Resolver built after mutation.** The failure is silent (nothing matches, the
  rename propagates nowhere). Add a test that renames and then asserts a dependent
  was rewritten, so a regression here fails loudly.
- **`temp` in the default path.** `_homeSchemaPath` dedupes the home schema out of
  the default path; a home of `temp` must not produce `['temp','main','temp']`.
- **Session `schema_path` changed between create and rename.** The resolver reads
  the path at call time, so a body created under one path can resolve differently
  later. That is already true of the planner (`_homeSchemaPath` re-reads the
  option on every body plan) — match it, do not invent a stored path.
- **Object that does not exist yet.** A view body may name a table created later
  (or dropped since). The miss → home-schema fallback must not throw.
- **Probe / rewrite equivalence.** `tableReferencedInAst` and
  `columnReferencedInAst` must resolve identically to their rewriting twins, or
  the DROP guards start refusing a different set than the rename follows.
- **Idempotence.** Second calls with the same pair must still find nothing.
- **The renamed table itself.** `rewriteTableForColumnRename`'s `isRenamedTable`
  check becomes a key comparison; a same-named table in another schema must not
  take the seeded branch.
- **Aliased cross-schema source.** `from temp.t z` then `z.x` — the alias map must
  store the resolved key, not the bare name.
- **Performance.** The resolver runs per reference. Its lookups are `Map.get` over
  a handful of schemas; if a DDL-heavy workload ever shows it hot, memoize per
  `(schema, name)` inside one resolver instance. Record that as a `NOTE:` at the
  builder, not a ticket.

# Second arm — collapse the duplicated table-rewrite loop (added by the review of `bug-table-rename-rewrites-cte-references`)

Same site, different defect, and this ticket already rewrites the signature of
every call listed above — so fold it in rather than churning the file twice.

"Rewrite a table's own definition for a table rename" is written **twice**:

- `rewriteTableForTableRename` in `runtime/emit/alter-table.ts` (~l.2188) loops over
  `checkConstraints` and `indexes` by hand, calling `renameTableInAst` per item;
- `rewriteTable` in `packages/quereus-store/src/common/store-module-rename.ts`
  (~l.213) calls the three collection helpers
  (`renameTableInIndexPredicates` / `renameTableInCheckConstraints` /
  `renameTableInColumnExpressions`) that wrap exactly those loops.

The two must agree on **which arms get a written-row context**, and nothing makes
them. Concrete evidence: adding `rowImageContext` had to be applied to the CHECK
helper *and*, separately, to the hand-rolled CHECK loop — miss one and a bare
`new.a` in a CHECK is silently rewritten on one path and preserved on the other,
with no test that compares the paths.

The invariant that retires the class: the per-arm row-context decision must exist
in exactly one place — the collection helpers — and `rewriteTableForTableRename`
must call them rather than re-deriving the loop. It already can: each helper
returns "did anything change", which is the only thing the hand-rolled loops
compute beyond the rewrite, and the function's own comment at the column arm
records that the per-item `{...cc}` / `{...idx}` shallow copies achieve nothing
(the ASTs are mutated in place, so `oldObject` shares them either way; flipping
`changed` is what re-registers the table). The FK loop stays as it is — it maps a
field rather than walking an AST.

Verify with a test that renames a table named `new` and asserts the engine path
and the store path leave the CHECK's row image alone identically — the pair that
currently has to be kept in step by hand.
