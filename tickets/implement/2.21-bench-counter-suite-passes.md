# Where this picks up

The harness half of `bench-counter-reporting` has landed and is working end to end. What
is left is declaring the per-benchmark `counters()` passes and proving they are stable.

## What already works (do not rebuild it)

- `bench/lib/counters.mjs` — helpers a `counters()` pass calls:
  - `snapshotStatement(db, sql, params?)` — turns metrics on, prepares, **fully drains**,
    returns the `WorkCounterSnapshot`, always finalizes the statement.
  - `snapshotStatements(db, { name: sql, … })` — several statements as one named bag.
    Needed because instruction keys are addresses *within one program*, so `r#0` of two
    different statements are different instructions with the same key and must never be
    summed.
  - `snapshotPlanShape(db, sql)` — prepare-only; returns `{ nodeCount, nodeTypes }`.
- `bench/lib/discover.mjs` — the `Benchmark` typedef documents `counters`, and `loadSuite`
  rejects a `counters` that is not a function.
- `bench/child.mjs` — runs `counters()` after sampling and before `teardown`, in its own
  `counters` failure phase, JSON-round-trips the return value, and ships it over IPC. A
  `counters()` that throws fails the benchmark loudly.
- `bench/run.mjs` — carries the block into the results JSON, adds a `Counters` column, a
  counter-change block under the table, a one-line counter summary, a `--no-counters`
  flag, and a `counters_collected` field in the results file.
- `bench/lib/compare.mjs` — `flattenCounters` / `diffCounters` / the per-benchmark counter
  verdict (`same` / `changed` / `new` / `dropped` / `none` / `skipped`). Exact integers,
  no tolerance. Never contributes to the exit code.

Verified by running `execution/full-scan-10k` twice and comparing:
`{instructionExecutions: 2, rowsOut: 20000, queryCalls: 1, rowsScanned: 10000,
updateCalls: 0}`, identical across two separate child processes, reported as
`Counters: same`.

## What to add

Follow the shape already in `execution.bench.mjs`:

```js
counters() { return snapshotStatement(db, 'select * from bench_t'); },
```

- **execution (14 remaining)** — each `fn` runs one query; the pass runs the same SQL
  through `snapshotStatement` against the `db` that `setup` built.
- **mutation (4)** — `update-where-1k` can use the `setup` database and
  `snapshotStatements` for its apply-then-reverse pair. `bulk-insert-10k`,
  `single-row-insert-1k` and `delete-where-100` build their own `Database` inside `fn`,
  so their `counters()` must build one too, populate it, and close it. For the two
  insert benchmarks, consider snapshotting the FIRST and the LAST batch as two named
  entries: work that grows with table size (index maintenance) is invisible in a
  first-batch-only snapshot.
- **planner (4)** — `snapshotPlanShape` only. These prepare and finalize; nothing
  executes, so there are no row or table counts. This is a real signal in its own right:
  it is the pass that would catch a rule regression turning a hash join back into a
  nested loop.
- **parser (4)** — none. They call `parser.parseAll` directly and never build a plan or a
  runtime, so there is nothing to count. Add a comment in the file saying that, so the
  next reader does not treat the absence as an oversight.

## Acceptance: stability, measured not assumed

Run the whole suite twice and diff the `counters` blocks of the two results files. Every
counter must be identical. The harness already runs each benchmark in its own child
process, so a suite-to-suite diff **is** the separate-process leg of the stability check.

```
node bench/run.mjs                              # writes results file A
node bench/run.mjs --baseline latest            # compares B against A
```

The second run's `Counters` column must read `same` for every benchmark, and the
work-counter-changes block must not print at all. Record the exact commands and the
outcome in the handoff.

**Any benchmark whose counters differ between the two runs gets its `counters()` removed,
with a comment saying which count moved and why it could not be stabilized.** A counter
that varies is worse than no counter, because the downstream regression-gate ticket will
fail builds over these numbers.

## Also measure

The counters pass adds one extra untimed execution per benchmark. Compare
`wall_clock_ms` between a `node bench/run.mjs` run and a `node bench/run.mjs
--no-counters` run and report the delta in the handoff. `--no-counters` already exists;
this is a measurement, not a feature.
