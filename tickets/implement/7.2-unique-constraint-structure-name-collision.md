# Two UNIQUE constraints must not derive one backing structure name

## Background

Every `UNIQUE` rule is enforced through a hidden backing structure. Its name is the
constraint's own name when it has one, and `_uc_<columns joined by _>` when it does not
(`implicitIndexNameForColumns` in `schema/catalog.ts` is the single spelling of that
rule).

Nothing stops two rules on one table deriving the *same* name. Two spellings reach it:

```sql
-- 1. a constraint name written with the engine's reserved `_uc_` prefix
create table t (id integer primary key, c integer, b integer,
                constraint _uc_c unique (b),
                unique (c));                 -- also derives `_uc_c`

-- 2. no reserved prefix at all — `_`-joined auto-names colliding on ordinary names
create table t (id integer primary key, a_b integer, a integer, b integer,
                unique (a_b),                -- derives `_uc_a_b`
                unique (a, b));              -- also derives `_uc_a_b`
```

Both are accepted. On the memory backend the second constraint then **adopts** the
structure built for the first, so it is enforced by a structure keyed on the *other*
constraint's columns — and silently accepts duplicates it should reject. On the store
backend the serving structure is resolved by columns rather than by name, so enforcement
falls back to a correct full scan; the declaration is merely nonsense there rather than
wrong.

`ALTER TABLE` refuses the same declaration — but only on the memory backend, and only by
accident: `assertUniqueConstraintIndexNameFree` compares the prospective name against
`tableSchema.indexes`, and the memory module happens to materialize a constraint's
structure there while the store module does not. The NOTE on
`findIndexShadowedByUniqueConstraint` states this and names the fix:

> If a caller ever needs the two to agree there, compare against the derived names of the
> table's other UNIQUE constraints as well, not just `.indexes`.

That is this ticket.

## The change

### 1. A backend-independent comparison, in `schema/catalog.ts`

Add a sibling to `findIndexShadowedByUniqueConstraint` that searches
`tableSchema.uniqueConstraints` instead of `tableSchema.indexes`, comparing derived
structure names case-insensitively (every other index-name comparison in the engine folds
case). Skip any constraint carrying `derivedFromIndex` — its structure *is* that index, so
it is already covered by the `.indexes` arm and matching it here would report the same
collision twice under two different messages.

Wire it into `assertUniqueConstraintIndexNameFree` **before** the existing `.indexes`
comparison, so a collision that both arms can see reports identically on memory and store.
Verified safe: every existing assertion on the `would collide with existing index '<name>'`
text (`test/alter-drop-rename-constraint.spec.ts` ~113/~137/~171,
`test/logic/10.5.7-implicit-unique-index-lifecycle.sqllogic`,
`packages/quereus-store/test/index-persistence.spec.ts` ~904/~999) is a collision with a
**user-created index**, which only the `.indexes` arm sees. Re-confirm this before
committing rather than trusting the list.

Message for the new arm — parallel to the existing one, but naming a constraint:

```
Cannot <operation>: its backing structure '<name>' would collide with the backing
structure of the UNIQUE constraint on (<columns>) on the same table. Rename the constraint.
```

### 2. The `CREATE TABLE` form

`CREATE TABLE` holds a whole constraint list at once and has no table to compare against,
so it needs the pairwise form: one pass over the built `uniqueConstraints`, deriving each
structure name and refusing the first repeat. Export it from `schema/catalog.ts` next to
`assertNoDuplicateUniqueConstraints`, and call it from the `createTable` guard block
**immediately after** `assertNoDuplicateUniqueConstraints` — a genuine duplicate must keep
producing the constraint-worded duplicate message rather than a structure-name one — and
**before `module.create`**, so a refusal leaves no storage behind.

At `CREATE TABLE` the table has no indexes at all (`AST.CreateTableStmt` carries no index
declarations), so the pairwise constraint comparison is the whole check there.

Message:

```
Cannot create table 't': the UNIQUE constraint '<a>' and the UNIQUE constraint on (<cols>)
both derive backing structure name '<name>'. Rename one of them.
```

Name each side the way the user wrote it — by constraint name when it has one, by column
list when it does not.

### 3. Where it must NOT go

Not on the import / rehydrate path (`importTable`, `importDDL`) — a catalog written before
this guard must still open, and `MemoryTableManager.ensureUniqueConstraintIndexes` keeps
its existing adoption behaviour as damage limitation for exactly those. Same placement
rationale the neighbouring `assertNoDuplicateUniqueConstraints` guard already documents.

## Tests

Two tests in `packages/quereus/test/index-ddl-roundtrip.spec.ts` pin today's behaviour and
must flip. Both carry a NOTE saying the shape is asserted "so a future fix visibly flips
it" and referencing a backlog slug that no longer exists (it was folded into this family) —
remove those references while flipping:

- `'two UNIQUE constraints deriving one structure name leave ONE index entry, not two'`
  (~241) → the `create table` is refused; nothing is registered.
- `'the same collision is reachable with ordinary column names'` (~281) → same.

Add, in `test/logic/10.5.7-implicit-unique-index-lifecycle.sqllogic` (it runs on **both**
backends deliberately, which is the point of this ticket):

- `create table` with the reserved-`_uc_`-prefix collision → `-- error:`
- `create table` with the ordinary-name `_uc_a_b` collision → `-- error:`
- `alter table … add constraint` producing a collision with another **constraint's**
  structure (not an index) → `-- error:`, same message on both backends
- `alter table … add column c text unique` where `_uc_c` is another constraint's derived
  name → `-- error:`
- `alter table … rename column` that makes two constraints derive one name → `-- error:`,
  and nothing moved
- **negative controls that must keep working:** two differently-named UNIQUEs over the same
  columns; a named UNIQUE beside an unnamed one over the same columns; a UNIQUE whose
  columns are already covered by a user index of a *different* name (structure reuse
  matches on columns, not names); a constraint derived from `create unique index`.

Run: `yarn test`, then `yarn test:store` for this one — the whole point is that both
backends now answer identically.

## Edge cases & interactions

- **Case folding.** `constraint _UC_C unique (b)` beside `unique (c)` must be refused;
  `_uc_` is not case-sensitive anywhere else in the engine.
- **Column names containing `_`.** The `_`-joined auto-name is ambiguous by construction
  (`(a_b)` vs `(a, b)`). This guard refuses the collision rather than disambiguating the
  name — do **not** change the naming rule, it is persisted in existing catalogs and
  mirrored by `quereus-store`'s `implicitUniqueIndexName` and
  `MemoryTableManager.implicitIndexNameFor`.
- **`derivedFromIndex` constraints** (synthesized from `CREATE UNIQUE INDEX`) must be
  skipped by the new arm, or every such constraint reports a collision with its own index.
- **Partial UNIQUE constraints** (`predicate` set) are genuinely different rules from a
  full one over the same columns, but their structures still cannot share a name — the
  collision is about the name, not the rule. Refuse, and cover it.
- **PRIMARY KEY.** The primary structure derives no `_uc_` name and takes no part.
- **Legacy catalogs.** A store catalog written before this guard, containing a colliding
  pair, must still reopen and must still behave as it does today. Add a test that goes
  through `importDDL` rather than `create table`.
- **`apply schema`.** Runs through `createTable`, so it inherits the refusal; a declaration
  block carrying the collision fails the migration rather than deploying it.
- **Sibling tickets** `7.1` and `7.3` add calls to the same `createTable` guard block. If
  one has landed, insert alongside it; the ordering constraint that matters is only
  "after `assertNoDuplicateUniqueConstraints`, before `module.create`".
