# The guard checks one hop, in one schema

An integrity assertion is the highest-blast-radius object in the catalog:
`AssertionEvaluator` recompiles **every** live assertion on any commit that
touched any table, so one body that no longer plans makes every write to the
whole database fail. `assertNoAssertionDependsOn` exists to prevent that by
refusing a drop, and it refuses only when an assertion in the dropped object's
**own schema** names that object **directly**. Two references defeat it.

## Miss 1 — the assertion reaches the object through a view

```sql
create table t (x integer primary key);
create view v as select * from t;
create assertion av check (not exists (select 1 from v where x < 0));
create table other (i integer primary key);

drop table t;                     -- accepted: the assertion names `v`, not `t`
insert into other values (1);
-- Table 't' not found in schema path: main
```

`other` has nothing to do with `t`, and the error names neither the assertion
nor the view.

## Miss 2 — the assertion lives in another schema

```sql
create table main.t (x integer primary key);
create assertion temp.at check (not exists (select 1 from main.t where x < 0));
drop table main.t;                -- accepted: the loop only reads main's assertions
insert into main.other values (1);
-- Table not found: main.t
```

## Both misses repeat under DROP COLUMN

`assertNoAssertionNamesColumn` carries the identical pair, verified:

```sql
create view v as select id, x from t;
create assertion a3 check (not exists (select 1 from v where x < 0));
alter table t drop column x;      -- accepted; every later write fails
```

and an assertion in `temp` naming `main.t`'s column is likewise not consulted.

## Root cause

Both guards ask *"does this one body mention this one object?"* when the
question is *"can this assertion reach this object?"*. The reach is a closure
over stored bodies: an assertion body names views and materialized views, whose
bodies name further views and base tables.

### The primitive that is missing

`walkTableRefs` in `schema/rename/table-rename.ts` is already sink-based — both
`renameTableInAst` (rewrite sink) and `tableReferencedInAst` (stop-at-first-match
probe) are thin wrappers. A third sink is a few lines:

```ts
/** Every real (non-shadowed) table/view reference in `node`, as canonical `<schema>.<name>` keys. */
export function collectTableRefsInAst(
    node: AST.AstNode | undefined,
    resolve: ResolveObjectRef,
): Set<string>;
```

Same traversal ⇒ same scope-awareness for free: a body whose `with t as (…)`
merely shadows the name still does not count as a reference, and a `new.` /
`old.` row-image qualifier still does not, so the closure cannot false-refuse
where the direct probe already does not.

### The closure

A new `packages/quereus/src/schema/object-dependency-closure.ts`:

```ts
/**
 * Every object key reachable from `body` through stored view / materialized-view
 * bodies, plus the bodies traversed to get there. Each body is walked under ITS
 * OWN home-schema resolver, so an unqualified name means what the planner would
 * make of it in that body.
 */
export interface ReachedObject {
    /** Canonical `<schema>.<name>` key of the object reached. */
    key: string;
    /** The stored body that named it, and that body's owner key — for the error message. */
    viaKey: string;
    viaBody: AST.QueryExpr | AST.Expression;
    viaResolve: ResolveObjectRef;
}

export function reachableObjects(db: Database, from: AST.Expression, homeSchema: string): ReachedObject[];
```

Breadth-first from the assertion body over one `snapshotObjectRefResolvers(db)`,
expanding a reached key only when it names a view (`schema.getView`) or a
maintained table (`isMaintainedTable` ⇒ `derivation.selectAst`), with a visited
set of keys so a malformed or mutually-referencing catalog terminates.

### What each guard then does

- **Table verb** (`assertNoAssertionDependsOn`): iterate assertions in **every**
  schema; refuse when the dropped object's key is in that assertion's reach.
- **Column verb** (`assertNoAssertionNamesColumn`): iterate assertions in every
  schema; refuse when **any body in the reach** — the assertion's own body
  included — names `<table>.<column>` per `columnReferencedInAst`. No column
  lineage through the view's projection is needed, and none should be built: if
  no body in the chain names the column, the assertion could not have been
  reading it in the first place.

## Edge cases & interactions

- **Shadowed names must still not count.** `create assertion a check (… with t
  as (select 1) select … from t …)` must not block `drop table t`. The
  scope-aware traversal gives this; a test must pin it, because a
  collect-everything sink is exactly where that property gets lost.
- **Cross-schema resolution in both directions.** An assertion in `temp` naming
  bare `t` where `temp.t` exists must not block dropping `main.t`; naming
  `main.t` explicitly must. An assertion in `temp` naming bare `t` where `temp`
  has no `t` resolves down the home path to `main.t` and **must** block.
- **Chain depth ≥ 2.** assertion → `v2` → `v1` → `t`. One-hop expansion is the
  natural under-fix; test three levels.
- **A materialized view in the chain**, and a chain that ends at an MV being
  dropped (`emitDropMaterializedView` is a third call site).
- **A view that is itself dropped.** `drop view v` while an assertion reaches
  `v` only through `v2` must refuse too — same closure, different target key.
- **A body naming a nonexistent object.** The resolver's miss→home fallback
  keys it stably; the closure must not throw or loop on it.
- **Assertion with no `checkExpression`** is skipped today (unreachable —
  there is no assertion persistence path). Keep the skip and its comment.
- **Error message.** Must name the assertion, the dropped object, and the path
  when it is indirect — `assertion 'av' reaches it through view 'v'` — otherwise
  the user is told to fix an assertion whose body does not mention the object.
  Include the assertion's schema when it differs from the dropped object's.
- **Over-refusal is the risk of this change.** It turns previously-accepted
  drops into errors. Run the full suite and read every new failure as a
  question: was that drop legitimately breaking an assertion, or is the closure
  too greedy? Adjust the test, not the guard, only when the former.
- **Ordering vs the other drop guards.** Run before any module call, as today.
- **Cost.** One catalog snapshot plus a BFS per drop, over already-parsed ASTs.
  DDL is rare; record a `NOTE:` at the site rather than caching, and say what
  would make caching worth it (a database with many assertions over deep view
  chains).

## Expected test outcomes

- `drop table t` with `av` reaching `t` through `v` → refused, message naming
  `av` and `v`; `insert into other` still works.
- Three-level chain refuses; `drop assertion av` then lets the drop through.
- `drop table main.t` with a `temp`-owned assertion naming `main.t` → refused.
- An assertion whose `with t as (…)` shadows the name does **not** block.
- `alter table t drop column x` with `a3` reaching `t` through `v` → refused;
  same for a `temp`-owned assertion naming `main.t`'s column.
- `drop view v` while an assertion reaches `v` through `v2` → refused.
