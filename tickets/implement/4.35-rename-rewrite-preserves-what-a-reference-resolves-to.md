# The rewrite must preserve what a reference resolves to

A stored body (a view, a materialized view, an integrity assertion, a CHECK, a
column DEFAULT) may name a table without a schema qualifier. Such a name resolves
against the body's own schema first and then the session search path, so a body
living in `temp` can legitimately mean a table in `main` — `temp` simply has no
table of that name.

When that table is renamed, `renameTableInAst` rewrites the reference **in
place**: it swaps the name and leaves the reference unqualified. The new name is
resolved from scratch the next time the body is planned, and by then the answer
may be a different table. If an earlier schema on the body's home path holds a
table with the *new* name, the reference now points there — no error, no warning.

The reference used to resolve to the renamed object. After the rewrite it does
not. That is the whole defect: **the rewrite is not required to preserve what the
reference resolves to.**

## Reproduction (re-verified at `b8760bc9`, current HEAD)

Setup shared by all three: `main.t` is renamed, `temp.t2` already exists, and a
`temp`-owned body reads a bare `t` (meaning `main.t`, because `temp` holds no `t`).

| body | after `alter table main.t rename to t2` | observed |
| --- | --- | --- |
| `create view temp.vt as select id, x from t` | body reads bare `t2` | `select * from temp.vt` → `{id:99, x:999}` (temp.t2's row) instead of `{id:1, x:10}` |
| `create materialized view temp.mv as select id, x from t` | `sourceTables` = `['main.t2']`, `stale` = false, reads correct — but body reads bare `t2` | `refresh materialized view temp.mv` replaces the contents with `{id:99, x:999}` |
| `create assertion temp.a check (not exists (select 1 from t where x < 0))` | violation query watches `temp.t2` | `insert into main.t2 values (2, -1)` commits cleanly; before the rename the equivalent write was refused |

## The invariant

> After rewriting a reference, re-resolving it — under the same home schema path,
> against the catalog **as it will be after the rename** — must yield the renamed
> object's key.

All three symptoms are one code site: the rewrite sink in `renameTableInAst`,
which calls `ref.setName(newName)` and nothing else. The `TableRef` the walk
hands its sink exposes only `schema` and `setName`, so a rewrite physically
*cannot* add a schema qualifier even where one is needed. Satisfy the
post-condition at the sink and all three symptoms close at once, and stay closed
when new body kinds are added.

## Shape settled by the fix-stage research

### 1. A post-rename sibling snapshot

`snapshotObjectRefResolvers` builds a `Map<schemaLower, Set<nameLower>>` and
derives one `ResolveObjectRef` per home schema from it. The post-rename name set
is that same map with `oldName` removed from — and `newName` added to — the
renamed schema's set. No live-catalog lookup, so the SNAPSHOT DISCIPLINE comment
in that file still holds for both snapshots.

Add to `ObjectRefResolvers`:

```ts
export interface ObjectRefResolvers {
	forHomeSchema(homeSchemaName: string): ResolveObjectRef;
	/**
	 * A sibling snapshot with one table rename applied — the catalog as it will
	 * look AFTER the statement. Used only to check the rename post-condition.
	 */
	withTableRenamed(schemaName: string, oldName: string, newName: string): ObjectRefResolvers;
}
```

Implementation: factor the current body into an internal builder over
`(db, bySchema)` so both the base snapshot and the sibling reuse it. Copy the
affected schema's `Set` rather than mutating it (the base snapshot must stay
answering pre-rename), and copy the outer `Map` shallowly.

### 2. Only two AST sites can carry the qualifier that matters

`walkTableRefs` has five emit sites. Their post-condition obligations differ, and
that difference is the reason the fix is not "qualify everything":

| site | file:line | needs `qualify`? |
| --- | --- | --- |
| DML target identifier (`visitDmlTarget`) | table-rename.ts:427 | **yes** — `IdentifierExpr.schema` |
| FROM `TableSource` | table-rename.ts:554 | **yes** — `ts.table.schema` |
| Seedless bare column qualifier (`binding === undefined`) | table-rename.ts:661 | **yes** — `ColumnExpr.schema` exists; see caveat below |
| Column qualifier already schema-qualified (`main.t.x`) | table-rename.ts:645 | no — it only matched because `objectRefKey(col.schema, name) === targetKey`, so `col.schema` IS the renamed schema and the post-condition holds by construction (the resolver is passthrough for a qualified name) |
| Column qualifier bound through an unaliased FROM source (`binding !== null`) | table-rename.ts:669 | no — it binds through the FROM frame, not the catalog. Qualifying the source (site 2) is the whole fix; the qualifier just needs the new bare name |

So `TableRef` grows an **optional** `qualify?: (schemaName: string) => void`,
present at exactly the three sites above. Absence is the signal "this reference
does not re-resolve through the catalog" — write that in the field's doc comment,
because it is the thing a future reader will otherwise get wrong.

Verified ordering fact that makes site 2 safe: `walkTableRefs` visits a select's
`columns` (line 473) *before* its `from` (line 487), and `collectFromBindings`
copies `{ schema, name }` by value into the frame before anything under the FROM
is visited. So a column qualifier still sees the pre-rewrite source name, and
qualifying the source afterwards cannot disturb it.

### 3. Qualify only when the post-condition fails

```ts
if (eq(ref.name, oldName) && resolve(ref.schema, ref.name) === targetKey) {
	ref.setName(newName);
	changed = true;
	if (ref.qualify && resolveAfter(ref.schema, newName) !== newTargetKey) {
		ref.qualify(renamedSchemaName);
	}
}
```

Eager qualification would churn the text (and the materialized-view `bodyHash`)
of every rewritten body in the common no-collision case. Conditional
qualification keeps the existing fallthrough expectations green
(`rename-cross-schema.spec.ts` and §49 of `41.3-alter-rename-propagation.sqllogic`)
and touches text only where the reference would otherwise move. The cost is that
the qualifying branch is rare — which is what the coverage grid below is for.

### 4. Make the post-rename resolver required, not optional

An optional parameter is how this defect comes back: the next caller omits it and
the post-condition silently stops holding. Bundle the target into one required
argument so every call site has to answer the question:

```ts
export interface TableRenameTarget {
	oldName: string;
	newName: string;
	/** Schema owning the renamed object. `targetKey` is `objectRefKey(schemaName, oldName)`. */
	schemaName: string;
	/** Resolution as the bodies planned it — the pre-mutation snapshot. */
	resolve: ResolveObjectRef;
	/** Resolution as it will be after the rename lands. */
	resolveAfter: ResolveObjectRef;
}
```

`targetKey` and `newTargetKey` are derivable inside the walker, so the five
collection entry points (`renameTableInAst`,
`renameTableIn{IndexPredicates,CheckConstraints,ColumnExpressions}`) each lose two
positional params and gain one object. `tableReferencedInAst` and
`collectTableRefsInAst` keep their current signatures — they are read-only and the
post-condition does not apply to them.

Backwards compat is explicitly not a concern for this repo, so change the public
signature rather than adding an overload.

### 5. Single-schema worlds pass the same resolver twice

`schema-differ.ts` (the inverse reconcile) and
`quereus-store/src/common/store-module-rename.ts` (a table's own CHECK / predicate /
column-expression rewrite) both build their resolver with
`singleSchemaObjectRefResolver(schemaName)`: qualified names pass through,
unqualified ones key under the one schema. Renaming inside that schema therefore
always resolves the bare new name back to itself, so `resolveAfter === resolve`
there and no qualification ever fires. Pass the same function for both fields and
say why in a one-line comment at each site.

Not to be conflated: `store-module-rename.ts` already documents a *different*
latent gap in its rollback arm (lines ~225–236 — the reverse pass reuses the
forward snapshot with the new name's key, which mis-keys when another schema on the
path already holds `newName`). That is its own defect and is out of scope here;
leave the comment intact.

## Things to confirm while implementing

- **The read-only probe must not drift.** `renameTableInAst` and
  `tableReferencedInAst` are deliberately one traversal so the DROP guards refuse
  exactly what a rename rewrites. Adding `qualify` to `TableRef` is inert for the
  probe and collect sinks — keep the post-condition logic inside
  `renameTableInAst`'s sink only, and keep the existing comment block at
  table-rename.ts:117–134 accurate.
- **`astToString` must render the qualifier.** A newly qualified FROM source has
  to round-trip through the re-persisted body SQL.
- **`bodyHash` churn is expected and correct** for a qualified materialized-view
  body — `applyMaterializedViewRewrite` restamps it from the rewritten body.
- **The declarative differ.** Qualification only fires when the body's home schema
  differs from the renamed table's, and the differ diffs one schema at a time
  against rename records for *that* schema — so a cross-schema qualification is
  outside its rename-record scope and should not churn a drop+recreate. Confirm
  rather than assume; the store-path tests are where it would show.
- **`self-qualifier-strip.ts` is unaffected** — it only strips *column* qualifiers
  whose name equals the owning table's, never a FROM source. Re-read
  `stripColumnQualifier` (self-qualifier-strip.ts:275) once the seedless column
  site can carry a schema, to be sure a `temp.t2.x` self-qualifier form cannot be
  produced where the strip would then decline.
- **The CHECK / DEFAULT looseness.** `snapshotObjectRefResolvers`'s header records
  that CHECK and column-DEFAULT bodies actually plan under
  `schemaAuthoredContext` (owning schema only), stricter than the home-path rule
  the resolver applies. A bare name in a CHECK that only resolves by falling
  through to another schema is a body the planner already rejects, so the seedless
  column site's `qualify` can only ever fire on an already-unevaluable body. That
  is harmless (arguably an improvement), but note it at the site so the next reader
  does not read it as a live path.
- **Idempotence** is preserved for free: a second call finds the name already
  `newName`, fails `eq(ref.name, oldName)`, and does nothing. `runRenameTable`
  relies on this (it calls `rewriteTableForTableRename` before the catalog swap and
  the propagation calls it again).

## Coverage the fix must leave behind

A grid, not three point tests. For each body kind — view, materialized view,
assertion — and each reference form — {schema-qualified, bare same-schema, bare
fallthrough} × {new name free, new name already taken in an earlier schema on the
body's home path} — assert the body still resolves to the intended table after the
rename. The existing tests cover exactly the "new name free" column; the collision
column is what is missing.

- For the materialized view, assert on `refresh materialized view`, not only on
  reads — the stale-rows path is what exposes the mis-bound body.
- For the assertion, assert that a violating write is still **refused**.
- Keep the existing negative cases green: a bare `t` that means `temp.t` must
  still be left untouched by a rename of `main.t`
  (`rename-cross-schema.spec.ts:280`, §49 of the sqllogic file).
- The store path shares the rewrite through `assertRenameDependentsPersistable`,
  so add at least the view + MV collision case to
  `41.3-alter-rename-propagation.sqllogic` (append as §60; the file currently ends
  at §59) so `yarn test:store` exercises it too.
