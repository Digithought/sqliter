# Batch the row fetches behind a secondary-index scan

## Context — what already landed

The storage interface now has a batch point-read, and the store table has a
pending-aware wrapper over it:

- `KVStore.getMany(keys)` — positional batch point-read, implemented on every backend
  (IndexedDB collapses N transactions into one; LevelDB uses the native multi-get).
- `StoreTableBase.readEffectiveRowsByKeys(keys)` — the batch twin of
  `readEffectiveRowByKey`. Resolves this transaction's pending overlay in memory FIRST
  (a pending delete never reaches the store; a pending put wins over the committed
  value), then issues one `getMany` for the remainder, and answers positionally with
  `null` for "no row". It does not dedup — ordering and dedup rules differ per scan
  shape, so they belong to the caller.

**Nothing calls `readEffectiveRowsByKeys` yet.** The scan path is unchanged and still
awaits one row at a time.

## What happens today

`scanIndex` (store-table-scan.ts ~line 794) does
`await this.readEffectiveRowByKey(entry.value)` inside the `for await` over index
entries. Nothing overlaps: each round trip completes before the next begins, and on
IndexedDB each one opened its own readonly transaction. So an index scan matching N rows
cost N serialized transactions. The index scan itself is fine — it goes through
`iterate` → the batched `getAll` path.

A downstream project measured the consequence on IndexedDB in headless Chromium: a
13 300-row read took **2375 ms via an index seek (~0.18 ms/row) against 227 ms for a full
table scan of the same rows plus filtering in JavaScript (~0.017 ms/row)** — an index ten
times *slower* than not using it. They shipped a workaround that disables the index. The
plainest indexed read pays it too: `select … from entry where account_id = ?` returning
**2119 of 36 000 rows in 307 ms**. Those are their numbers; the code path above is
verified by reading, not by local measurement.

A range read cannot fix this by widening the window — index entries point at scattered
data keys, so there is no contiguous data-store range to read. It has to be a batch
point-read.

## What to build

Two arms, both in `store-table-scan.ts`. They share one mechanism, so build the
mechanism once.

**Arm B — page the single-window index scan.**

Rework `scanIndex` to consume index entries in fixed-size batches (start at 256, matching
the iterate pager; name the constant, e.g. `ROW_RESOLUTION_BATCH`, and reference it from
`KVStore.getMany`'s "bounded by the caller" note). Collect up to K entries, resolve them
with one `readEffectiveRowsByKeys`, then yield in index-entry order.

Every existing per-row defense stays exactly as it is, just moved either side of the
batch boundary: skip a zero-length index value, skip a row that resolves to null,
re-check every row with `matchesFilters` (or any of the multi-seek window's residual
alternatives), and add to the multi-seek `seen` set only on yield.

Batching trades a little early-termination cost for throughput: `limit 1` reads one batch
rather than one row. That is the same trade `pagedIterate` already makes and the
`KVStore.iterate` contract already documents. Keep the batch bounded so peak memory stays
independent of the range size.

**Arm C — batch the multi-seek arms.**

`select … from t where col in (a, b, c)` is served as a multi-seek: one byte window per
distinct value. Both multi-seek functions are serial today and both are in scope:

- `scanMultiSeekPrimary` (~line 1003) awaits `readEffectiveRowByKey(p.key)` once per key
  in ascending key order. This is literally "fetch N rows by key" and becomes bounded
  batches of `readEffectiveRowsByKeys` over the sorted, deduplicated key list — the
  smallest change here.
- `scanMultiSeek` (~line 913) drives its windows one after another, each through
  `scanIndex`. Arm B batches *within* a window, but a hundred single-row windows still
  cost a hundred sequential row reads. Batch *across* windows too: the windows are
  already sorted disjoint by encoded key, so their concatenation is already the emission
  order.

### Suggested shape

The clean way to get arms B and C from one mechanism is to split `scanIndex` into a
producer and a batching consumer:

- a producer that walks `iterateEffective(indexStore, bounds)` and yields, per surviving
  index entry, its data key plus the window's `FilterInfo` alternatives — doing the
  zero-length skip and the `seen` pre-check (which still saves the read for a cross-window
  duplicate an EARLIER window already yielded);
- a consumer that pulls up to K of those, calls `readEffectiveRowsByKeys` once, and yields
  the rows that survive `matchesFilters`, updating `seen` on yield.

Then `scanIndex` runs the consumer over one window's producer, and `scanMultiSeek` runs
the SAME consumer over the concatenation of every window's producer. Bounding the
consumer by entry count (not by window count) gives arm C its bound for free: a hundred
one-row windows become one batch, and `… in (…) limit 1` materializes at most one batch
rather than every window.

## Edge cases & interactions

- **Ordering.** `scanIndex` must still yield in index-key order — the isolation overlay
  merges an index scan with staged rows by `(indexKey, PK)`, and an out-of-order stream
  misplaces overlay rows. Test with an open transaction holding pending writes.
- **Duplicate keys within one batch** (two index entries pointing at one row — possible
  for a stale entry). The `seen` pre-check runs before the batch is collected, so it
  cannot catch a duplicate *inside* the batch; the post-read yield path must re-check
  `seen` so the row is yielded once, not twice or zero times.
- **`seen` is still only added to on yield.** A stale index entry that fails its residual
  must not poison the set and suppress the row's live entry in a later window. Batching
  must not move that decision earlier.
- **Missing keys** stay skipped, and must not shift positions —
  `readEffectiveRowsByKeys` answers positionally with `null`.
- **Pending deletes and puts** are already resolved before the batch is issued by
  `readEffectiveRowsByKeys`; do not re-implement that precedence in the scan.
- **Early termination.** A consumer that breaks mid-batch must leave no open transaction
  or cursor and must not read a second batch. Verify with the existing bounded-iteration
  harness idiom (`packages/quereus-store/test/bounded-iterate.spec.ts`).
- **Store closed mid-scan.** Same behavior as today's per-key path: the scan may be
  suspended across an await, and `checkOpen` semantics must not regress.
- **Multi-seek residual alternatives.** A window can carry several merged tuples, each
  with its own residual `FilterInfo` (`extraTuples`); a row is accepted when it matches
  the primary info OR any alternative. Keep the accept decision per row and in order.
- **The remaining `readEffectiveRowByKey` callers** (unique-constraint probes in
  store-table-constraints.ts, backing-host) are out of scope — do not rework them, but
  the single-key method must keep existing and behaving identically.

## Expected results

- An indexed read of N rows issues on the order of `N / 256` store round trips, not N.
- Row sets AND their order are unchanged from before, for every scan shape.
