# The one hard subtlety — already resolved, do not re-derive

This is the part that took the investigation budget. Read it before writing the class;
it will save you from a design that looks right and silently breaks an exact-equality
assertion.

**The bug you will want to write:** a `CountingKVStore` built by delegation (wraps an
`inner: KVStore`, per the ticket's requirement — see "What to build" below) that
forwards `getMany` straight to `this.inner.getMany(keys)`. This looks like the obvious
delegating implementation. It is wrong.

**Why it's wrong:** `pushdown.spec.ts` line ~2055 (search `and nothing beyond them are
read` — exact text `'and nothing beyond them is read'`) asserts, after ONE
`getMany()` call carrying 3 keys against an `InMemoryKVStore`-backed data store:

```ts
expect(store.getManyCalls, 'the three points collapse into one batch').to.equal(1);
expect(store.getManyKeyCount, 'exactly the listed keys are batched').to.equal(3);
expect(store.getCount, 'and nothing beyond them is read').to.equal(3);
```

`getCount` must land on exactly 3 — not 0 — after a single 3-key `getMany`. That number
only exists today because the OLD counting doubles use **inheritance**:
`InMemoryKVStore.getMany` is implemented as `defaultGetMany(this, keys)` (see
`packages/quereus-store/src/common/kv-store.ts` ~line 268), which does
`Promise.all(keys.map(key => store.get(key)))` — and because `this` in an inherited
subclass is the SAME object, that `store.get(key)` call resolves via the prototype
chain back to the subclass's own overridden, counted `get()`. Batched keys land in
`getCount` as a side effect of virtual dispatch.

Delegation breaks that side effect: `this.inner` is a DIFFERENT object than the
wrapper. `this.inner.getMany(keys)` runs `defaultGetMany(inner, keys)` with `this =
inner`, so the internal `store.get(key)` calls resolve to the plain, uncounted
`inner.get`, never touching the wrapper's counted `get()`. Forwarding `getMany`
straight to `this.inner.getMany(keys)` would leave `getCount` at 0, not 3, and that
spec would fail (or worse, silently pass wherever the assertion is a bound like `.to.be
.at.most(N)` rather than `.to.equal(N)` — several are; grep `\.getCount\b` across
`pushdown.spec.ts` and `key-set-seek-store.spec.ts` for the full set, most are bounds,
one is exact-equal-3, treat all of them as load-bearing).

**The fix, already confirmed against the codebase:** `defaultGetMany` is EXPORTED from
`common/kv-store.ts` precisely for this. Its own doc comment says: *"Reading through
`store.get` (rather than the backend's internals) also keeps a wrapper's own `get` in
the path, which is what lets `CachedKVStore` and the counting test doubles keep
working."* That sentence is describing exactly this mechanism. So:

```ts
import { defaultGetMany } from '../common/kv-store.js';

export class CountingKVStore extends DelegatingKVStore {
	// ...counters, reset()...

	override async get(key: Uint8Array): Promise<Uint8Array | undefined> {
		this.getCount++;
		return this.inner.get(key);
	}

	override async getMany(keys: readonly Uint8Array[]): Promise<(Uint8Array | undefined)[]> {
		this.getManyCalls++;
		this.getManyKeyCount += keys.length;
		return defaultGetMany(this, keys);   // NOT this.inner.getMany(keys) — see note above
	}

	async *iterate(options?: IterateOptions): AsyncIterable<KVEntry> {
		for await (const entry of this.inner.iterate(options)) {
			this.iterateEntryCount++;
			yield entry;
		}
	}
}
```

`defaultGetMany(this, keys)` calls `this.get(key)` for each key — the WRAPPER's own
counted `get`, which in turn calls `this.inner.get(key)`. This reproduces the exact
current numbers for every existing assertion (verified by hand-tracing all `getCount`,
`getManyCalls`, `getManyKeyCount` assertions across the three inheriting specs — see the
grep above) regardless of what the wrapped backend actually is, and generalizes
correctly to wrapping a real backend (LevelDB, IndexedDB) later: the trade-off is that
the counting wrapper always measures batching **at the call boundary** (did the caller
invoke `getMany` once with N keys, vs. N calls to `get`) rather than the wrapped
backend's own internal round-trip count — which is the right thing to measure for these
specs (they're proving the *engine* batches its reads, not proving the backend has a
native multi-get). Document this trade-off in the class's doc comment — a future
benchmark author reaching for this class to measure a REAL backend's native batching
needs to know `getManyCalls`/`getManyKeyCount` reflect calls into the counting wrapper,
not round trips the inner backend actually made past it.

Write this reasoning (condensed) as a doc comment on `CountingKVStore.getMany` itself,
not just in this ticket — it is exactly the kind of non-obvious invariant that belongs
at the code site per this repo's comment policy.

## `createCountingProvider`

One parameterized factory replacing the three near-identical local copies
(`index-scan-batching.spec.ts`, `pushdown.spec.ts`, `key-set-seek-store.spec.ts`).
The real difference between them is scope: `index-scan-batching.spec.ts` counts EVERY
store (data, index, stats, catalog) into one exposed map; the other two count ONLY data
stores, keeping index/stats/catalog as plain uncounted `InMemoryKVStore`s in an internal
map the caller never sees. Sketch (already reasoned through, not yet written or
compiled — verify it against the three call sites before trusting it verbatim):

```ts
export type CountingProviderScope = 'data' | 'all';

export function createCountingProvider(
	countedStores: Map<string, CountingKVStore>,
	scope: CountingProviderScope = 'data',
): KVStoreProvider {
	const auxStores = new Map<string, InMemoryKVStore>();
	const aux = (key: string): InMemoryKVStore => {
		let s = auxStores.get(key);
		if (!s) { s = new InMemoryKVStore(); auxStores.set(key, s); }
		return s;
	};
	const counted = (key: string): CountingKVStore => {
		let s = countedStores.get(key);
		if (!s) { s = new CountingKVStore(new InMemoryKVStore()); countedStores.set(key, s); }
		return s;
	};
	const maybeCounted = (key: string): KVStore => (scope === 'all' ? counted(key) : aux(key));
	return {
		async getStore(schemaName, tableName) { return counted(`${schemaName}.${tableName}`); },
		async getIndexStore(schemaName, tableName, indexName) {
			return maybeCounted(`${schemaName}.${tableName}_idx_${indexName}`);
		},
		async getStatsStore(schemaName, tableName) {
			return maybeCounted(`${schemaName}.${tableName}.__stats__`);
		},
		async getCatalogStore() { return maybeCounted('__catalog__'); },
		async closeStore() {},
		async closeIndexStore() {},
		async closeAll() {
			for (const s of countedStores.values()) await s.close();
			for (const s of auxStores.values()) await s.close();
			countedStores.clear();
			auxStores.clear();
		},
	};
}
```

Check this against each call site's existing signature before wiring it in —
`index-scan-batching.spec.ts` calls `createCountingProvider(stores)` expecting index
stores to land in the SAME map it passed in (it later does
`stores.get('main.t_idx_ix_v')!`), which the `scope='all'` branch above satisfies since
`maybeCounted` calls `counted()` (writing into `countedStores`) when `scope === 'all'`.
`pushdown.spec.ts` / `key-set-seek-store.spec.ts` call it with just `(dataStores)`
(defaulting to `scope: 'data'`) and never read from the aux map.

  consistent.)
