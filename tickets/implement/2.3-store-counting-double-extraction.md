# What this is

The storage package proves the work-counter technique one layer below the engine: a test
double wraps a key-value store and tallies iterate yields, single-key reads, and batched
multi-key reads, and specs assert exact numbers on them — because rows alone cannot tell
a batched resolution from a serial one.

There are currently **two different shapes of that double, in four places**:

- `test/kv-store-doubles.ts` exports a `CountingKVStore` built on `DelegatingKVStore`
  that counts **only** `iterate` yields. Used by `bounded-iterate.spec.ts` and
  `kv-conformance.spec.ts`.
- `test/index-scan-batching.spec.ts`, `test/pushdown.spec.ts` and
  `test/key-set-seek-store.spec.ts` each declare their **own** class, also called
  `CountingKVStore`, extending `InMemoryKVStore` and counting `iterate` yields, `get`
  calls, `getMany` calls and (in two of the three) `getMany` key volume. Each of those
  three files also carries its own near-identical `createCountingProvider` factory.

Three copies of one idea, differing in which fields they happen to have, all named the
same thing. The next spec that needs one will make a fourth.

## What to build

One shared counting store in `@quereus/store/testing` — the export path that already
exists and already ships the conformance batteries, so a benchmark suite or a plugin's
spec can import it without reaching into another package's `test/` directory.

The shared version must be built by **delegation, not inheritance**, so it can wrap any
`KVStore` (in-memory, LevelDB, IndexedDB) rather than only `InMemoryKVStore` — that is
what makes it usable from a benchmark against a real backend. `DelegatingKVStore` in
`test/kv-store-doubles.ts` is the right base; move it across too if it has no other
reason to stay behind.

Counters it must carry, being the union of what the four current copies count:

- `iterateEntryCount` — entries pulled from `iterate()`
- `getCount` — `get()` calls
- `getManyCalls` — `getMany()` calls (the round-trip count)
- `getManyKeyCount` — keys carried by those calls (the batch volume)
- `reset()`

Preserve the subtlety the existing comments record: `InMemoryKVStore.getMany` delegates
through `this.get`, so batched keys land in `getCount` as well — round trips are asserted
on `getManyCalls`, batch volume on `getManyKeyCount`. That behaviour is a property of the
wrapped store, not of the counter, and a delegating wrapper must not accidentally change
it. State it at the shared class, since the three specs that currently repeat the note
will stop carrying it.

Also lift the repeated `createCountingProvider` factory. The three copies differ in one
real way: `index-scan-batching` counts **every** store (data, index, stats, catalog),
while `pushdown` and `key-set-seek-store` count **only data** stores so index traffic
does not pollute the assertion. Make that a parameter, not two functions.

# Edge cases & interactions

- **Behaviour must not change.** Every existing assertion in the five specs must pass
  unaltered. If any spec's numbers move, the wrapper changed semantics — most likely by
  wrapping a call the inherited version served directly, or by counting an inner
  delegation twice. Investigate; do not adjust the expected numbers.
- **The two current shapes count differently.** The delegating one counts only iterate
  yields; the inheriting ones count reads too. Merging them means `bounded-iterate.spec.ts`
  and `kv-conformance.spec.ts` now have extra fields available. Do not change what they
  assert.
- **Lazy iteration must survive the move.** The delegating version pulls one entry per
  `next()` on purpose, so a consumer that stops early is charged only for what it
  consumed. A shared version that buffers would silently break every bounded-iteration
  assertion — and `BufferingKVStore` in the same file exists precisely as the negative
  control for that bug.
- **`src/testing/` ships in the published package** (`files: ["dist"]`, with a `./testing`
  export and a `typesVersions` entry). Anything moved there is public API for plugin
  authors, so it needs real doc comments — and it must not import from `test/`.
- **The other doubles stay put.** `RescanningKVStore`, `BufferingKVStore`,
  `SortingGetManyKVStore`, `CompactingGetManyKVStore` and `AliasingGetManyKVStore` are
  deliberately-wrong stores used as negative controls. This ticket moves the *counter*.
  Moving a negative control into a published testing entry point is a separate decision;
  if `DelegatingKVStore` moves, re-export it back into `test/kv-store-doubles.ts` so those
  classes keep their base without a second copy.
- **Name collision.** Four things are currently called `CountingKVStore`. After the move
  there is one; make sure no spec ends up importing the shared one while shadowing it
  with a local `class CountingKVStore` that the compiler happily accepts.
- **Typecheck covers the specs.** `@quereus/store`'s `typecheck` script runs
  `tsc -p tsconfig.test.json --noEmit` as well as the main pass, so a signature drift in a
  spec call site is caught — run it, do not rely on the test run alone.

# Not in scope

The store benchmark suite that will be this utility's largest consumer, and any change to
what the existing specs assert.
