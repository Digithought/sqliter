# Separate "I estimate zero" from "I have proved nothing matches"

`BestAccessPlanResult.rows` is documented as *an estimate*. One consumer reads it as a
*proof*:

```ts
// planner/rules/access/rule-select-access-path.ts
if (accessPlan.rows === 0 && accessPlan.handledFilters.length > 0 && accessPlan.handledFilters.every(h => h)) {
    return createEmptyResultNode(tableRef);
}
```

When that fires, the table is never read at all — the plan gets a static empty relation.
That is only sound when the backend was *proving* a predicate unsatisfiable. Reading it
out of an estimate field means a backend that rounds a very selective estimate down to
zero, or that honestly reports how big the table is *right now*, has its read deleted —
and planning precedes execution, so "empty now" is not "empty later". A statement that
writes rows into a table and then reads them back in the same statement returns nothing.

The worst arm is already closed: the fold used to fire on a plan with **no filters at
all**, because `handledFilters.every(...)` is vacuously true over an empty list. What
remains is that the interface still has no way to distinguish the two claims, and both
shipped backends have had to defend against the overload with floors they document as
load-bearing:

- `vtab/memory/module.ts` — `Math.max(1, …)` in `estimateEqualityRows`, explicitly "guards
  the `rows: 0` fold".
- `quereus-store/src/common/store-module-access-plan.ts` (~1033) — `Math.max(1, …)`
  described as "LOAD-BEARING, not defensive".
- `quereus-store/src/common/store-module.ts` (~85) — the live-count floor, "`rows: 0` is
  not 'this table is empty' in the access-plan protocol".

Three separate sites paying a tax to work around one overloaded field.

## Decision

Add an explicit flag to the access-plan answer:

```ts
export interface BestAccessPlanResult {
    // …
    /** Estimated number of rows this plan will return. An ESTIMATE — never a proof. */
    rows: number | undefined;
    /**
     * Set only when the module has PROVEN that no row can satisfy the filters it
     * claimed in `handledFilters` (e.g. `IS NULL` on a NOT NULL column). The planner
     * replaces the entire table access with a static empty relation, so this must
     * never be set merely because the table is empty at plan time — planning precedes
     * execution. Defaults to false/absent; declining is always safe.
     */
    provablyEmpty?: boolean;
}
```

Move the fold onto that flag and drop the `rows === 0` test entirely. The
`handledFilters` conjunct stays as a **defensive assertion**: `provablyEmpty` with no
claimed filter is a contradiction (the module cannot prove a predicate unsatisfiable
without claiming it), so treat it as a module bug — reject it in `validateAccessPlan`
rather than silently folding.

Once the fold no longer reads `rows`, `rows: 0` is a plain estimate again and the three
`Math.max(1, …)` floors above become unnecessary. **Leave them in place** and change only
their comments to say they are now conservative rather than load-bearing — removing them
is a separate cost-model change with its own plan churn, and this ticket should not carry
it. (Record that as a `NOTE:` at each site, not as a ticket.)

`AccessPlanBuilder` gets a `setProvablyEmpty()` and, for the common case, an
`AccessPlanBuilder.empty(handledFilters)` static that builds the whole "nothing can match"
answer — cost 0, rows 0, all filters handled, `provablyEmpty: true` — so a module cannot
half-express it.

## Edge cases & interactions

- **A module sets `provablyEmpty` with `handledFilters` all false, or with an empty
  filter list.** `validateAccessPlan` must reject (`StatusCode.INTERNAL`), with a message
  naming the module. Test it.
- **A module sets `provablyEmpty` and a non-zero `rows`.** Contradictory; reject in
  validation, or normalize `rows` to 0 — pick one and state it in the doc comment. Prefer
  rejecting: silent normalization hides a module bug.
- **A module still returns `rows: 0` with all filters handled and no flag.** After this
  change the table is READ and the filters are enforced normally. That is a behavior
  change for any third-party module relying on the old overload — the correct new
  behavior, but call it out in `docs/module-authoring.md` in the same edit that changes
  the contract prose at ~line 213.
- **`validateAccessPlan` is not called by every module** — the store module does not call
  it. The planner must still behave sanely on an unvalidated bad answer: an unclaimed
  `provablyEmpty` should not fold. Keep the `handledFilters.length > 0 && every(...)`
  guard in `selectPhysicalNode` as the runtime backstop even though validation also
  rejects it.
- **The isolation layer** (`quereus-isolation`) wraps a module's access plan. If it
  reconstructs a `BestAccessPlanResult` field-by-field anywhere, the new flag must be
  carried through — a dropped flag is a lost optimization, but a *fabricated* one is a
  wrong answer. Grep for spread/rebuild sites there.
- **`index-nested-loop.ts` (~361)** reasons about "a module that answered its own seek
  with `rows: 0`". Re-read that comment against the new contract and correct it.
- **The seek-side empty-result paths** in `rule-select-access-path` (NULL seek keys,
  all-NULL `IN` lists) build `EmptyResultNode` from planner-side proofs, not from module
  answers. They are unaffected — confirm, don't touch.
- **`schema/lens-prover.ts` (~2472)** has its own `rows === 0` test in a different
  domain. Verify it is unrelated before leaving it alone.
- **Stale comment reference.** `rule-select-access-path.ts` (~line 411) points at
  `backlog/debt-empty-access-plan-fold-trusts-estimate`, a ticket that does not exist on
  the board or in `tickets/.pruned-tickets.jsonl`. This ticket resolves what it described;
  delete the reference.
