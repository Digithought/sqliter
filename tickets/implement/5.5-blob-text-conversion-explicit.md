# Text-to-binary stops guessing; hex becomes something you ask for

## Why now

`canonical-value-to-text` makes `cast(x'6162' as text)` produce `ab` instead of `6162`.
`BLOB_TYPE.parse` then sniffs the string coming back: even length, all hex characters,
non-empty → decode as hex. So `cast(cast(x'6162' as text) as blob)` becomes
`cast('ab' as blob)` becomes `x'ab'` — two bytes in, one different byte out. The guess was
already wrong on its own terms (`cast('abc' as blob)` and `cast('abcd' as blob)` take
different branches purely because of the length), but the text change is what turns it into
a round-trip that corrupts.

That change also removes the only way to get a hex spelling of binary data out of the engine,
because Quereus has no `hex()` function. This ticket restores the capability explicitly
rather than as a side effect of a heuristic.

## What changes

**`BLOB_TYPE.parse`, string arm.** Delete the hex sniff. A string always becomes its UTF-8
bytes, which is what SQLite's `cast(<text> as blob)` does. Everything else in `parse` stays.

**Add `hex(X)`.** SQLite-compatible: the argument's bytes as **uppercase** hex, no separator.
A non-blob argument is converted to bytes first, i.e. through the same path
`cast(X as blob)` takes — so `hex('abc')` is `616263`. `hex(null)` is null; `hex(x'')` is
the empty string.

**Add `unhex(X)`.** The inverse: a hex string to bytes. Returns **null** — not an error and
not a partial result — for anything that is not a whole number of hex digit pairs, matching
SQLite. `unhex('')` is the empty blob. One-argument form only; SQLite's two-argument
"ignore these characters" variant is not needed here and should not be half-built.

**Add `blob(value)`.** `docs/types.md` already lists it alongside `integer()`, `real()`,
`text()` and `boolean()`, and it is the only one of the five that was never written. Mirror
`TEXT_FUNC` in `func/builtins/conversion.ts`: `BLOB_TYPE.parse`, wrapping a failure in a
`QuereusError` with `StatusCode.MISMATCH`, null in → null out.

## Edge cases & interactions

- **The round trip this ticket exists for.** `cast(cast(x'6162' as text) as blob) = x'6162'`
  → true.
- **Round-trip is not total, and the test must say so.** A blob that is not valid UTF-8 does
  not survive: `x'ff'` renders as U+FFFD and re-encodes to `x'efbfbd'`. Assert that honest
  result rather than a `= x'ff'` that would have to be made to pass.
- **`cast('6162' as blob)` changes** from `x'6162'` to `x'36313632'` (the UTF-8 bytes of the
  four characters). Anyone who wanted the old answer writes `unhex('6162')`.
- **`cast('abc' as blob)` is unchanged** — odd length, so it already took the UTF-8 branch.
  Keep the existing assertion in `99.1-cast-syntax-extras.sqllogic:10` green.
- **Write path.** `BLOB_TYPE.parse` is reached by `validateAndParse` (`types/validation.ts`),
  so inserting text into a BLOB column now always stores UTF-8 bytes. Same for
  `alter table … alter column … set data type blob` backfill. Test an insert and read-back.
- **`unhex` case-insensitivity.** `unhex('CAFE')` and `unhex('cafe')` give the same bytes.
  `unhex('616')` (odd length) → null. `unhex('zz')` → null. `unhex(null)` → null.
- **`hex` of a bigint / boolean / JSON value** follows whatever `BLOB_TYPE.parse` does with
  it — do not add a second conversion table here. A JSON object reaches `parse`'s throw and
  therefore `hex(json_col)` errors; decide and state in the docstring whether that is
  acceptable or whether `hex` should return null, and test the choice either way.
- **Empty-blob distinctness.** `x''` stays a distinct non-null zero-length value throughout
  (`test/logic/07.9-in-value-list.sqllogic:146` already guards this) — `hex(x'')` is `''`,
  not null.
- **Lexer blob literals are untouched.** `x'6162'` is parsed by the lexer, not by
  `BLOB_TYPE.parse`, so literal syntax does not change.
