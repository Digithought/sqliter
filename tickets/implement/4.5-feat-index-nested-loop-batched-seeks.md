# Run a high-latency index-nested-loop join's seeks concurrently

## What exists today, in plain terms

An **index-nested-loop join** walks one side of a join (the *outer*) row by row
and, for each row, asks the storage module for the matching rows on the other
side (the *inner*) using an index. One lookup per outer row. On an in-process
table that is the right shape. On storage reached over a network it is one round
trip per outer row, and 20,000 outer rows means 20,000 sequential round trips.

The engine already has a runtime that overlaps such lookups: the **fan-out
lookup join** (`FanOutLookupJoinNode`). Its `batched` outer mode reads several
outer rows ahead of what it is emitting, keeps many lookups in flight at once
under a shared budget, and re-orders the finished rows back into outer order
before emitting, so the output is indistinguishable from the one-at-a-time
version. That runtime shipped, but nothing builds a fan-out node out of an
index-nested-loop join — the fan-out is only ever formed by
`rule-fanout-lookup-join`, which needs at least two branches and a declared
foreign-key relationship.

This ticket makes an index-nested-loop join into a **one-branch fan-out lookup
join in batched mode**, so it reuses that runtime verbatim.

## Design decisions already settled — do not re-open these

The plan pass read the fan-out node, both of its runtime drivers, the
recognition rules and the optimizer's pass machinery. The following are settled;
the ticket body below explains each.

1. **Reuse the fan-out's batched driver.** A dedicated batched nested-loop
   driver was considered and rejected: the fan-out driver already solves the
   hard parts (shared runtime context during a concurrent pump, strict-fork
   nesting, reorder buffer, in-flight budget) and re-deriving them in a second
   driver is the expensive half of the work.
2. **The branch is `atMostOne-inner` / `atMostOne-left`, proved, not guessed.**
   See "The at-most-one proof" below. A seek that cannot be proved to return at
   most one row is out of scope (backlogged as
   `feat-batched-lookup-for-multi-row-inner-matches`).
3. **The decision is made inside `ruleJoinPhysicalSelection`, as a priced
   candidate — not as a later rewrite rule.** A separate post-pass rule would
   only ever see index-nested-loop joins that already won the comparison *at
   one-lookup-at-a-time prices*, and under latency those mostly lose to hash
   join. Batching changes the price, so the price has to be in the comparison.
4. **One function owns the gates, the prefetch wrap and the flip.** Extracted
   from `rule-fanout-batched-outer` so the two callers cannot drift, and so a
   one-branch fan-out is never left in serial mode (which would be strictly
   worse than the join it replaced: per-row forking, no overlap).
5. **`semi`, `anti`, and `exists … as` joins keep the plain join.** The fan-out
   node has no semi/anti mode and no existence-flag support.

### Why this is worth building — measured against the current cost model

With `expectedLatencyMs = 25`, an outer of 20,000 rows, one row per seek, and
the shipped cost constants (`NL_JOIN_PER_OUTER_ROW` 1.0, `INDEX_SEEK_BASE` 0.5,
`INDEX_SEEK_PER_ROW` 0.3, `HASH_JOIN_BUILD_PER_ROW` 0.8,
`HASH_JOIN_PROBE_PER_ROW` 0.4), the crossover inner-table size at which
index-nested-loop beats hash join moves from about **1.3 million rows** to about
**128,000 rows** — a factor of ten more shapes where the seek plan wins. Those
numbers come from evaluating the shipped formulas by hand at
`outerRows = 20000`, not from a benchmark; they are the reason the work is worth
doing, not a claim about wall-clock.

Note also what this does *not* fix: the engine prices a full scan of a remote
table as **one** round trip, because `expectedLatencyMs` is defined as first-row
latency. A storage backend that answers one row per request (the IndexedDB
plugin's cursor reads) really pays it per row, and until the cost model can say
so, hash join keeps winning shapes it should lose. That is a separate, larger
gap — filed as `feat-per-row-latency-cost-for-remote-scans` in `backlog/`.

## What to build

### 1. The at-most-one proof, in `index-nested-loop.ts`

`FanOutLookupJoinNode`'s `atMostOne-*` branch modes are enforced at runtime: a
branch that yields more than one row for an outer row throws
`QuereusError(StatusCode.CONSTRAINT)`. So the proof must be a *proof*, not the
module's row estimate — a module that estimates 1 and returns 2 would turn a
working query into an error.

`tryIndexNestedLoop` already holds everything needed. Its `offered.combined` is
the full constraint list handed to the module — the synthesized join-key
equalities followed by the displaced leaf's pushed predicates — and the rule's
existing correctness argument guarantees every one of them is enforced somewhere
inside the rebuilt inner subtree (re-promised by the new seek, reattached by
`selectPhysicalNode`, or re-applied by `reapplyDeclinedPushed`), with join-key
leftovers covered by the ON condition. A `Filter` can only remove rows, so any
constraint enforced by a filter rather than by the index still counts toward the
proof.

Add to `IndexNestedLoopCandidate`:

```ts
/** True when the rebuilt inner provably yields at most one row per outer row. */
readonly atMostOne: boolean;
```

computed by a new local helper:

```
atMostOne(tableSchema, offered.combined) :=
  eq := { c.columnIndex -> c : c in combined, c.op === '=' }
        // ranges, IN, OR_RANGE never prove uniqueness
  candidateKeys :=
      [ primaryKeyDefinition.map(k => k.index) ]                                  // if non-empty
    ++ (uniqueConstraints ?? []).filter(u => u.predicate === undefined).map(u => u.columns)
    ++ (indexes ?? []).filter(i => i.unique && i.predicate === undefined)
                      .map(i => i.columns.map(c => c.index))
  return some key in candidateKeys, key non-empty, such that
      every col in key satisfies  eq.has(col) && collationSafe(eq.get(col), col)
```

with

```
collationSafe(constraint, colIdx) :=
  pred := normalizeCollationName(effectivePredicateCollation(constraint))
  decl := normalizeCollationName(tableSchema.columns[colIdx].collation ?? 'BINARY')
  return pred === 'BINARY' || pred === decl
```

Why each piece:

- **Partial keys are excluded** (`predicate !== undefined`): a partial unique
  index only constrains rows satisfying its WHERE clause.
- **Equality only.** A range or `IN` constraint on a key column matches many
  values.
- **The collation test is load-bearing.** Uniqueness is enforced under the
  column's declared collation; the seek's equality compares under the
  predicate's effective collation, and `extractEquiPairs` admits non-BINARY
  equi-pairs (they carry a `valueDiscriminating: false` flag rather than being
  rejected). If the predicate compares under a *coarser* collation than the key
  — a `NOCASE` join key over a `BINARY` unique column — then `'a'` and `'A'` are
  two distinct stored rows that both match, and the at-most-one claim is false.
  The two safe cases are: the collations are equal (identical equivalence
  classes), or the predicate is `BINARY` (the finest relation there is, so at
  most one row per class under any coarser column collation).
- **Over-fetch does not break the proof.** When the chosen index is coarser than
  the predicate, `selectPhysicalNode` classifies the constraint `COARSER_SAFE`
  and leaves a residual `Filter` above the seek that re-applies the exact
  comparison. The seek may hand back several rows; the filter narrows them to
  the ones the unique key admits at most one of. The reverse case (a *finer*
  index than the predicate) is classified `MISMATCH_UNSAFE`, `selectPhysicalNode`
  degrades to a scan, `rebuiltSeek` returns null, and the whole candidate is
  already declined before the proof runs.

`effectivePredicateCollation` is currently private in
`rule-select-access-path.ts`; export it, the way `classifyConstraintCover`
already is, rather than reimplementing the lattice.

Add unit coverage for the helper directly — it is the correctness core.

### 2. Extract the batched flip into one reusable function

In `rule-fanout-batched-outer.ts`, move the gates, the `EagerPrefetchNode` wrap
and the node construction into:

```ts
export function toBatchedOuter(
  node: FanOutLookupJoinNode,
  tuning: OptimizerTuning['parallel'],
): FanOutLookupJoinNode | null;
```

`ruleFanOutBatchedOuter` becomes a thin wrapper over it. The gates move verbatim:
idempotence, no cross branches, `branchCount < outerBatchConcurrency`, slowest
branch latency at or above `batchedOuterThresholdMs`, outer estimate at or above
`batchedOuterMinRows`, `outer.physical.concurrencySafe === true`, and the
`PlanNodeCharacteristics.isConcurrencySafe` checks on the outer and every branch.
Keep `outerRowEstimate` alongside it.

The `EagerPrefetchNode` wrap is load-bearing correctness, not an optimization:
the batched driver pumps the outer concurrently with in-flight branch forks, and
the prefetch node runs the outer sub-plan against its own forked context so
nothing mutates the shared `RuntimeContext` the row forks are counting. Keeping
it inside `toBatchedOuter` is what guarantees no caller can get batched mode
without it.

### 3. Build and price the batched candidate

Add to `planner/cost/index.ts`:

```ts
/**
 * Index-nested-loop with the per-outer-row seeks pipelined: the engine-side
 * per-row work is unchanged (single-threaded), only the storage latency is
 * amortized across the rows in flight.
 */
export function batchedIndexNestedLoopJoinCost(
  outerRows: number, rowsPerSeek: number, perSeekLatencyMs: number, inFlight: number,
): number;
```

`= outerRows * (NL_JOIN_PER_OUTER_ROW + INDEX_SEEK_BASE + rowsPerSeek *
INDEX_SEEK_PER_ROW + perSeekLatencyMs / max(1, inFlight))`.

For a one-branch fan-out the number of lookups in flight is
`min(tuning.parallel.outerBatchConcurrency, tuning.parallel.maxOuterReadAhead)`
— the driver's global permit budget bounded by its read-ahead window. That
mirrors `deriveReadAhead` in `runtime/emit/fanout-lookup-join.ts`, which is
module-private; state the coupling in a comment at both ends so a change to one
is noticed at the other.

In `ruleJoinPhysicalSelection`, for each surviving index-nested-loop candidate
(un-mirrored and mirrored) whose `atMostOne` is true and whose join type is
`inner` or `left` and which is not an existence join:

- build the serial one-branch fan-out (below),
- call `toBatchedOuter` on it; if it returns null, there is no batched candidate
  for that orientation — **do not enter a serial fan-out into the comparison**,
- otherwise price it with `batchedIndexNestedLoopJoinCost` and enter it as a
  sixth candidate.

Building the node and asking the gates in one step means the price and the plan
can never disagree.

Fan-out construction, for outer `O`, rebuilt inner `I` and the join's ON
condition `C`:

```
branch = {
  child:           new FilterNode(scope, I, C),
  mode:            joinType === 'left' ? 'atMostOne-left' : 'atMostOne-inner',
  outputAttrs:     I.getAttributes(),
  concurrencySafe: I.physical.concurrencySafe !== false,
}
new FanOutLookupJoinNode(scope, O, [branch], /* concurrencyCap */ 1,
                         preserveAttrs, /* outerMode */ 'serial')
```

- **The ON condition becomes a `Filter` inside the branch.** A fan-out branch
  has no residual slot. This is the same construction `rule-fanout-lookup-join`
  uses for its spine branches (`new FilterNode(scope, lookup, condition)`), and
  the condition's outer-side column references resolve through
  `RuntimeContext.context` exactly as the seek's own correlated keys already do.
  It cannot add rows, so it cannot break the at-most-one claim; and for a LEFT
  join, filtering the single row away yields an empty branch, which
  `atMostOne-left` NULL-pads — precisely LEFT-join semantics.
- **`preserveAttrs`**: for the un-mirrored orientation pass
  `node.getAttributes().slice()` — the logical join's layout is
  `[...left, ...right]` with the right nullable-widened for a LEFT join, which is
  exactly what the fan-out's `[...outer, ...branch]` layout with
  `isLeftBranchMode` widening produces, so pinning it keeps attribute identity
  verbatim. For the mirrored orientation pass `undefined` and let the node derive
  `[...right, ...leftRebuilt]`, matching what `rebuildWithMirroredNL` produces
  today.
- **`concurrencyCap` is 1** — one branch. The cross-row budget is the batched
  driver's `outerBatchConcurrency`, not this field.
- `connectionKey` stays unset; the emitter falls back to
  `rctx.activeConnection`, as `rule-fanout-lookup-join` does.

### 4. What the fan-out drops

`JoinNode.usingColumns` is a label used only by EXPLAIN to render `JOIN
USING(...)`; the fan-out has no equivalent field. A `USING` join that takes this
path renders as a fan-out instead. `buildJoinAttributes` ignores `usingColumns`,
so no attribute layout changes. Record it as a `NOTE:` at the construction site.

Row estimates also change slightly: `FanOutLookupJoinNode` reports the outer's
cardinality for an at-most-one branch (an upper bound for `inner`, exact for
`left`), where `JoinNode` used `estimateJoinRows`. Note it; do not chase it.

## Edge cases & interactions

- **Inert in-tree.** Every shipped module reports `expectedLatencyMs = 0`, so
  `toBatchedOuter`'s latency gate declines and `ruleJoinPhysicalSelection`
  behaves exactly as today. The full golden-plan sweep must be unchanged — the
  primary regression guard.
- **Zero-match outer row under `atMostOne-left`.** The branch yields nothing,
  `composeOuterRows` emits one NULL-padded row. Assert the result rows, not just
  the plan shape.
- **Outer smaller than the read-ahead window.** The cardinality gate
  (`batchedOuterMinRows`, default 256) normally prevents this, but tests lower
  it to 0. Drive an outer of 1 row and an outer of 3 rows through the batched
  driver and assert both the row set and the order.
- **A non-`concurrencySafe` inner module** (`concurrencyMode: 'serial'`): the
  branch spec's `concurrencySafe` is false, so the emitter wraps the branch in a
  connection lock. Assert the plan still forms and returns correct rows; a serial
  module makes the batching pointless but must not make it wrong.
- **Nesting inside another fan-out.** Two joins in one query where both qualify:
  the inner fan-out's branch forks are nested inside the outer's. Confirm the
  strict-fork counters unwind (run the test with `QUEREUS_FORK_STRICT=1`).
- **A `Filter` already inside the branch child** — from
  `feat-index-nested-loop-over-pushed-constraints`'s `reapplyDeclinedPushed`, or
  from `selectPhysicalNode`'s collation residual. The branch child then reads
  `Filter(ON) / Filter(residual) / IndexSeek`. Both filters only remove rows.
  Assert the composed shape and that `outputAttrs.length` still matches
  `child.getAttributes().length` (the node's constructor validates this).
- **A branch child that is `Alias(Project(Filter(IndexSeek)))`.** `newInner` is
  the whole rebuilt subtree, not a bare leaf. `emitCallFromPlan` handles it, but
  assert it, because `outputAttrs` is taken from the subtree top.
- **Composite unique key where only some columns come from the join.** The proof
  reads the combined constraint list, so `on b.tenant = o.tenant` plus a pushed
  `b.id = 5` should prove at-most-one against a `(tenant, id)` primary key. Test
  it.
- **A non-unique secondary-index seek.** The proof fails, no batched candidate
  is offered, the plan is whatever it is today. Test that it does *not* become a
  fan-out.
- **A `NOCASE` join key over a `BINARY` unique column.** `collationSafe` returns
  false, no batched candidate. Test it — this is the case that would otherwise
  produce a runtime `CONSTRAINT` error.
- **`semi` / `anti` / `exists … as` joins.** No batched candidate; the plain or
  index-nested-loop join stands. Test at least the existence case, since it also
  skips hash and merge.
- **Strict-fork test-harness false positive.** Executing a fan-out plan under an
  `ORDER BY` trips a documented strict-harness-only invariant (the Sort/Project
  above the fan-out creates a row slot while forks are counted active); see the
  guard comments in `test/optimizer/parallel-fanout.spec.ts`. Follow the existing
  convention: skip *execution* assertions under `QUEREUS_FORK_STRICT`, keep the
  plan-shape assertions running.
- **Both orientations qualify.** Existing tie-breaking is strict `<` in a fixed
  order, so an exact tie keeps the earlier candidate. Preserve that: a plan must
  not flip its drive side on a coin toss. Decide and document where the two
  batched candidates sit in that order (suggest: after their serial
  counterparts, un-mirrored before mirrored).
- **`toBatchedOuter` called twice on the same node.** Its idempotence gate
  (`outerMode === 'batched'`) must still hold when `ruleFanOutBatchedOuter` later
  visits a node this rule already flipped.

## Tests

Use the `HighLatencyMemoryModule` (`readonly expectedLatencyMs = 25`) and the
`db.optimizer.updateTuning({... parallel: { ...before, batchedOuterMinRows: 0 }})`
pattern from `test/optimizer/parallel-fanout-batched.spec.ts`. Plan shapes come
from `query_plan(?)`; look for `op === 'FANOUTLOOKUPJOIN'` and read `outerMode`
out of its `properties` JSON.

- Primary-key inner join over the high-latency module: the plan is a fan-out in
  `batched` mode with one `atMostOne-inner` branch, wrapped over an
  `EagerPrefetch` outer, and the rows match the same query run against the plain
  memory module.
- The same query with a LEFT join: one `atMostOne-left` branch; unmatched outer
  rows come back NULL-padded.
- Zero-latency control: no fan-out, plan identical to today.
- Latency present but `batchedOuterMinRows` restored to its default with a small
  outer: no fan-out (the cardinality gate holds).
- Non-unique secondary index: no fan-out.
- `NOCASE` join key over a `BINARY` unique column: no fan-out.
- Existence join with a high-latency inner: no fan-out.
- Composite primary key half-supplied by a pushed predicate: fan-out forms.
- Direct unit tests for the at-most-one helper, covering: primary key, unique
  constraint, partial unique constraint (declined), range constraint on a key
  column (declined), collation mismatch (declined).
- Full `yarn test` golden-plan sweep unchanged.
