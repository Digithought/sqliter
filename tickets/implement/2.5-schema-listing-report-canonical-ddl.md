# `schema()` reports definitions that re-create something else

## Background

`select sql from schema()` is the listing users read to find out how a table or index was
declared. The engine has one canonical definition writer — `generateTableDDL` /
`generateIndexDDL` in `schema/ddl-generator.ts` — and `schema()` uses it for exactly one case
(a maintained table, via `generateMaintainedTableDDL`). Every other row is written out by hand
from a small subset of the schema.

Nothing in the engine re-parses this text, so this is a **reporting** defect, not corruption.
It is still user-visible: the `.schema` command in the CLI prints this column, and the reported
text is what a user would copy to re-create the object.

## What was reproduced

**Tables.** The plain-table branch renders only column names and type tokens:

```
create table probe_t (a integer null, b text null, primary key (a));

schema().sql      →  create table "probe_t" ("a" INTEGER, "b" TEXT) using noalter()
generateTableDDL  →  CREATE TABLE "main"."probe_t" ("a" INTEGER NULL PRIMARY KEY, "b" TEXT NULL) USING noalter
```

Missing: the key, the nullability markers, defaults, collations, and every constraint. Both
omissions flip meaning rather than abbreviating — with the session's `default_column_nullability`
set to `not_null`, re-running the reported text gives NOT NULL columns; and a `CREATE TABLE` with
no `PRIMARY KEY` clause means "keyed by every column", so the reported text re-parses to a
different key than the one it is describing.

**Indexes.** `buildIndexCreateSql` has the same problem:

```
create unique index ux_b on it (b) where b is not null;

schema().sql  →  CREATE INDEX "ux_b" ON "it" ("b" COLLATE BINARY)
```

`UNIQUE` is gone, the `WHERE` predicate is gone, tags are gone, and a spurious
`COLLATE BINARY` is added. Re-running that text creates an ordinary full index where a unique
partial one was declared.

## Root cause

One code site — `packages/quereus/src/func/builtins/schema.ts` — carries two hand-rolled DDL
writers (`buildIndexCreateSql` and the inline `createSql` branch) alongside a call to the
canonical one. Both render a subset. This is the same defect as
`shadow-rebuild-render-through-canonical-ddl`, at a different site and with a different blast
radius; the two are independent and can land in either order.

## Shape of the fix

Delete both hand-rolled writers and call `generateTableDDL(tableSchema)` / 
`generateIndexDDL(indexSchema, tableSchema)`.

**Call them without a `db` argument.** The no-`db` form fully qualifies the name, always emits
`USING`, and always annotates nullability — so every reported row re-parses to the object it
describes in any session. This also matches the maintained-table arm right next to it
(`generateMaintainedTableDDL` resolves its context with no `db`), so the listing becomes
internally consistent. The visible cost is a longer, uppercase, schema-qualified string where
today's output is short and lowercase; that is a deliberate change, not a regression — say so in
a comment.

**The exposed-implicit-index loop needs an adapter.** `exposedImplicitIndexes` returns
`SyntheticExposedIndex` (name / columns / predicate / tags), not an `IndexSchema` — these are
implicit covering structures for UNIQUE constraints that the backend did not materialize
(store mode). They are unique by construction, so lift them to the shape `generateIndexDDL`
wants with `unique: true` rather than keeping a second writer alive for them.

Keep the existing `try { … } catch { createSql = null }` guard — the listing must not fail
because one object cannot be rendered.

## Expected behaviour

For every row `schema()` reports, the `sql` column parses back to the same object it describes —
key, nullability, defaults, collations, constraints, tags for a table; uniqueness, predicate and
tags for an index.
