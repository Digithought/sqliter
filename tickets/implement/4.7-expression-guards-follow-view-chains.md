# Widen the CHECK / DEFAULT / generated drop guards onto the reachability closure

`DROP TABLE`, `DROP VIEW`, `DROP MATERIALIZED VIEW` and `ALTER TABLE … DROP
COLUMN` refuse when another table's CHECK constraint, column `DEFAULT` or
`GENERATED ALWAYS AS` body **names** the dropped object. They do not refuse when
that body **reaches** the object through a view. The reachability closure that
answers the second question already exists —
`schema/object-dependency-closure.ts`, built by
`assertion-guards-follow-view-chains-and-schemas` and consumed by both assertion
guards. This ticket moves the CHECK / DEFAULT / generated family onto it, so the
catalog holds one definition of "reaches" rather than two.

## What was measured

Run in-session against `main` at `4aa7c763`, memory module, one `Database` per
case (`node --import ./packages/quereus/register.mjs <scratch>.ts`). Every case
below was **accepted** and left the referencing table unwritable:

| # | shape | drop | next write fails with |
|---|---|---|---|
| A | `check (n < (select max(v) from vv))`, `vv` = `select v from t` | `drop table t` | `Table 't' not found in schema path: main` |
| B | same | `alter table t drop column v` | `Column not found: v` |
| C | two-view chain `v2` → `v1` → `t` | `drop table t` | `Table 't' not found in schema path: main` |
| D | `n integer default ((select max(v) from vv))` | `drop table t` | `Table 't' not found in schema path: main` |
| E | two-view chain, drop the MIDDLE view | `drop view v1` | `Table 'v1' not found in schema path: main` |
| I | materialized view in the chain | `drop table t` | `materialized view 'mv' is stale; a source changed in an incompatible way` |
| Q | `g integer generated always as ((select max(vv.v) from vv))` | `drop table t` | `Table 't' not found in schema path: main` |
| R | cross-schema: `temp` CHECK → `temp` view → `main.t` | `drop table main.t` | `Table not found: main.t` |

Three control shapes were checked as **currently allowed and required to stay
allowed**:

| # | shape | verdict |
|---|---|---|
| F | plain view over `t`, no constraint reads the view | allowed — the engine's stated asymmetry, `41.10.4` §5 |
| G | `create view vv as with t as (select v from u) select v from t` — the CTE merely shadows the name | allowed |
| H | `check (new.n > 0)` on `x`, dropping a real table called `new` | allowed |
| P | other table's `check (… from uv)`, `uv` over a THIRD table with a like-named `v` | allowed — `41.10.2` §21's shape, one view deeper |
| S | cross-schema shadow: bare name in `temp` that `temp` itself holds, through a `temp` view | allowed |

## The change, site by site

### 1. `schema/object-dependency-closure.ts` — a root-only walk option

`reachableObjects` walks every body with `collectTableRefsInAst(body, resolve)`
and no options. That is correct for an assertion root and for every view body
below it, and **wrong for the roots this ticket adds**: a table's CHECK / DEFAULT
/ generated body owns the `new.` / `old.` namespace, so without
`TableRenameOpts.rowImageContext` a table literally called `new` lands in the
reach and false-refuses its own drop (control H). The module's header already
records exactly this and names this ticket as the consumer that must thread it.

Add a fifth parameter applied to the ROOT body only:

```ts
export function reachableObjects(
	db: Database,
	root: AST.AstNode,
	homeSchemaName: string,
	resolvers: ObjectRefResolvers,
	rootOpts?: TableRenameOpts,
): ObjectReach
```

and inside the breadth-first loop:

```ts
collectTableRefsInAst(current.body, current.resolve,
	current.ownerKey === undefined ? rootOpts : undefined)
```

`ownerKey === undefined` identifies the root uniquely — every child gets one from
`childBody`. The existing assertion callers pass nothing and are unaffected.
Replace the header's "A consumer rooting at one of those (`…`) must thread the
option onto the ROOT body's collection only" note with a statement of what the
parameter now does.

### 2. `schema/expression-dependents.ts` — probes return a path, not a boolean

Both entry points keep their signatures and their walk order
(`tablesProbedTargetFirst`, own-table first). What changes is the per-expression
probe: instead of one AST walk, build the reach from that expression and probe
every body in it.

`ExpressionProbe` becomes path-returning, since a caller needs to know *how* the
match was reached in order to phrase the error:

```ts
/** The reach path to the match — EMPTY for a direct match — or `undefined` for no match. */
type ExpressionProbe = (expr: AST.Expression | undefined) => ReadonlyArray<string> | undefined;
```

`findInChecks` / `findInColumnExpressions` return `{ describe, path }` instead of
a bare string, and `ExpressionDependent` gains `readonly path: ReadonlyArray<string>`.

**Table verb** (`findTableExpressionDependent`) — the whole probe becomes:

```ts
const names: ExpressionProbe = expr => expr &&
	reachableObjects(db, expr, table.schemaName, resolvers, { rowImageContext: true })
		.namerOf(targetKey)?.path;
```

`namerOf` is breadth-first, so the path is the shortest chain, and it is empty
exactly when the match is direct — which is what keeps the existing direct
message spelling unchanged.

**Column verb** (`columnProbe`) — the column question is not "does the reach
contain this key?" but "does any body in the reach name this column?", so it
loops `reach.bodies` the way `assertNoAssertionNamesColumn` already does. The
seeded/unseeded split stays load-bearing and applies to the ROOT body only:

```ts
return expr => {
	if (!expr) return undefined;
	const reach = reachableObjects(db, expr, homeSchemaName, resolvers, { rowImageContext: true });
	for (const reached of reach.bodies) {
		// Seeded ONLY on the probed table's own root body: a CHECK / DEFAULT there is
		// written against the row being written, so an unqualified name binds the owning
		// table implicitly. A view body below it is a relation with no such seed, and the
		// root body of ANOTHER table's expression binds that table's row, not ours.
		const seeded = ownTable && reached.ownerKey === undefined;
		const hit = seeded
			? columnReferencedInCheckExpression(reached.body, probedTableName, columnName,
				reached.resolve, targetKey, resolveColumnInSource)
			: columnReferencedInAst(reached.body, probedTableName, columnName,
				reached.resolve, targetKey, resolveColumnInSource);
		if (hit) return reached.path;
	}
	return undefined;
};
```

`columnProbe` needs the scanned table's schema name to root the closure, so give
it that plus `db` and `resolvers`; the call site already has all three.

The two deliberate own-table skips in `findInColumnExpressions` — the dropped
column's own DEFAULT, and every own-table generated body — stay exactly as they
are. Verified they are still right: an own-table generated body reading its own
`v` through a self subquery is already refused by `runDropColumn`'s
`generatedColumnDependencies` map (case J: `Cannot drop column 'v' from 't': it
is referenced by generated column 'g'`).

Delete the `Known gap, tracked by expression-guards-follow-view-chains` paragraph
from the module header and replace it with what the closure now buys, mirroring
`assertion-drop-guard.ts`'s two-bullet direct/indirect explanation.

### 3. The two guard call sites — name the chain

A user told that `ck` on `x` blocks `drop table t` will read `ck`'s body, find no
mention of `t`, and be stuck. Reuse `describeReachPath` so all four guard
families phrase an indirect refusal identically (`assertion-drop-guard.ts` §
`refersTo` is the pattern to copy — direct keeps the old wording, indirect gets a
new clause).

`expression-drop-guard.ts`:

```
direct   (unchanged):  cannot drop table 'main.t': it is referenced by CHECK constraint 'ck' on table 'x' — drop or redefine it first
indirect (new):        cannot drop table 'main.t': CHECK constraint 'ck' on table 'x' reaches it through view 'vv' — drop or redefine it first
```

`drop-column-guards.ts` (`refuseColumnExpressionDependent`):

```
direct   (unchanged):  Cannot drop column 'v' from 't': it is referenced by CHECK constraint 'ck' on table 'x'
indirect (new):        Cannot drop column 'v' from 't': CHECK constraint 'ck' on table 'x' reaches it through view 'vv'
```

Multi-hop renders as `through view 'v2' -> view 'v1'`, materialized views as
`materialized view 'm'` — `describeReachPath` already produces both, and
`95-assertions.sqllogic` §~992–1124 pins the spelling for the assertion family.

Keeping the DIRECT wording byte-identical is what stops `41.10.2` §1/§19/§20 and
`41.10.4` §1–§9 from needing edits.

Also fix `drop-column-guards.ts`'s header, which currently ends "the two
expression guards do not yet, which is the gap
`expression-guards-follow-view-chains` tracks" — that sentence becomes false.

## Expected behavior

Refused, `StatusCode.CONSTRAINT`, nothing applied — cases A–E, I, Q, R above,
plus `drop view vv` when a CHECK reaches `vv` only through a further view.

Still allowed — cases F, G, H, P, S above. These are the false-refusal shapes the
widening must not break; they are the reason this consumes the shared closure
(whose walk is scope-aware by construction) rather than growing a name-collecting
second one.

## Known interaction — do not try to fix here

An **own-table** CHECK whose subquery reads a VIEW and names a column
unqualified already false-refuses today, before any change here:

```sql
create table t (id integer primary key, v integer);
create table u (id integer primary key, v integer);
create view uv as select v from u;
alter table t add constraint ck check (id < (select max(v) from uv));
alter table t drop column v;
-- Cannot drop column 'v' from 't': it is referenced by CHECK constraint 'ck'   ← wrong
```

Cause: `buildColumnSourceResolver` (`schema/column-source-resolver.ts`) answers
"does source `s.t` expose column `col`?" by `getTable(t)?.columnIndexMap`, and a
VIEW is not a table there — so it returns `false`, the seeded probe concludes the
unqualified `v` binds to the seeded own table, and refuses. The qualified
spelling (`max(uv.v)`) is correctly allowed, and the other-table (unseeded) path
is correctly allowed (control P). This is the same missing capability —
`ViewSchema` carries no resolved output column list — that
`drop-column-guard-blind-to-star-reexposure` owns; an arm has been appended
there. **Consequence for this ticket: write every own-table-through-a-view test
case with a qualified column reference**, and do not add a control that depends
on the unqualified own-table spelling being allowed.

## Notes

- Cost is naturally bounded: the closure only expands objects a body actually
  names, so an expression naming no view costs one walk, exactly as today. No
  new `NOTE:` needed beyond the module header's existing one.
- `assertNoExpressionDependsOn` and the DROP COLUMN guards stay wired to the
  user-facing emitters only — rollback, catalog import and the declarative
  differ must not be vetoed. Nothing about that changes.
- Column lineage through a **star** projection (`create view v as select * from
  t`) still hides the column from the column verb after this lands. That is
  `drop-column-guard-blind-to-star-reexposure`, which is sequenced after this
  ticket precisely so one answer covers both families. The table verb has no
  such hole — it matches the object, not a column.
