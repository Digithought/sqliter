# Why

Everything the benchmark suite measures today runs over an in-memory key-value provider.
That is deliberate — it isolates store-layer cost from disk cost and it is deterministic
enough to run on every `yarn bench`. But the backend a real Node deployment uses is
LevelDB, and it has no measured numbers at all.

This ticket builds the *plumbing* for a disk-backed benchmark run: a temporary-directory
helper, an opt-in LevelDB backend, and a way for a row to be printed as advisory rather
than counted toward pass/fail. The measurement that motivates it all —
`bench-leveldb-read-cost`, split out of this ticket — lands on top.

# What already landed

## `bench/lib/tempdir.mjs` (new)

Fresh directory per call under `os.tmpdir()`, never in the working tree. Name shape is
`quereus-bench-<pid>-<label>-<random>` — the PID comes first, immediately after the
prefix, so the sweep can read it with one split.

`createBenchTempDir(label)` returns `{ dir, basePath, remove() }`; `basePath` is the
forward-slash form the LevelDB provider needs on Windows (same conversion
`test/logic.spec.ts` does). `remove()` is idempotent and **throws** if removal fails after
its retries (`rmSync` with `maxRetries: 5, retryDelay: 100`, which is what absorbs the
transient Windows `EBUSY` after a LevelDB close).

Removal has three layers because no one layer covers every way a run ends:

1. `remove()` in the benchmark's own teardown — the normal path.
2. A process-level `exit` hook in the worker — covers a throw, and covers the parent
   vanishing (`child.mjs` disconnects and calls `process.exit`, which runs exit handlers).
3. `sweepBenchTempDirs(forcePids)`, called by the **parent**. This layer exists because
   layer 2 structurally **cannot** cover `SIGKILL`, which is exactly how `run.mjs` kills a
   worker that blew `BENCH_TIMEOUT_MS` and how its SIGINT handler kills the active worker
   on Ctrl+C. The ticket's original claim that a process-level hook covers the killed
   worker was wrong; this is the correction.

The sweep never deletes by prefix alone — it removes a directory only when the PID in its
name is either force-listed by the caller or no longer alive (`process.kill(pid, 0)`;
`ESRCH` means gone, `EPERM` means alive and someone else's). So two concurrent bench runs
cannot delete each other's databases. PID reuse can make the sweep skip a genuinely stale
directory; that leaves litter for the next run, which is the side of the trade that cannot
corrupt a measurement.

`run.mjs` tracks `killedWorkerPids`, force-passes them, sweeps after the run and
(synchronously) inside its SIGINT/SIGTERM handler before exiting.

## `bench/lib/leveldb-backend.mjs` (new)

The one lazy `@quereus/plugin-leveldb` import site, cached per process (a failed load is
remembered too, so a doomed native-binding load is not paid per benchmark). Exports:

- `LEVELDB_ENV_VAR` = `QUEREUS_BENCH_LEVELDB`.
- `levelDBEnabled()` — treats `0`, `false`, `off`, `no` and empty as "no", so someone who
  set the variable to turn the rows *off* is not given a much longer run.
- `levelDBSkipReason()` — opt-in checked first (free, and overwhelmingly the answer), then
  the plugin load. Returns a reason naming the variable, or the load error.
- `createBenchLevelDBProvider(label)` — provider over a fresh temp directory, options left
  at their defaults (**`syncCommits: true`**, what a deployment runs). Exported because
  `bench-leveldb-read-cost` drives the key-value layer directly, with no `Database`.
- `openLevelDBDatabase()` — hands the provider to `openStoreDatabase(provider)`, so module
  construction, registration and close discipline are not duplicated. Close order is
  database → module (releases the LevelDB directory lock) → directory. A module-close
  failure is printed to stderr and not rethrown (a lost close race must not redden a
  build), but the directory removal still runs, and if *that* fails both errors are thrown
  together.

## `bench/lib/backends.mjs`

`STORE_LEVELDB_BACKEND` is exported with `informational: true`, `skipWorkload` asking
`levelDBSkipReason()` then `storeLoadFailure()`, and **no `openCounting`** — with the
reason at the site: `createCountingProvider(map, 'all')` wraps an in-memory map, not an
arbitrary provider, so this backend contributes timings only.

`BenchBackend.informational` is a new optional field, validated in `validateBackends`
(a truthy non-boolean would leave rows gated while their author believed them advisory).
`expandBackends` stamps `informational: true` onto every benchmark a declaring backend
produces, so no suite file can forget it, and sets no key at all otherwise.

**`STORE_LEVELDB_BACKEND` is deliberately NOT in `BACKENDS` yet** — that is the decision
the measurement below has to settle.

## The `informational` flag, end to end

- `discover.mjs` — `Benchmark.informational` typedef, `loadSuite` shape validation,
  `selectBenchmarks` carries a normalized strict boolean, and a new `informationalNames(suites)`
  returns every advisory full name **from the whole suite set** (not from the selection,
  because a guard must still be refused under a `--filter` that excluded its target, and a
  baseline can name a row this run never selected).
- `compare.mjs` — `compareRun(..., { informational: Set })`; `compareOne` sets
  `gated: status === 'regression' && !informational` and notes
  `'informational — reported, never gated'`. The **status still says `regression`** when the
  number moved; only gating changes.
- `run.mjs` — cyan `informational` marker as a trailing word (the way `unstable` and
  `pinned` are printed), on measured, skipped and failed rows alike; `checkRatioGuards`
  reports a guard naming an advisory row as **`misconfigured`**, checked *before* every
  other case so it cannot hide behind "skipped by `--filter`"; a yellow summary line for
  advisory regressions so a red status next to exit 0 does not read as a harness bug; and
  `informational: [...].sort()` in the results JSON, so `bench-regression-gate` can find
  the advisory rows without parsing names for an `@` suffix.

Verified so far: `node --check` passes on all six files, and `loadSuites()` still
enumerates 5 suites / 71 benchmarks with 0 informational (the flag is inert until the
backend joins `BACKENDS` or `bench-leveldb-read-cost` sets it directly).

# Remaining work

## Measure, then decide `BACKENDS` membership

This is the load-bearing decision and it must not be handed to the reviewer as a judgement
call. `execution` and `mutation` hold 19 workloads that `expandBackends` fans over every
entry of `BACKENDS`, and their sizes are fixed by the shared workload definition — a
LevelDB arm cannot be sized smaller without renaming the workload for every backend.

Time these two, with the backend temporarily added to `BACKENDS`:

- `mutation/bulk-insert-10k@store-leveldb` — 20 batched inserts of 500 rows, and the
  `own-database` lifecycle means a whole LevelDB is opened and closed **inside every timed
  call**.
- `mutation/single-row-insert-1k@store-leveldb` — 1 000 separate `insert` statements.
  (The original ticket called this `insert-1k-rows`; the workload's real name is
  `single-row-insert-1k` — see `bench/workloads/mutation.mjs`.) With `syncCommits: true`
  this is plausibly one fsync per row, so it is the one most likely to blow the budget.

`QUEREUS_BENCH_LEVELDB=1 yarn workspace @quereus/quereus bench --filter @store-leveldb`
is the run. Calibration checks `minSamples` (5) **before** `maxTotalMs`, so five samples
plus warmup (minimum 2 calls) is the floor — roughly seven calls — and `BENCH_TIMEOUT_MS`
(120 s) covers `setup` as well.

Then decide, and write the measured per-call numbers and the decision into the handoff
either way:

- comfortably inside the timeout → add `STORE_LEVELDB_BACKEND` to `BACKENDS` and update the
  "deliberately NOT here" comment on that array;
- near it → keep the backend **exported-only**, so only `bench-leveldb-read-cost`'s own
  arms use it, and record the measured cost in the comment that says why. Pinning a row
  with `iterations`/`warmup` is the third option and needs its reason written down.

## Verify the cleanup, on Windows

- Normal run with the variable set: afterwards `%TEMP%` holds no `quereus-bench-*`.
- Ctrl+C mid-benchmark: same.
- A worker `SIGKILL`ed by the parent timeout: same. Force it by temporarily lowering
  `BENCH_TIMEOUT_MS`, or by killing a worker by PID from another shell.
- With the variable unset: `yarn bench` completes and every LevelDB row prints a skip
  reason **naming the variable**.

## Confirm the flag actually ungates

An informational row that regresses against a baseline must not change the exit code.
Cheapest check: run with the backend in `BACKENDS`, save the results file, re-run with
`--baseline latest` on a machine or moment noisy enough to move the number — or edit a
copy of the baseline's median for one advisory row and compare against that.

## Document it

Nothing has been written yet. `docs/benchmarking.md` needs, in the "Storage backends"
section and the table there:

- the opt-in (`QUEREUS_BENCH_LEVELDB=1`), and that rows skip visibly without it;
- what `informational` means, that it is declared on the backend, that it is printed as a
  marker, that no ratio guard may name such a row (`misconfigured`), and that it never
  enters a verdict;
- the temp-directory lifecycle and the three cleanup layers, including the honest statement
  that a `SIGKILL`ed worker is cleaned up by the *parent's* sweep, not by its own hook;
- that `syncCommits` is left at its default `true` and is the biggest term in the cost;
- **that none of this enters `yarn check`** — `bench-regression-gate` budgets its fast mode
  around the memory backend plus the in-memory store provider, and should not have to
  rediscover that.

A `bench:leveldb` script in `packages/quereus/package.json` is a convenience, not a
requirement; add it only if the backend joins `BACKENDS`.

# Edge cases & interactions

- **Do not compare a LevelDB number against an in-memory number as a ratio guard.** The
  backend-dimension work already forbids cross-backend guards; the `misconfigured` refusal
  above is that rule made mechanical.
- **The plugin may fail to load** (native binding, platform). That is a `skip()` with the
  load error as its reason, not a failure — a machine that cannot run LevelDB still
  completes `yarn bench`. Already implemented; still worth confirming by hand once.
- **LevelDB holds an exclusive directory lock.** Each benchmark runs in its own forked
  process and each `createBenchTempDir` call mints its own directory, so nothing shares a
  path — including two `fn` calls of the same `own-database` benchmark.
