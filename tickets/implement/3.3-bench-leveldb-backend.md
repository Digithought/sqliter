# Why

Everything the benchmark suite measures today runs over an in-memory key-value provider.
That is deliberate — it isolates store-layer cost from disk cost and it is deterministic
enough to run on every `yarn bench`. But the backend a real Node deployment uses is
LevelDB, and it has no measured numbers at all.

This ticket builds the *plumbing* for a disk-backed benchmark run: a temporary-directory
helper, an opt-in LevelDB backend, and a way for a row to be printed as advisory rather
than counted toward pass/fail. The measurement that motivates it all —
`bench-leveldb-read-cost`, split out of this ticket — lands on top.

# Architecture

## Opt-in, never gated

Disk-backed numbers are not reproducible: page cache, filesystem and disk type dominate,
and none of them is a property of this repository's code. So:

- The LevelDB backend runs only when explicitly asked for — the environment variable
  `QUEREUS_BENCH_LEVELDB=1` is enough, and matches how `yarn test:store` is already
  selected. A `bench:leveldb` script wiring it up is a convenience, not a requirement.
- When not asked for, every LevelDB benchmark **skips visibly** through the existing
  `skip()` entry point, with a reason naming the variable. A missing row reads as
  "unchanged" to anyone diffing two runs; that is the failure mode `skip()` exists to
  prevent.
- Its rows are marked **informational** in the printed output and must never contribute to
  a pass/fail verdict — not the ratio guards, not the regression gate that
  `bench-regression-gate` will build on top of this.

## What was already established (do not re-derive)

The investigation that produced this ticket read the whole harness. Findings:

- **`@quereus/plugin-leveldb` is already a devDependency of `@quereus/quereus`** (see its
  `package.json`), so no dependency work is needed. `createLevelDBProvider` is exported
  from the package root.
- **The store package must stay behind one lazy import site.** `run.mjs` imports every
  suite file in the *parent* purely to enumerate benchmark names, so a static
  `import '@quereus/store'` anywhere reachable from `backends.mjs` would let an unbuilt
  `packages/quereus-store/dist` kill the whole run. `bench/lib/store-counters.mjs` is that
  one site and its header says so. The LevelDB plugin is a *second* package and needs its
  own lazy site — put it in a new `bench/lib/leveldb-backend.mjs` rather than growing
  `store-counters.mjs` (already 400 lines).
- **`openStoreDatabase(existingProvider)` in `store-counters.mjs` already accepts a
  provider.** So the LevelDB backend needs only to build a `LevelDBProvider` over a temp
  directory and hand it to that function — the isolation wrapper, module registration and
  close discipline all come for free, and the single-import rule stays intact.
- **`createCountingProvider(map, 'all')` wraps an in-memory map, not an arbitrary
  provider** — so the LevelDB backend has no `openCounting`, exactly as the memory backend
  has none. That is the honest report: it contributes timings, not storage-round-trip
  counts. Say so in its descriptor comment.
- **`BenchBackend.skipWorkload` already composes** with a binder's own `skip` (backend
  asked first, its reason wins) — see `composeSkip` in `backends.mjs`. The env-var check
  and the plugin-load check both belong there, checked in that order, so an unset variable
  is reported without paying a native-binding load.
- **The provider's `basePath` needs forward slashes on Windows** — `logic.spec.ts` passes
  `dir.replace(/\\/g, '/')` and this must do the same.
- **`Comparison.gated` already exists** in `compare.mjs` and `regressions` is
  `comparisons.filter(c => c.gated).length`, which drives `exitCode = 1` in `run.mjs`. So
  "never contributes to a verdict" is a small change: `compareRun` takes the set of
  informational full names and `compareOne` sets `gated: status === 'regression' &&
  !informational`.
- **`checkRatioGuards` in `run.mjs`** resolves guards by `suite/name`. No guard names a
  LevelDB row today, and one that did would be a guard-authoring mistake — report it as
  `misconfigured` (the status that already exists for a guard naming something it must
  not) rather than silently evaluating it.
- **Print the marker the way `unstable` and `pinned` are printed** — a trailing word on the
  row, not a column. `printTable` already does exactly this for those two.

## Temporary directories

Fresh directory per run, inside the OS temp directory — **never inside the repository
working tree** — and removed in teardown. A LevelDB database left behind silently changes
the next run's numbers and litters the machine.

`logic.spec.ts` already does this correctly and is the pattern to copy: build the path
under `os.tmpdir()` with a timestamp-plus-random suffix, `mkdirSync` it, and on teardown
close the module first (ignoring close errors, which LevelDB lock contention can produce)
and then `rmSync(dir, { recursive: true, force: true })`. Put it in `bench/lib/tempdir.mjs`
once rather than in each benchmark.

Removal must survive a file still being held: teardown runs in a worker that is about to
exit, and a failure to remove must be **reported, not swallowed**. Register a
process-level last-resort cleanup so a worker killed by the parent's timeout does not
leave a database behind.

# Edge cases & interactions

- **A killed worker leaves a database directory.** The parent kills a worker on timeout
  with `SIGKILL`, which runs no teardown. The last-resort cleanup above is what covers it;
  verify by killing a run mid-benchmark and checking the temp directory.
- **LevelDB holds a lock.** Two concurrent bench runs on the same machine must not
  collide — the per-run random suffix handles it, but only if it is per *worker*, not per
  suite import. Each benchmark runs in its own forked process, so a module-level directory
  minted at import time is per-worker and therefore correct; a directory minted at
  *suite-definition* time would not be.
- **The plugin may fail to load** (native binding, platform). That is a `skip()` with the
  load error as the reason, not a benchmark failure — a machine that cannot run LevelDB
  should still complete `yarn bench`.
- **Do not compare a LevelDB number against an in-memory number as a ratio guard.** The
  backend-dimension work already forbids cross-backend guards; this is the case that makes
  the rule concrete.
- **Wall-clock is the real risk of putting LevelDB in the shared backend dimension.**
  `execution` and `mutation` hold 19 workloads that `expandBackends` fans over every entry
  of `BACKENDS`, and their sizes are fixed by the shared workload definition — a LevelDB
  arm cannot be sized smaller without renaming the workload for every backend. A 10 000-row
  bulk insert on real disk with `syncCommits` on (the provider default) may be seconds per
  call. Calibration checks `minSamples` (5) *before* `maxTotalMs`, so five samples plus
  warmup (minimum 2 calls) is the floor — roughly seven calls — and `BENCH_TIMEOUT_MS`
  (120 s) covers `setup` as well. **Measure `mutation/bulk-insert-10k` and
  `mutation/insert-1k-rows` on LevelDB before committing to adding the backend to
  `BACKENDS`.** If either approaches the timeout, the honest answer is to pin it with the
  reason written down, or to keep the backend descriptor exported but out of the shared
  `BACKENDS` array so only `bench-leveldb-read-cost`'s own arms use it. Whichever way it
  goes, record the measured per-call cost and the decision in the handoff — do not leave it
  as a judgement call for the reviewer.
- **Nothing here enters `yarn check`.** `bench-regression-gate` explicitly budgets its fast
  mode around the memory backend plus the in-memory store provider. Say so in the docs so
  that ticket does not have to rediscover it.

# Tests

- With `QUEREUS_BENCH_LEVELDB` unset, `yarn bench` completes and every LevelDB row prints a
  skip reason naming the variable.
- With it set, a full run completes, and afterwards the OS temp directory contains no
  `quereus-bench-*` directories.
- A run interrupted mid-benchmark (Ctrl+C, and a worker `SIGKILL`ed by the parent timeout)
  also leaves none. Verify on Windows.
- An informational row that regresses against a baseline does not change the exit code.
