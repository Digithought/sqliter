# `CREATE TABLE` must ask the storage backend whether it could write the definition down

## Background — what breaks today

A JavaScript string can contain an *unpaired surrogate*: half of the two-code-unit pair
that encodes a character outside the basic range, with the other half missing. Such a
string has no valid UTF-8 encoding. The persistent store keys and stores text as UTF-8
bytes, so it refuses one.

`CREATE TABLE … using store` accepts a definition whose **generated DDL text** contains
an unpaired surrogate — a quoted column name, a `default '…'` string literal, a string
literal inside a `check` — because nothing asks the store at create time. Two outcomes,
depending on what happens next:

- the table is read or written at least once → the encoding error is raised on *that*
  statement, blaming an INSERT or SELECT for a problem in the CREATE;
- **the table is never touched → nothing raises at all.** The catalog write that would
  have failed rides a `SchemaChangeNotifier` listener (try/catch, log only) and then the
  store's async persist queue (`.catch`-log). Both swallow. The table is simply absent
  after the database is reopened, and the only trace is a `console.warn`.

The second case is silent data loss, and it is the reason this ticket is first in its
family.

## The mechanism that already exists

`assertCatalogObjectPersistable(db, kind, object)`
(`packages/quereus/src/schema/catalog-persistability.ts`) is a synchronous veto: it asks
every registered virtual-table module whether it could durably persist `object`, and lets
the first refusal propagate out of the statement. `CREATE VIEW`, `CREATE MATERIALIZED
VIEW` and the `ALTER TABLE … RENAME` dependent scan all call it. The store module's
implementation (`store-module-catalog.ts` ~277) runs *exactly* the derivation the write
path runs, so the veto and the write cannot disagree.

The hook already accepts a `'table'` kind — today only the RENAME pre-flight passes one.
`createTable` never calls it. That is the whole defect.

## The change

One call, in the guard block `SchemaManager.createTable` already maintains (the block
holding `validateDefaultDeterminism`, `assertNoDuplicateConstraintNames`,
`assertNoDuplicateUniqueConstraints`), placed **before `module.create`**:

```ts
assertCatalogObjectPersistable(this.db, 'table', baseTableSchema);
```

### Why before `module.create`, and why `baseTableSchema` is the right object

- **Before `module.create`** for the same reason the neighbouring duplicate-UNIQUE guard
  is there: a refusal must leave no storage behind, so the statement is a clean no-op.
- **`baseTableSchema` rather than `completeTableSchema`** because the post-`create`
  object does not exist yet at that point. This is safe: the only thing the veto reads is
  the *text* of the generated definition, and the only difference `finalizeCreatedTableSchema`
  introduces is collation reconciliation (`reconcilePkCollations`), which can substitute
  only engine-known collation names — it can never introduce an unencodable character.
  Say so in a comment at the call site so the next reader does not have to re-derive it.
- The store's self-filter `ownsTableCatalogEntry` matches on
  `table.vtabModule === this` (or a wrapper exposing this module as `underlying`, which is
  what a store table looks like under `@quereus/quereus-isolation`).
  `buildTableSchemaFromAST` sets `vtabModule` from the resolved module info, so the filter
  answers correctly on the pre-create object. A memory-backed table in a database that
  also has store tables is not owned by the store, yields no prospective entry, and is not
  checked — which is the behaviour we want.

### Where the check must NOT go

Not in `buildTableSchemaFromAST`, and not on the import / rehydrate path
(`importTable`, `importDDL`). A catalog written before this guard existed must still
open. This is the same placement rationale the FK-collation and duplicate-UNIQUE guards
already carry in that function — mirror their comment style.

## Tests

Two existing tests in `packages/quereus-store/test/lone-surrogate-keys.spec.ts`
pin the *current* late behaviour and must flip to a create-time refusal:

- `'rejects a column name carrying a lone surrogate, not just the table name'` — today
  creates the table and expects the INSERT to throw. After this change the `create table`
  itself throws, and the table must not be registered
  (`db.schemaManager.getTable('main', 't')` is `undefined`).
- `'rejects a DEFAULT string literal carrying a lone surrogate'` — same flip.

The explanatory comment at the head of that `describe` block enumerates "three different
rejection timings" and explicitly says DDL-text problems "surface on the first
INSERT/SELECT rather than at `CREATE TABLE`". That paragraph is now wrong — rewrite it:
a table is refused at CREATE like a view is, and the remaining lazy-persist timing note
applies only to catalogs written before the guard.

Add, in the same file:

- a `check` constraint carrying a lone-surrogate string literal → `create table` refused,
  table not registered (proves the veto reads the whole generated text, not just column
  names);
- a **negative** case: the same lone-surrogate column name on a `using memory` table in the
  same database still succeeds and still accepts writes — the store must not veto a table
  it does not own;
- the loss case made observable: create a store table with a lone-surrogate `default`
  literal, never touch it, and assert that after the fix the create was refused, so a
  reopen through a fresh `StoreModule` finds nothing unexpected (`loadAllDDL()`), mirroring
  the existing `'rejects both of two tables whose names differ only in a lone surrogate'`
  shape.

Run: `yarn workspace @quereus/store test` and `yarn test`.

## Edge cases & interactions

- **Memory-only database.** No module implements the hook, so the loop is a no-op and
  costs nothing. `CREATE TABLE` behaviour is unchanged — assert this stays true.
- **Table not owned by the store.** `ownsTableCatalogEntry` must return false for a
  `using memory` table so a mixed-backend database keeps creating memory tables freely.
- **`subscribedDb !== db`.** The store answers only for the `Database` it serves; a second
  `Database` sharing a module instance gets no veto. Existing behaviour, unchanged — do
  not "fix" it here.
- **Import / rehydrate.** `importTable` / `importDDL` must not gain the check. Verify a
  pre-existing catalog entry containing an unencodable literal still opens (it cannot be
  produced by the store, but a hand-written or foreign catalog can).
- **`apply schema`.** The declarative path executes `create table` through `createTable`,
  so it inherits the refusal. A migration batch that refuses mid-loop must leave the batch
  aborted through the existing `endSchemaBatch(error)` arm — no new rollback machinery.
- **Maintained tables.** `createMaintainedTable` builds through
  `buildDeclaredTableSchema` and then `createTable(…, preferBacking = true)`. It must get
  the same refusal, and the refusal must arrive before any backing store is built.
- **`create table … if not exists`** on an already-present table returns early, before the
  guard — unchanged, and correct (nothing new is being persisted).
- **Error shape.** The store's veto throws its own encoding error; do not re-wrap it into
  the `Module '<m>' create failed for table '<t>'` shape — that wrapper only covers
  `module.create`, and the guard fires before it.
