# A rule-tightening alteration runs before the rows that satisfy it

## What happens

A receiving device applies a batch's schema changes **before** its row changes
(`createStoreAdapter`, `store-adapter.ts` ~181-192). That order is right for a change that
*loosens* or *extends* a table — adding a column, dropping a constraint — because the rows
that follow need the new shape to land in. It is wrong for a change that *tightens* one,
because a tightening is only legal against rows the receiver does not have yet: they are
queued behind it in the same batch.

Verified end to end over two real engines with `test/sync/_peer-harness.ts`:

1. Both devices hold `orders` with one row whose `note` is empty.
2. Device A fills it in, then runs `alter table orders alter column note set not null`.
3. Both changes relay to device B in one batch.
4. B applies the schema change first, against a row that is still empty, and the engine
   refuses.
5. The whole batch is reported failed — the caller of `applyChanges` sees:

```
apply-to-store failed for 1 change(s): main.orders (alter_column): column note contains NULL values
```

The next sync round succeeds (by then B holds the filled row), so this is a spurious error
and a wasted round trip rather than permanent divergence. But it is an error the
application sees on an entirely ordinary sequence, and no single order — all-DDL-first or
all-DDL-last — is right for both kinds of alteration.

## The distinction that fixes it

Split the batch's schema changes into two groups by **what the alteration does to existing
rows**, and apply them on either side of the data:

- **Non-validating** (everything the batch's rows may depend on, and everything that does
  not inspect existing rows): applied **before** the data, exactly as today. Creates,
  drops, renames, `add column`, `drop constraint`, `set default`, `set collation`,
  `set null`, index drops, tag and maintenance changes.
- **Validating** (legal only against a row set the batch may still be delivering): applied
  **after** the data has landed. This is a deliberately narrow set — see below.

`decideAlterTable` (`store-adapter.ts` ~563) already parses each `alter_column` migration
with the engine's own parser and switches on the alteration arm, so the classifier has the
same information available at the same place. Add a sibling that answers "does this
alteration validate existing rows?" and partition on it.

Suggested apply order inside one `applyToStore` invocation:

```
non-validating DDL  →  row writes  →  validating DDL  →  engine ingestion seam
```

The seam runs last so it observes the final schema. Errors from the validating group
collect into `ApplyToStoreResult.errors` exactly as they do today, so a genuinely
unsatisfiable tightening still aborts the batch and still retries.

## The validating set, and why it is exactly these

Only alterations that **inspect existing rows without changing how those rows are stored or
addressed** are safe to move. The three that qualify:

- `alter column … set not null` (the reproduced case)
- `add constraint` — `unique`, `check` and foreign-key forms all validate existing rows
- a **unique** `add_index` migration — creating a unique index validates existing rows the
  same way. This one is *unverified*; confirm it fails the same way before moving it, and
  leave non-unique index creation in the non-validating group either way.

Two alterations look like they belong in this set and deliberately **do not**:

- **`alter primary key`** — re-keying is not merely validating. The batch's row changes
  carry primary-key values, and which key definition is in force decides how those rows are
  addressed. Moving the re-key after the rows would file them under the old key. It stays
  before the data, so its own tightening failure mode (duplicate values under the new key)
  remains; say so in the code comment rather than silently leaving it out.
- **`alter column … set data type`** — a type change rewrites stored values, so rows
  applied before it would be stored under the old type and then converted, which is not the
  same as the origin's history. Stays before the data, same treatment.

## Why moving them cannot regress a batch that works today

Today every schema change runs before all data. The only behaviour that changes is for a
validating alteration that arrives together with data. For that to break, the batch would
have to carry rows that *violate* the alteration and arrive after it in the origin's own
history — which the origin itself would have rejected. So no batch that succeeds today can
fail after the change, and batches that fail today succeed on the first round instead of
the second.

## Considered and not taken: full interleaving

The fully general answer is to replay the origin's history step by step — migrations and
row changes interleaved in timestamp order — which reproduces the origin exactly and needs
no classifier. It was rejected as disproportionate: the adapter collapses each row's
changes across the whole batch into one net operation (`buildRowOp`) and makes one
ingestion-seam call per invocation, both of which assume a single data phase. Unpicking
that is a much larger change than the two-phase split, and the split covers the cases that
actually occur. Worth revisiting only if a case turns up that two phases genuinely cannot
express.
