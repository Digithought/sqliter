# Why

Two problems remain once benchmarks are isolated and self-calibrating, and both are about
what happens *after* the numbers are collected.

**The regression rule ignores how noisy the number was.** `--baseline` colors any median
more than 20% above the baseline red and exits non-zero. It never asks whether the spread
within either run already exceeded 20% — in which case the delta is noise and the red is a
lie. The upstream ticket makes each benchmark report its own within-run spread; this ticket
is what uses it. Planning measured `execution/group-by-10k` producing medians of 58.22 and
65.03 ms in consecutive isolated runs — a 12% delta that is entirely noise, and would be
correctly reported as "no change" against the 63.2% spread the second run carried.

The same flat 20% is simultaneously **too loose** for the well-behaved benchmarks:
`execution/distinct-text-10k` reproduces to within 3% across four isolated runs, so a real
15% regression there is invisible under a 20% rule.

**Nothing records where the numbers came from.** The results JSON captures a timestamp, the
commit and the Node version. It does not capture the CPU, the core count, the memory, the
operating system, or whether the working tree was dirty. So a result file from one machine
compares against one from another and produces a confident-looking delta table describing
nothing but the hardware difference.

Two smaller frictions are worth clearing at the same time, because they are what stops
anyone using the comparison at all: naming a baseline requires pasting a timestamped
filename, and there is no machine-readable output, so a later gate script would have to
re-parse the human table.

# What to build

## Capture the environment

The results JSON grows an `environment` block:

- CPU model and logical core count (`os.cpus()`)
- total memory (`os.totalmem()`)
- platform, OS release, architecture (`os.platform()`, `os.release()`, `os.arch()`)
- Node version and V8 version (`process.version`, `process.versions.v8`)
- commit hash (already captured) **and** whether the working tree was dirty
  (`git status --porcelain` non-empty)

Dirty-tree detection uses the same `execSync` pattern as the existing commit lookup and
must degrade to `"unknown"` outside a git checkout rather than throwing — the harness must
still run for someone who unpacked a tarball.

## Refuse to compare incomparable runs quietly

When `--baseline` is given, compare the two environment blocks first and print a loud
banner at the **top** of the comparison — before the table, where it cannot be missed —
when they differ materially. Material means any of: different CPU model, different core
count, different platform or architecture, or a different Node major version. A baseline
with no `environment` block at all (written by the current harness) is itself a mismatch
and says so.

The banner warns; it does not refuse to print. Someone comparing across machines on purpose
should still get their table, clearly labelled as what it is.

## Make the delta rule noise-aware

For each benchmark present in both runs, combine the two within-run spreads into a noise
floor and judge the delta against it:

```
noiseFloor% = max(5, sqrt(rIQR_current^2 + rIQR_baseline^2))
```

Quadrature because the two runs' noise is independent; a 5% floor so a benchmark that
happens to report a near-zero spread does not start gating on 1% deltas.

- `|delta| <= noiseFloor` — printed as **no change**, uncolored. Not a regression, not an
  improvement.
- `delta > noiseFloor` and `delta > 10%` — regression: red, counts toward the non-zero exit.
- `delta < -noiseFloor` and `delta < -10%` — improvement: green.
- Anything between `noiseFloor` and the 10% minimum — printed with its percentage, plainly,
  and not gated. A change too small to care about is still worth seeing.

Print the noise floor beside the delta so the judgement is legible rather than magic.

A benchmark marked unstable in **either** run (within-run spread above 20%, or spread
unknown because the median rounded to zero) is **never** a regression. Print the delta,
mark the row unstable, and state in the summary how many benchmarks were excluded from
gating and why. A benchmark that cannot hold a stable number is a bug in the benchmark, not
a signal.

A baseline file written before this change carries no spread figures. Treat the missing
baseline spread as 20%, say so once in the banner, and carry on.

## Report every non-comparison distinctly

Four outcomes that are not "a delta", each of which must read differently and none of which
may be silence:

- **new** — in this run, absent from the baseline. Not a failure.
- **missing** — in the baseline, absent from this run. Usually means it threw or was
  filtered out; distinguish those two cases if `--filter` was given.
- **failed** — the benchmark errored this run (the prereq ticket's failure path).
- **unstable** — measured, but excluded from gating.

Close with a one-line summary counting each. A comparison that silently drops what it could
not evaluate reads as green when it is not.

## Ergonomics

- **`--baseline latest`** resolves the most recent file in `bench/results/`. Resolve it
  **before** this run writes its own result file, or `latest` compares the run against
  itself. An empty or missing results directory is a clear error, not a crash.
- **`--json`** writes the machine-readable result object to stdout and *nothing else* —
  progress lines, the human table, the banner and the guard output all move to stderr for
  that mode. A later gate script must be able to consume stdout without filtering.

# Edge cases & interactions

- **`--baseline latest` on the file this run writes.** Resolve the baseline path during
  argument handling, before the run, not after.
- **Filename ordering.** Result filenames are ISO timestamps with `:` and `.` replaced, so
  they sort lexicographically by time. Sort by name, not by filesystem mtime, which a copy
  or a checkout can reorder. Comment the assumption at the sort.
- **Old-format baseline files.** A file with no `environment` and no spread must not crash
  the comparison. Both fallbacks are stated above; make sure they are *reported*, not
  applied silently.
- **Degenerate medians.** A benchmark whose median rounds to zero produces a division by
  zero in the delta. `checkRatioGuards` already handles this for ratios; the delta path
  needs the same treatment — report it as unstable rather than emitting `Infinity`.
- **Colors on a redirected stream.** The harness emits raw ANSI escapes. Under `--json`,
  and generally when the stream is not a TTY, escapes should be suppressed so a captured
  log stays readable.
- **Exit-code contract.** Non-zero on: any benchmark failure, any ratio-guard failure, any
  gated regression. Unstable and new benchmarks never contribute. Document the contract in
  `docs/benchmarking.md` — a downstream ticket (`bench-regression-gate`) builds on it.
- **The results directory stays gitignored.** `.gitignore` line 26 excludes
  `packages/quereus/bench/results/`. Nothing here changes that; the checked-in reference
  set is `bench-regression-gate`'s problem.
- **Windows.** `os.release()` returns an NT version string, not a friendly name — fine, but
  do not try to prettify it into something that only parses on one platform. The dirty-tree
  `execSync` must not open a shell window or block.

# Acceptance

- `yarn bench --baseline latest` run twice in a row on an unchanged tree reports every
  benchmark as "no change" or as a sub-threshold delta, and exits zero. If it flags a
  regression on an unchanged tree, the noise floor is wrong — report the actual output
  rather than tuning until it goes green.
- A results file hand-edited to a different CPU model produces the mismatch banner.
- `yarn bench --json` emits parseable JSON on stdout with nothing else mixed in
  (`node bench/run.mjs --json 2>/dev/null | node -e "JSON.parse(...)"` is the check).
- `yarn docs:check` passes with the new doc present.
