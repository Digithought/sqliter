# Why

`bench-store-workloads` measures whole queries against the store. That is the right
top-level signal and a poor diagnostic: a full scan blends key decoding, iteration, row
deserialization and the isolation overlay into one number, so a regression in any one of
them reads as "the scan got slower" with no way to tell which.

Key building runs per row per index. It is the cheapest thing to measure directly, because
it is a pure function — no database needed — and it is where a lost fast path hides best.

# Architecture

A new suite file, `bench/suites/store.bench.mjs`. This ticket creates it and fills its
first section; `bench-store-micro-paths` appends the rest.

It is a **store-only** suite. Unlike `execution` and `mutation` it does not use the
backend-dimension expansion in `bench/lib/backends.mjs`, because these benchmarks call
store code directly rather than running a query that a storage engine could be swapped
underneath. Its benchmark names are therefore **bare and carry no `@` suffix**, and
`docs/benchmarking.md` must say why — otherwise the asymmetry reads as an oversight, and
the invariant that file currently states ("every entry of both suites is expanded") looks
violated.

Each entry is a plain benchmark object as `bench/lib/discover.mjs` documents it:
`{ name, setup?, fn, teardown?, counters?, skip? }`.

**Declare a `skip()` that returns `storeLoadFailure()`** from
`bench/lib/store-counters.mjs`, exactly as the backend expansion does for the `@store-mem`
rows. Without it, an unbuilt `packages/quereus-store/dist` fails every row in this suite
with a stack trace instead of skipping it with a stated reason. Reaching the store package
any way other than through `store-counters.mjs`'s single dynamic import is what kills the
whole `yarn bench` run at suite enumeration — see that file's header.

## What to cover

The value shapes the correctness suite already treats as hazardous, because those are where
a fast path can be lost silently:

- plain integer and plain text keys (the baseline),
- astral-plane text — surrogate pairs take the surrogate-aware slow path, the same
  distinction `execution/order-by-text-unicode-10k` exists to price at the comparator
  level,
- JSON keys,
- a collation-affected key (`NOCASE`), which routes through a key normalizer,
- a descending key (the encoder inverts every byte),
- a composite key of several columns.

Plus one benchmark timing `decodeCompositeKey`, so the decode side is priced once rather
than folded into every encode number.

## Two mechanics that will otherwise produce meaningless numbers

**Amortize inside `fn`.** The harness calls `await fn()` per iteration
(`bench/lib/calibrate.mjs`, `collectSamples`). A single `encodeValue` of an integer costs on
the order of a hundred nanoseconds; the `await` around it costs a microtask tick. Timing one
encode per call would report mostly harness overhead. Each `fn` must therefore build a fixed
number of keys per call — pick one shared constant, use it for every shape so the shapes stay
comparable to each other, and state in a comment that the reported figure is that many key
builds, not one.

**Build the fixture values in `setup`, never in `fn`.** Calibration times several
consecutive `fn` calls as one sample for sub-millisecond work, so an `fn` that allocates its
own input measures the allocation.

**Assert in `fn`, verify the round trip in `setup`.** Every benchmark must assert something
about its output or a broken builder that starts returning empty reads as an improvement.
The split that keeps the timed number honest:

- `setup` round-trips every fixture value through `decodeCompositeKey(encodeCompositeKey(v))`
  and throws on any mismatch. That is the assertion that stops the suite from measuring a
  broken encoder, and it costs nothing because it is untimed.
- `fn` asserts the total encoded byte length against the length `setup` recorded — cheap,
  and enough to catch an encoder that stopped producing bytes.

Do not put a full decode inside an encode benchmark's timed body: decode costs about as much
as encode, so it would halve the resolution of the very thing being measured. The dedicated
decode benchmark asserts equality on every value, since there the decode *is* the subject.

## `apply-schema-unchanged.mjs` stays ad hoc — decided

The upstream plan asked whether to fold `bench/apply-schema-unchanged.mjs` into the suite.
**It stays where it is**, for a reason that should be recorded at the file rather than
re-litigated:

It is not an end-to-end benchmark. It decomposes a no-op `apply schema` into the internal
functions the fast path removed (`computeSchemaDiff`, `generateMigrationPlan`), added
(`renderCatalogForComparison`, an exact string compare) and still pays
(`collectSchemaCatalog`), and it deliberately poisons the applied-state snapshot between
runs so the pre-fast-path shape is measured warm and in-process. The bench framework
measures one `fn` per benchmark and cannot express that decomposition; forcing it in would
keep one number and lose the five that make it useful. Its figures are quoted in
`docs/schema.md` as a one-off measurement, not as a tracked series.

Record this as a `NOTE:` at the top of `apply-schema-unchanged.mjs` — it already says "NOT
part of the bench suite"; this says *why*, so the question stops recurring — and as one line
in `docs/benchmarking.md`.

Giving the applied-state fast path a standing ratio-guarded benchmark is real work and is
parked separately: file `feat-bench-apply-schema-fastpath-guard` in `backlog/`.

# Edge cases & interactions

- **Use only public exports of `@quereus/store`.** `encodeValue`, `encodeCompositeKey`,
  `decodeValue`, `decodeCompositeKey`, `buildDataKey`, `buildIndexKey` and
  `BUILTIN_KEY_NORMALIZER_RESOLVER` are all exported from
  `packages/quereus-store/src/common/index.ts` today. Binding the suite to those means it
  breaks at a deliberate API change rather than at an internal refactor. Reach them through
  the accessor the prereq adds to `bench/lib/store-counters.mjs`, not through a second
  import site.
- **`encodeValue`'s default collation is `NOCASE`, not `BINARY`.** A benchmark that means to
  price the plain-text path must pass `{ collation: 'BINARY' }` explicitly, or it is
  silently measuring the normalizer path and the `NOCASE` benchmark beside it measures the
  same thing.
- **A collation name the resolver does not know throws.** `BUILTIN_KEY_NORMALIZER_RESOLVER`
  knows BINARY / NOCASE / RTRIM only and raises on anything else rather than guessing.
- **`encodeCompositeKey` mutates the per-value buffers it builds when a column is
  descending** (it XORs each byte in place). It allocates them itself, so this is safe — but
  a benchmark that tries to pre-encode and reuse buffers must not assume otherwise.
- **These benchmarks report no counters.** There is no `Database`, no plan and no storage
  traffic, so no `counters()` pass — the same position `parser` is in. Say so in the
  per-suite table in `docs/benchmarking.md`.

# Tests

- Every benchmark asserts its own result: a byte length in `fn`, a full round-trip in
  `setup`, and value equality in the decode benchmark.
- `yarn bench --filter store/` runs clean and produces a row per benchmark.
- With `packages/quereus-store/dist` absent, the whole suite reports `skipped` with the
  store-load reason rather than failing.
