# Charge the cost model for resolving an index entry to its row

## What happens today

`tryIndexAccessPlan` prices a secondary-index seek with no term at all for the per-row
data-store fetch that follows every index entry:

| arm | rows estimate | plan cost |
|-----|---------------|-----------|
| `eq` (`plan=2`/`5`) | `0.1 × N` | `0.3 + rows × 0.3` |
| `prefixRange` (`plan=7`) | `0.15 × N` | `0.2 + rows × 0.5` |
| `range` (`plan=3`) | `0.3 × N` | `0.2 + rows × 0.5` |
| full scan | `N` | `N × 1.0` |

(`N` is `request.estimatedRows`; the cost formulas come from `AccessPlanBuilder.eqMatch`
/ `rangeScan` / `fullScan` in `packages/quereus/src/vtab/best-access-plan.ts`.)

An index path reads BOTH stores — the index entry AND the row it names — while a full
scan reads one row per row, sequentially. The model charges the index path for neither
the second store nor the random access. That under-pricing is why a downstream project
had to disable an index by hand: their indexed read matched a large fraction of the
table and lost badly to the sequential scan the planner had priced as more expensive.

## What to build

Add a per-fetched-row **row-resolution** term to the secondary-index arms of
`tryIndexAccessPlan`, in the same unit as the full scan's `1.0`-per-row sequential read,
and say in a comment how the constant was chosen. It applies to every arm that resolves
index entries to rows — `eq`, `prefixRange`, `range`, and the multi-seek arm's
`multiRows`.

A defensible starting point is `1.0`: after the batching work, a batched random point
read costs roughly what one sequential row read costs, and the index path pays it ON TOP
OF the index-entry read it already pays. That puts the break-even at roughly two-thirds
of the table — an arm estimated to return more than that prices above a full scan.
Whatever constant is chosen, write down the reasoning; nothing here has been measured
locally.

### The part that needs a decision, and why it is not mechanical

**Raising the cost alone changes nothing observable.** `rule-select-access-path` calls
`getBestAccessPlan` once and uses whatever single plan the module returns; the engine
never compares it against an alternative. And `computeBestAccessPlan` currently ends with
`if (bestSeekPlan) return bestSeekPlan;` — the seek is returned regardless of how it
prices against the full scan it does not build. So for the ticket's expected result
("stops choosing an index seek for a predicate that matches most of the table") the
MODULE has to make the comparison: build the full-scan plan's cost and prefer it when the
best seek plan prices above it. Losing the seek is safe — the fall-back plan claims no
filters, so the residual is retained and the answer is identical.

Two things to weigh while doing that:

- **It is not the same as the open backlog ticket `bug-store-pk-range-preempts-cheaper-index`,**
  which is about the PK arms returning by POSITION instead of competing with the
  secondary-index arm. This is index-seek versus full-scan. Cross-reference it; do not
  fold it in, and do not change the PK arms' precedence here.
- **The multi-seek arm is the one that visibly flips, and it may flip too eagerly.**
  `multiRows = min(estimatedRows, inCount × rows)` saturates at the whole table once
  `inCount ≥ 10`, because `rows` is the fixed `0.1 × N` shape constant. With a
  resolution term of `1.0`, `where col in (…10 values…)` on a 1000-row table would price
  above the full scan and stop multi-seeking. That may be correct (10 seeks reading the
  whole table really is worse than one sequential pass) or may be an artifact of the
  shape constant — check what the existing multi-seek tests assert before deciding, and
  say in the ticket handoff which way it went.

### The honest limitation to record

`ARM_SELECTIVITY` is a table of SHAPE constants (0.1 / 0.15 / 0.3), not statistics —
the store keeps no per-column histograms and `request.estimatedRows` is the table row
count, not a selectivity-adjusted estimate. So a plain `eq` arm is modelled at 10%
selectivity whatever the predicate actually matches, and no resolution term makes it
price above a full scan. The downstream project's mispricing was in the SELECTIVITY
ESTIMATE at least as much as in the per-row cost, and this ticket does not fix that half.
Record it where the next reader will meet it — a `NOTE:` at `ARM_SELECTIVITY` naming real
index statistics as the fix — and say so plainly in the review handoff rather than
implying the whole gap is closed.

## Expected results

- Every secondary-index arm's advertised cost includes a per-fetched-row resolution term.
- A seek the model estimates will return most of the table loses to the sequential scan,
  while a selective one still wins.
- Rows returned are unchanged whichever path is chosen — a losing seek's filters go back
  to the residual.
