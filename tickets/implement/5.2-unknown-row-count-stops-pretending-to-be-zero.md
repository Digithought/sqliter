# `undefined` is the only spelling of "unknown"

## Why not a new estimate type

The parent plan ticket proposed a `RowEstimate` discriminated union
(`{kind:'unknown'} | {kind:'estimate', rows}`). **Rejected.** Every layer already types
the estimate as optional:

| layer | type today |
|---|---|
| `TableSchema.estimatedRows` | `number \| undefined` |
| `RelationalPlanNode.estimatedRows` | `number \| undefined` |
| `PhysicalProperties.estimatedRows` | `number \| undefined` |
| `BestAccessPlanResult.rows` | `number \| undefined` |

"Unknown" is already spellable, and `undefined` is already the spelling. A union rewrite
would touch 342 read sites across four packages and break every third-party storage
module for no additional expressiveness. The defect is not the type — it is that **one
producer writes `0` where it means unknown.**

## The one site

`SchemaManager` stamps `estimatedRows: 0` onto every `TableSchema` at CREATE TABLE and
never updates it. `catalogRowCount` — the single, shared "how many rows does this table
have" helper — reads it:

```ts
export function catalogRowCount(table: TableSchema): number | undefined {
    return table.statistics?.rowCount ?? table.estimatedRows;   // ← always 0 when un-analyzed
}
```

`TableSchema.estimatedRows` is written in exactly four places (three in `SchemaManager`,
one in the store module) and every one of them writes the literal `0`. Nothing in the
repository ever writes a real number into it. It is a field whose only effect is to
prevent `catalogRowCount` from returning `undefined`.

**Delete the field.** Then `catalogRowCount(table)` is `table.statistics?.rowCount`, a
never-analyzed table reports `undefined`, and there is no longer any place to store a
fake zero — the bad state becomes unrepresentable at the catalog layer without touching a
single module interface.

## What actually changes at runtime

Most consumers spell their fallback `estimatedRows || default`, which already treats `0`
and `undefined` alike. Those sites see **no change**. Verify each and say so in the
handoff rather than editing them:

- `rule-grow-retrieve.ts` ~369, ~800 — `|| … || 1000`, still 1000.
- `rule-select-access-path.ts` ~263 (`|| undefined`), ~1232 (`|| 1000`) — unchanged.
- `rule-lateral-top1-asof.ts` ~261 — `?? undefined`, now genuinely `undefined`.

**One site changes behavior, and it is the point of the ticket:**

```ts
// planner/stats/catalog-stats.ts ~137
tableRows(table: TableSchema): number | undefined {
    const rows = catalogRowCount(table);
    if (rows === undefined) return this.fallback.tableRows(table);   // ← dead today
    return rows;
}
```

Today `catalogRowCount` returns `0`, so the fallback (`NaiveStatsProvider`, default 1000)
is **never consulted** and every un-analyzed table costs out as a zero-row table. After
the change it returns `undefined` and the fallback runs. That is what makes the join cost
model stop treating a 20,000-row table as empty.

Expect plan churn wherever costing compares an un-analyzed table against a constant.
Measured evidence from the parent ticket, store backend, 10,000- and 20,000-row tables,
one selective filter: without `analyze` the planner picked a hash join over a full scan
(47.3 ms); with `analyze` it picked a correlated index seek (17.8 ms). This change does
not close that gap on its own — nobody knows the real sizes without `analyze` — but it
stops the planner asserting a size it never measured.

## Edge cases & interactions

- **A genuinely empty, analyzed table** must still report `0`, not `undefined`. That path
  runs through `statistics.rowCount`, untouched — but write the test, because it is the
  distinction the whole ticket exists to preserve.
- **`aggregateRowsFrom` in `row-estimates.ts`** has a deliberate `if (sourceRows === 0)
  return 0;` arm whose comment justifies it as protecting the never-analyzed sentinel.
  That justification expires here. Decide explicitly: the arm is still correct for a
  genuinely empty analyzed table (0 rows in ⇒ 0 groups out), so **keep it and rewrite the
  comment** to say so. Do not delete it.
- **CTE caching.** `PlanNodeCharacteristics.estimatesRows` returns
  `physical.estimatedRows ?? 1000`, so un-analyzed relations jump from `0` to `1000`. The
  prereq ticket removed the `sourceSize > 0` consumer; confirm nothing else gates on
  `estimatesRows(...) > 0` or `< threshold` in a way that flips. Grep `estimatesRows`,
  `isExpensive`, `getCacheThreshold`.
- **`database-auto-analyze.ts`** reads `catalogRowCount(table) ?? 0` in three places
  (~442, ~638, ~673) to decide when a table has grown enough to warrant a re-`analyze`.
  `undefined → 0` preserves today's arithmetic, but re-read each: "never analyzed" and
  "analyzed and empty" should almost certainly trigger differently. If they should, that
  is in scope here (same root cause); if the current collapse is right, leave a `NOTE:`
  saying why.
- **`store-module.ts` ~466** builds a `TableSchema` by hand for a table it is loading;
  dropping the field there must not break the object literal's type or the load path.
- **`manager.ts` ~2473** spells it `correctedSchema.estimatedRows ?? 0` while rebuilding a
  schema — deleting the field removes the line, but check nothing downstream reads the
  rebuilt schema's estimate positionally.
- **The public type export.** `TableSchema` is exported from `packages/quereus/src/index.ts`.
  Removing a field is source-breaking for anyone constructing one. Per `AGENTS.md`
  backwards compatibility is not yet a concern; note the break in the handoff.
- **Golden plans and plan-asserting logic tests.** Six `*.plan.json` files under
  `test/plan/` and seven `*.sqllogic` files carry plan assertions. Any that run against an
  un-analyzed table may change shape. **Re-derive each changed expectation and explain in
  the handoff why the new shape is better** — do not regenerate them wholesale, and never
  loosen an assertion to get green.
- **`test:store`.** The store backend has its own cost profile and its own seek-vs-scan
  veto that discriminates only on statistics-backed estimates. Run `yarn test:store` for
  this ticket specifically — it is the one place a 0→1000 flip is most likely to move a
  plan — and report the result even if it is a pre-existing failure.
