# Why

These are the paths that run per row, per index, per commit — the ones where a per-operation
cost that should have been per-batch can hide behind a whole-query number.

Unlike the key-encoding benchmarks the prereq adds, none of these can be reached without
white-boxing the store. So they are driven through a `Database` and **reported in storage
round trips as well as time**, which is the honest measurement anyway: round-trip counts are
exact integers, identical on every machine, where a wall-clock median describes one CPU.

# Architecture

Append to `bench/suites/store.bench.mjs`, which the prereq creates. Same rules apply: bare
names with no backend suffix, `skip()` wired to `storeLoadFailure()`, fixtures built in
`setup`, every `fn` repeatable back-to-back and asserting its own result.

The timed database comes from `openStoreDatabase()` and the untimed `counters()` pass from
`openCountingStoreDatabase()`, both in `bench/lib/store-counters.mjs` — a second database,
because the counting wrapper sits in front of every read and has no business inside a timed
number. `bench/suites/execution.bench.mjs`'s `queryCounters` is the pattern to copy: build
the fixture into the counting database, `resetCounters()` at the boundary between fixture
and subject, snapshot, then `readCounters()` **before** `close()`.

## Scan, seek, and batched row resolution

- sequential iterate throughput over a populated table,
- a point read on the primary key,
- a multi-key seek (`where pk in (...)`) at a few key counts,
- **the batched row resolution behind a secondary index.** `StoreTableScan.resolveRowBatch`
  pages at `ROW_RESOLUTION_BATCH` (256). Choose match-set sizes that straddle that boundary:
  well under 256, exactly 256, and a couple of multiples of it. The interesting failure is a
  batch that stops batching — the round-trip count would jump from `ceil(n / 256)` to `n`
  while the wall-clock on an in-memory provider barely moves. The batched-read call count is
  what catches it, and it is the reason this suite exists.

State the expected round-trip count in a comment beside each size, **derived from the
imported constant rather than from the literal 256**, so a change to the constant moves the
expectation instead of turning the comments into lies. A benchmark whose expected count is
written down is one whose regression is readable without a baseline.

`packages/quereus-store/test/index-scan-batching.spec.ts` already asserts this shape at the
spec level (`ceil(300 / 256) == 2` batches, and so on) — it is the reference for how the
counts come out, and the benchmark should agree with it.

## Transaction commit

`TransactionCoordinator` buffers every mutation of a transaction and writes them out on
commit — in one atomic batch when the provider has a shared commit domain, else one batch
per store. Queue N operations and commit, across a range of N (say 1, 10, 100, 1000,
10000). The shape of round-trips-versus-N is the measurement: flat per commit is correct,
linear in N means a per-operation cost that should have been per-batch.

**This is the benchmark that needs the write counters the harness ticket adds.** The read
counters cannot answer it: any workload queueing N operations must touch N rows, so reads are
linear in N no matter what the commit path does. The batch-round-trip count is the number
that must stay flat.

Note that `createInMemoryProvider` (what the timed and counting databases are built over)
implements no `beginAtomicBatch`, so the store commits **one batch per store**, not one per
transaction. The expected flat count is therefore per store touched, not literally one —
write the expectation down accordingly, and say in a comment that a provider with a shared
commit domain would show a different (also flat) number.

The workload must be repeatable back-to-back without growing the store. An `update` over a
fixed key range against a shared fixture is the shape that fits — the same fixed-point
argument `mutation/update-where-1k` already documents. **Verify before relying on it that
the store actually writes a row whose new value equals its old one**; if the update path
short-circuits a no-op write, the second and every later call queues nothing and the
benchmark measures an empty commit. If it does short-circuit, alternate the written value
between two constants instead: the table stays the same size and each call costs the same,
which is what repeatability actually requires.

## Index build

Building a secondary index over an existing table (`create index` on a populated table)
streams through `buildIndexEntries`. One benchmark at one table size, reported in round
trips. A repeatable `fn` creates and drops the index each call.

**The drop must actually erase**, or the second call builds an index over a store that
already holds the first call's entries and the benchmark measures something else entirely.
Two facts about the two providers, which differ here and which the benchmark has to be
written around:

- `createInMemoryProvider` — used by the timed database — **does** implement
  `deleteIndexStore`, and it erases: it clears a live store so an existing handle observes
  the erase, then drops the map entry.
- `createCountingProvider` — used by the `counters()` pass — implements **neither**
  `deleteIndexStore` nor `deleteTableStores`, deliberately and with a NOTE saying so. A
  drop-then-recreate against it reads the dropped store's entries back. The counters pass
  runs exactly once, so it must create the index **once and not drop it**.

**Where to put the assertion.** "Assert the index store is empty after the drop" does not
work as written: `erase` removes the map entry, so asking the provider for that index store
afterwards lazily creates a fresh empty one and the check passes no matter what. Assert
instead at the **start of each `fn` call** that the index store is empty or absent before the
`create index` — that is the check that actually fires when a drop stops erasing. Reaching the
provider needs the handle change the harness ticket makes to `openStoreDatabase()`.

## Catalog rehydration

Reopening a database with a non-trivial schema: build the schema over a store-backed
`Database`, close it, then open a fresh `Database` over the **same provider instance** and
measure the cost of rebuilding the schema from the `__catalog__` store. Reported in round
trips against that store, which is the count that would catch a rehydration that reads
per-table instead of scanning once.

Reusing the same `Database` measures nothing; building a new provider measures an empty
catalog. Assert the rehydrated schema has the expected table count, or the benchmark can
pass while reading nothing.

The schema should be non-trivial the way a real one is — tens of tables, some with
secondary indexes, some views — rather than one wide table.
`bench/apply-schema-unchanged.mjs` already contains a 54-table / 14-view declaration
generator (`buildDeclaration`); reuse its shape rather than inventing a second one.

# Edge cases & interactions

- **Use only public exports of `@quereus/store`,** reached through the accessor in
  `bench/lib/store-counters.mjs` — never a second import site, which would let an unbuilt
  store package kill the whole `yarn bench` run at suite enumeration.
- **Batching hides per-call setup.** Calibration times several consecutive `fn` calls as one
  sample for sub-millisecond work, so an `fn` that allocates a large fixture per call
  measures the allocation. Build fixtures in `setup`.
- **The commit benchmark at N = 10000 is not repeatable back-to-back for free.** Either
  reset inside `fn` and accept that the reset is in the number, stated in a comment, or pin
  it out of calibration with the reason written down. Do not leave a benchmark whose cost
  climbs across its own samples.
- **Wall-clock budget.** This section is on the order of a dozen benchmarks on top of a run
  the docs currently put at ~100 s for 46 benchmarks (the upstream ticket's "~35 s" is
  stale). Measure and report the added time. If it is large, the lever is
  `CALIBRATION.targetTotalMs` in `bench/lib/calibrate.mjs`, which shortens every benchmark
  evenly — not silently shrinking these workloads. If the honest number is too large to
  accept, say so and propose which sizes to drop rather than trimming them quietly.
- **Explicit `begin;` / `commit;` in SQL works** — see
  `packages/quereus/test/logic/10.1.2-ddl-in-transaction.sqllogic`.

# Tests

- Every benchmark asserts its own result, as `docs/benchmarking.md` requires: a row count, a
  round-trip count, an entry count before the index build.
- Two consecutive runs produce byte-identical counter blocks for this suite. That is the
  acceptance criterion; identical timings is not.
- The stated expected round-trip counts hold: `ceil(n / ROW_RESOLUTION_BATCH)` batched reads
  for a match set of n, and a commit batch-round-trip count that does not grow with the
  queued operation count.
