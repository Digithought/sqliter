## Probe-verified counter numbers (run 2 — design around these; expected blocks)

Fixture: bench_t (id integer pk, val integer), index on val, 10 000 rows val=id.

- Full scan: data `iterateEntries=10000`, all else zero everywhere.
- PK point read: data `singleGets=1`, nothing else anywhere.
- PK in-list k keys: data `getManyCalls=ceil(k/B)`, `getManyKeys=k`, zero iterates anywhere.
- Index range n rows: index `iterateEntries=n`, data `getManyCalls=ceil(n/B)`,
  `getManyKeys=n`, zero data iterates. Planner picks the index at ALL sizes up to n=1024
  (~10% selectivity) against the 10k fixture — no plan-shape assertion needed beyond the
  counter asserts.
- Commit (`begin; update bench_t set val = <c> where id < N; commit;`): **data
  `batchWrites=1`, index `batchWrites=1` — FLAT across N ∈ {1,10,100,1000}** (per-store
  fallback, one WriteBatch per touched store). `batchOps=N` data / `2N` index. Commits also
  provoke data `iterateEntries=N` and `getCount=2N` — do NOT assert those, only the flat
  claim + batchOps. `__stats__`/`__catalog__` untouched by commits.
- Same-value update does NOT short-circuit anywhere (verified in code and by repeat-commit
  byte-identical counters) — alternating constants is cheap insurance only.
- Index build create/drop cycles on the plain provider: before=0 / after=5000 across 3
  consecutive cycles.
- Rehydration of an 8-table catalog after reset: `__catalog__ iterateEntries=8` (ONE scan),
  `getCount=1` (clean-shutdown-marker probe), `__stats__ getCount=8`, no data store touched.
  For 54t fixture do NOT hard-assert entry count (views land beside table entries; index DDL
  rides in the table bundle; meta entries only after a closeAll that never happens here).

# Why

These are the paths that run per row, per index, per commit — the ones where a per-operation
cost that should have been per-batch can hide behind a whole-query number.

Unlike the key-encoding benchmarks the prereq adds, none of these can be reached without
white-boxing the store. So they are driven through a `Database` and **reported in storage
round trips as well as time**, which is the honest measurement anyway: round-trip counts are
exact integers, identical on every machine, where a wall-clock median describes one CPU.

# Architecture

Append to `bench/suites/store.bench.mjs`. Same rules as the existing half: bare names with
no backend suffix, `skip()` wired to `storeLoadFailure()`, fixtures built in `setup`, every
`fn` repeatable back-to-back and asserting its own result.

The timed database comes from `openStoreDatabase()` and the untimed `counters()` pass from
`openCountingStoreDatabase()` — a second database, because the counting wrapper sits in
front of every read and has no business inside a timed number.
`bench/suites/execution.bench.mjs`'s `queryCounters` is the pattern: fixture into the
counting database, `resetCounters()` at the fixture/subject boundary, snapshot, then
`readCounters()` **before** `close()`.

State the expected round-trip count in a comment beside each size, **derived from the
imported constant rather than from the literal 256**.

# Edge cases & interactions

- **Use only public exports of `@quereus/store`,** reached through
  `bench/lib/store-counters.mjs` — never a second import site.
- **Batching hides per-call setup** — build fixtures in `setup`.
- **Wall-clock budget:** measure and report the added time. If too large, the lever is
  `CALIBRATION.targetTotalMs` in `bench/lib/calibrate.mjs`, evenly — never silently
  shrinking workloads.

# Tests

- Every benchmark asserts its own result: a row count, a round-trip count, an entry count.
- Two consecutive runs produce byte-identical counter blocks for this suite — the
  acceptance criterion (identical timings is not).
- `ceil(n / ROW_RESOLUTION_BATCH)` batched reads for a match set of n; commit
  batch-round-trip count flat in N.
