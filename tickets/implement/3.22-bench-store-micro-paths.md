## Probe-verified counter numbers (run 2 — the expected blocks)

Fixture: bench_t (id integer pk, val integer), index on val, 10 000 rows val=id.

- Full scan: data `iterateEntries=10000`, all else zero everywhere.
- PK point read: data `singleGets=1`, nothing else anywhere.
- PK in-list k keys: data `getManyCalls=ceil(k/B)`, `getManyKeys=k`, zero iterates.
- Index range n rows: index `iterateEntries=n`, data `getManyCalls=ceil(n/B)`,
  `getManyKeys=n`, zero data iterates. Planner picks the index at all sizes up to n=1024.
- Commit: data/index `batchWrites=1` FLAT across N ∈ {1,10,100,1000}; `batchOps=N` data /
  `2N` index. Commits also provoke data `iterateEntries=N`, `getCount=2N` — reported, not
  asserted.
- Index build cycles on the plain provider: before=0 / after=5000 across 3 cycles.
- Rehydration repeatable (no clean-shutdown marker ever written on per-call modules);
  abandoned per-call modules hold no OS handles.

# Why

These are the paths that run per row, per index, per commit — the ones where a
per-operation cost that should have been per-batch can hide behind a whole-query number.
None can be reached without white-boxing the store, so they are driven through a
`Database` and reported in storage round trips as well as time: round-trip counts are
exact integers, identical on every machine, where a wall-clock median describes one CPU.

# Tests

- Every benchmark asserts its own result: a row count, a round-trip count, an entry count.
- Two consecutive `yarn bench --filter store/` runs produce byte-identical counter blocks
  — the acceptance criterion (identical timings is not).
- `ceil(n / ROW_RESOLUTION_BATCH)` batched reads for a match set of n; commit
  batch-round-trip count flat in N.
