# Store: cover `pk in (select …)` and the isolation-wrapped read for the new PK multi-seek

Split out of `feat-store-pk-in-list-multiseek`, which builds the planner arm and covers
the literal-list shape. This ticket covers the **second, more common caller** and the
transaction-visibility case. It is coverage-and-verification work: if the arm from the
prereq is right, little or no production code should change here — but the two gates in
**Open questions** below may force a small planner-side adjustment, so this is not a
pure test ticket.

## Why there are two callers

- **Literal list** — `rule-select-access-path` emits a `plan=5` multi-seek directly.
  Covered by the prereq.
- **`in (select …)` / semi-join** — subquery decorrelation produces a semi-join, and
  `rule-key-set-seek` rewrites the target leaf's `FilterInfo` at runtime into an ordinary
  single-column `plan=5` multi-seek, byte-identical to the literal form
  (`stampMultiSeek`). The rule always builds the key set and always probes, so a declined
  seek is a *scan branch*, not a wrong answer — just the full table read.

The store's own `key-set-seek-store.spec.ts` covers only a secondary-index target today.

## What is already known (do not re-derive)

- `resolveIndexDescriptor` resolves `_primary_` through `primaryKeyDescriptor`, so
  `rule-key-set-seek`'s descriptor lookup and its
  `descriptor.keyColumns[0].columnIndex === seekCol` check both pass for a single-column
  primary key.
- `claimedIndex` declines any plan whose `seekColumnIndexes.length !== 1`. A **composite**
  primary key therefore never takes the `in (select …)` path — only the literal-list one.
  That is a documented restriction ("sorting by single-column SQL value order equals
  index-key order only for a single key column"), not a bug to fix here. Pin it with a
  test that asserts the composite case keeps its hash semi join and still answers.
- `stampMultiSeek` omits `seekWidth` from the idxStr (⇒ 1), which matches
  `scanMultiSeekPrimary`'s requirement that `seekWidth === pkColumns.length` for a
  single-column primary key.
- The memory backend already serves `_primary_` key-set seeks under isolation
  (`packages/quereus-isolation/test/key-set-seek-merge.spec.ts`), so the merge machinery
  itself is exercised; what is new is the store answering as the underlying.
- The break-even arithmetic in the prereq's design section shows a 3-key set against a
  4-row store table still seeks — small fixtures are viable, no 200-row padding needed.

## Open questions this ticket must settle (each with a test, either way)

- **`seekPreservesTargetOrder` on a store PK target.** It returns false for every
  `IndexSeekNode`, but for an `IndexScanNode` walk leaf it requires the walk index name
  to equal the pushdown's index name and the index to be single-column. The store
  advertises primary-key ordering on its full scan, so a store leaf may well arrive as an
  ordering-only `IndexScan` over `_primary_` — in which case a `_primary_` key-set seek
  could newly satisfy the predicate, and `… in (select …) order by pk` would keep its
  seek instead of declining. Find out which branch it takes and pin it. If it does claim
  the order, also assert the ROW ORDER, not just that the rewrite fired.
- **The merge-arm gate.** `rule-key-set-seek`'s merge anchor additionally requires
  `seekPreservesTargetOrder` and a key-source row estimate under
  `min(maxKeys, breakEvenKeys)`. `pk in (select id from ksrc)` where the key column is
  itself a primary key plans as a MERGE semi join, so this is the arm a store PK target
  most naturally hits. Determine and pin which arm fires.

## Test coverage to add

In `packages/quereus-store/test/key-set-seek-store.spec.ts`, mirroring its existing
secondary-index cases and reusing `IdxStrCapturingStoreModule` / `multiSeekRe` /
`SCAN_RE`:

- **Replace** the `gates that must decline` case
  `a runtime set on the PRIMARY KEY declines: the store claims IN for secondary indexes
  only` (~line 454). It must now assert the rewrite fires (`KEYSETSEMIJOIN` in
  `query_plan()`) and the store receives `multiSeekRe('_primary_')`.
- Store module, no isolation: basic set; duplicate and NULL inner values collapse before
  `inCount` is stamped; an empty key set never opens the target; a one-key set; a set
  matching nothing still seeks; a `delete` and an `update` driven by the set read their
  victims through the seek.
- Composite primary key: the rewrite declines (see above) and the query still answers.
- **Under the isolation layer** (the `store behind the isolation layer` describe block),
  with staged puts and deletes both inside and outside the key list. The failure to look
  for is a stale row appearing beside its updated copy, or a deleted row resurfacing —
  this is the case `bug-isolation-multiseek-merge-order` was filed for, and
  `scanMultiSeekPrimary`'s ascending-encoded-key emission is what satisfies it. Assert
  RAW emission order, no JS re-sort:
  - a staged insert whose key is in the set surfaces;
  - a staged in-place update of an in-set row appears exactly once, in its new form
    (both streams carry it — a merge slip emits it twice);
  - a staged delete of an in-set row does not resurface;
  - staged rows outside the key list are excluded;
  - several staged rows straddling the committed keys interleave correctly;
  - a `delete … where pk in (select …)` inside a transaction, read back, then committed.
- Also add the store's own pending-op (no isolation layer) read-your-own-writes case, the
  twin of the existing `reads its own uncommitted writes through the seek` test.

## Expected results

- `select … from t where pk in (select …)` takes the seek branch of `KeySetSemiJoin`
  against a store-backed target, matching what a secondary-index target does today.
- Row sets identical to the pre-change plan in every case, including all declines.
