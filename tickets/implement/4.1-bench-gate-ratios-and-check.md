# Why

`bench-gate-reference` builds a gate over exact work counts. This ticket adds the second
portable measurement — a bound on one benchmark's speed against another's *in the same
run* — and makes the whole thing part of `yarn check`, which is this project's full
pre-release verification pass. There is deliberately no continuous-integration service and
this ticket does not add one; the gate is one more step in the run that already exists.

A ratio between two benchmarks in the same run cancels out machine speed, which is what
makes it gateable when an absolute millisecond figure is not. Today there is exactly one
such guard (`execution/correlated-subquery` against `hand-batched-peer-count`, max 10x), it
only runs under the full `yarn bench`, and nothing runs `yarn bench` automatically.

# Architecture

## Lift the guard logic out of `run.mjs`

`checkRatioGuards` and `reportRatioGuards` currently live in `bench/run.mjs` (a 1022-line
file) and are needed by `gate.mjs` too. Move them verbatim into `bench/lib/guards.mjs` and
import from both. This also puts them inside the type pass, which `bench/*.mjs` is not.

Keep every existing rule intact — they encode decisions worth preserving: a guard naming an
unselected benchmark is `skipped` under `--filter` and `misconfigured` without one; a guard
naming a failed or declined benchmark is `not-evaluated`; a guard naming an `informational`
row is `misconfigured`, checked before everything else.

## Only guard members are timed, and they are timed in forked processes

The gate's counters pass runs everything in one process, which is correct for counts and
wrong for timings — a benchmark's measured speed depends on which benchmarks preceded it in
the same process (measured at 0.37x-1.66x). So the guard pass is separate:

- The timed set is exactly the benchmarks named by some `ratioGuard`. Today that is two.
- Each is forked one at a time via the existing `bench/child.mjs`, exactly as `run.mjs`
  does, so the isolation guarantee that makes a ratio meaningful still holds.
- They are timed with a **reduced calibration profile** — a new `GATE_CALIBRATION` next to
  `CALIBRATION` in `bench/lib/calibrate.mjs`, with a shorter warmup and a shorter time
  target. The existing guard has roughly 10x headroom against its observed ratio, so a
  looser median is still far more precise than the guard needs.
- Budget: two forks plus two reduced-calibration measurements. Measure the actual added
  wall-clock and state it in `docs/benchmarking.md` next to the counters pass's ~42 s.

**A guard that fails under reduced calibration is re-measured once at full calibration
before it fails the run.** This is the "require it to reproduce" rule applied to ratios, and
it is what stops the gate from being routed around: a gate that produces false failures gets
disabled within a month. The report must show both measurements when this happens, and say
which one decided.

## Generalize the guard declaration

The plan called for making a guard cheap to add. Two changes:

- **A guard may name a benchmark in another suite** by writing its full `suite/name`; a bare
  name still resolves within the declaring suite. Today a guard cannot reach across suites
  at all, which rules out bounding an `execution` shape against a `store` micro-benchmark.
- **Validate the shape in `loadSuite`**, matching the existing checks on `counters`, `skip`
  and `informational`: a `ratioGuards` entry missing `name`, `baseline` or a finite positive
  `maxRatio` must fail loudly at load, not silently never evaluate. A guard nobody notices
  is not protecting anything.

Optionally add a `note` field carrying one sentence on what the guard protects, printed with
the verdict. The existing guard's note would be "catches `scalar-agg-decorrelation` failing
to fire".

The existing prohibitions stay and stay documented: no guard may name an `informational`
row, and no guard may bound a `@<backend>` row against a bare one — that prices a storage
engine against an in-process array, and there is no portable value for `maxRatio` there.

## Add guards for the shapes most prone to plan-shape regression

Add **at least two** new guards beyond the existing one. Candidate shapes, in rough order of
value:

- an indexed-filter benchmark against its full-scan twin — if index selection stops firing,
  the filtered form collapses toward the scan's cost;
- a batched storage-resolution row against an unbatched or single-key one in the `store`
  suite — if row resolution stops batching, the ratio moves sharply.

For each guard added: **measure the current ratio from a real `yarn bench` run, record it in
a comment next to the guard, and set `maxRatio` with at least 3x headroom over the measured
value** — or state in the comment why less headroom is defensible. An unmeasured `maxRatio`
is a guess that will either never fire or fire on a quiet Tuesday.

## The escape hatch, and it is visible

`--report-only` (and `QUEREUS_BENCH_GATE_REPORT_ONLY=1` for the case where the flag cannot
be threaded through a script) runs the full gate, prints the whole report including every
failure, and exits 0.

It must print a **loud, unmissable banner** — the same treatment `run.mjs` gives an
environment mismatch — saying the gate ran in report-only mode and did not fail the run. The
whole point is that the escape is *visible in the check log*, unlike the alternative escape
of quietly editing the reference set. Document when to use it: a stale reference set on a
release branch, or a machine under heavy load where a ratio needs re-measuring, and never as
a standing setting.

## Wire it into `yarn check`

`check` today:

```
docs:check → lint → build → typecheck → test:full → test:fork-strict → test:context-strict → test:repr-strict
```

Insert `bench:gate` **after `typecheck` and before `test:full`**.

- After `build`, necessarily: the bench suites import from `dist/`.
- Before `test:full`, deliberately — and this is a considered departure from the plan
  ticket, which assumed it would land at the end. `check` is `&&`-chained, so a gate placed
  after `test:full` reports a counter change only after the longest step in the run. The
  gate costs ~42 s and its failures are self-contained; surfacing them early is strictly
  better for the person running it. State the reason in `docs/architecture.md` section 6, so
  the next person does not "fix" the ordering back.

Add a root `bench:gate` passthrough alongside the existing `test:store` / `test:fork-strict`
passthroughs so the chain does not inline a `cd`.

## State the division of labour with the performance sentinels

`test/performance-sentinels.spec.ts` runs inside `yarn test` and asserts absolute wall-clock
with 10-50x headroom. It is not replaced and it is not merged; reconciling the workloads is
filed separately as `debt-perf-sentinels-share-bench-workloads`. What this ticket owes is a
plain statement in `docs/benchmarking.md` so nobody adds the same check twice:

- **Performance sentinels** — inside `yarn test`, absolute milliseconds, enormous headroom.
  They catch "something got an order of magnitude slower" on any machine, including a slow
  one, and they are the only thing in `yarn test` that looks at speed at all.
- **The regression gate** — inside `yarn check`, exact work counts and within-run ratios,
  never wall-clock. It catches *small* changes a 10x threshold can never see: one more
  storage round trip per row, a plan that stopped using an index.
- **`yarn bench`** — manual, the only place absolute timings are measured at all, and its
  exit code is deliberately not wired into anything automatic.
- **Where a new check goes**: the gate, unless it must run inside `yarn test`.

# Edge cases & interactions

- **A guard whose members are not in the counters set.** Guard membership and counter
  declaration are independent: a benchmark can be named by a guard and declare no
  `counters()`. The timed set is derived from the guards alone.
- **A guard member that skips** (a backend that declined) is `not-evaluated`, never a
  failure — the existing rule, and it must survive the move to `guards.mjs`.
- **`--filter` in gate mode** narrows both passes consistently, and a guard whose members
  were filtered out reports `skipped` rather than `misconfigured` — again the existing rule.
- **A cross-suite guard naming a suite that failed to load.** `loadSuites` throws on a
  malformed suite already; a guard naming a benchmark in a suite that loaded but does not
  contain it is `misconfigured`, the same as a bad bare name.
- **The re-measure path must not double-count.** A guard re-measured at full calibration
  produces a second reading for the same benchmark; the report must present them as one
  verdict with two measurements, not as two rows.
- **`--report-only` must still exit non-zero on a harness error** — a bad flag, an
  unreadable reference file, a suite that will not load. It suppresses *findings*, not
  breakage; otherwise a typo in the invocation reads as a passing gate.
- **`yarn check` on a dirty tree** is the normal case during development. The gate reports
  the dirty tree (from ticket A) and still runs; it must not refuse, or `check` becomes
  unusable outside a release branch.
- **Ordering interaction with `clean`.** Root `build` runs `yarn clean` first, so `dist/` is
  freshly built by the time the gate runs. A developer invoking `yarn bench:gate` directly
  against a stale or absent `dist/` gets an import error — that is the existing behaviour of
  every bench entry point and needs no new handling, but say so in the docs.

# Tests

Extend `test/bench-gate.spec.ts` (or add `test/bench-guards.spec.ts` if it grows) — again
running no benchmark:

- every existing `checkRatioGuards` status survives the move to `guards.mjs`: `ok`,
  `failed`, `skipped` under a filter, `misconfigured` without one, `not-evaluated` for a
  failed member, `not-evaluated` for a declined member, `misconfigured` for an
  `informational` member checked ahead of all of those.
- a bare guard name resolves within its own suite; a `suite/name` guard resolves across
  suites; a cross-suite name pointing at a nonexistent benchmark is `misconfigured`.
- `loadSuite` throws on a `ratioGuards` entry missing `name`, missing `baseline`, or with a
  `maxRatio` that is absent, zero, negative or non-finite.
- the re-measure rule: a guard failing the reduced measurement and passing the full one does
  not fail the run, and the verdict record carries both measurements.
- `--report-only` turns a failing verdict set into exit 0 while leaving the findings in the
  report, and does *not* suppress a usage error.

Then verify end to end: `yarn check` on a clean tree passes with the gate in the chain, and
the gate's added wall-clock is measured and written into the docs.
