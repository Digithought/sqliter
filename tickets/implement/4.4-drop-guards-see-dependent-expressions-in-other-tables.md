# The guards scan one table; the rename they are defined against scans every table

`ALTER TABLE … RENAME COLUMN` rewrites CHECK expressions, column `DEFAULT`s and
`GENERATED ALWAYS AS` bodies on **every table in every schema** — a CHECK may
contain a subquery, so another table's constraint can legitimately name this
column. The DROP guards that are supposed to refuse exactly what the rename
would have rewritten scan only `tableSchema`'s own constraints and columns.

Verified at HEAD (memory module, `main` only — no second schema needed):

```sql
create table T (id integer primary key, v integer);
insert into T values (1, 10);
create table X (id integer primary key, n integer, check (n < (select max(v) from T)));

alter table T drop column v;   -- accepted, no error
insert into X values (1, 1);   -- Column not found: v
```

The same shape through a default:

```sql
create table Z (id integer primary key, w integer default ((select min(v) from T)));
alter table T drop column v;   -- accepted
insert into Z (id) values (1); -- Column not found: v
```

`X` and `Z` are now unwritable and the error names neither `T`, the dropped
column, nor the constraint that broke.

## The same hole under the table verb

`DROP TABLE` has no expression-dependency guard at all:

```sql
create table T (id integer primary key, v integer);
create table X (id integer primary key, n integer, check (n < (select max(v) from T)));
drop table T;                  -- accepted
insert into X values (1, 1);   -- Table 'T' not found in schema path: main
```

Both verbs resolve at the same missing capability, so they are one ticket: the
catalog cannot answer *"which stored table expressions reference this object?"*.

## Root cause and the shape that retires it

Add one catalog-level query, in a new `packages/quereus/src/schema/expression-dependents.ts`,
and have every guard call it instead of hand-rolling a scan:

```ts
/** A stored, table-attached expression that references a probed object. */
export interface ExpressionDependent {
    table: TableSchema;
    /** What to call it in an error: `CHECK constraint 'ck1'`, `the DEFAULT of column 'w'`, … */
    describe: string;
}

/** Tables in EVERY schema whose CHECK / DEFAULT / GENERATED expressions name `<schema>.<table>.<column>`. */
export function findColumnExpressionDependents(
    db: Database, tableSchema: TableSchema, columnName: string,
): ExpressionDependent[];

/** Tables in EVERY schema whose CHECK / DEFAULT / GENERATED expressions name `<schema>.<object>`. */
export function findTableExpressionDependents(
    db: Database, schemaName: string, objectName: string,
): ExpressionDependent[];
```

Both walk `_getAllSchemas()`, build one `snapshotObjectRefResolvers(db)` and
take `forHomeSchema(table.schemaName)` per scanned table, and reuse the existing
probes — so "the drop refuses exactly what a rename would have rewritten" stays
true by sharing the walk rather than by comment.

**The own-table / other-table probe split is load-bearing**, and
`rewriteTableForColumnRename` already encodes it (`isRenamedTable` at
`alter-table.ts` ~2380):

- On the **altered table itself**, use the *seeded* probe
  (`columnReferencedInCheckExpression`) — a CHECK / DEFAULT there is written
  against the row being written and owns the `new.` / `old.` namespace.
- On **any other table**, use the *unseeded* probe (`columnReferencedInAst`) —
  that table's row image is its own columns, not ours; only an explicit
  reference through a subquery counts.

Getting this backwards produces false refusals on every table that happens to
have a like-named column.

## Policy: refuse, both verbs

Refuse is what the existing expression guards already do, it is SQLite's
position for the family, and it keeps `drop table T` and
`alter table T drop column v` from disagreeing about the same constraint.

Both guards are called **from the user-facing DDL emitters only** (`runDropColumn`,
`emitDropTable`) — never from `SchemaManager.dropTable`, which also drives
rollback, catalog import and the declarative differ's drop/recreate. That is
exactly where `assertNoAssertionDependsOn` is wired, and for the same reason: a
differ convergence that replaces both `T` and `X` must not be vetoed.

Accepted cost, same as the existing CHECK guard: an **unnamed** table-level
CHECK cannot be dropped by name, so a column (or table) it references can only
be removed by rebuilding the referencing table. Refusal messages must therefore
quote the offending expression when the constraint has no name.

## Not in scope — views and materialized views

Dropping a table or column out from under a plain view stays **allowed and
breaks the view**; that is the engine's stated position (`assertion-drop-guard.ts`
documents the asymmetry: a broken view breaks queries of that view, a broken
CHECK makes a whole table unwritable). Do not add a view arm here.

Partial-index predicates need no arm either: the parser rejects a subquery in a
partial-index predicate (`Unsupported expression in partial-index predicate:
subquery`), so such a predicate can only name its own table. Verified — a
comment in `schema/catalog-persistability.ts` already relies on this.

## Edge cases & interactions

- **Self-reference on the altered table.** The dropped column's *own* DEFAULT is
  skipped today (it goes away with the column). Preserve that; it is tested.
- **Like-named column on another table.** `check ((select min(v) from U) >= 0)`
  on table `X` must NOT block dropping `T.v`. The unseeded probe plus the
  resolver decide this — the existing scope-awareness tests are the model.
- **Cross-schema.** A CHECK in schema `A` whose subquery reads `main.T` must be
  found (the rename already rewrites it). A bare `t` in `A` that resolves to
  `A.t` must not.
- **The altered/dropped table appearing in its own scan.** `findTableExpressionDependents`
  will see the dropped table's own CHECKs naming itself. Those vanish with the
  table — skip the target table itself in the table verb; keep it (seeded) in
  the column verb.
- **Generated columns.** `runDropColumn` already refuses off
  `generatedColumnDependencies` for the altered table. Do not duplicate that arm
  for the same table; DO cover a *generated expression on another table* that
  reads the dropped column through a subquery.
- **Guard ordering.** All guards must run before `requireVtabModule` /
  `module.alterTable` / the module's drop, so a refused statement never reaches
  a persisting module.
- **`IF EXISTS`.** Governs absence, not dependency — it must not weaken the new
  `DROP TABLE` refusal, matching `assertNoAssertionDependsOn`.
- **Declarative-schema convergence.** Confirm `test/logic/50-declarative-schema.sqllogic`
  and the maintained-table suites still pass; a differ-driven drop must not be
  refused. If any of them break, the guard is wired at the wrong layer.
- **Error text.** Must name the dropped object, the referencing *table*, and the
  constraint (by name, or by expression when unnamed) — the current message
  names none of them.
- **Cost.** Each guard now walks every table in every schema. DDL is rare and the
  scan is over already-parsed ASTs; if it ever shows as hot, gate on a cheap name
  scan first. Record that as a `NOTE:` at the site rather than optimising now.

## Expected test outcomes

- `alter table T drop column v` with `X`'s CHECK reading `(select max(v) from T)`
  → refused, `StatusCode.CONSTRAINT`, message naming `X` and the constraint;
  `insert into X` still works afterwards.
- Same for a `DEFAULT` and for a `GENERATED ALWAYS AS` on another table.
- `drop table T` with that CHECK on `X` → refused; after `alter table X drop
  constraint <name>`, the drop succeeds.
- `check ((select min(v) from U) >= 0)` on `X` does not block dropping `T.v`.
- A cross-schema CHECK (`A.x` reading `main.T`) is caught; a bare `t` meaning
  `A.t` is not.
- Dropping a table under a plain view still succeeds (no regression).
