# Why

`yarn test:store` exists because the persistent path is different enough to need its own
full correctness run — key encoding, batched row resolution, transaction commit, index
build and catalog rehydration are all code the memory table never executes. None of it has
any performance coverage. A change that doubled the storage round trips behind a
secondary-index scan would leave `yarn bench` unchanged.

`bench-backend-dimension` built the mechanism. `store-shared-inmemory-provider` supplies the
provider. This ticket supplies the backend and the metric that actually matters for it.

# Architecture

## No new dependency is needed

`packages/quereus/package.json` already lists `@quereus/store` and
`@quereus/plugin-leveldb` as workspace devDependencies (they are what `yarn test:store`
runs on), and `node_modules/@quereus/*` are symlinks into `packages/`. Node resolves
symlinks to their real path, so `@quereus/store`'s import of `@quereus/quereus` and the
bench's own `../../dist/src/index.js` land on the same file and therefore the same module
instance. There is no dual-instance hazard and nothing to add to a manifest.

Everything here needs a built `dist/` in **both** packages, which `yarn build` already
produces in dependency order. A bench run against a stale `packages/quereus-store/dist`
measures the wrong code; say so in the docs next to the existing `dist/` warning.

**Load the store module lazily, not at the top of `backends.mjs`.** `run.mjs` calls
`loadSuites()` in the PARENT purely to enumerate benchmark metadata, which imports every
suite file. A static `import { createIsolatedStoreModule } from '@quereus/store'` therefore
makes an unbuilt or broken store package kill the entire `yarn bench` run at enumeration —
including the parser and planner suites, which have nothing to do with it. A dynamic import
inside the backend's `open()` (the pattern `test/logic.spec.ts` already uses at its
`loadStoreModules()`) keeps the failure local, and lets `skip()` report it as a reason.

## The store backend

One new descriptor in `bench/lib/backends.mjs`:

- `id: 'store-mem'`, `label: 'StoreModule (isolation-wrapped) over an in-memory key-value provider'`
- `open()` builds a provider via `createInMemoryProvider()` from `@quereus/store/testing`,
  calls `createIsolatedStoreModule({ provider })`, registers it as `'store'` and sets
  `default_vtab_module` to `'store'`; `close()` closes the `Database` and then the module's
  `closeAll()`.

Two decisions, both settled here rather than left to the implementer:

**It is isolation-WRAPPED by default.** `createIsolatedStoreModule` wraps `StoreModule`
with the isolation layer for read-your-own-writes, rollback and savepoints. That is what
`yarn test:store` runs and what a real deployment runs, so it is what the default row must
measure. A bare-`StoreModule` reading is a different question ("what does the wrapper
cost"), and answering it is `feat-bench-isolation-and-sync-suites`, not this ticket. Do not
add a second backend id for it here.

**The provider is in-memory, not on disk.** That is the point: it isolates *store-layer*
cost from *disk* cost, it is deterministic, and it is cheap enough to run on every `yarn
bench`. Disk is `bench-store-leveldb`, opt-in and out of any gate.

## The skip seam

`bench-backend-dimension` shipped `skip()` on a `Benchmark`, evaluated in the worker before
`setup`, keeping the row and printing `skipped — <reason>`. What it did **not** ship is a
way for a BACKEND to decline a workload — `BenchBackend` has `id` / `isDefault` / `label` /
`open` and nothing else, and the two suite binders never set `skip`.

`expandBackends` is the natural place to close that: it is already the one function that
sees a (workload, backend) pair, and wiring the skip there means neither suite file has to
repeat it and no future suite can forget it. Give `BenchBackend` an optional
`skipWorkload(workload)` returning a reason or `null`, and have `expandBackends` attach a
`skip` built from it. Decide deliberately what happens when a binder ALSO returns a `skip`
(compose them, or reject the combination loudly) — do not let one silently overwrite the
other, which is the failure mode the existing `bind`-returned-a-name check exists to
prevent.

## Round trips are the primary metric

Time on a store backend is a machine fact. The number that is stable across machines, and
the one a later gate keys on, is how many times the engine went to storage and with how
many keys.

The harness already has the right seam: `counters()` runs ONCE, untimed, after the timed
loop. So the timed `fn` runs against the plain provider (no counting overhead in the
number), and `counters()` builds a *second* database over
`createCountingProvider(map, 'all')` and drives the same statement. `mutation.bench.mjs`
already establishes the own-database-in-`counters()` pattern for three of its four entries.

`bench/lib/store-counters.mjs` returns a nested block, which `flattenCounters` in
`compare.mjs` already walks to arbitrary depth:

```js
{
  engine: { /* the existing WorkCounterSnapshot from snapshotStatement */ },
  store: {
    'main.bench_t':                  { iterateEntries, getManyCalls, getManyKeys, singleGets },
    'main.bench_t_idx_bench_t_val':  { /* same four */ },
  }
}
```

The four fields need naming care, because `CountingKVStore`'s raw counters do not mean what
their names suggest. Its `getMany` deliberately routes each key through the wrapper's own
counted `get`, so `getCount` includes every key of every batch. Therefore:

- `getManyCalls` = round trips (batched reads issued),
- `getManyKeys` = key volume carried by them,
- `singleGets` = `getCount - getManyKeyCount`, the reads that were genuinely one-at-a-time,
- `iterateEntries` = entries pulled from `iterate()`.

Derive `singleGets` in `store-counters.mjs`, once, with the reason in a comment — not at
each call site. A negative value is impossible and means the counting contract changed:
throw rather than report it.

Store names in the block are the BUILT names the counting map is keyed by, so they are
stable across runs and diffable path-by-path. Do not re-key them by table name. (For the
`populated` fixture those are `main.bench_t` and `main.bench_t_idx_bench_t_val`.)

The fixture populate must not be counted for the READ workloads — it is setup, not the
measurement — so the helper needs a reset between populating and driving the statement.

# Edge cases & interactions

- **Not every workload runs on the store.** Anything asserting memory-module behaviour, and
  anything the store's cost model plans differently, skips with a stated reason — never by
  omission. `logic.spec.ts`'s `MEMORY_ONLY_FILES` set (line ~56) and the
  `-- requires-capability:` mechanism are the precedent for *what* diverges; read them
  before deciding, and put the reason in the skip string. Two specific things to check
  rather than assume, both drawn from that set:
  - the store applies NOCASE to an **undecorated text primary key** where memory uses
    BINARY (`10.2.2-default-collation-memory.sqllogic`, and `docs/schema.md`
    §"Per-column PK key collation"). The `textPk` fixture declares exactly that, so confirm
    `text-pk-range-scan-10k@store-mem` still returns its 1 000 rows — the corpus is all
    lowercase, so it very likely does, but it should be confirmed rather than assumed.
  - the store's cost model can validly prefer a different join shape
    (`83-merge-join.sqllogic`). That does not make `join-1kx1k@store-mem` invalid — it
    still returns 1 000 rows — but it does mean its counters describe a possibly different
    plan than the memory row's, which is fine and worth a comment.
- **`ratioGuards` need no change.** They name bare benchmark names, which are the default
  backend's rows, and `execution.bench.mjs` already documents that guards are deliberately
  not expanded per backend.
- **The store path is slower, sometimes much slower.** Calibration adapts (`warmupTargetMs`
  250, `targetTotalMs` 1000, `maxTotalMs` 5000, `minSamples` 5), but `minSamples` is checked
  *before* `maxTotalMs`, so a 3-second call still costs ~5 samples plus warmup. Measure the
  added wall-clock of the store rows and report it; if any single benchmark approaches
  `BENCH_TIMEOUT_MS` (120 s at `run.mjs:53`, and it covers `setup` too), pin it with
  `iterations`/`warmup` and a comment saying why, rather than raising the timeout.
- **A pinned benchmark forfeits its spread figure.** Five samples cannot support a quartile
  range. Prefer a smaller row count for a store row over pinning it.
- **Populate cost is setup, not measurement** for the read workloads — but for the mutation
  workloads it *is* the measurement, and inserting 10k rows through the isolation overlay
  plus a transaction commit is a different order of cost than the memory table. Check
  `mutation/bulk-insert-10k@store-mem` explicitly before assuming 10k rows is the right size
  there; a smaller store-side row count with the count in the name is better than a
  benchmark nobody will wait for. `single-row-insert-1k` is the one to look at hardest: it
  issues 1 000 separate `db.exec` inserts, each its own implicit transaction, so on the
  store it prices 1 000 commits through the isolation layer.
- **The counters pass builds a second full database.** Three mutation entries already do,
  costing ~340 ms of a ~48 s run; the store versions cost more. The existing NOTE in
  `mutation.bench.mjs` names the fix — populate fewer rows in `counters()` than in `fn`,
  since counts need only be *the same every run*, not the timed row count. Take that option
  rather than growing the untimed pass, but note what it costs to build:
  `MutationWorkload.counters(db)` takes **no options today**, and `BATCH_COUNT` (20) /
  `SINGLE_ROWS` (1 000) are module constants in `bench/workloads/mutation.mjs`. Lowering
  those constants outright would also shrink the MEMORY rows' counters pass and weaken the
  claim its comments make — `bulk-insert-10k` snapshots the first and last batch precisely
  so that "insert cost does not grow with table depth" is checked across 9 500 intervening
  rows. So the reduction has to be **per-backend** (an options bag threaded to `counters`,
  defaulted to the current full scale), not a constant edit. Measure first; if the store
  counters passes turn out cheap, skip the parameterization and say so.
- **Counter portability is an assumption, not a fact.** `bench-regression-gate` records that
  nothing has yet compared counter blocks across two machines, and that
  `bug-join-order-depends-on-wall-clock` is a live mechanism by which plan choice — and so
  counts — could differ on a slower machine. Store round trips are reported here as facts
  about this run; do not add a gate.
- **Every store backend must leave no state behind.** `close()` must close the module, not
  only the `Database`. A leaked handle trips the worker's leaked-handle exit path, which
  presents as a hang.

# Tests

- One run of `yarn bench --filter @store-mem` completes, every row either produces numbers
  or states a skip reason, and a second run produces byte-identical `store` counter blocks.
  Identical counters across two runs is the acceptance criterion for the metric; identical
  *timings* is not and must not be asserted.
- `yarn bench` (unfiltered) still passes, and the bare-named memory rows' counters are
  UNCHANGED — nothing in this ticket may move them.
- `yarn workspace @quereus/quereus lint` clean (it type-checks the test files too).
