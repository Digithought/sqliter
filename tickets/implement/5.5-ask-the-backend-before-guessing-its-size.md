# Send "unknown" as unknown, so a backend that knows can answer

`BestAccessPlanRequest.estimatedRows` is documented as:

> the planner's hint, populated **only from `ANALYZE`-collected statistics**; `undefined`
> means unknown, and a module that can size itself may substitute its own count there.

Five places build that request. Three honor the contract:

| site | passes |
|---|---|
| `rule-select-access-path.ts` ~263 | `tableRef.estimatedRows \|\| undefined` |
| `rule-lateral-top1-asof.ts` ~261 | `tableRef.estimatedRows ?? undefined` |
| `access-leaf.ts` `buildProbeRequest` | whatever the caller passes (both callers pass undefined when unknown) |

Two do not:

```ts
// rule-grow-retrieve.ts ~369 and ~800
estimatedRows: tableRef.estimatedRows || context.stats.tableRows(tableSchema) || 1000
```

For a never-analyzed table this sends `1000` — a number nobody measured — and the module
can no longer tell it apart from a real 1000-row `analyze` result. Two consequences:

1. **A backend that knows its own size is locked out.** `quereus-store` maintains a live
   row count for every table and has a function whose entire purpose is to fill the gap:

   ```ts
   function sizeRequestFromLiveCount(request, table) {
       if (request.estimatedRows !== undefined) return request;   // ← always returns here
       const liveRows = table?.getKnownRowCount();
       ...
   }
   ```

   It returns early every time, because the request always carries a number.

2. **The same table gets two different sizes.** `rule-grow-retrieve` says 1000;
   `rule-select-access-path` says unknown. The module prices the same table differently
   depending on which rule asked, and the two answers are then compared.

## Decision

Make all five sites send `undefined` when nothing has been measured, and leave the
fallback where it already lives — on the module side, which is the only side that can do
better than a constant.

Concretely, `rule-grow-retrieve`'s two expressions become
`tableRef.estimatedRows ?? context.stats.tableRows(tableSchema)`, dropping the `|| 1000`.

Note the `??` rather than `||`: after the prereq ticket, `0` is a *measured empty table*
and must be sent as `0`, not swallowed into the next fallback.

The module-side defaults stay exactly as they are — `?? 1000` in
`store-module-access-plan.ts` (~533, ~900) and `|| 1000` in `vtab/memory/module.ts` — so a
module with no way to size itself behaves as it does today. The only change is that a
module *with* a way to size itself now gets the chance.

`context.stats.tableRows` may itself return the `NaiveStatsProvider` default rather than a
measurement (see the prereq ticket's change to `catalog-stats.ts`). Check whether it does
here, and if so pass the *catalog* count through instead and let the module's own default
be the sole fallback — a naive default dressed up as a hint defeats the whole point. State
what you found either way; this is the one judgment call in the ticket.

## Edge cases & interactions

- **A measured empty table** (`analyze`d, 0 rows) must reach the module as `0`, not as
  `undefined` and not as 1000. Test it against both backends.
- **Prepared-statement staleness.** `store-module.ts` (~85) documents that a statement
  compiled against a one-row table keeps its scan after the table grows, and that the fix
  belongs at the recompile trigger, not there. Making `sizeRequestFromLiveCount` actually
  fire makes that staleness *reachable* where it previously was not. Do not fix it here —
  but confirm the recompile trigger exists and note in the handoff whether it covers
  growth, or file a follow-up if it does not.
- **Plan churn on the store backend is the expected outcome, and it can go either way.**
  The store's seek-versus-scan veto discriminates per query only when the arm's row
  estimate is statistics-backed. Measured evidence from the parent plan ticket, in-memory
  provider declaring the IndexedDB cost profile (`pointRead: 3.0`), 20,000 rows: a range
  matching 55% of them picked an `IndexSeek` (96.7 ms) without `analyze` and an
  `IndexScan` + `Filter` (43.8 ms) with it; a 10% range correctly kept the seek in both
  cases. Feeding the live count should move the 55% case without disturbing the 10% case —
  build the test around exactly that pair, and if the 10% case moves, stop and report it.
- **Transaction-local counts.** `getKnownRowCount()` includes the open transaction's
  buffered delta, so a statement reading what its own transaction just wrote is now costed
  against the size it will actually see. Test insert-then-select inside one transaction.
- **`buildProbeRequest`'s callers** (`rule-key-set-seek.ts` ~423, `index-nested-loop.ts`
  ~407) both derive `tableRows` from `leaf.source.estimatedRows || undefined`. After the
  prereq ticket that `||` swallows a measured `0`; change both to `??`.
- **The memory backend** has no live count to offer, so it must be unaffected. Any memory-
  backend plan change is a bug in this ticket, not an improvement — assert that first.
- **`validateAccessPlanRequest`** should reject a negative or non-integer
  `estimatedRows`; confirm `undefined` remains valid and is not newly rejected.
- **The key-set-seek merge gate starts firing.** `rule-key-set-seek.ts` (~618) declines
  its rewrite when the key source's `physical.estimatedRows` exceeds the number of keys the
  runtime would seek with, and proceeds when that estimate is absent. It has never
  declined: on both backends a freshly-populated table's physical estimate reads `0` today
  (measured on `packages/quereus-store` with 7 committed rows — the leaf and the `Project`
  above it both report `estimatedRows: 0`, and the rewrite fires). After the prereq ticket
  it reads `undefined` and still proceeds — unchanged. After **this** ticket, on the store,
  it reads a real live count and can decline for the first time. That is the intended
  behavior, but it is a plan change nobody has ever observed: exercise it with a key source
  larger than the seek threshold and confirm the plan falls back to the merge semi join
  with identical rows. Note that running `analyze` first does *not* reach this gate — with
  a 30-row key source the optimizer picks an index-nested-loop join instead and
  `rule-key-set-seek` never runs — so the test must be built on the un-analyzed path.
