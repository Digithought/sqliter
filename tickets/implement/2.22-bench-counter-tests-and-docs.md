# Why

`yarn bench` is not part of `yarn test`, so the only thing checking the comparison rules
is a person reading a table. `bench-comparison.spec.ts` exists for exactly that reason and
already covers the timing rules; the counter rules that landed alongside them have no
coverage at all. The benchmarking guide likewise still describes a comparison with only a
timing verdict in it.

Sequenced after `bench-counter-suite-passes` because the doc has to state **which suites
qualify**, and that is settled by the stability check that ticket runs — not by the audit
that predicted it.

# What the tests need to pin

All pure functions over plain objects, in the style the file already uses — build records
by hand, never by running a benchmark.

`flattenCounters` (exported from `bench/lib/compare.mjs`):

- A full `WorkCounterSnapshot` flattens to dotted paths covering `plan`, `instructions`,
  `tables` and `totals`.
- **Instructions are addressed by their `key` field, not by position.** This is the whole
  reason the flattener has a special case: inserting one instruction must not report a
  change against every instruction after it. A test that inserts an instruction at the
  front and asserts exactly one added path is the guard.
- A bare `PlanShape` and a named bag of snapshots both flatten without special handling.
- An `undefined` field (an absent optional `nodeType`) is skipped rather than recorded, so
  a value compares equal to itself after a JSON round-trip.

`diffCounters`:

- No tolerance: a difference of one is reported.
- Paths are sorted, so two runs of the harness print changes in the same order.
- A path on one side only is reported with `null` on the other (rendered `absent`).
- Identical blocks produce an empty change list.

The per-benchmark counter verdict, through `compareRun`:

- Both sides carry counters and match ⇒ `same`.
- Both carry them and differ ⇒ `changed`, with every difference listed.
- Baseline entry has no `counters` ⇒ `new`, **not** `changed`.
- This run has none and the baseline did ⇒ `dropped`.
- Neither has one ⇒ `none`.
- `compareRun(..., { counters: false })` ⇒ every row `skipped`, so a `--no-counters` run
  does not report the whole baseline as dropped.
- A failed / new / missing / `--filter`-excluded benchmark carries `none`, never a diff.
  The `--filter` case matters most: a narrowed run must not report every unselected
  benchmark's counters as deleted.
- **A changed counter never sets `gated` and never raises `regressions`.** Gating is the
  downstream regression-gate ticket; reporting comes first so the counters can be watched
  for a while before anything fails a build over one.

# What the doc needs to say

A section in `docs/benchmarking.md`, near the comparison rules:

- What a work counter is, and the one-sentence reason it has no noise floor: a timing
  delta says "this might be slower", a counter delta says "this does different work".
  Different claims, so they never share a column.
- How to add a `counters()` pass, with the `snapshotStatement` example, and the rule that
  it runs after timing and before `teardown` — never inside `fn`, whose number the
  counting generators would corrupt.
- **The drain requirement**, and why a partial drain reads as a change in the engine when
  nothing changed but the loop. (The "Adding a benchmark" section already has a bullet on
  this; link rather than restate.)
- Which suites qualify and which do not, with the reason — as settled by the stability
  check, not as predicted.
- `--no-counters`, and the `counters_collected` field that distinguishes a file whose
  benchmarks declare no pass from one written by a `--no-counters` run.
- The per-benchmark cap on printed changes (`COUNTER_CHANGES_SHOWN` in `run.mjs`), and
  that the full list is always in the results JSON's `comparison` block.
- Add `bench/lib/counters.mjs` to the "Where the code lives" table.

`docs/benchmarking.md` is not near its size cap, so this can be additive.
