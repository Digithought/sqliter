# A literal DEFAULT must be checked against the column's declared type where it is declared

## What breaks today

```sql
create table a (id integer primary key, n integer default 'abc');   -- accepted
insert into a (id) values (1);
-- Error: Type conversion failed for column 'n': Cannot convert 'abc' to INTEGER
```

The declaration is the thing at fault, but the error arrives on the first insert that
relies on the default, and names that insert.

Three declaration sites share the gap:

| site | today |
|---|---|
| `create table … default 'abc'` on an `integer` column | accepted |
| `alter table … alter column n set default 'abc'` | accepted |
| `alter table … alter column n set data type integer` while the column's stored default is `'abc'` | accepted |

`alter table … add column n integer default 'abc'` already refuses it
(`runtime/emit/alter-table.ts` ~613 folds through `foldDefaultToType`), and so does
`set not null` when it has to backfill (`vtab/memory/layer/alter-column.ts` ~210). The
check exists; three sites just do not call it.

## The check

`foldDefaultToType(expr, logicalType, columnName)`
(`packages/quereus/src/types/validation.ts` ~185):

- returns `undefined` when the expression does not fold to a literal — a function call,
  a `new.<col>` reference, a bare column name. Those stay deferred to write time, which is
  correct and must not change;
- returns the converted value when it folds;
- **throws** `QuereusError(StatusCode.MISMATCH)` when the literal folds but cannot be
  converted, carrying the same message text the INSERT path produces.

So each of the three sites needs one call whose return value is discarded — the throw is
the whole point.

## The change

### `CREATE TABLE`

In the `createTable` guard block, before `module.create` (so a refusal leaves no storage
behind), fold every column's `defaultValue` against that column's `logicalType`. Place it
next to `validateDefaultDeterminism`, which already walks the same columns for a different
property.

Not on the import / rehydrate path — a catalog written before this guard must still open.
Same placement rationale the neighbouring guards already carry.

### `ALTER COLUMN`, both arms

Both live in the **engine-side** `runAlterColumn` (`runtime/emit/alter-table.ts` ~1425),
ahead of the `module.alterTable` call — which means one change covers memory and store
alike. Put them beside the `validateCollationForType` / `validateAlterColumnDefault`
checks already there, which have exactly this shape:

- **`set default`** — fold the *new* default against the column's *current* logical type,
  right after the existing `validateAlterColumnDefault` call (that one rejects bind
  params / bare columns / non-determinism; it says nothing about type).
- **`set data type`** — fold the column's *existing* stored default against the **new**
  type, beside the existing `validateCollationForType(oldCollation, inferType(newType))`
  check, which guards the analogous "the retype would mint a column CREATE TABLE would
  refuse" case for collation.

Do not touch the module-side `alter-column.ts` files in either backend. They stay as they
are; the engine-side gate is what makes the two agree.

## Tests

Prefer `test/logic/*.sqllogic` for these — they run on both backends under `yarn test:store`.

- `create table … (n integer default 'abc')` → `-- error:`, and the table is not registered.
- Every type family that can reject a literal: `integer default 'abc'`, `real default 'x'`,
  a `date` / temporal column with a non-parsing string default, `json default '{'`.
- **Convertible** literals still accepted and still stored converted: `integer default '7'`
  inserts `7`; `real default -123.0` (a `UnaryExpr`, not a bare literal) folds.
- Non-foldable defaults untouched: `default (some_function())`, `default (new.other_col)`,
  `default (other_col)` — accepted at declaration exactly as today.
- `alter column … set default 'abc'` on an `integer` column → `-- error:`, and the column
  keeps its previous default (assert via `schema()` / a subsequent insert).
- `alter column … set data type integer` on a `text` column whose default is `'abc'` →
  `-- error:`, and neither the type nor the stored rows moved.
- `alter column … set data type` where the default *is* convertible (`text default '7'` →
  `integer`) still succeeds, and a later insert stores `7`, not `'7'`.
- `drop default` followed by the same `set data type` succeeds — the remedy the error should
  leave available.

Run: `yarn test`, then `yarn test:store`.

## Edge cases & interactions

- **`any`-typed columns** accept every literal; the fold must not start rejecting them.
- **NULL default** (`default null`) folds to `null` and is always acceptable — must not be
  confused with `undefined` (not foldable). `foldDefaultToType` already distinguishes the
  two; the call site must not collapse them.
- **`drop default`** is `setDefault === null` in the AST and needs no check — mirror the
  existing comment at that site.
- **Mutation-context defaults.** A default reading a mutation-context variable is not a
  literal, folds to `undefined`, and stays deferred. Cover one so a later refactor cannot
  quietly start rejecting them.
- **Generated columns** carry `generatedExpr`, not `defaultValue`, and are out of scope
  here (see the sibling backlog ticket `bug-table-expression-name-resolution-adhoc`).
- **PRIMARY KEY columns** already refuse `set data type`; the new fold must sit after that
  refusal so the clearer error wins.
- **Legacy catalogs.** A persisted table with an unconvertible default must still reopen
  through `importDDL` — add a test, because this is the one behaviour the CREATE-side check
  could plausibly break.
- **`apply schema`** runs through `createTable`, so a declaration carrying a bad default now
  fails the migration instead of deploying it. A migration mid-batch failure must abort
  through the existing `endSchemaBatch(error)` arm — no new machinery.
- **Error identity.** Keep `StatusCode.MISMATCH` and the existing message text —
  `foldDefaultToType` already produces the same text the INSERT path does, which is what
  makes the early failure recognisable as the same problem.
- **Sibling tickets** `7.1` and `7.2` add calls to the same `createTable` guard block; if one
  has landed, insert alongside it.
