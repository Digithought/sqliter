# A foreign key that cannot be enforced must say so, not fail obscurely or fall silent

## Arm A — the parent table does not exist (verified)

```sql
create table GhostC (id integer primary key, c integer references NoSuchParent(refd));
insert into GhostC values (1, 5);
-- CHECK constraint failed: _fk_ghostc_c (NEW.c is null or 0)
```

`_fk_ghostc_c` and `NEW.c is null or 0` are both engine-synthesized: when
`buildChildSideFKChecks` cannot resolve the parent, it emits a null-guard chain terminated
by a falsy literal — a constraint that passes exactly when MATCH SIMPLE says it should
(any FK column NULL) and fails otherwise. The *behaviour* is right and documented
(`docs/sql-ddl.md`: "If the referenced parent table does not exist, non-NULL FK rows are
rejected"). Only the message is wrong: nothing in it says `NoSuchParent` does not exist.

A second route reaches the same place and is much harder to diagnose: an unqualified
parent name binds to the **referencing table's own schema**, so a table in an attached
schema referencing a table in `main` resolves to a parent that is not there.

### Decisions taken — do not relitigate these

- **Forward references stay legal.** `docs/sql-ddl.md` § Order Independence and
  `docs/schema.md` both document that a foreign key may name a table declared later, and
  `buildForeignKeyConstraintSchema` defers parent resolution for exactly that reason.
  Restore-from-dump and mutually-referencing tables depend on it. So this is **not** a
  `CREATE TABLE` refusal — it is an error-message fix at the enforcement seam.
- **The unqualified-parent binding rule stays as it is.** An unqualified parent resolving
  to the child's own schema is documented (`docs/sql-ddl.md` ~1009) and matches SQLite,
  where a foreign key cannot cross databases. Changing it is a semantic change with no
  defect behind it. The remedy for the cross-schema case is to qualify the parent, and the
  new message makes that obvious by naming the schema it looked in.

### The change

Give a synthesized check the ability to carry its own violation text:

- add an optional `violationMessage?: string` to `ConstraintCheck`
  (`planner/nodes/constraint-check-node.ts`) and to `ConstraintMetadataEntry`
  (`runtime/row-constraints.ts`), carried across by `buildConstraintMetadata`;
- `constraintViolationMessage(metadata)` returns it verbatim when present, and keeps its
  current `CHECK constraint failed: <name>[ (<expr>)]` derivation otherwise.

One producer today: the `!parentSchema` branch of `buildChildSideFKChecks`, which sets

```
CHECK constraint failed: <fk name> — referenced table '<schema>.<parent>' does not exist
```

Keep the `CHECK constraint failed:` prefix. `constraintViolationMessage` documents that
engine-level CHECKs and synthesized FK existence checks deliberately share it for
compatibility with existing assertions, and downstream consumers identify a foreign key by
its name. Only the expression hint is replaced.

`constraintViolationMessage` is the single source of truth for both the immediate and the
deferred (commit-time) paths, so a child-side FK check — which is deferred — must report
the same text either way. Verify both.

## Arm B — the FK column count does not match the parent's key (static; confirm by test)

Both builders silently drop the check when the resolved parent columns do not line up:

```ts
// buildChildSideFKChecks ~235
if (parentColIndices.length !== fk.columns.length) { log(...); continue; }
// buildParentSideFKChecks ~361
if (parentColIndices.length !== fk.columns.length) continue;
```

`resolveReferencedColumns` *throws* when a written parent column **name** is absent, and
`buildForeignKeyConstraintSchema` compares counts when the declaration writes a parent
column list. So the surviving hole is the **no-column-list** form: `references Parent`
defaults to the parent's primary key, and if that key has a different number of columns
than the child's FK, both checks are skipped and the foreign key is **not enforced at
all** — inserts accept orphans, and parent-side RESTRICT stops rejecting deletes.

Replace both `continue`s with a raised `QuereusError` naming the mismatch:

```
Foreign key '<name>' on table '<schema>.<table>': <n> column(s) reference the primary key
of '<schema>.<parent>', which has <m> column(s).
```

This is a behaviour change from "silently unenforced" to "the statement fails", which is
the correct direction: an unenforceable constraint must not look enforced. Confirm the
mismatch is genuinely unreachable through `buildForeignKeyConstraintSchema` before writing
the error — if a declaration path can produce it, the clearer place to refuse is there, and
the plan-time raise becomes the backstop.

Check `getBatchableRestrictFks` (~484) and the runtime RESTRICT pre-check in
`runtime/foreign-key-actions.ts` for the same skip; they must not disagree with the
builders about which foreign keys are enforced.

## Tests

`test/logic/*.sqllogic` (runs on both backends under `yarn test:store`):

- insert into a child whose parent does not exist → error text naming the missing
  `'<schema>.<table>'`, not the synthesized expression;
- the same with a NULL FK value → **accepted**, MATCH SIMPLE unchanged;
- a composite FK where only one column is NULL → accepted (MATCH SIMPLE);
- the cross-schema route: attach a second schema, create a child there referencing a table
  that exists only in `main`, insert → the error names `'<attached>.<parent>'`, making the
  binding rule visible; qualifying the parent (`references main.parent(id)`) then works;
- **forward reference still works end to end**: create the child first, create the parent
  after, then insert successfully — the check must resolve on the later plan, and this is
  the regression that a create-time refusal would have broken;
- create the parent, insert, then **drop** the parent and insert again → the missing-parent
  message, proving resolution is per-plan and not cached from creation;
- deferred reporting: the same failure inside an explicit transaction reports the same text
  at COMMIT;
- Arm B: `references Parent` where `Parent` has a two-column primary key and the child FK
  has one column → error at plan time; and the parent-side case, where a delete from
  `Parent` must not silently bypass RESTRICT.

## Edge cases & interactions

- **MATCH SIMPLE must not move.** The null-guard chain is the *behaviour*; only the message
  changes. A NULL in any FK column still satisfies the constraint.
- **`pragma foreign_keys = off`** — no checks are built at all; nothing here should make a
  disabled foreign key raise.
- **Mutation-context shadowing.** `buildChildSideFKChecks` skips bare column names claimed
  by a mutation-context variable (`shadowedByContext`); the null-guard branch builds
  `NEW.<col>` references, so it is unaffected — keep it that way.
- **Self-referencing FK** resolves against the table being created; it must never hit the
  missing-parent branch.
- **Maintained tables / derived rows.** `core/derived-row-validator.ts` builds its own check
  list with its own `_rebuild_failed` message shape; the new `violationMessage` field must
  not disturb it.
- **`ON DELETE CASCADE / SET NULL / SET DEFAULT`** to a missing parent: the cascade machinery
  is parent-side and never fires (the parent does not exist). Confirm no path tries to plan
  a cascade against a missing parent and produces a second, different error.
- **Sync apply path.** `_isFkRestrictSuppressed()` gates only `'fk-parent'` checks; the
  child-side missing-parent check is not gated and must stay ungated.
- **Message-shape compatibility.** Grep for assertions on `CHECK constraint failed: _fk` and
  on the null-guard expression text before changing the message; update any that pin the old
  hint.
