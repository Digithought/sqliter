# One `if` is the whole bug

`ALTER TABLE … RENAME` and `… RENAME COLUMN` walk **every** schema when they
rewrite dependent *tables* (CHECK expressions, foreign-key targets,
partial-index predicates, column `DEFAULT` / `GENERATED` expressions). The
same two functions then rewrite dependent *views, materialized views and
assertions* only when the schema being iterated is the renamed table's own:

```ts
// alter-table.ts ~2170 (table verb) and ~2322 (column verb)
if (schema.name.toLowerCase() === renamedSchemaLower) {
    // ... view loop, assertion loop, materialized-view loop
}
```

So the inconsistency lives inside a single statement: a foreign key in schema
`temp` follows a rename of `main.t`, but a view in `temp` over `main.t` does
not.

Verified at HEAD:

```sql
create table main.t (id integer primary key, x integer);
create view temp.vt as select id, x from main.t;
alter table main.t rename to t2;      -- succeeds
-- temp.vt body unchanged: select id, x from main.t
select * from temp.vt;                -- Table not found: main.t
```

With an assertion in place of the view, every later write to the database
fails instead.

## Why this is now a small change

The gate was a *workaround for a matcher that could not tell schemas apart*.
That matcher is gone: `debt-rename-walkers-resolve-names-like-the-planner`
(complete) replaced `schemaMatches(nodeSchema, defaultSchema)` with a
`ResolveObjectRef` callback plus a canonical `targetKey`, and the loops inside
the gate **already** derive their resolver per iterated schema:

```ts
const resolve = resolvers.forHomeSchema(schema.name);   // already correct
```

A reference matches only when it resolves — under the *walked body's own home
schema path* — to the renamed object's key. A bare `t` in a `temp`-owned view
that means `temp.t` therefore cannot match a rename of `main.t`, and an
explicit `main.t` in that same body does match. Removing the gate is the fix;
no new resolution logic is needed.

## The pre-flight has to widen with it

`assertRenameDependentsPersistable` (`schema/catalog-persistability.ts`) vetoes
a rename whose prospective dependent bodies a storage module could not persist.
Its view/MV arm is scoped to one `Schema` **because the propagation was**, and
its `rewrite: BodyRewrite` closure is built once at the call site against a
single home schema (`alter-table.ts` ~240 / ~398). Both must widen together, or
a cross-schema dependent gets rewritten without ever being vetted.

Shape to move to — the pre-flight walks every schema and asks the caller for a
rewrite bound to each body owner's home schema:

```ts
export type BodyRewriteFor = (homeSchemaName: string) => BodyRewrite;

export function assertRenameDependentsPersistable(
    db: Database,
    rewriteFor: BodyRewriteFor,      // replaces (schema, rewrite)
    rewriteTable: TableRewrite,
): void
```

The `schema` parameter disappears entirely; the dependent-table arm already
iterates `_getAllSchemas()` and is unchanged. Call sites pass
`home => ast => renameTableInAst(ast, oldName, newName, objectResolvers.forHomeSchema(home), renameTargetKey)`
and the column-verb equivalent.

## Keep `alter-table.ts` from growing

That file is 2,523 lines and is already named in `backlog/debt-oversized-source-files`.
This change should *shrink* the two propagation functions (a removed gate and
one dedent). If any helper is added, put it in a sibling module rather than
inline.

## Edge cases & interactions

- **A body in schema A naming a bare `t` that resolves to `A.t`, while `main.t`
  is renamed.** Must NOT be rewritten. This is the false positive the gate used
  to prevent structurally and the resolver now prevents by construction — it is
  the single most important regression test of this ticket.
- **The converse:** a body in schema A naming `main.t` explicitly must now be
  rewritten (both verbs, all three object kinds).
- **Home-path fallthrough.** `Database._homeSchemaPath(home)` is
  `[home, ...session path]`, so a bare `t` in a `temp`-owned view can legally
  resolve to `main.t` when `temp` has no `t`. That body *must* follow the
  rename. Cover it — it is the case a naive "only rewrite qualified references
  across schemas" shortcut would get wrong.
- **Snapshot discipline.** `snapshotObjectRefResolvers(db)` must still be built
  before the statement's first catalog mutation and the same instance threaded
  through pre-flight and propagation. Propagation runs *after* the catalog swap;
  a live lookup would resolve the freed name down the search path to a different
  object. Do not build a second snapshot inside the widened loops.
- **Materialized views in another schema.** `propagateTableRenameToMaterializedViews`
  re-keys `sourceTables` / `covers` and re-registers row-time maintenance. Confirm
  a cross-schema MV survives the rename live (not left stale) — see
  `test/mv-cross-schema-dispatch.spec.ts` for how cross-schema MV dispatch is
  already exercised.
- **Staleness restore.** `restoreUnaffectedMaterializedViews(db, preStaleMvs)`
  runs once after all schemas. More schemas now emit `view_modified` /
  `materialized_view_modified` events, so more MVs may be marked stale
  mid-statement and need restoring. Verify an MV in a third schema that the
  rename provably did not touch is not left stale.
- **`temp` in the session search path.** The default path puts `temp` ahead of
  `main` for lookups. A test that creates `temp.t` and `main.t` with the same
  name is the sharpest probe of both directions.
- **Event count.** A dependent must still fire exactly one `view_modified` /
  `materialized_view_modified` per rewritten object, not one per schema
  iterated. `test/alter-table-schema-events.spec.ts` is the existing contract.
- **Rollback.** A module veto raised by the widened pre-flight must still leave
  the catalog untouched — the pre-flight probes `spineCloneAst` copies; keep it
  that way when the arm starts walking foreign schemas.

## Expected test outcomes

- `create view temp.vt as select id, x from main.t; alter table main.t rename to t2;`
  → `temp.vt` body reads `main.t2`; `select * from temp.vt` returns rows.
- Column verb: `alter table main.t rename column x to y` → `temp.vt` body reads
  `y`; a `temp`-owned assertion over `main.t` keeps enforcing (writes succeed).
- `create table temp.t (…); create view temp.vt as select * from t;` then
  `alter table main.t rename to t2` → `temp.vt` **unchanged** (its bare `t` is
  `temp.t`).
- A `temp`-owned view with a bare `t` where `temp` has no `t` → follows the
  rename of `main.t`.
