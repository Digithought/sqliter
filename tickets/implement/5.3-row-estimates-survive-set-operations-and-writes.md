# Fill the four remaining holes in the row-estimate relay

`debt-join-rows-from-physical-children` moved the single-source operators and the join
family onto `physicalSourceRows(childPhysical, source)` — the helper that reads a child's
**physical** row count and falls back to its logical getter. Four groups of nodes were
left out, and a plan that passes through any of them reports no row count from that point
upward, in either the logical or the physical view.

| group | logical getter | physical stamp |
|---|---|---|
| `SetOperationNode` | absent | absent |
| `AsyncGatherNode` | present (composes branches) | absent |
| `CTENode`, `CTEReferenceNode`, `RemoteQueryNode` | absent | absent |
| `InsertNode`, `UpdateNode`, `DmlExecutorNode` | mixed | mostly absent |
| `DeleteNode`, `ReturningNode` | present | present but reads the **logical** source getter |

`union all` is the largest gap because it is the most common of these shapes.
`AsyncGatherNode` matters because a PostOptimization rule substitutes it for `union all`
on high-latency plans — so the branch that was supposed to preserve the estimate loses it
in the physical view anyway.

## Composition rules

Each node needs a rule that is a pure function of its children's counts, with `undefined`
propagating (any unknown input ⇒ unknown output), matching how `AsyncGatherNode`'s
existing logical getter already behaves. Use these:

- **`union all` / `except all`** — sum of branches.
- **`union`** — `max(branches) … sum(branches)`; report the **sum**. It is the honest
  upper bound and the deduplication factor is unknown; a `Distinct` above it is what
  narrows the claim. State the choice in the code comment.
- **`intersect`** — `min(branches)`.
- **`except`** — the left branch's count (upper bound; the right can only remove rows).
- **`AsyncGatherNode`** — reuse the existing logical getter's arms (`unionAll` → sum,
  `zipByKey` → max, `crossProduct` → product) from `computePhysical`, fed the *physical*
  children. Factor the arms into one shared function so the logical getter and
  `computePhysical` cannot drift — the same discipline `aggregateRowsFrom` applies to the
  aggregate family.
- **`CTENode` / `CTEReferenceNode`** — pass the body's count through unchanged.
- **`RemoteQueryNode`** — pass the source's count through; it re-shapes latency, not
  cardinality.
- **`InsertNode` / `UpdateNode` / `DeleteNode` / `DmlExecutorNode` / `ReturningNode`** —
  pass the source's count through. Where a getter already exists and reads
  `this.source.estimatedRows`, `computePhysical` must read the **physical** child instead
  (`physicalSourceRows`); the logical getter keeps reading the logical source. `DeleteNode`
  (~87) and `ReturningNode` (~263) are the two that look correct but are not.

Every stamp goes through `physicalSourceRows`, never through `source.estimatedRows`
directly — that is the whole reason the helper exists (a `Retrieve` subtree replaced by a
physical access node declares no logical getter, so reading the logical side there yields
`undefined` and silently drops the count).

## Edge cases & interactions

- **Set operations with membership flag columns.** `SetOperationNode.computePhysical` has
  a `hasMembershipColumns` branch that returns a different property set. Both branches
  must stamp the estimate; do not add it to only one.
- **`undefined` propagation.** A single unknown branch makes the whole result unknown —
  do not treat it as zero and do not substitute a default inside the node. Defaults belong
  at the consumer. Test a two-branch `union all` where one side is a table function with
  no estimate.
- **Overflow.** `crossProduct` multiplies; three large branches can exceed
  `Number.MAX_SAFE_INTEGER`. Clamp to a finite ceiling rather than emitting `Infinity` or
  a non-integer — several consumers do arithmetic on the value.
- **`except` with a larger right side.** The result cannot go negative; the left-branch
  upper bound handles this, but assert it.
- **Recursive CTEs** (`RecursiveCTENode`) go through the working-table machinery, not
  `CTENode`. Their fixpoint cardinality is genuinely unknowable from the branches — leave
  them reporting `undefined` and say so in a comment rather than inventing a multiplier.
- **A CTE referenced twice.** `CTEReferenceNode` instances share one `CTENode`; each
  reference reports the body's count. That is correct (each reference produces that many
  rows) — confirm the shared-node identity is not disturbed by any `withChildren` rebuild
  the stamping forces.
- **Data-modifying nodes with no `returning`.** These produce zero user-visible rows but
  drive writes. Decide whether the estimate describes rows *emitted* (0 or 1 for a
  changes-count row) or rows *processed*, make every node in the family agree, and
  document it on the helper. Disagreement here is what a reviewer will look for.
- **Plan churn.** Nodes above a set operation now get a real count where they had a
  default, so sort strategy, cache thresholds and enclosing join costs can move. Re-derive
  any changed golden plan and justify it.
