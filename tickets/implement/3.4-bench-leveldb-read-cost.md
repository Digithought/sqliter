# Why

Storage backends declare what their basic reads cost relative to one sequentially-scanned
row, and the query planner prices access paths with those numbers. IndexedDB's come from a
real browser benchmark. LevelDB declares nothing, so it takes the framework's parity
default — "a random read costs about what a sequential read costs", `pointRead: 1.0` /
`seekPositioning: 0.5` — chosen by assumption years ago and never measured.
`debt-leveldb-cost-profile-measurement` (backlog) asks for exactly the measurement these
arms make routine.

# Architecture

## Measure at the key-value layer, not through SQL

The unit `cost-profile.ts` defines is explicitly *one row read sequentially during a full
scan*. That is a storage-layer unit, so the arms drive the `KVStore` the LevelDB provider
hands out directly — no `Database`, no planner, no isolation overlay. Two reasons, both
load-bearing:

- Engine overhead is roughly equal on both sides of the ratio, so including it compresses
  every ratio toward 1.0 and understates the very difference being measured.
- The sibling IndexedDB harness measured at the raw IndexedDB API for the same reason, and
  the whole point of matching its 200-byte row values is that the two backends' numbers be
  comparable.

Row shape: 200-byte values, matching `packages/quereus-plugin-indexeddb/bench/README.md`
(worth reading before choosing one). Keys come from the store's real
`encodeCompositeKey` over a single integer column — reached through
`loadStoreKeyApi()`, never through a second `@quereus/store` import — so the byte layout
and ordering are the ones the engine actually writes. Note in a comment that the IndexedDB
harness used a bare 4-byte big-endian ordinal instead; the difference is a few bytes of key
against a 200-byte value.

## The three arms, and why they share one benchmark

Three measurements against one seeded dataset:

- **sequential** — a full `iterate()` over all N rows, draining values. Milliseconds per
  row. This is the 1.0 denominator by definition.
- **batched random point read** — R random keys read through `getMany`, paged at
  `ROW_RESOLUTION_BATCH` (read the imported constant, never restate 256), because that is
  the path `StoreTableScan` actually takes when it resolves index entries to rows. A naive
  `get` loop would price a path the engine never takes. Milliseconds per row.
- **single-key seek** — R separate `iterate({ gte, lt, limit: 1 })` calls, one per random
  key, each drained and closed. That is literally what `scanMultiSeek` does per seek
  window. Milliseconds per key.

**All three arms live in ONE benchmark per dataset size, not three.** The harness forks a
fresh process per benchmark, so three separate rows would compare three medians taken in
three processes with three different page-cache and block-cache histories — for a
disk-backed measurement that is the wrong experiment. One `fn` call performs one round of
all three arms against the same dataset in the same process; the harness's calibration
gives roughly a second of rounds; `teardown` takes the median per arm across rounds and
reports the two ratios.

Consequence to state plainly in the benchmark's comment: the harness's own median for these
rows is the cost of one whole round and is **not** the interesting number. The interesting
numbers are the per-arm milliseconds-per-operation and the two ratios.

## Reporting the ratios

Report them explicitly. A reader must not have to divide two table cells to get the number
the planner consumes.

Print them from `teardown` — `run.mjs` forwards each worker's stdout to the human stream
live, so a small block of `arm / ms-per-op / ratio` lines lands in the run output under the
row it belongs to.

Deliberately **not** in a `counters()` block: counter values are compared with no tolerance
and no noise floor because they are exact machine-independent integers, and a wall-clock
ratio is neither. Putting one there would report a "counter change" on every single run.
Record that reasoning at the site, so the next reader does not helpfully "fix" it.

## Cache-warm versus cache-cold, stated honestly

The cold/warm distinction is the whole question for a disk-backed store, and it must be a
declared property of each benchmark rather than an accident of run order. Two dataset
sizes: one comfortably inside the cache and one well outside it. The IndexedDB run found
the small size hid the effect entirely, which is exactly why both are needed.

**Be precise about what "cold" means here, because the obvious claim would be false.**
There is no portable way to drop the OS page cache from Node, and a dataset large enough to
exceed a modern machine's *page* cache cannot be seeded inside a benchmark's time budget.
What is achievable, and what these two sizes actually separate, is LevelDB's own **block
cache** (`classic-level` defaults to 8 MB):

- the small dataset fits inside it, so random reads are served in-process;
- the large dataset is well past it, so random reads go out to the filesystem — which on a
  warm machine usually means the OS page cache, not the physical disk.

Say exactly that in the benchmark's comment and in `docs/benchmarking.md`. A claim of
"cold" that is really "block-cache-miss, page-cache-hit" is worse than no claim. Suggested
sizes: 20 000 rows (≈4 MB of values, matching the IndexedDB harness's small size) and
200 000 rows (≈40 MB). Confirm the seed time for the large size fits well inside
`BENCH_TIMEOUT_MS` (120 s, which covers `setup`) before settling on it, and put the row
count in each benchmark's name.

## Then decide, and record the decision either way

The output is two ratios at two dataset sizes. Both outcomes are a result:

- **Near parity** (~1.0 and ~0.5): declare nothing, and record the measurement in
  `packages/quereus-plugin-leveldb/README.md` with the date, machine and dataset sizes, so
  the next person does not re-ask. LevelDB reads in-process through a block cache, so this
  is the likely outcome and it is not a wasted measurement.
- **Far from parity**: declare the measured `costProfile` on the LevelDB provider.

Either way, cross-reference `debt-leveldb-cost-profile-measurement` rather than duplicating
its reasoning, and note in the handoff that it collapses to "read the numbers and decide".
Do not close that ticket from here — the decision is a separate, deliberate act.

# Edge cases & interactions

- **These rows are informational**, through the same flag the prereq builds. They must not
  enter any ratio guard or any pass/fail verdict.
- **The `store` suite has no backend dimension** and its names carry no `@` suffix — see
  its file header. These arms are new named benchmarks in that suite, not a backend
  expansion of existing ones.
- **`skip()` composes from two reasons here**: `@quereus/store` not loading (the suite's
  existing `skipUnlessStoreLoads`) and the LevelDB opt-in being absent or the plugin failing
  to load. Both must reach the row as a stated reason.
- **Seed writes should go through `KVStore.batch()` directly**, not through SQL — the
  measurement is about reads, and a SQL seed would put the engine and the isolation overlay
  in the setup path for no gain.
- **Wall-clock.** Size the arms so no benchmark approaches the 120 s per-benchmark timeout,
  remembering that it covers `setup` (the seed) as well as the timed loop. Calibration
  checks `minSamples` (5) before `maxTotalMs`, so five rounds plus warmup (minimum 2 calls)
  is the floor. Pin anything that still runs long, with the reason written down.

# Tests

- With `QUEREUS_BENCH_LEVELDB` unset, both rows print a skip reason naming the variable.
- With it set, both rows complete and the two ratios appear in the run output at both
  dataset sizes.
- Afterwards the OS temp directory contains no `quereus-bench-*` directories, including
  after an interrupted run.

## The pieces, and their exact signatures

- `createBenchLevelDBProvider(label)` (`bench/lib/leveldb-backend.mjs`) returns
  `{ provider, temp }`. **The caller owns the close order**: `await provider.closeAll()`
  first (that is what releases LevelDB's exclusive directory lock), then `temp.remove()`.
  Getting this backwards fails on Windows. `openLevelDBDatabase` in the same file is the
  worked example on both its success and its failure path — but it builds a `Database`,
  which these arms deliberately do not want.
- `levelDBSkipReason()` (same file) returns the opt-in / load-failure reason or `null`.
  Compose it with the suite's existing `skipUnlessStoreLoads`: return the store reason if
  there is one, else the LevelDB reason. Both must be able to reach the row.
- `loadStoreKeyApi()` (`bench/lib/store-counters.mjs`) resolves `encodeCompositeKey` and
  `ROW_RESOLUTION_BATCH` through the harness's single dynamic `@quereus/store` import.
  It does **not** expose `incrementLastByte` — see the seek-window note below.
- `provider.getStore('main', '<table>')` hands back a `KVStore` directly. On this provider
  every store is a sublevel of one shared physical root.
- `LevelDBStore.iterate` honours `options.limit`; `getMany` is `abstract-level`'s native
  multi-get; `batch()` is a per-store chained batch — **not** the provider's
  `beginAtomicBatch`, so the `syncCommits: true` fsync-per-commit default does not apply
  to the seed. Seeding through `KVStore.batch()` is therefore cheap.

## Design questions already settled

**The single-key seek window.** Use `{ gte: key, lt: key ‖ 0x00, limit: 1 }`. Appending a
zero byte is a correct exclusive upper bound here without needing `incrementLastByte`
(which is not reachable through `loadStoreKeyApi`): `key` is a byte-prefix of `key ‖ 0x00`
so it sorts below it, and every other stored key differs from `key` *within* `key`'s own
length — composite-key column encodings are self-delimiting, so no stored key is a proper
prefix of another. Assert each seek drained exactly one entry; that is what catches the
argument being violated if the key shape ever changes.

**Two disjoint random key sets, not one.** The batched-`getMany` arm and the seek arm must
draw from *different* random keys. With one shared set the `getMany` arm pulls those blocks
into the block cache and the seek arm that follows it in the same round then measures a
cache hit, which is exactly the thing the large-dataset row exists to avoid claiming.

**Arm order within a round: sequential, then batched read, then seeks.** The sequential
full scan is both the 1.0 denominator and the within-round cache buster — at the large size
it streams ~40 MB through an 8 MB block cache (`classic-level`'s default `cacheSize`; the
provider does not override it) and evicts what the previous round's random arms left
resident. At the small size nothing is evicted, and that *is* the small row's finding.

**Seed the random draw deterministically** (a small seeded PRNG in the suite file), so two
runs on one machine draw the same keys and the numbers are comparable.

**Discard the first round from the per-arm medians.** Calibration's minimum is 8 rounds —
2 warmup calls (`CALIBRATION.minWarmup`) + 1 batch-sizing call + 5 samples
(`minSamples`) — so dropping one leaves at least 7. Guard the degenerate case (fall back
to every recorded round) rather than dividing by zero.

**`counters()` stays absent, and the reason belongs at the site** — as the ticket says.
Also worth knowing: a `counters` key that is present but not a function is rejected by
`bench/lib/discover.mjs`, and `informational` is validated as a *strict* boolean there, so
a truthy non-boolean would leave the row gated. Declare `informational: true` literally.

**Where the printed block actually lands.** `child.mjs` runs `teardown` and *then* sends
the result; `run.mjs` prints the row when the result arrives. So the block appears
immediately **above** its row, not under it. The ticket body above says "under" — correct
that when documenting.

**Be accurate about what the seek arm prices.** The real `scanMultiSeek` iterates a window
per seek key on the **index** store with `{gte, lt: incrementLastByte(gte)}` and **no**
`limit`; `scanMultiSeekPrimary` does not iterate per key at all — it batches through
`getMany` on the data store, the same path the `getMany` arm already prices. So the seek
arm prices *the shape* of one seek window (position an iterator, drain it, close it), not a
literal transcription of a call site. Say that in the comment rather than claiming
otherwise.

**Sizes and wall clock.** 20 000 and 200 000 rows × 200-byte values (≈4 MB and ≈40 MB), a
fixed random-key count shared by both sizes so the read arms stay comparable across them.
Seed in chunks (a few thousand operations per `batch()`), never one 40 MB batch. The
per-benchmark timeout is 120 s and it covers `setup`, so confirm the large row's
seed + 8 rounds against it once the numbers are real; pin `iterations`/`warmup` only if it
runs long, with the reason written down.

**Row shape.** 200-byte values, first 4 bytes the big-endian ordinal and the rest
deterministic filler, keyed by `encodeCompositeKey([BigInt(i)], { collation: 'BINARY',
normalizers: BUILTIN_KEY_NORMALIZER_RESOLVER })` over a single integer column. The
IndexedDB harness used a bare 4-byte big-endian ordinal as its key instead — note the
difference in a comment; it is a few bytes of key against a 200-byte value.
